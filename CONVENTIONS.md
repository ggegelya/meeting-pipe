# Conventions

Patterns this codebase uses consistently. Match them rather than inventing parallel ones. For terminology, see the [Glossary](./ARCHITECTURE.md#glossary). For the subsystem map, see [`ARCHITECTURE.md`](./ARCHITECTURE.md).

## Cross-cutting

### Comments policy

Default to no comments. Write one only when:

- A surprising constraint isn't visible from the code (a macOS-specific quirk, a race-condition workaround, a deliberately-non-obvious choice).
- An invariant must be preserved by the reader and isn't enforced by types.

Don't write what the code does (the names already do that). Don't reference the current task (`// E5 fix`), the bug ticket, or "added by …". Those rot.

### No em-dashes

Use hyphens, commas, or rewrite. Applies to code, commit messages, docs, PR bodies, anything you produce here.

Two enforcement points, each with two layers:

- CI: the `conventions` job in [`.github/workflows/ci.yml`](.github/workflows/ci.yml) fails the build on any em-dash in an added line (diff-based, so untouched legacy lines aren't flagged) AND on any em-dash present at all under `daemon/Sources` / `daemon/Resources` (whole-file, TECH-UI-2). Both match the raw U+2014 bytes via `LC_ALL=C grep -F` on an ANSI-C escape, with a matcher self-test; the old raw-character `grep -P` form went silently dead and let em-dashes through (repaired 2026-07-13).
- Pre-commit (local): [`scripts/pre-commit`](scripts/pre-commit) fires the same two checks at commit time. Install once with `ln -sf ../../scripts/pre-commit .git/hooks/pre-commit`. Without it, a violation only surfaces as a late CI red after the push, so install it.

### Truth fences (CI5)

Three classes of drift are checked mechanically by [`scripts/truth_fences.py`](scripts/truth_fences.py), run as the `truth-fences` CI job. All three go wrong *by omission*, which is why they are whole-state checks and not diff-based: nothing gets added when a knob quietly stops being read, so there is no added line for a diff guard to flag.

**Config keys.** The keys documented in `config.example.toml` (including commented-out ones, which still show the user the knob) and the README's Configuration reference are diffed against the keys the two readers actually parse: `ConfigStore.swift` (both the subscript reads and the `ensureTable` write-back; since ARCH9 the one Swift reader, `Config.swift` being a value it produces) and `config.py`'s pydantic models. Three ways to fail:

- a documented key nothing parses,
- a parsed key documented nowhere,
- a **dead knob**: parsed and persisted, but nothing anywhere reads the value. This is the END4(b) class, and it is the one a documented-versus-parsed diff structurally cannot see, because a dead knob *is* parsed, persisted, and rendered as a live Preferences control. The check is deliberately conservative: only reads through a config receiver (`cfg.x`, `configStore?.x`, `self._cfg.x`) count, assignments do not, and the Preferences UI is excluded, because rendering a control is what makes a dead knob convincing rather than evidence it drives anything.

Plus a completeness axis: a key in the README reference but not in `config.example.toml`, since the example file is what people copy.

**Event categories.** Every `Log.event` / `events.emit` category literal is diffed against the `### Categories` table below, in both directions, and action literals are checked for snake_case.

**`CLAUDE.md` entry length (DOC14).** Unlike the two above this is not prose-versus-code drift; it is prose-versus-attention. Those files are prepended to every prompt in their subtree, so a paragraph added to one is re-read on every turn forever, and nothing noticed `daemon/CLAUDE.md` going 3.8 KB to 71 KB in three months. The split it enforces: **`CLAUDE.md` carries the rule and a link, the sibling `docs/gotchas.md` carries the incident**, and only the first is resident.

The check is per *entry* (a `- ` bullet or a `| ` table row), not per file, because that is what separates a rule from a story without punishing a file for having many legitimate rules. The two populations do not overlap. Measured across all four files on 2026-08-16, a rule stated as one imperative line plus a link runs 160-680 bytes, while a bullet carrying its own narrative runs 1,100-3,300; `CLAUDE_MAX_ENTRY_BYTES` is 800, in the empty gap between them, so the fence fires on narrative and never on a rule. Failures are line-precise. `CLAUDE_MAX_BYTES` (24 KB) is a loose whole-file backstop for the far end, where every entry is a fair rule and there are simply too many to read on every turn; the answer there is to ask whether the subtree wants splitting. **Raising either number is not the fix.** Checked-out dependencies under `.build/` and parallel sessions' copies under `.claude/worktrees/` are skipped.

The script's three allowlists exist for known drift a named backlog task will clear, and **all three are empty** as of HYG2 (three dead knobs), DOC9 (eleven keys `config.example.toml` never showed) and DOC14 (the two subtree `CLAUDE.md` files, split onto their `docs/gotchas.md` siblings). That is the intended steady state. **A stale allowlist entry fails too**, so a list can neither outlive the drift it describes nor quietly absorb new drift; anything not listed fails from the day it appears.

Not mirrored into `scripts/pre-commit`: the whole-state scan takes ~2.7 s, which is too slow for every commit. Same call as the DSN3 token guards, which are also CI-only.

### Commits

```
<ID>: <short summary>          # backlog tasks
fix(<scope>): <summary>        # bug fixes
feat(<scope>): <summary>       # features outside the backlog
chore(<scope>): <summary>      # tooling, docs, deps
perf(<scope>): <summary>       # perf work
test: <summary>                # test-only changes
```

One logical change per commit. Subject line is enough for most commits; add a body only when *why* isn't obvious from the subject. Body lines wrap at ~72 chars.

Git identity: commit with the repository's configured git identity (`git config user.name` / `user.email`). Do not hardcode a personal name or email.

### Logging: `Log.event` vs `Log.writeLine`

Two functions, two purposes. Don't mix them up.

| Use | When | Consumers |
|---|---|---|
| `Log.event(category:action:attributes:)` | Anything a script will grep — state transitions, lifecycle, errors with structured context. snake_case action names. | `events.jsonl`, `mp logs`, `mp analyze-detection`, the dogfood scripts. |
| `Log.writeLine(_:_:)` | Free-form narrative for a human tailing the file. Sentences, not key-value pairs. | The per-category text logs in `~/Library/Logs/MeetingPipe/<category>.log`. |
| `Log.verbose(_:_:)` | OBS6: narration at a decision point (browser admission, reprompt cooldown, end hold opened and confirmed, mic capture format) that only matters when investigating. Written only while Preferences ▸ Advanced ▸ Verbose logging is on, read live. Never a failure (those stay unconditional), a title, a name or transcript text. The pipeline's twin is `MP_VERBOSE=1`, which `mp.verbose.configure` turns into the `mp` logger at DEBUG (never the root, so `httpx` stays at INFO). | The same per-category text logs. |
| `Log.failure(category:action:error:attributes:file:describe:)` / `(…reason:…)` | OBS1: anything that failed. One call writes the event row (the caller's attributes plus `error`, the description capped at 300 characters, and `error_domain` / `error_code` from the bridged `NSError`, which for a Swift enum is its module-qualified type name and case index), a `<file>.log` sentence (`daemon` by default, `recorder` at capture sites), and one os.Logger `.error` with the action, domain and code public and the description private. The `reason:` form is for a failure with no `Error` (`mp` not found, a watchdog's kill) and has no domain or code. `describe: false` keeps the description out of both files, for an error that can quote a name the owner chose (SEC38; the export copy uses it). A snake_case action named for what failed (`backup_schedule_failed`, `failure_sidecar_write_failed`), `stem` or `file` (a file name, never a full path) as attributes; categories from the table below. | `events.jsonl` and `<file>.log`, so Diagnostics, `mp logs` and `mp doctor` see it. |
| `Log.main.info` / `.warning` / `.error` | os.Logger for the unified system log. Use sparingly; the jsonl + writeLine surfaces are usually enough. **A failure is never os.Logger alone** (OBS1): os.Logger stores the reason as `<private>`, keeps about a week, and nothing in the app reads it. `LogFailureTests` fails on a `.warning(` / `.error(` outside its allowlist (non-failure notes, the two per-buffer capture writes REC22 counts, and sites already paired with an event, each with its reason). | Console.app, `log stream`. |

Most start/stop/error sites pair an event line (structured) with a writeLine (readable). Pipeline-side uses `mp.events.emit(...)` from `events.py`, same split.

### Error propagation

Throwing functions for in-module calls, `Result<T, Error>` at protocol/API boundaries. Each subsystem declares its own nested `enum X: Error, LocalizedError` (see `MeetingRecorder.RecorderError`, `PipelineLauncher.LaunchError`, `MeetingLibraryService.LibraryError`). There is no unified `MeetingPipeError`. Keep localized descriptions concise. UI failures use `FailurePresentation` and `FailureNotice`/`FailureDialog`; retain `PipelineLauncher.diagnostics(for:)` and optional `FailureMetadata` instead of flattening a process failure to its caption (UX80). Raw text belongs in Details and local logs.

Never `NSError(domain:code:userInfo:)`. A hand-rolled domain string plus `code: 1` carries no meaning a caller can branch on: `MeetingLibraryService` had eleven of them where "the file is missing" and "you typed nothing" were both code 1 in one method and both code 2 in another (ARCH4 replaced them with named cases).

### Test file naming

`<TypeUnderTest>Tests.swift` in `daemon/Tests/MeetingPipeTests/`. One test file per production type that has logic worth unit-testing. Suite class is `final class <TypeUnderTest>Tests: XCTestCase`. Pure-logic tests don't import AVFoundation / NSWorkspace — see the "Testability via clock and decision injection" pattern in Swift section.

Pipeline-side: `test_<module>.py` next to the module under `pipeline/tests/`.

### Dependencies

Don't add packages without asking. The dependency surface is deliberately small. Same for tools (don't pull in a new linter, formatter, or test runner).

### Secrets (macOS Keychain, SEC8)

Four managed API tokens live in the macOS login Keychain, not a file: `ANTHROPIC_API_KEY`, `NOTION_TOKEN`, `HF_TOKEN`, and `OPENAI_API_KEY` (the last joined with the `openai` backend in PROV1). Only the ones your configured backends and sinks need are ever set; the list is one source of truth on each side (`KeychainSecrets.managedKeys`, `mp.config.MANAGED_SECRET_KEYS`) and both the backup manifest and the SEC14 env scrub iterate it, so adding a fifth means editing those two constants and nothing else. Three trees touch the same items and must agree on the naming:

- Swift daemon: `KeychainSecrets` / `SecretsStore` (reads at startup; each Preferences save writes only the accounts that changed).
- Python pipeline: `mp.config.load_secrets` / `_keychain_get`.
- `scripts/install.sh` (prompt + migrate a legacy `secrets.env`) and `scripts/uninstall.sh --purge` (delete).

Contract: generic-password items, **service `com.meetingpipe.daemon`**, **account = the env-var name**. Every tree shells out to `/usr/bin/security` (never the native `SecItem` API), so a single stable accessor owns the item ACL: no per-access Keychain prompt, no per-rebuild cdhash churn.

```sh
security add-generic-password -U -s com.meetingpipe.daemon -a ANTHROPIC_API_KEY -w <value>   # the manual form; the daemon and install.sh send it on `security -i` stdin
security find-generic-password    -s com.meetingpipe.daemon -a ANTHROPIC_API_KEY -w
security delete-generic-password  -s com.meetingpipe.daemon -a ANTHROPIC_API_KEY
```

**The token never rides an argv (SEC23).** The daemon (`KeychainBackend.set`) and `scripts/lib/keychain.sh` (`kc_set`) start `security -i` and write the one `add-generic-password` line to its stdin, so `ps` shows only `security -i`. Inside double quotes `security -i` honours a backslash escape and expands nothing; only `\` and `"` are escaped, and a value with a newline, control byte or non-ASCII byte is refused rather than guessed at. A read is typed on every side: found, not found (status 44), or unreadable (any other status: locked, ACL denied, `security` not runnable). An unreadable account is never written or removed on the strength of an empty field, a remove that fails is an error, and a `secrets.env` migration (daemon and `install.sh` alike) deletes the file only once every managed key in it is stored. The daemon logs `keychain_read_failed` (`main` category, `account` and `status`, never the value) for an account it could not read at launch.

**The daemon's own environment carries no API token (SEC23), `HF_TOKEN` excepted** (the model downloader reads it from there). `SecretsStore` holds them; `PipelineLauncher.runMP` hands a spawn the persisted ones its SEC5 policy keeps, and the spawns that call `freshEnvironment()` bare (doctor, MCP status, the local-model check) get none, as do the ffmpeg spawns (`Secrets.scrubbedEnvironment`). A Python child that needs a token reads it from the Keychain itself (`load_secrets`); a hand-run `mp` does the same. Under a zero-egress run the daemon's SEC5 strip is no longer undone: `load_secrets()` declines to refill once `egress_guard.is_armed()`, and `arm()` pops any token that did arrive (SEC13). The httpx transport patch remains the network-layer backstop underneath that.

## Swift — `daemon/`

### Testability via clock and decision injection

Pure logic lives in its own type with explicit inputs (a `Date`, a `Bool`, a function pointer) so XCTest can drive it without AVFoundation, NSWorkspace, or TCC. Examples in repo:

- `MicGate.decide(state:)` - pure precedence over the fused mute signals, no AX or CoreAudio dependency. Test feeds synthetic probe states.
- `MuteSourceFusion.accepts(source:now:lastLogReadingAt:freshness:)` - which app-mute oracle wins when Teams' SlimCore log and the AX scrape both speak (MIC8), taking the clock as an argument so the precedence is a table test rather than a sleep. `SlimCoreMuteLog` beside it is the same split applied to a file format: the line parse, the family resolution, and the byte-range tail are functions of their arguments, so `LogMuteAdapter` is left holding only the timer and the queue hop.
- `AudioRetention.decide(...)` - pure keep / compress / drop verdict over a meeting's age and workflow policy, no filesystem dependency (STOR1).
- `WorkflowMatcher.match(source:workflows:)` — pure function, full unit coverage.
- `StatusBarModel.derive(_:)` - the menu-bar title, icon, header, and conditional rows from a snapshot of state + permissions + download + counts, no `NSStatusItem` (T3).
- `NotificationRouter.route(id:action:isDefault:doneEntry:)` - which delegate calls a notification response makes, no `UNUserNotificationCenter` (T3).
- `SearchIndexReconciler.decide(indexed:live:)` - the FTS upsert/delete diff, no SQLite and no filesystem (T3).
- `SearchIndexReconciler.mayApply(liveCount:indexedCount:scanListedDirectory:)` - whether a reconcile may apply its diff at all: an empty live set beside a non-empty index is believed only from a scan that listed a readable folder (PERF20).
- `PrepDisclosure.decide(card:expanded:pillHeight:maxCardHeight:width:)` - how tall the detection prompt stands with the "Last time" card open and whether that card scrolls, from the card's measured-at-width row layout and two constants, no `NSPanel` (UX34, width-threaded by UX47). Its sibling `PrepDisclosure.fadeVisible(contentHeight:viewport:offsetY:)` is the scroll cue's rule: the card's bottom fade shows only while content remains below the viewport, and lifts within 2pt of the bottom so the last row reads complete.
- `TutorialPlan.entry(for:presented:)` and `TutorialSpotlight.card(for:in:size:)` - the guided tour's two decisions (FEAT15): which surface has to be opened before a step, and where the narration card goes so it never covers the control it describes. Both pure, so the cases that matter (Back crossing a window boundary, a full-height rail with no room above or below) are testable without a screen. `TutorialSpotlight.focus(_:frames:viewport:)` is the third, folding "never reported", "reported at zero size" and "reported off-viewport" into one `.missing` verdict, because all three read identically to someone watching a tour ring nothing.

- `WindowActivationManager` (UX39, UX48) - the same seam where the logic is a *sequence* rather than a verdict, so there is nothing pure to extract: the six AppKit effects (set the activation policy, activate, hand activation off, install the main menu, remove it, hop to the next run-loop turn) are injected as closures, and the window arrives as an `ActivatableWindow` that `NSWindow` satisfies unchanged. The test records every effect and every window call in one ordered log and drains the run-loop hop by hand, which is what lets it assert that the policy flip precedes the fronting, that the fronting is never deferred and that a raise instead queues exactly one activation for the turn after it (UX56), and that the menu bar goes up and comes down with the policy rather than per window. Every defect it fixes is invisible to a "was it called" assertion. `MainMenu` beside it is the same shape one level down: `MainMenuHolder` is the one-property protocol `NSApplication` already satisfies, so a test can hand over a fake and see whether a second install replaced the menu or appended a second copy.

When a subsystem grows non-trivial conditional logic, lift the decision into a `decide(…)`-style entry point on its own type before adding the next branch.

### Lazy properties and `Self.`

```swift
// Wrong — fails on Swift 5.9+ "covariant 'Self' in stored property initializer".
private var icon = Self.makeIcon(size: Self.size)

// Right — fully-qualified class name.
private var icon = StatusBarController.makeIcon(size: StatusBarController.size)
```

The `lazy var` form (`private lazy var icon = …`) avoids the error too but defers init past the constructor — only use lazy when that's actually what you want.

### `ObservableObject` + Combine

- `@Published` properties auto-fire `objectWillChange`. Wire subscribers via Combine on `didPersist` / dedicated PassthroughSubjects rather than `objectWillChange` directly — fewer spurious rebuilds.
- Debounce writes through `DebouncedSaver` (CONC8): the store snapshots on main, the write runs on the saver's utility queue, the result comes back on main. `Timer.scheduledTimer(withTimeInterval: 0.5` appears only there.
- Round-trip TOML through `TOMLTable` so unknown keys survive (`ConfigStore.rawDocument`). Don't model fields you don't need.

### Status bar / menu rebuilds

Build the status menu when it opens, and at no other time. `StatusBarController` assigns one `NSMenu` at init and `menuNeedsUpdate` repopulates it in place; state, queue, permission and download setters update the title and icon and record the state the next open builds for (`rebuildMenu(state:)`, a name UX79's fence keeps), and build nothing. Anything the menu shows that costs a disk listing or a subprocess is a cached value refreshed off main: the open shows the cache, starts the read, and repopulates the open menu only if the value moved (PERF24: the failed count and the launch-agent state). Before PERF24 every setter built a whole menu, listing `raw/` each time, including every 2 s download tick, and the open threw it away; before that the 2 s permission poll rebuilt it twice a second.

### Tests need full Xcode

`swift test` from the command line errors on `import XCTest` if only Xcode Command Line Tools are installed. CI runs on `macos-14` with full Xcode. Write tests anyway; verify locally with the Xcode test runner, or `swift test` once full Xcode is set as the active developer dir (`sudo xcode-select -s …`).

### Shared test support (T13)

`daemon/Tests/TestSupport/` is the `MeetingPipeTestSupport` target, a dependency of both test targets. It holds `ManualScheduler` (the one hand-cranked stand-in for every `Scheduler` seam: every uncancelled registration stays live, `fire()` for a one-shot timer, `tick()` for a repeating one), `waitUntil(timeout:_:)`, `yieldRunway()`, `drainMain()` / `drainMainSync()` and `FakeFFmpeg` (T15: executable stand-in scripts, `script`, `copying` and `writingNothing`, handed in as `ffmpegPath:` or through `MEETINGPIPE_FFMPEG`). It imports Foundation only, never XCTest, because a plain `swift build` compiles every regular target and Command Line Tools have no XCTest. A double that needs an app module lives in that target's `Support/` folder instead: `FakePipelineDriver` (the one `PipelineDriver` fake) and `FakeMuteAdapter`. Use these rather than a file-local copy; nine schedulers and seven drivers had drifted apart before this existed.

**Wait on a condition, never on a yield count or a sleep.** A count is a guess at how many hops the work takes and goes vacuous when an `await` is added or the pool's width changes. Use `waitUntil { condition }` and assert its answer; the condition must be false before the awaited work starts. `yieldRunway()` is only for proving something did **not** happen. A test that converts to `waitUntil` becomes `async` and must be `@MainActor` when the code under test asserts the main queue. Load a resource in a throwing `setUpWithError()`, never with a force-try in a static initialiser, which kills the whole xctest run instead of failing one suite.

## Python — `pipeline/`

### Stdlib first

Reach for `pathlib`, `dataclasses`, `argparse`, `subprocess`, `json` before pulling in a dep. The pipeline ships pydantic for schemas, anthropic + httpx for the API, mlx-lm for the local-summary backend, and soundfile + numpy for the channel-aware speaker fallback. That is it.

### Lazy heavy imports

Top-of-file imports stay stdlib + light deps. The heavier imports the pipeline still has (`mlx_lm` for the local-summary backend, `soundfile` and `numpy` for the channel-aware speaker fallback in `diarize.py`) live *inside* the function that uses them:

```python
def summarize(self, transcript: str) -> MeetingSummary:
    from mlx_lm import load  # heavy; defer until the local backend runs
    ...
```

Why: `mp --help` and `mp logs` shouldn't pay an import cost they do not need. The Linux CI runner never installs the darwin/arm64-only mlx stack (platform markers in `uv.lock`), so a top-level `mlx_lm` import would fail there at collection time.

### Subcommand pattern

Each `mp <name>` lives in `pipeline/src/mp/<name>.py` exposing `def main(argv: list[str]) -> int`. Register in `pipeline/src/mp/__main__.py` with both the dash-form and snake-case alias:

```python
if cmd in {"my-cmd", "my_cmd"}:
    from .my_cmd import main as run
    return run(rest)
```

Use `argparse` inside `main`; don't share argparse instances across modules.

**Ctrl-C is handled once, at the router (PIPE13).** `__main__.main` wraps the dispatch ladder in a single `except KeyboardInterrupt`: it prints one line to stderr naming the interrupted command and returns `EXIT_INTERRUPTED` (130, the shell's `128 + 2` for SIGINT). That one place covers every subcommand precisely because they all arrive through `main(argv) -> int`, so no subcommand catches interrupts itself, and a supported way to stop a long run stops looking like a crash. Two things about it are load-bearing:

- **It does no cleanup, and must not grow a `finally`.** What the interrupt leaves on disk is the point: `mp ask` checkpoints its embedding index as it builds (AI11), so a Ctrl-C mid-build is what the next run resumes from (owner-verified 2026-07-31, interrupted at 112 stems and resumed at 112). A handler that tidied state or removed a partial index would break that silently, and the damage would surface only on the *following* run.
- **130 stays outside the exit vocabulary the daemon reads.** 3 is the all-sinks-failed publish contract, 2 is usage, 1 is any other failure; `SinkDispatcher.stage(for:)` branches on 3 alone, so 130 falls into its generic arm and reads as a plain pipeline failure. Adding a case for it there would be a new contract, not a clarification.

Only `ask` adds a clause about what survived (`_INTERRUPT_NOTES`), since the resume is the non-obvious half after a long build; every other command gets the bare line.

**SIGTERM unwinds, and exits 143 (PIPE22).** The daemon's Cancel and its watchdog both SIGTERM `mp`, and Python's default disposition killed the interpreter without running a single `finally`, so a Cancel during a local summary left the setsid'd `mlx_lm.server` resident. `main()` installs `_on_sigterm` just before the dispatch ladder: it raises `SystemExit(EXIT_TERMINATED)` (143, the shell's `128 + 15`), which no `except Exception` swallows, so every `finally` and `__exit__` runs and `LocalSummaryClient.close()` kills the server. `main` then prints `mp <cmd>: terminated` and returns 143; any other `SystemExit` (argparse's 2) passes through untouched. Three things about it are load-bearing:

- **It is one-shot.** The first SIGTERM swaps in a Python no-op handler before raising, so a second one (the daemon's Cancel followed by PIPE37's stdin-EOF self-signal) cannot abort the cleanup the first one started. A no-op handler rather than `SIG_IGN`, because an ignored disposition is inherited across `exec` by every `ps` and `lsof` child the unwind spawns. The daemon's SIGKILL after its grace stays the backstop.
- **It rolls nothing back, exactly as Ctrl-C does not.** The unwind runs the code's own `finally` blocks and nothing else, and none on `mp ask`'s path discards a checkpoint: `EmbeddingIndex.save`'s `except BaseException` drops only a pair the manifest provably does not name. `test_a_sigtermed_ask_keeps_its_checkpoint` pins that with a real signal.
- **143 is outside the daemon's exit vocabulary**, for the reason 130 is. The daemon reads a Cancel off its own per-run flag (`PipelineLauncher.outcome`), never the exit code, so nothing the Library shows changed.

**A missing managed secret is handled the same way, and for the same reason (PIPE16).** `MissingSecretError` is caught once beside the interrupt handler and returns 2, so every subcommand inherits the fail-fast without any of them learning about it. The contrast with the interrupt is worth keeping in view: the interrupt handler is at the router because nothing below it should act, while this one is at the router because it is the *last* resort, after any stage that owns a real recovery has taken it (the publish fan-out records the sink as failed and runs the rest).

### The entry contract (SEC13)

Any subcommand that can reach a sink, an engine, or a token calls `mp.entry.prepare(...)` before anything else. It resolves the per-meeting workflow overlay, arms the egress guard on the *resolved* config, then loads the Keychain secrets, in that order.

```python
cfg = entry.prepare(cfg, wav)             # a meeting-scoped command
cfg = entry.prepare()                     # library-wide (mp ask, mp digest)
cfg = entry.prepare(secrets=False)        # local-only (mp backup, mp restore)
```

Don't hand-roll the three calls. Arming before the overlay misses `workflow_nda_mode` for every per-meeting NDA workflow; loading secrets before arming leaves the cloud tokens in `os.environ` for the `mlx_lm.server` child to inherit. Both failures are silent.

A tripwire pins this (PIPE8, `test_entry_contract.py`): it walks every dispatch target in `__main__.py` and asserts each module calls `entry.prepare` or sits on a named read-only/diagnostic allowlist, so a new sink-reaching subcommand that forgets to arm is a red build, not a silent leak.

It reads that off the **AST**, and it checks both halves of the contract (CI6). A real `entry.prepare(...)` call node has to exist, so a mention in a docstring, a comment or a `# TODO` no longer satisfies it, which the original `if "entry.prepare" not in src` substring test did. And no call reaching a sink, an engine or a token, meaning a `*Client` / `*Publisher` construction or `load_secrets`, may run above it inside the function that arms, because "before anything else" is the property the triple exists for and ordering was the half nothing checked. Neither half fires against today's tree; the checker is a pure function over source text and its own tests drive it with modules written to break each half, so it is proven to bite rather than assumed to. `test_local_client_contract.py` (LOCAL19) is the same shape one level down.

`config.zero_egress(cfg)` is the single predicate behind every clamp (`effective_backend`, `effective_sinks`, `arm_for_config`, `workflow.apply_overrides`, `publish_notion.publish`). Write new clamps against it, never against `regulated_mode or workflow_nda_mode` directly.

**The library-wide form of `prepare()` has a second half (AUTO3).** With no anchor there is no overlay, so `workflow_nda_mode` can never become true and only the global `regulated_mode` clamps the run. That is a scope fact, not a safe default: it is why `mp ask` and `mp digest` could retrieve NDA text into a cloud prompt for as long as they did. So a library-wide command arms the guard *and* gates its corpus:

```python
cfg = entry.prepare()                              # arms on the global config
allow = visibility.visible_stems(root)             # AUTO3: which meetings may leave
```

`mp.visibility` is the single owner of that per-meeting decision the way `zero_egress` is the single owner of the per-run one, and it is fail-closed (`nda`, `regulated`, `no_sidecar`). Pass the resulting `allow_stems` down rather than filtering results: `chunk_library` / `refresh_index` / `load_or_build`, `actions.discover`, `digest.collect_*`, and every `mcp_tools` function take it, so withheld text is never chunked, embedded, or ranked in the first place.

`mp prefetch-model` is the one command that deliberately never arms: fetching a model is its purpose, and a cached model is what lets a later zero-egress run stay offline.

## Event log schema

Three append-only JSONL files at `~/Library/Logs/MeetingPipe/`:

- `events.jsonl`: written by the daemon via `Log.event(category:action:attributes:)` in `Logger.swift`.
- `diagnostics.jsonl` (OBS9): written by the daemon via `Log.diagnostic(category:action:attributes:)`, and from Core via `EventLog.emitDiagnostic`, same envelope and categories. It holds the high-volume rows whose only use is investigating a storm: `halbus` / `subscribe_attempt`, `subscribed`, `unsubscribed`; `signal` / `process_audio_object_resolved`, `process_audio_object_unresolved`; `coordinator` / `call_teardown_source_missing`. Those three families were 79.5 percent of `events.jsonl`'s bytes on the work laptop and held its history to 46 days; without them it grows about 34 KB a day, which is the order of 600 days in the same four files. The failure rows beside them (`subscribe_failed`, `unsubscribe_failed`, `call_teardown_source_recovered`) stay in `events.jsonl`. A reader of a moved row reads both families: `scripts/extract_detection_trace.py`, `scripts/dogfood_report.py`, `mp logs` and the Diagnostics window do; a new row that fires per poll or per HAL change belongs here, not in `events.jsonl`.
- `pipeline_events.jsonl`: written by the pipeline via `mp.events.emit(category, action, **attrs)` in `events.py`.

All three self-bound by size (PERF7). A file that reaches ~5 MiB rotates `foo.ext` -> `foo.1.ext` (index before the extension so it stays valid JSONL), shifting older generations up and dropping the oldest past 3 backups; `diagnostics.jsonl` keeps one backup (`Log.diagnosticGenerations`), since it is allowed to be short. launchd's `launchd.err.log` and `launchd.out.log`, which nothing else bounds, are rotated by the daemon at launch through `Log.rotateIfNeeded` (OBS9): launchd opened them before the process started, so the running daemon writes on into the renamed generation and the next spawn gets a fresh base. The same size cap covers the four tail-able text logs (`main.log`, `daemon.log`, `recorder.log`, `pipeline.log`). Both sides own the rotation of their own files: `Log.rotateIfNeeded` in Swift (run under the write lock before every append, `pipeline.log` included) and `mp.events.rotate_if_needed` in Python (called before each open-for-append, which for `pipeline.log` happens only on a hand run, since a daemon-spawned run leaves that file to the daemon, PERF13); the cap is `MEETINGPIPE_LOG_MAX_BYTES`-overridable for tests. Readers span the boundary via `Log.logGenerations` / `events.log_generations` (base plus generations, oldest first), so `mp logs` and `mp analyze-detection` keep working on the recent window.

Every line is one JSON object with at least three fields:

```jsonc
{
  "ts": "2026-05-14T15:32:01.234Z",   // ISO8601 with millisecond precision, UTC
  "category": "coordinator",          // see below
  "action": "recording_started",
  "launch_id": "5f0c…",               // daemon rows only (OBS5): one id per process
  // ...arbitrary JSON-serializable attributes
  "bundle_id": "us.zoom.xos",
  "summary_mode": "auto",
  "workflow_id": "0ac61f12-…"
}
```

### Categories

| Source | Categories |
|---|---|
| Daemon (`Log.event` / `EventLog.emit`) | `automation`, `axbus`, `coordinator`, `correction`, `daemon`, `detail`, `detector`, `doctor`, `halbus`, `library`, `lifecycle`, `main`, `micgate`, `perf`, `pipeline`, `recorder`, `recording`, `signal`, `transcription`, `ui`, `workflow` |
| Pipeline (`mp.events.emit`) | `pipeline`, `prefetch`, `publisher` |

This table is fenced: `scripts/truth_fences.py events` diffs it against the category literals at every `Log.event` / `events.emit` call site, in both directions, and CI runs it (CI5). A category emitted but not listed fails, and so does a category listed but no longer emitted.

A run's stages narrate under `pipeline` as `stage_started` and `stage_completed`, each with a `stage` attribute. `stage_progress` (the heartbeat, every 5 s while `run-all` runs) carries `stage`, `elapsed_s`, `beat` and, since PIPE53, `stage_elapsed_s`: seconds since the stage began or since the last unit of real work finished (a model call, a cleanup window), so it alone does not move while the timer thread beats over a hung request; the same key rides the stdout sentinel line the daemon parses. The daemon's `coordinator` / `pipeline_stalled` row (PIPE53) carries `stem` and `phase`: `launch` (no first beat within the launch budget, 120 s), `beat_gap` (beats stopped for 30 s) or `no_progress` (beats continue but `stage_elapsed_s` passed 90 s). A beat re-arms it after a `launch` or `beat_gap` flag; a `no_progress` flag ends when `stage_elapsed_s` drops back under the budget. `transcription` / `transcription_timed_out` (PIPE36) carries `abandoned_outstanding` (PIPE46): how many earlier transcribe-phase passes the deadline abandoned that have not returned when this one expires, each still holding its runner, models and the meeting's sample array. `transcription` / `transcription_late_return` (PIPE46) is one such pass coming back, with `file`, `phase` (`transcribe` or `redact`) and `seconds_after_deadline`; it changes nothing else (no transcript, no spawn), and the count drops on it. A pass that never returns has no row, which is the point: timed out with no late return is the wedge. `model_rejected_fallback` (PIPE28) is what `auto` leaves when it drops to local because the cloud rejected the model id, with `model` and `http_status`. `stage_failed` (PIPE19) is the third: a stage that raised but did not end the run, today only `diarize_cleanup`, with `error` (the exception type) and `message` (its text, capped at 300 characters). A stage that ends the run is `run_failed` instead. Before `stage_failed` existed a failed cleanup left a `stage_started` with nothing after it, which is how it went unnoticed that cleanup never ran on two backends.

`pipeline` appears in **both** rows on purpose. Two things it deliberately does not do, both worth knowing before you trust a number:

- **It is not exhaustive, and cannot be.** Test rows that name no meeting (`coordinator.state_change`, `workflow.migrator_seeded`, `daemon.notion_fetch_blocked`) are byte-identical to real ones and interleave with them in the same window, so no content or time discriminator separates them. They inflate benign counters; they fabricate no failures. A pass through the filter does not mean "the log is clean".
- **Not every reader needs it.** `mp analyze-detection` deliberately does not filter: it pairs `recording_started` / `recording_stopped` / `force_stop` / `mic_busy_*` / `mic_device_unavailable`, and there is not one residue row on any of those actions. `scripts/valid1_check.py --diar` keeps its own `engine` filter rather than delegating, because it also counts and prints what it skipped (`other_engines`) instead of dropping it silently. Check which actions your report actually reads before you add or skip a filter.

### Adding a new action

1. Pick the right category (don't invent one unless you're adding a new subsystem). A genuinely new one goes in the table above in the same commit, or CI5 fails the build.
2. Use snake_case for the action (`recording_started`, not `RecordingStarted`). Fenced: CI5 rejects a dotted or camelCase literal at any `Log.event` / `events.emit` call site. `detail` / `toolbar.action` was the last survivor and is now `toolbar_action`.
3. Add it directly via `Log.event(...)` / `events.emit(...)`. There's no central registry, and deliberately so: actions are ungoverned, only categories and the snake_case rule are fenced.
4. If the pipeline's `mp logs` filter or `mp analyze-detection` cares about it, update them too.

### Non-serializable attributes

Both sides coerce rather than drop (PERF13), so a stray attribute degrades one value instead of losing the whole row:

- Swift: `Log.event` writes a value JSON cannot hold as its string form (a file `URL` as its path, any other `URL` as its absolute string, a `UUID` as its `uuidString`, a `Date` in the log's ISO 8601 form, anything else as `String(describing:)`), recursing into arrays and dictionaries. A non-finite `Double` (NaN, infinity) becomes `null`, and at the top level gains a sibling `<key>_invalid: true` so a NaN stays distinguishable from a value that was absent. It used to return without writing, which `CONVENTIONS.md` documented as intended.
- Python: `default=str` coerces silently. Same outcome.

Still convert first where the string form is not what a reader wants: coercion is a floor, not a format. Don't add try/except scaffolding around emit calls.

### Writing and reading the logs (PERF13)

- **Every Swift append goes through `Log.append`.** One in-process lock covers check-rotate-append, and the file is opened per write with `O_WRONLY | O_APPEND | O_CREAT`, mode 0600, so two threads cannot overwrite each other, double-rotate, or lose a line to a first-create, and a second process appending the same file (the `MeetingPipe doctor` CLI writes `events.jsonl` too) cannot either. Writes are synchronous, so a line is in the kernel when `Log.event` returns: there is no unflushed tail on a crash, and no drain is needed at quit. Don't keep a long-lived `FileHandle` on a log; that is the shape that tore rows.
- **`pipeline.log` has one writer per run.** `PipelineLauncher.runMP` copies the child's stdout and stderr through `Log.append`, one call per chunk, and sets `MP_PIPELINE_LOG_OWNER=daemon` on every spawn; `orchestrate._configure_logging` then adds no `FileHandler` and does not touch or rotate the file. A hand-run `mp run-all` has no flag and keeps its `FileHandler`.
- **Python's rotation is locked (F212, OBS9).** `mp.events.rotate_if_needed` takes an exclusive `flock` on a sibling `<name>.lock` around the size check and the renames and re-reads the size inside it, so the main thread, the `mp-progress` heartbeat and concurrent `mp` processes rotate once between them, and a base another caller already moved is nothing to rotate rather than a raise that lost the row. The append stays outside the lock.
- **Readers count what they skip.** A torn line is skipped, never fatal, and counted: `mp logs` and `mp analyze-detection` print `N unparseable lines skipped` to stderr, and the Diagnostics window shows the count beside its event total.

## Flagged-moment markers (`<stem>.markers.json`)

The moments the user flagged mid-recording, with the flag-moment hotkey or the HUD's flag control (FEAT8, surfaced on the HUD by UX46; both call `MeetingSessionController.flagMoment`, so while a recording runs this file has one writer; after it, `mp merge-meetings` is the only other (PIPE47), folding a later fragment's flags in at its audio offset). A Swift-to-Python surface like `<stem>.meta.json`, but simpler. `MarkerFile.write` (Swift) rewrites it atomically on every flag press and once more at stop (REC26), so a recording that ends without `stop()` (a crash, a kill, a quit, a rebuild relaunch) leaves it beside the intermediates; orphan recovery never removes it, so the recovered final finds it by stem. Two readers consume it: the pipeline (`mp.markers`, where the transcript segments spanning each marker become user-flagged excerpts fed to the summarizer and listed in the BYO / long-meeting paste bundles) and the Library transcript tab (`MarkerFile.read`, rendering anchor chips that seek). Shape:

```json
{ "schema_version": 1, "markers": [ { "t_seconds": 42.5 } ] }
```

`t_seconds` is the offset in seconds from recording start, the same clock the transcript segments use. Written only when at least one moment was flagged, so an unflagged meeting leaves no sidecar. A merge (PIPE47) can add entries to the primary's file, shifted by each fragment's audio offset and deduplicated by offset, so it stays valid across a re-run. Both sides are fail-open: a missing or malformed file yields no flagged moments, never an error. Capture is deterministic (the daemon stamps offsets, the pipeline maps them to segments); the emphasis is model-side (a trusted system-prompt instruction), so a flag adds no new egress class, the excerpts travel to whichever backend already summarizes the transcript.

## Diarization cleanup audit (`<stem>.diarize_cleanup.json`)

What the LLM speaker-cleanup pass (`summarization.diarize_cleanup`, TECH-DIAR1) did to one meeting, per segment. Python-only: `diarize_cleanup.cleanup_transcript` writes it, `scripts/valid1_check.py --cleanup` reads it, and no Swift reads it, so it is not a cross-tree contract. Shape:

```json
{
  "schema_version": 1,
  "segments": 81,
  "labels_before": ["Sudip", "THEM-B", "Prajval"],
  "labels_after": ["Sudip", "Prajval"],
  "labels_eliminated": ["THEM-B"],
  "merges_count": 1,
  "reattributions_count": 0,
  "refusals_count": 1,
  "latency_ms": 900,
  "edits": [
    { "segment_index": 59, "from": "THEM-B", "to": "Prajval", "kind": "merge", "similarity": 0.554 }
  ],
  "refused": [
    { "segment_index": 71, "from": "THEM-D", "to": "Anisha", "kind": "merge",
      "similarity": 0.463, "reason": "voiceprint_distance" }
  ]
}
```

Keyed by the segment's array index, the same join key the two overlay sidecars use. `similarity` is the cosine between the two labels' voiceprints from `<stem>.embeddings.json`, and it is **omitted rather than zeroed** when either label has no embedding, so "allowed because the voices are close" cannot be misread as "allowed because nothing could be measured". `kind` is the model's own word for the edit and nothing validates it; it is recorded for the trail and never acted on (see `pipeline/docs/gotchas.md`).

`reason` on a refused edit is one of three: `voiceprint_distance` (the edits would empty the label, DIAR5), `reattribution_cap` (they move more than `REATTRIBUTE_MAX_FRACTION`, half, of one real label's segments away, counted over every destination, DIAR9), both only when the two labels' voiceprint similarity is below 0.65, and `outside_window` (the proposing window never showed that segment's `[n] speaker:` prefix, DIAR9; one record per index and label, even when another window legitimately relabelled that index; no `similarity`).

Two invariants worth keeping:

- **Written on every run of the pass, including the single-speaker no-op.** Presence means the pass ran; absence means it never did. Those two states have opposite readings for any later question about a meeting's labels, and the aggregate event counts cannot separate them.
- **The pass has a deadline (PIPE24).** `CLEANUP_DEADLINE_SEC` (10 minutes) bounds the whole pass: once it is past, no further window is issued, the edits gathered so far are applied, and the pass returns normally. The `pipeline`/`diarize_cleanup` event carries `windows_done`, `windows_total` and `deadline_hit` so a truncated pass is distinguishable from a complete one; the audit file is unchanged.
- **Rewritten in full, so it describes the last run only.** After a second `mp cleanup-diarization --force` the `from` labels are the first run's `to` labels, and `valid1_check.revert_cleanup` therefore recovers that intermediate transcript, not the finalizer's. That is why, since DIAR9, a transcript already carrying `diarize_cleaned` is skipped without a model call or a rewrite unless `--force` is given; the skip still emits `pipeline`/`diarize_cleanup` with `skipped: "already_cleaned"`.

It exists because the pass emitted only aggregate counts, so no owner correction could be traced to a cleanup edit rather than to a clustering mistake; DIAR5's own demonstration case had to be argued from two sidecars and could not be attributed from disk at all.

## Publish result (`<stem>.publish.json`)

This run's publish outcome (PIPE1). A Python-to-Swift surface: `publish_router.fanout` writes it (atomically) at the end of every fanout, and the daemon reads it back through `PublishResult.load`. Shape:

```json
{
  "schema_version": 1,
  "state": "full",
  "page_url": "https://www.notion.so/...",
  "ts": "2026-07-10T09:15:00+00:00",
  "sinks": { "notion": { "ok": true, "page_url": "https://...", "error": null, "failure": null } }
}
```

`state` is `full` (every sink succeeded), `partial` (some did), `none` (every sink failed, or sinks were configured and none ran because `build_publishers` skipped them, such as an obsidian sink with no vault path), or `local` (no sink was configured at all: the resolved `effective_sinks(cfg)` is empty, either because the workflow has no destinations or because the egress clamp dropped its only sink; WF10). `local` is a settled state, not a failure: Ready on the row, outside Needs you, settled for retention, and exit 0. `fanout` marks it with `no_sinks_configured` on its result, since only it sees the resolved sink list. `page_url` is the first successful sink that produced one, and null for a local-only workflow.

**Write order (PIPE34).** Before any sink runs, `fanout` replaces the file with a marker, `state` `unknown`, `page_url` null and `sinks` empty, so the previous run's outcome is gone before this run can succeed or fail. The final write then overwrites the marker. A final write that fails leaves the marker, never the previous run's file, and is a failed publish (exit 3, `sidecar_write_failed` on the result). A marker that cannot be written falls back to removing the old file; if that fails too, `fanout` runs no sink and the caller exits 3. Swift reads `unknown` like `none`: Unpublished with Republish, in Needs you, not settled for retention, and naming no destination. Either failed write emits `pipeline` / `sidecar_write_failed` with `file` (`run` or `publish`), `error` (the exception type) and `errno`. `<stem>.run.json` follows the same rule from the other side: `corrections.write_run_sidecar` removes the previous run's file when its own write fails, since no run sidecar (unknown engine, not correctable) is honest and a stale one is not; the callers stay non-fatal. `run_all` also removes a leftover `<stem>.apple_pending.json` at start, so the only sentinel the daemon can find after exit 0 is one this run wrote (F054).

Each failed sink may carry a `failure` object using the optional metadata schema below (UX80). Its existing `error` remains local diagnostics. A partial publish preserves successful destinations and exposes failed-destination details in the Library notice.

**`page_url` says what to open; `sinks` says who wrote it.** Swift reads both (`PublishResult.sinks`), because the two questions have different answers and only the map can name a destination for the user: `page_url` is whichever sink came first in `output.sinks` order, so a run that landed in Notion and the filesystem reports one URL and gives no clue which of the two produced it. `PublishLanding.decide` (UX49) is the one reader of that distinction: exactly one sink with `ok: true` is named, more than one is deliberately unnamed ("Open summary"), and a null `page_url` means no open affordance at all rather than a button that cannot open anything. Every local sink returns a `file://` `page_url`, so "has a URL" never meant "went to Notion", which is exactly what the done notification used to say.

The reason this exists rather than the daemon reading the per-sink `<stem>.<sink>.json` sidecars: a publisher that raises never writes its sidecar, so an earlier successful run's `<stem>.notion.json` survives and is indistinguishable from a fresh one. That is how an all-sinks-failed run used to notify "Meeting published" with a stale URL. This file is rewritten on every fanout, so it always describes the run that just finished.

Absent whenever the pipeline short-circuited before publish (no speech, suspect transcript, BYO, long-meeting bundle, Apple hand-off). Absent reads as "nothing published, nothing failed", never as a reason to fall back to a per-sink sidecar.

`state`'s five values (PIPE34 added `unknown`) are a vocabulary, not free text: six Swift sites compare against the bare literals (`MeetingRow`'s badge (`DonePublishBadge`) and its retry-vs-publish action, `AudioRetention.isSettled`, `LibraryScope.needsYou`, `MeetingDetailView+Header`), and a fifth value would make every one of them take the else-branch, rendering a publish that landed nowhere as a clean success. WF10 added `local` as a deliberate cross-tree change, with each site naming it rather than defaulting into it. A golden fixture pins the whole contract across both suites (CI4, below).

**This file is where `Meeting.publishState` comes from (PIPE14), and the two readers of it go through `PublishResult.resolveState`.** They used to read `<stem>.run.json`'s `publish_state` instead, which only `mp run-all` ever refreshes: `mp publish`, `mp merge-meetings` and `mp publish-from-paste` each rewrite this sidecar and touch the run sidecar not at all, so every one of the six branch sites stayed frozen at the last run-all's verdict. A successful Republish could not clear the Unpublished badge, the meeting never left Needs you, and `AudioRetention.isSettled` stayed false so retention never reclaimed the audio. `resolveState` still falls back to the run sidecar when this file is absent, for the meetings recorded before PIPE1 shipped it and for nothing else; it is never preferred, since it cannot be fresher than the file every fanout rewrites.

**All-sinks-failed is an exit code, not just a file.** `mp run-all`, `mp publish`, and `mp publish-from-paste` exit `3` (`publish_router.EXIT_PUBLISH_FAILED`, mirrored by `PipelineLauncher.publishFailedExitCode`) when every configured sink failed, or when the outcome could not be recorded in this file (`publish_router.publish_failed`, PIPE34; `mp merge-meetings` and `mp digest --publish` too). `SinkDispatcher.stage(for:)` maps that exit to `PipelineFailureSidecar.Stage.publish`, which is the one stage whose retry republishes the existing `<stem>.summary.json` instead of paying the summarizer twice. Zero sinks configured is a clean success, not a failure: see `publish_router.all_sinks_failed`, which is deliberately narrower than `publish_state(...) == "none"`. The rest of the vocabulary is 1 (any other failure), 2 (usage, and a missing managed secret), 130 (Ctrl-C, PIPE13) and 143 (SIGTERM, PIPE22); only 3 is branched on across the boundary, so the others reach `.pipeline` as generic failures.

**A missing secret is an exception, and only the boundary turns it into an exit code (PIPE16).** `config.require_env` raises `config.MissingSecretError`; `__main__.main` catches it once and returns 2, the same code its old `sys.exit(2)` returned. That `sys.exit` was the defect: `SystemExit` derives from `BaseException`, so calling it from library code walked through both of `orchestrate`'s `except Exception` handlers and skipped the `run_failed` emit, the exit-3 mapping and the publish-sidecar write at once. The publish stage never gets that far now, because `publish_router._build_one` catches it and returns an `UnavailablePublisher`, so a missing `NOTION_TOKEN` is a recorded sink failure inside the fan-out: the other sinks publish, `state` reads `partial` (or `none` when it was the only sink, which is the ordinary exit-3 path with its `run_failed` and its publish-only retry), and the row can no longer settle on "Ready" for a meeting that landed nowhere. See "Subcommand pattern" above for why 130 is deliberately not a fourth case here.

**A memory failure has no separate exit code (LOCAL16, UX80).** `SinkDispatcher.stage(for:)` recognizes structured `cause: memory` or the legacy `Not enough memory` phrase (`PipelineFailureSidecar.lowMemoryMarker`, case-insensitively). Missing-model fallback still recognizes `not in the local HuggingFace cache`. Keep both legacy signatures for old readers and sidecars. Exit 3 takes precedence over a memory cause because the completed summary can be republished.

### Optional failure metadata (UX80)

`PipelineLauncher` gives each subprocess a unique temporary `MP_FAILURE_PATH` (and, STOR9, an `MP_NOTICE_PATH` beside it for lines the owner should be shown), independent of its stderr tail and of every other process. `mp.failure_details` writes the first caught failure there atomically with owner-only permissions. Command-specific catches retain native evidence before returning: run-all, standalone summarize, Ask, and each publishing destination. The CLI boundary covers unhandled commands. A wrapper cannot replace an inner operation with a less specific one. `describe` classifies on the first link of the explicit `__cause__` chain, outermost first, that matches a known class (PIPE44), and reads the status, body and request id from the first link carrying a response or status; implicit `__context__` is still never followed. No environment variable means no transport file. This metadata is optional; existing exit codes, cancellation, logs, and successful output contracts are unchanged.

The same spawn sets `MP_PIPELINE_LOG_OWNER=daemon` (PERF13): the daemon copies the child's output into `pipeline.log`, so `orchestrate._configure_logging` adds no `FileHandler` of its own when it sees the flag. The constant is `PipelineLauncher.pipelineLogOwnerKey` in Swift and `orchestrate.PIPELINE_LOG_OWNER_ENV` in Python, pinned to each other by `PipelineLogOwnerPERF13Tests`.

```json
{"schema_version":1,"cause":"credits","provider":"anthropic","operation":"summary","remedy":"billing","http_status":400,"request_id":"req_0123456789abcdef"}
```

Required fields are version 1, `cause`, and `operation`. Causes are `credits`, `quota`, `missing_key`, `rejected_key`, `expired_key`, `connection`, `timeout`, `rate_limit`, `service_unavailable`, `model_missing`, `model_rejected` (a 404 or 403 that names the cloud model id, remedy `model`; PIPE28), `memory`, `overlay_unreadable` (summarize refused a present but unreadable speaker-label, correction or marker sidecar, `summarize.OverlayUnreadable`, remedy `retry`; STOR9: the file is named in the stderr line the Library shows, never in the metadata), `publish`, `interrupted`, `cancelled`, and `unknown`. Operations are `summary`, `ask`, `digest`, `publish`, `transcribe`, `processing`, `rename_voice`, `storage`, `integrations`, and `model`. Optional providers are `anthropic`, `openai`, `notion`, `local`, `filesystem`, `obsidian`, `lan`, and `claude_cli`; remedies are `billing`, `integrations`, `model`, or `retry`. HTTP status is an integer from 100 to 599. Request identifiers must be `req_` followed by 8-96 ASCII letters/digits, or a UUID. Unknown optional fields are discarded; malformed required fields, unsupported versions, and metadata of 4,096 bytes or more fall back to a short explanation with diagnostics retained.

The daemon consumes and removes the process file at termination. It remains the sole writer of `<stem>.error.json`, retaining `schema_version`, `stem`, coarse `stage`, raw `reason`, and `ts`, plus optional `failure` containing this metadata. Legacy sidecars load without rewriting. Confirmed billing signatures, explicit authentication exceptions, interruption, cancellation, and local-model/memory markers have narrow legacy fallbacks; generic HTTP 400/401 do not establish credits or expiry. A saved summary supersedes an old processing failure; publish failures and newer structured regeneration failures retain their notice alongside the saved summary.

Ask also writes diagnostic text in its result JSON. Retain that complete error when the stderr tail has truncated it, along with any additional process diagnostics; supplement the typed failure without replacing its exit status, native metadata, or cancellation.

The local report is built from an allowlist, never by redacting a traceback: numeric app version, ISO timestamp, operation/cause, recognized provider, valid status, and a validated request identifier. The displayed preview is the exact copied string. No request bodies, diagnostics, titles, paths, meeting content, or other log fields enter it. Opening Details and preparing/copying the report start no processing, network request, or event-log category.

### Supervised spawns (PIPE37)

`PipelineLauncher` exports `MP_SUPERVISED=1`, beside `MP_FAILURE_PATH`, on the spawns it stops when the app goes: the ask and every spawn anchored on a meeting (run-all, the Library re-runs, merge, finalize, paste publish, the Apple-phase publish; `PipelineLauncher.isSupervised` is the rule, and `roster enroll` is excluded by name). Those spawns get a stdin pipe whose only write end the daemon holds. `mp`'s `__main__` consumes the variable (pops it, so no descendant inherits it), starts a daemon thread that reads fd 0 to EOF, and then SIGTERMs its own main thread into PIPE22's unwind. The kernel closes the write end however the daemon ends, so this covers a crash, a SIGKILL and the termination ceiling's `exit`; an orderly Quit also SIGTERMs them first, from `Coordinator.shutdown` through `PipelineLauncher.terminateSupervised()`, which returns at once and sends no SIGKILL. The daemon writes nothing on the pipe. Stdin rather than the parent pid because the dev tier runs `mp` under `uv run`, so Python's parent is `uv` (`uv` 0.11 forwards both SIGTERM and the EOF). Backup, restore, digest, actions and roster spawns carry neither and finish on their own. No variable means no watch: a manual `mp` run is unaffected. A watch that cannot read its stdin fails open. **PIPE46 added the backstop that was missing.** The daemon's SIGKILL, which PIPE22's handler leaned on, does not exist once the app is gone, so any SIGTERM `mp` sends itself (the stdin-EOF watcher above, and the deadline below) arms `os._exit(143)` first, after `SELF_TERMINATE_GRACE_SEC` (30 s, the grace `runMP`'s own watchdog allows): a `finally` that blocks, or a native call that never returns to the eval loop, now ends there instead of running forever. And `PipelineLauncher.makeSpawn` exports `MP_DEADLINE_SEC`, the spawn's own `runMP` timeout in whole seconds, on **every** spawn, supervised or not: `mp`'s `main` pops it and arms a timer for that plus `DEADLINE_SLACK_SEC` (60 s, so the app's watchdog is always first while the app lives) which SIGTERMs the main thread into the same unwind and hard exit. A backup, restore, digest, actions or roster spawn, deliberately left to finish at Quit (PIPE37), therefore keeps the ceiling it already had instead of running as an orphan; a manual CLI run sets no key and is unchanged.

`scripts/valid1_check.py --coldstart` is the second supervisor (HYG23): `_run_timed` spawns its `mp summarize` with a stdin pipe and `MP_SUPERVISED=1`, so a Ctrl-C, crash or kill of the script still unwinds `mp` and the model server it started.

## Model prefetch progress stream (`mp prefetch-model` stdout)

The one cross-language contract that is a *stream*, not a file. `prefetch_model._emit` writes one JSON object per line to stdout (and mirrors each to `pipeline_events.jsonl` under category `prefetch`); the daemon's `ModelDownloadSupervisor` tails it and drives the menu-bar download title. Four events:

```jsonc
{"event":"started",  "repo_id":"...", "total_bytes":N, "cached_bytes":N, "revision":"..."}
{"event":"progress", "repo_id":"...", "downloaded_bytes":N, "total_bytes":N, "percent":0.42}
{"event":"complete", "repo_id":"...", "path":"...", "cached_bytes":N, "total_bytes":N, "revision":"..."}
{"event":"failed",   "repo_id":"...", "error":"...", "error_type":"..."}
```

`started` carries `cached_bytes` and no `downloaded_bytes`, so Swift falls back from one to the other; drop that fallback and a fresh download reports 0 bytes on its first event. An event name Swift does not recognise hits `handleEvent`'s `default` arm and is dropped, freezing the title on the previous state for the rest of a multi-minute download, which is why the fixture asserts no emitted event is ignored. Byte counts route through `NSNumber.int64Value` (`as? Int64` truncates multi-GB sizes).

## Action grouping (`ActionItem.group`, AI10)

`<stem>.summary.json`'s action items carry an optional `group`: the source a roll-up gathered the action from. **Only `mp digest` sets it** (the workflow of the meeting the action came from, or that meeting's title when the meeting is untagged); inside one meeting's summary every action shares one source, so a meeting summary leaves it null and renders exactly as it always did. It is deliberately absent from `schemas.SUMMARY_TOOL`, so no model ever fills it: the digest assembles it from facts already on disk.

The contract both renderers assume is **all-or-none**: a writer tags every action it emits or none of them. Both `markdown._action_runs` (Python) and `MeetingSummary.actionRuns` (Swift) split the list into *consecutive runs* sharing a group, never buckets, so the writer's order is the render order and a renderer never reorders a list it did not build. A mixed list therefore renders its untagged run with no heading, which reads as belonging to whatever heading preceded it. Don't produce one. The grouped render is pinned by `summary-md-golden.json`'s `action_groups_ai10` case, so the two trees cannot drift on it.

Swift's `MeetingSummary.jsonObject()` writes `group` as an explicit null when absent, matching `owner` / `due` and matching what the pydantic writer emits, so the in-app correction save never drops a grouping nor invents a key shape the other tree has not seen.

## Evidence anchors (FEAT10)

`<stem>.summary.json` carries up to two anchors per summary point, each an `{"quote": "<verbatim phrase>", "t": <seconds>}`. They ride in two places, because the four sections have two shapes on disk:

- **`actions[].evidence`**, inline, since an action is already an object.
- **`evidence: {"summary"|"decisions"|"questions": [[Evidence]]}`**, a parallel map *index-aligned* with the string section it names, since turning `summary` into a list of objects would break the ADR 0014 lock and every publisher. `evidence["summary"][2]` backs `summary[2]`.

Both are additive and optional: a pre-FEAT10 file has neither and round-trips unchanged, and every existing consumer ignores them.

Three rules are load-bearing:

**Alignment is repaired, not assumed.** The pydantic model trims or pads each section's anchor list to the section's length on every validate, and drops keys that are not one of the three sections. Readers still index-guard (`markdown._section_suffix`, Swift's `MeetingSummary.evidence(section:at:)`), because a hand-edited file reaches a renderer without passing through that repair, and a chip on the wrong bullet is worse than no chip.

**Nothing unverified reaches disk.** `evidence.verify` re-checks every anchor against the real `<stem>.json` segments after generation and drops what does not resolve, so a stored anchor always points at a real row. Absence beats a wrong anchor everywhere, which is also why the local map-reduce path and the Apple Intelligence backend emit none at all rather than guessing. LOCAL14's staged local pipeline is the exception that proves the rule: its extraction stage produces the quotes as a by-product, so it runs the same `verify` against segments recovered from the timestamped render before it even assembles a summary, and the pass in `summarize` then re-runs idempotently over the already-snapped anchors.

**Swift has to model the field.** `MeetingSummary.jsonObject()` re-serializes only what the struct knows about, and it is the writer behind *both* in-place `summary.json` rewrites (`MeetingLibraryService.setActionResolved`'s done/reopen toggle, the one path behind both the Facts rail and the Summary tab's row toggle since UX26, and `SummaryTab.persistEdit`'s correction save). An unmodeled field here is not preserved-by-default, it is deleted the first time the user ticks an action done. The correction save additionally *remaps*: `MeetingSummary.carryEvidence` keeps anchors on lines whose text the user did not touch and drops them from edited or newly added ones, because a quote backed the sentence that was there before.

AUTO2 adds a fourth, on the way out rather than in: in a Markdown-file note (obsidian / filesystem / lan) and in the stored `<stem>.summary.md`, each rendered `[mm:ss]` becomes a `[12:34](meetingpipe://open?stem=<stem>&t=<seconds>)` link that opens the Library on that transcript row. Three details are contract, not taste. The `t=` value keeps millisecond precision with trailing zeros stripped (`markdown.deeplink_seconds`, mirrored by `AppleIntelligenceSummarizer.deeplinkSeconds`), because `TranscriptSegmentLookup` picks the last segment starting at or before `t` and a truncated anchor would land on the row before the cited one. The stem is percent-encoded down to the RFC 3986 unreserved set, the same set Python's `quote(safe="")` keeps, so it is safe both as a query value and inside a Markdown link target; Swift must spell that set out in ASCII, since `CharacterSet.alphanumerics` would leave Cyrillic raw. And the link syntax replaces the outer brackets rather than nesting inside them, because a leading `[[` is an Obsidian wikilink. Notion stays plain text (custom schemes are not reliably clickable in its rich text), and a digest passes no stem because its actions come from many meetings.

LANG1 deliberately does not see quotes. `summary_language._summary_sections` reads the section strings and `actions[].task`, never `evidence`, so a forced-language summary over a foreign-language meeting (English summary, Ukrainian quotes) is not flagged as divergent and repaired when it was already correct. Keeping quotes in their own field rather than inside the section strings is what makes that exclusion structural.

## Local model server marker (`~/Library/Logs/MeetingPipe/mlx-server.json`)

Who owns the detached `mlx_lm.server` (LOCAL10). A Python-to-Swift surface: `mp.local_server.write_marker` writes it (atomically, `0600`) from `LocalSummaryClient._spawn`, `clear_marker` removes it once the server is confirmed gone, and the daemon reads it back through `LocalServerReaper.parseMarker`. Shape:

```json
{
  "schema_version": 1,
  "pid": 4242,
  "owner_pid": 1111,
  "port": 8765,
  "model": "mlx-community/Qwen2.5-7B-Instruct-4bit",
  "adapter_path": "",
  "spawned_at": 1770000000.0
}
```

The server is spawned with `preexec_fn=os.setsid`, so it lives in its own session and a signal aimed at `mp`'s process group misses it. Every clean exit path in `mp` calls `close()` and kills it, and since PIPE22 so does a SIGTERM, which the router turns into an unwind (see "Subcommand pattern"). What does not is a SIGKILL of `mp` itself, which `PipelineLauncher` sends when the SIGTERM grace runs out (a wedged `run-all`, or an unwind slower than the grace): no `finally` runs, the parent's idle-timeout `threading.Timer` dies with the parent, and a multi-GB server is left resident with nothing on the machine that knows it exists. This file is that knowledge.

**The marker is cleared only on a confirmed exit (PIPE22).** `terminate_server` re-checks `is_server_pid` after its ladder, and `LocalSummaryClient._terminate_proc` checks `proc.poll()` after a short wait following the SIGKILL. A server still alive keeps its marker, the kill reports False (`terminate_server` returns it, `_terminate_proc` returns it to the served-identity mismatch path, which then raises naming the pid rather than spawning onto a port the survivor holds), and `pipeline.local_server_survived_kill` records it. Both used to clear the marker before or regardless of the kill, so a survivor vanished from both readers.

**A client that reuses a server the marker names takes ownership while it uses it (PIPE22).** `LocalSummaryClient._adopt` re-stamps `owner_pid` to itself (`restamp_owner`, every other field kept, never creating a marker), and `close()` hands it back to the previous owner if that one is still alive (`hand_back_owner`). The re-stamp stops a reap after the spawner's Cancel from killing the server under a live `mp ask`; the hand-back stops the mirror case, where the re-stamper exits first and the spawner's server would otherwise read as orphaned. What neither covers: a re-stamper that is SIGKILLed before it can hand back, chains of three or more users, and the spawner's own `close()` killing a server someone else is using, which is the two-owner class [LOCAL21](./docs/backlog/tasks/LOCAL21.md) removes.

**An orphan is a live server with a dead owner.** Both sides apply the same two rules, and they have to agree or the daemon and `mp doctor` will describe the same marker differently:

- `pid` counts as the server only when `ps -o command= -p <pid>` contains `mlx_lm.server` or `mp.local_model_server` (the SEC27 shim the server now runs behind; `local_server.is_server_command` and Swift's `LocalServerReaper.isServerCommand` accept both). Liveness alone is not enough: pids are recycled, and this pid gets signalled.
- `owner_pid` counts as alive only when its command is a Python interpreter whose argv carries `-m mp` or a token ending in `/mp` (a console script shows in `ps` as its interpreter followed by the script path), split on whitespace so a path with a space still ends in a `/mp` token. A recycled owner pid must not shield an orphan, which the old rule (`"mp"` or `"python"` anywhere in the line, so `/tmp`, `sample`) let it do. `local_server.is_owner_command` and `LocalServerReaper.isOwnerCommand` implement it token for token, and both suites pin the same accept and reject lists (PIPE22).

A marker whose server is already gone is stale, not an orphan, and is cleared in passing. Three triggers reap: `Coordinator.reapStorage()` at launch and after every finished job; `PipelineLauncher`'s termination handler right after the watchdog kills a job; and the same handler after a user Cancel (PIPE22), since a cancelled job never reaches the after-job sweep. `mp doctor` reports one without killing it. `mp serve-local` writes no marker at all: the daemon spawns it directly and holds its lifetime through a child handle, so it can never be orphaned this way.

**The server is a pinned, offline, authenticated shim (SEC27).** `build_server_command` launches `python -m mp.local_model_server`, which verifies its `--model` is a local `snapshots/<sha>` directory (never a repo id, so nothing reaches the Hugging Face downloader; `local_snapshot.resolve_for_serving` picks it, `verify_snapshot` refuses `model_file`, `auto_map`, `.py`/`.pyc`/`.so`/`.dylib`), sets `HF_HUB_OFFLINE`, then runs mlx-lm's own `main` with three grafts: every request needs `Authorization: Bearer <bearer_for(token)>` (a one-way derivation, so the wire credential is not the health-proof key); an `Origin` header, a non-loopback `Host`, and every preflight are refused; the body may name only the configured model (or the alias `default_model`), the configured adapter, and no draft model, checked on the raw request and again in `ModelProvider.load`. The token is generated by the spawner (`LocalSummaryClient._spawn`, `mp serve-local`), handed over in the environment (never argv), and recorded by the *server* once bound at `~/Library/Application Support/MeetingPipe/mlx-server.token` (`{port, pid, token}`, `0600`), so a spawn that loses a port race never overwrites the winner's record. A client trusts a listener only after `GET /health?nonce=...` returns `HMAC-SHA256(token, "mp-local-server-health-v2:" + nonce)` (`local_server.health_proof`; its own domain prefix, which the bearer's label does not share, so no nonce can reproduce the bearer), and re-verifies before **every** request (a run lasts minutes; a server that died mid-run frees its port); the bearer goes only on the POST. The record is cleared when the server is confirmed gone, and a lost spawn race attaches to the winner. The record holds one server (one port). A preset's revision is pinned in `local_snapshot.PINNED_REVISIONS` (mirrors `resource_guard.PRESETS`); a custom model's is recorded in `local-model-pins.json` by `mp prefetch-model`. The child gets no managed token in any mode (`local_server.server_env`). Swift's `LocalModelPreloader` is unchanged: it spawns `mp serve-local` and sends no HTTP.

**Served identity is read from argv, not from the marker or the API (LOCAL11).** The marker answers *who owns* the server; the separate question of *what it serves* is answered by `local_server.served_identity(port)`, because a warm server is reused on a bare HTTP 200 and a `local_model` / `local_adapter_path` change would otherwise keep the old weights answering every run. Neither HTTP endpoint can tell you: `/v1/models` scans the whole HuggingFace cache and lists every downloaded MLX model (appending `--model` only when it is a filesystem path), and `/v1/chat/completions` echoes back whatever `model` the caller sent. Verified against mlx-lm 0.31.3. So identity comes from `lsof` on the port, `ps` on that pid, and a parse of the `--model` / `--adapter-path` flags `build_server_command` emitted; the marker's copies of those two fields are the fallback for when `lsof` is unavailable. Argv is the *spawn contract*, not a readback of the loaded weights, so this catches a server started for a different model, not one that failed to apply the adapter it was handed.

**The check is about the model only; the adapter is settled per request (LOCAL15).** mlx-lm 0.31.3 accepts `--adapter-path` and then ignores it (`ModelProvider.load` resolves the model alias before keying `_adapter_map` by it, so the lookup always misses; upstream #1248, fix PR #1249 unmerged), so the flag on the spawn command never decided anything. `LocalSummaryClient` therefore sends `adapters` in every request body, which does decide the loaded weights, and that makes our configured adapter the true answer in both directions: a warm server started with an adapter still answers our adapter-free requests from the base model. Two consequences the code encodes. An adapter-only difference is **not** a reuse mismatch, because respawning would hand the fresh server the same ignored flag and change nothing while costing a full model reload. And `LocalSummaryClient.adapter_path`, the value `<stem>.run.json` records, deliberately returns the configured path rather than the argv readback, unlike `model` which keeps the served-over-configured rule. The flag stays on the spawn command anyway: it costs nothing, it keeps the argv readback meaningful, and it becomes correct for free if upstream ever merges the fix. First request carrying an adapter costs one model reload (measured 5.9 s against a 7B, one-time per server lifetime; warm adapter requests were 0.24 s).

Three rules the two ends of that check have to keep:

- **Unknown is not mismatch, but foreign is (SEC27).** An unparseable `ps` line or no `lsof` reads as "no answer", and the server is then reused only if it proved the token (below). A listener `lsof` and `ps` *identified* as some other program is `source="foreign"`, a positive mismatch: the run is refused with a typed error naming the pid and command, in every mode, and nothing is sent to it. Respawning on ignorance costs a multi-GB reload; sending a transcript to whatever holds the port costs more.
- **Only kill what you spawned.** `LocalSummaryClient` replaces a mismatched server when it spawned it, or when the marker names that exact pid; it never kills the daemon's warm `mp serve-local`, which would just race that supervisor. The daemon restarts its own on `ConfigStore.didPersist` (`LocalModelPreloader.refresh`), which is the fix for that half.
- **Never launder the mismatch.** When the run proceeds against a server we could not replace, `<stem>.run.json` records the model that *served*, not the one config asked for, and `mp doctor` names the mismatch. The adapter it records is the one the request carried, which is what served (see LOCAL15 above).

## Daemon-internal recording artifacts

Six artifacts the daemon both writes and reads. Unlike `<stem>.meta.json`, none is part of the Swift-to-Python contract: the redactor and orphan recovery consume them before any pipeline run, so the pipeline never reads them directly (recovery does *rebuild* `<stem>.meta.json` from the manifest below). The MIC4/MIC5 capture-first work introduced the first three; REC2 added the recovery manifest; MIC14 added the off-record marker; REC1 added the failure breadcrumb, whose shape REC9 documented here once it grew a second reason to exist. Documented here per DOC6.

**`<stem>.mute-timeline.json`** (TECH-MIC4), next to `<stem>.wav`. The muted spans the offline redactor (TECH-MIC5) zero-fills. Shape:

```json
{ "version": 2, "spans": [ { "start_sec": 1.5, "end_sec": 3.2, "source": "mute" } ] }
```

Seconds from recording start, half-open `[start_sec, end_sec)`. `source` (MIC14) is `mute` (the app/hardware-mute oracle, the auto path) or `manual` (an explicit off-the-record toggle); an absent `source` in a version-1 file decodes as `mute`. Only genuine app/hardware-mute spans are recorded on the auto path, never `silentByRMS` (quiet) or `uncertain`, so redaction can never drop quiet-but-real speech; the redactor withholds an auto span carrying speech (MIC12) but always redacts a `manual` span (explicit intent). Written by `MuteTimelineFile.write` (atomically), read by `MuteRedactor`, and reaped after a successful redaction. Written under capture-first-redact (all spans) OR under default capture-first when a manual span exists (manual-only, MIC14), by `MuteTimelinePersistence`, the one rule both writers share; absent otherwise (default capture-first with no manual span, regulated, pre-MIC4). Since REC34 it is written at stop whether or not the merge produced a final, and by the termination flush on a quit once the engine teardown came back clean, so a quit or a failed merge recovers as redact-then-process rather than quarantined; only a crash, a force quit or a teardown that timed out leaves it missing.

**`<stem>.offrecord`** (MIC14), next to `<stem>.wav`. An empty marker written the moment the off-the-record toggle is first turned on during a capture-first recording, removed by `SinkDispatcher` once `MuteRedactor` answers `.redacted` or `.notNeeded` (SEC16; it used to go at the clean stop, before the job ran, which hid a failed timeline write). It closes an orphan-leak edge: the manual-only timeline is written only at stop, so a crash before stop would leave off-record audio in a recording that `OrphanRecordingRecovery` auto-publishes. The marker makes `quarantineReason` treat such an interrupted recording exactly like a redaction-opt-in orphan whose timeline was lost. Present with no timeline at redaction time, it makes the redactor fail closed with `timeline_missing`. Its write throws since REC21; a failure is reported and the span still starts. Since REC21 it also means "a cut is owed" whatever the mode: `OffRecordMarker.persistOwed` writes it before a memory-only or manifest-only copy of that fact is let go (a clean stop whose job owes a cut, `retryMeeting` and `retranscribeMeeting` over a manifest that says so), and the manifest is kept, or the re-transcribe refused, when even that write fails. Absent for recordings that never went off-record.

**`<stem>.capturemode`** (TECH-MIC5 review), next to `<stem>.wav`. A one-line plain-text marker written at recording **start** so orphan recovery, after a crash where `stop()` never ran, can still apply the right privacy posture. One token (`CaptureMode.marker`): `capture_first`, `capture_first_redact`, or `regulated_gate`. Read through `CaptureMode.readMarker`, which tells `absent` from `unreadable` (REC21: present but naming no mode, which both readers treat as owing a cut), by `OrphanRecordingRecovery.quarantineReason` (a capture-first-redact orphan with no timeline is quarantined, not auto-published) and by `MuteRedactor` (a `capture_first_redact` or unreadable marker with no timeline fails closed, SEC16). Orphan recovery clears it only after the quarantine move landed (REC21). Removed at a clean stop that produced a final and wrote its timeline; kept when the timeline write failed. Also removed when the start that wrote it fails (REC27: `start()`'s one catch), so a failed start leaves no marker behind in raw/.

**`<stem>.recovery.json`** (REC2), next to `<stem>.wav`. The start-time identity manifest: it persists the routing intent a crash would otherwise lose, so the orphan sweep never auto-egresses a BYO / NDA / regulated meeting that was interrupted mid-call. Written at recording **start** by `RecordingManifest.write`, shape:

```json
{ "schema_version": 1, "summary_mode": "auto" | "byo", "meta": { /* the MeetingMetaSidecar.build payload */ },
  "capture_mode": "capture_first" | "capture_first_redact" | "regulated_gate", "off_record": false }
```

`capture_mode` and `off_record` (REC21) are the second copy of the `.capturemode` and `.offrecord` markers: the capture mode the session started under, and `true` once an off-the-record span opened under lossless capture (`toggleOffTheRecord` rewrites the manifest from the session's own copy of its inputs). Either one saying a cut was owed quarantines an orphan with no timeline exactly as the marker would. A manifest written before REC21 lacks both and reads as `capture_mode` unknown, `off_record` false. `RecordingManifest.load` answers `absent`, `unreadable` or `parsed`, and anything present that is not what the writer produces is `unreadable`: bytes that do not parse, a `summary_mode` that is not exactly `auto` or `byo` (it used to map to `auto`), a `meta` that is present but not an object (it used to become an empty payload, dropping the NDA routing), or a `capture_mode` / `off_record` of the wrong type or value.

`summary_mode` routes the recovered enqueue (a `byo` orphan produces a paste bundle, not an Anthropic+Notion auto-summary); `meta` is replayed into a rebuilt `<stem>.meta.json` (skipped if one already exists) so the pipeline arms its egress guard for an NDA / regulated orphan and keeps the meeting title. Read by `OrphanRecordingRecovery.recover`. Removed at a clean stop that produced a final (kept, like `.capturemode`, when the merge failed so the recurring sweep can still route it; REC6 also runs that sweep after every job completion, not only at the next launch, and exempts a `.recovery.json` / `.recordfail.json`-bearing stem from the 24 h staleness cutoff). Absent for pre-REC2 orphans, which recover on the legacy `.auto` default.

**`<stem>.recordfail.json`** (REC1), next to where `<stem>.wav` would have landed. The breadcrumb that explains retained capture intermediates: it is written on every path where the post-process did not produce a promotable final, so the `.mic.wav` / `.system.wav` beside it read as a kept-for-recovery capture rather than stray debris. Shape:

```json
{ "schema_version": 1, "reason": "…why the post-process did not promote…", "retained": ["<stem>.mic.wav", "<stem>.system.wav"], "attempts": 2, "last_attempt_at": "2026-11-12T10:15:00Z" }
```

`reason` is free text and is the only place the *kind* of failure is recorded: a non-zero ffmpeg exit, a merge that timed out, or (REC9) a merged output shorter than the capture it was built from, which names its produced and expected seconds. Informational for a reader; nothing branches on it. What is load-bearing is the file's **existence** and its **`attempts`**: `OrphanRecordingRecovery.scanOrphanStems` exempts a stem carrying it from the 24 h staleness cutoff, `OrphanScan` surfaces it as an `mp doctor` finding, and REC6 deletes it once a re-merge succeeds. `attempts` (REC24) counts every failed post-process of the stem, the stop-time one included; each write reads the previous file and adds one, and a breadcrumb written before REC24 has no key and reads as 1. The after-job sweep skips a stem at `OrphanRecordingRecovery.maxAfterJobAttempts` (3) whatever other marker it carries, while the launch sweep ignores the cap, because a rebuild can ship the fix. `last_attempt_at` is the ISO 8601 UTC time of the latest failure, for a reader only. `schema_version` stays 1: both keys are additive. Written atomically by `RecordingPostProcessor.writePostProcessFailure`, which also emits `recorder`/`postprocess_failed`. Absent for every recording that finished normally.

**`<stem>.placement.json`** (REC36), next to where `<stem>.wav` would have landed. Daemon-internal (written by `MeetingRecorder`, read by `RecordingPostProcessor.recoverOrphan`, never by the pipeline). Where the orphan sweep should place the system channel and cut the recording when `stop()` did not finish the merge.

```json
{ "schema_version": 1, "system_head_offset_sec": 4.24, "limit_sec": 1800.0, "span_sec": 2400.5 }
```

Written by `stop()` straight after `endSession` (offset, `limit_sec` when a held end confirmed, and `span_sec`), because from that point `isRecording` is false and a quit skips the termination flush while the halt, teardown and drains run; rewritten without `span_sec` once the stop-time REC30 coverage check has run, just before the merge; removed once a verified final is promoted. So it survives a quit before the merge, a failed merge, a wedged writer and a kill inside the merge. The termination flush writes the offset and `span_sec` (recording start to capture stop) and no `limit_sec`: END9 decides a trim only when a held end confirms at stop, and the owner settled on 2026-11-17 that a quit during an unconfirmed hold keeps the tail. `span_sec` present means no coverage check has run, so recovery runs it once and rewrites the file without it, so a merge that keeps failing is not measured again. Recovery also removes a stale file beside a finished final or beside intermediates too small to merge, and the menu's Discard removes it. Kept apart from `<stem>.recordfail.json` on purpose: that file is rebuilt on every failure and would lose the placement before the retry. Absent, or anything that does not parse, holds a negative or non-finite value, or a non-positive `limit_sec`, recovers at offset 0 with no cut and logs `orphan_recovered_without_offset`. A kill mid-recording leaves none.

**`originals/<stem>.wav`** (ADR 0016), in `~/Library/Application Support/MeetingPipe/originals/`, NOT in the recordings dir. The kept full (un-redacted) recording, moved aside when `MuteRedactor` redacts the canonical `<stem>.wav`, and the folder a held-back or quarantined recording is *not* kept in (below). Deliberately outside the Library-scanned `raw/` tree and the Raw Files tab's reach: mode `0600`, excluded from Time Machine and iCloud. The redacted artifact is what every consumer reads; this is the recovery source only. ADR 0016's mandated retention policy + reaper ships as `OriginalsReaper` (age + size bounded: 30 days / ~10 GB, reaped at launch and after each pipeline job), and meeting deletion cascades into it via `MeetingLibraryService.softDeleteMeeting` (MIC13). **`originals/held/<stem>.wav`** (SEC26) is where a recording goes that must not be consumed and has no redacted twin: a held-back meeting (SEC16) and a capture-first-redact orphan whose timeline was lost, both through `MuteRedactor.quarantine`, same `0600` and backup exclusion. `OriginalsReaper` looks at regular files only, so it never enters `held/`; only the owner deletes from it (the meeting's delete cascade, or Preferences ▸ Storage ▸ Held-back recordings ▸ Show). A second hold of a stem never replaces a differing first (`<stem>.held-<n>.wav`). Every at-rest protection result is checked and a miss logs `recorder`/`at_rest_protection_failed` (`file`, `protection`, `error_domain`, `error_code`) while the move still completes.

`schema_version` (CI2, extended by CI4): `<stem>.meta.json` and every JSON sidecar writer that lacked one now stamp `schema_version: 1` (the `<stem>.error.json` failure sidecar and the pipeline publish receipts `<stem>.notion.json` / `.obsidian.json` / `.filesystem.json` / `.lan.json` / `.run.json` / `.empty.json` / `.apple_pending.json`). Two deliberate exceptions: `<stem>.mute-timeline.json` already carries its own `version` (now `2` after MIC14 added the span `source`, above), and `<stem>.summary.json` is the pydantic `MeetingSummary` data schema rather than a marker sidecar, so it is versioned through the model, not a stamp. `<stem>.speaker_labels.json` was the one cross-language sidecar CI2 missed and now stamps `1` too (CI4).

## Audio retention (STOR1)

**The recording's extension is not a constant.** A meeting's final recording is `<stem>.wav` as the recorder wrote it, `<stem>.flac` after a `compress` retention policy has run, or absent entirely after a `drop` policy. `MeetingStore.finalRecordingExtensions` is the single list, `MeetingStore.finalRecordingURL(stem:in:)` the single resolver, and `Meeting.audioURL` is `URL?` so the compiler forces every audio affordance to handle absence. Don't reconstruct `"\(stem).wav"` by hand. The one exception is `MeetingStore.sidecarAnchorURL(stem:in:)`, for the two callers (`mp roster enroll --wav`, `PipelineLauncher.appleContext`) that only derive sibling sidecar paths from the URL and never open it.

FLAC and not AAC, because `diarize.py` reads channels through `soundfile` (libsndfile), which decodes FLAC and not AAC: a lossy transcode would make a retried or regenerated meeting unreadable to the pipeline, on top of being irreversible in an archive.

**`[retention]` in `~/.config/meeting-pipe/workflows/<uuid>.toml`.** Written by `WorkflowStore.encode`, read by `.decode`. The table is **omitted entirely** while the workflow keeps its audio forever, so a workflow that never opted in stays byte-unchanged on disk:

```toml
[retention]
policy = "keep" | "compress" | "drop"
after_days = 30
```

Two fail-safes, because the policy deletes irreplaceable audio: a missing table decodes to `keep`, and so does a `policy` value this build doesn't recognise (one a newer build wrote).

**One reaper, two scopes.** `Coordinator.reapStorage()` runs at launch and after every pipeline job, off-main, and calls two sweeps that share a scheduler and the `coordinator` event category but not an algorithm. `OriginalsReaper` is bounded-cache eviction over `originals/` (age, then oldest-first under a byte ceiling). `AudioRetentionSweep` applies each workflow's policy to settled meetings in `raw/`, deciding through the pure `AudioRetention.decide`. Neither ever touches the live recording.

A meeting is eligible only when **settled**: `.done` and not a member of the Library's `Needs you` scope. `AudioRetention.isSettled` and `LibraryScope.needsYou.includes` have to agree, and a test pins that. A meeting whose workflow carries no policy, or whose workflow was deleted, keeps its audio forever. A meeting with no workflow at all (no `workflow_id` in its sidecar, or no sidecar) follows the default workflow's policy since REC20, so the default's retention covers manual recordings; with the default on `keep`, the shipped state the owner kept on 2026-11-12, that is still keep-forever. A sidecar that exists but cannot be read is not "no workflow" (SEC25): the sweep skips that meeting.

`compress` writes `<stem>.flac.writing`, moves it into place, reopens it with `AVAudioFile` and compares durations, and only then deletes the WAV. Every failure path leaves the WAV untouched. The waveform peaks cache is keyed on the stem but validated on the recording's size + mtime, so a transcode invalidates it in place; `drop` and `softDeleteMeeting` purge it outright, since nothing will re-derive it.

Events: `audio_compressed`, `audio_dropped`, `audio_retention_swept` (category `coordinator`).

## Cloud-sync detection (SEC12)

The zero-egress promise is enforced inside the pipeline process (`egress_guard`), but the filesystem can undo it: the default library at `~/Documents/Meetings/` sits inside iCloud's Desktop & Documents scope, and if that setting is on, every WAV and transcript uploads to Apple with nothing in meeting-pipe aware of it.

One rule set, two implementations: `mp.cloudsync.detect_sync_provider` (doctor's text line) and `CloudSyncDetector.detect` (the Preferences status pill). The duplication is deliberate. The alternative is a `mp storage-status --json` subprocess plus a JSON contract, for what is a path check; both sides are unit-tested against real extended attributes. **Change one, change the other.**

Walk the library path and its ancestors, up to **and including** `$HOME`, then stop. Home is checked (a home directory that is itself a sync root syncs everything under it); nothing above it is (a Mac whose home lives under a folder named `Dropbox` is not evidence). Signals, in descending confidence:

1. `~/Library/CloudStorage/<Provider>-<account>`, the modern File Provider root. Provider is in the directory name.
2. `~/Library/Mobile Documents/`, iCloud Drive proper.
3. The xattr `com.apple.icloud.desktop`, which macOS stamps on `~/Documents` and `~/Desktop` under Desktop & Documents sync.
4. The xattr `com.apple.file-provider-domain-id`, the generic "a sync client owns this" marker. Reports an unnamed provider, still enough to warn.
5. A directory literally named `Dropbox` / `Google Drive` / `OneDrive...`, for clients predating File Provider.

**Two dead ends, recorded so nobody re-walks them.** `Path.resolve()` / `resolvingSymlinksInPath()` does *not* reveal Desktop & Documents sync: macOS leaves `~/Documents` at its own path and symlinks `~/Library/Mobile Documents/com~apple~CloudDocs/Documents` **back to it**, so the resolution runs the wrong way. And `MobileMeAccounts.plist`'s `MOBILE_DOCUMENTS` service being enabled means iCloud *Drive* is on, not Desktop & Documents; keying on it flags every Mac with iCloud Drive. The service that governs Desktop & Documents is `CLOUDDESKTOP` (`Enabled: true` on older macOS, `status: "active"` on macOS 26), and neither implementation reads that plist at all: the shape moves between releases, and signal 3 above answers the same question from the filesystem, where the library actually lives.

Note for tests: `com.apple.icloud.desktop` can be written by an unprivileged process, `com.apple.file-provider-domain-id` cannot. Stamp the first for real; fake the read for the second.

**Severity.** A synced root is a `[WARN]`. A synced root under `regulated_mode`, or on a Mac with any NDA workflow (`mp.workflows.nda_workflow_names`, the only Python that reads the workflows dir), is a `[FAIL]`. `mp doctor` still returns 0 either way: it is a diagnostic, not a gate, and callers grep for `[FAIL]`.

`mp doctor` checks every on-disk root it writes, deduped by sync root (SEC35 widened this past the library): `recording.output_dir`, the `digests/` sibling, the `published/` folder whenever anything can send meetings there (`filesystem` in the global sinks, `regulated_mode`, any NDA workflow, since `apply_overrides` forces every zero-egress meeting and SEC25's fail-closed path onto that sink, a workflow listing a filesystem sink, read by `mp.workflows.sink_types_in_use`, or a folder that already holds files), the backup destination (the parent of the archive in `.last-backup.json` and the destination in the backup agent's `ProgramArguments`, both home-relative and an unreadable or relative one skipped, because the destination lives in the daemon's UserDefaults and not in `config.toml`), and the Obsidian vault and LAN mount when a sink or workflow names them. The first four are `[FAIL]` under a zero-egress promise; the vault and LAN share are `[WARN]` unless `regulated_mode` is on and the global sinks list them (the sidecar-less path; SEC18 item 1 makes them WARN-only when it lands), and a deduped line is strict if any of its roots is. The daemon's assisted move (`LibraryMover`) relocates the recordings and digests only, so doctor is what surfaces a `published/` still inside iCloud. The Storage pane's backup picker runs `CloudSyncDetector.detect` on the chosen folder (`BackupDestinationAdvice.syncWarning`, pure) and names the provider without refusing the choice, more strongly under regulated mode or an NDA workflow.

## Backup and restore (STOR2)

`mp.storage` owns every root path, with an injectable `home` so tests point the whole tree at a `tmp_path`. `mp backup` and `mp restore` and `mp doctor` all resolve through it, so they cannot drift on what "the library" means.

`mp backup <dir>` writes `meeting-pipe-backup-<YYYYMMDD-HHMMSS>.tar.gz`, stdlib `tarfile`, gzip **level 1**: JSON sidecars compress well even at level 1 while WAV barely compresses at any level, so the default level 6 burns minutes of CPU on a multi-gigabyte library for nothing. Each root goes under a stable prefix (`library/`, `digests/`, `config/`, `corrections/`) rather than an absolute path, which is what lets a new Mac restore to a different library location.

**Written whole or not at all, then pruned (STOR12).** The archive is written as `<name>.partial`, fsynced, and `os.replace`d to its final name; any exception deletes the `.partial` and leaves the marker alone, and the marker itself goes through `storage.atomic_write_text` (STOR8 item 2, landed with STOR12). Before anything is created, `check_free_space` refuses when the destination volume's free space (`shutil.disk_usage` on the nearest existing ancestor) is below `estimate_backup_bytes` (the bytes `_add_root` will include, walked by the same `_root_files` iterator) plus headroom: `RECORDING_RESERVE_BYTES` (REC20's two hours of capture plus merge, 4,608,000,000 bytes) when the destination shares the library's `st_dev`, `BACKUP_HEADROOM_BYTES` otherwise. After a successful run, `prune_old_backups` applies the owner's **retention policy** (chosen 2026-11-12): over the files directly in the destination whose names fully match `meeting-pipe-backup-YYYYMMDD-HHMMSS.tar.gz`, ordered by the timestamp in the name (never mtime), keep the newest `KEEP_RECENT` (7) plus the newest archive of each of the `KEEP_WEEKS` (4) most recent ISO weeks that are strictly before the oldest kept one's week and hold an archive. A daily schedule settles at 11. Hand-made archives under that name count; a renamed one does not. The archive just written is never removed, an unlink that fails is left for the next run, and a `.partial` whose name is over 24 hours old is removed. When anything was pruned it emits `pipeline` / `backup_pruned` with `count` and `bytes` (archives only), and the summary always prints `pruned N older backups (<size>)`. The summary prints from the manifest `run_backup` built; nothing reads the archive back.

**The source is guarded too (STOR13).** `check_library` refuses, before anything is created, a library root (`recording.output_dir`) that is not a directory; the other three roots keep their zero-files entry. `_root_files` walks with `os.walk(onerror=...)` instead of `rglob`, which skipped an unlistable folder silently, and an unlistable folder under the library is a `BackupError` naming up to five of them (the estimate walks the same iterator, so this lands before the `.partial`). The marker records `library_files`, the library root's archived file count. A run whose count is 0 while the previous marker's was above 0 is refused before the rename, so the marker and every archive stay untouched; deleting the marker is the escape hatch for a real wipe. A run whose count is below `PRUNE_SHRINK_RATIO` (half) of the previous one is written and stamped but not pruned: it emits `pipeline` / `backup_prune_skipped` with `library_files` and `previous_library_files`, and the summary prints `retention skipped: library has N files, last backup had M` in place of the pruned line. Both comparisons need an integer `library_files` and the same `audio_included` on both runs, so a pre-STOR13 marker or a `--no-audio` switch compares nothing.

**Walks per run (STOR12).** The manifest is the last member, so finding it walks the whole gzip stream, and any backward seek (`tar.extractfile(name)` after a walk, an extraction after `getmembers()`) restarts decompression from byte 0. So every reader iterates `for member in tar` and acts on each member as it passes: `read_manifest` and `plan_restore` are one pass each, and a real `mp restore` two (validate and size, then extract; `main` hands its `scan_archive` result to `restore_archive`). `test_backup_restore.py` pins those counts by tallying bytes read off disk; before STOR12 they were 2, 3 and 6. The daemon's three spawns size their watchdog with `PipelineLauncher.storageJobTimeout(bytes:)`: 30 minutes plus the bytes involved at 5 MB/s.

**Never archived**, each with a reason in the manifest's `excluded` list: `originals/` (ADR 0016 makes them 0600 and Time-Machine-excluded; a tarball on a NAS would undo that), `secrets.env`, `.last-backup.json` (a fact about *this* Mac), `published/`, and the caches. Keychain values are never exported; the manifest names the four managed items (from `MANAGED_SECRET_KEYS`) under service `com.meetingpipe.daemon` and `mp restore` prints the `security add-generic-password` commands.

`mp restore <archive>` maps prefixes back to **this** machine's roots via `backup_roots(cfg)`, refuses a destination that already has files (`--force` overrides), and extracts with `tarfile`'s `data` filter so a crafted member cannot escape; a `FilterError` surfaces as a `RestoreError`, not a traceback.

**A failing restore is safe (STOR17).** `scan_archive` is the one validating walk (`read_manifest` is its manifest-only form): it refuses a manifest with no `schema_version`, one above `MANIFEST_SCHEMA_VERSION`, or one missing `created_at`, `roots` or `keychain`, and maps `EOFError`, `zlib.error`, `TarError`, `OSError` and a bad JSON payload to `RestoreError` (a gzip cut short raises `EOFError`, which is neither of the obvious two). The same walk sums `member.size` per destination prefix and keeps the largest member, so `check_restore_space` costs no pass: per destination volume it refuses, before the first write, when free space is below the incoming bytes plus the largest member (the temp copy coexists with what it replaces) plus `RECORDING_RESERVE_BYTES` on the library's volume or `BACKUP_HEADROOM_BYTES` elsewhere. Replaced files are not credited. A dry run is never refused for room. Each member is extracted to `.<name>.restoring` beside its target, still through the `data` filter, then `os.replace`d over it, so a failure part way (ENOSPC, an unplugged drive) leaves every file either as it was or whole from the archive; the `RestoreError` names the member, the errno name and how many files were already restored, and re-running the restore completes it. `main` passes its `scan_archive` result to `restore_archive`, so a real restore stays at two passes.

**The dry-run plan (STOR5).** `mp restore <archive> --dry-run --json [--out PATH]` emits `mp.restore.plan_restore`'s `RestorePlan` TypedDict instead of the prose report: per root the destination, how many files land, how many of those are new, how many already exist and would be overwritten, and whether the destination is occupied at all, plus capped `added_sample` / `replaced_sample` path lists so a preview can name *which* meeting comes back. `--json` requires `--dry-run` (it describes a restore, so a machine-readable "what just happened" would be a second shape) and `--out` requires `--json`; with `--out` the JSON goes to the file and stdout keeps a readable trace, which is what lands in `pipeline.log`. Swift's `RestorePlan` (`daemon/Sources/MeetingPipe/RestoreFlow.swift`) decodes it, so the keys are a **Python-to-Swift contract**: renaming one silently empties the confirm the owner presses. The plan and the real run are one walk seen twice (`_restorable_members` is the single home of the prefix dispatch and the `config.toml` carve-out), so a preview cannot describe a different restore than the one that then runs.

**Preferences ▸ Storage ▸ Restore from backup** is that plan's only consumer (STOR5): pick an archive, the dry run is spawned, its plan is rendered as the confirm's blast radius, and only a press of the destructive button spawns the real `mp restore <archive> --force`. `--force` is not optional there and the preview is what replaces the refusal it suppresses: every in-app restore writes into live roots, which a plain `mp restore` refuses because it was written for a new Mac's empty ones. Restore and backup are mutually exclusive (`StorageBusyGate`), since a `mp backup` walking the library mid-restore archives a half-restored library. The clean-Mac first restore stays a Terminal step, and the pane's footer and the README runbook both say which is which.

**The config-root exception.** A new Mac must write `config.toml` *before* restoring, since that file names the destinations. So `config.toml` (and `.last-backup.json`) do not count toward the config root's occupancy check, and the backup's `config.toml` never overwrites an existing one: it names the old Mac's paths, and restoring it would repoint `output_dir` at a library that is not there. Every other config file (workflows, roster, voiceprint, glossary) restores normally. Found by walking the runbook; keep the runbook walkable.

`mp doctor` reports the last backup's age from `~/.config/meeting-pipe/.last-backup.json`. Informational only: the owner may be relying on Time Machine. The marker is `{at, archive, bytes, audio_included, destination_encrypted, library_files}`, written 0600 by `storage.atomic_write_text`; `destination_encrypted` (STOR8) is `true`, `false`, or `null` when `diskutil` could not tell, absent on a marker older than STOR8. Swift's `LastBackup.read` reads it for the Preferences age line, and doctor `[WARN]`s on `false` and on `null` (a present `null`, not an absent field).

## MCP server status (`mp mcp-serve --status --json`, AUTO3)

`mp mcp-serve --status --json` prints what the read-only MCP server would expose, without serving:

```json
{
  "enabled": false,
  "transport": "stdio",
  "tools": ["search_meetings", "get_meeting", "get_transcript", "list_meetings", "list_actions"],
  "sdk_available": true,
  "visible": 175,
  "withheld": 42,
  "withheld_by_reason": {"nda": 3, "no_sidecar": 39}
}
```

Swift's `MCPStatus` (`daemon/Sources/MeetingPipe/Preferences/MCPStatusStore.swift`) decodes it, so the keys are a **Python-to-Swift contract** in the same sense STOR5's restore plan is: rename one and Preferences ▸ Integrations renders "Unknown" for the counts that are the whole point of the control. `withheld_by_reason`'s keys are `visibility`'s reason constants (`nda`, `regulated`, `no_sidecar`, and AUTO6's `regulated_global`, which `status` reports for every meeting while the global `regulated_mode` is on), and Swift maps each to a phrase, so an unmapped reason renders as itself rather than vanishing.

**The counts are read, never recomputed.** `mp.visibility` is the single owner of which meetings may leave the machine, and the number the owner reads has to be the number the server enforces, not a second implementation that agrees today. That is also why this is a subprocess call rather than a Swift sidecar walk. It obeys UX67: `MCPStatusStore.refresh()` runs detached, the child is killed at `ceilingSeconds`, and the read is re-taken on the pane's `.onAppear` rather than per render.

`--status` deliberately works without the optional `mcp` extra (`sdk_available` is how it says so), because Preferences has to render on an install that never opted in.

### Model-written fields are fenced one at a time (AUTO8)

Every string a tool returns that a model wrote or a person said (a meeting `title`, the `content` blocks, search `excerpt`s, an action's `task` and `owner`) is wrapped in `prompt_safety`'s untrusted markers, field by field, so rows stay plain JSON. A client that wants the bare text strips the first and last line. A `due` that is an ISO date stays bare; any other `due` is model prose, fenced, and ranked as undated. Stems, dates, `workflow` (an owner-configured name) and the booleans are not fenced. `task` is capped at `mcp_tools.TASK_MAX_CHARS` (300, ending in `...` when cut), and `owner` and `due` go through `clean_person` / `clean_due` on read, so a `summary.json` the Swift Apple Intelligence summarizer wrote gets the scrub the Python schema applies at write time. `list_actions` ranks every match before it cuts at `limit` (dated by soonest `due`, then undated newest meeting first) and returns `total` and `truncated` beside `count`. A new tool whose description carries `UNTRUSTED_NOTE` is held to this by a table-driven test over the registered tools.

### Tool arguments are closed (AUTO5)

Every tool's `inputSchema` carries `additionalProperties: false`, and `dispatch` rejects an argument the called tool does not declare, returning a client-visible payload rather than an answer:

```json
{
  "error": "unknown_argument",
  "tool": "get_transcript",
  "unknown": ["offset"],
  "accepted": ["around", "stem", "window"]
}
```

Both halves exist on purpose: the schema binds a client that validates, `dispatch` binds one that does not. The accepted set is derived from the schemas (`TOOL_ARGUMENTS`), so the check and the advertisement cannot drift, and a sixth tool inherits the rule without being edited in.

The rule is a property of `dispatch` rather than of one branch, in the same way read-only-ness is. Before AUTO5 an undeclared key was read by nobody and rejected by nobody, so a client that guessed at a parameter got a plausible right-looking answer back: on 2026-08-21 one passed `offset` to `get_transcript`, received a byte-identical window, concluded the argument was being ignored, and left the tool to read the meeting file off disk, which bypasses both the visibility gate and the corrections overlay. **A wrong call has to fail loudly, because the fallback from a silently-wrong tool is the unguarded path.**

One related shape, same commit: an explicit `0` is no longer read as absent. `int(arguments.get(k) or default)` turned `window: 0` into 4000 and `limit: 0` into the default, because `0` is falsy. Only a missing argument takes the default now; an explicit one reaches the tool that owns its bound and is clamped there (`window` to its 200 floor, `limit` to `max(1, ...)`).

## Speaker enrollment (FEAT3-VOICEPRINT / FEAT3-ROSTER)

Speaker enrollment learns voices so "me vs them" holds on the mono / merged recordings where the stereo mic-channel trick can't, and recurring named people surface by name. Five artifacts:

**`speaker_embeddings`** on the draft `<stem>.json`. The daemon (`FluidAudioRunner`) writes a 256-d L2-normalized embedding per diarized speaker (a duration-weighted mean of that speaker's per-segment embeddings), keyed by the diarization speaker id. It rides the transcript sidecar but is **transient**: `orchestrate._finalize_streamed_transcript` pops it (voiceprint enroll/match + roster match), then strips it from the final `<stem>.json` and re-persists it keyed by final label to `<stem>.embeddings.json` (below). So it never reaches the Library-facing transcript. Omitted when diarization produced no speakers.

**A diarizer that threw (DIAR8).** The draft `<stem>.json` carries `diarization_failed` and `diarization_failure_reason`, and Swift labels every segment `speaker_unknown` (its own junk-drawer string, also what a healthy run leaves on words no span covered, so it is never the signal). The pipeline keys on the flag: `orchestrate._streamed_segments_have_speakers` returns False for `diarization_failed` before counting a label, so `finalize_streamed_transcript` reaches the stereo channel path (`assign_speakers_by_channel`, mic to the user, system to the others) for daemon output. The finalized transcript keeps `diarization_failed: true` and Swift's reason (Python's own mono reason only when Swift gave none) and adds `speaker_fallback`: `channel` (labelled by microphone and system channel) or `none` (nothing labelled; a Swift-flagged mono failure keeps `speaker_unknown`, an unflagged mono one is relabelled `Speaker?` as before). A transcript that already carries `speaker_fallback` is not routed back through the fallback, because that pass needs the WAV and a second `mp finalize` over a compressed recording would wipe the labels. `speaker_fallback` is absent on every transcript from before DIAR8 and on a healthy run, and a merge keeps it only when every fragment agrees. Readers gate on `diarization_failed`, never on `speaker_fallback` alone. On the event side, `transcription` / `engine_succeeded` gains `diarization_ok` (false only when the diarizer threw; a runner that never diarizes reads true) and `language` (the sidecar's), and `transcription` / `diarization_failed` (`file`, `error_type` the Swift error's type name, `reason` capped at 300 characters) fires once beside it, below the same commit point, so an abandoned pass writes neither. The Transcript tab shows a one-line notice from `TranscriptDiarizationNote`, with the reason in its help text.

**`<stem>.embeddings.json`** next to `<stem>.wav`: `{schema_version: 2, embeddings: {<final label>: [256 floats]}, near_misses?: {<final label>: <roster name>}}`. The per-meeting per-speaker embeddings, keyed by the FINAL label the transcript shows (the "me" name, a roster name, or a `THEM-A` cluster) so the Library naming affordance can look up a speaker's embedding by the label it renames. Read by `mp roster enroll`, which folds the named speaker's embedding into the roster; the CLI also relabels the transcript in place, but the daemon passes `--no-relabel` (FEAT3-UNDO, below) so this file's keys are left untouched. Persists after the run (post-meeting naming needs it). Not read by the Library directly. `mp merge-meetings` (PIPE47) also adds each later fragment's voiceprints to the primary's file under the label the merged transcript gives that voice (the fragment's Library rename of the key, then the merge's renumbering of its per-recording `THEM-x` / `speaker_N` labels); a label the primary already has keeps the primary's vector, and an unreadable file refuses the merge rather than being overwritten.

`near_misses` (FEAT14, schema 2) is the same record from the other side: for a `THEM-x` the two-gate rule **declined**, the enrolled person it came closest to. Written only when there is one, so it is absent from every meeting finalized before it existed and both readers treat absent as "nothing to suggest". It carries **no similarity**, deliberately: the cosine that produced it stays inside `mp.roster.MatchResult`, because a number rendered beside a name is read as the probability that the voice is that person, which it is not, and at the one or two enrolment samples the roster actually holds it is not a good proxy for one either. Swift reads it through `MeetingStore.nearMisses` and offers it as **one context-menu item on the chip**, `Name as <person>`, gated again on that person still being enrolled; it never pre-fills the naming sheet and never writes anything on its own. The gates themselves are untouched by it, which `test_the_two_gates_still_decline_exactly_what_they_declined` pins.

**`voiceprint.json`** at `~/.config/meeting-pipe/voiceprint.json`, sibling of `config.toml`. The pipeline-owned running-average self-voiceprint: `{schema_version: 1, embedding: [256 floats], meetings: N}`. `mp.voiceprint.VoiceprintStore` writes it (auto-enrolls from the mic-channel user of stereo recordings, capped after a few meetings) and `mp.diarize.match_voiceprint` reads it to identify "me". The daemon reads it **read-only** for the Preferences "Voice profile" status + Reset (`VoiceprintProfile`); not part of the `<stem>.meta.json` contract, but display-only surfacing of shared per-user state, like the daemon reading `config.toml`. Written `0600` through `storage.atomic_write_text` in a `0700` directory (`storage.ensure_private_dir`, which also tightens an older 0755), as `roster.json` and every `<stem>.embeddings.json` are (SEC22); `tests/test_sec22_private_files.py` fences hand-rolled temp-and-replace writers outside an allowlist.

**The owner cluster (DIAR11).** Which diarized cluster carries the owner's name is decided by `mp.diarize`, in this order: the channel-assigned mic speaker; else the mic tier, `pick_mic_speaker`, which takes the cluster with the most mic-channel speech among those at 0.6 or more of their speech on the mic, needs `MIN_MIC_SPEECH_SEC` of it (15 s, provisional until the owner-run replay revises it) and declines when a second mic-side cluster holds `RUNNER_UP_SHARE` (a quarter) of the winner's mic time (two local voices; `MicTier.split` records them, and with no voiceprint at all `_me_signals` and the fold name both as one over-split owner and enrol the leader, the owner's 2026-11-17 decision, accepting audit F096); else the voiceprint match. When the mic pick and the voiceprint disagree the voiceprint wins if its cluster is itself mic-side and otherwise nobody is named, and `orchestrate._me_signals` enrols the mic pick into `voiceprint.json` only when the voiceprint picked the same cluster or none exists yet. After labelling, an unnamed cluster at `roster.MATCH_MIN` (0.65) to the voiceprint is folded into the owner when it is mic-side and, if an owner is already named, also sounds like that cluster (0.65 to it), and left alone, counted as flagged, when it is system-side; a cluster the roster names is never folded, and nothing is folded when a disagreeing mic pick and voiceprint pick named nobody. When several raw ids end up under the owner's label, `<stem>.embeddings.json` keeps the chosen cluster's vector for it. `finalize` emits `pipeline`/`owner_cluster_chosen` once per finalize of a labelled transcript: `stem`, `tier` (`channel`, `mic`, `voiceprint` or `none`), the chosen cluster's `mic_fraction`, `mic_seconds` and `voiceprint_score`, the best other cluster's `runner_up_fraction` and `runner_up_seconds`, and `folded` and `flagged` counts, with null for evidence that did not exist and no label, name or text. `scripts/valid1_check.py --owner-cluster --owner-name NAME [--reselect]` recomputes the field report's two numbers (owner's name on a cluster under cosine 0.5; THEM-x at 0.65 or more holding 5 percent or more of speech) from the transcripts and embeddings, before and after the new pick, read-only, measuring both against the mean of the owner-labelled vectors on disk (`--reference voiceprint` measures against the self-voiceprint, which the new pick is fed, so it flatters the after).

**`roster.json`** at `~/.config/meeting-pipe/roster.json`: `{schema_version: 1, people: [{name, samples, sources, centroids}]}`. `sources` (FEAT24) is additive and index-aligned with `samples`: each entry is `{stem, label, fp}`, the meeting speaker the sample was taken from (`fp` fingerprints the sample beside it, so a list shifted by an older writer reads as legacy instead of pointing at another meeting), or `null` for a sample enrolled before provenance existed (those are matched by vector at undo time, cosine >= `UNENROLL_MATCH_MIN`, and a roster without `sources` loads unchanged). Eviction past the cap and the dimension filter drop a sample and its entry together. Named third-party voiceprints: each person keeps a capped set of enrolled sample embeddings reduced to up to three k-means centroids. `mp.roster.RosterStore` matches a speaker to a name with a two-gate rule (top cosine >= 0.65 AND runner-up margin >= 0.07, biasing to leave-unknown over a wrong name); `match_detail` returns that verdict plus the near miss behind a decline (FEAT14), which `match` narrows back to the verdict alone, so no caller that only wants a name can act on a suggestion by accident; `mp roster enroll/list/forget/rename` manage it, and `orchestrate` applies matches at finalize (`diarize.resolve_speaker_labels`: unmatched voices become stable `THEM-A/B` clusters). The daemon **mutates** it only through the CLI: enrollment (Library "Name this speaker", offered only for a cluster that carries a voiceprint in `<stem>.embeddings.json`) spawns `mp roster enroll --no-relabel`, un-enroll (the FEAT3-UNDO "Undo naming" / the cast strip's "Un-name", and the old name on a rename) spawns `mp roster unenroll --name --label --wav`, which takes back only that meeting's sample and forgets the person only when it was their sole one (FEAT24), the whole-person `mp roster forget --name` is reachable only from FEAT3-MANAGE "Remove", which confirms, and rename (FEAT3-MANAGE, plus the cast strip's "Rename everywhere", UX40) spawns `mp roster rename --old --new`, so the matching + k-means logic keeps one owner. A label with no voiceprint (a `speaker_unknown` line, an unclustered raw id) is never enrolled: naming it is overlay-only, so it cannot hit `roster enroll`'s missing-embedding exit 2. The **reads** the daemon does directly are the read-only Preferences ▸ Pipeline "People" list and the Library's People rail (DV3), both through `RosterProfile` (name + sample count), the same display-only exception `VoiceprintProfile` makes for `voiceprint.json`.

Renaming is one path for both surfaces, `RosterRename.run`, because `mp roster rename` alone renames a name nothing else on disk uses: summaries and transcripts keep whatever they were written with, so a rename would empty the renamed person's history in the very rail that lists it. So the rename **carries**: after the CLI call lands, the new name is written into the reversible `<stem>.speaker_labels.json` overlay of every meeting the person appears in (`RosterRename.carry` over `PeopleRail.renamed`). Three shapes, all covered, because a person reaches a meeting three ways: the pipeline baked the roster name into `<stem>.json` at finalize (no overlay entry, so map the raw label), the name came from an in-app naming (rewrite the overlay value), or a regenerate did both. `<stem>.json` is never rewritten (FEAT3-UNDO's invariant) and identity mappings are pruned, so renaming back collapses what the carry added. A failed carry is not a failed rename: the roster entry has already moved, so the per-meeting failure is logged and the caller is told the rename succeeded.

`roster rename` emits `pipeline`/`roster_renamed`, `roster unenroll` emits `pipeline`/`roster_unenrolled` (`name`, `label`, `stem`, `removed`, `person_removed`; the counts live on this row only) and the daemon-side undo and rename-unenroll emit `coordinator`/`roster_undo_{done,failed}` and `roster_rename_unenroll_{done,failed}`; the daemon-side rename/remove emit `coordinator`/`roster_{rename,remove}_{requested,done,failed}`, with `meetings_carried` on the rename's `done`.

**Missing is empty, unreadable is not (STOR9).** `roster.json` and `voiceprint.json` are read through `storage.load_json_object`: an absent file is an empty roster or no print, and a present one that cannot be read, is not JSON, or is not its shape (a top-level list, a non-object person, an embedding that is not 256 numbers) is `storage.StoreUnreadable`, `kind` `io` or `parse`. Readers degrade: `RosterStore.names` and matching name nobody, `_me_signals` skips the print, and finalize goes on. Writers do not: `enroll` moves an unparseable roster aside as `roster.json.corrupt-<UTC yyyyMMdd-HHmmss>` and writes the new person (`quarantined_to` names where it went), and every other writer, and every writer over an `io` failure, refuses and leaves the file as it was. `VoiceprintStore.update` refuses, and finalize skips the enrol rather than resetting the print. `enroll`, `unenroll`, `forget`, `rename` and `update` hold an exclusive `flock` on `<file>.lock` (0600, never removed) around the read-modify-write, so two namings a moment apart keep both people. `summarize` refuses a present but unreadable `<stem>.speaker_labels.json`, `<stem>.transcript_corrections.json` or `<stem>.markers.json` (`OverlayUnreadable`, exit 1, naming the file) rather than summarize without the owner's edits; a missing one is the normal case. Each refusal, quarantine or skip emits `pipeline` / `store_unreadable` with `store` (`roster`, `voiceprint`, `speaker_labels`, `transcript_corrections`, `markers`), `path_kind` (`config` or `library`, never the path), `reason` (the errno name or `unparseable`) and `outcome` (`refused`, `quarantined`, `skipped`; the spec's `action` is every row's event-name key). `mp doctor` WARNs once per unusable roster, voiceprint or `glossary.toml`. The Swift stores follow the same rule through `StoreLoad` (`missing`, `loaded`, `unparseable`, `unreadable`) and `StoreGuard`: `SpeakerLabelStore` and `TranscriptCorrectionStore` writers start from `loadForWrite` (an unreadable sidecar throws `StoreRefusal`, "Couldn't read <file>: <reason>; nothing was changed", and an unparseable one, a non-object top level included, is moved to `<name>.corrupt-<UTC yyyyMMdd-HHmmss>` first, Python's name byte for byte), and `replace` checks the file too, since its callers computed from the fail-open read. A re-transcribe reads both sidecars typed before it touches `<stem>.json` and refuses over either broken kind (`StoreGuard.valueForCarry`): the carry re-anchors them onto the new numbering, so one it could not read would land on the wrong lines once it read again. `SavedSearchStore` and `WorkflowCorrectionStore` hold a failed launch load and re-read before their next mutation: a file that reads now is adopted, an unparseable one is quarantined, an unreadable one refuses. `GlossaryStore` follows ARCH9: a `glossary.toml` that will not read or parse holds `readError` (shown in the Vocabulary pane with the path) and every write refuses until `reload()` reads it; and every save re-reads the file and applies only the pane's own changes since its last load or save (G012), so a term the transcript's Add to Vocabulary wrote survives, a delete stays deleted, and `flush()` with no change writes nothing. Swift emits `store_unreadable` with the same four attributes under `library` (per-meeting sidecars) or `coordinator` (the rest; `path_kind` `config` or `app_support`), through `Log.failure` with no description, since a file error's text names the path. A quarantine, and a refusal no caller reports (the launch-loaded stores' quiet mutators), posts one notification through `StoreNotice`; a throwing writer's caller reports its own refusal; `mp` reaches the same notification by appending a line to the per-spawn file named by `MP_NOTICE_PATH` (`storage.post_notice`, today the roster quarantine), which `PipelineLauncher` posts and removes when the spawn ends. `coordinator` / `consent_save_failed` is an "Always for this app" that will not reach disk (since UX97 the pick is a `config.toml` key, so this fires when that file cannot be read and saves are refused; it was a silent `try?`). `LegacyConsentMigration` reads the pre-UX97 `auto_consent.json` through `StoreLoad` once at launch: unreadable is left alone (`store_unreadable`, `refused`), unparseable is quarantined, and a loaded list is saved onto `recording.auto_consent_apps` before the file is removed (`coordinator` / `auto_consent_migrated` with `count`; `auto_consent_migration_failed` when the config cannot take it).

**`<stem>.speaker_labels.json`** next to `<stem>.wav`: `{schema_version: 1, labels: {<raw label>: <name>}, segments: {<index>: <label>}}`. Written by the Swift daemon (`SpeakerLabelStore`), read by both the daemon (`TranscriptLoader.load`, for display) and the pipeline (`mp.speaker_overlay`, on a regenerate), so the resolution is a **Swift-to-Python contract**: both sides must resolve identically, and the base label (per-segment override if present, else the raw speaker) is mapped through the `labels` name table (so a segment reassigned to a named cluster shows the name). Pinned by `Fixtures/speaker-overlay-golden.json` (CI4), which also pins that both readers are fail-open *in the same way*: an empty cluster key, an empty or non-string name, and a non-integer segment key are dropped on both sides, and segment keys are canonicalized (`"01"` reads as `1`) because Swift keys them by `Int`. Being fail-open in different ways was a real divergence, Python used to resolve a speaker to `""` or to an integer where Swift ignored the entry, so a regenerated summary could attribute lines to a speaker the Library never showed. The reversible overlay for in-app speaker naming (FEAT3-UNDO) and per-segment reassignment (FEAT3-SEGMENT): rather than rewriting `<stem>.json` in place (the old one-way door), the daemon records the assigned name/label here (and, for a cluster that carries a voiceprint, also enrolls it into the roster; a voiceprint-less label such as `speaker_unknown` or a per-line "New person" assignment is overlay-only, so naming it can no longer fail on a missing embedding). `labels` name a whole diarization cluster; `segments` override a single segment, winning over the cluster, and a segment value can be a brand-new name absent from `labels` (the "New person" path), which resolves to itself on both sides. Undo/reset drops the entry, so the original diarization label in `<stem>.json` is always recoverable. A later regenerate applies the overlay so the summary + attendees reflect it (`summarize` re-renders `<stem>.json` through `transcript_corrections.overlaid_markdown`, which composes this overlay with the text corrections below); on the first run there is no overlay. Parallels `<stem>.transcript_corrections.json` (the text-correction overlay, below); an empty overlay deletes the sidecar. A **re-transcribe** (ASR3) re-derives both keys from scratch, so the sidecar is re-anchored rather than kept: `TranscriptOverlayCarry` maps each old cluster onto whichever new cluster owns a strict majority of its speaking time and each old segment index onto whichever new segment covers half its span, injectively, dropping and reporting what it cannot place. Keeping the keys would put a name on a different voice; deleting the file would throw away work the owner did by hand.

**`<stem>.transcript_corrections.json`** next to `<stem>.wav`: `{schema_version: 1, segments: [{index, original_text, edited_text}]}`. Written by the Swift daemon (`TranscriptCorrectionStore`) when the user edits a transcript line (the Transcript tab's "Edit text"), and read by both the daemon (display overlay, so `<stem>.json` keeps the raw ASR) and the pipeline (`mp.transcript_corrections`, PIPE9) so a regenerate AND the `mp ask` embedding index run on the corrected words. Like `speaker_labels` it is a **Swift-to-Python contract**: both sides resolve by the segment's array index (`TranscriptSegment.index` = the `<stem>.json` `enumerate` position), pinned by a golden parity fixture (`Fixtures/transcript-corrections-golden.json`, read by both suites). `original_text` is the pipeline snapshot at edit time (drift detection); a reader is fail-open on `schema_version`. `transcript_corrections.overlaid_markdown` composes this with the speaker overlay so any re-read (`summarize`, `embed_index.chunk_stem`) applies both, and `transcript_corrections.publish_text` is the view every publisher sends (PIPE51: `publish_router.fanout` resolves it once and hands each sink `transcript_text`; the filesystem and LAN signatures hash it, so a correction republishes), and both sidecars are in `embed_index.STEM_SOURCE_SUFFIXES`, so a correction invalidates the cached index for the meeting it corrected (AI11 made that per stem; before it, one correction re-embedded the whole library). Undo/reset (an empty overlay) deletes the sidecar. A re-transcribe re-anchors the index keys the same way the speaker overlay's are re-anchored (above), and re-snapshots `original_text` against the new transcript so it keeps meaning "this is what the pipeline produced"; a correction the new transcript already satisfies is retired rather than carried, matching `upsert`'s existing no-op rule.

## Backlog and task delegation

The active backlog lives in `docs/backlog/`: the highest-numbered `meetingpipe-q<N>-backlog.md` (currently `meetingpipe-q6-backlog.md`) holds the process rules and band-origin notes; each task is one file, `docs/backlog/tasks/<ID>.md` (split 2026-07-17), whose `---` header of one-line `key: value` fields (`id`, `title`, `category`, `status`, `priority`, `comment`, plus `verification` while owner-owed and `closed` once done) is the task's whole state, and `docs/backlog/INDEX.md` is generated from those headers by `scripts/backlog.py` (2026-10-26). Earlier quarters are archived beside it; `q6-final.md` is the frozen done record up to 2026-10-26. Task IDs follow `<letter><number>` (`C2`, `E5`, …); the `TECH-` prefix was dropped from the active backlog and the `/tech-task` command, and historical code/ADR references keep the old form as provenance. When a task ships done-done, its header takes `status: done`, `closed: <date>` and a one-line ship note in `comment:`, and the file stays where it is, so no link to it breaks; regenerate the index in the same commit. Partial items keep `status: partial` with the remainder in `comment:`; owner-owed ones take `status: owner-verify` once the owner approves. `INDEX.md` is `merge=union` in `.gitattributes` and is regenerated after every rebase, and CI5's `backlog` fence fails a stale one (until 2026-10-26 the state lived in one hand-edited ToC table every session rewrote, and parallel landings conflicted on almost every rebase).

The delegation section at the top of the active backlog is the canonical entry contract. The `/tech-task` slash command in `.claude/commands/tech-task.md` is the codified version of it.

## What NOT to do

- Don't pull pipeline-side logic into the daemon (or vice versa). They communicate via `<stem>.meta.json` and `events.jsonl`, not in-process.
- Don't add fields to `MeetingMetaSidecar.swift` without also updating `mp.workflow.apply_overrides` and its test (`test_workflow_overlay.py`).
- Don't add Anthropic or Notion calls in the daemon. The daemon stays offline; outbound HTTP is the pipeline's job. The one sanctioned exception is FluidAudio's speech-model fetch on a cold cache, which a regulated or NDA meeting is refused (SEC36, `SpeechModelGate`).
- Don't introduce a new TOML section without round-trip test coverage in `ConfigStoreTests` — the unknown-keys-survive guarantee depends on `ensureTable` working for fresh sections.
- Don't bypass `Log.event`. Ad-hoc print / log statements break `mp logs` and `mp analyze-detection`.
