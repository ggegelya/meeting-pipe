# daemon/ - the evidence behind the rules

Every rule in [`../CLAUDE.md`](../CLAUDE.md) links to a section here. The rule is what you must do; this section is why, and what it cost to find out. Read one when you are about to touch the thing it names, when a rule looks arbitrary and you want to know whether your case is the exception, or when you are changing the rule itself. Most of these record a measurement, so they are worth reading before you re-derive one.

Kept out of `CLAUDE.md` deliberately (DOC14). That file is prepended to every prompt in this subtree, so prose there is paid for on every turn whether or not it is relevant; this file is paid for only when read. `scripts/truth_fences.py claude` is what keeps the split honest.

Adding a rule means a line there and a section here, in the same commit. Each heading carries the task id that produced it, so `docs/backlog/` and `git log` remain the long form.

## Patterns to match

### Strict concurrency is on for this target

**Strict concurrency is on for this target too (CONC4).** `Package.swift` compiles the `MeetingPipe` executable with `-strict-concurrency=targeted`, like the Core island. A new `Sendable` capture warning is a real cross-thread finding: fix it (typed payload, `@Sendable` closure, `@preconcurrency` on an un-audited Apple module, or a `Task { @MainActor in self?.x }` hop), don't silence it. `MeetingSessionController` and `SinkDispatcher` carry a documented `@unchecked Sendable` because `@MainActor` on them cascades into the GCD / Timer / delegate layer (the out-of-scope `complete` migration); prefer a real fix over adding a third.

### Pure logic on its own type with explicit inputs

**Pure logic on its own type with explicit inputs.** When a subsystem grows non-trivial branching, lift the decision into a `decide(at: Date, …) → Action` style entry point on its own struct (see `MicGate.decide`, `AudioRetention.decide`, `MeetingSourceScorer.score`, `WorkflowMatcher.match`). The host that owns AVFoundation / NSWorkspace / TCC just forwards inputs in. T3 applied this to three shipped-untested surfaces: `StatusBarModel` (title / icon / menu rows, beside the 731-line `StatusBarController`), `NotificationRouter` (which delegate calls a notification response makes, plus the identifier vocabulary), and `SearchIndexReconciler` (the FTS upsert/delete diff). Each extraction found a real defect, so treat "this is only presentation" as a reason to extract, not a reason to skip it.

**And then repoint the caller at it, in the same commit.** T3 wrote `StatusBarModel` and its 31 tests and repointed only some of the controller: `derive`, `title`, `icon(for:)` and `rows` were left with **zero production callers** for a month, while `StatusBarController` went on composing its own title, picking its own icon, and hand-ordering its own conditional rows in `populateMenu`. Two copies of one decision, one of them tested, and the archive row recorded it as lifted *out of* the controller, which it was not (`q6-final.md`, corrected by ARCH6).

They diverged, exactly the way an untested copy does. UX22 added a "Finish setup" row to the shipped menu and there was no `Row` case for it, so 19 of 31 tests were pinning a menu the user never saw; a `hasPendingPermissionIssue()` wrapper in the controller had had no call site since the extraction. ARCH6 repointed all three decisions, added the `finishSetup` case, and widened UX55's one-row source fence to `test_the_status_bar_menu_is_built_from_the_model`, which asserts the controller names `StatusBarModel.rows(`, `.title(` and `.icon(`.

The thing to take from it: **an extraction that leaves the original in place has not reduced the branching, it has doubled it**, and the new copy is the one with the tests, so the suite gets greener while the shipped surface gets no safer. If repointing the caller is too risky to do in the same commit, that is worth saying out loud in the commit message, because nothing else will notice. Two mechanical tells that this happened: a pure decision type whose functions no `Sources/` file calls, and a hand-written conditional cascade sitting next to a model that describes the same conditions.

One case was deliberately **not** collapsed and is still live: `setStopping` rebuilds the menu with `.idle`, so `headerLabel`'s `.stopping` branch is reachable only from tests and the menu header reads `MeetingPipe: Idle` for the second or two a flush takes, while the title correctly reads `Stopping…`. Fixing it changes what the menu says and shows mid-stop (the `.idle` menu also carries the Start row), so it needs its own task rather than a green-to-green refactor.

### MeetingSessionController talks to SessionHost, not Coordinator

**`MeetingSessionController` talks to `SessionHost`, not `Coordinator`.** Adding a subsystem the session logic needs means adding it to `SessionHost` (and to `FakeSessionHost` in the tests), not reaching for `Coordinator`. Protocol-type it only if a test cannot construct the real thing; a global read (the way `beginRecording` used to call `AVCaptureDevice.authorizationStatus`) has to come through the host or it takes the branch back out of reach.

### Fully-qualified type name in stored-property initializers

**Fully-qualified type name in stored-property initializers.** `Self.foo` errors with "covariant 'Self' type cannot be referenced from a stored property initializer" on Swift 5.9+. Write `StatusBarController.foo` instead. `lazy var` sidesteps this but only use lazy when deferred init is what you want.

### Combine subscriptions filter to value changes

**Combine subscriptions filter to value changes.** `removeDuplicates()` + `dropFirst()` before triggering rebuilds. The permissions poll runs at 2 s; subscribing to `objectWillChange` rebuilt the status-bar menu twice a second until the snapshot dedupe landed (`StatusBarController.PermissionsSnapshot`).

### ObservableObject and @Published debounce writes

**`ObservableObject` + `@Published` debounce writes.** `ConfigStore.scheduleSave` is the template: 500 ms `Timer.scheduledTimer`, gated on an `isInitialized` flag so the init's `didSet` storm doesn't trigger a spurious save.

### TOML round-trip preserves unknown keys

**TOML round-trip preserves unknown keys.** Read into `TOMLTable`, mutate only what the UI models, write back. New top-level tables need `ensureTable("foo")` to fetch the *live* pointer back after insertion (TOMLKit's `subscript SET` copies the source node, so first-assignment-per-fresh-table is silently dropped without this). Two stores do this now: `ConfigStore` over `config.toml` and `GlossaryStore` over `glossary.toml` (FEAT11). The glossary case is the sharper one, and since UX44 it is sharper still: the store models `[fuzzy].enabled` (the near-miss toggle) and **nothing else in that table**, so preservation there is per *key*, not per table. `writeBack` sets that one key in place rather than rewriting the table, which is what leaves `max_distance` and anything a later pipeline adds beside it alone; a write that lost them would change matching behaviour behind the user's back. The glossary's resolution is mirrored from `mp.glossary` and pinned by `Fixtures/glossary-golden.json`, whose `fuzzy_enabled` field the Swift store is now checked against too. It now has two callers rather than one (FEAT12 added the transcript's "Add to Vocabulary"), and the second went in as `GlossaryStore.addTerm` rather than as its own writer for exactly that reason: a second place that decided what a live row is would drift from `liveTerms` and take the fuzzy-preservation guarantee with it.

## Don't

### No outbound HTTP from the daemon

Don't call Anthropic / Notion APIs from the daemon. Outbound HTTP belongs in the pipeline.

### Launch at login has one owner

Don't `bootout` the resident `com.meetingpipe.daemon` agent from inside the app, and don't add a second mechanism for login-start. That agent is what launches the app, so booting it out kills the process doing the booting, under the user's pointer. `LaunchAtLoginService` (UX42) is the one owner: it reads `launchctl print-disabled gui/<uid>` and writes `enable` / `disable`, never `bootout`, and never rewrites the plist's `RunAtLoad` (launchd's disabled-overrides database is the single source of on/off, and it is also the one that survives `install.sh` regenerating the plist). The shape it replaced is the cautionary tale: the toggle drove `SMAppService.mainApp`, which the agent never consulted, so the app started at login however the switch was set and turning it off unregistered something that had never launched anything. The shell half of the same rule is `scripts/lib/login-agent.sh`, sourced by `install.sh` and `rebuild.sh`; `install.sh`'s old `launchctl load -w` re-armed the toggle on every install, because `-w` *is* a write of an enabled override. Editing that helper means re-running `sh scripts/test-login-agent-guard.sh`. **That one owner owns relaunch-after-quit too, so a surface asking "would a quit really quit" has to consult it and not only `UISettings.disableAutoRestart`**: the status bar kept offering "Quit (do not relaunch)" with the agent disabled, describing a distinction the machine no longer made (UX55). It reads `status().isOn` in `refreshMenuBeforeDisplay` and caches it, deliberately: `populateMenu` also runs on every model-download progress tick and every processing-count change, and `status()` spawns `launchctl`, so an inline read would be a subprocess per tick on the main queue.

### Startup work and the single-instance guard

Don't add startup work to `App.main()` above `SingleInstanceGuard.standDownIfPeerIsRunning()` (UX54). Everything above that call runs in the copy that is about to quit as well as in the one that lives, which is why the SEC8 Keychain migration sits below it: two processes racing on that migration was the reason to order them this way, not tidiness. The guard's exit status is `EXIT_SUCCESS` and must stay there, because the LaunchAgent's `KeepAlive = { SuccessfulExit = false }` reads a non-zero exit as "bring me back" and would respawn the stood-down copy every `ThrottleInterval` seconds forever. The half that decides which copy dies is pure (`decide`) and the newcomer always loses, since the incumbent may be mid-recording; keep it that way rather than reaching for `NSApp` inside it. **And never ask AppKit who this process is up there.** `NSRunningApplication.current` before `NSApplication` exists is a *placeholder*: measured 2026-08-04 across three live instances, it answers `processIdentifier` **-1**, nil `bundleIdentifier`, nil `launchDate`, `isTerminated` **true**. The guard shipped reading its own identity from it, and `decide` over a current with pid -1 reduces to `peer.pid < -1`, false for every real pid, so it returned `.start` to every copy and `second_instance_stood_down` was never emitted once while the owner watched two and three daemons run. The peer *query* was never the broken half and does not need moving or warming: `runningApplications(withBundleIdentifier:)` at `main()` entry, before `NSApplication`, correctly listed 0 then 1 then 2 peers with the right pids in the same probe. So identity comes from the kernel (`ProcessInfo.processInfo.processIdentifier` and `SingleInstanceGuard.kernelStartTime`, a `sysctl` `KERN_PROC_PID` read of `p_starttime`), which needs no Launch Services connection. Two facts that come with it: a peer's Launch Services `launchDate` is nil far more often than not (79 of 104 running apps on the dogfood Mac, **including the launchd-started MeetingPipe**), so the kernel read backs peers too rather than letting the order fall to pid comparison near the ~99998 wrap; and the two clocks are the same one, median disagreement 14 ms over the 25 apps LS did date. The wider lesson is the one that cost the walkthrough: a guard whose failure mode is "decided not to act" is silent by construction, so it logs one unified-log line naming the peer count on the start path too, not only on the stand-down.

### A deny-list of sidecars rots against the inventory

Don't pick a file out of a directory by excluding the ones you know about. A deny-list has to be re-completed every time a sibling is added, and it says nothing at all when it is not: the reader silently takes whatever `readdir` handed back first.

CI6 is the worked example, in `MeetingStore`'s row loader. The transcript is `<stem>.json` exactly, and both writers agree on that (`orchestrate._finalize_streamed_transcript` on the Python side, the FluidAudio draft on ours). The selector used to be a `files.first` over `.json` with the known sidecar suffixes excluded, and that list had fallen **thirteen sidecars** behind the inventory in `ARCHITECTURE.md`'s on-disk table, `.embeddings`, `.filesystem`, `.speaker_labels`, `.markers`, `.recovery` and the rest among them. Picking one of those yields a sidecar with no `audio_seconds`, so the duration recovery downstream returns nil and the row reports nothing wrong.

Match the name you want (`$0.lastPathComponent == "\(stem).json"`). It cannot fall behind, because it never had to enumerate the things it is not.

The general shape, worth carrying past this one seam: a rule written as "everything except the ones I listed" has a maintenance obligation attached to a file nobody edits when they add the twelfth sidecar, and its failure is silent by construction. Prefer stating what you want over stating what you do not.

### What belongs in an always-loaded file

`daemon/CLAUDE.md` holds **constraints you must obey while editing Swift in this subtree, and nothing else**. That is DOC15's answer, written down so the next session at the cap inherits a decision instead of trimming to fit.

The reasoning is a cost the file pays that other docs do not: it is prepended to every prompt in its subtree, so every byte is re-read on every turn, forever, by sessions that may never touch the thing it describes. A rule earns that because obeying it is unconditional. A lookup table does not, because it is consulted occasionally and a session that needs it can open the file it lives in.

**What the cap actually measures.** `CLAUDE_MAX_BYTES` is a whole-file backstop and `CLAUDE_MAX_ENTRY_BYTES` a per-entry one, and the two catch different failures. Per-entry catches a narrative pasted where a rule belongs. Whole-file catches the thing that has no individually guilty line: DOC14 split the narrative out on 2026-08-17 and left 5,487 bytes of headroom, and one day of parallel batches spent 5,430 of it adding fourteen legitimate one-line rules. Nothing in that day was wrong. Accretion is the failure mode, which is why the fence's own message says raising the constant is not the fix.

**The cost of ignoring it is displacement, not just size.** At the cap two rules could not land where they belonged. FEAT15's tour-anchor rule, a Swift rule about Swift files, went into the **root** `CLAUDE.md`, where every session in the repo reads it including ones that never open Swift. CI6's deny-list finding got no rule line at all and survived only as a comment inside `MeetingStore`, which no session is guaranteed to read. A full file does not stop rules being written; it scatters them somewhere worse.

**What DOC15 did, in the order to try again.** Move what is not a rule (the file index went to `ARCHITECTURE.md`, whose Daemon section the index's own intro already named as the authority). Delete a second copy of something another always-loaded file already says (the build commands are in the root verify table). Merge rules that share a subject, since two lines on one anchor were two lines to read. Trim narrative out of rule lines that had it inline while the section they link to carried it in full. Only then consider a further subtree split, which is the owner's call because a fourth always-loaded file is a cost every session in that directory pays.

### A save must never destroy the old state before installing the new one

Don't write a file by removing the destination and moving a temporary into its place. `Data.write(to:options:.atomic)` already writes to a temporary and renames it in, so the manual dance is redundant, and it is strictly less safe than the one-liner it wraps.

PERF8 found the shape copy-pasted into **four** sidecar writers: `SpeakerLabelStore`, `TranscriptCorrectionStore`, `CorrectionStore` and `PipelineFailureSidecar`. All four did `write(to: temp)`, then `removeItem(destination)`, then `moveItem(temp, destination)`.

**The failure direction is the point.** Between the remove and the move the real file does not exist, and the only copy of the data is in a `.tmp` that nothing in either tree reads or sweeps. Every reader here is fail-open, so a missing file reads as empty rather than as an error. A process death in that window therefore does not lose the edit being saved: it silently loses **every** entry the file ever held, unrecoverably, and the app reports no problem at all. Three of the four hold hand-made edits the pipeline cannot regenerate, which is which voice the owner said was Sudip and which words they corrected.

That window is not theoretical for this app. Four `.ips` reports landed on 2026-08-13 and 08-14, and REC12 is a confirmed uncatchable ObjC abort that runs no termination handler, so nothing gets a chance to tidy up.

**Two things to copy.** First, the repo already had the right pattern one file over: `WorkflowStore.persist` writes a `.writing` sibling then `replaceItemAt`, and `ConfigStore` does the same. Reach for those or for plain `.atomic` rather than inventing a third shape. Second, **fence the shape rather than the effect**. A behavioural test here is weak: the obvious way to make a write fail, an unwritable directory, fails at the *first* step, so the old code preserves the previous file too and the test passes against the bug. The window only opens between two operations inside one function and is not observable from outside the process. `AtomicSidecarWriteTests` therefore greps the four writers for `moveItem(at: temp`, which is what actually fails against the pre-fix tree, and keeps the behavioural tests as a check on the property rather than as the regression guard.

A defect that was copy-pasted four times will be copy-pasted a fifth. The grep is what catches that.

### A zero is a measurement, and an unfinalized WAV is full of them

Don't let a parser return `0` for something it could not read. A nil propagates into a fallback that was written for the unknown case; a zero flows into arithmetic as if it were a fact, and `max(x, 0)` quietly discards whatever the zero was standing in for.

REC14 is the worked example, and the interesting part is that the filed diagnosis was wrong in a way that would have shipped a green test over a live bug.

The 2026-08-14 incident recovered a 113-minute call as a 46.6-minute file, missing about 67 minutes of the far side. Everyone's reading, including REC13's own gotcha above and REC14's spec, was: the process was killed, so the WAV headers were never finalized, so the durations were unreadable, so `mergeLengths` took its no-duration fallback, which ends with the mic by REC9's deliberate bias. The proposed fix was to re-bias that fallback.

**That fallback never ran.** `AVAudioFile` writes the `data` chunk's size as a placeholder and patches it when the handle closes, so a killed writer leaves the field at `0` with the samples still on disk. `audioDurationSec` computed `dataSize / byteRate` and returned `0.0`, which is not "unreadable". `mergeLengths` saw two readable durations, took `max(2798.5, offset + 0)`, and cut to the mic. The observed final was 2798.5 s, which is the mic's length to the sample, and that is the fingerprint that settles it. Re-biasing the nil branch would have satisfied the spec's acceptance test and changed nothing at all.

The real fix is that the length was never a guess to begin with. `byteRate` lives in the `fmt ` chunk, written when the file is created, so it survives any kill; only `dataSize` needs patching. Measuring the payload against the file's actual size makes the duration exact arithmetic on the one path where the header cannot be trusted, which is why REC14 took route B (derive it) over route A (re-bias the fallback): route B dissolves the fallback rather than tuning it.

Two habits worth carrying. **Check what a parser returns for a damaged input before designing around it**; a five-line probe that built an unfinalized WAV and printed `0.0` is what redirected this task. And **treat a non-positive duration as no measurement** at the policy layer too, as belt and braces, so the next zero from anywhere cannot win a `max()` the way this one did.

### A documented divergence is still a divergence

Don't let a comment explaining why two surfaces disagree stand in for a reason they should. Writing the split down makes it look decided, and the next reader inherits a justification instead of a defect.

UX79 is the worked example, and what makes it worth recording is how well documented the bug was. `StatusBarController.setStopping` set `titleState = .stopping(...)` and then called `rebuildMenu(state: .idle)`, so the menu-bar title read "Stopping…" while the menu header one click below it read "MeetingPipe: Idle". Three separate places said so on purpose: the call site ("Deliberately `.idle`, not `titleState`: the menu built during a flush is the idle one"), the field's own doc ("Deliberately NOT `lastMenuState` ... Collapsing the two would change what the menu says mid-stop"), and `menuInputs` ("`state` is a parameter rather than a read of `lastMenuState` because `setStopping` passes `.idle` here on purpose"). Each revision that touched it re-justified the split rather than questioning it, and T3's archive entry then claimed the fix had shipped, which ARCH6 had to correct in place.

**The cost was hiding in the half nobody wrote down.** The `.idle` menu does not just carry the wrong header, it carries the `.idle` **rows**, which means a Start Recording row. Its action reaches `MeetingSessionController.toggleManual`'s `.stopping` case, which is a bare `break`. So the app offered a control that did nothing, said nothing and logged nothing, for the length of the post-processing. `rows(_:)`'s own switch already had `default: break` with the comment "`.stopping` is a genuine no-op mid-flush", so the model knew the right answer the whole time and the controller was withholding the state that would apply it.

The fix was one line, `rebuildMenu(state: titleState)`. That is the shape to watch for: when a comment says two things are deliberately out of step, check what *else* rides on the value being passed, because a state is rarely consulted for one thing only.

Two things to carry. **Fence the call, not just the output.** Every model-level test here would stay green if a later caller passed `.idle` again, since they read `StatusBarModel`; the regression that actually recurs is at the call site, and it recurred three times. And **an unreachable branch is a claim about a state you never enter**: `headerLabel`'s `.stopping` case was written, correct, and reached only from tests for as long as the split stood, which is the same finding CI6 made about a deny-list nobody could reach the end of.

### A guard belongs at the funnel every path goes through, not at the call sites

Don't put a "have I already got one of these" check on the entry point that happened to need it. Put it where every entry point converges, or the next one added inherits nothing and the bug comes back under a different name.

PIPE18 is the worked example, and what makes it worth writing down is that the fix already existed. PIPE11 built duplicate-click coalescing in July, correctly, on `SinkDispatcher.enqueueLibraryRun`, after a Reprocess and three regenerates raced on one stem and the surviving summary was decided by which subprocess exited last. `SinkDispatcher` has four enqueue paths. That guard covered one. The `.full` and `.retranscribe` paths, and the private funnel all three call, had nothing.

So on 2026-08-14 the owner pressed **Retry pipeline** seven times in twelve seconds and got seven full `mp run-all` passes queued for one 25-minute recording, then removed six by hand. Their log shows `pipeline_queued` at depths 1 through 7 and **zero** `pipeline_coalesced`, because nothing on that path could emit one. The class of defect had been diagnosed, fixed and shipped a month earlier, for one kind out of three.

The guard now lives in the private `enqueue(job:completion:)`, and `isAlreadyQueued` is pure beside it. A fifth entry point gets the behaviour by construction.

**Two things to copy, beyond the placement.** Make it a coalescer rather than a lockout: the predicate reads only what is *in the queue*, so once a job has run and left, the same ask queues again, and the legitimate second retry after a second failure keeps working. A guard that blocks that is worse than the bug it fixes. And **pick the identity from the data, not from the vocabulary**: the first draft keyed on the stem, meaning `file.deletingPathExtension().lastPathComponent`, which reads as obviously right because one directory holds every recording under a timestamp stem. It is wrong, and `SinkDispatcherTests` caught it in the same run: those tests build per-test temp directories each holding a `clip.wav`, so a stem-keyed guard collapsed two unrelated recordings into one. `.full` and `.retranscribe` are only ever enqueued with the recording URL, so the file itself is both stricter and sufficient; a library run keeps PIPE11's `(verb, stem, backend)` and never consults the file, which is what lets it anchor on the transcript while the queue holds audio.

### A terminating subprocess must prove it is still the one you are tracking

Don't let a `terminationHandler` write state without first checking that the process handing it the news is the one the object currently owns. The handler is asynchronous and the object is not, so by the time it runs the world may have moved: the process may have been cancelled, or replaced by a newer one doing the same job.

LOCAL20 is the worked example, and the owner's log is what settles it. They switched the summarization backend away from a local model mid-download and got a failure banner they could not discard. One line explains the whole thing:

```
[2026-08-04T15:00:14.626Z] model prefetch terminated rc=15 state=failed(... error: "prefetch exited 15")
```

**`rc=15` is SIGTERM**, which is exactly what `cancel()` sends. Nothing failed. The prefetch ran three minutes of healthy traffic and was killed by the user's own switch, then reported itself as a failure 99 seconds before the screenshot. `cancel()` had cleared `process` but left `state` at `.downloading`, and `handleTermination` tested only that state and a non-zero exit status, so a signal the app itself sent became evidence of a fault.

The identity check is the fix, and it is worth more than the state it protects. `handleTermination` also nils `process` and `stdoutHandle` and clears `currentModelId` on its way past. `ensure` replaces an in-flight download by calling `cancel()` then `spawn()`, so the abandoned process's termination could arrive *after* the replacement had started and tear down the live download's handles, or write `.failed` for the previous model over the new one's `.downloading`. That path was reachable and had never been reported. `terminationOutcome(isTrackedProcess:state:terminationStatus:)` is pure and returns `.ignore` for it, and the handler returns before the teardown rather than after, which is the point rather than an optimisation.

Two smaller rules came with it. **Cancelling should leave an honest state**: `.idle`, not the `.downloading` it was, or the next surprising event finds an object that still believes work is in flight. And **a state a user cannot clear is a bug even when it is true**: `.failed` had `retryable: true` and nothing else, so the only exit from a failure was to re-download the model you had just moved away from. `.completed` already auto-collapsed and was the model for what `.failed` lacked.

Worth knowing for the next reader: the menu-bar title gives the download clause priority over the processing clause while idle, so a phantom failure also suppressed `Processing (N)` indefinitely. The owner's screenshot has `↓ failed` in the menu bar with "24 meetings failed" in the menu below it, so the one clause DSN7 allows was spent on the untrue thing.

### A shared controller needs a control that outlives the surfaces sharing it

Don't hoist state up to a parent for continuity and leave every control for it down in the children. The hoist is usually right; what it quietly creates is a window where the thing is running and nothing on screen can stop it.

UX78 is the worked example. `AudioPlaybackController` is a `@StateObject` on `MeetingDetailView` rather than on a tab, deliberately, because that is what lets a summary citation chip jump into the transcript and keep its play head. But `play`, `pause`, `togglePlayPause`, `seek`, the rate and channel pickers all live inside `AudioTab`, and the per-line play affordances inside `TranscriptTab`, so selecting Summary removed the entire transport while the audio kept going. The owner's report is exact: "I have no controls, and playback still running". The only exits were switching back to a tab that has controls, or closing the window, which on a shared screen is worse than merely inconvenient.

The codebase already half-knew the rule. `TranscriptTab` pauses when an editing or naming sheet opens (playback scrolls the list out from under the cursor) and again on `rightMouseDown` so a context menu can open against a still list. Two narrow cases handled inside one tab, while the widest case, the tab switch itself, went unhandled. That is the shape to watch for: local pauses accumulating in a child are evidence that the parent owes a control, not that the cases are covered.

Two rules for the control itself, both of which look like details and are not. **A paused play head still needs its control**, so the visibility test cannot be a bare `isPlaying` or the press that stops the audio is also the press that hides the way to resume it. And **check the loaded file, not just the player**: `MeetingDetailView` has no `.id(meeting.stem)`, so SwiftUI reuses it and the controller survives a selection change with the previous meeting's file still loaded, while only the two audio-bearing tabs call `load`. Switching meetings from Summary therefore replaced nothing, so the meeting you just left kept playing under the new title, and a transport shown then would have driven the wrong audio. `DetailTransport.decide` takes both the loaded URL and the meeting's own, which makes that unreachable rather than unlikely; the stem-change hook pauses as well, so the sound stops even before the header hides.

### An aggregate label needs the distinction the row already makes

Don't let a surface that summarises many items collapse a distinction the per-item surface makes correctly. The summary is the one a user sees first, so when the two disagree the summary is the one that is believed.

UX77 is the worked example, and the shape of it is worth more than the fix. `SinkDispatcher` publishes a queue depth, `processingJobs.count`, which is the union of the running job and everything waiting: the active job is the list's head only once it has started. Three aggregate surfaces rendered that number, and all three hardcoded the word "Processing" beside it, because the depth was the only thing the seam carried and no one surface had any way to know better. The meeting's own row, meanwhile, split the two states deliberately (`ProcessingPresentation.label` returns `Queued: <job>` for a pending job and stage-plus-elapsed for a running one) and was right the whole time. So the owner's screenshot had a toolbar pill reading `Processing 1` directly above a row reading `Queued: Re-transcribe`: one job, two nouns, contradicting each other about whether anything had begun. With nothing started, `Processing 1` was describing zero running jobs.

The fix that generalises is not softening the word. It is **giving the aggregate the same discriminator the row has, at the seam**, so `onQueueDepthChanged: ((Int) -> Void)` became `onQueueActivityChanged: ((QueueActivity) -> Void)` carrying `isRunning` alongside `depth`. The discriminator already existed one line away (`activeJob != nil`); it simply had never been published. Then derive the word once, in `QueueActivityPresentation.noun`, because three call sites each holding their own copy of a string is what let them agree for months and then drift. This is the same rule as `SummarizationEngine` for backend names and `PublishLanding` for sink names, applied to a state word rather than a proper noun.

Two smaller things that fell out of it. The noun describes the head and the number counts the whole queue, which is how a person says it out loud; the richer split (`Processing 1 · 2 queued`) was rejected because DSN7 gives the menu-bar title exactly one clause and a split is two things competing for it. And `ProcessingTracker` publishes one `QueueActivity` rather than two `@Published` properties, since the halves are always read together and publishing separately would be both an extra re-render and one more way for the toolbar to disagree with the menu bar.

### A caption added to a fixed-width row is a width decision

Don't append a caption to a row in the Library rail (or any fixed-width list row) without deciding what gives way when they no longer fit. Nothing warns you, and the failure is silent until someone screenshots it.

UX76 is the worked example. `WorkflowScopeRow` accumulated five siblings in one `HStack` under a single `.lineLimit(1)`: emoji, name, `· default`, WF9's `· duplicate name`, FEAT11's `· no context`. Each caption arrived with its own task, each was individually defensible, and each source comment argues correctly for the information it adds. What nobody owned was the total. SwiftUI truncates siblings together and a plain `Text` has no priority over its neighbours, so the row degraded exactly backwards: the footnotes describing the workflow survived at the expense of the name identifying it. The owner's main workflow, 105 meetings, rendered as `Pers… · defa… · no c…`. The other rows corroborate the mechanism cleanly, since `General` carried no captions and read fine, `Client work` carried one and kept its name, and `Personal` carried two and lost everything.

Two habits come out of it. **Give the identifying element `.layoutPriority` above its decorations**, so truncation starts at the footnotes; a row where the name and its captions are peers will eventually eat the name at some width. And **prefer a glyph to a phrase for a boolean footnote**: `WorkflowRailRow.decide` returns one `Marker` per fact carrying its own symbol, VoiceOver label and optional tooltip, which is a fraction of the width and keeps every fact reachable. Demoting to a glyph is only honest if the words survive somewhere, so each marker keeps its `.help` and its accessibility label; a glyph with neither is a fact deleted, not a fact moved.

The composition is pure and tested (`WorkflowRailRowTests`) precisely so the next caption has to come through `decide` rather than being appended to the `HStack` the way the first three were. Note the tooltip layering while you are in there: WF9's explanation is attached to the whole row and FEAT11's to its own element, deliberately, so they do not fight; the collision marker therefore carries a nil `help` on purpose.

### The sidecar is a single Swift-to-Python contract

Don't add a key to `MeetingMetaSidecar.build` without also updating `mp.workflow.apply_overrides` on the Python side. They're a single contract; the sidecar is the only Swift to Python surface.

### Publish state comes from publish.json

Don't read a per-sink sidecar (`<stem>.notion.json`) to learn whether a run published. A failed publisher never writes one, so an earlier run's file survives. Read `<stem>.publish.json` via `PublishResult.load` (PIPE1). **`Meeting.publishState` disobeyed this rule until PIPE14** and read `<stem>.run.json`'s `publish_state`, which only `mp run-all` refreshes, so a standalone `mp publish` left all six branch sites frozen at the previous verdict; both readers now go through `PublishResult.resolveState`, which prefers the publish sidecar and keeps the run sidecar only as a pre-PIPE1 fallback. Its shape, the `"full"` / `"partial"` / `"none"` vocabulary six sites branch on, the `mp prefetch-model` progress events `ModelDownloadSupervisor` switches on, and the speaker-overlay resolution are all pinned against Python by generated fixtures (CI4, `CI4ContractFixtureTests`). Changing the Python writer means regenerating them: `cd pipeline && uv run python ../scripts/gen_contract_fixtures.py`.

### Re-runs go through the pipeline lane

Don't spawn `mp summarize` / `mp publish` for an existing meeting outside the pipeline lane. `MeetingLibraryService.regenerateMeeting` / `.republishMeeting` enqueue a `.libraryRun` job (PIPE11) so a re-run cannot overlap a run-all or a second re-run on the same stem; calling `launcher.summarize(...)` directly from a new Library action puts the last-writer-wins race back, and it was decided by which subprocess exited last. The mirror trap is inside the lane: the regenerate chain's publish leg calls `performRepublish`, not `republishMeeting`, because re-entering the queue there would wait on the slot the job itself is holding.

### A subprocess this app killed is not a failure

Don't report a subprocess this app killed as a failure. `PipelineLauncher.LaunchError.cancelled` exists because the daemon sends the SIGTERM itself on the owner's Cancel, the child exits 15, and every surface used to render that back as `Pipeline failed: pipeline exited 15: …` captioned with whatever the child last wrote to stderr, which for a killed run is a routine INFO line (UX50). Any site that renders, notifies, or logs a pipeline error asks `PipelineLauncher.isCancellation(err)` first: four already do (`SinkDispatcher.invokePipeline`, `PipelineJobDispatcher.route`, and `MeetingLibraryService`'s regenerate / republish / ask legs), and the Library's one Cancel button reaches **all** of them, since UX28 put the re-summarize and publish re-runs in the same retain slot run-all uses. What does *not* change is the modelling: a cancelled job still completes as a failure so the row stays retryable, and it still writes a marker, because a row with no terminal sidecar sits in Processing with nothing running and then ages into a `.failed` that names no reason at all. The cancel flag is per run (`PipelineRunSlots.RunHandle`), never a bool on the launcher: a click landing just after a run ended would otherwise still be set when the next run started and label *its* genuine failure a cancellation. The same task made `nonZeroExit`'s second value a **caption** rather than the raw tail, picked by `failureCaption(stderr:)` (last `ERROR`/`CRITICAL` line, else last `WARNING`, else the tail); LOCAL16's `.memory` staging rides on the marker surviving that selection, which it does because `orchestrate` reports the fault through `log.exception`. **And the half that took a second pass to see: a completion nobody is told about is still a completion.** The row's live progress entry used to be cleared by the Coordinator's `onDone` / `onError`, which is to say by the *reporting* of a completion, while `PipelineJobDispatcher.route` returns early for exactly the two kinds that report nothing (a cancel, and a library re-run whose own surface reports it). So the quieting shipped by UX50 took the clear with it: the owner's cancelled Reprocess left the row frozen at `Cleaning up 0:20` in the **In progress** block, beside an idle toolbar, and it survived closing and reopening the Library because the entry lives on `LibraryWindowModel` and not in the view. `SinkDispatcher.onActiveProgressEnded` is the one clear now, fired from `completeActiveJob` on every path, next to UX28's busy-chip clear and for the same stated reason; the done and error closures no longer touch it. The class to watch for is state whose lifetime is a **job's** being cleared from a branch whose lifetime is a **message's**.

**UX69 widened the rule past the subprocess, and the widening is the part worth remembering: a full job has two halves and only the second one is a process.** Cancel used to be gated on the row's live entry, which only a pipeline heartbeat wrote, so on the owner's 110 minute meeting the row offered no Cancel for 58.6 s and about 52.5 s of that was the daemon's own FluidAudio pass, a share that scales with meeting length. The entry now begins when that pass starts and moves to a second phase at the spawn. Publishing it that early is only honest because the pass is genuinely interruptible: `SinkDispatcher` holds the pass in `transcriptionTask`, `cancelActiveJob` signals both that and `cancelActiveRun` (each a no-op for the half that is not live, so neither the click nor the queue has to know which one is), and `PipelineLauncher.isCancellation` answers for both error types, since a click reports itself as `LaunchError.cancelled` from a killed spawn and as a `CancellationError` from a cancelled Task. **Do not offer a Cancel over a phase that cannot be stopped.** A visible control that does nothing is worse than the silence it replaced, which is why leg (a) of that task could have shipped alone had the pass turned out not to be interruptible.

**The interruption is not uniform, and the bound belongs to FluidAudio rather than to this repo.** `AsrManager.transcribe` routes long audio through upstream's `ChunkProcessor`, which calls `Task.checkCancellation()` once per chunk and again before every CoreML prediction, so a click during ASR lands inside a chunk. `DiarizerManager.performCompleteDiarization` is synchronous and declares no checkpoint at all, so a click that lands inside diarization is honoured when it returns. `FluidAudioRunner.transcribe` therefore carries checkpoints at each phase boundary it owns, the one after diarization being the one that closes that gap. Do not try to shorten it by driving the diarizer chunk by chunk here: that re-implements its speaker tracking and moves output DIAR2 tuned against a hand-labelled corpus, which is DIAR4's migration and not a cancel.

**And the trap the marker rule sets on this path: a cancelled pass has more than one way out.** The obvious one throws, and the other does not. A click landing in the last moments of the pass leaves the runner with a finished sidecar and nothing to throw from, so without `SinkDispatcher`'s own `Task.checkCancellation()` after the call returns, the click is swallowed, the pipeline spawns for a job the owner stopped, and **no marker is written at all** (verified by removing that one line: the test then finds a spawned run and a nil sidecar stage). That is the empty-recording shape again, a row sitting in Processing with nothing running until the 2 hour age fallback turns it into a `Failed` naming no reason. The rule to carry: when work becomes cancellable, enumerate its exits and check that each one writes the terminal marker, because the exit that does not throw is the one that looks finished.

### Nothing blocking inside an audio render callback

Don't log or write files from inside an audio render callback (`MeetingRecorder` taps, `SystemAudioCapture`). Those run on real-time threads; blocking work there glitches the recording.

### The two capture channels need an explicit length policy

Don't merge the two capture channels without an explicit length policy, and don't let a byte count stand in for "the merge worked". `amerge` has no length option at all (`ffmpeg -h filter=amerge` on 8.1 lists `inputs` and `layout_mode` and nothing else), so a bare merge ends at the **shorter** input: a 10 s mic plus a 3 s system produced a 3.000000 s final, measured by hand with the shipped arg vector. `produceFinal` then deleted both intermediates, and the 4 KiB plausibility floor waved the result through at 192 KB while `recording_stopped {produced_final: true}` reported a clean success. Across the owner's whole log that discarded mic tail on 140 of 153 recordings, and on 2026-07-15, where system capture only came up 35.9 s into a 41.2 s meeting, it destroyed 87% of one. `RecordingPostProcessor.mergeLengths` is the one policy now (`apad` on each leg, `adelay` for a late system channel, `-t max(mic, offset + system)`) and `outputIsPlausible` re-measures the produced file against that target, failing closed onto the kept intermediates plus a `.recordfail.json`. **Padding the tail is not the whole fix**: a channel that started late carries the END of the meeting, so merging it at sample 0 puts real words against the wrong timestamps, which is worse than dropping them because the result reads as a correct transcript. And note what the fix had to repair besides code: two comments and one notification body asserted this padding for months before it existed (`MeetingRecorder.stop`'s "the ffmpeg merge pads to the longer input", `RemoteAudioWarning.interrupted`, and "the recording is mic-only from that point"). They are true now, and only while the policy holds.

### Never re-open a capture file to resume writing

Don't re-open a capture file to resume writing it, and don't leave a teardown path unbounded because a sibling path is bounded. `AVAudioFile(forWriting:)` **truncates** ("Will overwrite a file at the given URL", `AVAudioFile.h:68`; measured in `SystemCaptureRetryPlannerTests` rather than taken on trust), so `retrySystemAudio` re-entering `startSystemCapture` with the same URL destroyed every system sample captured before an SCStream death (REC10). Three things made that invisible: `handleSystemAudioLost` deliberately keeps the partial on disk *and says so in a doc comment*, REC8 made the retry hands-off so no human decision stood between the death and the overwrite, and the recovered channel then merged at sample 0, so the remote side played back early by the outage rather than reading as missing. The fix is to keep the handle and pad the gap (`SystemCaptureRetryPlanner`), which also means the SCStream-start-failure branch must not delete a file that now holds real audio. The mirror trap is REC11's: `stop()` used REC7's bounded `finish(timeout:)` while `flushIntermediatesForTermination` called the unbounded `finish()` on the same writers, so the wedge REC7 exists to bound was still unbounded on the one path that runs at quit, under a comment promising "Deadlock-free" that was true about deadlock and silent about an indefinite block. Both of these are the same class: a guarantee asserted in prose on the path that does not hold it. When two paths drain, cancel, or close the same thing, check them against each other, and when a comment states an invariant, check the code under it states the same one. Note also which reads are safe: an `AVAudioFile` write handle buffers, so its `length` is rounded to what it has flushed and its header is not valid until every strong reference is released, which is why `stop()` drops `micFile` / `systemFile` before ffmpeg reads and why a test must read back through a fresh `AVAudioFile(forReading:)`.

### A notification observer with a queue makes the poster wait

Don't register a `NotificationCenter` block observer with a non-nil `queue:`, and don't leave a synchronous `AVAudioEngine` call unbounded. `addObserver(forName:object:queue:using:)` with a queue does not merely schedule the handler: it wraps it in an `NSOperation`, enqueues it, and has the **poster** block on `-[NSOperation waitUntilFinished]`. Whoever posts inherits the handler's latency, on the posting thread, which is usually a thread the app does not own.

On 2026-08-14 the poster was AVFAudio's own `engine` serial queue, posting `.AVAudioEngineConfigurationChange` from `AVAudioEngineImpl::IOUnitConfigurationChanged()` during a sleep/wake plus display-topology storm (two `did_wake_while_recording` with `engine_running: false`, repeated device changes, an SCStream restart 8 s before the stop). `MeetingRecorder` had registered that observer with `queue: .main`. A live `sample 57648` caught the engine queue blocked in **2516 of 2516 samples** at `postNotificationName` -> `_CFXNotificationPost` -> `waitUntilFinished`. Every `AVAudioEngine` call serializes on that queue, so the stop path queued behind a wait that never ended: the owner pressed stop at 17:31:43, `state_change recording -> stopping` was the last event for **52 minutes**, and `system.wav` kept growing at ~394 KB/s to 1.28 GB, on a path to the 4 GiB RIFF ceiling. `addMainQueueObserver` is the one registration now: nil queue, explicit `DispatchQueue.main.async`, so the handler still runs on main and the poster never waits.

**Read the sample before you retell this one.** The main thread was **idle** in `__CFRunLoopRun` and still servicing `MeetingDiscoveryWatcher.armPollTimer` throughout, which refutes the main-thread-freeze reading this superficially resembles, and also refutes the tidy lock story (main blocked in `removeObserver` holding the notification-center lock). **Why `OperationQueue.main` never drained that operation is not established**, and the fix does not depend on it: with a nil queue there is no operation to drain. A pickup wanting the answer needs a second sample plus `OperationQueue.main.operationCount`.

Three further things that incident settled, none of which the deadlock alone predicts:

- **Bounding the engine calls is a separate fix from removing the wait.** `stop()`, `recoverCapture` and `flushIntermediatesForTermination` all called `removeTap` / `engine.stop()` / `setVoiceProcessingEnabled(false)` synchronously on main, so each inherited any wedge on that queue. `EngineTeardown` bounds all three with abandon-on-timeout and emits `engine_teardown_timed_out` with a `path` attribute; `MicLevelMonitor.startBounded` covers the last unbounded `engine.start()`, which mattered more than it looks because that monitor's `start` and `stop` share one private serial queue, so a wedged start made it un-stoppable for the process lifetime with the tap still open.
- **Graceful termination failed too, and not where you would look.** `kill -TERM` stopped the capture but the process did not exit in 10 s and `kill -9` was required. `flushIntermediatesForTermination` **never ran**: its first statement is a `Log.writeLine`, which is unbuffered (open, seek, write, close), and that line is absent for the whole of 2026-08-14. So the block was **upstream of the flush**, in `AppDelegate.flushAndExit` before the recorder is touched. Which call blocked is **not established** (the sample predates the SIGTERM). That is why the ceiling is armed in `flushAndExit` on a global queue, not inside the flush: bounding the flush's internals would not have saved this recording, because the flush never started.
- **The cost was not the wedge, it was what the wedge did to the merge.** After `kill -9`, orphan recovery worked perfectly, and the final was still **46.6 min against 113 min of wall clock**, missing ~67 minutes of the *other side of the call*. Chain: no flush, so no finalized WAV headers, so the merge cut to the mic. ffmpeg said so in its own output (`Estimating duration from bitrate`, `Packet corrupt`). **REC14 fixed this on 2026-08-19 and corrected the middle of that chain while doing it**, which is worth reading before trusting the sentence above: it is not that the durations were unreadable and the no-duration fallback fired. An unfinalized WAV reads as **0.0**, not as nil, so `mergeLengths` saw two readable durations and `max(2798.5, offset + 0)` chose the mic. The fallback never ran. See [a zero is a measurement, and an unfinalized WAV is full of them](#a-zero-is-a-measurement-and-an-unfinalized-wav-is-full-of-them).

### installTap raises where start() throws

Don't hand a format to `installTap` without going through `GuardedTapInstall`, don't reach for the ObjC barrier from anywhere else, don't retry a tap on an engine that already raised, and don't read `MicLevelMonitor.isRunning` as "the engine is up". `AVAudioNode.installTap(onBus:bufferSize:format:block:)` reports failure by **raising an Objective-C `NSException`**, which Swift cannot catch: there is no `try` that helps and no `catch` that runs, so `objc_terminate` calls `abort()`. `AVAudioEngine.start()` one statement below it *throws*, and the shipped code guarded that one and left the fatal one bare.

**All four MeetingPipe crash reports on the owner's machine were this one call** (REC12, read 2026-08-14): identical `EXC_CRASH`/`SIGABRT`, `AVAudioEngineImpl::InstallTapOnNode` -> `+[NSException raise:format:]`, on the `MeetingPipe.MicLevelMonitor` queue, 1 to 16 hours into each run. Correlated against `events.jsonl`, `prompt_shown` precedes each abort by **0.049 to 0.097 s**, and they chain: launchd relaunches at +1.2 s and the replacement dies at the next prompt it loses the race on. Cost: on 08-13 15:00 the owner accepted the *second* prompt, so the recording starts ~4 s into the call; the 08-13 16:24 re-prompt produced no recording at all.

**Which raise condition fired is inferred, not read, and stays that way.** A crash report's `asi` field holds only "abort() called"; `NSException.reason` (the string naming the failed precondition) is nowhere in it. `UncaughtExceptionLogger` now writes name and reason to `daemon.log` before the process dies, so the next one is one line instead of a four-report reconstruction. What the guard rules out is the condition readable from the format alone: `inputNode.outputFormat(forBus: 0)` returns 0 Hz / 0 ch while the HAL has no usable input, and `AVAudioFormat` holds both happily (measured: `AVAudioFormat(standardFormatWithSampleRate: 0, channels: 1)` returns a live object), so a non-nil format is not evidence of a usable one. What it cannot rule out is the format disagreeing with the node's hardware format at the instant `installTap` re-reads it, and no pre-check can: on 08-13 the device was AirPods Pro renegotiating to 24000 Hz as the call came up, against 48000 on the 08-14 crashes.

**That last one is closed by an Objective-C `@try` barrier, shipped 2026-08-17 once the owner approved the vehicle.** `MPRunCatchingObjCException` lives in `MeetingPipeObjC`, a third target holding one `.m` and its header, and it exists as a target only because SwiftPM has no mixed ObjC/Swift target: no third-party dependency, nothing else in it, and deliberately not a dependency of `MeetingPipeCore`, whose island rules keep its floor at Foundation plus TOMLKit. `GuardedTapInstall` runs the install inside it and turns a raise into an `Outcome` plus a `mic_tap_install_raised` event carrying the exception's `reason`, which is the string a crash report never had. The staging path is unaffected, and that was checked rather than assumed: a C target with no resources emits no `.bundle`, the symbol links statically into the executable, and `rebuild.sh` copies exactly the executable plus every `*.bundle`, so its payload is unchanged. `install.sh`'s standalone `swift-frontend` pass over `MeetingPipeAppIntents.swift` never reads `Package.swift`, and still gathers its 8 const values.

**A caught raise has to be terminal, and "has to" is doing real work: both callers have a live retry path into that call.** Catching an `NSException` out of AVFAudio's C++ frames is not a clean recovery. The unwind passes through Swift frames the compiler emitted as non-unwinding, so their cleanups never run, and it leaves `InstallTapOnNode` part-way through whatever it was doing; nothing about the engine is defined afterwards. Meanwhile `MicLevelMonitor.start` runs on every prompt and `MeetingRecorder.recoverCapture` runs on every device change, so a barrier documented as "do not retry" would have been retried within a day. It is structural instead: a raise **condemns the engine**, held weakly by identity so the record dies with the engine, and the seam refuses a condemned engine every later tap. The way back is a replacement, never a retry, which is why `MeetingRecorder.start` swaps its own engine when it finds it condemned (otherwise one raise during a device change would have cost every later recording, not just that one), and why `MicLevelMonitor` simply stops metering (its engine is a `let` and a flat waveform is its documented degradation). `Outcome` keeps the two apart on the type: a refused *format* is transitional and stays retryable on the same engine, a raise never is.

**No test can demonstrate the abort, and a comment claiming otherwise was written and then measured wrong.** XCTest installs its own ObjC exception handler around each test case, so neutering the barrier turns the raise tests red as ordinary failures ("required condition is false: format.sampleRate == hwFormat.sampleRate (NSInvalidArgumentException)") rather than killing the binary. The daemon has no such handler, which is the whole bug. So the tests pin the testable half, that a raise comes back as a value with its reason attached and that the engine is never offered a second tap; the abort itself stays evidenced by the four crash reports.

**The state half is a separate bug and is fixed.** `AVAudioEngine` stops itself and drops its taps on a configuration change and tells nobody who did not ask, so `MicLevelMonitor.isRunning` diverged from the engine silently: it went on reporting metering that had stopped, and `start`'s `!isRunning` guard then refused to rebuild the tap that was already gone. Two changes, and they compose: the monitor observes `.AVAudioEngineConfigurationChange` scoped to its own engine (through `addMainQueueObserver`, then a second hop to its private `audioQueue`, because unlike `MeetingRecorder`'s observer this one's state is not main-confined), and `stop()` no longer gates its teardown on the flag at all. The second is what closes the residual REC13 left documented on `startBounded`: an abandoned start that later succeeds leaves a running engine the monitor believes is stopped, and a `guard isRunning` there stranded a live tap for the process lifetime.

**Surviving the raise is not the same as keeping the meeting, and REC15 is the bill for that (2026-08-19).** The barrier worked exactly as designed on three raises that day and produced zero crash reports; what it left behind was an auto-start that failed with a toast and, later the same morning, a mic that was dead for the rest of a live call. The distinction that resolves both is already written above and was simply not acted on: a refused **format** is a state, unchanged a millisecond later, while a **raise** is a race against a hardware format that moved between our read and `installTap`'s re-read. A race is worth exactly one more attempt on an engine that never raised, and the owner proved it by hand, starting again 22 s later, reading 48000 Hz where the tap had been requested at 24000, and recording 22 minutes. So both call sites now replace and retry **once**: never on the condemned engine, never in a loop (a second raise means the format is still moving, and looping there is the busy-wait the condemnation exists to refuse), and never for a format refusal. `recoverCapture` also has to re-apply voice processing and re-read the format on the replacement, because a new node carries neither, and the `voiceProcessingEnabledForSession` flag is what `stop()` reads to decide whether to flip it back off.

### A terminal failure has to stand its own retry down

Don't let a path that gives up leave the trigger that called it armed, and don't trust a comment about what stops a watchdog. REC15's second half, and the more expensive one.

Every terminal return from `MeetingRecorder.recoverCapture` leaves the engine **stopped**, and REC8 deliberately un-gated the 1 Hz tap-liveness watchdog from `engine.isRunning` so that a silently stopped engine would be caught, which makes a stopped engine the strongest re-arm trigger there is. The two are correct separately and a busy-wait together: on 2026-08-19 a raise condemned the engine mid-recording, recovery refused the tap, and the watchdog re-entered recovery every second and was refused every time, 12 consecutive refusals in 12 seconds, ending only because the owner hung up. On a call that ran another hour that is an hour of dead mic, three log lines a second, and a full engine teardown per tick.

**The reason it looked impossible is a comment that was true when it was written.** The `.timedOut` branch asserted the watchdog "stops once isRunning is false". That stopped being true at REC8, in a change whose entire point was to make it untrue, and nothing failed when it decayed because it was prose. Both halves of that pairing are worth remembering: an un-gating is a change to every reader of the gate, and a claim about a *sibling* subsystem's behaviour is the kind that rots silently, because the test that would catch it lives on the other side of the boundary.

**The fix is a bound, not a latch, and the shape is the point.** `TapWatchdogPolicy.decide` gained a `micAbandoned` input, checked before everything else because it is the only input that says asking again cannot help. It is set at once when a **fresh** engine also raises, which is provably unfixable by repetition, and otherwise after 5 consecutive failed recoveries counted in `reportRecoveryFailure`, which every terminal return already passes through. A latch on the first failure would have been wrong: the other four returns (wedged teardown, converter init, restart failed, restart timed out) can succeed on the next attempt, and giving up on one would throw away a recovery that was going to work. The counter clears on a successful recovery and in `start()`, so a bad meeting never taxes the next one. And a real device-change notification still reaches recovery while abandoned, which is the whole distinction the flag draws: a route change carries new information, a fixed-interval tick carries none, so the thing to stand down is the timer and not the subsystem.

Two things worth keeping straight. The off-main `audioQueue` is **not** the problem and must not be undone; it exists because an on-main `engine.start()` stalled prompt presentation on 2026-06-24, and it is why this aborts on thread 9 rather than on main. And `boundedEngineStart` / `runWithTimeout` are **not** the tool here: they bound a *hang*, and a timeout does not catch a raise. Finally, these four reports are `bug_type: 309`, which project memory associates with launch-time code-signing SIGKILLs; the discriminator is the exception type and whether the backtrace is empty, never the bug type.

### A signal cannot corroborate itself

Don't accept a second read of the same oracle as independent evidence, and don't let a "verify" step quietly bypass the guard that would have refused. END9, filed 2026-08-04 after three chopped recordings, built 2026-08-20 after eighteen.

`PromotionEngine.tick` carries a `requiresCorroboration` guard for `ax_leave_button_invalid` precisely because that signal is staleness-prone, and it demands a **cross-class** corroborator: `if leading.requiresCorroboration && !crossClassCorroborated { return nil }`. That guard was correct and it never ran. `MeetingSessionController.rescueProvisionalEnd` walked the AX tree for a Leave button about 120 ms after `AXLeaveButtonSignal` had walked it, found nothing, and called `confirmProvisionalEnd()`, which skips the debounce *and* the guard and then appends its own walk to `confirmedBy`. So the end read as corroborated by the very walk that found nothing, and `confirmed_by: ["ax_leave_rewalk"]` in the event log was self-certification dressed as evidence.

**Two walks 120 ms apart are one sample.** Teams tears its accessibility tree down and rebuilds it in-process, for 1 to 65 s at a time, while every window stays on screen, unmoved, titled and readable. Measured two-sided on 2026-08-03: the controls went unreadable at 12:51:19.064Z, both walks had run by 12:51:19.918Z, an independent discovery scan at 12:51:40.133Z still reported `leave_button:false, mute_button:false, calling_controls_toolbar:false, title_match:true`, and the full live-call signature returned at 12:51:52.277Z. The blackout was at least 21.1 s, and the two walks sit inside it with roughly 200x margin. The contrast with the mute side is the defect in one line: `AXMuteButtonProbe` needs **five** consecutive unknown reads before it even re-resolves, and latches the prior state throughout; the Leave signal needed one invalid read and one empty walk.

**The fix is a different oracle, not a longer wait.** A debounce cannot help, because native Teams has no cross-class corroborator to wait for: `usesProcessAudio` is false for every native config after DET2, and `shareableContentWindow` shares an evidence class with `axLeaveButton` by construction. So `CallTeardownOracle` asks Teams instead, through the one line it writes when a call's DRM registration is released (`SlimCoreModule::WindowContentProtectionProvider: UnregisterCall <id>`). It carries no localized text and no window reference, which is what makes it independent of the rendering changes that make the AX read unreliable.

**Measured before building, and the shape of that measurement is the reusable part.** Correlating every teardown line against every provisional end, split by leading signal, gives both the defect and its own control:

| leading signal | confirm | hold |
|---|---|---|
| `ax_leave_button_invalid` | 58 | 18 |
| `shareable_content_window_gone` | 2 | 8 |
| `process_audio_is_running_input_false` | 4 | 0 |

The process-audio row is why the ax-leave row can be trusted as a defect count rather than as oracle drift: a healthy signal against a healthy oracle produces zero holds. When the confirm rate fell from the 84.9% recorded at filing to 76.3%, that row is what said the oracle was fine and the false ends had simply become more frequent. **Always measure a new oracle against a signal you already believe**, or a drop in agreement is unattributable.

**Degrade toward the old behaviour, never toward the new one.** An unreadable or missing log confirms immediately, which is exactly what the code did before, so the change can only be neutral or better. The hold is capped at 150 s and the cap is itself a confirm, because a hold that could run forever is a worse bug than the one being fixed. And the cap is the drift detector: repeated `hold_cap_reached` rows are what say the line has been renamed. A naive "no teardown lines lately" check would have been wrong, since a generation is created per Teams restart and a freshly restarted Teams has an empty one.

### Teams mute state, and how to read its log

Don't take Teams' mute state off the newest file in its log directory, don't believe the timezone that file prints, and don't add a third app-mute producer without a source tag. MIC8 reads `AirPodsService: Input mute event received: mute|unmute` out of Teams' SlimCore media log, and all four of these were measured rather than guessed. **Resolve by log family** (`MSTeamsNM_SlimCore_`): the Electron shell log rotates hourly and the media log only on a Teams restart, so the file carrying the signal is never the freshest one, measured 8th of 132 on 2026-08-04, and a flat newest-N cut is exactly what made a 2026-07-13 recon conclude Teams was not logging at all. **The stamp is UTC with the local offset suffixed after it**, so `07:30:24.277723+03:00` happened at 07:30:24 UTC; parsing the offset as real is wrong by the offset everywhere except on a UTC machine. **Anchor on the whole message**, because the shell log's hourly ECS config blob carries an `hfpOsUnmuteFixEnabled` key that a bare `mute` token reads as a hit. And **an absent line is unknown, never unmuted**: the `AirPodsService` component name is a misnomer, but the data cannot rule out a dependency on AirPods being connected for output. The fusion is the last one: two producers now write `MicGate`'s app-mute field and both arrive through `injectAxMuteEvent`, so a new one passes its `MuteReadingSource` or it silently competes on last-writer-wins with the oracle that is supposed to outrank it. `docs/spikes/mic8_log_correlation.py` is the standing regression test after a Teams update, and it is cheap: one command, no meeting needed.

### Event-stream data goes through Log.event

Don't `print(...)` for event-stream data. Use `Log.event(category:action:attributes:)` so `mp logs` / `mp analyze-detection` see it. A new category goes in the `CONVENTIONS.md` table in the same commit and the action must be snake_case, both fenced by `scripts/truth_fences.py` (CI5).

### Config defaults live in ConfigDefaults

Don't hardcode a config default at its read site when more than one reader needs it. `ConfigDefaults` (ARCH5) is the single home that `Config.load`, `Config.defaultFallback`, and `ConfigStore.init` all read; a literal in two of the three is how Preferences and the running daemon come to disagree about a value nobody changed.

### Network promises in copy are derived from the routing

Don't put a parenthetical promise about the network in a control's copy without deriving it from the routing. `DigestNarration` (UX63) is `RegulatedMode`'s sibling for the weekly digest, and the string it replaced is the cautionary tale: the sole footer of the group that installs the digest's LaunchAgent read "on-device (no new egress)", unconditionally, while an unattended run on 2026-08-03 logged `POST https://api.anthropic.com/v1/messages` and "narrative via anthropic". The module's own docstring had it right in the **qualified** form ("No new always-on egress: this is a command you run or schedule"), and the qualification is the entire content: it is a claim about *scheduling*, not about the network, and dropped it reads as a guarantee. Three rules decide which engine narrates, and they compose only because none of them can ever select a cloud engine: `summarization.digest_local_only` (the owner-chosen opt-out UX63 added, applied Python-side by `digest.narration_config` as a narrowed config handed to the one chokepoint, never a second selection path), the zero-egress clamp, and the ask/digest `apple_intelligence` substitution. `auto` is deliberately reported as **itself** rather than resolved, since it picks per run on whether the cloud answered and its own name already says "cloud, fall back to local". The test worth copying is the paired one: the footer's "nothing leaves it" clause is asserted to appear *exactly* when `staysOnThisMac` is true, over every backend crossed with regulated and local-only, so neither half can move without the other.

### Backend display names live in SummarizationEngine

Don't spell a summarization backend's display name at its render site either. `SummarizationEngine` (UX31) is the same rule for strings the user reads: it is keyed off the raw backend id and exposes the three registers the surfaces need (bare name for the pickers, `Name (where it runs)` for provenance / menu / inspector, a present-tense phrase for the busy and Ask lines), and the eight sites all read it. Seven independent switch tables is how the detail header came to call `anthropic` "Claude (cloud)" while the `...` menu over it called the same call "Anthropic (cloud)"; worse, `claude_cli` and `openai` shipped and nobody remembered five of the seven, so an OpenAI meeting rendered no engine at all. A new backend adds one entry there and one case to `WorkflowBackend`, and `SummarizationEngineTests` fails until it does both. **A phrase needing two engines is a function on that type, not a fourth `var` and never a string at the render site** (UX64's `answeredFooter(ran:substitutedFrom:)`): `mp ask` and `mp digest` have no Apple Intelligence path, so `engine.complete_text` answers on the local MLX model and stamps `substituted_from`, and the Ask pane dropped the key on the floor and rendered "Answered on-device" while spawning the resident multi-GB model the owner picked that backend to avoid. Note the nil rule is *stricter* than UX31's and deliberately so: an unnameable engine on **either** side yields nil, because falling back to the plain single-engine line over a run the pipeline recorded as a substitution would hide exactly the fact the line exists to show, and a line that contradicts the record is worse than no line. And check whether the fact is actually on disk before promising a surface it: the digest reader loads `<stem>.summary.json`, which carries no engine at all, and `DigestResult` records `backend` without `substituted_from`, so the same line there is a Python change plus a new read, not a render.

### Regulated-mode copy is derived from the clamp

Don't describe a privacy clamp in copy written beside it rather than derived from it. `RegulatedMode` (UX60) is the `SummarizationEngine` rule applied to a *consequence* instead of a name, and it is the one where drift was a false privacy claim: the only control for `modes.regulated_mode` was titled "Skip Notion publish" with a Notion-only sublabel and footer, while `config.effective_backend` pins summarization to the on-device model for **every** meeting whenever it is on. On the owner's `anthropic` config, flipping it for one client call silently repointed the whole library onto Qwen at lower quality, and if the model was never fetched the run refuses outright rather than downloading. `README.md` had additionally asserted the **opposite of the code** in three places for months, including a `mp doctor` warning that had been an `_info` since 8591d186. The fix is that every string is built from `RegulatedMode.effectiveBackend`, the mirror of the Python chokepoint, so `RegulatedModeTests` can assert the clamp and the sentence about it in one breath. Two traps came with it. The copy has to be **gated on whether the clamp actually moves anything**, or a Mac already on `local` is warned about a change that cannot happen there, which is the guard-fires-on-everything failure in miniature. And the missing-model case had to be surfaced *here*, at the switch, not only in the menu bar's Finish setup row: `ConfigRefreshCoordinator.prefetchDecision` keys on the **configured** backend, so a Mac on `anthropic` never pre-fetches the model regulated mode is about to demand, and nothing downloads until someone asks. That is what the inline UX21 `LocalModelPreflight` affordance in that group is for; the eager prefetch does not cover it.

**The same pane's privacy callout was the version of this that had already rotted, and it rotted two ways at once (DOC12).** The paragraph under the permission cards read "the pipeline only reaches the network when sending the transcript to Anthropic for summarization, and when publishing to Notion", fixed, on a build shipping five more backends (`local`, `auto`, `apple_intelligence`, `claude_cli`, `openai`) and three more sinks (Obsidian, filesystem, LAN). On a Mac configured for OpenAI publishing to a network share it named neither real destination, on the one surface someone opens *because* they are asking where their data goes. `PrivacyReach` derives both halves and reports the **upper bound** on reach, since per-workflow NDA mode only ever clamps further: a privacy sentence may be more cautious than the run and may never be less. Its sink switch is exhaustive for the same reason `WorkflowBackend.engine` is, because a fifth sink defaulting to "stays on this Mac" is how the first version was written.

The second way is worth more than the first, because it survives a rewrite of the string. The permission rows in the same pane held a **private second copy** of `PermissionsCenter.Kind.rationale`, a `private var rationale` switch on the row struct, and it was the copy that rendered. DET11 reworded the shared one on 2026-08-15; the pane went on promising that Accessibility "reads browser tab titles to detect Meet and Teams Web sessions", a path this owner has never used, while the onboarding step one flow away (which reads `kind.rationale`) said the true thing about window and call-control reads. Nothing failed: both compiled, both had a plausible switch over the same four cases, and grep for the shared property found the onboarding site and not the drifted one. So when a shared table exists, check what the surface actually renders rather than what it could render, and treat a `private var` shadowing a shared name as the smell it is.

### Publish sink names live in PublishLanding

Don't spell a publish sink's name at its render site either, and don't infer the destination from anything but `<stem>.publish.json`. `PublishSink` / `PublishLanding` (UX49, extended by UX62 with a `symbolName` register and `PublishLanding.localNote`) is the `SummarizationEngine` rule for where a meeting *landed*: one phrase per sink, plus the pure `decide` that maps a run's sinks map to what a surface may claim. **The rule had two more disobedient readers than UX49 found, both fixed by UX62, and both failed the same way: silently, on the majority case.** `MeetingStore.needsRepublish` counted only `.notion.json` and `.obsidian.json` as evidence of a publish, so a filesystem or LAN publish was indistinguishable from never published and the row's inline Republish capsule could not appear for it, ever; and the detail header's Open buttons branched on those same two sidecars, so the same meetings had no open action at all. That is not a tail: the owner's default `Personal` workflow is filesystem-only and held 117 of 190 tagged meetings, **107 of 245 stems** had a `.filesystem.json` and no `.notion.json`, 13 of the last 15 meetings were blind, and every NDA meeting is too, since NDA mode force-selects filesystem-only sinks. Two things worth carrying: the staleness read takes the sidecar's **mtime** rather than a `ts` inside it (every publish path rewrites that file, so its mtime *is* the last publish, and parsing a timestamp buys nothing), and a reader added to `PublishURLs.fingerprint` at the same time, because a file that "nothing here reads" stops being one the moment a button is built from it and a guard that cannot see it means the button never appears. `localNote` answers only for filesystem and LAN on purpose: Obsidian's header button is an `obsidian://` deep link assembled from the vault relationship, so serving it from `publish.json`'s `page_url` would open the note *outside* Obsidian, and it reads the **per-sink** `page_url` rather than the top-level one, which is whichever sink came first in `output.sinks`. The done notification is the cautionary tale, and a quiet one, since nothing was broken: its body and its Open button were the literal `"Open in Notion"`, consulting nothing, so the owner's last nine meetings all published to the filesystem and all announced a Notion page, offering to open a local Markdown file as if it were one (the action itself opens `page_url`, so it always landed correctly). Two traps live in that rule. `page_url` alone cannot name a destination: it is the *first* successful sink in `output.sinks` order, so it says what to open and not who wrote it, which is why two landings read as `.unnamed` rather than picking one. And a notification action's title is baked into its **category** at registration time, so a phrase that varies needs a category per phrase (`NotificationRouter.doneCategory(for:canCorrect:)`); that is the mechanical reason the literal survived as long as it did.

### One row, one speaker identity

Don't read a transcript row's speaker off `segment.speakerID`, and don't let one row answer "who is this line" twice. A line carries two identities, the raw diarization label in `<stem>.json` and whatever the speaker overlay resolves it to, and a per-line reassignment (FEAT3-SEGMENT) deliberately moves only the second, since leaving `<stem>.json` intact is what makes every naming reversible. The row used to render the overlay's answer and branch its menu on the raw one, so a line moved off Sudip onto Unknown E read "Unknown E" and still offered **Rename…** for Sudip; typing a name there would have re-enrolled Sudip's voiceprint under it and renamed her on every other line of the meeting, silently (UX57). The one read is `MeetingCast.rowSpeaker(for:overlay:voiceprintLabels:)`: it answers with the label the row *is* (the per-segment override, else the raw label), the in-app name over it, and the menu items, each carrying its own target label so a call site has no raw label in scope to hand a callback by mistake. Its gates mirror `VoiceResolutionBar.actions(for:)`, which is why the cast strip was the one surface that stayed right through this, and it is also the identity anything else keyed per row (a colour, a dot) should ask. **Colour is the first taker (UX58), and it is now `MeetingCast.colorIndex(for:in:)` plus `TranscriptDisplay.color(atCastIndex:)`, a slot in the meeting's cast rather than a property of a label; there is no `color(for: <raw label>)` left to call.** The one line it replaced was three defects at once: keyed on the raw label, so the dot stayed on Sudip when a line left her; `abs(label.hashValue) % 8` in a language that reseeds string hashing per process, so every speaker changed colour on every launch (measured across three processes, `THEM-A` on slot 3, then 4, then 7); and about a 92% chance that two of six voices drew the same slot. Cast position is a pure function of the meeting's files, so it is stable across launches, unique to the palette's eight, and it moves with a reassignment because the identity it indexes does. Two consequences worth knowing: the colour is per **meeting**, so one person can read differently in two meetings, and naming somebody does not repaint anything, since the name lands on a cast member that already exists rather than appending one. **The cast strip mirrors that same index now (UX59)**, as a `colorIndex` on `VoiceResolution.Voice` filled in `derive`, not as a read the chip does for itself: two surfaces each deriving "which colour is this person" is exactly the disagreement UX59 existed to remove, so a third surface that wants a speaker hue asks the same function or takes the slot from the pure type, and never re-derives one. The trap on the chip is the mark it sits next to. Its leading glyph is tinted by `VoiceResolutionBar.tint(for:)`, which is FEAT11's resolution status, so the identity dot went in as a **separate sibling view** rather than as a recolour of that glyph; recolouring it would have made every chip consistent with the transcript and simultaneously destroyed the only surface that says whether roster matching worked. Keep the two marks separate, and keep both off hue-only: identity is the dot plus the name beside it, status is a distinct symbol per origin plus its tint plus the `Name` affordance.

### A transcript row is not the diarizer's unit

Don't read "one transcript row, two voices in it" as evidence that diarization failed to *split* there. The row is built two layers above the diarizer: `SegmentBuilder.build` attributes ASR tokens to speaker spans, and `SegmentBuilder.coalesce` then folds consecutive **same-speaker** fragments into one readable turn (DIAR2 leg b). So an undivided row is equally consistent with the diarizer having split correctly and given both halves the same cluster, and the two readings point at opposite fixes: segmentation resolution against cluster assignment. Measure the diarizer's own spans before choosing.

This is not hypothetical, and it cost two tasks. The canonical case is 2:01 in `20260727-103155`, where a phrase starts in Sudip's voice and continues in Yash's inside one 25.3 s row. DIAR2 recorded it as "a speaker change *inside* one segment, so no clustering threshold can split it", filed DIAR4 to chase the `stepRatio` segmentation dial on that reading, and `ARCHITECTURE.md` inherited the same sentence. DIAR4's probe measured it on both pipelines, and **both already emit a boundary there and label the two sides the same speaker**. Online at the shipped 0.55: four spans across the row (121.97-124.61, 125.92-129.94, 130.00-139.94, 140.00-147.12), all cluster `1`. Offline at `stepRatio` 0.1: two spans (121.84-124.65, 125.96-147.12), both `S1`. Two pipelines sharing no clustering algorithm, no embedding model and no step size put a boundary within 0.04 s of each other; it is a 1.31 s silence, which is why it is cheap to find. It lands where the handover is as far as the ASR text can place it (six words of Sudip, so roughly three seconds into a row starting at 121.84). The boundary was never missing; the attribution across it is what is wrong, which puts the case in the same family as the multi-person `THEM-A` in `20260803-103042` rather than in a segmentation family of its own, and the fix works on assignment (per-span re-scoring against enrolled voiceprints, an overlap-aware pass) rather than on segmentation. Re-run the probe to check this rather than inheriting it: it is two lines of output. Trail, pre-registered thresholds and the NO-GO: [`docs/spikes/diar4-offline-diarizer-migration.md`](../../docs/spikes/diar4-offline-diarizer-migration.md).

Three adjacent facts from the same spike, worth having before anyone reopens the offline-diarizer question, which DIAR4 closed NO-GO. `OfflineDiarizerManager.process` returns the same `DiarizationResult` / `[TimedSpeakerSegment]` the online `performCompleteDiarization` does in FluidAudio 0.14.8, so the "different result type" DIAR2 recorded in July is no longer a migration cost. What *is* a cost is invisible at the type level: the offline pipeline embeds with different model weights at the same 256 dimensions, so every enrolled FEAT3 voiceprint and every `<stem>.embeddings.json` would keep loading and keep producing cosine distances in the wrong space. The failure mode is silent wrong roster matches, not a crash, and any migration has to re-enroll the roster. And the offline path clusters *harder*, not better, on this corpus: 3 clusters on `20260727-103155` where the online path at 0.55 returns 10 and the shipped sidecar carries 9 speaker keys, which is the under-clustering DIAR2 spent its sweep buying back.

### A config key needs a consumer

Don't add a config key to `Config.swift` / `ConfigStore.swift` without a consumer and a line in `config.example.toml`. CI5's dead-knob fence fails on a key that is parsed, persisted, and rendered as a Preferences control while nothing reads the value; that shipped three times before it was fenced, and the symptom is a user changing a setting and nothing happening.

### Fields in summary.json must be modeled in Swift

Don't add a field to `<stem>.summary.json` on the Python side without modeling it in Swift's `MeetingSummary` too. `jsonObject()` re-serializes only the fields the struct knows about, and it is the writer behind *both* in-place rewrites of that file (`MeetingLibraryService.setActionResolved`'s done/reopen toggle, which both the Facts rail and the Summary tab route through since UX26, and `SummaryTab.persistEdit`'s correction save). An unmodeled field is not preserved-by-default; it is silently deleted the first time the user ticks an action done. FEAT10's `evidence` is the worked example, `EvidenceTests` pins it, and anything the editor can retext also needs a remap rule (`MeetingSummary.carryEvidence`) so a stale citation cannot outlive the sentence it backed. Those same two rewrites are why **`<stem>.summary.json`'s mtime never means "this summary was generated then"**: ticking one action done makes a months-old summary look freshly written. Anything asking when the prose was produced reads `<stem>.run.json`'s `ts` instead (UX41's `MeetingStore.namesChangedSinceSummary` is the shipped reader), and not the run sidecar's mtime either, since a publish rewrites that file to record `publish_state`.

### A window holding user text must re-check what it read

Don't let a window that holds user-authored text write a record about a file it read once and never re-checked. `CorrectionWindow` (UX65) is the case, and it is the **inverse** of the rule above it: UX52's store-revision reload key is the wrong tool here, because silently re-reading would discard the owner's in-progress edit, which is worse than the bug. So the guard is at the **save**, not on the read: `show()` captures `SummaryIdentity` (the file's bytes), `SummaryStaleness.hasMoved` compares it in `performSave`, and a moved file raises a choice instead of writing. Three things are worth carrying. **The direct lost update people expect here does not exist**, and the sweep that surfaced this named the wrong mechanism: `handleOutcome` writes one file, `corrections/<stem>.json`, and never opens `<stem>.summary.json`; the surface that overwrites the live summary is `SummaryTab.persistEdit`, which already tracks an mtime and is deliberately out of scope. The damage is one step removed instead, and it is why this is not cosmetic: `CorrectionsTab.performRevert` restores `<stem>.summary.json` **from the record's `original_summary`** and then deletes the record, so a stale original is superseded prose waiting to be written back over whatever is current, under a button labelled Revert, and `corrections/` is simultaneously the LoRA corpus. And identity is the **bytes**, not an mtime plus a size: a rewrite producing identical content moves the mtime, and stopping a save to ask about a change that did not happen is the fires-on-everything failure the walkthrough's last step exists to catch. `performSave` takes the dialog as a parameter for the same reason: the assertion that matters is "no record was written", which has to be pinned on the bytes of the record file rather than on a return value.

### Run state must outlive the view that started it

Don't keep a running job's state in a view the navigator rebuilds. The Library's center column is an `if/else` on `scope`, so every rail switch destroys the projection view and its `@State` with it; Ask held its whole run there (question, asking, answer) and a switch to Facts threw the answer away while `mp ask` kept burning its ten-minute budget invisibly, uncancellably, into a result file the `defer` then deleted (UX37). Run state that outlives its view lives on `LibraryRootView` as a `@StateObject` (`AskModel`, `DigestListModel`), and the view renders it. The tell is easy to miss: an unstructured `Task {}` is NOT cancelled when the view that started it dies, so nothing looks wrong, it just completes into nothing.

### Finish an operation by publishing MeetingStore.revision

Don't finish an operation that rewrote a meeting's files without publishing `MeetingStore.revision`, and don't grow a second signal beside it. The `if/else` on `scope` above is also why a missing refresh hides: a tab or rail switch rebuilds the detail pane from disk, so an operation that publishes nothing still looks correct the moment the user navigates, and navigating is the natural thing to do while waiting. The one signal is the store's rescan: `revision` bumps, and each pane keys its `.task(id:)` on `(stem, revision)` with a modification-date guard so an unrelated rescan is a no-op (`SummaryTab.SummaryReloadKey`, `TranscriptTab.TranscriptReloadKey`, `MeetingDetailView.PublishURLsReloadKey`). The header is *nearly* free, since the same scan rebuilds the `Meeting` it reads, and the exception is the one thing in it read off disk: the Notion / Obsidian Open buttons come from the two publish sidecars, so they need a key of their own (UX53). Re-transcribe was the reported instance (UX52): it ended at `retranscribe_done` having published nothing and leaned on the directory watcher, so a finished run left the old transcript on screen; `MeetingLibraryService` now calls its injected `refreshLibrary` on both outcomes, after the overlay carry so the rows and the cast strip are never a run apart. Two traps come with it. The guard has to cover **every** sidecar the pane reads, not just the obvious one: a rename writes only `<stem>.speaker_labels.json`, so a guard watching `<stem>.json` alone would skip exactly the reload it exists to allow. And publishing only part of what an operation changed reads as a fix: a re-transcribe changes the text, the speaker clusters, and the header lines at once. UX53 swept all 29 operations against that, and the useful result is which half actually breaks. **Publishing is almost never the problem.** Both trees write sidecars atomically, an atomic write is a temp file plus a rename, and the watcher is on the *directory* fd, so essentially every operation already reaches a bump without asking; re-transcribe was unusual in that its own publish mattered (its `mp finalize` leg rewrites in place). What breaks is the second half, a pane that gets the bump and ignores it, and it has one grep-able signature: a `.task(id: meeting.stem)` or an `.onAppear` sitting over a disk read. Check for that before adding a signal. The two stem-keyed loads still in the detail view are deliberate and documented where they are (`AudioTab` must not re-attach the player under a listener; `CorrectionsTab` is a modal sheet), and the surfaces UX53 named rather than fixed are in `docs/backlog/tasks/UX53.md`, each with the design question that kept it out of that task.

### Step state must outlive a navigator rebuild

Don't keep state a step must not lose in a view the navigator rebuilds, and don't treat `WorkflowStore.delete` as guaranteed. Both halves shipped in onboarding's workflow step and together put four "Client work" rows in the owner's config (WF9). `OnboardingRootView` is a `switch step`, so Back / Continue destroys and recreates the step and its `@State` with it; anything that has to outlive a round trip lives on the root and comes down as a `@Binding` (`OnboardingWorkflowChoice`). And `delete(id:)` returns `false` for the default rather than throwing, so a caller replacing a workflow reuses its id instead of deleting and re-creating: every preset is created `isDefault: true`, so the delete was always a no-op and the replacement always landed beside its predecessor. Nothing new calls `delete` directly: `WorkflowDeletion.run` is the one flow (UX30), it maps that `false` to a reason the surface has to show, and it dismisses the host exactly once on success. A workflow *editor* saves through `WorkflowStore.update`, never `upsert`, because the append branch is how a sheet left open over a deleted workflow used to write it back.

### Shared primitives are the design system, and are not private

Don't pile inline styles into a SwiftUI view, and don't declare a shared-looking primitive `private`. The shared primitives (`SettingsGroup`, `SettingsRow`, `SettingsSegmented`, `SettingsSlider`, `SettingsStatusPill`, `SettingsSecretField`, `SettingsHotkeyField`, plus the destructive `MPDangerButtonStyle` / `.mpDanger` and the wrapping `FlowLayout`, in `Preferences/PreferencesControls.swift`) are the design system, alongside the DSN24 button styles in `Design/MPButtonStyle.swift` (`.mpGhost`, `.mpIcon`). Add new primitives there rather than parallel one-offs. The danger button is the worked example of the `private` half: it shipped inside `BatchActionsPane` for the Library's "Move to Trash", so the workflow editor could not see it, wrote a code comment asserting the app had no destructive button style, and rendered Delete as a neutral ghost capsule with the same weight as Save (UX30). `FlowLayout` is the second (UX51), and it also shows where the line is: it stayed `private` in `PreferencesView+Recording.swift` through UX38, which looked at promoting it and declined **for one speculative caller**, correctly. A real second caller is the trigger, not a hypothetical one, and when it arrives the move is to promote rather than to write a second copy beside it.

### Never anchor a CALayer mask at origin zero

Don't anchor a `CALayer` mask (or any layer) on a scrolling view at `origin: .zero`. A mask is positioned in its layer's coordinate space, and an `NSClipView`'s bounds *origin* is exactly what moves when its document scrolls, so a zero-anchored mask keeps covering the document's first screenful while the viewport moves away from it, and every point past that composites **fully transparent** rather than unmasked. UX47's prep-card fade shipped that way for an afternoon: scrolled 82pt into a 205pt card with a 123pt viewport, content survived only in bounds 82-123 and the OPEN ACTIONS eyebrow and action rows below were invisible however far the owner scrolled. Take `clip.bounds` whole. `PrepCardTests` fences it, after first tripping on the comment that explains it.

### Never frame-size a scroll view's Auto Layout document

Don't frame-size a scroll view's document that hosts Auto Layout content, and don't trust `translatesAutoresizingMaskIntoConstraints` to hold the frame you set there. UX34 handed `PrepCardView` a 600pt frame as an `NSScrollView` document; under the layout engine a TAMIC-true document with constraint-based subviews takes its size from the *content*, so the card laid itself out 879pt wide, every trailing constraint held against an edge 279pt past the glass, the configured tail-ellipsis never fired (bullets sliced mid-glyph at the clip), and the right-aligned date rendered off-panel from UX34's landing until UX47 caught it with a layout probe. Constraint-host the document instead: TAMIC false, width pinned to `scroll.contentView`, height pinned to the measured content height. The height half of UX34's "known before the view exists" reasoning was always sound; only the width was lying.

### Shapes are greedy in both axes

Don't put a bare `Rectangle` (or any `Shape`) as a stack sibling when you want the stack sized to its content. Shapes are greedy in both axes, so with no width constraint the shape takes every point offered, the enclosing `VStack` inherits that greed, and a row of such stacks divides the whole pane while the trailing `Spacer` gets nothing. The detail pane's tab strip shipped exactly that (UX36): `tabButton` drew the active-tab underline as a `Rectangle` sibling beneath the label, so the source read `HStack { tabs; Spacer(minLength: 0) }` and looked left-aligned, while the app rendered three tabs spread across a 1230pt pane with an underline several times wider than its word. Draw an underline as an `.overlay(alignment: .bottom)` on the thing it underlines, so it sizes to that thing. `SummaryLayoutTests` pins the overlay form, since neither greed nor alignment is observable at runtime.

### SettingsRow column widths, and window minimums

Don't let a `SettingsRow`'s control column fight its label column for width, and don't set a window's minimum below the floor the SwiftUI root inside it declares. The info column is greedy (`.frame(maxWidth: .infinity)`) while a button, pill, or picker has no compression resistance of its own, so the squeeze lands on the control and truncates its text: Storage's "Choose destination…" read as an ellipsis, with People and Caches carrying the same two-ghost-button shape (UX43). The row fixes that column horizontally now, which is only what the locked `PWRow` mockup already pinned with `flexShrink: 0`; the one control that genuinely wants the remaining width (the Pipeline pane's scrolling prompt preview) passes `controlFills: true`, because pinning a `ScrollView` to its ideal width is a mile of unwrapped prose. The window half is the same defect a level up: `PreferencesWindow` allowed 720x560 against a root demanding 780x660, so the user could resize past the hierarchy's own floor. Use `contentMinSize`, not `minSize`, which is frame-space and would still allow a content box a title bar shorter than asked. And a `ScrollView` created *outside* a content switch keeps its offset across it, so Storage scrolled to the bottom left General opening at the bottom: reset with a `ScrollViewReader` and a constant top anchor, never `.id(<the selection>)` on the content, which resets the offset by discarding every pane's `@State` with it.

### Never offer a picker option whose setter drops it

Don't offer a picker option whose setter drops it. The Local model picker offered Custom unconditionally while its binding derived the selection from the stored model id alone, so picking Custom wrote nothing, the getter re-derived the previous preset, the picker snapped back, and the Model id field gated on Custom could never appear: a row that had been dead since it shipped (UX43). Custom is a real target now (the pane holds the selection in `@State`, and `LocalModelPreset.showsModelIdField` reveals the field for exactly the selections that write nothing on their own). The other resolution is DIAR3's, for a control with no field behind it: `SpeakerSeparation` offers Custom only while it is already the selection, so it is a readout nobody can pick. Either is fine; an option always on offer that does nothing is not.

### The detail header is chrome, not content measure

Don't put a detail pane's header on one of its tabs' content measures, and don't centre a measured column in an uncapped one. `MeetingDetailView`'s header and tab strip are a **chrome band** on `bgSunk` spanning the pane (UX36), deliberately not on `SummaryLayout.readingMeasure`: `TranscriptTab` and `AudioTab` are full-width, so a header indented to the summary's measure is aligned on one tab and misaligned on the other two the moment the tab changes. The band recesses rather than lifts, because on `bgRaised` it was an 11-of-255 step off the dark canvas, invisible in a screenshot, and a band nobody can see licenses nothing. Content then left-aligns on **one** edge across every tab, which is affordable only because `LibraryLayout.detailMaxWidth` caps the column: uncapped, left alignment leaves a growing void to the right (the original shape) and centring puts the summary 200+ pt right of the header and transcript so the axis jumps per tab (the second shape, rejected on sight). Cap the column, then left-align; `SummaryLayoutTests` pins both halves. The measure itself (720, the top of the 640-720 band `design/README.md` allows, owner-picked 2026-07-29) is shared by **both reading tabs**: `TranscriptTab` rides the same `SummaryLayout.readingMeasure` stack, because at full pane width its wrapped monologue turns were the longest lines in the app and the right edge jumped ~300pt between the two reading tabs. The pieces inside the transcript's measure (cast strip, captions, rows) carry no horizontal padding of their own, so the stack's gutter is the only inset; re-adding a row-level inset re-opens the edge disagreement in miniature. Audio, the playback transport, and the empty states stay full-bleed on purpose: instruments and states, not reading content. The mirror of this is a footer: give it the width of the thing it serves, not of the pane it sits in. `WorkflowInspector`'s Edit shipped on a full-pane `bgRaised` plinth under a 416pt card, a filled band three times wider than its own content, and the owner read it as a control from another app (UX33). A resting surface gets a hairline and no fill, per `design/README.md`; the card's footer is the card's width.

### Derive a content ceiling, not a floor

Don't cap a pane's content at the width its narrowest allowed window would dictate. `WorkflowInspectorLayout.cardMaxWidth` is the worked example: the first pass derived 416 from `LibraryLayout.detailMinWidth - 2 * padding` so the card kept side margins at the floor, which is a correct derivation of the wrong quantity, since `.frame(maxWidth:)` already shrinks a wider cap back at the floor. The result was a card frozen at the minimum window's width on every window, which is the ribbon UX33 existed to remove. Derive a *ceiling* from what the content wants to read at (here the 640-720 reading column), and let the frame handle the floor.

### Window activation has one owner

Don't front, activate, or count a Dock-participating window from its own `show()`. `WindowActivationManager.showWindow(_:)` owns the open sequence for the four that take a Dock icon (Library, Preferences, Diagnostics, Guide) and `didCloseWindow(_:)` owns the way back, because both halves are ordering bugs a diff cannot show (UX39). `setActivationPolicy` is processed asynchronously, so a `makeKeyAndOrderFront` + `activate` in the same run-loop turn as the flip, or before it, which is how all three sites used to read, is evaluated against the still-accessory app: macOS then appends the app to the Cmd+Tab MRU **tail**, and the owner's report was that the Library sat last in the switcher with no way to Cmd+Tab straight back. **But nothing waits for that transition any more, and UX56 is the reason (two passes, and the second is the one to know).** The wait was unconditional. Its cost is a run-loop turn in which the app the user came from can keep or reclaim focus, and on macOS 14 activation is cooperative, so this app asks rather than takes. Pass one narrowed the wait to "while a policy raise is in flight", which fixed the reported case (a Preferences window landing behind the Library that opened it: the toolbar gear, Cmd+, from the main menu, the Vocabulary and permission cross-links) and left the raising path alone. Walking that on 2026-08-04 the owner found the discriminator on the path still waiting: the window came up behind the frontmost app **and** the app sat at the Cmd+Tab **tail**, which is precisely the position the wait exists to buy. So on the one path that still deferred, the deferral was paying its cost and buying nothing, which is evidence against the wait rather than for a wider one. Pass two removed it: every window is fronted and activated in the turn that asked, and a raise queues **one** `activate` for the turn after it, when the transition has certainly landed. That keeps UX39's rule 1 as a *retry* rather than as a wait, it is a no-op on an app that is already frontmost, and it is queued per transition (at the raise) rather than per window, so two windows opened in one turn front in ask order with the second on top and share the one retry. Note also which path is which, because it is the opposite of the obvious reading: every open from the status-bar menu with nothing else up **is** a first-window open, since the last close drops the policy back to `.accessory`. The manager counts by window identity for a second reason of the same kind: `NSWindow.isVisible` is false while a window is miniaturized, so the `if !w.isVisible` guard each site carried counted a reopen-from-the-Dock as a fresh open while only one `windowWillClose` ever arrived, and the app stayed `.regular` with nothing on screen. QuickFind, Onboarding, and Correction skip the handshake on purpose (a floating panel and two one-shots), which is the only reason they still call `NSApp.activate()` themselves; that is also the modern spelling, since `activate(ignoringOtherApps:)` is deprecated on the macOS 14 floor. **The menu bar rides the same two moments (UX48):** `MainMenu.install` in the step that raises the policy, `MainMenu.remove` in the step that drops it. Those panels therefore still have no main menu while they are up, which is the known edge and belongs to UX27, not to a second install site.

### Command-key shortcuts need a main menu

Don't fix a missing command-key shortcut with a hidden control in the view hierarchy. `NSApp.mainMenu` is where macOS matches a command-key event **first**, and this app had none at all, so Cmd+C, Cmd+A, Cmd+X, Cmd+V, Cmd+M, Cmd+W and Cmd+, were all the system beep in the Library and a transcript's text could not be copied out with the keyboard (UX48). The shape that had been tried instead is the cautionary tale: 292dfe49 hid a zero-opacity SwiftUI `Button` carrying `.keyboardShortcut(",")` in `LibraryWindow`'s background and wrote a comment asserting that a key equivalent needs one there. Measured at pickup, that button does fire; what it cannot do is generalise, because Copy and Select All have to reach the text under the pointer rather than a control this app owns, so a second patch of that shape would have been one more per-shortcut special case. `MainMenu.swift` is the one place now: App / Edit / Window, every item on a **nil target** so AppKit walks the responder chain from the key window. Preferences lands on `AppDelegate.openPreferencesFromMainMenu` rather than on `Coordinator`, since a menu item's chain reaches `NSApp`'s delegate and not the coordinator. Adding a row means adding it there, with a chord `MainMenuTests`'s collision check can see.

### The reading surfaces have no NSTextView

Don't assume the reading surfaces have a right-click Copy to fall back on. There is **no `NSTextView` in this app**: the transcript, the summary, Ask, and the Guide are SwiftUI `Text` under `.textSelection(.enabled)`, which AppKit backs with a `SwiftUI.SelectionTextField` (an `NSTextField` subclass) that carries no `.menu`, returns nil from `menu(for:)`, and does not respond to `copy:` (measured 2026-08-04 with an offscreen `NSHostingView` probe). `TextEditor` is the only NSTextView-backed control here and it appears only in editing sheets. So the main menu is not a convenience over a working mouse path; on the reading surfaces it is very likely the only path text has out of the app. **Both probes ran without a real selection, and the owner falsified their strong reading on 2026-08-04.** The measurements themselves stand: with nothing selected, that field answers `acceptsFirstResponder` **false**, `makeFirstResponder(field)` leaves the *window* as first responder, `window.fieldEditor(false, for:)` is **nil**, and `validRequestor(forSendType: .string, returnType: nil)` is nil (offscreen `NSHostingView` probe by UX48, repeated on a real on-screen `NSWindow` by FEAT13). What neither probe could do is create a live selection: a synthetic `mouseDown` enters AppKit's tracking loop and blocks, and `selectAll:` on a field that refuses first responder is a no-op. So both measured the **no-selection** state and neither covers the case the user is actually in. Walking UX48 on 2026-08-04, the owner selected transcript text with the mouse, right-clicked **the selection**, got a context menu, and **Copy worked**. So a real selection does engage a text path AppKit will serve, a mouse route out of the app exists, and the earlier conclusion that "no field editor is ever engaged" is true only of the untouched control. UX48's band stayed P2 on that evidence. Do not right-click the transcript **line** to check this: the row carries its own `.contextMenu` (Edit text…, Clarify…), so it answers first and tells you nothing about the text path. What remains genuinely unmeasured is whether this process can read that selection **programmatically**; the nil `validRequestor` was measured with no selection, so treat FEAT13's row-context-menu affordance as the right design (the row owns its own actions, which the owner independently confirmed is where those belong) with its stated justification unproven rather than established.

### App Intents compile standalone

Don't reference another file's types from `Automation/MeetingPipeAppIntents.swift`. `install.sh` compiles that file **standalone** with `swift-frontend` to emit the App Intents metadata Shortcuts discovers, and a lone-file compile cannot resolve cross-file references. The breakage is silent in the worst way: `swift build` still succeeds, the app still installs, and only the native Shortcuts actions quietly vanish. Keep its `meetingpipe://` verbs as literals (`MeetingPipeAppIntentsTests` pins them to `AutomationCommand.parse` so they cannot drift), and re-run `daemon/scripts/auto1-app-intents-probe.sh` after an Xcode bump, since the extraction rides private compiler flags.

### App Intents are discoverable but not invocable

Don't try to make the native App Intents actually run on an ad-hoc-signed build, and don't re-derive why they don't. They are **discoverable but not invocable**: all six list in Shortcuts, and invoking one fails with "Shortcuts couldn't communicate with the app" (the app is never contacted, never crashes, logs no `automation` event). Six causes were excluded by measurement on 2026-07-19/20 (symbols present, LS registration fine, `openAppWhenRun` both ways, launchd vs `open -a`, `LSUIElement` both ways, no crash); the remaining one is code signing, since the bundle is `spctl`-rejected with `TeamIdentifier=not set`. `install.sh` therefore emits the metadata only under `MP_APP_INTENTS=1`. The header comment in that file carries the full list, so read it before spending an evening on this.

### A no-op test is not a conflict test

Don't take a test that a second writer **agreed** with an override as covering the case where it **disagrees**. `TranscriptOverlayCarry.carry` retires a text correction the new transcript already satisfies, whose reasoning is right ("the ratchet subsumed the fix, and keeping a no-op override would only make the next diff harder to read"). What that asks is whether the transcript moved *toward* `editedText`. It had no test for the transcript having moved *away* from it, which is what a vocabulary term does when the owner authored both halves, so the carry could not see the one case where its two inputs contradict each other. Observed on `20260803-165412` the day FEAT13 and FEAT12 both landed (UX66): `glossary.toml` carried `Jorji = "Georgy"` under the Personal workflow, the re-transcribed `20260803-165412.json` held `Georgy` and seven `Max` and **no `Jorji` anywhere**, so the rule applied correctly, and the pane still rendered `Jorji` because `TranscriptCorrectionStore.apply` overlays `editedText` at load. The owner read it as the rule failing; `Macs` looked fine only because no overlay sat on those lines. Two properties made it worse than one confusion: it is **permanent** (every load re-applies it, and every later re-transcribe re-anchors and re-snapshots `originalText` to the new text, so a stale override comes out looking freshly authored) and it was **silent** (it counted as `carried`, which reads as success). The fix is not a precedence change. Overlay-beats-rule is correct and stays: a per-meeting manual fix should outrank a global rule. What was wrong is that the loser was invisible, so `carry` now takes the meeting's resolved terms and counts a contradiction apart from `carriedCorrections`, and both report surfaces name it. Matching is `Clarify.containsTerm`, the same `\b(<key>)\b` case-insensitive rule the substitution replaces on, because a conflict detector looser than the rule it checks reports conflicts that rule cannot cause. The generalisation worth carrying: **whenever two write paths can touch the same text, a test that they agree is not a test that they conflict, and the conflict case is the one that ships silently.**

### A Preferences control that shells out is on the freeze list too

Don't leave a `Process` round-trip on the main thread because the control around it looks cheap, and don't cache a machine reading for a view's lifetime. `LaunchAtLoginModel` did both, and the two together are UX67: walking UX55 on 2026-08-04 the owner found **Launch at login** and **Relaunch after quitting** would not move, and only a full app quit cleared it. The filing named two candidate mechanisms, a refused `launchctl` (the switch correctly showing the machine, UX42's design) and a stale cached reading (UX53's missing-refresh class). **Reading the code, neither explains the report, and that is the useful part.** *Relaunch after quitting* does not touch launchd at all: it binds to `ui.disableAutoRestart`, a plain `@Published` on the `UISettings` singleton with a `UserDefaults` `didSet`, so it has no refusal path and no cached read and cannot decline to move. The only thing that stops both toggles at once is the main thread being blocked, and the one blocking thing in that pane is `ProcessLaunchctl.run`: `readDataToEndOfFile` returns when the child's pipe closes, so a `launchctl` that does not exit blocks it forever, and `LaunchAtLoginModel.set` made up to three of those calls (`enable`, `print`, `bootstrap`) inline. The session that produced the report had just run `./scripts/rebuild.sh`, which boots the `com.meetingpipe.daemon` label out and bootstraps it back, so the domain was busy with that exact label while the pane was open. That is candidate **C**, it is the same class as a stuck `stopCapture` or a wedged AX round-trip, and it explains all three of the owner's observations: both toggles dead together, the window otherwise fine (main only wedges while a click is in flight), cleared by a full quit. All three are fixed rather than one: every `launchctl` call now has a watchdog that kills the child at `ProcessLaunchctl.ceilingSeconds`, the model runs reads and writes on a detached task and publishes back on main with an `isBusy` the toggle disables on, and the reading is re-taken on the pane's `.onAppear` rather than only in `init`. A refused write also emits `daemon.launch_at_login_write_refused` now, carrying launchctl's exit status and stderr tail, so candidate A stops depending on somebody happening to look at the group footer. Two things worth keeping: the initial read stays synchronous, because the alternative is rendering a placeholder before the machine has been asked, which is the control-lies-about-launchd defect UX42 removed; and `refresh()` is not a per-render read, since `status()` spawns a subprocess and UX55 already recorded what an inline read on a hot path costs. **The generalisation: a control whose two halves fail independently, where one half cannot fail at all, is not two bugs. It is one blocked thread.**

### A scroll anchor belongs outside the padding, and ordering cannot fence it

Don't make a scroll-to-top anchor the first **child** of a container that carries the top padding. `PreferencesView` did, so a pane switch landed 28pt below the top with a band still to scroll up into (UX68, found on UX43's own walkthrough the day it was verified). The cause is exact rather than approximate: `.padding(.vertical, 28)` was applied to the `VStack` while the zero-height anchor was that stack's first child, so the anchor's top edge sat 28pt below the scrollable content's true top, and `scrollTo(anchor: .top)` aligned it with the viewport exactly as asked, leaving the padding above the fold. The offset **was** the padding constant and would have tracked any change to it, which is why a numeric compensation was the wrong fix twice over. The fix moves the padding onto the content beside the anchor and leaves the 620 width cap on the stack, so the rendered geometry is unchanged (the anchor is still greedy horizontally and still bounded by that cap). **The `.id()` strategy is right and stays**: re-identifying the content on `selectionState.current` would reset the offset and also tear down every pane's own `@State`. The same shape exists in `GuideView.document` and is deliberately not fixed here (UX68 scoped the other scrollers out): its `.padding(.vertical, MPSpace.s6)` is on the `VStack` whose children carry the `.id(index)` jump targets, so a jump to block 0 lands below the true top, while a jump to any later heading is correct because aligning that heading with the viewport top is what was asked for. Narrower defect, own row if it is ever reported.

**The second half is about the fence, and it cost a real correction.** The first version of this test asserted the anchor appears *before* the padding in the source, and it passed against a deliberate revert to the broken shape. It had to: a modifier on a container is written after that container's closing brace, so the anchor precedes the padding in the text under both shapes. The discriminator is the **brace** between them, and the fence reads it now. Generalise it: a source fence over SwiftUI has to be run against the bug it claims to catch before it is believed, because the shapes differ by nesting and nesting is exactly what flat text order does not carry.

### A window that follows its content is not fixed by adding a scroller

Don't reach for a `ScrollView` when a window grows past the display, and don't look for the missing height constraint inside the view. `AskView` already had a `ScrollView` over the whole session and the window still grew past the screen with the oldest answers unreachable (UX70, P1, four or five questions at the Wider width). A scroller only takes over once the height it is **offered** is smaller than its content, and the window kept enlarging itself to match, so the offer never shrank. The escape is one line in `LibraryWindow.show()`: an `NSHostingController` propagates its content's size upward by default, and `NSWindow(contentViewController:)` follows it. Measured with an offscreen window and a real layout pass: a hosted column of one 200pt entry reports `intrinsicContentSize.height` 200, forty entries report 8000, and with `sizingOptions = []` both report `noIntrinsicMetric`. That is why the fix is `host.sizingOptions = []` at the window rather than a ceiling in the Ask pane: **every centre-column rail rides the same escape** (Facts, People, Meeting time, Digests all render unbounded lists there), so it is one fix rather than four, and nothing is lost because `setContentSize` and the frame autosave already own the window's size. **Read `preferredContentSize` for none of this.** It is the API `sizingOptions` names and it reads `(0, 0)` for every input in the test harness, so a fence built on it passes on the bug and on the fix alike; the intrinsic size is the same number arriving by a route that is actually observable. That correction is the reusable part: before trusting a headless AppKit measurement, check that it moves at all between the broken and the fixed shape.

### One markdown rule, and a placeholder is not content

Don't render engine prose with `Text(someString)`, and don't write a second markdown parser next to the one that already exists. `AskView` did the first, so an answer containing `**Planning the final release**` showed its asterisks, on every item of every numbered list, and the owner reported it as missing rich text (UX71). The engines are prompted for prose and return markdown, so that is the normal case rather than a malformed reply. The renderer was already next door and `private`: `SummaryRenderedView.inlineMarkdown` is now `SummaryMarkdown.inline`, promoted because Ask is a real second caller, which is the trigger `daemon/CLAUDE.md` names. Three things about it are load-bearing rather than incidental. `.inlineOnly` is what keeps a bare `[20260803-165412]` in the prose literal text instead of a link, so a stem mentioned in an answer cannot become a second affordance competing with the citation chips already under it. It parses **one paragraph**, so the pane renders one `Text` per line (`SummaryMarkdown.lines`) instead of handing it the whole answer, which would collapse a five-item list into a paragraph. And `.textSelection(.enabled)` moved with it, because UX48 established a real mouse selection is how text leaves this app and a change of renderer is exactly where that gets dropped by accident.

**The column half is the more general lesson.** Ask sits in the centre column of the Library's split view, and the detail column beside it had nothing to show, so it rendered a centred sentence: "Answers are drawn from your meetings, on-device, with citations." next to an answer already on screen, across roughly half the window. Three sibling rails did the same thing with their own sentence. A placeholder that restates what the pane beside it is doing is not content, it is a column admitting it has no job, and four of them is a pattern rather than an oversight. Owner's call (2026-08-17) was to drop it for all four rather than for the one reported. The rule is `LibraryScope.ownsTheWholeCentreColumn` rather than a branch at the render site, so the pane's contents and the column's width cannot disagree about which rails have a detail column, and its `switch` is exhaustive with no `default`, so a scope added later has to answer the question on purpose. `.digests` is deliberately not in the set: its centre column lists the digests and its detail column reads the selected one at full width, which is a real use and the reason the reader was moved there.


### A share writes three flavors and renders what the reader sees

Don't put a document on the pasteboard in one flavor, and don't build a share by reading a file and rendering it. Both are FEAT16, and both are the kind of mistake that passes every test that does not specifically look for it.

**The flavor half.** A single `NSPasteboardItem` carries `.rtf`, `.html` and `.string` at once; the receiving app takes the richest flavor it understands, and Paste and Match Style (Cmd+Shift+V in Teams, Slack, Notes and the rest) reads the plain one. So "keep the formatting" and "keep paste-without-formatting working" are one write rather than a tradeoff, and writing only HTML is the failure mode: the first paste looks perfect and the owner's plain-paste option is silently gone everywhere. `RichTextShare.write` is the one writer, it sets all three richest-first on one item, and it takes the board as a parameter (AUTO4's `copyTemplate` precedent) so the tests pin real behaviour against a scratch `NSPasteboard(name:)` instead of stomping the owner's clipboard on every run. `.rtf` is derived from the HTML through `NSAttributedString`'s reader rather than hand-built, which keeps HTML the single source; that reader is **main-thread-only**, so the header's action loads and renders on a detached task and writes back on main.

**The reader half, which is the sharper one.** What is on disk is not what the transcript tab shows. `TranscriptDisplay.displayName` maps `speaker_0` to `Speaker 1`, `speaker_unknown` to `Unknown speaker` and `THEM-A` to `Unknown A`; speaker renames live in `SpeakerLabelStore` and text edits in `TranscriptCorrectionStore`, both reversible overlays applied at read time rather than written back into `<stem>.json` (which is what keeps every naming undoable). A share written as "read `<stem>.json`, render it" therefore copies raw internal ids and un-corrected text, and it would look correct in every test that does not check for exactly that, which is why `RichTextShareTests` drives a fixture holding `speaker_0`, `THEM-A` and one renamed cluster and asserts all three flavors carry the reader's names. `MeetingShare` resolves through `TranscriptLoader.load` (which applies the corrections) then `MeetingCast.rowSpeaker`, the one read `daemon/CLAUDE.md` already names, so nothing here is re-derived. The summary has the same property in a milder form and the same answer: UX26's action checkboxes write back into `<stem>.summary.json`, so that file is the truth, and it renders through `AppleIntelligenceSummarizer.renderMarkdown`, the one summary renderer this side, rather than a second one that would drift from Python's.

**One more split worth keeping.** The summary goes through the markdown-to-HTML pass and the transcript deliberately does not. `TranscriptRow` renders spoken text as `Text(segment.text)`, a plain `String` with no markdown parsing, so a line reading `we need *some* buy-in` shows its asterisks in the app; sending that line through a markdown renderer on the way to the clipboard would turn one word italic and drop two characters the reader can see. That is the same divergence as reading the raw file, arriving by a different road. So the transcript marks up only the speaker name and the timestamp, escapes the words, and otherwise leaves them alone. The generalisation: **a renderer is only "what the reader sees" if it makes the same interpretation decisions the reading surface makes**, and interpreting more is as wrong as resolving less.

### Never pin a contrast ratio for a colour the repo does not own

`ContrastFloorTests` pins an exact WCAG ratio per token pair, and that rule is right for every hex value in `Tokens.swift`: a palette edit that moves any pair, even upward, should fail and be re-recorded rather than pass unnoticed. It is wrong for a pair built on an AppKit system colour, and the difference cost two weeks of red CI.

UX14 made the speaker palette appearance-aware: light mode uses deep hex variants (the raw system hues fail WCAG on paper), while dark mode keeps the native `.systemBlue`, `.systemPurple` and friends, which are already legible there. That is a good product decision. It also means half the palette's ratios are computed from colours Apple owns, and Apple moves them between macOS releases.

UX59 pinned all sixteen on 2026-08-04. The eight light pins were reproducible anywhere. The eight dark ones encoded the author's macOS, so the daemon job went red on the next push and stayed red until 2026-08-18: locally `swift test` passed 7 of 7, and on the runner six of eight dark pins were adrift, in both directions (4.96 against a pinned 5.59, 9.43 against 8.94). Re-pinning to the runner's numbers only moves the failure to the author's Mac, which is the tell that the pin itself is the defect rather than either machine.

The floor is the part that protects a reader, and it held on both machines the whole time: the lowest runner value was 3.57 against a 3:1 floor for a non-text UI mark, so nothing was ever actually illegible. So `assertPair` takes `pin: Double?` and the dark speaker pairs pass `nil`, asserting the floor alone.

The general rule: **pin what the repo controls, floor what it does not.** Before adding a pin, ask where the colour comes from. If the answer is AppKit, a system accent, or anything that follows the user's appearance settings, a pinned ratio is a bug with a two-week fuse and the only honest assertion is the floor.

### A capture tool must not emit a verdict it never computed

`daemon/scripts/cal3-teams-title-probe.swift` records real Microsoft Teams window titles during live meetings, and its `--report` mode emits a block that pastes straight into `daemon/Tests/MeetingPipeTests/Fixtures/window_titles.json`. Until HYG6 (2026-08-18) every emitted row carried `"expected": "recognize"` as a string literal. The probe never calls `MeetingSourceScanner.isActiveMeetingWindow` and, by an explicit decision in its own header, carries **no Teams title pattern at all**, precisely because guessing one is the defect CAL3 exists to fix. So it was asserting a value it had no way to know.

The other half is what made that expensive. `WindowRecognizerFixtureTests` reads `expected` and hard-asserts it (`XCTAssertEqual(recognized, expected)`), so the first real Teams title that this recognizer rejects would have turned weeks of owner capture into a red suite, on whatever unrelated commit the paste happened to land beside. And a rejected real title is not a remote possibility here: CAL3 was filed on the measurement that real Teams titles do **not** match this repo's guessed formats, at 3% coverage. VALOWN1's paste step said to do it "whatever the verdict says", so the trap was armed on the honest path as well as the careless one.

`expected` now takes three values. `recognize` and `reject` are asserted as before; `unknown` is **reported**, printing `[fixture] UNCLASSIFIED recognizer=… titles=…` and asserting nothing, and a human promotes the row after reading that line. Anything else fails rather than reading as `reject`, since a typo silently satisfying the negative case is the same failure one level down. The probe emits `unknown` for every capture, and a `reject` on a real captured title is now what it always should have been, a DET-band finding about `isActiveMeetingWindow` rather than a broken build.

The generalisation, which is not about window titles: **a tool that records evidence and a tool that judges it are two tools, and a recorder that fills in the judgement column is stating an untested hypothesis in a place the suite treats as ground truth.** When the recorder cannot compute the answer, the honest emission is "unclassified" plus a reporting path, not a plausible default. A plausible default is worse than a blank one, because it is the one nobody re-reads.

### A document rendered in a window has a second reader

`docs/GUIDE.md` is deliberately one file serving two readers, and DOC11 chose that for a good reason that still holds: no guide prose in Swift means editing the document is the whole edit, which is what makes its same-commit maintenance contract enforceable at all. The cost is that every line has to be true in a checkout *and* in a window, and the two disagree about what a path is.

DOC11 found one case of the disagreement and fixed exactly that case. Its parser flattens a same-document `[label](#anchor)` to its label, for the recorded reason that "one in a window resolves to nothing". Four repo-relative links were sitting in the same document while that shipped: `[`SETUP.md`](./SETUP.md)`, `[`README.md`](../README.md)` described to the reader as "the reference for every surface and every setting", `[Moving to a new Mac](../README.md#moving-to-a-new-mac)`, and `[`README.md`](../README.md#troubleshooting)`. A fifth, the engineering glossary in `ARCHITECTURE.md`, was found by the sweep. Read from the app they are worse than the anchors, not merely as bad: an anchor that does nothing is a disappointment, while a live-looking link to a document the reader has just been told is authoritative is a promise the app cannot keep, on a path that only means something inside a git checkout. That is what the owner reported on DOC11's acceptance day as "references to some development related files, which is definitely not okay from the product perspective".

**The generalisable half is the shape of the rule, not the four links.** DOC11's predicate was a list of shapes to reject (`target.hasPrefix("#")`), and the shapes that fail are open-ended: `#anchor`, `./SETUP.md`, `../README.md`, `docs/GUIDE.md`, a bare `assets/x.png`. The shapes that work are a closed set, because they are the ones the system can open. So DOC13 inverted it into `GuideDocument.canFollow`, an allowlist of `http` / `https` / `mailto`, and everything else flattens. Rejecting shapes is how the four survived a change that was specifically about this problem.

Editorial discipline is the other half, and it needed somewhere to live that the next editor is actually standing in. `<!-- repo-only -->` … `<!-- /repo-only -->` marks a run of lines a markdown renderer shows and this parser drops, which is what lets the one file carry a contents list (the rail is the app's copy of it, and two contents lists with one of them dead text is worse than one), a pointer to its sibling documents, and the rule itself as a note at the top of the file it governs. Three treatments in preference order, recorded there: fold the fact in, drop the pointer, mark it repo-only. An unclosed block swallows the rest of the document, which is the safe direction to fail and a terrible way to ship, so `GuideDocumentTests` fences the balance.

Two fences, and neither is redundant. One walks the *parsed* blocks and fails on a surviving link target containing `../` or ending in `.md`, which is the property the reader actually experiences. The other walks the *source outside the markers* for the same shapes, because the first would pass on a repo path parked inside a repo-only block: it would never render, and it would still be sitting in the file as the shape the next edit copies. The first catches a link the renderer would show; the second catches the habit.

`GuideDocument.missingCopy` is the one deliberate exception, and it is worth knowing why so it does not get "fixed". It names `./scripts/install.sh`, because it is the only state in the guide surface with no control behind it: the app has no copy of the document, re-running the installer is the entire fix, and a message in product register naming no command would leave the reader stuck. What did go was the sentence saying which file it ships as, which the reader cannot act on. The test is whether the reader can do anything with the string, not whether it looks like a path.

### A UISettings property with no writer is invisible to CI5

`scripts/truth_fences.py` catches a **dead config knob**: a key documented in `config.example.toml` or the README, rendered as a control, parsed and persisted, and consumed by nothing. It catches it by diffing *sets of `config.toml` keys*, which means it cannot see the same defect anywhere else, and `UISettings` is exactly anywhere else. Its properties are cosmetic preferences persisted straight to `UserDefaults`, deliberately kept out of `config.toml` so that file stays small and pipeline-parseable, and the fence never looks at them.

ARCH6 found two sitting there. DSN1's IA pass cut the Preferences controls for `menuBarIconStyle` (outline vs filled) and `showRegulatedBadge`, and left both properties behind. Nothing in the app assigned either one afterwards, so each was pinned at its init default forever, while the code reading them looked entirely alive: an `if style == .outline` branch inside `StatusBarController.makeIdleIcon`, two `@Published` Combine subscriptions wired in `init` to recompute on a change that could never arrive, and a `regulatedMode && UISettings.shared.showRegulatedBadge` whose second half was decoration. A year of green fences and green suites said nothing, because none of them can.

Both are now gone, along with their `UserDefaults` keys, their branches and their subscriptions. `didSet` never fired for either (Swift skips property observers during `init`), so no key was ever written and nothing is orphaned in the defaults domain.

The check the fence cannot do for you is one grep: **a `UISettings` property needs a writer, and the writer is a control.** Grep for assignments (`ui.<name> =`, a `$ui.<name>` binding), not for reads; a property with reads only is pinned, whatever its branches suggest. The same question applies to any other non-TOML setting store added later. And read a green `truth_fences.py config` as "no dead *config* key", never as "no dead knob".

### An injection seam nothing injects, and a guard nothing can reach

Three more shapes ARCH6 removed, together because the tell is the same in each: the code documents an intent, and nothing exercises it.

**`PrepCardProviding`** was a protocol with one conformer (`PrepCardStore`), one injection site that always passed that conformer, and no test that ever supplied a fake. Its comment said it kept the prompt panel from learning where recordings live, which the single method does on its own. The "use it instead" option was priced first and is genuinely expensive here: the branch a fake would reach is `MeetingPromptWindow.applyPrepCard`, which needs a presented `NSPanel` and its `lastTimeButton`, so the seam would have paid off only alongside a panel-presentation harness this repo does not have. Collapsed; re-introduce it when a second real source exists.

**`MeetingSourceScanner.scan(keepStickyOnEmpty:)`** documented a `true` mode for mid-recording ("a transient empty scan must not unbias the next pass"), and the one production caller passed `false` for the parameter's whole life, so the protection did not exist. Deleted rather than wired, on what the pin actually buys: it is a tie-break bonus in `MeetingSourceScorer.pickBest`, so it decides nothing unless two candidates score equal (never seen in this Teams-only dogfood), and the only other thing it feeds is `winnerChanged`, which gates one `discovery_shadow_pick` log line. Wiring it would have meant plumbing recording state into `MeetingDiscoveryWatcher`, which does not have it. Note the shape of the argument: empty passes mid-call are *common*, not rare (DET9 measured 48 s between confident winners, END9 a 21-33 s AX blackout), so the flag would have been active often and still changed nothing observable. Frequency is not impact.

**`PromptEndPolicy`** filtered a bare `ax_leave_button_invalid` end carrying an empty `confirmedBy` out of the prompt-clearing path, and had been unable to fire since START1. Deleted, with both comments corrected to name the guard that really holds: START1's `requiresCorroboration` check in `PromotionEngine.handleStarting`, over in Core. **If you ever relax that check, re-derive what the prompt path should do with an uncorroborated end**, because the daemon-side belt is no longer there.

A fourth was a stale comment rather than dead code, and deserves the same suspicion. `PrimarySignalKind.requiresCorroboration`'s doc said a lone ax-leave invalid is held "until a reliable signal (window-gone) corroborates". END6/AUD-10 had already put `axLeaveButton` and `shareableContentWindow` in one `EndEvidenceClass`, and `tick()` requires a *cross-class* corroborator, so for a native meeting window-gone can never satisfy that guard and the debounce path the comment describes can never fire. The rule was right and the comment was out of date. When a doc names a specific collaborator, check that the collaborator still qualifies.

### A tour is a set of claims about controls

FEAT15 shipped a guided tour over the app's own windows, and the owner picked that shape over the two cheaper ones with the trade stated: driving the real UI is the most work and the most fragile against layout, and it is the only option that cannot go stale about what exists. Getting the second half of that sentence to be true is the whole of the design, and it is not the animation.

**What goes stale, and what catches it.** A step makes three claims: a control exists, it is called what the narration calls it, and it lives in a place the app can open. Each is checked mechanically, because the failure a person sees is a tour that dims a window and rings nothing, which reads as a rendering bug rather than as a doc rot and so gets reported (if at all) as the wrong thing.

- The control is deleted. Its `.tutorialAnchor(.x)` is written *on* the control, so deleting one deletes the other, and the anchor is then attached nowhere. `TutorialFenceTests` walks every case in `TutorialAnchor` and fails on an unattached one, and on a second attachment, since two controls claiming one anchor rings whichever laid out last.
- The control is renamed. Each case declares `namedIn`, the file that must spell its `control` as a quoted literal, and the fence reads that file with whole-line comments stripped, because `PreferencesView+Permissions.swift` carries a comment saying "Regulated mode lives here" that would otherwise satisfy the check forever.
- The narration re-spells the name. It may not: the card renders `anchor.control`, and a fence rejects a step whose own prose contains its control as a whole word. That is `SummarizationEngine` and `PublishLanding`'s rule (UX31, UX49) one level up, so a rename is one edit in the enum rather than a hunt through copy.
- The anchor is deleted outright. The compiler, at every step that named it.

The runtime residue is a card that says so. `TutorialSpotlight.focus` answers `.missing` for an anchor that reported nothing, reported a zero-size frame (a control in a branch the window is not showing still reports, at zero size), or reported a frame wholly off the viewport, and the card prints the control's name with a line saying it is not on screen. That is deliberately the weaker guard: the fences are what fail a build, and this only catches what a checkout cannot see, such as a pane the tour did not select.

**Anchors point only at unconditionally-rendered controls, and that is a rule.** The filter bar's "Save as smart folder" was the first candidate for a step and had to be dropped: it is drawn only once a filter is active, so a tour opened on a clean Library would have rung nothing every time and the `.missing` card would have been the normal case rather than the alarm. Driving the real UI means a step may assume only what the surface guarantees. Making the tour set up its own preconditions is a different and much larger promise: it would be the tour driving app *state*, and every step of it would need undoing.

**The overlay lives inside the window, not above it.** A floating panel would need the target window's frame, its title-bar inset, and a child-window relationship kept in step with every move and resize, all to arrive at the coordinates the geometry probes already report directly; it would also put a second window into `WindowActivationManager`'s counting (UX39). So `.tutorialStage(_:)` is an `.overlay` on the surface root with a named coordinate space, and an anchor's frame is read in the same space the hole is drawn in. The price is that the title bar is never dimmed, which is the better behaviour anyway: the reader can still move or close the window mid-tour.

**A Preferences pane is its own surface.** A control on an unselected pane is exactly as invisible as one in a closed window, so `TutorialSurface` has `preferencesPipeline` and `preferencesPermissions` as separate cases routed through the deeplinks the app already has (`show(initial:)`). `TutorialWindow` is the coarser thing, one per hosted root, because that is the granularity a SwiftUI overlay actually has.

**The plan is phrased against what is presented, not against the previous step.** A forward-only walk marks step four `.stay` because its neighbour on the way down is in the same window. Coming back to it from a Preferences step, that left Back narrating a window the reader could not see. `TutorialPlan.entry(for:presented:)` is the single rule and `entries(for:)` is derived from it.

**What is still fragile, honestly.** A control that is scrolled out of its pane resolves as `.missing` even though it exists, because the tour does not drive scroll position. Both Preferences anchors sit on groups that are in view at the window's own minimum height, which is an assumption a future pane reshuffle can break without any fence noticing. The fences cover *what exists and what it is called*; they do not cover *where it happens to be sitting*, and no source fence can.

### A feature can ship green, documented, and never once run

END9 shipped on 2026-08-20 with 28 new tests, a doc comment describing its wiring, an ARCHITECTURE.md paragraph describing its behaviour, and a `decide()` whose logic was correct. It never executed. END10 fixed it a day later, after the owner reported that recordings "often drop at the beginning for no obvious reason". Two independent defects, and the pair is worth keeping because neither is exotic and both were invisible to a green suite.

**One: `Coordinator` held the watcher and never called `start()`.** The stored property carried the comment "started once at session setup and never per meeting", which was a claim about a line that was never written; the commit that added the property added the comment in the same three lines and never touched `Coordinator.start()`. `CallTeardownWatcher.State.available` initialises `false` and its only writer lives inside `tick()`, which is reachable only from `start()`, so `snapshot().available` was `false` for the life of every process. `CallTeardownOracle.decide` opens `guard input.oracleAvailable else { return .confirm(reason: .oracleUnavailable) }`, so every provisional end confirmed on its first consult, before `beginTeardownHold` could create its timer, emit `lifecycle_end_held` or show the HUD. The whole hold collapsed into the pre-END9 behaviour. Field proof: `lifecycle_end_held` had **zero** occurrences across every log generation, and the only two END9-instrumented confirms in existence were both false positives carrying `oracle: "oracle_unavailable"`, one chopping a live call at 31.6 s and the other at 78.7 s.

**Two: a run-loop `Timer` re-armed from a GCD queue fires exactly once.** `tick()` dispatches its work onto `readQueue` and calls `rearm` from inside that closure. The default scheduler was `Timer.scheduledTimer`, which attaches to `RunLoop.current`, and a GCD worker has no run loop being run, so the tail would have stopped after its first read even once started. `LogMuteAdapter`, the component END9's own doc comment says its threading mirrors, does not have this bug: its read closure ends with an explicit `DispatchQueue.main.async` into `consume(_:)`, whose `defer { rearm() }` therefore runs on main. END9's copy dropped the hop and kept the `Timer`. **If you schedule a repeat off the main queue, use a `DispatchSourceTimer`**, which has no run-loop dependency, or hop to main first. Which one is a design question rather than a style one: this watcher takes the dispatch timer precisely because its whole point is that the blocking half stays off main and only the parsed instant crosses back under a lock, so hopping a once-a-second file read through the main queue would contradict the class.

**Why 28 green tests could not see either.** `CallTeardownHoldTests.makeController` builds its own `CallTeardownWatcher` over a temp directory and calls `start()` on it by hand, and `FakeSessionHost.callTeardown` points at `/nonexistent/meetingpipe-tests` so `available` is false by construction. The suite pinned `decide()` and the hold state machine, both correct, while hard-coding the exact production state that was broken. Its ship note's "neutering `decide` to an unconditional confirm turns 9 red" was true and proved nothing about whether anything called it.

**So the fence is on the wiring, not the unit.** `CoordinatorWiringFenceTests` brace-matches the body of `Coordinator.start()` on the checkout and fails if `callTeardown.start()` is not in it, and `CallTeardownWatcherTests.testDefaultSchedulerReArmsOffTheMainQueue` drives the real default scheduler from a non-main context and asserts the tail ticks more than once. A source fence rather than a constructed `Coordinator`, for the same reason `TutorialFenceTests` is one: the real object builds a status-bar item, four windows and the AX and HAL buses, none of which stands up headless. **The general rule this is an instance of: when a component's correctness depends on somebody calling it, test the calling, because a unit suite over the component will be green either way.**

### An oracle that cannot see is not evidence

END10's other half, and the reason "start the watcher" was not the whole task. Starting it without these makes a fix that appears to work and then chops at a lower rate, which is harder to diagnose than a total failure.

**Availability was presence-only, recomputed every tick, with no hysteresis.** `s.available = tail.url != nil` flips on one directory listing, and the shared SlimCore resolver demonstrably flaps: `micgate`/`log_mute_source_missing` fired 323 times between 2026-08-05 and 2026-08-21, 8 of them during a single live recording, while the generation sat on disk the whole time. Any provisional landing in a flap second confirmed immediately. The fall is now damped by `unavailableAfterFailures`, and **the constant is a measurement**: every one of those 323 rows is an isolated single tick, the longest consecutive run in the corpus is 1, and there are zero runs of 2 or more, so 2 would already absorb every flap ever observed and 3 is that with margin. The rise is deliberately not damped, because a resolve that worked is proof the log is there. Re-measure before nudging it; the corpus is `events*.jsonl`.

**A `try?` made three different failures into one value.** `SlimCoreMuteLog.generations` opened with `guard let names = try? manager.contentsOfDirectory(...) else { return [] }`, so a TCC refusal, a transient I/O error and a genuinely absent family were indistinguishable, which is why those 323 rows say nothing about their own cause. It now returns a `Listing` carrying the `NSError` domain and code, and the host emits it. Note where the logging lives: Core has no `Log.event`, and the island rule is that decisions are pure and hosts do the I/O reporting, so the cause travels out through a return value to whoever owns an `EventLog`.

**A frozen generation read as a healthy oracle.** One was last written at 13:36:15 and still frozen at 14:06 with Teams running, while the owner's call ran to 13:56. Nothing checked, so a dead log would have held every genuine end for the full 150 s cap. The snapshot now carries the generation's mtime and `decide` answers `.logStale` when it predates the recording, which confirms for the same reason `oracleUnavailable` does: **an oracle that cannot see is not evidence the call is still up.** It is a separate `Reason` from `oracleUnavailable` on purpose, so the field log can tell a missing log apart from a frozen one.

**`lastTeardownAt` was session-monotonic and never scoped to the recording.** A previous call's `UnregisterCall` landing inside the 15 s lookback confirmed a later provisional; the last teardown before the 2026-08-21 chop was at 13:36:02, fifteen seconds before that recording even started. The lookback still applies, because the line leads the AX edge by about 1.3 s, but it can no longer reach back past the moment the recording began. **Writing the test for this is where it is easy to fool yourself**: the first version put the teardown 13 s before the recording start, which is *outside* the lookback from a provisional opening 10 s in, so it passed against the unfixed code for the wrong reason. It has to land inside the lookback and before the recording start to exercise anything.

**Generations ranked by mtime rather than by their own names.** The names encode creation order and never move; mtime is the field that does, so touching a rotated generation made it outrank the live one. Ranking is now by the name's stamp with mtime as the fallback for a name that does not parse.

### A doc can promise what the wiring never delivered

END11's shape, and the reason it is filed separately from the END9/END10 pair above rather than as more of the same. The failure is identical in kind, a component that only works if somebody calls it and nobody did, but this one had a *user-facing* promise on top of it.

`MeetingLifecycleCoordinator.armLeaveButton` was one line, `activeAdapter?.armLeaveButton(element)`, and `activeAdapter` is set only by `engage`. The only caller of `engage` is `handleDiscovery`, whose skip-latch and `isCoolingDown` branches both `return` before reaching it. So every explicit start (the menu row, the `⌃⌥M` hotkey, `meetingpipe://record`, the start-late notification) walked the AX tree, found the Leave button, handed it to a nil adapter, and dropped it. No `lifecycle`/`in_meeting`, no Leave-button signal, no provisional end, no end at all. `20260817-164312.wav` ran **72 minutes**, through a `system_capture_lost`, a full system sleep and a 106.8 s wake gap, because nothing could stop it; it had been started 11 seconds after a false end chopped the previous recording, which is the loop in one pair of stems.

**DET13 is not to blame and this is not a reopen.** DET13 fixed source attribution and did fix it: it retained the cooldown-suppressed sighting so `armLifecycleLeaveButton` had a `source` and found a button. Its ToC row then recorded the outcome as "`armLifecycleLeaveButton` has something to arm on", which was true about the element and silently untrue about the adapter. DET13's own change-2 finding even names the constraint in passing, describing a resolver as running "behind the `engageLifecycle` this branch returns before". The fact was known at that seam and its consequence for the neighbouring clause was not carried across. **When a fix makes an input reachable, check that its consumer is reachable too**; "X now has something to work with" is a claim about X's argument, not about X.

**The guide had already been updated to promise the behaviour.** `docs/GUIDE.md` told the reader that starting late "gets the app chip and the automatic stop", and that a hotkey start inside the cooldown is "attached to the call, so it gets the app chip and stops on its own when you leave, instead of running on until you notice". Both sentences describe END11's fix, written a fix early. They needed no edit once the wiring landed, which is the uncomfortable part: **a doc that is true only after the next task ships reads exactly like a doc that is true now**, and the same-commit contract cannot catch it, because the sentence was written in the same commit as a change that genuinely did half the job.

**The silent optional chain is the mechanism worth remembering.** `activeAdapter?.armLeaveButton(element)` cannot fail, cannot warn, and leaves nothing to grep. It now emits `lifecycle`/`arm_leave_button_dropped` with a reason instead, which is the whole of the difference between a dead feature you find in a day and one you find in five weeks. Its doc comment had said "no-op when no adapter is live" the entire time, so the behaviour was documented and still nobody knew it was the *normal* case.

**Engaging is guarded on `isEngaged`, and the guard is not an optimisation.** `engage()` opens with `disengage()`, so an unguarded engage on an explicit start would stop a healthy discovery-engaged adapter and reset the engine to `.idle` in the middle of a live meeting. `test_engagingTwice_resetsTheEngine_whichIsWhyTheGuardExists` pins exactly that, so the reason survives the next person who reads the guard as redundant.

**What a source-less recording gets, stated rather than left undefined.** It has no pid and no AX anchor, so it engages nothing and no end signal can ever reach it. Its only automatic bound is the mic-only silence backstop, which is already fed for every recording (`armSystemLevelMirror` is called on every start and `IdleStopBackstop` has no bundle dependency), so the bound exists rather than needing to be built. **Be honest about what that bound is worth**: per the dogfood record it has fired zero times, because it needs an uninterrupted stretch of non-hot mic verdicts with no system audio, and ambient noise or a sleep both break the streak. It is a real bound whose field efficacy is unproven, and reworking its VAD input is its own task. A duration ceiling was considered and rejected: this band's entire pathology is recordings being cut short, and adding a second chopper to fix a runaway is how you trade a rare visible failure for a common invisible one.

**One thing the audit turned up that the spec had backwards.** The spec asked for a matching release on every terminal path for the idle-sleep power assertion, reading `idle_sleep_assertion_held` 111 against `released` 110 as a leak. Both terminal paths (`stop()` and `flushIntermediatesForTermination`) already released, and the single unmatched hold traces to `2026-08-14T13:34:55Z`, a process that vanished with no `app_terminate` three days later, where the OS reclaims the assertion anyway. But there *was* a real leak next door: `stop()` opens with `guard let final = currentFile, let micURL, let systemURL else { return false }`, which returns before the release, so an assertion acquired by a start that never produced a file held idle sleep off for the life of the process. **A held resource released at the bottom of a function is only released on the paths that reach the bottom.**

### A fix that is correct at the moment it runs and wrong immediately after

REC16 item 1, and the reason it was filed against REC16 rather than folded into REC15's outstanding verification. REC15 taught `recoverCapture` to replace a condemned `AVAudioEngine` mid-recording, which is right. `armConfigurationChangeObserver()` registers with `object: engine`, so the observer is bound to one specific instance, and REC15 did not re-arm it. From the moment recovery ran, the observer was watching an object nothing posts to any more: `AVAudioEngineConfigurationChange` from the live engine never reached `handleConfigurationChange`, so the exact failure the observer exists to catch, a device pulled mid-call, went unhandled for the rest of the recording. REC15's shipped behaviour is correct at the instant of recovery and wrong for every second after it.

Every replacement now goes through `replaceEngine(reason:)`, which drops the old observer, swaps the engine, and re-arms only if one was armed before. A helper rather than one extra call inside `recoverCapture`, because the failure mode is a *fourth* site being added later; the fence counts the bare assignments and expects exactly two, the stored-property initializer and the one inside the helper. Note which two sites were already harmless and why it is position rather than care: `start()`'s replacement runs before the first arm, and `unwindFailedEngineStart` runs on a failed start with no recording to lose. **A guard that holds by accident of ordering is worth routing through the same helper anyway**, because the ordering is what a later edit changes without noticing.

### Two clocks measuring one recording, and only one of them sleeps

REC16 item 2. The mic channel measured its outage with `Date()`; the system channel measured its with `ProcessInfo.processInfo.systemUptime`. On Darwin that clock does not advance while the machine is asleep, so the two channels disagreed by exactly the sleep duration whenever a recording spanned one.

**Measured 2026-08-17.** `system_capture_lost` at 17:45:14 local, `system_capture_resumed` and `did_wake_while_recording` both at 17:54:31. Wallclock gap 557.0 s; the pad written was `gap_sec: 106.81894104165258`, `pad_clamped: false`. The shortfall is 450.2 s, and `pad_clamped: false` is what rules out the cap and proves the computed gap really was that short. The result is not lost audio, it is a silently wrong timeline: the finished file is shorter than the meeting by the sleep, and every system-channel sample after the wake is stamped seven and a half minutes early against the mic channel and against reality, which transcript and diarization timestamps then inherit.

The planner's doc comment had defended the monotonic choice, and its reasoning was sound as far as it went: an NTP step mid-meeting cannot move `systemUptime`. It is outweighed rather than wrong. An NTP correction on a running Mac is slewed and small; a sleep is unbounded and ordinary. **When two measurements of the same span must agree, the clock is not a per-site preference.** Same class as PIPE10's summarize timeout, in a different subsystem.

**Fixing the clock made a dormant constant load-bearing, which is the part worth pausing on.** `maxPadSeconds` was 300, comfortably above every gap a monotonic clock could ever report, so it had never fired. Measuring truthfully means a sleep-length gap now reaches it, and at 300 the 2026-08-17 case would have clamped and stayed misaligned by 257 s: the same failure wearing a fix, which is exactly what that constant's own doc comment warns against. It is now 900, re-derived against the corpus rather than nudged: the outages on record are 7.68 s, 7.83 s and 557.0 s, so 900 gives 1.6x headroom over the largest while still cutting an overnight sleep rather than writing it out at ~384 KB/s. **Whenever you correct a measurement, re-check every threshold downstream of it**; a bound that has never fired has never been tested either.

### A failure that leaves the recording running has to stay on screen

REC16 item 3. Every `configuration_change_unrecoverable` path ends in `reportRecoveryFailure`, which counts, may abandon the mic, and fires `onConfigurationChange?(.failed)`. None of them stop the recording, and the daemon log line says "mic capture stopped", meaning the mic rather than the recording. So the recording ran to its normal end writing a dead mic channel behind one dismissible notification. In the field the event fired 13 times against 5 recoveries, and once the toast was gone that path was indistinguishable from a healthy one. An owner reporting recordings "dropping" is satisfied by a file that keeps growing while capturing nothing just as well as by one that ends early.

The HUD now carries a persistent "Mic lost" state for the rest of the recording. **Deliberately the state label rather than the degraded banner the spec pointed at**: that banner carries a "Retry system audio" action, and an abandoned mic has no retry to offer, since the recorder arrives there by giving up after its budget. A control that cannot act is worse than a state that is simply true. MIC14's off-record label is this file's own precedent for a persistent state with no action attached, and it costs no geometry, since `HUDPanelGeometry.pillWidth` was already sized for the longer "Off the record".

It outranks both other label owners, because it is the only one of the three reporting something broken rather than something chosen. And it is per-recording state on a window that outlives the recording, so `dismiss()` clears it: without that, a meeting that lost its mic would open the next one reading "Mic lost" and the other two labels would defer to a failure that had already ended.
