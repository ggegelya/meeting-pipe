# daemon/ — the evidence behind the rules

Every rule in [`../CLAUDE.md`](../CLAUDE.md) links to a section here. The rule is what you must do; this section is why, and what it cost to find out. Read one when you are about to touch the thing it names, when a rule looks arbitrary and you want to know whether your case is the exception, or when you are changing the rule itself. Most of these record a measurement, so they are worth reading before you re-derive one.

Kept out of `CLAUDE.md` deliberately (DOC14). That file is prepended to every prompt in this subtree, so prose there is paid for on every turn whether or not it is relevant; this file is paid for only when read. `scripts/truth_fences.py claude` is what keeps the split honest.

Adding a rule means a line there and a section here, in the same commit. Each heading carries the task id that produced it, so `docs/backlog/` and `git log` remain the long form.

## Patterns to match

### Strict concurrency is on for this target

**Strict concurrency is on for this target too (CONC4).** `Package.swift` compiles the `MeetingPipe` executable with `-strict-concurrency=targeted`, like the Core island. A new `Sendable` capture warning is a real cross-thread finding: fix it (typed payload, `@Sendable` closure, `@preconcurrency` on an un-audited Apple module, or a `Task { @MainActor in self?.x }` hop), don't silence it. `MeetingSessionController` and `SinkDispatcher` carry a documented `@unchecked Sendable` because `@MainActor` on them cascades into the GCD / Timer / delegate layer (the out-of-scope `complete` migration); prefer a real fix over adding a third.

### Pure logic on its own type with explicit inputs

**Pure logic on its own type with explicit inputs.** When a subsystem grows non-trivial branching, lift the decision into a `decide(at: Date, …) → Action` style entry point on its own struct (see `MicGate.decide`, `AudioRetention.decide`, `MeetingSourceScorer.score`, `WorkflowMatcher.match`). The host that owns AVFoundation / NSWorkspace / TCC just forwards inputs in. T3 applied this to three shipped-untested surfaces: `StatusBarModel` (title / icon / menu rows, out of the 731-line `StatusBarController`), `NotificationRouter` (which delegate calls a notification response makes, plus the identifier vocabulary), and `SearchIndexReconciler` (the FTS upsert/delete diff). Each extraction found a real defect, so treat "this is only presentation" as a reason to extract, not a reason to skip it.

### MeetingSessionController talks to SessionHost, not Coordinator

**`MeetingSessionController` talks to `SessionHost`, not `Coordinator`.** Adding a subsystem the session logic needs means adding it to `SessionHost` (and to `FakeSessionHost` in the tests), not reaching for `Coordinator`. Protocol-type it only if a test cannot construct the real thing; a global read (the way `beginRecording` used to call `AVCaptureDevice.authorizationStatus`) has to come through the host or it takes the branch back out of reach.

### Fully-qualified type name in stored-property initializers

**Fully-qualified type name in stored-property initializers.** `Self.foo` errors with "covariant 'Self' type cannot be referenced from a stored property initializer" on Swift 5.9+. Write `StatusBarController.foo` instead. `lazy var` sidesteps this but only use lazy when deferred init is what you want.

### Combine subscriptions filter to value changes

**Combine subscriptions filter to value changes.** `removeDuplicates()` + `dropFirst()` before triggering rebuilds. The permissions poll runs at 2 s; subscribing to `objectWillChange` rebuilt the status-bar menu twice a second until the snapshot dedupe landed (`StatusBarController.PermissionsSnapshot`).

### ObservableObject and @Published debounce writes

**`ObservableObject` + `@Published` debounce writes.** `ConfigStore.scheduleSave` is the template: 500 ms `Timer.scheduledTimer`, gated on an `isInitialized` flag so the init's `didSet` storm doesn't trigger a spurious save.

### TOML round-trip preserves unknown keys

**TOML round-trip preserves unknown keys.** Read into `TOMLTable`, mutate only what the UI models, write back. New top-level tables need `ensureTable("foo")` to fetch the *live* pointer back after insertion (TOMLKit's `subscript SET` copies the source node, so first-assignment-per-fresh-table is silently dropped without this). Two stores do this now: `ConfigStore` over `config.toml` and `GlossaryStore` over `glossary.toml` (FEAT11). The glossary case is the sharper one, and since UX44 it is sharper still: the store models `[fuzzy].enabled` (the near-miss toggle) and **nothing else in that table**, so preservation there is per *key*, not per table. `writeBack` sets that one key in place rather than rewriting the table, which is what leaves `max_distance` and anything a later pipeline adds beside it alone; a write that lost them would change matching behaviour behind the user's back. The glossary's resolution is mirrored from `mp.glossary` and pinned by `Fixtures/glossary-golden.json`, whose `fuzzy_enabled` field the Swift store is now checked against too. It now has two callers rather than one (FEAT12 added the transcript's "Add to Vocabulary"), and the second went in as `GlossaryStore.addTerm` rather than as its own writer for exactly that reason: a second place that decided what a live row is would drift from `liveTerms` and take the fuzzy-preservation guarantee with it.

## Don't

### No outbound HTTP from the daemon

Don't call Anthropic / Notion APIs from the daemon. Outbound HTTP belongs in the pipeline.

### Launch at login has one owner

Don't `bootout` the resident `com.meetingpipe.daemon` agent from inside the app, and don't add a second mechanism for login-start. That agent is what launches the app, so booting it out kills the process doing the booting, under the user's pointer. `LaunchAtLoginService` (UX42) is the one owner: it reads `launchctl print-disabled gui/<uid>` and writes `enable` / `disable`, never `bootout`, and never rewrites the plist's `RunAtLoad` (launchd's disabled-overrides database is the single source of on/off, and it is also the one that survives `install.sh` regenerating the plist). The shape it replaced is the cautionary tale: the toggle drove `SMAppService.mainApp`, which the agent never consulted, so the app started at login however the switch was set and turning it off unregistered something that had never launched anything. The shell half of the same rule is `scripts/lib/login-agent.sh`, sourced by `install.sh` and `rebuild.sh`; `install.sh`'s old `launchctl load -w` re-armed the toggle on every install, because `-w` *is* a write of an enabled override. Editing that helper means re-running `sh scripts/test-login-agent-guard.sh`. **That one owner owns relaunch-after-quit too, so a surface asking "would a quit really quit" has to consult it and not only `UISettings.disableAutoRestart`**: the status bar kept offering "Quit (do not relaunch)" with the agent disabled, describing a distinction the machine no longer made (UX55). It reads `status().isOn` in `refreshMenuBeforeDisplay` and caches it, deliberately: `populateMenu` also runs on every model-download progress tick and every processing-count change, and `status()` spawns `launchctl`, so an inline read would be a subprocess per tick on the main queue.

### Startup work and the single-instance guard

Don't add startup work to `App.main()` above `SingleInstanceGuard.standDownIfPeerIsRunning()` (UX54). Everything above that call runs in the copy that is about to quit as well as in the one that lives, which is why the SEC8 Keychain migration sits below it: two processes racing on that migration was the reason to order them this way, not tidiness. The guard's exit status is `EXIT_SUCCESS` and must stay there, because the LaunchAgent's `KeepAlive = { SuccessfulExit = false }` reads a non-zero exit as "bring me back" and would respawn the stood-down copy every `ThrottleInterval` seconds forever. The half that decides which copy dies is pure (`decide`) and the newcomer always loses, since the incumbent may be mid-recording; keep it that way rather than reaching for `NSApp` inside it. **And never ask AppKit who this process is up there.** `NSRunningApplication.current` before `NSApplication` exists is a *placeholder*: measured 2026-08-04 across three live instances, it answers `processIdentifier` **-1**, nil `bundleIdentifier`, nil `launchDate`, `isTerminated` **true**. The guard shipped reading its own identity from it, and `decide` over a current with pid -1 reduces to `peer.pid < -1`, false for every real pid, so it returned `.start` to every copy and `second_instance_stood_down` was never emitted once while the owner watched two and three daemons run. The peer *query* was never the broken half and does not need moving or warming: `runningApplications(withBundleIdentifier:)` at `main()` entry, before `NSApplication`, correctly listed 0 then 1 then 2 peers with the right pids in the same probe. So identity comes from the kernel (`ProcessInfo.processInfo.processIdentifier` and `SingleInstanceGuard.kernelStartTime`, a `sysctl` `KERN_PROC_PID` read of `p_starttime`), which needs no Launch Services connection. Two facts that come with it: a peer's Launch Services `launchDate` is nil far more often than not (79 of 104 running apps on the dogfood Mac, **including the launchd-started MeetingPipe**), so the kernel read backs peers too rather than letting the order fall to pid comparison near the ~99998 wrap; and the two clocks are the same one, median disagreement 14 ms over the 25 apps LS did date. The wider lesson is the one that cost the walkthrough: a guard whose failure mode is "decided not to act" is silent by construction, so it logs one unified-log line naming the peer count on the start path too, not only on the stand-down.

### The sidecar is a single Swift-to-Python contract

Don't add a key to `MeetingMetaSidecar.build` without also updating `mp.workflow.apply_overrides` on the Python side. They're a single contract; the sidecar is the only Swift to Python surface.

### Publish state comes from publish.json

Don't read a per-sink sidecar (`<stem>.notion.json`) to learn whether a run published. A failed publisher never writes one, so an earlier run's file survives. Read `<stem>.publish.json` via `PublishResult.load` (PIPE1). **`Meeting.publishState` disobeyed this rule until PIPE14** and read `<stem>.run.json`'s `publish_state`, which only `mp run-all` refreshes, so a standalone `mp publish` left all six branch sites frozen at the previous verdict; both readers now go through `PublishResult.resolveState`, which prefers the publish sidecar and keeps the run sidecar only as a pre-PIPE1 fallback. Its shape, the `"full"` / `"partial"` / `"none"` vocabulary six sites branch on, the `mp prefetch-model` progress events `ModelDownloadSupervisor` switches on, and the speaker-overlay resolution are all pinned against Python by generated fixtures (CI4, `CI4ContractFixtureTests`). Changing the Python writer means regenerating them: `cd pipeline && uv run python ../scripts/gen_contract_fixtures.py`.

### Re-runs go through the pipeline lane

Don't spawn `mp summarize` / `mp publish` for an existing meeting outside the pipeline lane. `MeetingLibraryService.regenerateMeeting` / `.republishMeeting` enqueue a `.libraryRun` job (PIPE11) so a re-run cannot overlap a run-all or a second re-run on the same stem; calling `launcher.summarize(...)` directly from a new Library action puts the last-writer-wins race back, and it was decided by which subprocess exited last. The mirror trap is inside the lane: the regenerate chain's publish leg calls `performRepublish`, not `republishMeeting`, because re-entering the queue there would wait on the slot the job itself is holding.

### A subprocess this app killed is not a failure

Don't report a subprocess this app killed as a failure. `PipelineLauncher.LaunchError.cancelled` exists because the daemon sends the SIGTERM itself on the owner's Cancel, the child exits 15, and every surface used to render that back as `Pipeline failed: pipeline exited 15: …` captioned with whatever the child last wrote to stderr, which for a killed run is a routine INFO line (UX50). Any site that renders, notifies, or logs a pipeline error asks `PipelineLauncher.isCancellation(err)` first: four already do (`SinkDispatcher.invokePipeline`, `PipelineJobDispatcher.route`, and `MeetingLibraryService`'s regenerate / republish / ask legs), and the Library's one Cancel button reaches **all** of them, since UX28 put the re-summarize and publish re-runs in the same retain slot run-all uses. What does *not* change is the modelling: a cancelled job still completes as a failure so the row stays retryable, and it still writes a marker, because a row with no terminal sidecar sits in Processing with nothing running and then ages into a `.failed` that names no reason at all. The cancel flag is per run (`PipelineRunSlots.RunHandle`), never a bool on the launcher: a click landing just after a run ended would otherwise still be set when the next run started and label *its* genuine failure a cancellation. The same task made `nonZeroExit`'s second value a **caption** rather than the raw tail, picked by `failureCaption(stderr:)` (last `ERROR`/`CRITICAL` line, else last `WARNING`, else the tail); LOCAL16's `.memory` staging rides on the marker surviving that selection, which it does because `orchestrate` reports the fault through `log.exception`. **And the half that took a second pass to see: a completion nobody is told about is still a completion.** The row's live progress entry used to be cleared by the Coordinator's `onDone` / `onError`, which is to say by the *reporting* of a completion, while `PipelineJobDispatcher.route` returns early for exactly the two kinds that report nothing (a cancel, and a library re-run whose own surface reports it). So the quieting shipped by UX50 took the clear with it: the owner's cancelled Reprocess left the row frozen at `Cleaning up 0:20` in the **In progress** block, beside an idle toolbar, and it survived closing and reopening the Library because the entry lives on `LibraryWindowModel` and not in the view. `SinkDispatcher.onActiveProgressEnded` is the one clear now, fired from `completeActiveJob` on every path, next to UX28's busy-chip clear and for the same stated reason; the done and error closures no longer touch it. The class to watch for is state whose lifetime is a **job's** being cleared from a branch whose lifetime is a **message's**.

### Nothing blocking inside an audio render callback

Don't log or write files from inside an audio render callback (`MeetingRecorder` taps, `SystemAudioCapture`). Those run on real-time threads; blocking work there glitches the recording.

### The two capture channels need an explicit length policy

Don't merge the two capture channels without an explicit length policy, and don't let a byte count stand in for "the merge worked". `amerge` has no length option at all (`ffmpeg -h filter=amerge` on 8.1 lists `inputs` and `layout_mode` and nothing else), so a bare merge ends at the **shorter** input: a 10 s mic plus a 3 s system produced a 3.000000 s final, measured by hand with the shipped arg vector. `produceFinal` then deleted both intermediates, and the 4 KiB plausibility floor waved the result through at 192 KB while `recording_stopped {produced_final: true}` reported a clean success. Across the owner's whole log that discarded mic tail on 140 of 153 recordings, and on 2026-07-15, where system capture only came up 35.9 s into a 41.2 s meeting, it destroyed 87% of one. `RecordingPostProcessor.mergeLengths` is the one policy now (`apad` on each leg, `adelay` for a late system channel, `-t max(mic, offset + system)`) and `outputIsPlausible` re-measures the produced file against that target, failing closed onto the kept intermediates plus a `.recordfail.json`. **Padding the tail is not the whole fix**: a channel that started late carries the END of the meeting, so merging it at sample 0 puts real words against the wrong timestamps, which is worse than dropping them because the result reads as a correct transcript. And note what the fix had to repair besides code: two comments and one notification body asserted this padding for months before it existed (`MeetingRecorder.stop`'s "the ffmpeg merge pads to the longer input", `RemoteAudioWarning.interrupted`, and "the recording is mic-only from that point"). They are true now, and only while the policy holds.

### Never re-open a capture file to resume writing

Don't re-open a capture file to resume writing it, and don't leave a teardown path unbounded because a sibling path is bounded. `AVAudioFile(forWriting:)` **truncates** ("Will overwrite a file at the given URL", `AVAudioFile.h:68`; measured in `SystemCaptureRetryPlannerTests` rather than taken on trust), so `retrySystemAudio` re-entering `startSystemCapture` with the same URL destroyed every system sample captured before an SCStream death (REC10). Three things made that invisible: `handleSystemAudioLost` deliberately keeps the partial on disk *and says so in a doc comment*, REC8 made the retry hands-off so no human decision stood between the death and the overwrite, and the recovered channel then merged at sample 0, so the remote side played back early by the outage rather than reading as missing. The fix is to keep the handle and pad the gap (`SystemCaptureRetryPlanner`), which also means the SCStream-start-failure branch must not delete a file that now holds real audio. The mirror trap is REC11's: `stop()` used REC7's bounded `finish(timeout:)` while `flushIntermediatesForTermination` called the unbounded `finish()` on the same writers, so the wedge REC7 exists to bound was still unbounded on the one path that runs at quit, under a comment promising "Deadlock-free" that was true about deadlock and silent about an indefinite block. Both of these are the same class: a guarantee asserted in prose on the path that does not hold it. When two paths drain, cancel, or close the same thing, check them against each other, and when a comment states an invariant, check the code under it states the same one. Note also which reads are safe: an `AVAudioFile` write handle buffers, so its `length` is rounded to what it has flushed and its header is not valid until every strong reference is released, which is why `stop()` drops `micFile` / `systemFile` before ffmpeg reads and why a test must read back through a fresh `AVAudioFile(forReading:)`.

### Teams mute state, and how to read its log

Don't take Teams' mute state off the newest file in its log directory, don't believe the timezone that file prints, and don't add a third app-mute producer without a source tag. MIC8 reads `AirPodsService: Input mute event received: mute|unmute` out of Teams' SlimCore media log, and all four of these were measured rather than guessed. **Resolve by log family** (`MSTeamsNM_SlimCore_`): the Electron shell log rotates hourly and the media log only on a Teams restart, so the file carrying the signal is never the freshest one, measured 8th of 132 on 2026-08-04, and a flat newest-N cut is exactly what made a 2026-07-13 recon conclude Teams was not logging at all. **The stamp is UTC with the local offset suffixed after it**, so `07:30:24.277723+03:00` happened at 07:30:24 UTC; parsing the offset as real is wrong by the offset everywhere except on a UTC machine. **Anchor on the whole message**, because the shell log's hourly ECS config blob carries an `hfpOsUnmuteFixEnabled` key that a bare `mute` token reads as a hit. And **an absent line is unknown, never unmuted**: the `AirPodsService` component name is a misnomer, but the data cannot rule out a dependency on AirPods being connected for output. The fusion is the last one: two producers now write `MicGate`'s app-mute field and both arrive through `injectAxMuteEvent`, so a new one passes its `MuteReadingSource` or it silently competes on last-writer-wins with the oracle that is supposed to outrank it. `docs/spikes/mic8_log_correlation.py` is the standing regression test after a Teams update, and it is cheap: one command, no meeting needed.

### Event-stream data goes through Log.event

Don't `print(...)` for event-stream data. Use `Log.event(category:action:attributes:)` so `mp logs` / `mp analyze-detection` see it. A new category goes in the `CONVENTIONS.md` table in the same commit and the action must be snake_case, both fenced by `scripts/truth_fences.py` (CI5).

### Config defaults live in ConfigDefaults

Don't hardcode a config default at its read site when more than one reader needs it. `ConfigDefaults` (ARCH5) is the single home that `Config.load`, `Config.defaultFallback`, and `ConfigStore.init` all read; a literal in two of the three is how Preferences and the running daemon come to disagree about a value nobody changed.

### Network promises in copy are derived from the routing

Don't put a parenthetical promise about the network in a control's copy without deriving it from the routing. `DigestNarration` (UX63) is `RegulatedMode`'s sibling for the weekly digest, and the string it replaced is the cautionary tale: the sole footer of the group that installs the digest's LaunchAgent read "on-device (no new egress)", unconditionally, while an unattended run on 2026-08-03 logged `POST https://api.anthropic.com/v1/messages` and "narrative via anthropic". The module's own docstring had it right in the **qualified** form ("No new always-on egress: this is a command you run or schedule"), and the qualification is the entire content: it is a claim about *scheduling*, not about the network, and dropped it reads as a guarantee. Three rules decide which engine narrates, and they compose only because none of them can ever select a cloud engine: `summarization.digest_local_only` (the owner-chosen opt-out UX63 added, applied Python-side by `digest.narration_config` as a narrowed config handed to the one chokepoint, never a second selection path), the zero-egress clamp, and the ask/digest `apple_intelligence` substitution. `auto` is deliberately reported as **itself** rather than resolved, since it picks per run on whether the cloud answered and its own name already says "cloud, fall back to local". The test worth copying is the paired one: the footer's "nothing leaves it" clause is asserted to appear *exactly* when `staysOnThisMac` is true, over every backend crossed with regulated and local-only, so neither half can move without the other.

### Backend display names live in SummarizationEngine

Don't spell a summarization backend's display name at its render site either. `SummarizationEngine` (UX31) is the same rule for strings the user reads: it is keyed off the raw backend id and exposes the three registers the surfaces need (bare name for the pickers, `Name (where it runs)` for provenance / menu / inspector, a present-tense phrase for the busy and Ask lines), and the eight sites all read it. Seven independent switch tables is how the detail header came to call `anthropic` "Claude (cloud)" while the `...` menu over it called the same call "Anthropic (cloud)"; worse, `claude_cli` and `openai` shipped and nobody remembered five of the seven, so an OpenAI meeting rendered no engine at all. A new backend adds one entry there and one case to `WorkflowBackend`, and `SummarizationEngineTests` fails until it does both. **A phrase needing two engines is a function on that type, not a fourth `var` and never a string at the render site** (UX64's `answeredFooter(ran:substitutedFrom:)`): `mp ask` and `mp digest` have no Apple Intelligence path, so `engine.complete_text` answers on the local MLX model and stamps `substituted_from`, and the Ask pane dropped the key on the floor and rendered "Answered on-device" while spawning the resident multi-GB model the owner picked that backend to avoid. Note the nil rule is *stricter* than UX31's and deliberately so: an unnameable engine on **either** side yields nil, because falling back to the plain single-engine line over a run the pipeline recorded as a substitution would hide exactly the fact the line exists to show, and a line that contradicts the record is worse than no line. And check whether the fact is actually on disk before promising a surface it: the digest reader loads `<stem>.summary.json`, which carries no engine at all, and `DigestResult` records `backend` without `substituted_from`, so the same line there is a Python change plus a new read, not a render.

### Regulated-mode copy is derived from the clamp

Don't describe a privacy clamp in copy written beside it rather than derived from it. `RegulatedMode` (UX60) is the `SummarizationEngine` rule applied to a *consequence* instead of a name, and it is the one where drift was a false privacy claim: the only control for `modes.regulated_mode` was titled "Skip Notion publish" with a Notion-only sublabel and footer, while `config.effective_backend` pins summarization to the on-device model for **every** meeting whenever it is on. On the owner's `anthropic` config, flipping it for one client call silently repointed the whole library onto Qwen at lower quality, and if the model was never fetched the run refuses outright rather than downloading. `README.md` had additionally asserted the **opposite of the code** in three places for months, including a `mp doctor` warning that had been an `_info` since 8591d186. The fix is that every string is built from `RegulatedMode.effectiveBackend`, the mirror of the Python chokepoint, so `RegulatedModeTests` can assert the clamp and the sentence about it in one breath. Two traps came with it. The copy has to be **gated on whether the clamp actually moves anything**, or a Mac already on `local` is warned about a change that cannot happen there, which is the guard-fires-on-everything failure in miniature. And the missing-model case had to be surfaced *here*, at the switch, not only in the menu bar's Finish setup row: `ConfigRefreshCoordinator.prefetchDecision` keys on the **configured** backend, so a Mac on `anthropic` never pre-fetches the model regulated mode is about to demand, and nothing downloads until someone asks. That is what the inline UX21 `LocalModelPreflight` affordance in that group is for; the eager prefetch does not cover it.

### Publish sink names live in PublishLanding

Don't spell a publish sink's name at its render site either, and don't infer the destination from anything but `<stem>.publish.json`. `PublishSink` / `PublishLanding` (UX49, extended by UX62 with a `symbolName` register and `PublishLanding.localNote`) is the `SummarizationEngine` rule for where a meeting *landed*: one phrase per sink, plus the pure `decide` that maps a run's sinks map to what a surface may claim. **The rule had two more disobedient readers than UX49 found, both fixed by UX62, and both failed the same way: silently, on the majority case.** `MeetingStore.needsRepublish` counted only `.notion.json` and `.obsidian.json` as evidence of a publish, so a filesystem or LAN publish was indistinguishable from never published and the row's inline Republish capsule could not appear for it, ever; and the detail header's Open buttons branched on those same two sidecars, so the same meetings had no open action at all. That is not a tail: the owner's default `Personal` workflow is filesystem-only and held 117 of 190 tagged meetings, **107 of 245 stems** had a `.filesystem.json` and no `.notion.json`, 13 of the last 15 meetings were blind, and every NDA meeting is too, since NDA mode force-selects filesystem-only sinks. Two things worth carrying: the staleness read takes the sidecar's **mtime** rather than a `ts` inside it (every publish path rewrites that file, so its mtime *is* the last publish, and parsing a timestamp buys nothing), and a reader added to `PublishURLs.fingerprint` at the same time, because a file that "nothing here reads" stops being one the moment a button is built from it and a guard that cannot see it means the button never appears. `localNote` answers only for filesystem and LAN on purpose: Obsidian's header button is an `obsidian://` deep link assembled from the vault relationship, so serving it from `publish.json`'s `page_url` would open the note *outside* Obsidian, and it reads the **per-sink** `page_url` rather than the top-level one, which is whichever sink came first in `output.sinks`. The done notification is the cautionary tale, and a quiet one, since nothing was broken: its body and its Open button were the literal `"Open in Notion"`, consulting nothing, so the owner's last nine meetings all published to the filesystem and all announced a Notion page, offering to open a local Markdown file as if it were one (the action itself opens `page_url`, so it always landed correctly). Two traps live in that rule. `page_url` alone cannot name a destination: it is the *first* successful sink in `output.sinks` order, so it says what to open and not who wrote it, which is why two landings read as `.unnamed` rather than picking one. And a notification action's title is baked into its **category** at registration time, so a phrase that varies needs a category per phrase (`NotificationRouter.doneCategory(for:canCorrect:)`); that is the mechanical reason the literal survived as long as it did.

### One row, one speaker identity

Don't read a transcript row's speaker off `segment.speakerID`, and don't let one row answer "who is this line" twice. A line carries two identities, the raw diarization label in `<stem>.json` and whatever the speaker overlay resolves it to, and a per-line reassignment (FEAT3-SEGMENT) deliberately moves only the second, since leaving `<stem>.json` intact is what makes every naming reversible. The row used to render the overlay's answer and branch its menu on the raw one, so a line moved off Sudip onto Unknown E read "Unknown E" and still offered **Rename…** for Sudip; typing a name there would have re-enrolled Sudip's voiceprint under it and renamed her on every other line of the meeting, silently (UX57). The one read is `MeetingCast.rowSpeaker(for:overlay:voiceprintLabels:)`: it answers with the label the row *is* (the per-segment override, else the raw label), the in-app name over it, and the menu items, each carrying its own target label so a call site has no raw label in scope to hand a callback by mistake. Its gates mirror `VoiceResolutionBar.actions(for:)`, which is why the cast strip was the one surface that stayed right through this, and it is also the identity anything else keyed per row (a colour, a dot) should ask. **Colour is the first taker (UX58), and it is now `MeetingCast.colorIndex(for:in:)` plus `TranscriptDisplay.color(atCastIndex:)`, a slot in the meeting's cast rather than a property of a label; there is no `color(for: <raw label>)` left to call.** The one line it replaced was three defects at once: keyed on the raw label, so the dot stayed on Sudip when a line left her; `abs(label.hashValue) % 8` in a language that reseeds string hashing per process, so every speaker changed colour on every launch (measured across three processes, `THEM-A` on slot 3, then 4, then 7); and about a 92% chance that two of six voices drew the same slot. Cast position is a pure function of the meeting's files, so it is stable across launches, unique to the palette's eight, and it moves with a reassignment because the identity it indexes does. Two consequences worth knowing: the colour is per **meeting**, so one person can read differently in two meetings, and naming somebody does not repaint anything, since the name lands on a cast member that already exists rather than appending one. **The cast strip mirrors that same index now (UX59)**, as a `colorIndex` on `VoiceResolution.Voice` filled in `derive`, not as a read the chip does for itself: two surfaces each deriving "which colour is this person" is exactly the disagreement UX59 existed to remove, so a third surface that wants a speaker hue asks the same function or takes the slot from the pure type, and never re-derives one. The trap on the chip is the mark it sits next to. Its leading glyph is tinted by `VoiceResolutionBar.tint(for:)`, which is FEAT11's resolution status, so the identity dot went in as a **separate sibling view** rather than as a recolour of that glyph; recolouring it would have made every chip consistent with the transcript and simultaneously destroyed the only surface that says whether roster matching worked. Keep the two marks separate, and keep both off hue-only: identity is the dot plus the name beside it, status is a distinct symbol per origin plus its tint plus the `Name` affordance.

### A config key needs a consumer

Don't add a config key to `Config.swift` / `ConfigStore.swift` without a consumer and a line in `config.example.toml`. CI5's dead-knob fence fails on a key that is parsed, persisted, and rendered as a Preferences control while nothing reads the value; that shipped three times before it was fenced, and the symptom is a user changing a setting and nothing happening.

### Fields in summary.json must be modeled in Swift

Don't add a field to `<stem>.summary.json` on the Python side without modeling it in Swift's `MeetingSummary` too. `jsonObject()` re-serializes only the fields the struct knows about, and it is the writer behind *both* in-place rewrites of that file (`MeetingLibraryService.setActionResolved`'s done/reopen toggle, which both the Facts rail and the Summary tab route through since UX26, and `SummaryTab.persistEdit`'s correction save). An unmodeled field is not preserved-by-default; it is silently deleted the first time the user ticks an action done. FEAT10's `evidence` is the worked example, `EvidenceTests` pins it, and anything the editor can retext also needs a remap rule (`MeetingSummary.carryEvidence`) so a stale citation cannot outlive the sentence it backed. Those same two rewrites are why **`<stem>.summary.json`'s mtime never means "this summary was generated then"**: ticking one action done makes a months-old summary look freshly written. Anything asking when the prose was produced reads `<stem>.run.json`'s `ts` instead (UX41's `MeetingStore.namesChangedSinceSummary` is the shipped reader), and not the run sidecar's mtime either, since a publish rewrites that file to record `publish_state`.

### A window holding user text must re-check what it read

Don't let a window that holds user-authored text write a record about a file it read once and never re-checked. `CorrectionWindow` (UX65) is the case, and it is the **inverse** of the rule above it: UX52's store-revision reload key is the wrong tool here, because silently re-reading would discard the owner's in-progress edit, which is worse than the bug. So the guard is at the **save**, not on the read: `show()` captures `SummaryIdentity` (the file's bytes), `SummaryStaleness.hasMoved` compares it in `performSave`, and a moved file raises a choice instead of writing. Three things are worth carrying. **The direct lost update people expect here does not exist**, and the sweep that surfaced this named the wrong mechanism: `handleOutcome` writes one file, `corrections/<stem>.json`, and never opens `<stem>.summary.json`; the surface that overwrites the live summary is `SummaryTab.persistEdit`, which already tracks an mtime and is deliberately out of scope. The damage is one step removed instead, and it is why this is not cosmetic: `CorrectionsTab.performRevert` restores `<stem>.summary.json` **from the record's `original_summary`** and then deletes the record, so a stale original is superseded prose waiting to be written back over whatever is current, under a button labelled Revert, and `corrections/` is simultaneously the LoRA corpus. And identity is the **bytes**, not an mtime plus a size: a rewrite producing identical content moves the mtime, and stopping a save to ask about a change that did not happen is the fires-on-everything failure the walkthrough's last step exists to catch. `performSave` takes the dialog as a parameter for the same reason: the assertion that matters is "no record was written", which has to be pinned on the bytes of the record file rather than on a return value.

### Run state must outlive the view that started it

Don't keep a running job's state in a view the navigator rebuilds. The Library's center column is an `if/else` on `scope`, so every rail switch destroys the projection view and its `@State` with it; Ask held its whole run there (question, asking, answer) and a switch to Facts threw the answer away while `mp ask` kept burning its ten-minute budget invisibly, uncancellably, into a result file the `defer` then deleted (UX37). Run state that outlives its view lives on `LibraryRootView` as a `@StateObject` (`AskModel`, `DigestListModel`), and the view renders it. The tell is easy to miss: an unstructured `Task {}` is NOT cancelled when the view that started it dies, so nothing looks wrong, it just completes into nothing.

### Finish an operation by publishing MeetingStore.revision

Don't finish an operation that rewrote a meeting's files without publishing `MeetingStore.revision`, and don't grow a second signal beside it. The `if/else` on `scope` above is also why a missing refresh hides: a tab or rail switch rebuilds the detail pane from disk, so an operation that publishes nothing still looks correct the moment the user navigates, and navigating is the natural thing to do while waiting. The one signal is the store's rescan: `revision` bumps, and each pane keys its `.task(id:)` on `(stem, revision)` with a modification-date guard so an unrelated rescan is a no-op (`SummaryTab.SummaryReloadKey`, `TranscriptTab.TranscriptReloadKey`, `MeetingDetailView.PublishURLsReloadKey`). The header is *nearly* free, since the same scan rebuilds the `Meeting` it reads, and the exception is the one thing in it read off disk: the Notion / Obsidian Open buttons come from the two publish sidecars, so they need a key of their own (UX53). Re-transcribe was the reported instance (UX52): it ended at `retranscribe_done` having published nothing and leaned on the directory watcher, so a finished run left the old transcript on screen; `MeetingLibraryService` now calls its injected `refreshLibrary` on both outcomes, after the overlay carry so the rows and the cast strip are never a run apart. Two traps come with it. The guard has to cover **every** sidecar the pane reads, not just the obvious one: a rename writes only `<stem>.speaker_labels.json`, so a guard watching `<stem>.json` alone would skip exactly the reload it exists to allow. And publishing only part of what an operation changed reads as a fix: a re-transcribe changes the text, the speaker clusters, and the header lines at once. UX53 swept all 29 operations against that, and the useful result is which half actually breaks. **Publishing is almost never the problem.** Both trees write sidecars atomically, an atomic write is a temp file plus a rename, and the watcher is on the *directory* fd, so essentially every operation already reaches a bump without asking; re-transcribe was unusual in that its own publish mattered (its `mp finalize` leg rewrites in place). What breaks is the second half, a pane that gets the bump and ignores it, and it has one grep-able signature: a `.task(id: meeting.stem)` or an `.onAppear` sitting over a disk read. Check for that before adding a signal. The two stem-keyed loads still in the detail view are deliberate and documented where they are (`AudioTab` must not re-attach the player under a listener; `CorrectionsTab` is a modal sheet), and the surfaces UX53 named rather than fixed are in `docs/backlog/tasks/UX53.md`, each with the design question that kept it out of that task.

### Step state must outlive a navigator rebuild

Don't keep state a step must not lose in a view the navigator rebuilds, and don't treat `WorkflowStore.delete` as guaranteed. Both halves shipped in onboarding's workflow step and together put four "Client work" rows in the owner's config (WF9). `OnboardingRootView` is a `switch step`, so Back / Continue destroys and recreates the step and its `@State` with it; anything that has to outlive a round trip lives on the root and comes down as a `@Binding` (`OnboardingWorkflowChoice`). And `delete(id:)` returns `false` for the default rather than throwing, so a caller replacing a workflow reuses its id instead of deleting and re-creating: every preset is created `isDefault: true`, so the delete was always a no-op and the replacement always landed beside its predecessor. Nothing new calls `delete` directly: `WorkflowDeletion.run` is the one flow (UX30), it maps that `false` to a reason the surface has to show, and it dismisses the host exactly once on success. A workflow *editor* saves through `WorkflowStore.update`, never `upsert`, because the append branch is how a sheet left open over a deleted workflow used to write it back.

### Shared primitives are the design system, and are not private

Don't pile inline styles into a SwiftUI view, and don't declare a shared-looking primitive `private`. The shared primitives (`SettingsGroup`, `SettingsRow`, `SettingsSegmented`, `SettingsSlider`, `SettingsStatusPill`, `SettingsSecretField`, `SettingsHotkeyField`, plus the destructive `MPDangerButtonStyle` / `.mpDanger` and the wrapping `FlowLayout`, in `Preferences/PreferencesControls.swift`) are the design system, alongside the DSN24 button styles in `Design/MPButtonStyle.swift` (`.mpGhost`, `.mpIcon`). Add new primitives there rather than parallel one-offs. The danger button is the worked example of the `private` half: it shipped inside `BatchActionsPane` for the Library's "Move to Trash", so the workflow editor could not see it, wrote a code comment asserting the app had no destructive button style, and rendered Delete as a neutral ghost capsule with the same weight as Save (UX30). `FlowLayout` is the second (UX51), and it also shows where the line is: it stayed `private` in `PreferencesView+Recording.swift` through UX38, which looked at promoting it and declined **for one speculative caller**, correctly. A real second caller is the trigger, not a hypothetical one, and when it arrives the move is to promote rather than to write a second copy beside it.

### Never anchor a CALayer mask at origin zero

Don't anchor a `CALayer` mask (or any layer) on a scrolling view at `origin: .zero`. A mask is positioned in its layer's coordinate space, and an `NSClipView`'s bounds *origin* is exactly what moves when its document scrolls, so a zero-anchored mask keeps covering the document's first screenful while the viewport moves away from it, and every point past that composites **fully transparent** rather than unmasked. UX47's prep-card fade shipped that way for an afternoon: scrolled 82pt into a 205pt card with a 123pt viewport, content survived only in bounds 82-123 and the OPEN ACTIONS eyebrow and action rows below were invisible however far the owner scrolled. Take `clip.bounds` whole. `PrepCardTests` fences it, after first tripping on the comment that explains it.

### Never frame-size a scroll view's Auto Layout document

Don't frame-size a scroll view's document that hosts Auto Layout content, and don't trust `translatesAutoresizingMaskIntoConstraints` to hold the frame you set there. UX34 handed `PrepCardView` a 600pt frame as an `NSScrollView` document; under the layout engine a TAMIC-true document with constraint-based subviews takes its size from the *content*, so the card laid itself out 879pt wide, every trailing constraint held against an edge 279pt past the glass, the configured tail-ellipsis never fired (bullets sliced mid-glyph at the clip), and the right-aligned date rendered off-panel from UX34's landing until UX47 caught it with a layout probe. Constraint-host the document instead: TAMIC false, width pinned to `scroll.contentView`, height pinned to the measured content height. The height half of UX34's "known before the view exists" reasoning was always sound; only the width was lying.

### Shapes are greedy in both axes

Don't put a bare `Rectangle` (or any `Shape`) as a stack sibling when you want the stack sized to its content. Shapes are greedy in both axes, so with no width constraint the shape takes every point offered, the enclosing `VStack` inherits that greed, and a row of such stacks divides the whole pane while the trailing `Spacer` gets nothing. The detail pane's tab strip shipped exactly that (UX36): `tabButton` drew the active-tab underline as a `Rectangle` sibling beneath the label, so the source read `HStack { tabs; Spacer(minLength: 0) }` and looked left-aligned, while the app rendered three tabs spread across a 1230pt pane with an underline several times wider than its word. Draw an underline as an `.overlay(alignment: .bottom)` on the thing it underlines, so it sizes to that thing. `SummaryLayoutTests` pins the overlay form, since neither greed nor alignment is observable at runtime.

### SettingsRow column widths, and window minimums

Don't let a `SettingsRow`'s control column fight its label column for width, and don't set a window's minimum below the floor the SwiftUI root inside it declares. The info column is greedy (`.frame(maxWidth: .infinity)`) while a button, pill, or picker has no compression resistance of its own, so the squeeze lands on the control and truncates its text: Storage's "Choose destination…" read as an ellipsis, with People and Caches carrying the same two-ghost-button shape (UX43). The row fixes that column horizontally now, which is only what the locked `PWRow` mockup already pinned with `flexShrink: 0`; the one control that genuinely wants the remaining width (the Pipeline pane's scrolling prompt preview) passes `controlFills: true`, because pinning a `ScrollView` to its ideal width is a mile of unwrapped prose. The window half is the same defect a level up: `PreferencesWindow` allowed 720x560 against a root demanding 780x660, so the user could resize past the hierarchy's own floor. Use `contentMinSize`, not `minSize`, which is frame-space and would still allow a content box a title bar shorter than asked. And a `ScrollView` created *outside* a content switch keeps its offset across it, so Storage scrolled to the bottom left General opening at the bottom: reset with a `ScrollViewReader` and a constant top anchor, never `.id(<the selection>)` on the content, which resets the offset by discarding every pane's `@State` with it.

### Never offer a picker option whose setter drops it

Don't offer a picker option whose setter drops it. The Local model picker offered Custom unconditionally while its binding derived the selection from the stored model id alone, so picking Custom wrote nothing, the getter re-derived the previous preset, the picker snapped back, and the Model id field gated on Custom could never appear: a row that had been dead since it shipped (UX43). Custom is a real target now (the pane holds the selection in `@State`, and `LocalModelPreset.showsModelIdField` reveals the field for exactly the selections that write nothing on their own). The other resolution is DIAR3's, for a control with no field behind it: `SpeakerSeparation` offers Custom only while it is already the selection, so it is a readout nobody can pick. Either is fine; an option always on offer that does nothing is not.

### The detail header is chrome, not content measure

Don't put a detail pane's header on one of its tabs' content measures, and don't centre a measured column in an uncapped one. `MeetingDetailView`'s header and tab strip are a **chrome band** on `bgSunk` spanning the pane (UX36), deliberately not on `SummaryLayout.readingMeasure`: `TranscriptTab` and `AudioTab` are full-width, so a header indented to the summary's measure is aligned on one tab and misaligned on the other two the moment the tab changes. The band recesses rather than lifts, because on `bgRaised` it was an 11-of-255 step off the dark canvas, invisible in a screenshot, and a band nobody can see licenses nothing. Content then left-aligns on **one** edge across every tab, which is affordable only because `LibraryLayout.detailMaxWidth` caps the column: uncapped, left alignment leaves a growing void to the right (the original shape) and centring puts the summary 200+ pt right of the header and transcript so the axis jumps per tab (the second shape, rejected on sight). Cap the column, then left-align; `SummaryLayoutTests` pins both halves. The measure itself (720, the top of the 640-720 band `design/README.md` allows, owner-picked 2026-07-29) is shared by **both reading tabs**: `TranscriptTab` rides the same `SummaryLayout.readingMeasure` stack, because at full pane width its wrapped monologue turns were the longest lines in the app and the right edge jumped ~300pt between the two reading tabs. The pieces inside the transcript's measure (cast strip, captions, rows) carry no horizontal padding of their own, so the stack's gutter is the only inset; re-adding a row-level inset re-opens the edge disagreement in miniature. Audio, the playback transport, and the empty states stay full-bleed on purpose: instruments and states, not reading content. The mirror of this is a footer: give it the width of the thing it serves, not of the pane it sits in. `WorkflowInspector`'s Edit shipped on a full-pane `bgRaised` plinth under a 416pt card, a filled band three times wider than its own content, and the owner read it as a control from another app (UX33). A resting surface gets a hairline and no fill, per `design/README.md`; the card's footer is the card's width.

### Derive a content ceiling, not a floor

Don't cap a pane's content at the width its narrowest allowed window would dictate. `WorkflowInspectorLayout.cardMaxWidth` is the worked example: the first pass derived 416 from `LibraryLayout.detailMinWidth - 2 * padding` so the card kept side margins at the floor, which is a correct derivation of the wrong quantity, since `.frame(maxWidth:)` already shrinks a wider cap back at the floor. The result was a card frozen at the minimum window's width on every window, which is the ribbon UX33 existed to remove. Derive a *ceiling* from what the content wants to read at (here the 640-720 reading column), and let the frame handle the floor.

### Window activation has one owner

Don't front, activate, or count a Dock-participating window from its own `show()`. `WindowActivationManager.showWindow(_:)` owns the open sequence for the four that take a Dock icon (Library, Preferences, Diagnostics, Guide) and `didCloseWindow(_:)` owns the way back, because both halves are ordering bugs a diff cannot show (UX39). `setActivationPolicy` is processed asynchronously, so a `makeKeyAndOrderFront` + `activate` in the same run-loop turn as the flip, or before it, which is how all three sites used to read, is evaluated against the still-accessory app: macOS then appends the app to the Cmd+Tab MRU **tail**, and the owner's report was that the Library sat last in the switcher with no way to Cmd+Tab straight back. **But nothing waits for that transition any more, and UX56 is the reason (two passes, and the second is the one to know).** The wait was unconditional. Its cost is a run-loop turn in which the app the user came from can keep or reclaim focus, and on macOS 14 activation is cooperative, so this app asks rather than takes. Pass one narrowed the wait to "while a policy raise is in flight", which fixed the reported case (a Preferences window landing behind the Library that opened it: the toolbar gear, Cmd+, from the main menu, the Vocabulary and permission cross-links) and left the raising path alone. Walking that on 2026-08-04 the owner found the discriminator on the path still waiting: the window came up behind the frontmost app **and** the app sat at the Cmd+Tab **tail**, which is precisely the position the wait exists to buy. So on the one path that still deferred, the deferral was paying its cost and buying nothing, which is evidence against the wait rather than for a wider one. Pass two removed it: every window is fronted and activated in the turn that asked, and a raise queues **one** `activate` for the turn after it, when the transition has certainly landed. That keeps UX39's rule 1 as a *retry* rather than as a wait, it is a no-op on an app that is already frontmost, and it is queued per transition (at the raise) rather than per window, so two windows opened in one turn front in ask order with the second on top and share the one retry. Note also which path is which, because it is the opposite of the obvious reading: every open from the status-bar menu with nothing else up **is** a first-window open, since the last close drops the policy back to `.accessory`. The manager counts by window identity for a second reason of the same kind: `NSWindow.isVisible` is false while a window is miniaturized, so the `if !w.isVisible` guard each site carried counted a reopen-from-the-Dock as a fresh open while only one `windowWillClose` ever arrived, and the app stayed `.regular` with nothing on screen. QuickFind, Onboarding, and Correction skip the handshake on purpose (a floating panel and two one-shots), which is the only reason they still call `NSApp.activate()` themselves; that is also the modern spelling, since `activate(ignoringOtherApps:)` is deprecated on the macOS 14 floor. **The menu bar rides the same two moments (UX48):** `MainMenu.install` in the step that raises the policy, `MainMenu.remove` in the step that drops it. Those panels therefore still have no main menu while they are up, which is the known edge and belongs to UX27, not to a second install site.

### Command-key shortcuts need a main menu

Don't fix a missing command-key shortcut with a hidden control in the view hierarchy. `NSApp.mainMenu` is where macOS matches a command-key event **first**, and this app had none at all, so Cmd+C, Cmd+A, Cmd+X, Cmd+V, Cmd+M, Cmd+W and Cmd+, were all the system beep in the Library and a transcript's text could not be copied out with the keyboard (UX48). The shape that had been tried instead is the cautionary tale: 292dfe49 hid a zero-opacity SwiftUI `Button` carrying `.keyboardShortcut(",")` in `LibraryWindow`'s background and wrote a comment asserting that a key equivalent needs one there. Measured at pickup, that button does fire; what it cannot do is generalise, because Copy and Select All have to reach the text under the pointer rather than a control this app owns, so a second patch of that shape would have been one more per-shortcut special case. `MainMenu.swift` is the one place now: App / Edit / Window, every item on a **nil target** so AppKit walks the responder chain from the key window. Preferences lands on `AppDelegate.openPreferencesFromMainMenu` rather than on `Coordinator`, since a menu item's chain reaches `NSApp`'s delegate and not the coordinator. Adding a row means adding it there, with a chord `MainMenuTests`'s collision check can see.

### The reading surfaces have no NSTextView

Don't assume the reading surfaces have a right-click Copy to fall back on. There is **no `NSTextView` in this app**: the transcript, the summary, Ask, and the Guide are SwiftUI `Text` under `.textSelection(.enabled)`, which AppKit backs with a `SwiftUI.SelectionTextField` (an `NSTextField` subclass) that carries no `.menu`, returns nil from `menu(for:)`, and does not respond to `copy:` (measured 2026-08-04 with an offscreen `NSHostingView` probe). `TextEditor` is the only NSTextView-backed control here and it appears only in editing sheets. So the main menu is not a convenience over a working mouse path; on the reading surfaces it is very likely the only path text has out of the app. **Both probes ran without a real selection, and the owner falsified their strong reading on 2026-08-04.** The measurements themselves stand: with nothing selected, that field answers `acceptsFirstResponder` **false**, `makeFirstResponder(field)` leaves the *window* as first responder, `window.fieldEditor(false, for:)` is **nil**, and `validRequestor(forSendType: .string, returnType: nil)` is nil (offscreen `NSHostingView` probe by UX48, repeated on a real on-screen `NSWindow` by FEAT13). What neither probe could do is create a live selection: a synthetic `mouseDown` enters AppKit's tracking loop and blocks, and `selectAll:` on a field that refuses first responder is a no-op. So both measured the **no-selection** state and neither covers the case the user is actually in. Walking UX48 on 2026-08-04, the owner selected transcript text with the mouse, right-clicked **the selection**, got a context menu, and **Copy worked**. So a real selection does engage a text path AppKit will serve, a mouse route out of the app exists, and the earlier conclusion that "no field editor is ever engaged" is true only of the untouched control. UX48's band stayed P2 on that evidence. Do not right-click the transcript **line** to check this: the row carries its own `.contextMenu` (Edit text…, Clarify…), so it answers first and tells you nothing about the text path. What remains genuinely unmeasured is whether this process can read that selection **programmatically**; the nil `validRequestor` was measured with no selection, so treat FEAT13's row-context-menu affordance as the right design (the row owns its own actions, which the owner independently confirmed is where those belong) with its stated justification unproven rather than established.

### App Intents compile standalone

Don't reference another file's types from `Automation/MeetingPipeAppIntents.swift`. `install.sh` compiles that file **standalone** with `swift-frontend` to emit the App Intents metadata Shortcuts discovers, and a lone-file compile cannot resolve cross-file references. The breakage is silent in the worst way: `swift build` still succeeds, the app still installs, and only the native Shortcuts actions quietly vanish. Keep its `meetingpipe://` verbs as literals (`MeetingPipeAppIntentsTests` pins them to `AutomationCommand.parse` so they cannot drift), and re-run `daemon/scripts/auto1-app-intents-probe.sh` after an Xcode bump, since the extraction rides private compiler flags.

### App Intents are discoverable but not invocable

Don't try to make the native App Intents actually run on an ad-hoc-signed build, and don't re-derive why they don't. They are **discoverable but not invocable**: all six list in Shortcuts, and invoking one fails with "Shortcuts couldn't communicate with the app" (the app is never contacted, never crashes, logs no `automation` event). Six causes were excluded by measurement on 2026-07-19/20 (symbols present, LS registration fine, `openAppWhenRun` both ways, launchd vs `open -a`, `LSUIElement` both ways, no crash); the remaining one is code signing, since the bundle is `spctl`-rejected with `TeamIdentifier=not set`. `install.sh` therefore emits the metadata only under `MP_APP_INTENTS=1`. The header comment in that file carries the full list, so read it before spending an evening on this.

### A no-op test is not a conflict test

Don't take a test that a second writer **agreed** with an override as covering the case where it **disagrees**. `TranscriptOverlayCarry.carry` retires a text correction the new transcript already satisfies, whose reasoning is right ("the ratchet subsumed the fix, and keeping a no-op override would only make the next diff harder to read"). What that asks is whether the transcript moved *toward* `editedText`. It had no test for the transcript having moved *away* from it, which is what a vocabulary term does when the owner authored both halves, so the carry could not see the one case where its two inputs contradict each other. Observed on `20260803-165412` the day FEAT13 and FEAT12 both landed (UX66): `glossary.toml` carried `Jorji = "Georgy"` under the Personal workflow, the re-transcribed `20260803-165412.json` held `Georgy` and seven `Max` and **no `Jorji` anywhere**, so the rule applied correctly, and the pane still rendered `Jorji` because `TranscriptCorrectionStore.apply` overlays `editedText` at load. The owner read it as the rule failing; `Macs` looked fine only because no overlay sat on those lines. Two properties made it worse than one confusion: it is **permanent** (every load re-applies it, and every later re-transcribe re-anchors and re-snapshots `originalText` to the new text, so a stale override comes out looking freshly authored) and it was **silent** (it counted as `carried`, which reads as success). The fix is not a precedence change. Overlay-beats-rule is correct and stays: a per-meeting manual fix should outrank a global rule. What was wrong is that the loser was invisible, so `carry` now takes the meeting's resolved terms and counts a contradiction apart from `carriedCorrections`, and both report surfaces name it. Matching is `Clarify.containsTerm`, the same `\b(<key>)\b` case-insensitive rule the substitution replaces on, because a conflict detector looser than the rule it checks reports conflicts that rule cannot cause. The generalisation worth carrying: **whenever two write paths can touch the same text, a test that they agree is not a test that they conflict, and the conflict case is the one that ships silently.**

### A Preferences control that shells out is on the freeze list too

Don't leave a `Process` round-trip on the main thread because the control around it looks cheap, and don't cache a machine reading for a view's lifetime. `LaunchAtLoginModel` did both, and the two together are UX67: walking UX55 on 2026-08-04 the owner found **Launch at login** and **Relaunch after quitting** would not move, and only a full app quit cleared it. The filing named two candidate mechanisms, a refused `launchctl` (the switch correctly showing the machine, UX42's design) and a stale cached reading (UX53's missing-refresh class). **Reading the code, neither explains the report, and that is the useful part.** *Relaunch after quitting* does not touch launchd at all: it binds to `ui.disableAutoRestart`, a plain `@Published` on the `UISettings` singleton with a `UserDefaults` `didSet`, so it has no refusal path and no cached read and cannot decline to move. The only thing that stops both toggles at once is the main thread being blocked, and the one blocking thing in that pane is `ProcessLaunchctl.run`: `readDataToEndOfFile` returns when the child's pipe closes, so a `launchctl` that does not exit blocks it forever, and `LaunchAtLoginModel.set` made up to three of those calls (`enable`, `print`, `bootstrap`) inline. The session that produced the report had just run `./scripts/rebuild.sh`, which boots the `com.meetingpipe.daemon` label out and bootstraps it back, so the domain was busy with that exact label while the pane was open. That is candidate **C**, it is the same class as a stuck `stopCapture` or a wedged AX round-trip, and it explains all three of the owner's observations: both toggles dead together, the window otherwise fine (main only wedges while a click is in flight), cleared by a full quit. All three are fixed rather than one: every `launchctl` call now has a watchdog that kills the child at `ProcessLaunchctl.ceilingSeconds`, the model runs reads and writes on a detached task and publishes back on main with an `isBusy` the toggle disables on, and the reading is re-taken on the pane's `.onAppear` rather than only in `init`. A refused write also emits `daemon.launch_at_login_write_refused` now, carrying launchctl's exit status and stderr tail, so candidate A stops depending on somebody happening to look at the group footer. Two things worth keeping: the initial read stays synchronous, because the alternative is rendering a placeholder before the machine has been asked, which is the control-lies-about-launchd defect UX42 removed; and `refresh()` is not a per-render read, since `status()` spawns a subprocess and UX55 already recorded what an inline read on a hot path costs. **The generalisation: a control whose two halves fail independently, where one half cannot fail at all, is not two bugs. It is one blocked thread.**

### A scroll anchor belongs outside the padding, and ordering cannot fence it

Don't make a scroll-to-top anchor the first **child** of a container that carries the top padding. `PreferencesView` did, so a pane switch landed 28pt below the top with a band still to scroll up into (UX68, found on UX43's own walkthrough the day it was verified). The cause is exact rather than approximate: `.padding(.vertical, 28)` was applied to the `VStack` while the zero-height anchor was that stack's first child, so the anchor's top edge sat 28pt below the scrollable content's true top, and `scrollTo(anchor: .top)` aligned it with the viewport exactly as asked, leaving the padding above the fold. The offset **was** the padding constant and would have tracked any change to it, which is why a numeric compensation was the wrong fix twice over. The fix moves the padding onto the content beside the anchor and leaves the 620 width cap on the stack, so the rendered geometry is unchanged (the anchor is still greedy horizontally and still bounded by that cap). **The `.id()` strategy is right and stays**: re-identifying the content on `selectionState.current` would reset the offset and also tear down every pane's own `@State`. The same shape exists in `GuideView.document` and is deliberately not fixed here (UX68 scoped the other scrollers out): its `.padding(.vertical, MPSpace.s6)` is on the `VStack` whose children carry the `.id(index)` jump targets, so a jump to block 0 lands below the true top, while a jump to any later heading is correct because aligning that heading with the viewport top is what was asked for. Narrower defect, own row if it is ever reported.

**The second half is about the fence, and it cost a real correction.** The first version of this test asserted the anchor appears *before* the padding in the source, and it passed against a deliberate revert to the broken shape. It had to: a modifier on a container is written after that container's closing brace, so the anchor precedes the padding in the text under both shapes. The discriminator is the **brace** between them, and the fence reads it now. Generalise it: a source fence over SwiftUI has to be run against the bug it claims to catch before it is believed, because the shapes differ by nesting and nesting is exactly what flat text order does not carry.

### A window that follows its content is not fixed by adding a scroller

Don't reach for a `ScrollView` when a window grows past the display, and don't look for the missing height constraint inside the view. `AskView` already had a `ScrollView` over the whole session and the window still grew past the screen with the oldest answers unreachable (UX70, P1, four or five questions at the Wider width). A scroller only takes over once the height it is **offered** is smaller than its content, and the window kept enlarging itself to match, so the offer never shrank. The escape is one line in `LibraryWindow.show()`: an `NSHostingController` propagates its content's size upward by default, and `NSWindow(contentViewController:)` follows it. Measured with an offscreen window and a real layout pass: a hosted column of one 200pt entry reports `intrinsicContentSize.height` 200, forty entries report 8000, and with `sizingOptions = []` both report `noIntrinsicMetric`. That is why the fix is `host.sizingOptions = []` at the window rather than a ceiling in the Ask pane: **every centre-column rail rides the same escape** (Facts, People, Meeting time, Digests all render unbounded lists there), so it is one fix rather than four, and nothing is lost because `setContentSize` and the frame autosave already own the window's size. **Read `preferredContentSize` for none of this.** It is the API `sizingOptions` names and it reads `(0, 0)` for every input in the test harness, so a fence built on it passes on the bug and on the fix alike; the intrinsic size is the same number arriving by a route that is actually observable. That correction is the reusable part: before trusting a headless AppKit measurement, check that it moves at all between the broken and the fixed shape.

### One markdown rule, and a placeholder is not content

Don't render engine prose with `Text(someString)`, and don't write a second markdown parser next to the one that already exists. `AskView` did the first, so an answer containing `**Planning the final release**` showed its asterisks, on every item of every numbered list, and the owner reported it as missing rich text (UX71). The engines are prompted for prose and return markdown, so that is the normal case rather than a malformed reply. The renderer was already next door and `private`: `SummaryRenderedView.inlineMarkdown` is now `SummaryMarkdown.inline`, promoted because Ask is a real second caller, which is the trigger `daemon/CLAUDE.md` names. Three things about it are load-bearing rather than incidental. `.inlineOnly` is what keeps a bare `[20260803-165412]` in the prose literal text instead of a link, so a stem mentioned in an answer cannot become a second affordance competing with the citation chips already under it. It parses **one paragraph**, so the pane renders one `Text` per line (`SummaryMarkdown.lines`) instead of handing it the whole answer, which would collapse a five-item list into a paragraph. And `.textSelection(.enabled)` moved with it, because UX48 established a real mouse selection is how text leaves this app and a change of renderer is exactly where that gets dropped by accident.

**The column half is the more general lesson.** Ask sits in the centre column of the Library's split view, and the detail column beside it had nothing to show, so it rendered a centred sentence: "Answers are drawn from your meetings, on-device, with citations." next to an answer already on screen, across roughly half the window. Three sibling rails did the same thing with their own sentence. A placeholder that restates what the pane beside it is doing is not content, it is a column admitting it has no job, and four of them is a pattern rather than an oversight. Owner's call (2026-08-17) was to drop it for all four rather than for the one reported. The rule is `LibraryScope.ownsTheWholeCentreColumn` rather than a branch at the render site, so the pane's contents and the column's width cannot disagree about which rails have a detail column, and its `switch` is exhaustive with no `default`, so a scope added later has to answer the question on purpose. `.digests` is deliberately not in the set: its centre column lists the digests and its detail column reads the selected one at full width, which is a real use and the reason the reader was moved there.
