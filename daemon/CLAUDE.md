# daemon/ — Swift menu-bar app

Loaded when you touch files in this subtree. The full subsystem map is in [`../ARCHITECTURE.md`](../ARCHITECTURE.md); patterns in [`../CONVENTIONS.md`](../CONVENTIONS.md); terms in [`../ARCHITECTURE.md#glossary`](../ARCHITECTURE.md#glossary). This file is the short list of things that bite if you forget them.

## Build + test

```bash
swift build               # from daemon/
swift test                # full Xcode required locally (CI on macos-14 has it)
../scripts/coverage.sh swift   # T3: llvm-cov report, not a gate; needs full Xcode
```

`swift test` fails with `import XCTest` if only Command Line Tools are installed. Write tests anyway — CI runs them. To run locally, `sudo xcode-select -s /Applications/Xcode.app` first.

## Patterns to match

- **Strict concurrency is on for this target too (CONC4).** `Package.swift` compiles the `MeetingPipe` executable with `-strict-concurrency=targeted`, like the Core island. A new `Sendable` capture warning is a real cross-thread finding: fix it (typed payload, `@Sendable` closure, `@preconcurrency` on an un-audited Apple module, or a `Task { @MainActor in self?.x }` hop), don't silence it. `MeetingSessionController` and `SinkDispatcher` carry a documented `@unchecked Sendable` because `@MainActor` on them cascades into the GCD / Timer / delegate layer (the out-of-scope `complete` migration); prefer a real fix over adding a third.
- **Pure logic on its own type with explicit inputs.** When a subsystem grows non-trivial branching, lift the decision into a `decide(at: Date, …) → Action` style entry point on its own struct (see `MicGate.decide`, `AudioRetention.decide`, `MeetingSourceScorer.score`, `WorkflowMatcher.match`). The host that owns AVFoundation / NSWorkspace / TCC just forwards inputs in. T3 applied this to three shipped-untested surfaces: `StatusBarModel` (title / icon / menu rows, out of the 731-line `StatusBarController`), `NotificationRouter` (which delegate calls a notification response makes, plus the identifier vocabulary), and `SearchIndexReconciler` (the FTS upsert/delete diff). Each extraction found a real defect, so treat "this is only presentation" as a reason to extract, not a reason to skip it.
- **`MeetingSessionController` talks to `SessionHost`, not `Coordinator`.** Adding a subsystem the session logic needs means adding it to `SessionHost` (and to `FakeSessionHost` in the tests), not reaching for `Coordinator`. Protocol-type it only if a test cannot construct the real thing; a global read (the way `beginRecording` used to call `AVCaptureDevice.authorizationStatus`) has to come through the host or it takes the branch back out of reach.
- **Fully-qualified type name in stored-property initializers.** `Self.foo` errors with "covariant 'Self' type cannot be referenced from a stored property initializer" on Swift 5.9+. Write `StatusBarController.foo` instead. `lazy var` sidesteps this but only use lazy when deferred init is what you want.
- **Combine subscriptions filter to value changes.** `removeDuplicates()` + `dropFirst()` before triggering rebuilds. The permissions poll runs at 2 s; subscribing to `objectWillChange` rebuilt the status-bar menu twice a second until the snapshot dedupe landed (`StatusBarController.PermissionsSnapshot`).
- **`ObservableObject` + `@Published` debounce writes.** `ConfigStore.scheduleSave` is the template: 500 ms `Timer.scheduledTimer`, gated on an `isInitialized` flag so the init's `didSet` storm doesn't trigger a spurious save.
- **TOML round-trip preserves unknown keys.** Read into `TOMLTable`, mutate only what the UI models, write back. New top-level tables need `ensureTable("foo")` to fetch the *live* pointer back after insertion (TOMLKit's `subscript SET` copies the source node — first-assignment-per-fresh-table is silently dropped without this). Two stores do this now: `ConfigStore` over `config.toml` and `GlossaryStore` over `glossary.toml` (FEAT11). The glossary case is the sharper one: `[fuzzy]` is a live pipeline knob with **no** UI, so a write that did not preserve it would turn fuzzy matching off behind the user's back, and its resolution is mirrored from `mp.glossary` and pinned by `Fixtures/glossary-golden.json`.

## Don't

- Don't call Anthropic / Notion APIs from the daemon. Outbound HTTP belongs in the pipeline.
- Don't add a key to `MeetingMetaSidecar.build` without also updating `mp.workflow.apply_overrides` on the Python side. They're a single contract; the sidecar is the only Swift to Python surface.
- Don't read a per-sink sidecar (`<stem>.notion.json`) to learn whether a run published. A failed publisher never writes one, so an earlier run's file survives. Read `<stem>.publish.json` via `PublishResult.load` (PIPE1). Its shape, the `"full"` / `"partial"` / `"none"` vocabulary six sites branch on, the `mp prefetch-model` progress events `ModelDownloadSupervisor` switches on, and the speaker-overlay resolution are all pinned against Python by generated fixtures (CI4, `CI4ContractFixtureTests`). Changing the Python writer means regenerating them: `cd pipeline && uv run python ../scripts/gen_contract_fixtures.py`.
- Don't spawn `mp summarize` / `mp publish` for an existing meeting outside the pipeline lane. `MeetingLibraryService.regenerateMeeting` / `.republishMeeting` enqueue a `.libraryRun` job (PIPE11) so a re-run cannot overlap a run-all or a second re-run on the same stem; calling `launcher.summarize(...)` directly from a new Library action puts the last-writer-wins race back, and it was decided by which subprocess exited last. The mirror trap is inside the lane: the regenerate chain's publish leg calls `performRepublish`, not `republishMeeting`, because re-entering the queue there would wait on the slot the job itself is holding.
- Don't log or write files from inside an audio render callback (`MeetingRecorder` taps, `SystemAudioCapture`). Those run on real-time threads; blocking work there glitches the recording.
- Don't `print(...)` for event-stream data. Use `Log.event(category:action:attributes:)` so `mp logs` / `mp analyze-detection` see it. A new category goes in the `CONVENTIONS.md` table in the same commit and the action must be snake_case, both fenced by `scripts/truth_fences.py` (CI5).
- Don't hardcode a config default at its read site when more than one reader needs it. `ConfigDefaults` (ARCH5) is the single home that `Config.load`, `Config.defaultFallback`, and `ConfigStore.init` all read; a literal in two of the three is how Preferences and the running daemon come to disagree about a value nobody changed.
- Don't spell a summarization backend's display name at its render site either. `SummarizationEngine` (UX31) is the same rule for strings the user reads: it is keyed off the raw backend id and exposes the three registers the surfaces need (bare name for the pickers, `Name (where it runs)` for provenance / menu / inspector, a present-tense phrase for the busy and Ask lines), and the eight sites all read it. Seven independent switch tables is how the detail header came to call `anthropic` "Claude (cloud)" while the `...` menu over it called the same call "Anthropic (cloud)"; worse, `claude_cli` and `openai` shipped and nobody remembered five of the seven, so an OpenAI meeting rendered no engine at all. A new backend adds one entry there and one case to `WorkflowBackend`, and `SummarizationEngineTests` fails until it does both.
- Don't add a config key to `Config.swift` / `ConfigStore.swift` without a consumer and a line in `config.example.toml`. CI5's dead-knob fence fails on a key that is parsed, persisted, and rendered as a Preferences control while nothing reads the value; that shipped three times before it was fenced, and the symptom is a user changing a setting and nothing happening.
- Don't add a field to `<stem>.summary.json` on the Python side without modeling it in Swift's `MeetingSummary` too. `jsonObject()` re-serializes only the fields the struct knows about, and it is the writer behind *both* in-place rewrites of that file (`MeetingLibraryService.setActionResolved`'s done/reopen toggle, which both the Facts rail and the Summary tab route through since UX26, and `SummaryTab.persistEdit`'s correction save). An unmodeled field is not preserved-by-default; it is silently deleted the first time the user ticks an action done. FEAT10's `evidence` is the worked example, `EvidenceTests` pins it, and anything the editor can retext also needs a remap rule (`MeetingSummary.carryEvidence`) so a stale citation cannot outlive the sentence it backed.
- Don't keep state a step must not lose in a view the navigator rebuilds, and don't treat `WorkflowStore.delete` as guaranteed. Both halves shipped in onboarding's workflow step and together put four "Client work" rows in the owner's config (WF9). `OnboardingRootView` is a `switch step`, so Back / Continue destroys and recreates the step and its `@State` with it; anything that has to outlive a round trip lives on the root and comes down as a `@Binding` (`OnboardingWorkflowChoice`). And `delete(id:)` returns `false` for the default rather than throwing, so a caller replacing a workflow reuses its id instead of deleting and re-creating: every preset is created `isDefault: true`, so the delete was always a no-op and the replacement always landed beside its predecessor. Nothing new calls `delete` directly: `WorkflowDeletion.run` is the one flow (UX30), it maps that `false` to a reason the surface has to show, and it dismisses the host exactly once on success. A workflow *editor* saves through `WorkflowStore.update`, never `upsert`, because the append branch is how a sheet left open over a deleted workflow used to write it back.
- Don't pile inline styles into a SwiftUI view, and don't declare a shared-looking primitive `private`. The shared primitives (`SettingsGroup`, `SettingsRow`, `SettingsSegmented`, `SettingsSlider`, `SettingsStatusPill`, `SettingsSecretField`, `SettingsHotkeyField`, plus the destructive `MPDangerButtonStyle` / `.mpDanger`, in `Preferences/PreferencesControls.swift`) are the design system, alongside the DSN24 button styles in `Design/MPButtonStyle.swift` (`.mpGhost`, `.mpIcon`). Add new primitives there rather than parallel one-offs. The danger button is the worked example of the `private` half: it shipped inside `BatchActionsPane` for the Library's "Move to Trash", so the workflow editor could not see it, wrote a code comment asserting the app had no destructive button style, and rendered Delete as a neutral ghost capsule with the same weight as Save (UX30).
- Don't frame-size a scroll view's document that hosts Auto Layout content, and don't trust `translatesAutoresizingMaskIntoConstraints` to hold the frame you set there. UX34 handed `PrepCardView` a 600pt frame as an `NSScrollView` document; under the layout engine a TAMIC-true document with constraint-based subviews takes its size from the *content*, so the card laid itself out 879pt wide, every trailing constraint held against an edge 279pt past the glass, the configured tail-ellipsis never fired (bullets sliced mid-glyph at the clip), and the right-aligned date rendered off-panel from UX34's landing until UX47 caught it with a layout probe. Constraint-host the document instead: TAMIC false, width pinned to `scroll.contentView`, height pinned to the measured content height. The height half of UX34's "known before the view exists" reasoning was always sound; only the width was lying.
- Don't put a bare `Rectangle` (or any `Shape`) as a stack sibling when you want the stack sized to its content. Shapes are greedy in both axes, so with no width constraint the shape takes every point offered, the enclosing `VStack` inherits that greed, and a row of such stacks divides the whole pane while the trailing `Spacer` gets nothing. The detail pane's tab strip shipped exactly that (UX36): `tabButton` drew the active-tab underline as a `Rectangle` sibling beneath the label, so the source read `HStack { tabs; Spacer(minLength: 0) }` and looked left-aligned, while the app rendered three tabs spread across a 1230pt pane with an underline several times wider than its word. Draw an underline as an `.overlay(alignment: .bottom)` on the thing it underlines, so it sizes to that thing. `SummaryLayoutTests` pins the overlay form, since neither greed nor alignment is observable at runtime.
- Don't put a detail pane's header on one of its tabs' content measures, and don't centre a measured column in an uncapped one. `MeetingDetailView`'s header and tab strip are a **chrome band** on `bgSunk` spanning the pane (UX36), deliberately not on `SummaryLayout.readingMeasure`: `TranscriptTab` and `AudioTab` are full-width, so a header indented to the summary's measure is aligned on one tab and misaligned on the other two the moment the tab changes. The band recesses rather than lifts, because on `bgRaised` it was an 11-of-255 step off the dark canvas, invisible in a screenshot, and a band nobody can see licenses nothing. Content then left-aligns on **one** edge across every tab, which is affordable only because `LibraryLayout.detailMaxWidth` caps the column: uncapped, left alignment leaves a growing void to the right (the original shape) and centring puts the summary 200+ pt right of the header and transcript so the axis jumps per tab (the second shape, rejected on sight). Cap the column, then left-align; `SummaryLayoutTests` pins both halves. The measure itself (720, the top of the 640-720 band `design/README.md` allows, owner-picked 2026-07-29) is shared by **both reading tabs**: `TranscriptTab` rides the same `SummaryLayout.readingMeasure` stack, because at full pane width its wrapped monologue turns were the longest lines in the app and the right edge jumped ~300pt between the two reading tabs. The pieces inside the transcript's measure (cast strip, captions, rows) carry no horizontal padding of their own, so the stack's gutter is the only inset; re-adding a row-level inset re-opens the edge disagreement in miniature. Audio, the playback transport, and the empty states stay full-bleed on purpose: instruments and states, not reading content. The mirror of this is a footer: give it the width of the thing it serves, not of the pane it sits in. `WorkflowInspector`'s Edit shipped on a full-pane `bgRaised` plinth under a 416pt card, a filled band three times wider than its own content, and the owner read it as a control from another app (UX33). A resting surface gets a hairline and no fill, per `design/README.md`; the card's footer is the card's width.
- Don't cap a pane's content at the width its narrowest allowed window would dictate. `WorkflowInspectorLayout.cardMaxWidth` is the worked example: the first pass derived 416 from `LibraryLayout.detailMinWidth - 2 * padding` so the card kept side margins at the floor, which is a correct derivation of the wrong quantity, since `.frame(maxWidth:)` already shrinks a wider cap back at the floor. The result was a card frozen at the minimum window's width on every window, which is the ribbon UX33 existed to remove. Derive a *ceiling* from what the content wants to read at (here the 640-720 reading column), and let the frame handle the floor.
- Don't reference another file's types from `Automation/MeetingPipeAppIntents.swift`. `install.sh` compiles that file **standalone** with `swift-frontend` to emit the App Intents metadata Shortcuts discovers, and a lone-file compile cannot resolve cross-file references. The breakage is silent in the worst way: `swift build` still succeeds, the app still installs, and only the native Shortcuts actions quietly vanish. Keep its `meetingpipe://` verbs as literals (`MeetingPipeAppIntentsTests` pins them to `AutomationCommand.parse` so they cannot drift), and re-run `daemon/scripts/auto1-app-intents-probe.sh` after an Xcode bump, since the extraction rides private compiler flags.
- Don't try to make the native App Intents actually run on an ad-hoc-signed build, and don't re-derive why they don't. They are **discoverable but not invocable**: all six list in Shortcuts, and invoking one fails with "Shortcuts couldn't communicate with the app" (the app is never contacted, never crashes, logs no `automation` event). Six causes were excluded by measurement on 2026-07-19/20 (symbols present, LS registration fine, `openAppWhenRun` both ways, launchd vs `open -a`, `LSUIElement` both ways, no crash); the remaining one is code signing, since the bundle is `spctl`-rejected with `TeamIdentifier=not set`. `install.sh` therefore emits the metadata only under `MP_APP_INTENTS=1`. The header comment in that file carries the full list, so read it before spending an evening on this.
