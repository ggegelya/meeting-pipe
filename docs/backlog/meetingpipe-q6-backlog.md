## How to pick up a task (delegation)

Mechanics are codified in `/tech-task <ID>` (read the task here, read the orientation docs, implement, verify, one commit on `main`, do not push). Soft context that command does not carry:

- Task ids carry no `TECH-` prefix (e.g. `/tech-task STOR1`). Historical code comments, ADRs, and commits keep the old `TECH-` form as provenance.
- **Full specs live one per task in [`tasks/<ID>.md`](./tasks/)**; items carried from Q4 unchanged keep theirs in [`q4-final.md`](./q4-final.md) (search the id), so each spec has a single owner.
- User locale: 99% English / Ukrainian. Do not default examples to German. Verify any new `uk` labels in `MuteLabels.toml` with the user.
- The user is vibe-coding: high-level explanations, does not read code. Lean on the ARCHITECTURE.md diagrams. Blind sub-pixel visual churn is out of bounds; visual changes need eyes, and the daemon is a menu-bar app that is not screenshotable here, so a rendered eyeball is owner-owed.
- No em-dashes in any output (CI fails on a U+2014 in any added line repo-wide, and on any U+2014 present at all under `daemon/Sources` / `daemon/Resources`; `scripts/pre-commit` blocks both at commit time when installed). Use hyphens, commas, or rewrite. Commit with the repo's git identity. Do not push without permission.
- Binding constraint (CLAUDE.md): the primary user is the author; selling is tertiary; technical excellence in core functionality comes first. The BRAND launch band stays deferred. The 2026-07 redesign band (DSN20-29 + WF6 + UX15) shipped in Q5; the only redesign residual is the owner-run `/design-sync` push, an outward sync tracked as an owner action, not a task.
- The AI/DV standing rule: every `AI*`/`DV*` capability and any new engine call must route through the local engine path so the `egress_guard` clamps it under regulated/NDA, honour `effective_backend()` (forced local under regulated/NDA), and add no new always-on egress.
- Owner walkthroughs (2026-07-30, owner request): every task gated on an owner action (a verification remainder, a probe run, a decision, an eyeball) carries an `## Owner walkthrough` section at the end of its spec, steps tagged [owner] / [session] by who acts. When picking such a task up, follow that section step by step with the owner instead of re-deriving the procedure, and give new filings of that shape the same section.
- Owner verification is gated and lives elsewhere (2026-08-18, owner request): a session may not decide on its own that its task is owner-owed. It states what the owner has to do, what a pass looks like, what it costs them, and why a harness cannot check it instead, then stops and asks. Only on approval does the task's header take `status: owner-verify` and `verification: simple` or `complex` (by what the check costs the owner); [`owner-verification.md`](./owner-verification.md) carries the gate. Filed after REC12 and REC13 both landed with walkthroughs the owner could not run when asked. An unapproved or vague verification is not a status, it is unfinished scoping.
- Acceptance bars never pin an absolute suite total (2026-08-04, HYG5): a figure like `baseline at filing: 1770` is true against exactly one base and stops being true the moment anything else lands, which during a parallel batch is immediately and repeatedly. The bar is the suite being green plus the number of tests the task adds (`swift test` green, 8 new tests), because both halves stay checkable against any base. Measure the baseline on your own branch rather than trusting a filed one, and record what you measured in the ship note, not back in the bar.
- The de-CLI standing rule (2026-07-10): the CLI is a debugging escape hatch, not a product surface. A task that ships a user-facing capability includes its UI affordance in the same task; a CLI-only ship is `partial`, not done. Exempt by class (owner-dev diagnostics): dogfood, analyze-detection, corrections-stats, train-adapter, spike harnesses. Rationale: the Q4 validation audit carried 13 tasks for the CLI-only-no-UI pattern, it recurred in Q5 (AI4), and unwritten goals lose to written personas in an AI-steered repo.

## Marking a task done

A task's state is its header in `tasks/<ID>.md`; [`INDEX.md`](./INDEX.md) is regenerated from it (`python3 scripts/backlog.py index`) and committed in the same commit. When a task ships done-done, set `status: done`, add `closed: <date>`, and put a one-line ship note naming the commit in `comment:`. The file stays where it is, so every link to it keeps resolving. A partial ship stays `partial` with the remainder named in `comment:`.

When the remainder is the owner running something rather than a session building something, it does not stay `partial` and it does not move on a session's own say-so. Name the verification, get the owner's approval, then set `status: owner-verify` and `verification: simple` or `complex`. [`owner-verification.md`](./owner-verification.md) carries the gate, the two weights, and how a task leaves it. `/tech-task` codifies both.

Before 2026-10-26 a done task's row and spec moved into [`q6-final.md`](./q6-final.md) and its `tasks/` file was deleted. That archive is frozen now, and the next paragraph is the rule its entries follow.

**Entry header form in the archive.** An archived entry opens with the bold form, `**[DONE] <ID> (<priority>): <title>**`, on its own paragraph. Two forms had accreted by 2026-08-18, 132 bold against 28 headings, and three of the ten landings that day picked the heading form while three picked bold, so it was two live conventions being chosen at random rather than anyone's slip. HYG8 settled it on the majority form on 2026-08-19 and **deliberately did not restyle the 28 existing heading entries**: the point is to stop the divergence growing, and rewriting 28 archived headers churns a record for no reader's benefit. A bold line is a paragraph rather than a heading, so **it must be preceded by a blank line** or markdown folds it into the paragraph above and renders both as one run-on; that is invisible in a diff and has happened twice, both times from a both-sides-add merge in this file.
