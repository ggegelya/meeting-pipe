# T18: The cross-tree goldens pin less than CONVENTIONS claims: the meta-contract fixtures assert about half the sidecar keys Python reads, the prefetch golden and the publish failure shape come from hand-written generator inputs, and the restore plan has no generated fixture

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source findings: G020, G018, F188, F193 and G049 in the [independent audit](../../audits/2026-11-12-independent-audit.md), merged at filing because they share one seam: `scripts/gen_contract_fixtures.py`, the fixtures under `daemon/Tests/MeetingPipeTests/Fixtures/`, and the Swift and Python tests that read them. Every claim below was re-read in code at HEAD `3a2da4fc` on 2026-11-14; one was narrower than reported and says so.

CONVENTIONS' [cross-tree golden fixtures](../../../CONVENTIONS.md#cross-tree-golden-fixtures) section opens with "Every Swift-Python surface where both trees implement the same thing is pinned by one checked-in fixture that both suites read". Four places where that is not so:

**1. The meta-contract fixtures pin the overlay, not the sidecar (G020).** The seven `meta-contract/*.meta.json` files are written and verified by `MetaContractFixtureTests` on the Swift side. On the Python side the `test_contract_fixture_*` tests in `pipeline/tests/test_workflow_overlay.py` assert only what `apply_overrides` resolves: `summarization.backend`, `output.sinks`, `summarization.team_context`, `notion.database_id`, `modes.workflow_nda_mode`, `modes.regulated_mode`, plus `schema_version` and the literal `held_end_trim_sec`. The fixtures also carry `workflow_name`, `workflow_id`, `meeting_title` and `source_display_name`, and nothing in Python asserts them, although production reads each: `read_meta(...).get("workflow_name")` in `actions.py`, `mcp_tools.py` and `glossary.py` (per-workflow vocabulary); `meta.get("workflow_id")` in `summarize.py` (the previous-meeting lookup); and `publish_notion.py` through `_load_meta_sidecar` for `apply_meeting_title` (`meta.get("meeting_title")`) and the Notion Workflow and Source properties (`meta.get("workflow_name")`, `meta.get("source_display_name")`). `workflow_extra_sections` (WF7, written by `MeetingMetaSidecar` as `dict["workflow_extra_sections"] = sections.map`, read by `workflow.py` as `raw_sections = meta.get("workflow_extra_sections")`) is in no fixture at all. A rename of any of these on either side passes both suites and degrades silently: the glossary falls back to global terms, the Notion page loses its title and properties, extra sections vanish from summaries.

**2. The prefetch golden never runs `_emit` (G018).** `gen_prefetch` takes event and field names from `_emit_call_sites()`, an `ast.walk` over `prefetch_model.py`, fills values from `PREFETCH_FIELD_VALUES`, builds `record = {"event": event, "repo_id": REPO_ID}` itself and writes `json.dumps(record, sort_keys=True)`, a copy of the line in `prefetch_model._emit`. `pipeline/tests/test_prefetch_model.py` never captures stdout. So a change to `_emit`'s envelope (its `event` or `repo_id` key, or how it serializes) reaches Swift's `ModelDownloadSupervisor.handleEvent` with the golden unchanged and both suites green. Correction at filing: the audit says the documentation claims the golden is produced by calling `_emit`. CONVENTIONS is honest ("and AST-walks `prefetch_model`'s `_emit` call sites"); the overclaim is the generator's module docstring, "Every case here is produced by CALLING the shipping Python code, never by hand".

**3. The restore plan has no shared fixture (F188, F193).** `RestorePlan` (`RestoreFlow.swift`, `struct RestorePlan: Decodable`) is the whole content of the in-app restore confirm (root `CLAUDE.md`, "Restore plan"). `RestoreFlowTests.fixturePlan()` decodes `planJSON`, a raw string literal whose comment says "Verbatim `mp.restore.plan_restore` output (paths shortened)", pasted on an unrecorded date. The Python side, `test_backup_restore.py` (`test_plan_counts_every_root_and_names_what_lands` and its neighbours), asserts `plan_restore`'s own result. Neither reads a shared file, the generator has no restore family, and CONVENTIONS' fixture table has no restore row. A field rename in `plan_restore` passes both suites and the preview renders an empty plan, which is what the literal's own comment warns of. F188's other half, the Swift-written `summary.json`, is [PIPE54](./PIPE54.md)'s.

**4. The publish golden never carries a real failed sink (G049).** In `publish_router.fanout` a failed sink records `{"error": str(e), "error_type": type(e).__name__, "failure": failure}` with `failure = emit_failure(e, operation="publish", provider=p.name)`, and `_write_publish_sidecar` copies `error` and `failure` into each sink entry. The generator's `PUBLISH_CASES` give failed sinks only `{"error": "401 Unauthorized"}` and `{"error": "vault path not writable"}`, so every sink in `publish-result-golden.json` has `"failure": null`. `CI4ContractFixtureTests.test_publish_result_golden` asserts `sink.ok` and `sink.pageURL` per sink and neither `error` nor `failure`, although `PublishResult.SinkOutcome` decodes both and `MeetingStore` uses `publishResult?.sinks.first { !$0.ok }?.failure` as the row's `failureMetadata`. So the failure presentation for a failed publish is unpinned across the trees; `failure-metadata-golden.json` pins `describe`'s classification, not its trip through the sidecar.

Related: [DOC20](./DOC20.md) (CONVENTIONS' "every surface pinned" sentence; this task makes the table true, DOC20 owns the wording), [ARCH21](./ARCH21.md) (the JSON Schema spike, which would subsume item 1 if adopted), [STOR5](./STOR5.md) (the in-app restore), [PIPE54](./PIPE54.md), [PIPE33](./PIPE33.md) (the Python file-contract owner), [WF10](./WF10.md) (added `workflow-no-sinks.meta.json`), CI4 in [q6-final.md](../q6-final.md) and CI2 in [q5-final.md](../q5-final.md).

## Scope

1. **Assert every consumed sidecar key.** In `test_workflow_overlay.py`, for each meta-contract fixture, assert the value every Python reader takes from it: `workflow_name` and `workflow_id` through `read_meta`, `meeting_title` and `source_display_name` through `publish_notion._load_meta_sidecar` (or the resolved `apply_meeting_title` title and the Notion property dict), and the parsed extra sections through the `workflow.py` reader. Add one Swift-written fixture carrying `workflow_extra_sections` (via `MetaContractFixtureTests`, as the other seven are written) with a Python assertion on the parsed sections. The list of consumed keys is built by reading each `read_meta` and `_load_meta_sidecar` caller, and written as a constant in the test so a new reader extends it visibly.
2. **Call `_emit`.** `gen_prefetch` keeps `_emit_call_sites()` for the event and field inventory, but produces each line by calling `prefetch_model._emit` with stdout captured (and the event log pointed at a temp file), so the golden carries the bytes the shipping code writes. Fix the module docstring to say which families are called and which inventory is AST-derived.
3. **A failed sink from the real path.** Add a publish case whose failed sink is produced by running `fanout` with a stub publisher that raises (a `ConnectionError` stand-in), so `error`, `error_type` and `failure` come from `emit_failure`. `CI4ContractFixtureTests.test_publish_result_golden` asserts `sink.error` and `sink.failure` against the fixture for every sink.
4. **Generate the restore plan.** Add a `restore-plan-golden.json` family to `gen_contract_fixtures.py` that builds a small archive in a temp dir and calls `mp.restore.plan_restore`, with paths normalised. `RestoreFlowTests` decodes it instead of `planJSON`, and `test_ci4_contracts.py` regenerates and diffs it like the other generated families.
5. **CONVENTIONS.** Add the restore-plan row to the cross-tree fixtures table, and name the failed-sink case in the publish row.

## Explicitly not

- Replacing the fixtures with JSON Schemas. That is ARCH21's spike; this task closes the gaps in the mechanism that exists.
- Generating the meta-contract fixtures from Python. Swift is their writer, so Swift generating them is right; the gap is only the Python assertions.
- The Swift-written `summary.json` shape (F188's other half): [PIPE54](./PIPE54.md).
- Rewording CONVENTIONS' "every surface" sentence: DOC20.
