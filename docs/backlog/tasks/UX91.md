# UX91: A Preferences change that fails to reach config.toml or the Keychain is logged only to os.Logger, so the control keeps the new value while the pipeline runs on the old one and nothing tells the user

Band origin: filed 2026-10-25 from the 2026-10-25 observability audit band ([observability audit](../../audits/2026-10-25-observability-audit.md) row O6, UI-6 and SW-5). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Re-verified against `main` at `01e904a` on 2026-10-25 by code reading. Never observed: a failure needs a write or `replaceItemAt` error on `~/.config/meeting-pipe/` (disk full, a permission-damaged or read-only directory) or a failing `security` call, and the only record would be in os_log, which is not persisted in the logs folder.

**The config save failure goes nowhere a person can see.** `ConfigStore.scheduleSave` debounces 0.5 s, calls `writeBack()`, then on `writeQueue`:

```swift
do {
    try self.persistToDisk()
    DispatchQueue.main.async { self.didPersist.send() }
} catch {
    Log.main.error("ConfigStore persist failed: \(String(describing: error))")
}
```

`persistToDisk` itself is careful (it propagates the `replaceItemAt` error, and its comment says "a silent failure means every later edit also vanishes with no signal to the user"), but the caller then drops the error into an os.Logger whose interpolated reason is stored as `<private>`. The only published state on `ConfigStore` is `parseError` (ARCH9's unparsed-file refusal). `didPersist` fires on success only, so nothing downstream learns of the failure; it simply never refreshes.

**The Keychain path has the same shape.** `SecretsStore.scheduleSave` catches `persist()`'s error with `Log.main.error("SecretsStore persist failed: ...")`. `persist()` writes the three accounts in order, so a failure on the second leaves the first written and the rest not. The App's `secrets.didPersist` sink that mirrors keys into the daemon's environment (which `PipelineLauncher.freshEnvironment` copies into every child) does not run, and the Python child re-reads the Keychain through `load_secrets()`, so the next run sees the old or absent key either way while the field shows the new one. The resulting summary fails as "Anthropic key missing" and points the user back at the same field.

**What diverges.** The skeptic narrowed the finder's regulated-mode example, and the narrowing holds in code: `PipelineLauncher.cloudSecretPolicy` builds a fresh `ConfigStore(configURL:)` from disk for every spawn, so token stripping and the pipeline agree with each other (both read the old file). The split is between the Preferences control, the in-memory consumers of `ConfigStore` (the toggle and the live capture path), and the file. The outcome is the one that matters: the owner switches Regulated mode on, the save fails, and the next summary still goes to the cloud engine while the switch reads on.

**A precedent exists in the same app.** `GlossaryStore` carries `@Published private(set) var saveError: String?`, sets it in `flush()`, and `VocabularyEditor` renders it. Neither `ConfigStore` nor `SecretsStore` has the equivalent.

## Scope

1. **Publish the failure.** `ConfigStore` gains `@Published private(set) var saveError: SaveFailure?` (a small value: which store, a one-line reason, the time), set on main from the `writeQueue` catch and from `saveNow`, cleared by the next successful `persistToDisk`. `SecretsStore` gains the same, naming the account that failed (`ANTHROPIC_API_KEY`, `NOTION_TOKEN`, `OPENAI_API_KEY`) and never the value. Keep the in-memory values (reverting a field under the user's cursor is worse); the next edit retries the save as today.
2. **Show it in Preferences.** A one-row banner above `paneContent` in `PreferencesView.detailContent`, shown on every pane while either `saveError` is set: "Your last change was not saved: <reason>", with **Try again** (calls `saveNow()`) and, for the config store, **Reveal in Finder**. It sits above the controls rather than replacing them, unlike `ConfigParseErrorPane`, because the file is still readable and the user may want to undo the change.
3. **Show it in the menu.** A `StatusBarModel.Row` case for an unsaved setting ("⚠ A setting was not saved - open Preferences"), present while either error is set, deep-linking to Preferences. One row for both stores.
4. **Record it.** One `daemon/config_save_failed` event per failure with `store` (`config` or `keychain`), the error's domain and code, and for the Keychain the account name and the `security` exit status. Never the stderr text of a `security` call and never a value. A matching `Log.writeLine("daemon", ...)` line so it reaches `daemon.log`. If OBS1's `Log.failure` helper has landed, use it instead of the pair.
5. **Docs in the same commit.** [GUIDE.md](../../GUIDE.md) section 10 gets a short recipe beside "Preferences says the settings file has a syntax error": what the banner means, that the change is still on screen but not in effect, and that **Try again** or freeing disk space fixes it. The "Start here" paragraph's list of menu rows needs no change (it does not enumerate them).

## Explicitly not / out of scope

- Reverting the in-memory value on failure, or blocking the control until the write lands. Rejected: the debounce means the user may have typed three more characters by the time the write fails, and the banner already says the change is not in effect.
- Making the daemon's in-memory consumers read from disk. `cloudSecretPolicy` already does for egress; the rest are UI state.
- `security` argv exposure, the ignored `remove` status and the migration that deletes `secrets.env` after a failed set: SEC23.
- The parse-error case: ARCH9 shipped it, and UX94 makes it visible outside Preferences.
- A general `Log.failure` migration of the other 51 os.Logger-only sites: OBS1. `config_saved` with key names on success: OBS5.

## Acceptance

- `ConfigStoreTests`: with the config directory made read-only (or `configURL` pointing under a file, so `createDirectory` throws), an edit followed by the debounce sets `saveError`; a later successful save clears it; `didPersist` does not fire on the failure. Same for `saveNow()`.
- `SecretsStoreTests` with a throwing fake `SecretsBackend`: `saveError` names the failing account; the value never appears in `saveError` or in the emitted event attributes.
- `StatusBarModelTests`: the unsaved-setting row is present when the input flag is set and absent otherwise.
- The banner is pinned by a view-model or source-reading test in the existing style (present above `paneContent` when either error is set).
- `config_save_failed` is emitted under the existing `daemon` category, so `python3 scripts/truth_fences.py events` stays green.
- `cd daemon && swift build` and `swift test` green, N new tests in the commit body; `bash scripts/ci-local.sh fences` green.
- Owner check (confirms, not a gate): `chmod a-w ~/.config/meeting-pipe`, toggle any Preferences switch, see the banner and the menu row within a second; restore the permission, press **Try again**, both clear.
