# UX54: Two MeetingPipes can run at once, and nothing stops the second

Band origin: filed 2026-07-31, owner-reported during UX42's walkthrough: "at some point after I launch meeting pipe, after first logout, I got two apps again in menubar, which is not okay", and separately "I see two after rebuild run I think. not sure exactly when". Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The owner saw two menu-bar icons, each showing its own Idle indicator, meaning two full daemons were live at the same time. By the time it was inspected the duplicate had gone (`pgrep` found one process, pid 93301, launchd-owned), so the surviving evidence is the screenshot and the owner's account rather than a live capture. The "again" in their report matters: this is not the first time.

**There is no single-instance guard.** A grep of `App.swift` for the usual shapes (`NSWorkspace.runningApplications` filtered by bundle identifier, an already-running check, a self-terminate on finding a peer) returns nothing. Two copies launched by any means will both run, both install a status item, both detect meetings, and both record.

Why it is reachable is the interesting part, and UX42's sequence is full of opportunities. With launch at login off, `rebuild.sh` relaunches the app directly rather than through launchd; `install.sh` leaves the agent disabled and tells the owner they may need to open the app themselves; and turning launch at login back on enables an agent whose job is to start an app that is, at that moment, already running because the owner started it by hand. Any of those can produce a manually-started process and a launchd-started process side by side. The exact trigger is unconfirmed and the pickup should establish it rather than assume, but the fix does not depend on which one it was.

The cost is not cosmetic. Two daemons means two detectors polling AX, two recorders that can both answer the same meeting, two pipelines that can be spawned for the same stem, and a `pipeline_cancelled` or a job-queue guarantee that is only single-process. PIPE11's whole point was that same-stem runs must serialize, and a second process is outside the lane that enforces it.

## Scope

Refuse to be the second instance. At launch, before installing the status item or starting any subsystem, check for another running copy of this bundle and, if one is found, bring the incumbent forward and terminate quietly rather than starting a second daemon.

`App.swift` is the seam, and the check belongs before `setActivationPolicy(.accessory)` and before the coordinator exists, so a rejected instance never touches the event log, the recorder, or launchd. Keep the decision pure and testable (given a list of running peers and this process's identity, start or stand down), matching the repo's `decide()` idiom, since the AppKit half is untestable.

Two cases to keep distinct: a peer started by launchd and a peer started by hand are both peers, and whichever loses should be the newcomer, so the running one keeps its recording. A daemon mid-recording must never be the one that dies.

## Explicitly not / out of scope

**Not the launch-at-login mechanism.** UX42 settled that the agent is the single owner of login-start and relaunch-after-quit, and this task does not add a second mechanism or change that one. It guards against duplicates however they arise.

**Not `rebuild.sh` or `install.sh`.** They may well be the trigger, and a guard in the app is the durable fix regardless, since the app can be launched by Finder, Spotlight, `open`, launchd, or a script. Naming the trigger is diagnosis, not scope.

**Not multi-user or multi-Mac.** One instance per user session is the bar; G1's two-Mac hub is unaffected.

## Acceptance

A pure test pins the decision: given a peer with the same bundle identifier and a different pid, this instance stands down; given no peer, it starts; given only itself in the list, it starts.

Manually verifiable and worth pinning in the walkthrough rather than a test, since it needs two real launches: starting a second copy while one runs leaves exactly one status item and one process.

An instance that stands down writes nothing to the event log beyond, at most, one line saying it did so, and never emits detector, recorder or pipeline events.

`cd daemon && swift build` and `swift test` green. `python3 scripts/truth_fences.py both` green (a new event action needs its row). No em-dashes in changed lines.


## Walkthrough findings, 2026-08-04: the guard does not fire, reproduced in-session

**The task does not close and the fix is not where the design effort went.** The owner hit two menu-bar icons again after `./scripts/rebuild.sh`, screenshot confirming two live Idle indicators.

**Reproduced on demand:** with two instances already up, a third was launched directly from `~/Applications/MeetingPipe.app/Contents/MacOS/MeetingPipe` and it also stayed alive (count went 2 to 3). This is not a race that needs luck to catch.

**Four things ruled out by measurement, so do not spend time on them again:**

1. The guard **is** in the shipped binary: `strings` finds both `second_instance_stood_down` and its log line.
2. It **is** wired at `App.swift:19`, inside `isDaemon` and above everything else.
3. `NSRunningApplication.runningApplications(withBundleIdentifier:)` **does** work before `NSApplication` exists, and **does** list every instance including a directly-launched one. Probed standalone against the live processes: 3 of 3, correct PIDs.
4. `decide` returns `.standDown` when run by hand over that exact observed data, including the case where the newcomer's own `launchDate` is nil and the comparison falls back to the pid.

**And yet `second_instance_stood_down` has never been emitted, in either events file, ever.** So the ordering rule this task spent its design on is not the problem, and neither is the wiring.

**Leading hypothesis, to prove or refute first:** the guard's own peer query returns an empty list at the instant it runs, in the first milliseconds of `main()` before this process's Launch Services connection is established, in which case `decide` correctly returns `.start` over an empty list and the guard is working perfectly on wrong input.

**How to settle it cheaply:** log the peer count the guard actually sees, then compare a query at `main()` entry against one a run-loop turn later. That is a diagnostic, not the fix.

**The one thing the fix must not do:** move the guard later to make the query succeed. A rejected instance must not install a status item, set an activation policy, or start a subsystem first, which is the whole reason the call sits where it does. If the query genuinely cannot work that early, the answer is a different peer-detection mechanism at that point in startup, not a later call.

**Adjacent, observed the same day and not part of this task:** `~/Applications/MeetingPipe.app` exists and Launch Services knows it, but Spotlight reports "unknown indexing state" for the home volume, so the app cannot be found by search. That is a machine-level index problem rather than an app defect, though `install.sh` running `mdimport` on the bundle would help.
