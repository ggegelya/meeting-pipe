# UX97: 'Always for <app>' consent is persisted with no in-app revoke, while Preferences says every meeting will prompt

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Sources: F010 in the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md) (confirmed, with two corrections the verifier made), and D022 in the [2026-11-13 recording reliability audit](../../audits/2026-11-13-recording-reliability-audit.md) (low, speculative, an independent confirmation). Re-verified in code at HEAD `3a2da4fc` on 2026-11-14; it holds as stated.

**Two lists, one shown.** The prompt's "Always for <app>" item reaches `Coordinator.notifier(_:didChooseAlways:)` (through `meetingPrompt(_:didChooseAlways:)` for the panel), which calls `consent.setAutoConsented(bundleID: source.bundleID, value: true)`, emits `user_consented_always`, clears suppression and starts the recording. `ConsentStore` persists the set to `~/Library/Application Support/MeetingPipe/auto_consent.json`. That is the only `setAutoConsented` call in the daemon, and it always passes `true`; nothing passes `false`. The start check in `MeetingSessionController` reads either list: `coordinator.liveAutoConsentApps.contains(source.bundleID) || coordinator.consent.isAutoConsented(bundleID: source.bundleID)`, then emits `auto_consent` and calls `beginRecording` with no prompt. `liveAutoConsentApps` is `configStore?.autoConsentApps`, the `recording.auto_consent_apps` key, and that is the only list Preferences renders: `PreferencesView+Recording`'s "Auto-record allowlist" group shows `store.autoConsentApps` with a remove tag per entry and, when it is empty, "No apps yet - every meeting will prompt." So after one Always pick, Preferences states the opposite of what the app does.

**The manual workaround is weaker than it looks** (the verifier's correction). `ConsentStore.init` reads the file once into `private var bundles`, and `save()` rewrites the file from that in-memory set. Deleting `auto_consent.json` while the app runs changes nothing until a restart, and a later Always pick in the same run writes the deleted entries back.

**Why it matters beyond the copy.** An Always app turns every sighting into a recording, including a false one (D022's framing): a mic-in-use prompt for a browser, picked Always once, records every later mic use in that browser. The person cannot see that this is armed, and cannot undo it from the app.

**Field.** Not in play on the work laptop: the 2026-11-13 field pack has 0 `auto_consent` rows over 114,553 events from 2026-09-29 to 2026-11-13 ([recording reliability audit](../../audits/2026-11-13-recording-reliability-audit.md), "What I re-derived"). That audit's step 0 asks the owner not to press Always for Teams until the start race is fixed, which [END20](./END20.md) owns.

**Related.** [SEC24](./SEC24.md) (P3) notes Always silences the prompt for good and scopes only a disclosure. [UX88](./UX88.md) makes the allowlist accept app names rather than raw bundle ids; this task should land on the same list UX88 edits. [STOR9](./STOR9.md) covers `auto_consent.json` being unreadable and saved over as empty. [DET26](./DET26.md) (P3, gated) binds Always to microphone sessions and says it must not land before this task.

## Scope

One list, visible and editable. Either of these, the pickup says which and why:

- **Fold (preferred if cheap).** Make the prompt's Always pick append the bundle to `ConfigStore.autoConsentApps` (so it shows in the allowlist with its remove tag), migrate the existing `auto_consent.json` entries into `recording.auto_consent_apps` once at launch, then stop reading `ConsentStore` (or keep it read-only for that one migration). The start check then reads one list.
- **Show both.** Render the `ConsentStore` set in the same "Auto-record allowlist" group, marked as picked from the prompt, with a remove control that calls `setAutoConsented(bundleID:value: false)`; fix the empty-state copy to depend on both lists.

Either way, the empty-state text "No apps yet - every meeting will prompt." is shown only when no list would auto-record. Removing an entry takes effect for the next sighting without a restart.

## Explicitly not

- Guarding `didChooseAlways` on the `.prompting` state like its sibling handlers (D022's second point): [END20](./END20.md) item 2 owns it.
- The consent disclosure to other participants: [SEC24](./SEC24.md).
- App-name entry instead of bundle ids: [UX88](./UX88.md).
- An unreadable `auto_consent.json`: [STOR9](./STOR9.md). If the fold option is taken, STOR9's row for this file closes with it, and the pickup says so there.
- Binding Always to a microphone session: [DET26](./DET26.md).

## Acceptance

- Tests (a Coordinator or ConsentStore-level test plus a pure test over whatever list model the allowlist group renders):
  - an Always pick for a bundle makes that bundle appear in the list model Preferences renders, and the empty-state predicate is false;
  - removing it through that model makes `isAutoConsented` (or the single list's contains) false, so the next sighting of that bundle prompts rather than emitting `auto_consent`;
  - with the fold option: a pre-existing `auto_consent.json` with two bundles is migrated into `auto_consent_apps` once, and a second launch does not duplicate them; with the show-both option: deleting via the control persists, and a later Always pick for another bundle does not write the removed one back.
- `cd daemon && swift build` and `swift test` green, N new tests named in the commit body; `bash scripts/ci-local.sh` green.
- [docs/GUIDE.md](../../GUIDE.md) and the README describe where an Always pick shows up and how to undo it, in the same commit.
