# UX100: Quick Find, notification and deeplink targets are dropped when the Library window is first created

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source: F009 (high, confirmed by both verifiers) in the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md), with P015 (low, inferred) from the [2026-11-13 responsiveness audit](../../audits/2026-11-13-responsiveness-audit.md) folded in. Re-verified in code at HEAD `3a2da4fc` on 2026-11-13.

**The window is built on first show.** `LibraryWindow.show()` creates `LibraryRootView(model: model)` and its `NSWindow` only when `window` is nil; `Coordinator.init` builds just the `LibraryWindow` wrapper, and no launch path calls `show()`. Every caller sets its request on `LibraryWindowModel` first and then calls `show()`:

- `Coordinator.openMeeting(stem:)` does `libraryModel.pendingSelection = stem` then `libraryWindow.show()`. Its callers are Quick Find's `onSelect` (Enter on a result, in `Coordinator`) and the failure-notification click in `Coordinator+Delegates` (`if let stem { openMeeting(stem: stem) }`).
- `Coordinator.openLibraryViaAutomation(scope:)` sets `libraryModel.pendingScope = mapped` then `show()`. It serves `meetingpipe://library?scope=`, `meetingpipe://ask` and `meetingpipe://digest`, and Quick Find's Cmd+Return, whose `onAsk` routes through `handleAutomation(.ask(question:), source: "quick_find")`, which sets `pendingAskQuestion` after the scope request.

**Only the transcript jump survives a cold open.** `LibraryRootView.onAppear` runs `meetingStore.start()`, `recomputeCounts()`, `reloadFacts()` and `resolveTranscriptJump()`, with the comment "the deeplink that opened this window set its request before the view existed, so `onChange` never fired for it." `pendingSelection` and `pendingScope` are read only in `.onChange(of: model.pendingSelection)` and `.onChange(of: model.pendingScope)`, which do not fire for the initial value, and each is cleared only inside its own handler (`model.pendingSelection = nil`, `model.pendingScope = nil`). No test references either property.

**What the owner sees.** After a launch, the first Quick Find pick or failure-notification click opens the Library on All meetings with nothing selected. The first `meetingpipe://library?scope=facts` (or `people`, `time`, `digests`) link opens the default rail. A Cmd+Return Ask from Quick Find lands on All meetings, and because `pendingAskQuestion` was set and `AskView.onAppear` calls `consumePendingQuestion()`, the stored question runs by itself whenever the Ask rail is next opened, possibly much later. Because the stale value is never cleared, picking the same meeting again (or sending the same scope again) is not a change, so `onChange` stays silent on the retry too; a different stem does work.

**Correction at filing:** the `meetingpipe://open?stem=` citation link is not affected. `openMeetingViaAutomation` uses `pendingTranscriptJump`, which AUTO2 already resolves in `onAppear` and on the first scan. The dropped deeplinks are the scope ones (`library`, `ask`, `digest`), so the acceptance below tests a `library?scope=` link rather than an `open` link.

**Field evidence.** The [field evidence pack](../../audits/2026-11-13-field-evidence.md) cross-check rates F009 "cannot tell": 8 `automation`/`command` `open_library` rows via `url_scheme` between 2026-10-22T21:26:32Z and 21:30:28Z, three within 40 ms, and no row records what the window showed. Nothing brackets a Library open, so the defect is invisible in the log.

**Same seam, P015.** The first Library open after a launch also pays one main-thread SwiftUI build of toolbar, sidebar, list and detail column with no feedback beyond the menu closing, and the list then waits on the first `MeetingStore.refresh()` scan. The responsiveness audit's ranked fix 10 proposes building the Library window hidden a few seconds after launch and running `MeetingStore.refresh()` once. Its cost was not measured (no event brackets a window open), so it is the optional half of this task.

## Scope

1. **Consume the pending targets on first appearance.** In `LibraryRootView`, give `pendingSelection` and `pendingScope` the treatment `resolveTranscriptJump` has: extract the two `onChange` bodies into `applyPendingSelection()` and `applyPendingScope()` and call both from `onAppear` as well as from their `onChange` (or switch the two modifiers to `onChange(of:initial: true)`). Order matters: apply the scope first, then the selection, since a selection forces `.allMeetings`.
2. **Clear after every attempt.** Each consumer sets its pending value back to nil whether or not it acted, so a repeat of the same stem or scope is a fresh edge.
3. **Do not leave an orphaned Ask question.** When the `ask` scope switch was not applied (the window existed but the switch was swallowed, or the request was superseded by a later scope), clear `pendingAskQuestion` instead of letting the next manual visit to the Ask rail run it. With item 1 in place the normal path consumes it on the cold open, so this is the backstop; the seam is `Coordinator.handleAutomation`'s `.ask` case and `AskView.consumePendingQuestion`.
4. **Optional, P015: prewarm.** After launch settles, build the Library window without ordering it front so the first open is an `orderFront`, and run `MeetingStore.refresh()` once so the list is populated. Constraints from the audit: only the Library may call `MeetingStore.start()` (the watcher must stay attached only while the window is visible), `WindowActivationManager` stays the only owner of fronting (UX39), and a hidden window holds memory that PERF27 just worked to release. If the pickup session cannot measure a first-open cost worth that trade, leave item 4 out and say so in the commit body.

## Explicitly not

- Changing how `pendingTranscriptJump` resolves (AUTO2 already handles the cold open).
- Authenticating or confirming `meetingpipe://` commands: [AUTO7](./AUTO7.md). The automation reference itself: [AUTO4](./AUTO4.md). The App Intents half of [AUTO1](./AUTO1.md) stays deferred.
- Quick Find's own first-open state over an unscanned library (P017 in the responsiveness audit), which is a separate seam in `QuickFindWindow`.
- Keeping Preferences and Guide windows warm (P014, P018): same ranked fix in the responsiveness audit, different windows, not filed here.

## Acceptance

- Tests (a `LibraryRootView`-level host test or a pure extraction the view calls; the pickup picks the seam that can be driven headless):
  - a cold open with `pendingSelection` set before `show()` selects that stem and switches to All meetings, and leaves `pendingSelection` nil;
  - a failure-notification click (`openMeeting(stem:)` from the delegate path) on a never-shown window selects the stem;
  - a `meetingpipe://library?scope=` link on a never-shown window lands on that rail and leaves `pendingScope` nil;
  - a Quick Find Cmd+Return on a never-shown window lands on the Ask rail and runs the question once; opening the Ask rail again later does not run it a second time;
  - the same stem sent twice in a row selects it both times.
- If item 4 ships: a test that the prewarm builds the window without fronting it and without attaching the watcher (`MeetingStore.start()` not called until the window appears).
- `swift test` green with the new tests; `bash scripts/ci-local.sh` green.
- `docs/GUIDE.md` recipes that describe opening a meeting from Quick Find or a notification still read true (no wording change expected).
