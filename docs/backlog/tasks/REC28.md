# REC28: a system capture the channel has given up on can still write into it, so a stream whose stopCapture() hung delivers into the next recording's system WAV, and the start Task applies its outcome off the main thread

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Review findings RECORDING-2 (medium after verification; the finder said high) and RECORDING-9 (low, confirmed), re-read in code at `01e904a` on 2026-10-25. [REC17](./REC17.md) fenced the start side: an attempt the recorder abandoned stops its own late stream and delivers nothing. The stop side, and the start Task's own outcome, have no equivalent.

**`stop()` does not cut delivery for a stream it adopted.** `SystemAudioCapture.stop()` reads `let live: SCStream? = withStartLock { if !attempt.isCompleted { attempt.stopped(); return nil }; defer { stream = nil }; return stream }` and then `try await live.stopCapture()`. For an adopted stream that clears `stream`, so `holdsAdoptedStream` turns false and `didStopWithError` goes quiet, but `stream(_:didOutputSampleBuffer:of:)` gates only on `guard !isStartAbandoned else { return }`, which stays false for an adopted attempt. Until `stopCapture()` actually takes effect, every buffer still reaches `onBuffer`.

**Two callers stop waiting for that.** `SystemAudioChannel.haltCapture()` (stop step 3) gives up after 5 s (`if await runWithTimeout(seconds: 5, { await capture?.stop() }) == false`, emitting `system_capture_stop_timed_out` with no attributes) and sets `systemCapture = nil`. `handleSystemAudioLost(reason:stalledForSeconds:autoRetry:)` runs `systemCapture = nil` then `Task { await dying.stop() }`, unbounded and unevented, and REC8's automatic retry follows 7 s later into the same open file (REC10's `.resumeOpenFile`).

**The channel takes a buffer from any capture.** `startSystemCapture(systemURL:isRetry:)` builds `SystemAudioCapture { [weak self] pcm in guard let self = self, self.systemFile != nil else { return } ... }`, and the channel is `MeetingRecorder`'s `let systemChannel`, on the recorder the `Coordinator` creates once, so it outlives every recording. After `closeFile()` a zombie stream's buffers are dropped, but the next recording's `openSystemFile(at:)` sets `systemFile` and `systemWriter` again and they pass. Then:

- The far side holds two streams interleaved, roughly doubled, and `system_audio_sec` can approach twice the wallclock, which drives `mergeLengths`' target and, at twice the 384 kB/s rate, reaches [REC19](./REC19.md)'s 4 GiB ceiling at about 1 h 33 min instead of 3 h 6 min.
- `systemFires` advances past `systemFiresAtArm` from the zombie, so `checkSystemLiveness` and `systemChannelHealth` (REC17's per-attempt gates) see a live channel while the new stream is dead.
- `systemFirstFrameUptime` is stamped by the zombie as soon as the file opens, so REC9's head offset reads about 0 for a new stream that starts late, and its audio is merged at the head instead of where it was captured.
- Within a meeting, a stalled stream that resumes while its `dying.stop()` hangs writes into the still-open file before and alongside the retry's stream, displacing REC10's silence pad.

The ScreenCaptureKit session itself (the privacy indicator, the per-buffer conversion) keeps running until process exit; nothing in this app can stop a stream whose `stopCapture()` never returns.

**How likely.** ScreenCaptureKit's async calls do hang for long periods here: `stopCapture` for about 7 minutes on 2026-06-05 (the reason `runWithTimeout` exists, REC7) and `startCapture` for 64 minutes on 2026-09-17 (REC17). Whether a stream keeps delivering while its `stopCapture` hangs is not established: REC13's `system.wav` growing at about 394 KB/s on 2026-08-14 came from a stop path blocked on the engine, not from a hung `stopCapture`. The current log generation (2026-10-12 to 2026-10-24) holds no `system_capture_stop_timed_out` row. Hence P2, though the outcome is a corrupted next recording.

**The start Task applies its outcome from the cooperative pool (RECORDING-9).** `startSystemCapture` is a synchronous, nonisolated method on a plain class (`final class SystemAudioChannel`; the package sets no default isolation under tools 5.9 with `-strict-concurrency=targeted`), so `systemStartTask = Task { [weak self] in switch await boundedSystemCaptureStart(...) { ... } }` runs on the global executor. Its `.started` branch writes `self?.systemDegraded = false`; its `.failed` branch writes `self?.systemCapture = nil` and `systemDegraded = true` and, on a fresh file, `systemFile = nil`, `systemWriter = nil` and `try? FileManager.default.removeItem(at: systemURL)`. Only `.timedOut` hops to main, and only it checks identity (`handleSystemAudioStartTimedOut`'s `guard systemCapture === capture`). Main reads and writes the same fields in `checkSystemLiveness`, `systemChannelHealth`, `retrySystemAudio`, `haltCapture`, `drainWriter` and `closeFile`, while the class doc says "main for every entry point". The window is microseconds and a fresh start that failed delivered nothing, so the reachable cost is small: a retry on main that saw `hasOpenFile` and padded the old writer, then lost its stream when the late `.failed` cleared the file and writer (the buffer closure's `systemFile != nil` then fails, and with no buffers the watchdog never fires). It is filed with RECORDING-2 because the identity check is the same mechanism.

## Scope

Seam: `SystemAudioCapture.stop()` and its sample-buffer delegate; `SystemAudioChannel.startSystemCapture(systemURL:isRetry:)`, `haltCapture()` and `handleSystemAudioLost(reason:stalledForSeconds:autoRetry:)`.

1. **Cut delivery before awaiting the stop.** A delivery gate set under `startLock` at the top of `stop()`, before `await live.stopCapture()`, and checked by `didOutputSampleBuffer` beside `!isStartAbandoned`: a separate flag, or a field with its own mutator on `SystemCaptureStartAttempt` so the decision stays pure. Not `attempt.stopped()`: it is a no-op once the attempt completed, and it would change what `Abandonment` means.
2. **The channel accepts buffers only from its live attempt.** A per-attempt generation on the channel, set by `startSystemCapture` and invalidated by `haltCapture` and by `handleSystemAudioLost` (so a resumed stall cannot write before the retry's pad), captured by the buffer closure and checked before `systemFires`, `systemFirstFrameUptime` or the writer are touched. A generation rather than `systemCapture === capture`, because the closure is passed into the capture's `init` and cannot capture the capture.
3. **Apply the start outcome on main, to its own attempt.** The start Task's outcome handling runs on the main actor (the ScreenCaptureKit awaits inside `boundedSystemCaptureStart` still run off main), and `.started` and `.failed` act only when the capture is still the channel's (the generation, or `systemCapture === capture`). Lifting the switch into a main-confined method that takes the outcome is the natural seam for the tests below. Correct the class doc's threading paragraph, and the REC17 comment in `SystemAudioCapture.stop()`, which reads as if stop pre-empts delivery in general rather than only for a start still in flight.
4. **Bound and record the in-meeting stop.** `handleSystemAudioLost`'s `Task { await dying.stop() }` goes through `runWithTimeout` with the same 5 s as `haltCapture` (`stopCapture()` suspends, so the Task form is the right one per CI8), and both timeouts emit `system_capture_stop_timed_out` with a new `path` attribute (`stop` or `loss`), so a zombie is visible in `events.jsonl`.

## Explicitly not

- Calling `removeStreamOutput(_:type:)` before `stopCapture()` as the fix: it is a synchronous ScreenCaptureKit call that can block on the same wedged internals. If used at all, off main and bounded; item 1 does not depend on it.
- Stopping a stream whose `stopCapture()` never returns: not possible from here. Items 1 and 2 make it inert, and item 4 makes it visible.
- `SystemAudioCapture`'s unguarded statics (`cachedContent`, `permissionState`, `displayReconfigObserver`): [CONC6](./CONC6.md).
- The 4 GiB intermediate ceiling itself: REC19. The mic side's abandoned writer drain reporting into the next recording's failure tracker is the review's RECORDING-3 ([REC25](./REC25.md)), handled with the write-path findings.

## Acceptance

- Pure tests beside `SystemCaptureStartREC17Tests`: an adopted attempt delivers until the stop gate is set and nothing after; setting the gate changes neither `completed()`'s answer nor an existing `Abandonment`; an abandoned attempt still delivers nothing.
- A source fence that `SystemAudioCapture.stop()` sets the gate before `await live.stopCapture()` and that `stream(_:didOutputSampleBuffer:of:)` consults it.
- A pure test of the channel's acceptance predicate (a stale generation, or no open file, touches nothing), and a fence that the buffer closure calls it before `systemFires &+= 1`.
- Through the lifted outcome method: a late `.failed` for a capture that a retry or `stop()` already replaced leaves `systemFile`, `systemWriter`, `systemDegraded` and the file on disk as they were; a late `.started` for one leaves `systemDegraded` alone; a current one behaves as today. Plus a fence that the outcome handling is main-isolated.
- The loss path's stop timeout emits `system_capture_stop_timed_out` with `path: "loss"` (a fake capture whose stop never returns, or a fence where no seam exists, saying so), and the stop path's carries `path: "stop"`.
- `cd daemon && swift build` warning-clean under `-strict-concurrency=targeted`, `swift test` green with N new tests stated in the commit body, `bash scripts/ci-local.sh` green, `python3 scripts/truth_fences.py both` green (`recorder` is an existing category).
- Evidence (confirms, does not gate): after `./scripts/rebuild.sh`, any later `system_capture_stop_timed_out` row is followed by a next recording whose `intermediate_durations.system_audio_sec` is no longer than its wallclock.
