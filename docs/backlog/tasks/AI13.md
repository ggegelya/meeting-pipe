# AI13: The embedding index is rewritten whole and in place every eight meetings, so a kill inside a save forces a full rebuild and two writers can tear it

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Review finding PYTHON-5 (finder medium, verifier confirmed medium). Re-checked against `main` on 2026-10-25 in [embed_index.py](../../../pipeline/src/mp/embed_index.py).

**The write.** `EmbeddingIndex.save` does `np.save(directory / "vectors.npy", self.vectors)`, then opens `chunks.jsonl` with `.open("w")` and writes one `json.dumps` line per chunk, then `(directory / "manifest.json").write_text(...)`, all over the live files in `DEFAULT_INDEX_DIR` (`~/Library/Caches/meeting-pipe/ai2-index`). `_persist` wraps it and catches only `OSError`.

**How often.** `refresh_index` builds `checkpoint = _assemble(embedder, chunks, blocks, stems=done, fingerprint="")` and `_persist`s it after every `CHECKPOINT_EVERY_STEMS = 8` stale meetings, then persists the final index once more. Each checkpoint stacks, sorts and copies every row so far and writes all of it, so a fresh build of N meetings writes about N squared over 16 meetings' worth of rows, and a refresh that re-embeds one changed meeting rewrites the whole index twice. The module docstring's item 2 ("The checkpoint is the index") describes this design.

**What a kill mid-save leaves.** `_load_reusable` returns None, which means rebuild from zero, when `EmbeddingIndex.load` raises `ValueError` (a torn `.npy` or a truncated JSONL line) or when `index.vectors.shape[0] != len(index.chunks)` ("has %s vectors for %d chunks; rebuilding"). A kill after `np.save` and before the chunks write produces exactly that pair: new vectors, old chunks, old manifest. A kill after the chunks and before the manifest is benign, since the extra stems are re-embedded.

**Who kills.** A Library Cancel SIGTERMs `mp ask`, and `PipelineLauncher.ask` runs it with `timeout: 10 * 60`. Python installs no SIGTERM handler ([PIPE22](./PIPE22.md)), and PIPE22's planned handler raises `SystemExit` at the next bytecode, which lands inside the per-chunk JSONL loop as easily as anywhere else: the process unwinds cleanly and leaves the same torn pair.

**Two writers.** `mp ask` and `mp mcp-serve` both default `--index-dir` to `embed_index.DEFAULT_INDEX_DIR` and both refresh into it, from separate processes, with no lock; inside one MCP session two first `search_meetings` calls can also race into two builds (the [AUTO6](./AUTO6.md) amendment filed from this review, finding PYTHON-6 ([AUTO6](./AUTO6.md))). Interleaved in-place writes can leave a pair that never belonged together.

**What it does to AI11's promise.** AI11 (archived in [q6-final.md](../q6-final.md)) shipped "a kill resumes from it instead of restarting, so the daemon's 10-minute cap can no longer create a permanent rebuild loop". That holds for a kill between saves and not for one inside a save, and the share of build time spent inside `save` grows with the library. Magnitude: the owner's 227-meeting build took 39 s on 2026-07-31 (AI11's walkthrough), far under the cap, so the present cost is one wasted rebuild after an unlucky Cancel rather than a loop; [PERF9](./PERF9.md) counted about 434 meetings on 2026-10-23. At the finder's projection of about 1,250 meetings at about 57 chunks each (384-dim float32 vectors at 1.5 KB a chunk, plus up to 1,200 chars of chunk text per JSONL line), one save is roughly 200 to 250 MB and a fresh build writes tens of GB, which is where a rebuild approaches the 10-minute cap and the loop returns.

## Scope

1. **Never overwrite a live file.** `save` writes `vectors-<gen>.npy` and `chunks-<gen>.jsonl` under a fresh generation id, then replaces `manifest.json` through `storage.atomic_write_text` with the generation it names, and only then deletes generations the manifest no longer names. `load` and `_load_reusable` read the files the manifest names. A kill at any point leaves the previous manifest naming a complete pair. Bump `INDEX_SCHEMA_VERSION`, so an existing index rebuilds once through the existing "predates" log line instead of the loader carrying a second layout.
2. **One writer at a time.** The manifest replace and the cleanup of old generations run under an exclusive `fcntl.flock` on a lock file in `index_dir`, so two processes cannot delete each other's generation between its write and its replace. Embedding stays outside the lock.
3. **Checkpoint on time, not count.** Replace the every-8-meetings checkpoint with one taken when at least a minimum interval (a named constant, about 30 s) has passed since the last save, so the save share of a build stays bounded, a short refresh saves once at the end, and a kill still loses at most that interval's embedding. `ask_index_refresh_done` gains `checkpoints` and `save_s` attributes so the cadence is visible in the event log. The module docstring's item 2 is rewritten to match.

## Explicitly not

- A temporary directory swapped in with `os.replace`: the rename fails with `ENOTEMPTY` onto a non-empty directory on macOS.
- Per-batch shard files with compaction, or SQLite. Both remove the rewrite cost more thoroughly and add a load path and a compaction policy; the time-based cadence bounds the cost with far less code. AI11 also recorded that a vector database is the wrong size for a personal library.
- A SIGTERM handler ([PIPE22](./PIPE22.md)); this task makes the index safe whichever way the process dies.
- The MCP server's once-built cached index and its concurrent first builds (the [AUTO6](./AUTO6.md) amendment from this review).
- [PIPE30](./PIPE30.md)'s atomic-write fence: the manifest goes through `storage.atomic_write_text`, and the generation files are new names rather than replaces, so the fence needs no allowlist entry. [PIPE29](./PIPE29.md) leaves the index readers raising on a corrupt index by design, and that stays.
- A deleted meeting's chunks staying until the next refresh ([STOR7](./STOR7.md)).

  - a save interrupted after the vectors write (patch the chunks write to raise) leaves `_load_reusable` returning the previous complete index (fails on the current code, which returns None);
  - a save interrupted mid-JSONL (a truncating patch) leaves the same;

  - two writers saving into one `index_dir` concurrently (two processes, or two threads holding separate lock descriptors) end with a manifest that names a complete, loadable pair;
