# FEAT24: Undo naming and Un-name in one meeting run a whole-person roster forget, deleting that person's voice samples from every other meeting

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source: finding G003 in the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md) (high, confirmed by both verifiers, re-read at HEAD `4949c9c0` by the audit author). Re-verified in code at HEAD `3a2da4fc` on 2026-11-13 for this filing; the claim holds as reported, with one more entry path (below).

**Naming adds one sample; undo removes the person.** `MeetingLibraryService.nameSpeaker` runs `launcher.rosterEnroll(name: trimmed, label: label, wav: anchor, noRelabel: true)`, and `mp roster enroll` reads the label's vector from `<stem>.embeddings.json` and calls `RosterStore.enroll`, which appends one sample to an existing person (`samples.append(sample)`, then `samples[-_MAX_SAMPLES:]` and a centroid recompute). `MeetingLibraryService.undoSpeakerNaming` drops the overlay entry and then, whenever the label has a voiceprint, runs `launcher.rosterForget(name: name)`. `mp roster forget` calls `RosterStore.forget`, which is `kept = [p for p in people if p.get("name") != name]`: the whole person, every sample, from every meeting. No per-sample removal exists in `roster.py`. So undo is not the inverse of naming: a person with several samples from earlier meetings who is wrongly accepted for one voice here and then un-named loses all of them, is never auto-matched again, and drops out of the People list (`RosterProfile.people` reads `roster.json`'s `people`).

**Rename in one meeting does the same.** `MeetingLibraryService.renameSpeaker` enrolls the voice under the new name and then runs `self.launcher.rosterForget(name: oldName) { _ in }`: the old person is deleted whole, and the result is discarded, so a failure is silent and nothing is logged.

**It fires without a confirm.** The chip's **Un-name** (`VoiceResolutionBar`, `.unname`, a destructive `Button` calling `onUnname` directly) and the transcript row's **Undo naming** (`TranscriptTab`, `Button("Undo naming", role: .destructive) { onUndoName(label, currentName) }`) both call straight through. Only the deliberate Preferences **Remove** (`PreferencesView+Pipeline`) has an `NSAlert`. [docs/GUIDE.md](../../GUIDE.md) tells the user naming "is fully reversible" and that **Undo naming** "also stops later meetings using the name", and that accepting a **Name as** suggestion adds a sample to that person.

**A second entry path the audit did not name.** `MeetingCast` offers `.rename` and `.unname` for any row whose label is in the overlay's `labels` map (`if let name = overlay.labels[label]`). The rename-everywhere carry (`RosterRename.carry`, shipped with the people rail, see [q6-final.md](../q6-final.md)) calls `PeopleRail.renamed`, which for a meeting whose attendees carry the old name writes `next.labels[old] = new`, including meetings where the pipeline matched the name at finalize and the owner never enrolled a sample. In such a meeting the raw label is the baked name, and `<stem>.embeddings.json` is keyed by that final label, so `MeetingStore.voiceprintLabels` contains it. Undo naming on that row therefore passes the voiceprint guard and runs `rosterForget(name: new)`, deleting the whole person although this meeting contributed nothing. Traced by reading at filing; not exercised.

**Tests pin the forget, never the loss.** `MeetingLibraryServiceTests.test_undoSpeakerNaming_reverts_overlay_immediately_and_forgets` asserts `driver.forgetInputs == [name]` for a person with no prior samples; `pipeline/tests/test_roster.py` pins whole-person forget. Nothing covers undo on a pre-existing multi-sample person. The audit's scratch run of `RosterStore` showed a person at 9 samples, 10 after an accept, and gone after the undo.

**Field evidence.** The [2026-11-13 field evidence](../../audits/2026-11-13-field-evidence.md) rates G003 "cannot tell", with the row reading "no undo-naming event exists". Not yet observed, and the loss is silent when it happens: `undoSpeakerNaming` logs `roster_undo_requested` but no done or failed row, and `renameSpeaker` logs nothing about its forget.

**Why it was shaped this way.** FEAT3-UNDO and UX40 (both done, [q6-final.md](../q6-final.md)) routed Undo and Un-name to `mp roster forget` so a wrongly named voice stops being auto-named later. That intent is right; whole-person granularity is the defect. [STOR7](./STOR7.md) explicitly scopes per-meeting sample removal out as "a schema change" it does not own; this task introduces that provenance.

**Legacy samples.** Every sample already in the owner's `roster.json` was written without provenance. Their origin is still recoverable for the common case: `mp roster enroll` reads the vector from `<stem>.embeddings.json` and `RosterStore.enroll` stores `_l2_normalize([float(x) for x in embedding])`, which is deterministic, so re-normalising the same meeting's label vector reproduces the stored sample while that sidecar is unchanged. After a re-transcribe rewrites `<stem>.embeddings.json`, it no longer matches, and the safe outcome is to leave the roster alone.

## Scope

1. **Provenance in `roster.json`.** `RosterStore.enroll(name, embedding, *, stem=None, label=None)` records where each sample came from. Recommended shape: an additive `sources` list beside `samples`, index-aligned, each entry `{"stem": ..., "label": ...}` or `null` for a legacy sample, so `samples` keeps its shape and `RosterProfile.people`'s `sampleCount` and every older reader stay correct. Whatever shape is chosen, the dimension filter (`[s for s in ... if len(s) == EMBEDDING_DIM]`) and the `_MAX_SAMPLES` eviction must drop a sample and its provenance together, never misaligning them. `mp roster enroll` passes `stem` (from `--wav`) and `--label`. Keep the record compatible with [FEAT19](./FEAT19.md) leg 1 (passive samples keyed by stem) and [STOR7](./STOR7.md) (per-meeting removal on delete), so the roster gets one schema change, not three.
2. **`RosterStore.unenroll(name, stem, label, embedding=None) -> (removed, person_removed)`.** Removes every sample of `name` whose provenance is `(stem, label)`; for a sample with no provenance, removes it only when its vector matches the re-normalised `embedding` (cosine at or above a tolerance like 0.9999, constant documented beside it). Recomputes centroids from what is left. Removes the person only when no samples remain. A person with no matching sample is left byte-identical. Written through the same atomic writer as `enroll`.
3. **`mp roster unenroll --name --label --wav`** in `roster_cmd.py`, mirroring `enroll`'s arguments (it reads the label's vector from `<stem>.embeddings.json` for the legacy match; a missing sidecar means provenance-only matching, not an error). Emits `pipeline` `roster_unenrolled` with `name`, `label`, `stem`, `removed` and `person_removed` (`roster_enrolled` carries `name`, `label`, `stem` and `relabeled` today, so `name` stays in for parity). Exit 0 whether or not a sample was removed, since "this meeting contributed nothing" is a correct no-op, not a failure; exit 2 only on a malformed invocation. The counts live on this pipeline event only; the daemon does not parse them.
4. **Daemon seam.** `PipelineLauncher.rosterUnenroll(name:label:wav:completion:)` with a defaulted protocol extension so fakes compile. `MeetingLibraryService.undoSpeakerNaming` calls it instead of `rosterForget`. `MeetingLibraryService.renameSpeaker` unenrolls this meeting's sample from `oldName` after the new enroll succeeds, instead of forgetting `oldName`, and reports a failure through `notifyError` like undo does. Both log `coordinator` `roster_undo_done` / `roster_undo_failed` (the rename adds `roster_rename_unenroll_done` / `roster_rename_unenroll_failed`) with `stem` and `label`, plus `error` on failure; the sample counts are on the pipeline's `roster_unenrolled` row.
5. **Copy.** The whole-person forget stays reachable only from the Preferences People pane's **Remove**, which already confirms. No confirm is added to Un-name or Undo naming, because after this change each is the exact inverse of the naming it undoes. Update the `undoSpeakerNaming` and `renameSpeaker` doc comments and [docs/GUIDE.md](../../GUIDE.md)'s naming recipes ("fully reversible", "also stops later meetings using the name", the chip's **Un-name**) to say undo removes the voice sample this meeting added, and that the person stays recognised from their other meetings.

## Explicitly not

- No confirm dialog on Un-name or Undo naming as the fix: a confirm on a whole-person forget would still lose the other meetings' samples on a yes, and the audit's direction prefers the per-sample inverse.
- Not making `roster forget` cascade into `<stem>.embeddings.json`: that is [SEC22](./SEC22.md) item 3. Sequencing note: SEC22's cascade landing first would make this defect worse (an undo in one meeting would also strip the name from every meeting's embeddings), so this task should land first, or SEC22 must not ship while undo still routes through `forget`.
- Not removing samples when a meeting is deleted: [STOR7](./STOR7.md) owns that and builds on this provenance.
- Not passive enrolment, merge, or a name picker: [FEAT19](./FEAT19.md). Not the cross-meeting clustering queue: [DIAR10](./DIAR10.md), whose fan-out writes this task gates.
- No migration pass over `roster.json`: legacy samples keep `null` provenance and are matched by vector only at undo time.

## Acceptance

- pytest in `test_roster.py`: a person with samples from three meetings, unenrolled for one `(stem, label)`, keeps the other two samples and recomputed centroids; a person whose only sample is unenrolled is removed and `person_removed` is true; a legacy sample with no provenance is removed only when its vector matches the given embedding; an unenroll with no matching sample leaves `roster.json` byte-identical; eviction past `_MAX_SAMPLES` and the dimension filter keep `samples` and provenance aligned; a roster written before this change loads, matches and enrolls unchanged.
- pytest for `mp roster unenroll`: reads the label's vector from `<stem>.embeddings.json`, emits `roster_unenrolled` with both counts, and works with the sidecar missing (provenance-only).
- `MeetingLibraryServiceTests`: undo naming on a pre-existing multi-sample person calls `rosterUnenroll` with this meeting's stem and label and never `rosterForget`; rename in one meeting unenrolls `oldName` for this stem and label and never forgets it; an undo on a row whose overlay came from the rename-everywhere carry reverts the overlay and calls `rosterUnenroll` for this stem and label, never `rosterForget` (the roster staying untouched when this meeting contributed no sample is pinned by the pytest no-match case); the existing overlay-only test stays green; the existing forget-asserting test is rewritten to the new contract. `RosterProfileTests` stay green against a roster carrying provenance.
