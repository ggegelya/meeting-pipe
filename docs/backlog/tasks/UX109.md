# UX109: The menu's failed count and the Library disagree on an error.json that cannot be read, so a fresh meeting is "failed" in the menu and "processing" in the Library for up to two hours

Band origin: filed 2026-11-26 from the ARCH20 session (commit `a8f5a945`), which moved the menu count onto `MeetingStatus.decide` and left this corner as documented. Owner approved filing on 2026-11-25/26. Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

**One ladder, two readings of the same file.** ARCH20 made `MeetingStatus.decide` the single status ladder for the Library (`MeetingStore.buildMeeting`), the menu's failed row (`MeetingStore.unrecoveredFailureStems`), `LibraryMover.inFlightReason` and `AudioRetentionSweep.candidates`. Each reader hands it `Facts.error` as one of three `MeetingStatus.ErrorSidecar` cases, and they do not all see the same case for the same file (read at HEAD `0f141418` on 2026-11-26):

- `unrecoveredFailureStems` passes `.unopened` for an `error.json` with no summary (`!f.summary ? .unopened`), without opening it. Its docstring says so: "Deliberately a superset in one corner: an `error.json` with no summary is counted without being opened, where the Library, which opens it, ignores one that does not decode." Both callers go through it: the menu count (`MeetingLibraryService`, with `diskFailureReaders`) and the launch auto-retry (`Coordinator+AutoRetry.runLaunchAutoRetry`, `.filenameOnly`).
- `LibraryMover` sets `f.error = .unopened` from the filename alone.
- `buildMeeting` and `AudioRetentionSweep.candidates` open the file through `PipelineFailureSidecar.read` and pass `ErrorSidecar(recorded, modified:)`, which is `.undecodable` when the read returns nil.

`decide` treats them differently: `.unopened` with no summary is `keepsFailure = !f.hasSummary`, so `.failed` at once; `.undecodable` is `keepsFailure = false`, so the stem falls through to the age rule: `.processing` until `Meeting.staleProcessingThresholdSec` (2 h) after the stem's start, then `.failed` with no reason. `MeetingStatusTests.test_an_undecodable_error_is_no_failure_but_keeps_a_row` and `MeetingStoreTests.test_an_undecodable_error_sidecar_keeps_a_row_and_ages_ARCH20` pin the Library half.

**What "cannot be read" covers.** `PipelineFailureSidecar.read(at:)` returns nil when the data cannot be read (permissions, a dataless file), when it is not JSON (a truncated or hand-edited file), and when `stage`, `reason` or `ts` is missing or `stage` is not a known `Stage` raw value (a file written by a newer build, or edited). The daemon writes these files itself, so the realistic triggers are a truncated write, a hand edit, and a build rollback across a new `Stage` case.

**What the owner sees.** For a meeting under two hours old: the menu's failed row counts it, and the Library shows it in progress with no reason and no Retry. For a stem whose name does not parse, `buildMeeting` returns no row at all (`guard let startedAt = MeetingStore.parseStem(stem) else { return nil }`), while the menu still counts it failed, so the menu names a failure the Library cannot show. The launch auto-retry is a third answer: it counts the stem, then drops it, because its `compactMap` over `PipelineFailureSidecar.read` discards a sidecar that does not decode. The mover agrees with the menu: an undecodable sidecar makes the stem terminal for `inFlightReason`, while the Library calls the same stem in flight.

## The decision (owner)

One rule for an `error.json` that exists but cannot be read, applied by every reader.

- **Option A, the Library's rule wins: an unreadable record is no failure.** The menu count and `LibraryMover` open the sidecar when there is no summary too (through `FailureStateCache`, so an unchanged file is decoded once), and pass `.undecodable` when it does not decode. Cost: one decode per error stem without a summary on the menu's cold pass, and a recent meeting with a broken record reads as in progress, with no Retry, for up to two hours.
- **Option B, the menu's rule wins: a record that exists is a failure, whatever it says.** `decide` treats `.undecodable` like `.unopened`, and the Library row reads Failed with Retry and a reason line saying the failure record could not be read (wording through `docs/GUIDE.md`'s register). The launch auto-retry keeps the stem instead of dropping it, with no `ts`. Cost: a hand-edited or newer-build file shows as failed rather than in progress, which is the recoverable state.

Filer's lean, for the owner to overrule: B. The file is only ever written on a failure, a Failed row with Retry is the state the owner can act on, and A shows a spinner for up to two hours over a meeting whose pipeline has already stopped.

## Scope (after the decision)

1. Option A: `unrecoveredFailureStems` asks `readers.errorEvidence` for every error stem, mapping nil to `.undecodable`; `LibraryMover` opens the sidecar the same way. Update the "superset" sentence in the docstring.
2. Option B: in `MeetingStatus.decide`, `.undecodable` takes `.unopened`'s branch; `buildMeeting` supplies the reason line for a failed row with no decodable record; `runLaunchAutoRetry` stops discarding a stem whose sidecar does not decode.
3. Either way, one test that builds the same directory once and asserts the menu count, the Library row and `LibraryMover.inFlightReason` agree on it.

## Explicitly not

- An `error.json` beside a summary: both readers already open it there (`readers.errorEvidence` for the menu), and an undecodable one beside a summary is `.done` in both.
- The age clock itself, `LibraryMover`'s newest-write `startedAt` (STOR16), and UX101's owned-stem rule: unchanged.
- Repairing or rewriting an unreadable sidecar: the readers report, they do not fix.

## Acceptance

- A test in `MeetingStatusTests` (or `MeetingStoreTests`) over a temp directory holding a fresh `<stem>.wav` plus `<stem>.error.json` containing `{not json`, and a second stem with an unknown `stage`: `unrecoveredFailureStems(... diskFailureReaders ...)`, the scanned Library row's status and `LibraryMover.inFlightReason` give one answer per stem. Option A: not counted, `.processing`, in flight. Option B: counted, `.failed` with the unreadable-record reason, not in flight.
- Option A: `test_the_menu_count_agrees_with_decide_on_every_final_recording_row` gains an `.undecodable` row and stays green. Option B: `test_an_undecodable_error_is_no_failure_but_keeps_a_row` and `test_an_undecodable_error_sidecar_keeps_a_row_and_ages_ARCH20` are rewritten to the new rule, and an auto-retry test keeps an undecodable stem in the launch pass.
- The new agreement test red against the pre-fix code.
- `cd daemon && swift build` and `swift test` green, with the number of new tests in the commit body; `bash scripts/ci-local.sh` green. If option B changes visible copy, `docs/GUIDE.md` is updated in the same commit.
