# UX48: No main menu, so every command-key shortcut is dead in the Library

Band origin: filed 2026-07-31, owner-confirmed live during the UX39 owner walkthrough ("nothing works, everything make a tick"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

On 2026-07-31 the owner ran UX39's walkthrough and reported that Cmd+M did nothing but produce the system beep, and separately that "when MeetingPipe is in focus, top header is not showing it". Asked to widen the check, they confirmed the same beep for **Cmd+A, Cmd+C, Cmd+W and Cmd+,**, and later that **Cmd+K opens Quick Find only while the status-bar dropdown is open**. Every one of those is the same cause.

The app installs no main menu. `LibraryWindow.swift:535` states it in a comment written for an unrelated reason: "The status-bar menu's key equivalent (StatusBarController) is not validated against a key window in this LSUIElement app (no NSApp.mainMenu)". macOS dispatches a command-key event to `NSApp.mainMenu.performKeyEquivalent` before anything else, so with no menu there is nothing to match a standard shortcut, and the unhandled event becomes the beep. The same absence is why the menu bar never reads MeetingPipe: there are no menus to display, so macOS leaves the previous app's in place.

**This is not a UX39 regression, and the pickup session should not go looking for one.** `WindowActivationManager.showWindow` calls `window.makeKeyAndOrderFront(nil)` (`WindowActivationManager.swift:96`), and the Library genuinely becomes the key window: the owner typed a question into the Ask field in the same sitting (UX38's eyeball passed), which requires key status. What UX39 changed is that the app now flips to `.regular` correctly and takes a Dock icon and a Cmd+Tab slot, which makes the gap more visible and more incongruous (a window that presents as a normal app window and honours no standard shortcut) without having caused it.

**The gap has been papered over once already, ineffectively, and that is the most useful fact here.** Commit `292dfe49` (2026-05-29, "fix(library): open Preferences with Cmd+, from the Library window") added a zero-opacity SwiftUI `Button` carrying `.keyboardShortcut(",", modifiers: .command)` at `LibraryWindow.swift:537-542`, with the comment quoted above as its rationale. The owner confirmed on 2026-07-31 that **Cmd+, ticks like the rest**, so that workaround does not work today and there is no evidence it ever did. The working hypothesis for why, to be confirmed at pickup rather than assumed: SwiftUI implements `.keyboardShortcut` through the menu system as well, so a view-hierarchy button cannot route around a missing `NSApp.mainMenu`. If that holds, then adding a second per-shortcut patch of the same shape is guaranteed to fail the same way, which is the real reason to fix the cause instead.

**Measured 2026-08-04, and that hypothesis is refuted.** The same probe rebuilt `292dfe49`'s shape verbatim (a zero-opacity `Button` with `.keyboardShortcut(",", modifiers: .command)` in a `.background`, hosted by `NSHostingView`, `NSApp.mainMenu` nil) and dispatched a synthetic Cmd+, at the window: `performKeyEquivalent` returned **true and the button's action ran**. SwiftUI's shortcut dispatch does not need a main menu; `NSWindow.performKeyEquivalent` recurses the view tree after the main menu declines, and with no main menu it is simply the first thing asked. The same probe confirmed the other half of the diagnosis exactly as filed: Cmd+C, Cmd+A, Cmd+M and Cmd+W all returned **false** with no menu installed, which is the beep.

Why the owner saw Cmd+, tick anyway is therefore **not settled**, and is worth one glance during the walkthrough rather than a spike: the likeliest reading is that it did fire and Preferences opened behind the Library, which is UX56's report filed the same day. The conclusion the task rests on is unchanged and is stronger without the hypothesis: the reason not to add a second hidden button is not that hidden buttons cannot work, it is that Copy and Select All must reach **the text under the pointer**, which no button this app owns can be. That is a generality argument, and it survives the measurement.

Impact is a daily-use gap rather than a cosmetic one: the Library's whole purpose is reading transcripts and summaries, and text cannot be lifted out of them with Cmd+C.

## The one unmeasured fact, which decides the band

**Does right-click Copy still work in the transcript and summary views?** An `NSTextView` builds its own context menu rather than deriving it from the main menu, so a mouse path plausibly survives, and this task is filed P2 on the assumption that it does. Measure it first at pickup: if right-click Copy is also dead, there is no way at all to get text out of the app, which is a broken core promise and the owner should be asked to re-band to P1 (the DIAR2 precedent for naming a re-band in the row).

**Measured 2026-08-04, and the premise does not hold: this app contains no `NSTextView` at all.** An offscreen `NSHostingView` probe (a plain `NSWindow`, `NSApp.mainMenu` nil, never activated) reports that SwiftUI's `.textSelection(.enabled)` is backed by `SwiftUI.SelectionTextField`, an **`NSTextField`** subclass, which carries no `.menu`, returns **nil** from `menu(for: rightMouseDown)`, does not respond to `copy:`, `paste:` or `selectAll:`, and has no ancestor in the view chain carrying a menu either. Every reading surface is that: `TranscriptTab.swift:803`, `SummaryRenderedView.swift:141`, `AskView.swift:342`, `GuideView.swift`. `TextEditor` is the only NSTextView-backed control in the app and it appears only in editing sheets (`CorrectionEditor`, the paste box, the prompt editor), none of which is a reading surface.

So the mouse path this task's P2 band assumed almost certainly does not exist, and the recommendation is **P1**. The hedge, stated so the owner can close it in one gesture: the probe could not create a live text selection headlessly (synthesizing `mouseDown` on that field enters AppKit's tracking loop and blocks), so it measured "no menu with no selection" rather than "no menu with a selection". The concrete way it could be falsified: a selectable `NSTextField` conventionally engages the window's **field editor** (which *is* an `NSTextView`, with the standard text context menu) once a selection exists, so a right-click after selecting could find a menu that a right-click before selecting does not. Walkthrough step 1 is that check, and it is one right-click.

That same mechanism is why the fix works on the reading surfaces at all: whatever holds a live selection is what Edit ▸ Copy's `copy:` reaches down the responder chain. It is also why Cmd+A does not select a whole transcript, and the guide says so: `selectAll:` goes to the first responder, and the transcript is selectable text rather than a field you are typing in.

## Scope

Install a minimal `NSApp.mainMenu` when the app flips to `.regular`, and tear it down on the way back to `.accessory`. `WindowActivationManager` already owns exactly that transition in one place (`showWindow` raises the policy on the first window, `didCloseWindow` drops it on the last), so it is the seam, and no call site needs to learn about menus.

The menu only needs the items whose key equivalents are missing, which is the App menu (Preferences, so `292dfe49`'s hidden Button can be deleted rather than left as dead code), an Edit menu (Undo, Redo, Cut, Copy, Paste, Select All, wired to the standard first-responder selectors so `NSTextView` picks them up for free), and a Window menu (Minimize, Close). Nothing bespoke: these are `NSMenuItem`s pointing at the standard responder-chain actions, and the responder chain already exists.

Delete the `292dfe49` workaround as part of this, so the file stops carrying a comment asserting a technique that does not work.

## Explicitly not / out of scope

**UX27 (floating-panel keyboard operability) is a different problem and is not fixed by this.** Its surfaces are the detection prompt and the recording HUD, which are borderless Dock-less `NSPanel`s that deliberately skip the activation handshake, and its symptom is Tab focus and focus rings rather than command-key equivalents. A main menu does not give a panel key focus. Leave UX27 at P4 where the owner put it, and do not fold the two together.

**Quick Find (Cmd+K) is in scope, and it is the clearest proof of the cause.** It is not a global hotkey: `HotkeyManager`'s Carbon registrations cover only manual-start, force-stop, the flag and off-record (`Coordinator.swift:457-499`), while Cmd+K is a key equivalent on the status-bar menu (`StatusBarController.swift:558-560`). The owner reported on 2026-07-31 that it "works only when menubar dropdown is opened and visible", which is exactly right and exactly the diagnosis: an `NSMenu` matches its own key equivalents while it is open, and nothing matches them when it is closed, because that is the job `NSApp.mainMenu` would do. This is also precisely what the `LibraryWindow.swift:535` comment describes ("The status-bar menu's key equivalent (StatusBarController) is not validated against a key window in this LSUIElement app"), written about this very shortcut. A main menu fixes it along with the rest, and Cmd+K working with no menu open is part of this task's acceptance.

**That last sentence is wrong, and the 2026-08-04 pickup did not ship it.** HYG6 filed the same defect independently. `NSApp.mainMenu.performKeyEquivalent` searches the **main menu tree only**, and an `NSStatusItem`'s menu is not in it, so installing a main menu does nothing for a key equivalent that lives on the status-bar menu. Cmd+K therefore still opens Quick Find only while that dropdown is open. The diagnosis in the paragraph above is sound; only the inference that a main menu inherits the status item's chords is not. Two ways to actually deliver it, both **outside the scope enumerated above and left to the owner**:

- **Cmd+K from any MeetingPipe window:** give Quick Find a row on the main menu, four lines beside Preferences and the same `AppDelegate` bridge. This is the one the pickup would recommend.
- **Cmd+K with another app frontmost:** only a Carbon global hotkey can do this, since a non-active app receives no keystrokes at all. It would take Cmd+K away from every other app on the Mac, which is exactly why `HotkeyManager`'s four existing chords are all Ctrl+Opt-based. Recommended against.

**Do not add per-shortcut view-hierarchy handlers.** That is the approach `292dfe49` took and it is the thing this task exists to stop repeating.

**Not a redesign of the status-bar menu.** `StatusBarController`'s menu is the app's menu-bar-extra surface and is unrelated to `NSApp.mainMenu`.

Its real intent, whether closing the last window hands activation on, needs an observable that does not involve the menu bar: whether the previously-active app becomes frontmost and takes keystrokes.
