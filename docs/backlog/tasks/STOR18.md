# STOR18: Move to Trash has no guard for the meeting being recorded: the row, the detail header and the batch pane all trash the live capture files

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source: [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md) findings F008 and G036 (data lens, both confirmed), the same defect reached from two directions. Re-verified in code at HEAD `3a2da4fc` on 2026-11-14.

**The service trashes whatever shares the stem.** `MeetingLibraryService.softDeleteMeeting(stem:)` lists `outputDir()`, keeps every entry where `MeetingStore.stem(of: url) == stem` (the name up to the first dot), and calls `fm.trashItem` on each, then cascades into `originals/<stem>.wav` and the waveform cache. While a recording runs, `MeetingRecorder.start` has created `outputDir/<stamp>.mic.wav` and `<stamp>.system.wav`, plus the `.capturemode` marker, and `MeetingSessionController.writeRecoveryManifest` has written `<stem>.recovery.json`; all of them match. The service's collaborators are `outputDir`, `launcher`, `enqueue` and friends; nothing passes it the recorder's ownership or `LibraryWindowModel.liveRecordingStem`.

**No surface gates on the live stem.** The live meeting is in the list: `LibraryListView.inProgressMeetings` pins the row whose `$0.stem == libraryModel.liveRecordingStem`, and the row is built with `isLiveRecording: libraryModel.liveRecordingStem == meeting.stem`. Its context menu's `Button(role: .destructive) { promptDelete() }` ("Move to Trash…") is `.disabled(processing.isBusy)`, and `ProcessingPresentation.isBusy` is `self != .idle`, which tracks pipeline-lane jobs and is `.idle` during capture. Selecting that row shows the ordinary detail pane (`LibraryWindow` builds `MeetingDetailView(store: model.meetingStore, meeting: only)` with no live-recording branch), whose header "More" menu carries `Button("Delete…", role: .destructive) { toolbarAction("delete") { confirmDelete() } }`; `confirmDelete` calls `libraryModel.softDeleteMeeting(stem: meeting.stem)` after `LibraryDialogs.confirmSoftDelete` with no other check. `BatchActionsPane.runSoftDelete` loops `libraryModel.softDeleteMeeting(stem:)` over every selected stem, and its "Move to Trash" button is `.disabled(isRunning)` only, so a multi-select of today's rows that includes the pinned live row trashes it with the rest.

**What happens next.** `trashItem` is a rename, so the recorder's open file descriptors keep writing into the files now in the Trash and the HUD keeps showing Recording. At stop, `MeetingRecorder.mergeIntermediates` tests the original paths (`FileManager.default.fileExists(atPath: micURL.path)` and the same for `systemURL`); both are gone, so it logs `WARN: neither mic nor system has audio data - leaving <final> absent` and returns false. `MeetingSessionController`'s stop path then logs `recording_stopped` with `produced_final: false`, skips `coordinator.jobs.enqueue`, writes the meta sidecar, and notifies "Could not finalize <file>. The raw recording was kept and will be recovered automatically." That promise rests on the orphan sweep, which scans `outputDir` for intermediates and the recovery manifest; both are in the Trash, so the sweep finds nothing and the meeting never reaches the pipeline. The audio survives only as two intermediates in the Trash that nothing in the app will look for.

**REC23 is the precedent and does not cover this.** [REC23](./REC23.md) (done 2026-10-26) introduced `RecordingStemOwnership` (`MeetingRecorder.stemOwnership`, read as `recorder.ownedStems`), claimed in `start()` before the first file is created and released after stop finishes, precisely because `liveRecordingStem` is a UI mirror set only after `start()` returns. It wired that into the orphan sweep (`Coordinator.recoverOrphanedRecordings`: `excludingStems: ownedStems` and `isOwned: { ownership.contains($0) }`), the stranded-job reaper and the retention sweep (`liveStems: ownedStems`), never into a user delete. [STOR7](./STOR7.md) rewrites the same function for footprint, honest counts and off-main batching, and guards nothing about the live stem.

**A queued or running job is the same hazard, one step later.** `softDeleteMeeting` also ignores `libraryModel.activeProcessing` and `pendingProcessing`. The row's `processing.isBusy` gate covers the row menu for those, but the header and the batch pane do not, so a meeting whose `mp run-all` is in flight can have its WAV and sidecars trashed under the subprocess. FEAT9's merge cleanup (`mergeMeetings`' success branch, `self.softDeleteMeeting(stem:)` per fragment) also goes through this function; the merge is spawned directly through `launcher.mergeMeetings`, not the pipeline lane, so its fragments are not `activeProcessing` while the cleanup runs and a guard keyed on lane state does not block a normal merge.

## Scope

1. **Service guard (the fix).** `MeetingLibraryService` gains an injected `deletionBlock: (String) -> DeletionBlock?` (`enum DeletionBlock { case recording, processing }`), defaulted to `{ _ in nil }` like the other collaborators. The `Coordinator` wires it, on main, to `.recording` when `recorder.stemOwnership.contains(stem)` (the reaper's form, not `liveRecordingStem`) and `.processing` when `libraryModel.processing(for: stem).isBusy`. `softDeleteMeeting` checks it before listing the directory and returns `.failure(LibraryError.meetingInUse(stem:reason:))`, trashing nothing. Every caller goes through this seam, including the merge cleanup, so no surface can bypass it. `RecordingStemOwnership` is `@MainActor`; when STOR7 moves the batch off main, the block is resolved on main per stem before the hop.
2. **Name the skipped rows.** `BatchActionsPane.runSoftDelete` counts `.meetingInUse` separately from other failures, and the finished state says how many were skipped because they are recording or processing. The confirm (`confirmingDelete`) excludes those stems from its count and says they will be skipped when the selection contains one.
3. **Disable on the surfaces.** The row's "Move to Trash…" is disabled when `isLiveRecording` as well as when `processing.isBusy`; the detail header's "Delete…" is disabled for the live stem and for an active or queued job, with a help tag saying why. These are presentation; the service guard is what holds.
4. **Event.** A refused delete logs `Log.event(category: "coordinator", action: "delete_refused", attributes: ["stem": stem, "reason": "recording" | "processing"])`, under the `coordinator` category CONVENTIONS.md's event log schema already lists (the category `merge_succeeded` and `summary_preview_discarded` use from the same service).

## Explicitly not

- STOR7's footprint enumerator, honest trashed counts and off-main batch delete. Same function, separate concern; whichever lands second rebases onto the other, and the guard stays the first check.
- Guarding the library move and the live-row status pill: separate findings in the same audit band, filed on their own.
- Soft-delete tests moving files into the real user Trash (F192, low): adjacent, not fixed here, though the new refusal tests trash nothing by construction.
- Correcting the "will be recovered automatically" notification for other no-final causes. With the guard in place this path no longer reaches it.
- Recovering intermediates already trashed by this bug. Nothing on the owner's machine is known to have hit it; no recovery tooling is filed.
