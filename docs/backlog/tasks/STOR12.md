# STOR12: Automatic backups are never pruned, so a daily full-library archive fills its destination, and backup and restore decompress the whole archive several extra times against a fixed 30-minute cap

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Verified in code on 2026-10-25 against `main` at `01e904a`. Review findings PERSISTENCE-2 and PYTHON-3 (both high, both confirmed) and PYTHON-4 (medium, confirmed).

**Every run adds a full copy and nothing removes one.** `backup.create_backup` writes `destination / f"meeting-pipe-backup-{now.strftime('%Y%m%d-%H%M%S')}.tar.gz"` holding the whole library (`backup_roots`, recordings included unless `--no-audio`), `digests/`, `~/.config/meeting-pipe/` and the corrections corpus. STOR4's `BackupSchedulerService.apply` installs `com.meetingpipe.backup` with `arguments: ["backup", destination]` (no `--no-audio`), daily by default. A grep of `pipeline/src`, `daemon/Sources` and `scripts/` finds the archive name only in the writer, in `mp restore`'s argument help, and in the restore file panel's message (`PreferencesView+Storage`); nothing deletes an older archive. [STOR8](./STOR8.md) lists retention under Explicitly not as "Not filed; note it if the pickup sees it bite". Gzip at level 1 barely shrinks WAV (the module docstring says so), so each archive is about the library's size and N days leave N full copies.

**Magnitude.** The final recording is 16 kHz stereo `pcm_s16le` (`RecordingPostProcessor`'s `-ar 16000 -c:a pcm_s16le`), 64,000 bytes a second: the owner's `20261016-122748.wav` is 71,669,838 bytes for 1,119.84 s of audio. On 2026-10-25 the owner's library (`~/Documents/Meetings/raw`) is 324 MB (61 files, 9 WAVs, no FLAC), so a daily archive is about 0.3 GB and a year of them about 118 GB with no new meetings at all, and every recorded hour adds about 230 MB to every later archive. An external drive fills and then every run fails. `check_destination` refuses only an unmounted `/Volumes/<name>` and never checks free space, and a destination anywhere outside `/Volumes` is on the startup disk, the volume the recorder writes to and the space REC20's planned recording preflight measures.

**Latent on the owner's Mac.** On 2026-10-25 `~/Library/LaunchAgents` holds no `com.meetingpipe.backup.plist` and there is no `.last-backup.json`, so no archive exists yet. It bites from the first night after Automatic backup is turned on, with certainty.

**The summary re-reads the archive it just wrote.** `create_backup` builds the manifest in memory and adds it as the last member; `backup.main` then reopens the archive with `tarfile.open(archive, "r:gz")` and `tar.extractfile(MANIFEST_NAME)` only to print it. Reaching the last member of a gzip stream decompresses all of it, so every run decompresses the whole archive once more for a summary it already held.

**Restore decompresses it several times.** `restore.read_manifest` makes the same walk to the last member. The real run (`restore.main`) calls `read_manifest`, then `restore_archive` calls it again ("validate before touching anything"), then `_restorable_members` calls `tar.getmembers()` (a full header walk) and the extraction that follows seeks back to the first member, which in a gzip stream restarts decompression from the start. The preview (`plan_restore`) is `read_manifest` plus a `getmembers` walk. By this reading the preview is two full passes and the real run four, so an in-app restore (STOR5 always runs the preview, then the real run) decompresses the archive about six times; the pickup measures the count rather than trusting it.

**All three in-app runs share a fixed 30-minute cap.** `PipelineLauncher.backup(dir:completion:)`, `restorePreview(archive:completion:)` and `restore(archive:completion:)` each call `runMP(..., timeout: 30 * 60, ...)`, whose watchdog sends SIGTERM and then SIGKILL 30 s later. `mp` has no SIGTERM handler ([PIPE22](./PIPE22.md)), so a killed **Back up now** leaves a truncated archive under its final name (STOR8 item 2 fixes the name). A killed restore is worse, and the code says so: `restore`'s doc comment reads "a restore killed halfway leaves a library that is neither the old one nor the backup, so there is no safe point to stop it at", yet the watchdog stops it at 30 minutes whatever its progress. Today's 324 MB library is far from the cap; the cap is a cliff that a library of a few hundred GB, at several passes each, walks into, and the throughput has not been measured.

## Scope

1. **Retention on the destination**, in `pipeline/src/mp/backup.py`: a `prune_old_backups(destination, ...)` that `create_backup` calls after the archive is complete. It runs only when this run succeeded and only once the new archive has its final name; it considers only files directly in `destination` whose names match `meeting-pipe-backup-YYYYMMDD-HHMMSS.tar.gz` exactly, orders them by the timestamp in the name (not mtime), never deletes the archive just written, and also removes that pattern's `.partial` leftovers older than 24 hours (a run killed by SIGKILL, which no handler can clean up). The policy is the owner's, decided before code (Owner walkthrough); the proposal is the newest 7 archives plus the newest archive of each of the 4 ISO weeks before them, so a daily schedule holds at most 11. The summary prints `pruned N older backups (<size>)` and, when N is above zero, emits `pipeline` `backup_pruned` with `count` and `bytes`.
2. **Free-space check before writing.** Estimate the archive as the sum of the bytes `_add_root` would include (WAV barely compresses at level 1, so this is an upper bound). When the free space on the destination's volume (`shutil.disk_usage` on the nearest existing ancestor) is below the estimate plus a headroom constant, raise `BackupError` naming the free space, the estimate and how many existing archives the folder holds, before anything is created. When the destination shares the library's volume (`st_dev` equal), the headroom is REC20's recording reserve (two hours of capture intermediates plus their merge, about 4.6 GB, stated beside the constant), so a backup never takes the space the next recording needs.
3. **No re-read for the summary.** `create_backup` returns the manifest it built along with the archive path, and `backup.main` prints from that. No archive format change.
4. **Fewer restore passes.** `restore.main` passes the manifest it read into `restore_archive` instead of `restore_archive` reading it again; `_restorable_members` iterates the archive lazily (`for member in tar`) instead of `tar.getmembers()`, so extraction follows the header walk forward with no rewind; `plan_restore` reads the manifest when its one walk reaches it (it is the last member) instead of calling `read_manifest` first. Target: the preview one pass, the real run two (validate, then extract). The plan JSON STOR5 decodes (CONVENTIONS "Backup and restore") does not change.
5. **A cap that scales.** Replace the three fixed `30 * 60` caps with one pure `PipelineLauncher.storageJobTimeout(bytes:)`: 30 minutes as the floor, plus the bytes involved (`StorageStats.libraryBytes` for a backup, the archive's file size for the preview and the restore) at a conservative floor throughput named beside the constant. The restore doc comment quoted above is the reason the cap must not fire on a run that is still making progress.

## Explicitly not

- `.partial` plus `os.replace`, file modes, the marker's atomic write and destination encryption: [STOR8](./STOR8.md). This task depends on STOR8 item 2, because retention must never count a truncated archive as a kept backup; if this is picked up first, it lands STOR8 item 2 with it and STOR8 drops that item.
- Incremental or deduplicating backups (a per-file manifest diff, an rsync-style mirror). They would cut the nightly full gzip and the per-copy disk cost, but they change what an archive is and how restore works: an owner design decision, not a fix.
- Making scheduled runs `--no-audio` by default. The audio is the irreplaceable part of the corpus (STOR4's own framing), so that changes what a backup protects; put it to the owner only if retention plus item 2 is not enough.
- Run-outcome visibility for scheduled runs (attempt marker, events, Preferences line, doctor warning): [STOR10](./STOR10.md). If it has landed, the prune count rides on its `backup_completed` event instead of a separate action.
- A destination inside a synced folder: [SEC18](./SEC18.md) item 5. The SIGTERM handler that lets STOR8's cleanup run on a kill: [PIPE22](./PIPE22.md).
- STOR5's restore flow, which is in [owner-verification.md](../owner-verification.md) and stays there: this task changes how the plan is computed, not what it says.
- Observed adjacency, from the same review's subprocess findings (SUBPROCESS-8 ([CONC5](./CONC5.md)), PERSISTENCE-12 ([CONC5](./CONC5.md))): the Storage pane's schedule controls run `launchctl` bootout and bootstrap synchronously on main.
