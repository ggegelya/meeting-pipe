# UX55: "Quit (do not relaunch)" is still offered when nothing can relaunch

Band origin: filed 2026-07-31, owner-reported at the end of UX42's walkthrough: "I guess I just need to see one 'quit' instead of 'quit dont relaunch, no? cause when this flag is off, relaunch is not working for classic quit." Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The status-bar menu offers two quit rows, and the second is conditional (`StatusBarController.swift:596-610`):

```swift
menu.addItem(NSMenuItem(title: "Quit MeetingPipe", ...))
// TECH-UX7: when auto-restart is on (the default), offer a one-off quit
// that does not relaunch. Hidden when the user already disabled
// auto-restart, since the plain Quit above already means quit.
if !UISettings.shared.disableAutoRestart, let coordinator = coordinator {
```

The comment states the right rule: the extra row exists only when plain Quit would be undone by a relaunch, and is hidden otherwise. The condition implements it against one input, `UISettings.shared.disableAutoRestart`, which is a preference the user sets.

**UX42 added a second way for relaunch to be off, and this condition did not learn about it.** That task established the login agent as the single owner of both login-start and relaunch-after-quit, and its own closing note says so: "with launch at login OFF, **Quit MeetingPipe** really quits, because the relaunch-after-quit behaviour is the same launch agent and it is not running the app." So when launch at login is off, plain Quit already means quit, exactly the condition the comment says should hide the extra row, and the row is shown anyway because `disableAutoRestart` is still false. The owner reached that conclusion from the menu alone, which is the clearest possible evidence that the row is confusing rather than merely redundant.

Not a UX42 regression in behaviour: quitting works correctly either way, and the second row is harmless if used. It is a truthfulness defect of the same family UX42 itself was about, a control that describes a distinction the machine no longer makes.

## Scope

Make the row's condition ask whether a relaunch can actually happen, rather than only whether the user disabled the preference. That is the conjunction of `disableAutoRestart` being false **and** the launch agent being enabled, and `LaunchAtLoginService` (UX42) is already the one reader of the latter.

Keep the decision where it can be tested. `StatusBarModel` is the pure presentation type for this menu and its own comment at `:262` already describes this rule, so the predicate belongs there with the agent state as an input, not as a second live read inside the controller's menu-building code.

The menu is rebuilt on state changes already (the `PermissionsSnapshot` dedupe exists precisely because it rebuilds often), so the row should appear and disappear as the toggle moves without needing a restart. Confirm that rather than assume it.

## Explicitly not / out of scope

**Not the quit behaviour**, and not TECH-UX7's crash-relaunch safety net, which UX42 verified still works (a `kill -9` brings the icon back within ten seconds). Only the row's visibility changes.

**Not the wording of either row.** "Quit MeetingPipe" and "Quit (do not relaunch)" both read fine when each is genuinely applicable.

**Not the Preferences copy.** The Startup pane's explanatory text was rewritten by UX42 and is correct.

## Acceptance

`StatusBarModelTests` pin the predicate: auto-restart on and agent enabled shows both rows; auto-restart disabled shows one; **agent disabled shows one even with auto-restart on** (the case this task adds); both off shows one.

The row appears and disappears in a running app as Launch at login is toggled, without a relaunch.

`cd daemon && swift build` and `swift test` green. No em-dashes in changed lines.
