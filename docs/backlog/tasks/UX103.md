# UX103: Batch actions act on meetings the list no longer shows, and Quick Find treats a multi-word query as one phrase unlike the filter bar

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source: F171 and G061, both low and not verified by the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md). Re-verified in code at HEAD `3a2da4fc` on 2026-11-14: F171 holds as stated; G061 holds with the narrowing below. Neither has a log surface in the [field evidence pack](../../audits/2026-11-13-field-evidence.md), so this is code-derived.

**F171, the batch is resolved against the whole library.** `LibraryRootView` owns `@State private var meetingSelection: Set<Meeting.ID>` and passes it to `LibraryListView` as the `List(selection:)` binding. `detailPane(workflowStore:)` resolves the batch as `let selected = model.meetingStore.meetings.filter { meetingSelection.contains($0.id) }` and shows `BatchActionsPane(meetings: selected, libraryModel: model)` when `selected.count > 1`. The only rule that prunes the set is `.onChange(of: scope) { ... if newScope.clearsMeetingSelection { meetingSelection = [] } }`, and `LibraryScope.clearsMeetingSelection` is `isWorkflow` (UX33). Nothing intersects the selection with what `LibraryListView.recomputeDerived()` leaves in `derived.filtered`.

**Scenario.** Cmd-click five meetings in All meetings, then type a search (or set a Status chip, or open Needs you, NDA only or a saved folder) so one of them is on screen. The detail column still reads "5 meetings selected", and Move to Trash, Re-transcribe, Re-summarize all, Republish, Merge and Export act on all five. The pane is not silent, since `leadRow` shows the count and `selectionCard` previews up to three titles, but four of the rows it acts on are not in the list the owner is looking at, and the trash confirm ("Move \(meetings.count) meetings to Trash?") gives only a number.

**G061, Quick Find's query is one phrase.** `QuickFindRanker.normalizeQuery` is documented "Trims, lowercases, collapses whitespace" but only does `raw.trimmingCharacters(in: .whitespacesAndNewlines)` then `lowercased()`. `scoreField(query:haystack:weight:)` then requires `hay.hasPrefix(q)` or `hay.contains(q)` for the whole query. `MeetingFilterEngine.tokenize` splits on whitespace and `matchesQuery` requires `needles.allSatisfy { hay.contains($0) }`, so the filter bar's "client zoom" requires both words anywhere in `searchableText`, and Quick Find's requires the phrase.

Correction at filing (G061): the divergence is narrower than "finds different meetings". Both surfaces union an FTS5 lookup, and `SearchQuery.ftsMatch` turns each token into a prefix term with an implicit AND over a body that includes `searchableText` (`SearchIndexer.documentBody(for:)`). So when the index is healthy and has reached the stem, Quick Find still returns a meeting whose words are apart, but only through `rank`'s `ftsMatches` arm: scored at `transcriptBaseline` (10, below every field weight) with the subtitle "transcript" although the words are in its title. It drops out entirely when the index is unavailable or has not reached the stem, and for a query whose tokens are all one character (`SearchQuery.indexMatch` sends nothing below `minimumIndexedTokenLength`). A double space between words ("client  zoom") also fails every field match, which the doc's "collapses whitespace" says it should not.

**Related.** [PERF30](./PERF30.md) (same band) changes the filter bar's search timing and names this task. [STOR18](./STOR18.md) (same band) gates the batch pane's trash on a live stem. [STOR7](./STOR7.md) owns what trash deletes. [PERF9](./PERF9.md) owns the list's rendering cost. [PERF20](./PERF20.md) (done) made `scoreField`'s word-boundary tier reachable; this keeps it.

## Scope

1. **Prune a multi-selection to the visible list.** In `LibraryListView.recomputeDerived()` (or an `onChange` of the derived list), when `selection.count > 1`, intersect it with the ids in `derived.filtered`. Leave a single selection alone: `LibraryRootView`'s `pendingSelection` handler sets `scope = .allMeetings` and `meetingSelection = [stem]` without clearing the filter, so pruning a lone selection would undo a Quick Find or notification jump to a meeting the current filter hides. If the pickup session finds intersecting inside the list view fights the `List` binding, the fallback is to show "N selected meetings are hidden by the current view" in `BatchActionsPane.leadRow` and exclude them from every action; say which in the commit body.
2. **Tokenize Quick Find like the filter bar.** `normalizeQuery` splits with `MeetingFilterEngine.tokenize` (one tokenizer, not a copy) and its doc says what it does. A field matches when it contains every token; the prefix tier applies when the field starts with the first token, the word-boundary tier when every token starts a word. A meeting whose tokens are split across fields matches at the lowest weight among those fields, so the in-memory set Quick Find returns is never smaller than the filter bar's for the same words. A one-token query scores exactly as today.

## Explicitly not
