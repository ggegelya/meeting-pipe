# UX65: the grading window records a summary that is no longer on disk, and a later Revert writes it back

Band origin: filed 2026-08-04 at the owner's explicit request, off UX53's sweep (row 20 of its table), which named it as an owner-gated recommendation rather than filing it. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

`CorrectionWindow` is the standalone summary-grading window (ADR 0015), reached from the done-meeting notification and the Recent meetings menu. `show(stem:recordingsDir:)` reads `<stem>.run.json` and `<stem>.summary.json` once (`CorrectionWindow.swift:19-30`) and holds the result in a `CorrectionViewModel` for the window's whole life. Nothing on that path observes the store, watches the directory, or re-reads at save time, so a `mp summarize` rerun, a Retry, a Keep-preview, or a Save from the Library's own editor landing while the window is open leaves it editing prose that is no longer the summary.

**UX53's row 20 named the right window and the wrong mechanism, and the correction is the reason this spec exists.** That row said the window's save "writes that back over the new summary". It does not. `handleOutcome` (`CorrectionWindow.swift:78-108`) calls `CorrectionStore.write` and nothing else, and `CorrectionStore.write` (`CorrectionStore.swift:65-121`) writes one file, `corrections/<stem>.json`. It never opens `<stem>.summary.json`. The surface that does overwrite the live summary is the Library's in-tab editor, `SummaryTab.persistEdit` (`SummaryTab.swift:685-715`), which is a different code path and which already tracks `loadedSummaryMtime` (`SummaryTab.swift:22-24`).

So the direct lost update does not exist. Two real defects do, and the first is a lost update one step removed.

**1. A stale `original_summary` becomes a real overwrite through Revert.** The record `CorrectionStore.write` persists carries `original_summary` = whatever the window loaded (`CorrectionWindow.swift:92`). `CorrectionsTab.performRevert` (`CorrectionsTab.swift:219-243`) restores `<stem>.summary.json` from exactly that key with `data.write(to: summaryURL, options: .atomic)` and then deletes the correction file. So grading a summary in a window that went stale, then reverting that correction later, writes prose that was superseded before the grading over whatever is current, and destroys the record that would have shown what happened. The user action at the far end is labelled Revert and reasonably reads as safe.

**2. The corrections corpus is training data, and a stale original records a diff nobody made.** `corrections/` is globbed by `mp corrections-stats` and by the LoRA phase (`pipeline/src/mp/corrections.py:20`, `:181`; `mp train-adapter`), and `SummaryTab.persistEdit`'s own comment says the standalone window writes "the same path ... so the LoRA training set sees both surfaces identically". A record whose `original_summary` is two generations old encodes an edit from prose the model never emitted on this run. `verdict = .bad` (`CorrectionWindow.swift:84`) has the same problem in a sharper form: it files a judgement against a summary that has already been replaced.

Neither is visible at the time. The window shows no indication it went stale, and the record it writes is well-formed.

## Scope

Detect at **save** time that `<stem>.summary.json` has moved under the window, and make the user's next step a decision rather than a silent write. The seam is `CorrectionWindow.handleOutcome` (`CorrectionWindow.swift:78`), immediately before the `CorrectionStore.write` call, with the staleness predicate itself a pure function so it can be pinned without a window.

Capture the identity of what was loaded in `show()` (modification date plus size, or a content hash; `SummaryTab.swift:22-24` already keeps an mtime for the same file and is the local precedent), carry it on `CorrectionViewModel`, and compare against the file on disk inside `handleOutcome`.

On a detected move, do not write. Tell the user the summary changed while they were editing and offer the two honest options: discard their edit and reopen against the current summary, or keep editing and save against the current summary as the original. Which of those is the default is the one open call this task makes; either is defensible and the spec does not pre-decide it.

## Explicitly not / out of scope

**Not a reload key, and this is the whole reason UX53 did not fix it in place.** Silently re-reading on a store-revision bump would discard the owner's in-progress edit, which is a worse failure than the one being fixed and is why the UX52 idiom (`@ObservedObject` store plus a `<Key>(stem:revision:)` reload) is the wrong tool here. The window is a modal-shaped editor over user-authored text; every other surface UX53 fixed renders text the user did not type.

**Not `SummaryTab`.** The Library's in-tab editor is a separate path with its own mtime tracking, and UX53 scored it separately. If the same class is found there it is a new row, not this one.

**Not `CorrectionsTab.performRevert` itself.** Revert restoring `original_summary` is correct behaviour given a correct record; the defect is upstream, in the record. A guard there would treat the symptom.

**Not the `verdict = .bad` semantics.** That a bad verdict against a superseded summary is meaningless follows from the same staleness and is fixed by the same detection; no change to what `bad` means.

**Not retroactive repair of existing records.** Whether any `corrections/*.json` on disk already carries a stale original is unmeasured, and a corpus migration is a separate decision. If the pickup session measures it cheaply, record the number in this spec rather than acting on it.

## Acceptance

`cd daemon && swift build` clean and `swift test` green, with new tests (leave the count to the session that writes them; do not pin an absolute suite total).

The staleness predicate is pure and pinned directly, not asserted through a window: unchanged file reads as fresh; a file rewritten in place with new content reads as stale; a file rewritten with identical bytes is a documented choice either way, stated in the test name.

`CorrectionWindow.handleOutcome` writes no correction record on the stale path. Pin it on the bytes of `corrections/<stem>.json`, the way `ClarifyTests` pins the Venusaur case on the bytes of both files: the file must not exist, or must be unchanged, after a save attempt against a moved summary.

The fresh path is unchanged: a save with the summary untouched still writes exactly the record it writes today, with `original_summary` equal to the loaded summary.

A source fence that `CorrectionWindow` captures the identity in `show()` and reads it in `handleOutcome`, since a capture that is never compared is the failure mode this task is about and a passing write-path test would not see it.

`python3 scripts/truth_fences.py both` green. No em-dashes in changed lines. No new `.system(size:` in changed lines (DSN3).
