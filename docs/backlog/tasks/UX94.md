# UX94: A config.toml that does not parse is surfaced only inside Preferences, with no event and no menu row, and every summary then fails as an unknown error offering a Retry that fails again

Band origin: filed 2026-10-25 from the 2026-10-25 observability audit band ([observability audit](../../audits/2026-10-25-observability-audit.md) row O16, UI-7). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Re-verified against `main` at `01e904a` on 2026-10-25 by code reading. Not reachable on the audit Mac (its `config.toml` parses); reachable after any hand edit with a typo, which the [GUIDE](../../GUIDE.md) section 10 recipe "Preferences says the settings file has a syntax error" treats as an expected case.

**The daemon fails closed, quietly.** ARCH9 made `ConfigStore.read` return a `ConfigParseError` (message, line, column) instead of an empty document, and `apply` sets `regulatedMode = file.parseError != nil` and refuses saves. That part is right. What reaches the user is one line in `App.swift`:

```swift
Log.main.error("config.toml at \(Config.defaultPath.path) does not parse, running on defaults with regulated mode on and saves refused: \(parseError.message)")
```

That is os.Logger, so the reason is stored as `<private>` and nothing reaches `~/Library/Logs/MeetingPipe`. The only other consumer of `parseError` is `PreferencesView.detailContent`, which shows `ConfigParseErrorPane` instead of the panes. No event is written, the menu has no row, and `SetupChecklist` has no item. Detection, the prompt timeout, the auto-record allowlist and the summarization engine all revert to defaults with regulated mode on, and nothing outside Preferences says so. `ConfigStore.reloadIfUnparsed` re-reads only when Preferences opens (`PreferencesWindow.show`).

**The pipeline fails as unknown.** `Config.load` calls `tomllib.load(f)` with no `TOMLDecodeError` handler, so `mp run-all` raises out to `__main__.main`'s `except Exception`, which calls `failure_details.emit_failure`. `describe` has no branch for it, so the metadata is `cause: "unknown"`, `remedy: "retry"`, and the traceback goes to stderr. In the Library, `FailurePresentation` titles it "Couldn't create the summary" with "Retry when you are ready, or open Details to inspect the failure.", and Retry fails the same way until the file is fixed. On Python 3.11 (the pinned range is `>=3.11,<3.13`) `TOMLDecodeError` has no `lineno` attribute; the position is only in the message, for example `Invalid value (at line 2, column 1)`. A file that parses but fails pydantic validation in `Config(**raw)` (a string where a number belongs) takes the same unknown path. `mp doctor`'s `check_config` already catches both and prints `config parse error`, so doctor is not the gap.

## Scope

1. **Record it at launch.** In `App.swift`, when `store.parseError` is set, emit `daemon/config_parse_failed` with `line` and `column` (never the message text, which can quote the file's content) and write the same fact to `daemon.log` via `Log.writeLine`. Emit it again from `reloadIfUnparsed` only when the state changes (fixed or newly broken), as `config_parse_failed` or `config_parse_recovered`.
2. **A menu row and a Finish setup item.** A `StatusBarModel.Row` case "⚠ Settings file has a syntax error - open Preferences" while `parseError` is set, opening Preferences (whose pane already names the line and offers **Open in editor**). `SetupChecklist` gains a `configUnreadable` item with the same target. Opening the menu calls `reloadIfUnparsed()` so a fix in an editor clears the row without a Preferences visit; it is a no-op once the file parses, so it cannot race a save.
3. **A typed cause from the pipeline.** `Config.load` catches `tomllib.TOMLDecodeError` and pydantic's `ValidationError` and raises one `ConfigUnreadableError(path, line, column, key)` (line and column parsed from the 3.11 message; `key` the dotted location of the first validation error, never its value). `failure_details.describe` maps it to a new cause `config` with remedy `config`. Swift adds `FailureMetadata.Cause.config` and `config` to `decode`'s remedy whitelist; `FailurePresentation` gives it the heading "Settings file has a syntax error" and the explanation "Fix line N of config.toml, then retry." (or "Check the <key> setting in config.toml, then retry."), and `settingsLabel` "Open Preferences", which `MeetingDetailView.failureNotice`'s `settings` closure routes to Preferences rather than Integrations. Retry stays offered, because it is the right next step once the file is fixed. PIPE28 adds `model_rejected` to the same enum; if both are in flight, land the two causes together so `FailureMetadata.Cause` changes once (PIPE28's own note).
4. **Pin the contract.** Add a `config` case to `gen_failures` in `scripts/gen_contract_fixtures.py` and regenerate `failure-metadata-golden.json` (`cd pipeline && uv run python ../scripts/gen_contract_fixtures.py`), so the Swift decoder test sees it.
5. **Docs in the same commit.** [GUIDE.md](../../GUIDE.md) section 10, "Preferences says the settings file has a syntax error": the menu bar now says so too, without opening Preferences, and the failed meeting's notice names the line and leads with **Open Preferences**; the sentence "their summaries fail until the file is fixed" stays true. README's config reference, if it describes the failure, in the same commit.

## Explicitly not / out of scope

- Repairing or rewriting a broken file. ARCH9's rule stands: never write over a file that does not parse.
- A notification at launch. The menu row is durable and a launch banner would repeat on every relaunch; one quiet row is the register PRODUCT.md asks for.
- Validating config types on the Swift side. `ConfigStore` reads what it models and preserves the rest; the pipeline's validation is the authority, and item 3 makes its verdict readable.
- Glossary and workflow files, which already catch `TOMLDecodeError` (`glossary.py`, `workflows.py`); an unparseable workflow being dropped silently is SEC21's amendment.
- Config saves that fail on a readable file: UX91.
