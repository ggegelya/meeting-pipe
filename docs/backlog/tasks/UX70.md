# UX70: asking several questions grows the Library window past the screen, and the answers cannot be scrolled to

Band origin: filed 2026-08-04 at the owner's request, found while walking AI12 the day it shipped. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The owner reported it as the critical one of four Ask findings that pass: "multiple ask questions increase size of the window beyond available screen size and theres no way to scroll it".

AI3 stacks answers newest-first and AI12 made wide answers routine, so a session of three or four questions is now the normal case rather than the edge. When the window outgrows the display, the content below the fold is unreachable: not merely awkward, but answers the user paid an engine call for that they cannot read.

**The obvious fix is wrong, and that is the most useful thing in this filing.** There is already a `ScrollView` over the session, at `AskView.swift:288`, wrapping the running card and every entry. So this is not a missing scroller and "wrap it in a ScrollView" is a non-fix. The scroller exists and is not the thing constraining height.

The likely shape, to be confirmed rather than assumed: the answer body is `Text(a.answer).fixedSize(horizontal: false, vertical: true)` (`:383-387`), which asks for whatever height the prose needs; inside a column whose height is content-driven, a tall enough stack proposes an ideal height the window adopts. If nothing between the `ScrollView` and the window imposes a ceiling, the window grows to fit rather than the scroller taking over. Whichever it turns out to be, the fix is a height constraint at the right level, not another scroller.

Two related observations from the same sitting, filed separately so this one stays a single defect: the Ask pane's presentation, including its unrendered markdown and its empty trailing column, is [UX71](./UX71.md).

## Scope

Make the Ask session scroll within the window instead of growing it, at whatever level the sizing actually escapes. Reproduce first with several long answers, since the number that triggers it is unknown and it may need a wide answer to show.

Check the neighbouring rails while there: `Facts`, `People` and `Digests` render lists in the same centre column, and if any of them can drive the window the same way this is one fix rather than four.

## Explicitly not / out of scope

**Not adding a second `ScrollView`.** One exists. A second would nest scrollers and make it worse.

**Not the answer stacking.** Newest-first with the running card above the history is AI3's design and the owner has not asked for it to change.

**Not the reading measure.** The capped column at `SummaryLayout.readingMeasure` is UX36's rule and is unrelated to vertical growth.

**Not the presentation issues**, which are UX71.

## Acceptance

`cd daemon && swift build` clean and `swift test` green, with new tests (leave the count to the session that writes them; do not pin an absolute suite total).

The height constraint is pinned at the decision rather than by rendering: a test that the pane's sizing does not depend on entry count, the way `HUDPanelGeometryTests` pins geometry without drawing anything. A test that merely constructs the view proves nothing here, since the old code constructed fine too.

`python3 scripts/truth_fences.py both` green. No em-dashes in changed lines. No new `.system(size:` in changed lines (DSN3).
