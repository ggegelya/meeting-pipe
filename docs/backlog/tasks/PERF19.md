# PERF19: in-call signal polls never slow down: ScreenCaptureKit is enumerated up to twice a second with no in-flight guard, and the adaptive backoff lasts one poll

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Review findings DETECTION-10 (confirmed, medium) and DETECTION-11 (confirmed, low), re-verified at HEAD 01e904a on 2026-10-25, plus one defect found in the same function while re-checking.

**ScreenCaptureKit at 2 Hz (DETECTION-10).** `ShareableContentSignal` ([`ShareableContentSignal.swift`](../../../daemon/Sources/MeetingPipeCore/Lifecycle/Signals/ShareableContentSignal.swift)) is started by both `NativeLifecycleAdapter` and `BrowserMeetingLifecycleAdapter` at engage and stopped at disengage, so it runs from the prompt to the end of every detected meeting. `public static let activePollInterval: TimeInterval = 0.5` and `idlePollInterval = 1.0`; `adjustCadence(forActive:)` picks the active rate whenever the meeting window is present. Each poll runs `defaultProbe`, which calls `SCShareableContent.getExcludingDesktopWindows(false, onScreenWindowsOnly: true)`, an enumeration of every on-screen window on the system through WindowServer and `replayd`, and maps each into a summary. That is 7,200 enumerations an hour while the window is present and 3,600 while it is not. Since Teams dropped its title suffix on 2026-10-08 ([END14](./END14.md)), `MeetingTitlePatterns.teams` rejects call windows titled without a meeting stem, so for many Teams calls the signal sits in the absent state at 1 Hz, which is still once a second for the whole call. The cost of one enumeration has not been measured.

**Why the 2 Hz tier exists, and why it no longer pays.** The type comment says "sub-second reaction to window disappearance, the leading signal for Teams click Leave". END17 (2026-10-24, ADR 0017) changed what a window-gone does during a recording: `shareableContentWindow` is a weak end, and `PromotionEngine` confirms a weak end only when two evidence classes have stayed ended for `defaultConfirmDwell` (60 s) or one has for `defaultLoneDwell` (720 s). Half a second of earlier reaction buys nothing against a 60 s dwell. Before the recorder arms, `.starting` still ends directly on a window-gone, where half a second is equally immaterial.

**Abandoned requests.** `defaultProbe` bridges the async API with a semaphore and `guard semaphore.wait(timeout: .now() + probeTimeout) == .success else { return nil }` (`probeTimeout = 2.0`). A timeout leaves the completion pending inside ScreenCaptureKit, and nothing records that a request is outstanding, so the next poll issues another. The timer is a `DispatchSourceTimer` on the serial `pollQueue`, so a 2 s blocked handler coalesces later fires and a wedged `replayd` adds about one request every 2 s rather than two a second (the verifier's correction). Whether SCK eventually completes or drops those callbacks cannot be read from code, so the accumulation is plausible rather than shown. Two smaller consequences of the same path: every nil poll emits `signal`/`shareable_content_unavailable` with no dedupe, one row every 2 s for the rest of a session against a wedged `replayd`; and a late completion writes the captured `var result` after the waiter has returned.

**A nil first probe disarms the signal (found at HEAD, not a review finding).** `start(context:titleMatch:)` arms nothing itself ("The initial evaluate arms the first timer via `adjustCadence`"). But `evaluate(reason:)` returns on a nil probe before it reaches `adjustCadence(forActive:)`, and `restartTick(interval:)` is reachable only from `adjustCadence`. So if the initial probe at engage returns nil (Screen Recording not granted yet, or a 2 s SCK timeout while the meeting app is drawing its call UI), no timer is ever armed and the signal never evaluates again for that engage. `ShareableContentSignalTests.test_nil_probe_logs_unavailable_without_flapping` covers a nil only after a successful first probe.

**The adaptive backoff lasts one poll (DETECTION-11).** `AdaptivePollCadence` ([`AdaptivePollCadence.swift`](../../../daemon/Sources/MeetingPipeCore/Lifecycle/AdaptivePollCadence.swift), TECH-PERF5) is meant to run `fast` "until the listener proves it is delivering, then backs off to `slow`", returning to `fast` once the listener "goes quiet for a full poll period". Its rule is `let next = listenerSinceLastPoll ? slow : fast; listenerSinceLastPoll = false; return next`. The three listeners that call `noteListener()` are edge-only: `kAXUIElementDestroyedNotification` in `AXLeaveButtonSignal` (fires once, when the button is destroyed), value and title changes on the mute button in `AXMuteButtonProbe` (fire on a toggle), and `kAudioProcessPropertyIsRunningInput` changes in `ProcessAudioSignal` (fire at join and leave). For an edge-only listener, quiet is the normal steady state, so the poll after a slow interval is fast again and the 5 s `defaultSlowPollInterval` is effectively never sustained. All three poll at 1 Hz for every engaged session. Each poll is a cheap single-element read, so the cost is wakeups, small next to review findings DETECTION-1 ([PERF10](./PERF10.md)), DETECTION-6 ([PERF18](./PERF18.md)) and DETECTION-7 ([CONC9](./CONC9.md)).

## Scope

1. **One rate for `ShareableContentSignal`: 1 s.** Set `activePollInterval` to the idle value (keep both constants so adapters and tests read the same names), and rewrite the type comment's "sub-second reaction" claim against END17's dwell. Do not go below 1 Hz here: the absent-state poll is what sees a returning window revert a window-gone provisional (END14), and that timing has its own tests.
2. **At most one SCK request in flight.** Split `defaultProbe` into a small bridge over an injected fetch (default `SCShareableContent.getExcludingDesktopWindows`) so it is testable. A lock-guarded flag is set before the fetch and cleared by its completion, even after the waiter gave up; a poll that finds it set returns nil at once without a second request (the existing "unavailable, hold prior state" path). The completion hands its result through the same lock, which removes the late write to the captured `result`.
3. **`shareable_content_unavailable` once per outage**, deduped the way `shareable_content_no_match` is through `lastUnmatchedCandidates`, with the next successful probe re-arming it.
4. **Arm the tick on a nil probe.** On the nil path, arm at the idle interval when nothing is armed yet (`currentInterval == 0`), so a transient failure at engage costs one second, not the session.
5. **A backoff that holds in steady state.** Change `AdaptivePollCadence` so `slow` is sustained once polls stop bringing news: after a few consecutive polls whose reading matched the signal's current state (the pickup states the count beside the constant), the cadence stays `slow` until a poll reads a change the listener did not deliver, or reads unknown, when it returns to `fast`; it still starts `fast` after every arm. Each of the three call sites passes whether its poll observed a change. State the worst case per signal beside the constant: a dropped notification is noticed up to `slow` (5 s) later, which END17's 60 s dwell absorbs for the two end signals; for `AXMuteButtonProbe` an unknown reading returns the cadence to `fast`, so its re-resolve after `defaultRearmThreshold` unknown reads keeps its current timing.

## Explicitly not

- Moving `AXMuteButtonProbe` and `ProcessAudioSignal` off main: [PERF10](./PERF10.md), which touches the same call sites' schedulers. Either can land first; the second rebases.
- The SCK probe on main at engage (`start` runs the initial evaluate on its caller, which is main): [PERF10](./PERF10.md) item 3 and review finding DETECTION-2 ([PERF15](./PERF15.md)).
- Slowing the absent-window poll below 1 Hz, or making window-gone `requiresCorroboration`: END tuning, and [END14](./END14.md) records the latter as explicitly not.
- Replacing the poll with an event-driven source for other apps' windows: a different design with its own spike; this task only bounds the poll.

## Acceptance

- `ShareableContentSignalTests`: the present-window cadence is 1 s (the existing `lastInterval, 0.5` assertion updated with the reason); with a fake fetch that holds its completion, the next poll returns without a second request; a completion after the waiter timed out clears the flag and the following poll issues exactly one request; three consecutive nil polls emit one `shareable_content_unavailable`, and a success followed by a nil emits a second; a nil initial probe still arms a tick, and a later successful probe reports `present`.
- `AdaptivePollCadenceTests`: steady agreeing polls sustain `slow` across at least twenty polls; a poll observing an unannounced change returns `fast`; an unknown reading returns `fast`; a fresh arm starts `fast`. `AXLeaveButtonSignalTests`, `AXMuteButtonProbeTests` and `ProcessAudioSignalTests` stay green, each with one new test that its steady state reaches `slow`.
- `PromotionEngineTests` and `MeetingLifecycleCoordinatorTests` green unchanged.
- `cd daemon && swift build` and `swift test` green, new test count in the commit body; strict concurrency clean with no new `@unchecked Sendable`; `bash scripts/ci-local.sh` green.
