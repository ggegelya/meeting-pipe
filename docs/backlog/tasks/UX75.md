# UX75: digest action groups after the first reserve their rows' height and draw nothing

Band origin: filed 2026-08-10 from the owner's 2026-08-04 testing notes, with two screenshots: "There's something wrong with digest UI. you can see on screenshot, it has HUGE blank spaces". Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The owner's screenshots show the digest's **Action items** section rendering `GENERAL` with its five rows, then `PERSONAL` followed by roughly 700pt of nothing, then `TEAM STANDUP: PORTAL UPDATES & INFRASTRUCTURE` followed by more nothing, then `CLIENT WORK` followed by roughly 650pt of nothing, then the `Action scope` footer. The footer contradicts the body on the same screen: it says "Showing 16 of 131 open action(s) ... General: 5 of 19 shown, Personal: 5 of 102 shown, Client work: 5 of 9 shown".

**The data is complete, so this is a render defect and nothing upstream needs looking at.** Both digest artifacts for that morning were read on 2026-08-10 and both are correct:

- `~/Documents/Meetings/digests/digest-20260803.summary.md` contains all 16 checkbox lines under their four `###` group headings, including the five Personal rows and the five Client work rows the screenshot leaves blank.
- `digest-20260803.summary.json` carries `actions` with 16 entries, each with its `group` field populated (`General`, `Personal`, `Team Standup: Portal Updates & Infrastructure`, `Client work`).

The app renders from the JSON, so the values reach the view and are dropped there.

The blank space is the tell: it scales with the number of rows the group should have (five rows leaves a large gap, the one-row Team Standup group leaves a small one). The rows are being laid out and not drawn.

## The seam

`DigestReaderView` renders the whole digest through the shared `SummaryRenderedView(summary: sel.summary)` ([DigestsView.swift:207](../../../daemon/Sources/MeetingPipe/DigestsView.swift#L207)), so the defect lives in the summary renderer and the digest is only where it is visible.

`SummaryRenderedView` builds the grouped action list at [SummaryRenderedView.swift:80-101](../../../daemon/Sources/MeetingPipe/SummaryRenderedView.swift#L80):

```swift
LazyVStack(alignment: .leading, spacing: MPSpace.s2) {
    ForEach(Array(actionRuns.enumerated()), id: \.offset) { _, run in
        if let group = run.group {
            Text(group)...
        }
        ForEach(Array(run.actions.enumerated()), id: \.offset) { _, a in
            ActionItemRow(...)
        }
    }
}
```

One outer `ForEach` emits, per run, an optional header plus a **nested** `ForEach`. That makes the `LazyVStack`'s direct children heterogeneous compound subtrees rather than a flat row sequence, and a lazy container's realization is per direct child. The comment above it records why the container is lazy (a digest can carry a few dozen rows, and building them all up front "froze scrolling"), which is a real constraint and not something to discard.

`actionRuns` itself ([:182](../../../daemon/Sources/MeetingPipe/SummaryRenderedView.swift#L182)) was read and is correct: it partitions in order, carries each row's index back into `summary.actions` for UX26's toggle, drops empty-task rows, and returns nil for a run left with none. It is already covered by a test pinning that index mapping. The group headers render, which proves the runs exist with their names; only the nested rows are missing.

Both screenshots are post-first-layout and the missing groups stay missing after scrolling, so this is not a transient realization delay that settles.

## Scope

Give the lazy container a flat, homogeneous sequence of direct children so each row is realized on its own terms.

The natural shape is to flatten `actionRuns` into one array of an enum-or-struct row type (`.groupHeader(String)` / `.action(ActionItemRow.Action)`) with stable identities, and have a single `ForEach` over it. That keeps the laziness the comment argues for, keeps `actionRuns` and its index mapping untouched as the source of truth, and removes the nesting that is the defect.

Two things to preserve, both load-bearing:

- **The index mapping.** `ActionItemRow.Action.index` is what UX26's toggle writes through, and `actionRuns`' comment is explicit that a row pointing one place and writing another would resolve the wrong commitment. Flattening must carry the index unchanged; the existing test on that mapping should still pass without modification.
- **The single-run case.** A meeting's own summary yields exactly one run with a nil group and must keep rendering as a flat list with no header, which is what `actionRuns` already guarantees and what the flattening must not perturb.

Worth deciding at pickup rather than pre-deciding here: whether the digest's bounded list still needs a lazy container at all. AI10 bounds the digest to the review window (16 rows on the reported day), and a plain `VStack` has no realization behaviour to get wrong. The counter-argument is that this view is shared with meeting summaries and the original freeze was real. The flattening fixes it either way, so treat the container choice as a separate judgement and say which was chosen and why.

## Progress (2026-08-18, shipped; owner walkthrough owed)

Shipped: the flatten, seven tests, and the docs sync check. Owed: the walkthrough below, which is the only thing that can show the rows draw.

**One citation in the sections above had already rotted, and the other two rotted the moment this landed.** `DigestsView.swift:207` pointed 17 lines short of the call by pickup; the render is `DigestReaderView.body`'s `SummaryRenderedView(summary: sel.summary)`, inside the `ScrollView` that also carries the `See every open action in Facts` link. `SummaryRenderedView.swift:80-101` and `:182` were still accurate at pickup and are not any more, since this change added ~75 lines above `actionRuns`. Everything below cites by type and function name (HYG6).

**The change.** `SummaryRenderedView.ActionListRow` is the flattened row type: `.groupHeader(name:runStart:)` or `.action(ActionItemRow.Action)`. `SummaryRenderedView.actionListRows` builds it from `actionRuns`, emitting each run's heading (when it has one) followed by that run's rows, and `body` drives one `ForEach` over that. The nested `ForEach` is gone, so the `LazyVStack` is handed one child per row rather than one compound subtree per run, and the section's own guard moved from `!actionRuns.isEmpty` to `!actionListRows.isEmpty`, which is the same predicate reached one hop later.

**`actionRuns` was not touched, deliberately, and the index mapping is carried rather than re-derived.** The flatten moves `ActionItemRow.Action` values whole instead of re-spelling their fields, so there is no second place for `index` (the position in `summary.actions` that UX26's toggle writes back through) to be computed and therefore no second place for it to drift. The existing `ActionResolveTests.testActionRowsCarryTheirIndexIntoTheSummary` passes **unmodified**, and one of the new tests asserts the flattened indices equal `actionRuns.flatMap(\.actions).map(\.index)` exactly, so the two can never silently disagree.

**Identity is by position, not by text.** A row is named by the index it already owns in `summary.actions`; a heading by the index of the first row it heads. Naming a heading by its group text looks simpler and is wrong: `MeetingSummary.actionRuns` splits into *runs* and not buckets, so a writer emitting `A, B, A` legitimately yields two headings reading `A`, and duplicate ids make `ForEach` drop or reuse rows. Pinned by `testRowIdentitiesAreUniqueEvenWhenTwoRunsShareAGroupName`.

**The container decision, which the spec left open: the `LazyVStack` stays.** Four reasons, in the order they carried weight. The comment above it records a real measured freeze rather than a precaution, and the spec itself says that is not something to discard. The view is shared: `SummaryTab`'s read-only render and its A16 compare pane, which stacks **two** `SummaryRenderedView`s, are the same code as the digest reader, so AI10's bound on the digest does not bound every caller. `ActionItemRow.metadataBand`'s own doc comment justifies choosing `ViewThatFits` over truncation by "These rows sit in a `LazyVStack` inside a `ScrollView`, which caches no height and re-measures on a width change", so swapping the container would falsify a documented premise one screen away in the same file and owe that comment an edit. And the flatten removes the only reason the laziness was misbehaving: a homogeneous row sequence is exactly the shape a lazy container realizes one child at a time, so keeping it now costs nothing. The bug is fixed by the flatten either way, which is what makes leaving the container alone the smaller change rather than the lazier one.

**Geometry is preserved by construction, and nothing visual was re-tuned.** The container keeps `spacing: MPSpace.s2` and both row kinds keep the exact modifier chain they had while nested, the heading's own `.padding(.top, MPSpace.s2)` included. That padding is the whole of the difference in rhythm: `MPSpace.s2` sits between every pair of leaves, and the heading's extra top pad is what puts more air above a heading than between a heading and the first row under it. A flatten that "tidied" it into a uniform container spacing is exactly what walkthrough step 2 is looking for, so it was left alone. No spacing, font or colour value was changed, and the diff of `body` is the loop shape plus comments. Stated as what it is: a source-level argument, since a session cannot eyeball a menu-bar app.

**Tests: 7 added**, all in `ActionResolveTests` under a `UX75` mark. The reported digest's shape (four groups, one single-row) flattening to the right interleaved sequence; every run after the first contributing its rows, which is the defect in one assertion; the index mapping surviving the flatten including for runs after the first, and agreeing with `actionRuns`; a meeting's own nil-group summary flattening to rows with no heading (walkthrough step 4); an empty group name likewise; unique identities across two runs sharing a name; and the empty cases, including a run whose only row has an empty task, which must not leave its heading behind.

Each was run against a deliberately reintroduced defect before being believed, since a test written after a fix passes for free. Mutant 1, only the first run contributing rows, is the shipped bug: 4 of the new tests go red. Mutant 2, a nil group inventing an empty heading: 2 go red. Mutant 3, a heading identified by its text: 1 goes red. All green on restore, and `swift test` is green whole.

**What the tests cannot do.** They pin the sequence the container is handed. They cannot prove SwiftUI realizes and draws it, which is the actual symptom and the reason the walkthrough below is part of acceptance rather than a courtesy. Read this as "the input to the container is now the shape the container needs", not as "the bug is closed".

**Docs checked, nothing owed.** `ARCHITECTURE.md` names the file in the Library-window list and says nothing about the render's internal shape. `CONVENTIONS.md`'s "Action grouping (`ActionItem.group`, AI10)" describes the runs *contract* (all-or-none, runs never buckets, the CI3 golden), all of which is unchanged and now depended on more explicitly by the identity rule. `README.md`, `docs/GUIDE.md` and `docs/SETUP.md` describe no user-visible behaviour that moved: the fix makes the surface show what it already claimed to. `PRODUCT.md` and `design/README.md` carry no rule this touches, since no token, spacing or type value changed. `daemon/docs/gotchas.md` has no section this falsifies.
