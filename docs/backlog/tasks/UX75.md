# UX75: digest action groups after the first reserve their rows' height and draw nothing

Band origin: filed 2026-08-10 from the owner's 2026-08-04 testing notes, with two screenshots: "There's something wrong with digest UI. you can see on screenshot, it has HUGE blank spaces". Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The owner's screenshots show the digest's **Action items** section rendering `GENERAL` with its five rows, then `PERSONAL` followed by roughly 700pt of nothing, then `TEAM STANDUP: PORTAL UPDATES & INFRASTRUCTURE` followed by more nothing, then `CLIENT WORK` followed by roughly 650pt of nothing, then the `Action scope` footer. The footer contradicts the body on the same screen: it says "Showing 16 of 131 open action(s) ... General: 5 of 19 shown, Personal: 5 of 102 shown, Client work: 5 of 9 shown".

**The data is complete, so this is a render defect and nothing upstream needs looking at.** Both digest artifacts for that morning were read on 2026-08-10 and both are correct:

- `~/Documents/Meetings/digests/digest-20260803.summary.md` contains all 16 checkbox lines under their four `###` group headings, including the five Personal rows and the five Client work rows the screenshot leaves blank.
- `digest-20260803.summary.json` carries `actions` with 16 entries, each with its `group` field populated (`General`, `Personal`, `Team Standup: Portal Updates & Infrastructure`, `Client work`).

The app renders from the JSON, so the values reach the view and are dropped there.

The blank space is the tell: it scales with the number of rows the group should have (five rows leaves a large gap, the one-row Team Standup group leaves a small one). The rows are being laid out and not drawn.

## The seam

`DigestReaderView` renders the whole digest through the shared `SummaryRenderedView(summary: sel.summary)` ([DigestsView.swift:207](../../../daemon/Sources/MeetingPipe/DigestsView.swift#L207)), so the defect lives in the summary renderer and the digest is only where it is visible.

`SummaryRenderedView` builds the grouped action list at [SummaryRenderedView.swift:80-101](../../../daemon/Sources/MeetingPipe/SummaryRenderedView.swift#L80):

```swift
LazyVStack(alignment: .leading, spacing: MPSpace.s2) {
    ForEach(Array(actionRuns.enumerated()), id: \.offset) { _, run in
        if let group = run.group {
            Text(group)...
        }
        ForEach(Array(run.actions.enumerated()), id: \.offset) { _, a in
            ActionItemRow(...)
        }
    }
}
```

One outer `ForEach` emits, per run, an optional header plus a **nested** `ForEach`. That makes the `LazyVStack`'s direct children heterogeneous compound subtrees rather than a flat row sequence, and a lazy container's realization is per direct child. The comment above it records why the container is lazy (a digest can carry a few dozen rows, and building them all up front "froze scrolling"), which is a real constraint and not something to discard.

`actionRuns` itself ([:182](../../../daemon/Sources/MeetingPipe/SummaryRenderedView.swift#L182)) was read and is correct: it partitions in order, carries each row's index back into `summary.actions` for UX26's toggle, drops empty-task rows, and returns nil for a run left with none. It is already covered by a test pinning that index mapping. The group headers render, which proves the runs exist with their names; only the nested rows are missing.

Both screenshots are post-first-layout and the missing groups stay missing after scrolling, so this is not a transient realization delay that settles.

## Scope

Give the lazy container a flat, homogeneous sequence of direct children so each row is realized on its own terms.

The natural shape is to flatten `actionRuns` into one array of an enum-or-struct row type (`.groupHeader(String)` / `.action(ActionItemRow.Action)`) with stable identities, and have a single `ForEach` over it. That keeps the laziness the comment argues for, keeps `actionRuns` and its index mapping untouched as the source of truth, and removes the nesting that is the defect.

Two things to preserve, both load-bearing:

- **The index mapping.** `ActionItemRow.Action.index` is what UX26's toggle writes through, and `actionRuns`' comment is explicit that a row pointing one place and writing another would resolve the wrong commitment. Flattening must carry the index unchanged; the existing test on that mapping should still pass without modification.
- **The single-run case.** A meeting's own summary yields exactly one run with a nil group and must keep rendering as a flat list with no header, which is what `actionRuns` already guarantees and what the flattening must not perturb.

Worth deciding at pickup rather than pre-deciding here: whether the digest's bounded list still needs a lazy container at all. AI10 bounds the digest to the review window (16 rows on the reported day), and a plain `VStack` has no realization behaviour to get wrong. The counter-argument is that this view is shared with meeting summaries and the original freeze was real. The flattening fixes it either way, so treat the container choice as a separate judgement and say which was chosen and why.
