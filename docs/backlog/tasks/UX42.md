# UX42: Launch-at-login toggle truthfulness (one mechanism owns login)

Band origin: filed 2026-07-29 (owner report, item 12: "regardless this toggle checked or not (it is not on my app) app is started at login"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Root cause confirmed 2026-07-29, and it is two mechanisms that have never met:

- **What actually starts the app at login**: the launchd user agent `install.sh` writes at `~/Library/LaunchAgents/com.meetingpipe.daemon.plist` (:483-489 from `scripts/launchd.plist.template`), loaded with `launchctl load -w` (:531) and kickstarted (:539). The template carries `RunAtLoad=true` and `KeepAlive {SuccessfulExit=false}` (template :17-23), and the comment at :14-16 shows both are deliberate design (TECH-UX7: a clean quit exits fully, a crash relaunches). `rebuild.sh:75-88` re-bootstraps the same plist on every dev rebuild, so the agent is continuously refreshed.
- **What the toggle controls**: `LaunchAtLoginService` wraps `SMAppService.mainApp` only (`LaunchAtLoginService.swift:7-9` status-derived read, :17-31 register/unregister with errors swallowed to the log), surfaced in Preferences General (`PreferencesView+General.swift:7`, :93-101) with a footer that says "Registers MeetingPipe with macOS via SMAppService" (:47). Honest about SMAppService; blind to launchd.

Turning the toggle off unregisters an SMAppService entry that was never what launched the app, and leaves the agent armed. Nothing in the app can remove the agent (only `uninstall.sh:70-71` boots it out); `LaunchAgentScheduler`'s digest/backup agents are clean (`StartCalendarInterval` only, no RunAtLoad, and they run `mp`, not the app). The repo even records the split: `docs/backlog/q3-final.md:564`.

One sharp edge to carry: the agent label and the app bundle id are the same string, `com.meetingpipe.daemon` (`install.sh:189`, `Endpoints.swift:6`, template :7), which makes `launchctl print` output and System Settings Login Items entries ambiguous, and makes any dual-registration state (agent + SMAppService both on) look like one entry when it is two.

## Scope

Make exactly one mechanism own login-start, and make the toggle drive it. Recommendation, recorded with the reasoning so pickup does not re-derive it:

**The LaunchAgent owns everything; SMAppService usage is removed.** Reasons: the agent's `KeepAlive` crash-relaunch is deliberate TECH-UX7 design and only supervises agent-started instances, so login-starting via SMAppService would bypass the supervision the product wants; install, rebuild, and uninstall already manage the agent end to end; and two registration systems is the bug this task exists to kill.

- Toggle ON: ensure the plist exists and run `launchctl enable gui/$UID/com.meetingpipe.daemon` (bootstrap if not loaded).
- Toggle OFF: `launchctl disable gui/$UID/com.meetingpipe.daemon`. Disable, not bootout: booting out the agent that owns the running process kills the app under the user's pointer; disable prevents the next login-start and leaves the running instance alone. Decide-and-record whether to also rewrite the plist's `RunAtLoad` to match (belt), noting `launchctl`'s disabled-overrides DB survives plist rewrites either way.
- The toggle's read path reports the real state (`launchctl print-disabled gui/$UID` parsed, or the service's own status query), so the control cannot lie again. Errors surface in the footer instead of being swallowed.
- `install.sh` and `rebuild.sh` respect an existing disabled state: replace `load -w` with a bootstrap that does not force-enable (the `-w` write is exactly what would re-arm a toggled-off install on the next rebuild).
- `LaunchAtLoginService` becomes the wrapper over this (rename or repurpose), with the launchctl invocations behind an injected runner so the state machine is unit-testable. Footer copy updated to name what it really does.
- README and SETUP.md's login/quit semantics paragraphs update in the same commit (DOC10 rule); note for a future D8/notarized world that SMAppService with System Settings visibility could be revisited, so the alternative is recorded, not lost.

## Explicitly not in scope

Renaming the agent label or bundle id (a migration with real breakage risk; the collision is documented here as a known sharp edge instead). Changing TECH-UX7's quit/crash-relaunch semantics. Uninstall behavior. The digest/backup scheduler agents.

## Acceptance

Unit tests over the service with an injected launchctl runner: ON from disabled runs enable (and bootstraps when missing), OFF runs disable and never bootout, state reads reflect the runner's canned print-disabled output, a runner failure surfaces as a user-visible error string.

A script-level assertion (or documented manual step in the PR) that `install.sh` over a disabled agent leaves it disabled.

`cd daemon && swift build` and `swift test` green (baseline at filing: 1770). Repo dash guard green.

Owner eyeball, two halves: toggle OFF, `launchctl print-disabled gui/$(id -u)` lists `"com.meetingpipe.daemon" => disabled`, the running app stays alive, and after the next real login the app has not started; toggle ON and the next login starts it. A crash (kill -9) still relaunches when the toggle is ON.

## Progress (2026-07-31): shipped, the eyeball is owner-owed

Everything but the owner eyeball is in, and the eyeball is the one part no session can do: it needs a real logout, and the session deliberately never ran a mutating `launchctl` against the real service (that would change whether the owner's app starts at their next login, as a side effect of a test). `swift build` clean, `swift test` green at 1997 (1980 before, 17 new), `bash scripts/test-login-agent-guard.sh` 9/9, truth fences and both dash guards clean, `bash -n` on all four touched shell scripts; no Python touched, its suite re-confirmed at 1157.

The spec's recommended direction held up under implementation and shipped as written. `LaunchAtLoginService` is now a value type over an injected `LaunchctlRunning`, exposing `status()` and `set(enabled:)` returning a `LaunchAtLoginStatus` (a three-case `LaunchAtLoginState` plus an optional user-visible error). `ProcessLaunchctl` is the real runner, and the tests never construct it, which is the point: running the suite can never change whether the developer's own Mac starts MeetingPipe at the next login.

**The one delegated decision, and its answer: `RunAtLoad` is not rewritten.** Three concrete reasons, none of them visible from the spec alone. (1) The belt is the *weaker* of the two mechanisms, not the stronger: `install.sh` regenerates the plist from `scripts/launchd.plist.template` on every run, so a `RunAtLoad=false` write survives exactly until the next install, while the disabled-overrides database survives it. (2) A rewritten plist only takes effect after a bootout + bootstrap, which is precisely the app-killing move the disable-not-bootout rule exists to avoid, so the belt cannot be fastened without the harm. (3) `rebuild.sh` relies on `RunAtLoad` to bring the daemon back after its bootout, so `RunAtLoad=false` would leave a dev rebuild with the daemon down and the script's own `pgrep` verification dying. One writer, one reader.

**Reads.** `status()` shells `launchctl print-disabled gui/<uid>` and parses the label's line. A label with **no** override line is `enabled`, because that is what launchd means by absence, and reading absence as off would make every fresh install's toggle claim the app does not start when it does. A missing plist reads `notInstalled` and calls no launchctl at all. An unreadable `print-disabled` falls back to the plist's own `RunAtLoad` intent **and says so in the footer** ("The switch shows the launch agent's own setting, which may not match"), because presenting an unread state as a confident one is the original bug in miniature.

**Writes.** ON runs `enable`, then `print` to see whether the job is loaded, then `bootstrap` only if it is not; order matters, since bootstrapping a still-disabled service fails. OFF runs `disable` and nothing else. A refused write re-reads launchd and reports what it is actually holding rather than what was asked for, with the launchctl exit status and stderr in the message. `test_neither_direction_ever_uses_a_destructive_verb` pins the whole rule against `bootout` / `unload` / `kill` / `kickstart` / `remove` in both directions.

**The UI is a `@StateObject`, not `@State`.** `LaunchAtLoginModel` holds the status. A `@State` initial-value expression is re-evaluated on every re-render of the enclosing view, and `ConfigStore` publishes on every keystroke in this pane's hotkey fields, so `@State private var x = LaunchAtLoginService().status()` would have meant one `launchctl` subprocess per character typed. `@StateObject` takes an autoclosure SwiftUI calls once per view identity.

**The shell half.** `scripts/lib/login-agent.sh` is a new sourced helper with two functions: `login_agent_disabled_in_output` (a pure text predicate) and `login_agent_disabled` (the launchctl query over it). The split is what made the acceptance's "script-level assertion that install.sh over a disabled agent leaves it disabled" testable without running an installer on the owner's machine: `scripts/test-login-agent-guard.sh` feeds the predicate nine canned cases (the disabled override, an explicit enabled one, an absent label, empty output, a prefix-colliding sibling in both directions, launchctl's spacing, and two truncated lines that must fail *closed*), invokes no launchctl, and mutates nothing. It is now a mandatory gate in the root `CLAUDE.md` verify table, the way `test-prune-worktrees.sh` is.

`install.sh`'s `launchctl load -w` became a plain `bootstrap` inside a disabled guard, and its final "MeetingPipe is running in your menu bar" line is now conditional, because with the agent disabled nothing started it and saying otherwise is the same class of untruth. `rebuild.sh` branches too: with the agent disabled it pkills and `open`s the app directly rather than bootstrapping (which would fail on a disabled service and `die` on a state the owner chose on purpose), and the existing `pgrep` verification covers both paths.

**Cost recorded rather than lost:** dropping SMAppService means MeetingPipe no longer appears under System Settings ▸ General ▸ Login Items, so there is no system-level surface for the switch. That is written into the service's doc comment as worth revisiting in a notarized, Developer-ID world (D8), where SMAppService could own login-start and the agent could shrink to supervision alone. It is not worth two mechanisms today. The label / bundle-id collision was carried unchanged, as the spec directed.

**Noted and deliberately not fixed here:** `uninstall.sh` boots out the agent and removes the plist but never clears the disabled override, so an uninstall followed by a reinstall keeps launch at login off. That is arguably the right behaviour (the override is the owner's stated preference, and it is keyed on the label, not the plist), and "Uninstall behavior" is explicitly out of this task's scope, so it is named here rather than changed.

## Owner walkthrough (for the session that picks this up)

Added 2026-07-31, per the 2026-07-30 standing rule: every task gated on an owner action carries one. Walk the owner through it step by step; the owner does not read code. Steps are tagged [owner] / [session] by who acts. This one needs two real logouts, so it is worth doing in one sitting at the end of a day.

The one command the owner needs, used several times below. It prints what launchd will do at the next login, and it changes nothing:

```sh
launchctl print-disabled gui/$(id -u) | grep meetingpipe
```

1. [session] Precondition: one `./scripts/rebuild.sh`, so the running app is this build. Launch at login should still be ON at this point, so this takes the normal relaunch path.
2. [owner] Open **Preferences ▸ General ▸ Startup** and read the grey text under the two switches. Pass: it talks about a launch agent and about what happens when you quit. If it still says "Registers MeetingPipe with macOS via SMAppService", you are on the old build; redo step 1.
3. [owner] Before touching anything, run the command above. Pass: it prints `"com.meetingpipe.daemon" => enabled`, or prints nothing at all (which also means enabled), matching the switch being on. This is the check that used to fail: the switch and the machine disagreeing is the whole bug.
4. [owner] Turn **Launch at login** OFF. Three things to look at, in order. Pass: (a) MeetingPipe is **still running** in your menu bar, it must not vanish; (b) the grey line under the switch now reads "MeetingPipe only starts when you launch it manually."; (c) the command above now prints `"com.meetingpipe.daemon" => disabled`.
5. [owner] With it still off, run `./scripts/rebuild.sh`. Pass: it says launch at login is off and that it is relaunching the app directly, it finishes without an error, MeetingPipe is running again, and the command above still prints `=> disabled`. (Before this task a rebuild here would have failed outright.)
6. [owner] Still off, run `./scripts/install.sh`. This is the check the acceptance names, and the one that could not be tested from a session without running an installer on your Mac. Pass: near the end it says launch at login is off and the agent is left disabled, the final summary does **not** claim MeetingPipe is running in your menu bar, and the command above still prints `=> disabled`. (You may need to open the app yourself afterwards.)
7. [owner] Log out and log back in. **Pass: MeetingPipe does not start.** This is the original report, in reverse: the toggle now means what it says.
8. [owner] Open MeetingPipe yourself from `~/Applications`. Turn **Launch at login** back ON. Pass: the grey line goes back to "will start automatically when you log in", and the command above prints `=> enabled`.
9. [owner] Log out and log back in again. **Pass: MeetingPipe starts on its own.**
10. [owner] Last one, the crash check, so the fix did not cost the TECH-UX7 safety net. In a terminal: `kill -9 $(pgrep -f "MeetingPipe.app/Contents/MacOS/MeetingPipe")`. Pass: the menu-bar icon comes back within about ten seconds.
11. Steps 3 to 10 passing moves UX42 to done. Worth knowing rather than testing: with launch at login OFF, **Quit MeetingPipe** really quits, because the relaunch-after-quit behaviour is the same launch agent and it is not running the app. That is stated in the Preferences footer, the README, and `docs/SETUP.md`.
