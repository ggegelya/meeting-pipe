# UX42: Launch-at-login toggle truthfulness (one mechanism owns login)

Band origin: filed 2026-07-29 (owner report, item 12: "regardless this toggle checked or not (it is not on my app) app is started at login"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Root cause confirmed 2026-07-29, and it is two mechanisms that have never met:

- **What actually starts the app at login**: the launchd user agent `install.sh` writes at `~/Library/LaunchAgents/com.meetingpipe.daemon.plist` (:483-489 from `scripts/launchd.plist.template`), loaded with `launchctl load -w` (:531) and kickstarted (:539). The template carries `RunAtLoad=true` and `KeepAlive {SuccessfulExit=false}` (template :17-23), and the comment at :14-16 shows both are deliberate design (TECH-UX7: a clean quit exits fully, a crash relaunches). `rebuild.sh:75-88` re-bootstraps the same plist on every dev rebuild, so the agent is continuously refreshed.
- **What the toggle controls**: `LaunchAtLoginService` wraps `SMAppService.mainApp` only (`LaunchAtLoginService.swift:7-9` status-derived read, :17-31 register/unregister with errors swallowed to the log), surfaced in Preferences General (`PreferencesView+General.swift:7`, :93-101) with a footer that says "Registers MeetingPipe with macOS via SMAppService" (:47). Honest about SMAppService; blind to launchd.

Turning the toggle off unregisters an SMAppService entry that was never what launched the app, and leaves the agent armed. Nothing in the app can remove the agent (only `uninstall.sh:70-71` boots it out); `LaunchAgentScheduler`'s digest/backup agents are clean (`StartCalendarInterval` only, no RunAtLoad, and they run `mp`, not the app). The repo even records the split: `docs/backlog/q3-final.md:564`.

One sharp edge to carry: the agent label and the app bundle id are the same string, `com.meetingpipe.daemon` (`install.sh:189`, `Endpoints.swift:6`, template :7), which makes `launchctl print` output and System Settings Login Items entries ambiguous, and makes any dual-registration state (agent + SMAppService both on) look like one entry when it is two.

## Scope

Make exactly one mechanism own login-start, and make the toggle drive it. Recommendation, recorded with the reasoning so pickup does not re-derive it:

**The LaunchAgent owns everything; SMAppService usage is removed.** Reasons: the agent's `KeepAlive` crash-relaunch is deliberate TECH-UX7 design and only supervises agent-started instances, so login-starting via SMAppService would bypass the supervision the product wants; install, rebuild, and uninstall already manage the agent end to end; and two registration systems is the bug this task exists to kill.

- Toggle ON: ensure the plist exists and run `launchctl enable gui/$UID/com.meetingpipe.daemon` (bootstrap if not loaded).
- Toggle OFF: `launchctl disable gui/$UID/com.meetingpipe.daemon`. Disable, not bootout: booting out the agent that owns the running process kills the app under the user's pointer; disable prevents the next login-start and leaves the running instance alone. Decide-and-record whether to also rewrite the plist's `RunAtLoad` to match (belt), noting `launchctl`'s disabled-overrides DB survives plist rewrites either way.
- The toggle's read path reports the real state (`launchctl print-disabled gui/$UID` parsed, or the service's own status query), so the control cannot lie again. Errors surface in the footer instead of being swallowed.
- `install.sh` and `rebuild.sh` respect an existing disabled state: replace `load -w` with a bootstrap that does not force-enable (the `-w` write is exactly what would re-arm a toggled-off install on the next rebuild).
- `LaunchAtLoginService` becomes the wrapper over this (rename or repurpose), with the launchctl invocations behind an injected runner so the state machine is unit-testable. Footer copy updated to name what it really does.
- README and SETUP.md's login/quit semantics paragraphs update in the same commit (DOC10 rule); note for a future D8/notarized world that SMAppService with System Settings visibility could be revisited, so the alternative is recorded, not lost.

## Explicitly not in scope

Renaming the agent label or bundle id (a migration with real breakage risk; the collision is documented here as a known sharp edge instead). Changing TECH-UX7's quit/crash-relaunch semantics. Uninstall behavior. The digest/backup scheduler agents.

## Acceptance

Unit tests over the service with an injected launchctl runner: ON from disabled runs enable (and bootstraps when missing), OFF runs disable and never bootout, state reads reflect the runner's canned print-disabled output, a runner failure surfaces as a user-visible error string.

A script-level assertion (or documented manual step in the PR) that `install.sh` over a disabled agent leaves it disabled.

`cd daemon && swift build` and `swift test` green (baseline at filing: 1770). Repo dash guard green.

Owner eyeball, two halves: toggle OFF, `launchctl print-disabled gui/$(id -u)` lists `"com.meetingpipe.daemon" => disabled`, the running app stays alive, and after the next real login the app has not started; toggle ON and the next login starts it. A crash (kill -9) still relaunches when the toggle is ON.
