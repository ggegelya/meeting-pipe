## Progress (2026-08-03, all three shipped; owner-owed eyeball only)

All three defects are fixed and fenced. `swift build` clean, `swift test` **2039 tests, 0 failures** (10 new in `PreferencesSurfaceTests.swift`); `truth_fences.py both` clean; no em-dashes.

**(a) ScrollViewReader, not `.id()`** (the pick the spec asked to record). `PreferencesView`'s detail pane wraps its `ScrollView` in a `ScrollViewReader`, puts a zero-height `Color.clear.frame(height: 0).id(Self.topAnchor)` at the top of the content, and scrolls to it on `.onChange(of: selectionState.current)`. `.id(selectionState.current)` on the content would also have reset the offset, as a side effect of discarding every pane's own `@State` (a People rename mid-flight, a disclosure just opened), which is a much larger change than "open at the top". The anchor's id is a constant, so the anchor itself re-identifies nothing.

**(b) `contentMinSize`, a wider default, and the control column hugs.** The window's floor is now the SwiftUI root's own declared 780x660, set as `contentMinSize` rather than `minSize`: the latter is frame-space, so 660 there would still have allowed a content box a title bar shorter than the root demands. A test reads both numbers out of the two files and asserts they agree, so the next change to either cannot quietly re-open the gap. The default opening size is **820x660** (owner call, 2026-08-03, the eyeball the spec reserved): the sidebar and the pane's 32pt gutters take about 200 points, so a 780 default offered roughly 515 to content designed to read at 620, and the measure was unreachable until the user resized. The design kit follows, since it recreates the shipped surface (`PreferencesWindow.jsx` and the kit README). `SettingsRow`'s control column takes `.fixedSize(horizontal:vertical:)`, horizontal only, which is exactly what the locked mockup already pinned (`PWRow` in `PreferencesWindow.jsx` carries `flexShrink: 0`) and what the row's own doc comment already claimed; the Swift had shipped without it. One row opts out via the new `controlFills: true`: the Pipeline pane's prompt preview is a scrolling block that wants the remaining width, and a `ScrollView` fixed to its ideal width is a mile of unwrapped prose. Storage, People, and Caches are all covered by the one change, as the spec expected.

**(c) Shape 1** (the recommendation, and the pick recorded here). `PipelineSectionView` holds the picker's selection in `@State localModelSelection`, so Custom is a position the binding can actually hold, and the Model id field writes through a `customModelDraft` rather than straight into the store. Nothing invalid is ever persisted on the way to something valid, which is the reason shape 2 was passed over: its sentinel empty id would have gone through `ConfigStore`'s 500 ms debounced save. The rules themselves are pure statics on `LocalModelPreset` (`id(forModelId:)`, `modelId(forID:)`, `showsModelIdField(forID:)`, `persistableModelId(_:)`), so the whole walkthrough is testable headlessly; the field is revealed for exactly the selections that write nothing on their own, so the two rules cannot drift back into a dead option. Selecting Custom seeds the field with the id currently in force and leaves the store alone; a blank field never reaches `config.toml`, and the Active model row below keeps stating what is actually configured.

**Two coordination notes, from reading the source rather than the spec.** LOCAL16's RAM-tier annotations **do** exist on this picker (`LocalModelTier.rowLabel` / `.isRunnable` at the preset rows, `.annotation` in the sublabel), and they read the preset table rather than the binding, so the two changes compose exactly as the spec predicted. And DIAR3's `SpeakerSeparation` doc comment plus the `speakerSeparationBinding` comment both cited this picker's dead Custom as their worked counter-example; both are rewritten here, since the fix would otherwise have left two comments asserting a bug that no longer exists.

## Context

Three defects, one surface, each verified 2026-07-29.

**(a) Scroll position survives pane switches.** The detail side of the `NavigationSplitView` is one `ScrollView` created outside the pane switch (`PreferencesView.swift:64-72`); `detailContent` is a `@ViewBuilder switch selectionState.current` (:77-109), so only the content changes while the ScrollView's identity (and its backing NSScrollView offset) persists. Scroll to the bottom of Storage, switch to General: General opens at the bottom. No `ScrollViewReader`, `scrollTo`, or `.id(` exists anywhere under `Preferences/` (grep zero).

**(b) The window can be smaller than its own content's floor, and control columns lose the squeeze.** `PreferencesWindow` sets content size 780x660 with `minSize` 720x560 (`PreferencesWindow.swift:45-46`) while the SwiftUI root demands `.frame(minWidth: 780, minHeight: 660)` (`PreferencesView.swift:73`): resizing to the allowed 720 squeezes a hierarchy that declared 780 as its floor. Under squeeze (and even at the default width, where the sidebar + 32pt padding leave ~515pt for a pane designed to 620), `SettingsRow` gives the label column the greedy share (`.frame(maxWidth: .infinity)` at `PreferencesControls.swift:114`) and the control `HStack` no `.layoutPriority` or `.fixedSize` (:116), and `.mpGhost` buttons have no compression resistance of their own, so button text truncates. The reported row is Storage's two-button backup row ("Choose destination..." / "Back up now", `PreferencesView+Storage.swift:188-195`); the same two-ghost-button shape recurs in People ("Rename..." / "Remove", `PreferencesView+Pipeline.swift:132-137`) and Caches (`PreferencesView+Storage.swift:364-382`), so the row-level fix covers all three.

**(c) "Custom" in the Local MLX model picker is a dead branch.** The picker offers three presets plus a hard-coded `Text("Custom").tag(LocalModelPreset.customId)` (`PreferencesView+Pipeline.swift:59-67`). The selection binding's getter derives purely from the stored model id (`currentLocalModelPresetId`, :345-348: known preset id, else custom); the setter explicitly skips the custom tag (:353-358: `if newID != LocalModelPreset.customId ...` writes a preset's model id, else nothing). So clicking Custom writes nothing, SwiftUI re-reads the getter, the picker snaps back to the previous preset, and the dependent "Model id" field, gated on the derived value being custom (:69-76), can never appear. Custom is reachable today only by hand-editing `config.toml` to a non-preset id, exactly the fall-through the preset comment describes (`PreferencesWindow.swift:89-92`).

## Scope

- **(a)** Reset scroll on pane change. Prefer `ScrollViewReader` + a top anchor + `.onChange(of: selectionState.current) { scrollTo(top) }` over `.id(selectionState.current)` (identity reset also tears down pane-local `@State` like the People selection; the reader approach only moves the scroll). Record the pick and why.
- **(b)** Raise `minSize` to match the root's 780x660 (and consider a default of ~820 wide so the 620 design measure is actually reachable; owner-eyeball call). Give `SettingsRow`'s control column `.fixedSize()` (or `.layoutPriority(1)`) so buttons never truncate; one change in `PreferencesControls.swift` covers Storage, People, and Caches.
- **(c)** Make Custom selectable. Two shapes, pick one at pickup and record: (1) an explicit selection `@State` on the pane that decouples the picker from the store (Custom selects immediately, shows the Model id field seeded with the current id, and a valid edited id writes through), or (2) the setter seeds a sentinel (`store.summarizationLocalModel = ""`) so the getter's fall-through fires, with the empty id treated as not-yet-valid (no spawn, inline hint) until the field is filled. Shape 1 avoids ever persisting an invalid id through the 500 ms debounced ConfigStore write and is the recommendation. Coordinate with LOCAL16, which annotates the same picker with RAM tiers; land compatibly (the annotation reads the preset table, not the binding, so no structural conflict is expected).

## Explicitly not in scope
