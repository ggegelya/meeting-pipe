# UX66: a correction overlay and a vocabulary rule that touch the same word fight, and the stale overlay wins silently

Band origin: filed 2026-08-04, found by the owner during FEAT13's and FEAT12's owner walkthroughs on the same day both landed. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The two write paths FEAT13 exists to keep visibly distinct can act on the same word in opposite directions, and nothing reconciles them.

Observed on `20260803-165412`, 2026-08-04. The owner had a per-meeting correction overlay on segment 2 and a workflow-scoped vocabulary term for the same name. After a Re-transcribe the transcript on disk read the rule's version and the screen read the overlay's, so the rule looked broken while working correctly:

- `~/.config/meeting-pipe/glossary.toml` carried `[workflow.Personal.terms] Jorji = "Georgy"`.
- `20260803-165412.json` after the run contained `Georgy` and seven `Max`, and **no `Jorji` anywhere**. The rule applied.
- `20260803-165412.transcript_corrections.json` carried `index 2`, `original_text` "Okay, Georgy. Got it Then you already put two messages for the Max, right? For the frame? Yeah.", `edited_text` "Okay, Jorji. Got it ...".
- `TranscriptCorrectionStore.apply` (`TranscriptCorrectionStore.swift:110-122`) overlays `editedText` at load, so the pane rendered `Jorji`.

The owner's report was "Jorji remains old, but Macs is fine". `Macs` had no overlay on its lines, so the rule showed through; the name did, so it did not.

**The carry already knows this hazard exists and cannot see this instance of it.** `TranscriptOverlayCarry.carry` retires a correction the new transcript already satisfies (`TranscriptOverlayCarry.swift:166-169`, `if target.text == correction.editedText { result.retired += 1 }`), whose doc comment is exactly right about why: "the ratchet subsumed the fix, and keeping a no-op override would only make the next diff harder to read." That test asks whether the transcript moved **toward** `editedText`. It has no test for the transcript having moved **away** from it under a rule the owner also authored. So the overlay is carried rather than retired, and `originalText` is re-snapshotted to the new text (`:175`, `originalText: target.text`) for a good reason of its own (the sidecar should describe what the pipeline produced, not a sentence that no longer exists). The combined effect is that a stale overlay comes out of a Re-transcribe looking freshly authored against the current transcript, asserting the opposite of the rule, with nothing on screen saying so.

Two properties make it worse than a one-off confusion. It is **permanent**: every later load re-applies it, and every later Re-transcribe re-anchors and re-snapshots it again, so it never decays. And it is **silent**: the Re-transcribe report counts carried, dropped and retired, and this correction is counted as carried, which reads as success.

Not a regression. Both halves are new (FEAT13 2026-08-04, FEAT12 2026-08-03) and each is correct alone; the interaction is what nobody owned. Overlay-beats-rule is also the right precedence and is not what this task disputes: a per-meeting manual fix should outrank a global rule. What is wrong is that the loser is invisible.

## Scope

Detect at carry time that a correction now contradicts a vocabulary rule, and tell the owner rather than resolving it silently.

The seam is `TranscriptOverlayCarry.carry`, beside the existing retire test at `TranscriptOverlayCarry.swift:166`, which is pure and already has the old text, the new text and the edited text in hand. The missing input is the glossary, so the decision needs the terms in scope for the meeting's workflow passed in; keeping the function pure means passing them as a parameter rather than reading the file there.

The test to add is the mirror of the retire test: a correction whose `editedText` contains a term's **key** where the new transcript contains that term's **value** at the same segment is a contradiction, not a carry. Count those separately from `carried`, and surface the count in the Re-transcribe report the way `dropped` already is, so "3 edits carried, 1 now disagrees with a vocabulary rule" is what the owner reads.

Whether a contradicting correction is then kept, dropped, or offered as a choice is the one open decision. Keeping it preserves overlay-beats-rule and needs only the report line; dropping it silently discards the owner's typing and should not be done without asking.

## Explicitly not / out of scope

**Not changing overlay-beats-rule precedence.** A per-meeting fix outranking a global rule is correct and is what FEAT13's two blast radii are built on. This task makes the conflict legible, it does not invert the winner.

**Not the `originalText` re-snapshot** (`:175`). Its reasoning holds: a sidecar pointing at a sentence that no longer exists is worse. The re-snapshot is what makes a stale overlay *look* fresh, but removing it would trade one confusion for another.

**Not fuzzy matching.** `[fuzzy]` is off in the owner's config and the substitution is `\b(<key>)\b` on both sides (FEAT13 pinned `Clarify.substitute` to mirror `mp.glossary` exactly, `c++` limitation included). A contradiction test built on the same literal rule inherits the same limits, deliberately.

**Not the several-garbles-per-name problem, observed in the same session and worth its own row if it recurs:** the same meeting also read `Georgi` at segment 6, a different misspelling of the same name that the `Jorji` term cannot touch, because a rule fixes the exact spelling it names. That is a vocabulary-coverage question, not a conflict question.

**Not retroactive repair.** How many correction sidecars in the library already contradict a live rule is unmeasured. Cheap to count if the pickup session wants to (`~/Documents/Meetings/raw/*.transcript_corrections.json` against `glossary.toml`); record the number here rather than acting on it.

## Acceptance

`cd daemon && swift build` clean and `swift test` green, with new tests (leave the count to the session that writes them; do not pin an absolute suite total).

The contradiction test is pure and pinned directly in `TranscriptOverlayCarryTests`, with four cases named on their scenario rather than their mechanism: a correction the new transcript already satisfies still **retires** (the existing behaviour must not regress); a correction contradicting a term in scope is counted as a contradiction and not as a plain carry; a correction untouched by any term still carries; and a term scoped to a different workflow does not count as a contradiction for this meeting.

The Re-transcribe report names the contradiction count when it is non-zero, and says nothing extra when it is zero. Pin it on the outcome value, not on a rendered string.

The `20260803-165412` case is pinned as a regression fixture from the real data in Context: glossary `Jorji = "Georgy"`, new segment text "Okay, Georgy. …", edited text "Okay, Jorji. …" reads as a contradiction.

`python3 scripts/truth_fences.py both` green. No em-dashes in changed lines.
