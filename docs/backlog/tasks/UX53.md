# UX53: Sweep every operation for whether the open view learns it happened

Band origin: filed 2026-07-31 at the owner's explicit request, so it would not be lost: "this is not the first issue, I need full assessment all over the app for this", said on discovering that a finished re-transcribe leaves the transcript on screen unchanged. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

UX52 records one instance: `MeetingLibraryService.retranscribeMeeting` completes, logs `retranscribe_done`, and bumps nothing, so the open detail view keeps rendering the previous transcript until the user switches tabs. The owner's point is that the instance is not the problem. A missing refresh is a defect class, and finding the rest by waiting for the owner to trip over them is the slow way.

**The reason this class hides is structural and worth stating up front, because it shapes the sweep.** The Library's centre column is an `if/else` on `scope`, so switching tabs or rails destroys the projection view and rebuilds it from disk. That means *any* operation that fails to publish a change still looks correct the moment the user navigates anywhere, and navigating is the natural thing to do while waiting. A user learns the workaround without noticing they learned it, so these bugs are under-reported rather than rare. The same property is documented in `daemon/CLAUDE.md` as the reason run state must not live in that view (UX37's Ask incident), which is the same structural fact biting from the other side.

There is also a known-good side to copy from: several operations do refresh correctly today (rename, enroll, reassign, regenerate), so the right idiom exists in this codebase and the sweep is looking for paths that skipped it, not for a mechanism to invent.

## Scope

Enumerate every operation that mutates a meeting's on-disk state, and for each determine whether an open detail view (and the row in the list) reflects the change without navigation. This is `/audit`-shaped work: parallel passes over the surfaces, adversarial verification of anything claimed broken, then filing.

The list to start from, to be completed rather than treated as exhaustive: re-transcribe (known stale, UX52), regenerate / re-summarize, republish, speaker rename, speaker un-name, enroll to roster, workflow reassign, transcript line correction (PIPE9), action item resolved / reopened, evidence-bearing summary rewrite, trash / delete, retention sweep and reaper deletions, glossary change, and anything writing a sidecar the detail view reads.

For each, record the observed behaviour rather than the intended one, and separate three outcomes: refreshes correctly, does not refresh, or refreshes only partially (the transcript updates but the cast strip does not, and similar). Partial refresh is the most likely shape here, because a re-transcribe changes the text, the speaker clusters, and the header lines, and a fix that publishes one of those is easy to mistake for a fix.

Fix the trivial ones in place where the working idiom applies directly; file anything with a real design question rather than growing this task without limit.

## Explicitly not / out of scope

**Not UX52.** That instance has its own task and its own owner walkthrough; this sweep must not absorb it, and if UX52 lands first this sweep verifies it rather than redoing it.

**Not a rearchitecture of the Library's view lifecycle.** The `if/else` on `scope` is deliberate and load-bearing; this task adds refresh signals where they are missing, it does not change how views are torn down.

**Not non-meeting surfaces** (Preferences, Diagnostics, the status-bar menu) unless a pass finds the same class there, in which case name it rather than fixing it here.

**Not performance.** Whether a refresh is efficient is a separate question from whether it happens.

## Acceptance

A table in this spec listing every enumerated operation against its observed refresh behaviour, with the three outcomes distinguished and the partial ones saying which part went stale. No operation is left as "probably fine": an unchecked row is an unfinished sweep, and saying so is the point of writing the table down.

Every stale operation is either fixed in the same pass or filed with its own row, and the filings are listed here so the sweep's coverage can be read after it closes.

Where fixes land: `cd daemon && swift build` and `swift test` green, and each fix pins its notification at the service level rather than asserting on rendering, matching UX52's acceptance.

No em-dashes in changed lines.

## Owner walkthrough (for the session that picks this up)

Per the 2026-07-30 standing rule. Steps are tagged [owner] / [session] by who acts. Most of this is a session job; the owner's part is confirming the fixes and, more usefully, saying which stale surfaces actually annoy them.

1. [session] Run the sweep and produce the table before changing anything, so coverage is legible and the owner can see what was checked.
2. [owner] Read the list of stale operations and say which ones you have already hit in normal use. That ordering matters more than severity guessed from code: a surface you never look at after an operation costs nothing, and one you always look at costs every time.
3. [session] Fix in that order, then hand back the checks.
4. [owner] For each fix, do the operation with the view open and **do not navigate**. Pass: the screen updates on its own. Not navigating is the entire test, since navigation has always worked and is what hid every one of these.
5. [owner] Say "UX53 good to close" (or what is still stale); [session] moves the row and the spec into `q6-final.md` and deletes this file.
