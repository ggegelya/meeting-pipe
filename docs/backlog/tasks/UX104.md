# UX104: Play gives no feedback until the audio engine starts, and a Play before the Audio tab's waveform loads is silently dropped

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source findings: P021 and P030 in the [responsiveness audit](../../audits/2026-11-13-responsiveness-audit.md) (ranked fix 5, "publish the intent at the click"), both low, both present in the two field builds and at HEAD. Re-verified in code at HEAD `3a2da4fc` on 2026-11-13. No field measurement exists: playback logs nothing, so the audit's only proxy is the recorder's input engine start on the work laptop (74 starts: median 62 ms, p90 192 ms, max 1503 ms), and an output start on a Bluetooth route is expected to sit at the slow end.

**P021, the glyph flips on completion.** `AudioPlaybackController.startPlayback(from:)` sets `wantsPlayback = true`, `currentTime = t` and enqueues the engine work; only inside that work, after `engineCall(site: "connect", ...)`, `engineCall(site: "player_stop", ...)`, `anchor(at:)` and `boundedEngineStart(seconds: startBudget)` return `.started`, does it set `isPlaying = true`. The property's own doc says so: "False while a start is still in flight." All three Play surfaces read `isPlaying` for their glyph (the Audio tab's `transportControls`, `Image(systemName: playback.isPlaying ? "pause.fill" : "play.fill")`; the Transcript playback bar; the header's `DetailTransport`), so each shows Play over a start that is already under way. PERF21 made the wait recur: a pause arms `armIdleStop()` and `idleStopGraceSeconds = 3.0` later the engine is stopped, so a Play more than 3 s after a pause pays the start again.

**A second press during the start is dropped too (found at filing).** `togglePlayPause()` is `if isPlaying { pause() } else { play() }`, and `play()` returns at `guard audioFile != nil, !wantsPlayback`. So a user who sees no change and presses again, meaning Pause, gets nothing; the start completes and audio begins after the press that tried to stop it.

**P030, a Play before the waveform is discarded.** `AudioTab.body` runs `.task(id: meeting.stem) { await reload(); if let audio = meeting.audioURL { playback.load(url: audio) } }`, so `load` waits for the waveform peaks (a few ms on a peaks-cache hit, a full decode on a miss). The footer with the Play button and its `.keyboardShortcut(.space, modifiers: [])` sits outside the `content` switch, so it is live while `ProgressView("Loading waveform…")` shows. Two outcomes:

- No file loaded yet (first audio tab of the session): `play()` returns at `audioFile != nil`, so the press is dropped with nothing on screen.
- Correction at filing, sharper than the audit's "discarded": after a meeting switch, `MeetingDetailView`'s `.onChange(of: meeting.stem)` only calls `playback.pause()` (UX78), so the controller still holds the previous meeting's `AVAudioFile`. A Play or Space during the new meeting's waveform load plays the meeting the user just left, under the new meeting's title. The header transport is safe (`DetailTransport.decide` guards `loaded == expected`); the Audio tab footer has no such guard. The Transcript tab is not affected the same way, since its audio `.task` calls `load` without awaiting anything first.

Related: [PERF21](./PERF21.md) (owner-verify, owns the engine lifetime and the 3 s idle stop), [UX78](./UX78.md) (partial, the per-meeting pause and the header transport), [PERF12](./PERF12.md) (the 15 Hz re-render while playing), [OBS7](./OBS7.md) (filed in this band, `ui_action` and `ui_feedback` events this task should use for Play).

## Scope

1. **Publish the intent at the click.** Add a published `isStarting` (or publish `wantsPlayback` read-only) on `AudioPlaybackController`, set in `startPlayback(from:)` before the work is enqueued and cleared where `isPlaying` becomes true, in `failPlayback`, in `pause()` and in `load(url:)`/`teardown()`. The three Play surfaces draw Pause when `isPlaying || isStarting`, and a failed start reverts the glyph through `failPlayback`, so the control never shows Pause over silence. `togglePlayPause()` branches on the same intent (`wantsPlayback ? pause() : play()`), so a press during a start cancels it; `pause()` already handles a start in flight through the epoch.
2. **Load before the waveform.** In `AudioTab`'s `.task(id: meeting.stem)`, call `playback.load(url:)` before `await reload()`. `load` is a synchronous `AVAudioFile(forReading:)` open plus model state, not an engine call, so it adds no wait to the waveform.
3. **No Play over a file that is not this meeting's.** Disable the Audio tab's Play button and its Space shortcut while `playback.loadedURL != meeting.audioURL`, the same predicate `DetailTransport.decide` uses for the header.
4. Optional, decided by the pickup session against PERF21's rules: keep the engine warm while a detail pane with audio is visible rather than for a flat 3 s, only if PERF21's owner walkthrough does not object; otherwise leave the idle stop alone and rely on item 1 for feedback.

## Explicitly not

- Changing PERF21's engine chain, its bounded calls or its retire-on-timeout rule.
- Unloading the file on a meeting switch to a meeting without audio, or on Summary: UX78's remainder.
- The 15 Hz detail re-render: [PERF12](./PERF12.md).
- Instrumentation beyond the one `ui_action` mark per Play surface that [OBS7](./OBS7.md) defines.

## Acceptance

- `AudioPlaybackControllerTests`: with a fake engine whose `start` blocks until released, `isStarting` (or the published intent) is true synchronously after `play()` returns and `isPlaying` is false; after release `isPlaying` is true and `isStarting` false; with a start that fails or times out, both are false and `loadError` is set; a `togglePlayPause()` during the blocked start leaves the player not playing once the start returns.
- A view-model or pure test over the Audio tab's Play enablement: disabled when `loadedURL` is nil or another meeting's URL, enabled when it equals `meeting.audioURL`.
- A test that the Audio tab's load order puts `playback.load(url:)` before the waveform reload (a seam that records the order, or the task body lifted into a testable function), so a Play issued while the waveform is still loading starts this meeting's audio.
- `cd daemon && swift build` and `swift test` green, with the number of new tests in the commit body; `bash scripts/ci-local.sh` green.
- `docs/GUIDE.md`'s playback recipe updated in the same commit only if its wording about the Play control changes.
