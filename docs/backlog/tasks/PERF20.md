# PERF20: The Library search index is wiped at every launch and rebuilt with one full-table scan per meeting, and every search keystroke queries it synchronously on main

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Verified in code on 2026-10-25 against `01e904a` (review findings LIBRARY-1 and LIBRARY-6, both confirmed by the verifier). They are one task because their fixes share one `SearchIndex` schema bump, which costs every install exactly one rebuild.

**The launch-time wipe.** `Coordinator.init` builds `SearchIndexer(store: libraryModel.meetingStore)`, and `SearchIndexer.init` subscribes with `cancellable = store.$revision.receive(on: DispatchQueue.main).sink { ... let snapshot = store.meetings; self.indexQueue.async { self.reconcile(snapshot) } }`. A `@Published` projected publisher delivers its current value on subscribe, so the sink runs once with `revision == 0` while `MeetingStore.meetings` is still its initial `[]`. Nothing scans at launch: the only callers of `MeetingStore.start()` and `refresh()` are `LibraryRootView`'s `onAppear`, `QuickFindModel.refresh()` and the `refreshLibrary` closure `Coordinator` hands `MeetingLibraryService`. `SearchIndexReconciler.decide(indexed:live:)` then returns `.delete(stem:)` for every indexed stem (`for stem in indexed.keys.sorted() where !liveStems.contains(stem)`), and `reconcile` applies them. The code's own intent says the opposite: `SearchIndexReconciler.Entry.sig` is documented "Stable across launches, unlike a `hashValue`, so a relaunch does not reindex the whole library", and the comment above the subscription assumes "`revision` bumps on the first scan too, so the initial build rides the same path". A scan whose directory listing fails wipes the index the same way, because `MeetingStore.performScan(directory:)` returns `[]` from `guard let entries = try? fm.contentsOfDirectory(...) else { scanCache.removeAll(); return [] }` (the unreadable-folder case STOR11, 2026-10-25 observability band, makes visible). Present since UX16 (`90e1ed3d`, 2026-07-12): `git log` shows the subscription unchanged since, so this is a defect present at ship, not a regression.

**What this Mac shows, 2026-10-25.** `sqlite3 -readonly` on `~/Library/Caches/MeetingPipe/search/index.sqlite` returns 0 rows in `docs` and in `doc_meta` (`user_version` 1), while `~/Documents/Meetings/raw` holds 9 stems, each with a `<stem>.md` transcript. The files were written at 2026-10-18T11:59:58Z, two seconds after the running daemon (pid 77137) started; a one-page main file and a 10-frame WAL (41,232 bytes) read as a freshly created schema rather than deleted rows, so the wipe itself is code-verified, not observed here. What is observed is the other half: no scan has populated the index in that process's seven days, and `DoctorCommand.probeSearchIndex()` returned `status: .ok` with "FTS index reachable; 0 meetings indexed." on all 19 `search.index` probes in `events.jsonl` on 2026-10-24. The probe never compares the count with the library.

**The rebuild is quadratic.** On the first Library or Quick Find open the scan re-upserts every meeting. `SearchIndex.upsert(stem:sig:body:)` runs `BEGIN; DELETE FROM docs WHERE stem = ?; INSERT INTO docs(stem, body) ...; INSERT OR REPLACE INTO doc_meta ...; COMMIT;` per stem, even for a stem that was never indexed, and `SearchIndex.delete(stem:)` runs the same DELETE. The table is `fts5(stem UNINDEXED, body, tokenize='unicode61')`; FTS5 plans only `MATCH` and `rowid` constraints, so `WHERE stem = ?` scans the whole table once per call. N meetings cost N full-table scans plus N separately committed transactions at the launch wipe and again at the rebuild, plus one read of every `<stem>.md`. Not measured; at the work library's size (about 434 meetings, PERF9, 2026-10-23) that is about 434 scans of up to 434 rows and 434 commits after every relaunch, growing quadratically. `SearchIndex.search(_:)` takes the same serial `queue` with `queue.sync` from main, so a keystroke during the rebuild waits behind whichever DELETE scan is running.

**The health signal says ready too early.** `reconcile` ends with `if self.health != .degraded { self.health = .ready }` after any pass, including the empty one, so UX23's `.building` state (`SearchIndexer.searchHint(for:)`, "Indexing transcripts…") is gone before the real rebuild starts, and transcript-only matches are silently missing from both search surfaces until it ends. UX16's union with the in-memory corpus keeps title and summary hits, so the loss is transcript text only.

**Every keystroke searches on main.** `FilterBarView` binds `TextField("Search titles, summaries, decisions…", text: $filter.query)` directly, `LibraryListView` runs `.onChange(of: filter) { _, _ in recomputeDerived() }`, and `recomputeDerived` calls `libraryModel.matchingStems(filter.query)` on main; `QuickFindModel`'s `@Published var query` has `didSet { recomputeMatches() }`. Neither is debounced. `SearchQuery.ftsMatch(_:)` turns every token into a prefix term (`"\($0.lowercased())*"`) and the table has no `prefix=` option, so a one-letter query merges the doclists of every term starting with that letter; `SearchIndex.search` orders the result with `ORDER BY rank` (bm25 over every match) and `SearchIndexer.matchingStems(_:)` discards the order with `Set(index.search(match))`. `LibraryRootView.recomputeCounts()` also runs every saved search's FTS query on main per revision. The verifier put the cost at tens of ms per key at today's library and hundreds at thousands of meetings.

**The ranker's word-boundary boost is unreachable.** `QuickFindRanker.scoreField(query:haystack:weight:)` returns on `hay.hasPrefix(q)`, then on `hay.contains(q)`, and only after both fail runs `for sep: Character in [" ", "\n", "(", "[", "-"] { if hay.contains(String(sep) + q) { return weight * 1.2 } }`, which cannot succeed once `contains(q)` has failed. A non-matching field costs seven passes over its haystack per keystroke, and a word-boundary match never gets its 1.2x weight. `QuickFindRankerTests` asserts no 1.2x value (grep, 2026-10-25).

## Scope

The seams are `SearchIndexer.init` / `reconcile(_:)` and `SearchIndex.prepareSchema()` / `upsert` / `delete` / `search` for the index, and `LibraryListView.recomputeDerived()`, `LibraryRootView.recomputeCounts()`, `QuickFindModel.recomputeMatches()` and `QuickFindRanker.scoreField` for the query path.

1. **Reconcile only a store that has scanned.** The `$revision` sink returns while `store.hasLoadedOnce` is false. `refresh()` sets `hasLoadedOnce` in the same main-queue block as the first real `revision` bump, so the `.receive(on:)` delivery after it sees it true. A bare `dropFirst()` is not enough, since it leaves item 2's case.
2. **Never wipe on an empty live set the scan did not confirm.** A reconcile whose live set is empty while the index is not is skipped unless the store's last scan listed a readable, empty directory. `MeetingStore` exposes that fact: STOR11's root state if it has landed, otherwise a flag `performScan` sets when its listing succeeded. Stale rows are harmless meanwhile, because both search surfaces intersect FTS hits with the in-memory meetings.
3. **Delete by rowid, and not at all for a new stem.** `doc_meta` gains the FTS `rowid` of each stem's document; `delete` and the delete half of `upsert` use `DELETE FROM docs WHERE rowid = ?`; `upsert` skips the delete when `doc_meta` has no row for the stem. `SearchIndex.schemaVersion` goes from 1 to 2, which `prepareSchema` already turns into a drop and rebuild.
4. **Batch the rebuild's writes.** `reconcile` groups its upserts into transactions of a bounded size (a named constant around 50, its reason in a comment), not one per stem and not one for the whole library, because `search` waits on the same queue from main.
5. **Honest health.** `health` stays `.building` until the first reconcile against a loaded store completes, so the UX23 hint shows during a real rebuild. `DoctorCommand.probeSearchIndex()` reports `.warn` when the index holds fewer stems than the library has `<stem>.md` transcripts, naming both counts, instead of `.ok` with "0 meetings indexed".
6. **The query path.** In the same schema bump, add `prefix='2 3'` to the FTS5 table. Drop `ORDER BY rank` from `SearchIndex.search` (both callers use a `Set`). Skip the FTS lookup for a one-character query (the in-memory corpus still answers it). Debounce the Library filter's and Quick Find's free-text query by 150 to 250 ms, one named constant shared by both, and run the FTS lookup off main, applying a result only if the query it was computed for is still current. Saved-search counts in `recomputeCounts` take the same off-main lookup.
7. **The ranker.** Either move the word-boundary check inside the `contains(q)` success branch, so the intended boost is reachable, or delete the loop; say which in the commit body and pin it with a ranker test either way. Lowercase the title haystack once per scan instead of per keystroke in `QuickFindRanker`'s `"title"` field.

Read `docs/GUIDE.md`'s search recipe before shipping and update it in the same commit if it describes the hint or search-as-you-type timing.

## Explicitly not

- The unreadable-library surface, its doctor probe and its watcher retry: STOR11 (2026-10-25 observability band). Item 2 only reads the state STOR11 introduces.
- One transaction for the whole rebuild: rejected, since `search` is a `queue.sync` from main and typing would stall behind it.
- Moving the index off SQLite, or changing what `SearchIndexer.documentBody(for:)` indexes.
- `MeetingStore`'s watcher re-armed by Quick Find and its no-op revision bumps, which cause extra reconciles: the MeetingStore task filed beside this one from the same review.
- PERF9's list-rendering cost, which `recomputeDerived`'s output feeds; PERF9 owns `listBody` and `MeetingRow`.
- The Python semantic index (`mp.embed_index`) and its staleness after a delete: STOR7.

## Acceptance

- `SearchIndexerTests`: an indexer attached to a store that has not scanned leaves a pre-populated index untouched (fails on `main`, where every row is deleted); a store whose scan reported a listing failure does not empty the index; a store that scanned a readable empty directory does; health is `.building` until the first loaded reconcile and `.ready` after it.
- `SearchIndexTests`: a schema-1 file opened by the new code is dropped and rebuilt at version 2; `upsert` of a new stem issues no DELETE and of an existing stem removes only that stem's row (pinned by row counts or a statement-count seam, not timing); a one- and two-letter prefix query still matches after `prefix=`; `search` returns the same stem set as before over a fixture library.
- A reconcile over N new stems commits in ceil(N / batch) transactions (counting seam).
- `DoctorCommandTests`: `probeSearchIndex()` is `.warn` for an empty index beside a library with transcripts and `.ok` when the counts match.
- Query path: a burst of keystrokes inside the debounce window issues one FTS lookup; a result computed for a superseded query is discarded; a one-character query issues none.
- `QuickFindRankerTests`: the word-boundary case scores as the chosen design says.
- `cd daemon && swift build` and `swift test` green, with the number of new tests in the commit body; `bash scripts/ci-local.sh` green.
- Evidence (confirms, does not gate): after an install and a relaunch with no recording running, `sqlite3 -readonly ~/Library/Caches/MeetingPipe/search/index.sqlite "select count(*) from doc_meta"` still equals the indexed stem count before the Library is opened, and doctor's `search.index` row agrees.
