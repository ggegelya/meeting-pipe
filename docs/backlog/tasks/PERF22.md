# PERF22: Quick Find leaves the library watcher attached for the life of the process, every launch's first scan parses every transcript for its length, and every rescan republishes even when nothing changed

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Verified in code on 2026-10-25 against `01e904a`. Five review findings, all in `MeetingStore`'s `start()` / `stop()` / `refresh()` / `buildMeeting` and Quick Find's one caller: LIBRARY-3 and UI-5 (the same watcher defect from two finders), PERSISTENCE-7, LIBRARY-5 and LIBRARY-9.

**Quick Find re-arms the watcher and nothing stops it.** `LibraryRootView`'s `.onDisappear` calls `meetingStore.stop()`, with the comment "without this a closed Library would keep rescanning on every pipeline write". `QuickFindWindow.show()` calls `model.refresh()` on every Cmd+K, and `QuickFindModel.refresh()` is `meetingStore.start(); selectedIndex = 0; recomputeMatches()`; `QuickFindWindow.hide()` is `panel?.orderOut(nil)`, the panel has `hidesOnDeactivate = true`, and the Library's `onDisappear` is the only `stop()` caller. The store is shared (`Coordinator` passes `libraryModel.meetingStore`). So after one Cmd+K with the Library closed the watcher stays attached until the Library is next opened and closed. Each create, rename or delete in the recordings directory (atomic writes rename, and a pipeline run writes dozens of files) then runs a debounced `refresh()`: a full `performScan` (cheap for cached rows), a main-queue publish of the whole array, a `SearchIndexer` reconcile (two `resourceValues` stats per meeting in `signature(for:)` plus a `SELECT` of every signature), and Quick Find's `meetingStore.objectWillChange.receive(on: DispatchQueue.main).sink { [weak self] in self?.recomputeMatches() }` twice per scan, once for `meetings` and once for `revision`, each re-ranking the whole library and running an FTS query for the last typed query into a hidden panel. The verifier rated it a few ms of main per pipeline run: real, minor, and a defeat of the Library's documented intent.

**The cancel handler closes the wrong descriptor.** `attachWatcher()` sets `watcherFD = fd` on main and installs `src.setCancelHandler { [weak self] in guard let self = self else { close(fd); return }; if self.watcherFD >= 0 { close(self.watcherFD); self.watcherFD = -1 } }`, which closes the current descriptor, not its own. `stop()` calls `detachWatcher()`, which cancels and nils `watcher` at once, while the cancel handler runs later on `scanQueue`, behind any in-flight `performScan`. A `start()` inside that window opens fd2; the old handler then closes fd2, so the new source watches a closed descriptor and the Library silently stops auto-refreshing until the next stop and start, and fd1 leaks. `watcherFD` is also written from main and from `scanQueue` with no synchronization. Reaching it needs a stop and a start within one scan's duration (the Library closing and Quick Find opening, or a SwiftUI disappear and appear pair), so it is rare; its five uses are all in `attachWatcher`.

**The first scan of every launch parses every transcript for one number.** `scanCache` is in memory only (`private var scanCache: [String: CacheEntry] = [:]`), so each process builds every row once. `buildMeeting` calls `MeetingStore.duration(audio:transcriptJSON:startedAt:)`, which since UX74 (shipped 2026-08-18, row `partial` on its owner walkthrough) tries the transcript's `audio_seconds` first: `transcriptJSON.flatMap({ readJSON(at: $0) }).flatMap({ $0["audio_seconds"] as? Double })`, a `JSONSerialization` parse of the whole word-level `<stem>.json` for one top-level key. Before UX74 a row with audio stat'ed the file instead, so UX74 moved the cold scan from a stat per row to a full transcript parse per row; its values are right and are not in question here. Measured on this Mac on 2026-10-25: 9 transcripts, mean 260 KB, largest 1.0 MB. At that mean the work library's 434 meetings (PERF9, 2026-10-23) is about 110 MB of JSON per launch, parsed on the scan queue while `LibraryListView` shows its `hasLoadedOnce` spinner and Quick Find shows nothing. Rows that are never cached rebuild on every scan: an age-inferred `.failed` row (`age > Meeting.staleProcessingThresholdSec`, `cacheable = false`) re-parses its transcript and, because `failure?.stage != .transcribe` is true when `failure` is nil, also runs `MeetingLibraryService.hasReusableTranscript(stem:in:)` (an `.md` read plus a second parse) for the rest of the process, although past the threshold its status cannot change with age.

**Every rescan republishes.** `refresh()` ends `self.meetings = result; self.revision &+= 1` unconditionally, so a rescan that found nothing new (a Library re-open's `start()`, a Quick Find open, the `pendingRescan` follow-up) wakes every revision consumer. On main, `ScopeCounts.build` calls `LibraryScope.includes(_:workflows:now:)` for 6 scopes per meeting, each computing `Calendar.current.startOfDay(for: now)` or `Calendar.current.date(byAdding: .day, value: -7, to: now)` inside the loop, plus `workflows.first(where:)` per meeting, and `MeetingGroup.group(_:now:)` runs two `dateComponents` and a `MeetingFormatters.monthYear.string(from: ts)` per meeting older than this month. The verifier put it at 10 to 40 ms of main per revision at 2000 meetings, less today.

**The constraint on any no-op skip.** `revision` is also the "a file changed" signal: `TranscriptTab`'s `TranscriptReloadKey(stem:revision:)` (UX52), `SummaryTab`'s `SummaryReloadKey`, `MeetingDetailView`'s `PublishURLsReloadKey` and `SearchIndexer`'s mtime signatures all need a bump after a write that may change no `Meeting` field, such as a re-transcribe rewriting `<stem>.json` and `<stem>.md` or an overlay write. A skip that compares `Meeting` values alone, which the review suggested, would silently break UX52's refresh.

## Scope

The seam is `MeetingStore` (`attachWatcher()`, `refresh()`, `performScan(directory:)`, `duration(audio:transcriptJSON:startedAt:)`, `buildMeeting`) plus `QuickFindModel.refresh()` and its sink, and `ScopeCounts.build` / `MeetingGroup.group` for the date work.

1. **Quick Find does not own the watcher.** `QuickFindModel.refresh()` calls `meetingStore.refresh()`, a one-shot scan that keeps the open-time freshness it relies on, instead of `start()`. Its sink observes `meetingStore.$revision` (one event per scan) instead of `objectWillChange`, and does not recompute while the panel is hidden; `show()` recomputes. The query is not cleared on hide, which would be a behaviour change nobody asked for. Reference-counting `start` and `stop` is rejected: more machinery than one extra caller needs, and a duplicated `onDisappear` would underflow it.
2. **The cancel handler closes its own descriptor.** `src.setCancelHandler { close(fd) }`, and `watcherFD` is deleted.
3. **Durations survive a relaunch.** A small rebuildable cache under `~/Library/Caches/MeetingPipe/` (the search index and waveform cache precedent, ADR 0003) maps a stem to its duration plus the transcript's and the audio's mtime and size it was computed from. It is loaded at `MeetingStore.init` and written off main after a scan that changed it. `MeetingStore.duration` consults it first and computes as today, in UX74's order, only on a miss or a changed file. Rejected: reading the audio header first, which reorders UX74's precedence while its walkthrough is open and, on an iCloud-synced library, materializes an evicted recording whole during a scan (STOR6 keeps scan reads to small sidecars); and writing `audio_seconds` into `meta.json`, a cross-tree sidecar contract change for a cache problem.
4. **An aged failed row is cached.** An age-inferred `.failed` row is cacheable once past `Meeting.staleProcessingThresholdSec`, since after that only a file change, which changes its signature, can change it. If [ARCH20](./ARCH20.md)'s `MeetingStatus.decide` has landed this is one row of its table; if not, ARCH20 inherits it.
5. **Skip a publish that changes nothing.** On `scanQueue`, before the main hop, `refresh()` compares the scan's per-stem signatures (the `signature(of:)` maps `performScan` already builds, plus the edited-stems overlay) and the final rows with the last published ones, and skips `meetings =` and `revision &+= 1` only when both are identical. `hasLoadedOnce` and the `pendingRescan` follow-up still run. Comparing signatures as well as rows is what keeps UX52's reload key and the other file-change consumers firing on a write that changes no `Meeting` field.
6. **Hoist the date work.** `ScopeCounts.build` computes its scope cutoffs once per build and passes them into the check, and `MeetingGroup.group` caches month titles by (year, month).

## Explicitly not

- [PERF8](./PERF8.md)'s own-write suppression (item 2) and per-stem change signal (item 4). Item 5 here does not suppress a write the app made, because that write changes a signature.
- [ARCH15](./ARCH15.md)'s `@Observable` migration of `MeetingStore`. Item 1's `$revision` sink stays valid either way.
- [ARCH20](./ARCH20.md)'s status-ladder refactor, which keeps behaviour unchanged; item 4 is a one-row cacheability change, coordinated as stated. UX74 owns the duration order and its tests, which item 3 leaves untouched.
- STOR11 (2026-10-25 observability band), which also edits `attachWatcher` for an unreadable root: whichever lands second rebases.
- Persisting the whole scan cache (every `Meeting`): more than the measured cost needs; the duration is the only expensive field.
- The search index's own launch wipe and query cost: the search task filed beside this one from the same review.

## Acceptance

- `QuickFindModel` tests: `refresh()` scans without attaching the watcher (a store seam reports whether it is watching), so after a Quick Find open with the Library closed a write into the directory triggers no rescan; one store revision produces one recompute; no recompute while hidden; `show()` recomputes.
- `MeetingStoreTests`: a stop followed at once by a start, with a scan held in flight, leaves the new watcher live (a write after it triggers a rescan) and closes the old descriptor (fails on `main`).
- `MeetingStoreTests`: a second `MeetingStore` over the same fixture with a warm duration cache returns identical `durationSec` values and parses no `<stem>.json` (counting seam on the transcript reader); a changed transcript mtime invalidates that entry only; every UX74 duration test (`test_duration_prefers_transcript_audio_seconds_over_a_touched_wav_mtime` and its siblings) passes unchanged.
- `MeetingStoreTests`: an age-inferred `.failed` row past the threshold is served from the cache on the next scan, with no `hasReusableTranscript` call.
- `MeetingStoreTests`: `refresh()` over an unchanged directory does not bump `revision`; touching one sidecar's mtime with no `Meeting` field change does (the UX52 guard); a `.processing` row ageing into `.failed` with no file change does.
- `ScopeCounts` and `MeetingGroup` results are identical to today's over a fixture spanning several months and a DST change (calendar and time zone pinned).
- `cd daemon && swift build` and `swift test` green, with the number of new tests in the commit body; `bash scripts/ci-local.sh` green; `ARCHITECTURE.md`'s `MeetingStore` bullet names the duration cache in the same commit.
