# UX105: Move library, Evict unused, Clear waveform peaks and the Launch at login toggle show no busy state between the click and the result

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source findings: P041, P042 and P043 in the [responsiveness audit](../../audits/2026-11-13-responsiveness-audit.md) (ranked fix 7, "busy states for occasional controls"), all low, present in both field builds and at HEAD. Re-verified in code at HEAD `3a2da4fc` on 2026-11-13. Evidence is code reading plus one measurement on the home Mac: a read-only `launchctl print-disabled gui/<uid>` took 4.5 to 5.4 ms over 8 runs. None of these controls logs a click, so no field timing exists.

**P041, Move library.** The confirm's button runs `pendingMove = nil; Task { await stats.executeMove(plan) }`, which dismisses the dialog at once. `StorageStatsStore.executeMove` then awaits `Task.detached { try LibraryMover.execute(plan) }` and publishes nothing until it returns, then `rescan()`. The pane's only move-related state is `isPlanningMove` (PERF13), which covers measuring the plan, not executing it, so the "Move library…" button (`.disabled(stats.isPlanningMove)`) is enabled again during the move. A same-volume move is a rename and lands in tens of ms; a cross-volume move copies the whole library and the pane looks idle for seconds to minutes, with a second move one click away.

**P042, Clear waveform peaks and Evict unused.** `clearWaveformCache()` and `evictUnusedModels()` each await a detached delete, log `waveform_cache_cleared` or `models_evicted`, then `await rescan()`. Until `rescan()` sets `isScanning` (which only relabels the header's Rescan button), the row keeps the old size and its button stays enabled (`.disabled((stats.stats?.waveformCacheBytes ?? 0) == 0)`, likewise for evictable model bytes). Found at filing: `rescan()` returns at `guard !isScanning` when a scan is already running, so a clear or evict that finishes during the pane's own `.task { await stats.rescan() }` leaves the stale size on screen until the next manual Rescan.

**P043, Launch at login.** `launchAtLoginBinding` reads `launchAtLogin.status.isOn` and writes through `LaunchAtLoginModel.set(enabled:)`, which sets `isBusy` (the row disables) and moves the knob only when the detached `service.set(enabled:)` returns. That is UX42's rule, stated in the binding's comment: the switch renders what launchd holds after the write, "not what was asked for". Separately, `LaunchAtLoginModel.init` calls `service.status()` synchronously, and it is built in `GeneralSectionView.init` through `StateObject(wrappedValue:)`, so each General pane identity runs one `launchctl print-disabled` on main (about 5 ms here; the comment above the class records `rebuild.sh` holding launchd while the pane is open).

Correction at filing: the audit suggests seeding the model "from the status menu's PERF24-cached state". `StatusBarController` caches only a Bool, `launchAgentEnabled`, which is "Optimistic until the launch read lands" (default true) and cannot represent `.notInstalled` or a refusal. It can seed the knob's position, not the full `LaunchAtLoginStatus`, so a seeded model still needs the off-main read before it may show a footer reason.

Correction at filing (re-read 2026-11-14): the synchronous read in `LaunchAtLoginModel.init` is deliberate, not an oversight. Its doc comment says "The initial read is still synchronous, and stays that way on purpose", because the alternative is "a placeholder state rendered before the machine has been asked, which is the control-lies-about-launchd defect UX42 removed". A seeded knob is that placeholder, so moving the read off main crosses the same UX42 rule as leading the knob, and item 3 below is owner-gated together with item 4. The cost being traded is one bounded `print-disabled` (about 5 ms measured) per General pane build.

Related: [CONC5](./CONC5.md) (process spawning policy), [PERF13](./PERF13.md) (done, planning off main), [PERF24](./PERF24.md) (done, the menu's cache), [PERF29](./PERF29.md) (filed in this band, cold Preferences builds), [STOR7](./STOR7.md); UX42 is archived in [q6-final.md](../q6-final.md).

## Scope

1. **Move library.** Add `@Published private(set) var isMoving` on `StorageStatsStore`, set before the detached `LibraryMover.execute` and cleared after `rescan()` returns (on success and failure). The Storage pane shows a small progress row with the destination in the library group while it is true and disables Move library, and `StorageBusyGate` gains `moveRunning` so Back up now and Restore are disabled during a move too (a backup walking a library mid-move archives a half-moved tree, the same reason the gate already gives for backup against restore).
2. **Clear waveform peaks and Evict unused.** One `@Published private(set) var clearingCache: CacheKind?` (or two Bools) set before each detached delete and cleared after the follow-up scan has published. The row shows a spinner in place of its size and disables its button meanwhile. Make the follow-up scan run even when a scan is in flight (queue one more scan, or await the running one and scan again), so the size shown after a clear is never the pre-clear size.
3. **Launch at login, the main-thread read. Owner-gated (walkthrough step 1).** Only with the owner's yes, move `LaunchAtLoginModel.init`'s `service.status()` off main: seed the knob from the status menu's cached `launchAgentEnabled` (passed in), start in `isBusy` with the row disabled, and run the read through the existing `refresh()` path. No reason text is shown until that read lands.
4. **Launch at login, leading the knob. Owner-gated.** Only with the owner's yes (walkthrough step 1): the knob moves to the requested position at the click with `isBusy` showing, and snaps back with the refusal reason when `LaunchAtLoginRefusal.decide` reports one. Without that yes, keep UX42's rule and ship items 1 and 2 (plus item 3 if it alone was approved); a small inline spinner beside the disabled switch is then the busy state, and `LaunchAtLoginModel.init`'s comment is updated if item 3 lands.

## Explicitly not

- Making the move cancellable or resumable, or its progress a byte count: an indeterminate busy row is the whole ask.
- Guarding a move against a recording or a running job: a different defect, not a feedback one.
- Rename everywhere, People rename and remove, and Cancel's Cancelling state (P029, P033, P036 in the same ranked fix): the same pattern on other surfaces, not this task's controls.
- Any change to `LaunchAtLoginService`'s launchctl calls or `scripts/lib/login-agent.sh`.

## Acceptance

- `StorageStatsStore` tests with an injected mover and deleter that block until released: `isMoving` is true from `executeMove`'s start until it returns, on success and on a thrown error; `clearingCache` is true from the call until the post-clear stats publish; a clear that finishes while another scan is in flight still publishes stats taken after the delete.
- A `StorageBusyGate` test: `moveRunning` disables backup and restore and is disabled by either.
- With the login controls left as they are, a `LaunchAtLoginModel` test that `isBusy` is true from `set(enabled:)` until the fake service answers and the busy spinner's predicate follows it. If item 3 is approved, a test with a fake service that counts calls by thread: constructing the model makes no `status()` call on main; the model starts busy with the seeded position and settles to the fake's answer. If item 4 is approved: `set(enabled: true)` shows `isOn` true synchronously, and a refusal reverts it and emits `launch_at_login_write_refused` as today.
- `bash scripts/test-login-agent-guard.sh` stays green (untouched); `cd daemon && swift build` and `swift test` green, with the number of new tests in the commit body; `bash scripts/ci-local.sh` green.
- `docs/GUIDE.md`'s Storage and launch-at-login recipes updated in the same commit if the controls' behaviour they describe changes.
