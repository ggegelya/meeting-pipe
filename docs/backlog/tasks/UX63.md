# UX63: the weekly-digest toggle says "on-device (no new egress)"; the scheduled run posts to Anthropic

Filed 2026-08-03 by the audit band. Medium, CONFIRMED by an independent skeptic that found no guard, default, second path or test that rescues the string.

## What is wrong

The Preferences toggle that installs the weekly-digest LaunchAgent describes the digest as running on-device, while the shipped digest narrates through `engine.complete_text` under `effective_backend()`.

- `daemon/Sources/MeetingPipe/Preferences/PreferencesView+Pipeline.swift:236` is the sole footer of `SettingsGroup("Weekly digest")`: `Text("The digest summarizes your open actions and recent decisions across the whole library, on-device (no new egress). Generate one on demand from the Library's Digests view.")`. It is unconditional, not behind a flag, and it is the only copy at the point the schedule is switched on.
- `pipeline/src/mp/digest.py:23` makes the module's own claim in the correct, qualified form: "No new always-on egress: this is a command you run or schedule", and `:16-18` says narration "honours `effective_backend()` and the egress guard clamps it under regulated / NDA".
- `README.md:535` uses the same qualified form: "It is latency-tolerant and adds no always-on egress".

The Preferences string drops the qualification, and the parenthetical "(no new egress)" reads as a guarantee about the network rather than about scheduling.

Observed, not theorized: the owner's unattended run on **2026-08-03** produced `digest.err.log:1` = `INFO httpx: HTTP Request: POST https://api.anthropic.com/v1/messages "HTTP/1.1 200 OK"`, with `digest.out.log:2` confirming "narrative via anthropic". So a launchd job posts a slice of the library's open actions and decisions to Anthropic every Monday at 09:00 with no UI in front of it, having been switched on by a control that said on-device.

## A second-order note, deliberately not folded in

`pipeline/src/mp/digest.py:434` is `cfg = entry.prepare()  # SEC13: arm, then secrets. Library-wide, so no meeting anchor.` The guard therefore arms only on a globally regulated config and never on a per-meeting NDA flag, so facts drawn from an NDA workflow's summaries ride the same call. That is **AUTO3's leg 0** ("which stems may leave this machine"), which is already filed and already names this exact shape. Report it there, do not duplicate it here.

## Scope

Rewrite the footer to say what the code does: facts are gathered on-device, and the narrative goes to whichever engine `summarization.backend` selects. Name the current engine inline the way `SummarizationEngine` already does elsewhere, so the string cannot go stale when the backend changes.

If the intent was genuinely zero-egress, the alternative is to pin the digest's narration to the local engine regardless of the global backend. That is a behaviour change and needs the owner's call, so the pickup asks rather than assumes.

## Acceptance

Suite green with new tests. The footer names the engine that will actually run, and a test pins that the string and the resolved backend cannot drift apart. If the owner chooses the behaviour change instead, the digest narrates locally and a test pins it.
