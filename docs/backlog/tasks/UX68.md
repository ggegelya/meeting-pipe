# UX68: a pane switch scrolls Preferences to 28pt below the top, not to the top

Band origin: filed 2026-08-04 at the owner's request, found on UX43's own owner walkthrough the day it was verified. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

UX43 fixed the reported bug: Preferences used to open a newly-selected pane at whatever offset the previous pane was left at, so switching from the bottom of a long Storage pane to General showed an apparently blank screen. That is genuinely fixed and the owner confirmed it.

What the owner then found is that the reset lands **close** to the top rather than **at** it. Two screenshots taken with no scrolling of any kind, one before a pane switch and one after, show the second sitting slightly lower: the pane header is pushed to the very bottom of its normal position and there is a small band still available to scroll up into. UX43's step 2 states the bar as "It has to open at the **top**", so this is that step not quite met rather than a new class of problem.

**The cause is visible in the implementation and is an anchor placed inside the padding it should be outside of.** `PreferencesView.swift:78-95`:

```swift
ScrollView {
    VStack(alignment: .leading, spacing: 0) {
        Color.clear.frame(height: 0).id(Self.topAnchor)
        detailContent
    }
    .padding(.horizontal, 32)
    .padding(.vertical, 28)
    ...
}
.onChange(of: selectionState.current) { _, _ in
    proxy.scrollTo(Self.topAnchor, anchor: .top)
}
```

`.padding(.vertical, 28)` is applied to the `VStack`, so it sits **outside** the stack's children while the zero-height anchor is the stack's **first child**. The anchor's own top edge is therefore 28pt below the scrollable content's true top. `scrollTo(anchor: .top)` aligns the anchor with the viewport top exactly as asked, which leaves that 28pt of top padding scrolled off above the viewport, and the user can scroll back up into it.

So the offset is not approximate and not a SwiftUI quirk: it is exactly the top padding, and it will track any future change to that constant.

## Scope

Make the anchor represent the top of the scrollable content rather than the top of the padded stack. The seam is the same block, and the smallest correct change is to move the anchor above the padding rather than to compensate for it numerically. Do **not** fix this by scrolling to a negative offset or by subtracting 28 anywhere: a hard-coded compensation silently rots the moment the padding constant moves, which is the same class of defect HYG5 spent a task removing from the specs.

UX43's own reasoning for the anchor approach still stands and should not be revisited: re-identifying the content with `.id(selectionState.current)` would reset the offset but also tear down every pane's `@State`, which is a far larger change than "open at the top". This task moves one view, it does not change the strategy.

## Explicitly not / out of scope

**Not the pane-switch strategy.** The `ScrollViewReader` plus constant-id anchor is the right shape and its rationale is recorded in the code comment; only the anchor's position is wrong.

**Not the padding values.** 28pt vertical and 32pt horizontal are DSN choices and this task does not touch them; it stops the scroll reset from depending on one of them.

**Not the other scroll surfaces.** The Library's centre column and the Guide window have their own scrollers and were not reported. If the same anchor-inside-padding shape is found there, name it rather than fixing it here.
