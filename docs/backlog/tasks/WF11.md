# WF11: Renaming a workflow orphans its meetings, its NDA-only membership and its vocabulary, because meetings and glossary tables resolve by workflow name

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source: findings G004 (high, confirmed) and G008 (confirmed, same root) in the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md), with F186 (the vocabulary half, verified) from the same report's low table. The [field evidence report](../../audits/2026-11-13-field-evidence.md) rates G004 "cannot tell": daemon.log carries three workflow-name hashes (May, June onward, 8 lines in July) and 4 `workflow reassigned` lines from 2026-07-23 to 2026-07-31, with one name since August, so a past rename is plausible but not provable from the logs. G008 has no log surface.

**A rename migrates nothing.** `WorkflowEditor.save()` in `WorkflowsView.swift` sets `clone.name = trimmedName` and calls `store.update(clone)`, which rewrites only `workflows/<uuid>.toml`. Meeting sidecars are written only by `MeetingMetaSidecar.build` and `.reassigned`, both of which stamp `workflow_id` and `workflow_name`, so every existing meeting keeps the old name. The only editor cue is WF9's `nameCollisionHint`, which fires on collisions, not renames.

**The Library resolves membership by name only.** `LibraryScope.Context.workflow(for:)` looks up `meeting.workflowName` in `workflowsByName`. Both `.workflow(let id)` (`context.workflow(for: meeting)?.id == id`) and `.ndaOnly` (`context.workflow(for: meeting)?.flags.ndaMode == true`) go through it, as does `ScopeCounts.build` in `LibrarySidebar.swift` via `s.includes(m, in: context)`. The inspector's `LibraryWindow.meetings(for:)` filters `$0.workflowName == workflow.name`. `.untagged` is `meeting.workflowName?.isEmpty ?? true`, so orphaned meetings are not Untagged either. `Meeting.workflowID` (lifted from the sidecar's `workflow_id` in `MeetingStore`) and `Meeting.workflowNDAMode` are both available and unused for membership. `LibraryScope`'s header says the scope "carries `Workflow.ID` rather than the name so a rename can't silently drop the scope", and `Context.workflow(for:)` says "The rail's scope uses id, so a rename can't orphan it"; both are false for the meetings inside the scope.

**The caches do not see a rename.** `LibraryWindow.CountsKey` holds `workflowIDs`, and its doc comment reads "renaming one does not, and shouldn't trigger a recount". `LibraryListView.DerivedKey` holds `workflowsCount`. Neither includes names or NDA flags, so the list and badge stay stale until something else bumps the store revision, while the inspector, computed at render, empties at once.

**The vocabulary is keyed by name on both sides (F186).** `GlossaryStore.resolvedTerms(in:workflowName:)` reads `document["workflow"]?.table?[name]` and `mp.glossary.load_glossary` reads `(raw.get("workflow") or {}).get(workflow_name)`, with `workflow_name` from the meeting's `meta.json` when not passed; its sole pipeline caller is `orchestrate.py`'s `load_glossary(wav)`, and the daemon's re-transcribe carry calls `GlossaryStore.resolvedTerms(at:workflowName:)` with `MeetingLibraryService.workflowName(stem:in:)`, which reads `workflow_name`. New meetings after a rename carry the new name, so the `[workflow."<old>"]` table is never read again, and the Vocabulary editor's workflow picker lists only current names, so the table is unreachable from the UI (`WorkflowsView`'s `vocabularySection` already notes that `glossary.toml` "keys a workflow's table by name").

**Bounds.** Nothing on disk is lost. The NDA egress clamp reads the sidecar snapshot (`workflow_nda_mode`, applied in `pipeline/src/mp/workflow.py`), not the live name, so no orphaned NDA meeting publishes. Orphaned meetings remain in All meetings and filterable by the old name, per-meeting reassign exists, and renaming back restores everything. Hence P2.

**The id path is known and used elsewhere.** `PrepCardStore.matches(meta:workflowID:workflowName:)` prefers `workflow_id` and falls back to `workflow_name`, and `summarize.py`'s prior-meeting lookup matches on `workflow_id`. Name-keyed Library resolution was kept on purpose for cross-machine portability (TECH-B4), and UX30, UX33 and WF9 (all done, see [q6-final.md](../q6-final.md)) documented its delete and duplicate-name costs but never a rename. `README.md`'s "Two workflows with the same name" paragraph says "renaming stays free".

Correction at filing: G008's direction reads NDA membership from `meeting.isZeroEgress`, but `Meeting.isZeroEgress` is `(workflowNDAMode ?? false) || (regulatedMode ?? false) || metaUnreadable`, which would put every regulated-mode meeting and every meeting with an unreadable sidecar into NDA only. The NDA-only predicate should read `meeting.workflowNDAMode`, falling back to the live workflow only when the sidecar predates that key.

Correction at filing: `PrepCardStore.matches` does not fall back to the name when an id is present and differs, which is right for a prep card but would break TECH-B4 portability in the Library (a library moved to a Mac whose workflows carry other UUIDs would orphan every meeting). The Library resolution falls back to the name when the sidecar's id names no live workflow.

## Scope

1. **Id-first resolution in one place.** `LibraryScope.Context` gains a `workflowsByID` table, and `workflow(for:)` returns the live workflow whose `id` matches `meeting.workflowID` (case-insensitive UUID compare, as `PrepCardStore.matches` does); when the sidecar has no `workflow_id` or it names no live workflow, it falls back to today's `workflowName` lookup. `.workflow(id)` and `ScopeCounts.build` inherit it.
2. **NDA only from the recorded posture.** `.ndaOnly` returns `meeting.workflowNDAMode` when the sidecar has it, else the resolved workflow's `flags.ndaMode`. This also stops a later NDA toggle on a workflow from moving past non-NDA meetings into NDA only, which matches the rows' lock and the egress clamp, both of which already read the sidecar.
3. **The inspector uses the same resolution.** `LibraryWindow.meetings(for:)` filters through `LibraryScope.Context.workflow(for:)` rather than `workflowName == workflow.name`, so the inspector and the rail badge still cannot disagree (the reason its comment gives for name matching).
4. **Cache keys see names and flags.** `CountsKey` and `DerivedKey` carry each workflow's id, name and NDA flag (one small `Equatable` fingerprint shared by both), replacing `workflowIDs` and `workflowsCount`; the "renaming one does not, and shouldn't trigger a recount" comment goes.
5. **Move the glossary table on rename.** When the editor saves a changed name, `GlossaryStore` moves `[workflow."<old>"]` to `[workflow."<new>"]` (a new method, e.g. `renameWorkflowTable(from:to:)`), merging into an existing destination table with the destination's keys winning, and leaving the global `[terms]` untouched. A `daemon.log` line records the move with term counts only.
6. **Resolve a meeting's glossary name through its id on both sides.** So a pre-rename meeting re-finalized or re-transcribed later still finds the moved table: Swift `MeetingLibraryService.workflowName(stem:in:)` (the glossary caller) and Python `load_glossary`'s meta read both map the sidecar's `workflow_id` to the current workflow name (Swift through `WorkflowStore`, Python through `mp.workflows._load_workflow_docs`), falling back to `workflow_name` when the id is absent or unknown. The CI4 `glossary-golden.json` fixture gains a renamed-workflow case, regenerated with `scripts/gen_contract_fixtures.py`.
7. **Docs and comments in the same commit.** The `LibraryScope` header and `Context.workflow(for:)` comments, `LibraryWindow.meetings(for:)`'s comment, `README.md`'s "Two workflows with the same name" and "Deleting a workflow" paragraphs (same-named workflows now keep separate meetings wherever the sidecar has an id), WF9's `WorkflowNameCollision.explanation` copy if its sentence is no longer true, `ARCHITECTURE.md` if it states name resolution, and any `docs/GUIDE.md` workflow or vocabulary recipe that does.

## Explicitly not

- Rewriting `workflow_name` in every meeting sidecar on rename: N file writes into an iCloud-synced library, and it would erase the record of the name the meeting was recorded under.
- Id-keying `glossary.toml` tables: the file is hand-editable by name (UX44), and item 5 plus item 6 close the class without a format change.
- The filter bar's workflow chips and `MeetingFacets` (`MeetingFilter`), which filter by the recorded name; that is still the way to find meetings by an old name.
- `mp prep`'s and `mcp_tools._workflow_name`'s name keying (a shell caller types a name), and `mp doctor`'s `nda_workflow_names`.
- [SEC21](./SEC21.md)'s fail-open NDA classification and its "turning NDA on later does not cover past meetings"; item 2 keeps the Library consistent with today's sidecar-snapshot egress rule and does not change it.
- The delete flow (UX30): a deleted workflow's meetings still fall back to the name and stay out of Untagged, as documented.
- [UX88](./UX88.md) (matching rules UI).
