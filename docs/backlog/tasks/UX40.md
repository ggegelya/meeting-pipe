# UX40: Voice chip rename and un-name, honest strip count

Band origin: filed 2026-07-29 (owner exploratory sweep, item 11: "when I name someone from the voice panel, I am not able to rename or unname it"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The FEAT11 cast strip (`VoiceResolutionBar.swift`) renders one chip per voice and branches on exactly one thing: `voice.offersNaming`, true only for `.unresolved` with a voiceprint (`VoiceResolution.swift:52`). Every other state (`.you`, `.roster`, `.namedHere`, `.unattributed`, unresolved-without-voiceprint) is a static chip with a `.help` tooltip (:125-134). No chip has a context menu.

The machinery for rename and un-name exists one layer down and the strip just never reaches it:

- The naming sheet already supports rename: `SpeakerNamingMode { enroll, rename, assignNew }` (`TranscriptTab.swift:906`), and the mode is picked off `NamingTarget.currentName` (:290). The strip's callback hard-codes the enroll shape, never passing a current name (:260-262), so it can only ever open enroll.
- The transcript row's right-click menu offers "Rename..." and "Undo naming" (:849-865, wired to `renameSpeaker` and `libraryModel.undoSpeakerNaming` which drops the overlay entry and un-enrolls), but only when the name lives in the `SpeakerLabelStore` overlay (`clusterName` at :779-781). A `.roster`-origin voice (name baked into `<stem>.json` by the pipeline's finalize, no overlay entry) fails that gate AND fails the `canEnroll` gate, so it gets no Rename, no Undo, and no Name, in the strip or the row menu. Its only rename is the global Preferences People flow (`RosterRename`, which carries the new name across every meeting's overlay).

The count confusion, working as designed but misleading: the header tallies `rosterMatched + namedHere` of `others` (which excludes `.you` and `.unattributed`, `VoiceResolution.swift:73`, :83-84, :146-151), while the strip renders every classified member (:153-160; `VoiceResolutionBar.swift:30`). The owner's screenshot: 9 chips, "7 of 7 voices named", because the owner chip and an "Unknown speaker" chip render but do not count. The exclusion logic is right (the `speaker_unknown` junk drawer must never be offered for naming, and counting the owner would inflate every meeting); the copy just reads as a count over what is visible.

## Scope

- Per-state chip affordances, all routed to existing paths, no new naming machinery:
  - `.namedHere`: context menu with "Rename..." (open the sheet in `.rename` with `currentName` set) and "Un-name", `role: .destructive` (route to the same `undoSpeakerNaming`).
  - `.roster`: context menu with "Rename everywhere..." routing into the `RosterRename` flow, with copy naming the blast radius (it renames this person across all meetings, which is what a roster rename means); plus the existing `.help` explaining the roster match.
  - `.unresolved` with voiceprint: keep the current Name affordance, also as a menu item for consistency.
  - `.you` / `.unattributed`: help text only, unchanged.
- Wire `currentName` through the strip's callback so the sheet opens in the right mode (the one-line gap at `TranscriptTab.swift:260-262`).
- Header copy counts what it shows or says what it counts: prefer rewording over recounting, e.g. "All 7 other voices named." / "5 of 7 other voices named." with the existing empty-roster and no-others variants (`VoiceResolution.swift:78-93`) kept. The word "other" is the fix: it makes the owner-and-unknown exclusion legible in four characters.

## Explicitly not in scope

Changing `VoiceResolution` classification or the counting exclusions (correct as designed). Per-segment reassignment flows (exist, untouched). The roster UI itself. The staleness consequence of a rename on the summary (UX41, filed the same day). FEAT11's owner-owed rebuild eyeball.

## Acceptance

Tests extend the `VoiceResolution`/strip suites: menu offering per origin state (namedHere gets Rename + Un-name, roster gets the everywhere-rename, unresolved keeps Name, you/unattributed get none); the strip's rename path passes `currentName` so the sheet mode resolves to `.rename` (pin at the `NamingTarget` seam); Un-name from the chip invokes the same `undoSpeakerNaming` service call the row menu uses (one implementation).

Header copy tests: the 9-chip/7-named repro renders "All 7 other voices named."; a partial case renders the of-form; empty-roster and no-others variants unchanged.

## Progress (2026-07-31): shipped, the eyeball is owner-owed

Everything but the rendered eyeball is in. `swift build` and `swift test` green at 1962 (1949 before, 13 new), truth fences and both dash guards clean; no Python touched.

The per-chip menu is a second pure rule beside the glyph and wording maps, `VoiceResolutionBar.actions(for:)`, rendered by a `ForEach` over its output so the view cannot offer something the rule does not. `VoiceResolution`'s classification and counting are untouched, as specced.

Two gates went in that the spec did not name, both for the same reason (a chip must not offer an action the flow behind it would turn into a no-op, the `WorkflowRowActions` rule):

- `.namedHere` splits. Rename plus Un-name are offered only when the key is a **cluster** label, which is the transcript row menu's own gate (`overlay.labels[speakerID]`) read off the key rather than off a second overlay lookup. The other `.namedHere` shape is FEAT3-SEGMENT's "New person", whose name lives in the overlay's per-segment map and never in `labels`: "Un-name" there would drop an entry that is not present and the chip would not move. That chip offers nothing and its tooltip points at the row menu's "Reset to original label" instead.
- A roster rename that fails now says so. `RosterRename.run`'s failure was surfaced by its two existing callers through a field of their own; a chip has no error slot, so it gets `LibraryDialogs.reportRosterRenameProblem`, the sibling of UX32's workflow refusal for the identical reason. A modal that asks for a new name and then changes nothing is exactly the silence worth a dialog.

Header copy took a third variant the spec's two examples did not cover: at 1 of 1 it reads "The other voice is named.", because "All 1 other voice named" is not a sentence and a 1:1 is the most common meeting there is. The `detail` clause ("2 voices are still unnamed.") was left alone: it only ever renders beside the of-form, whose "of 7 other" has already scoped the number.

Also in the same change: `NamingTarget.mode` lifts the sheet-mode decision out of the sheet's argument list so the rename seam is pinnable, and the tooltips on the states that grew a menu now say a right-click is there (an invisible context menu on a chip is close to not shipping the affordance).

Known limits, both pre-existing and shared with the other two rename surfaces: the overlay carry only reaches a meeting that has a `.summary.json` or a `.speaker_labels.json` and lists the person, so a finalized meeting whose summarize failed keeps the old name on its chips until it is summarized; and a roster voice that was renamed in-app first has a display name that is an overlay alias over the baked label, so the prompt renames what the chip shows.

**Owner-owed:** the eyeball above. Needs one `./scripts/rebuild.sh`.
