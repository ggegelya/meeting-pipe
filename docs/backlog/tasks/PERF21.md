# PERF21: Library playback leaves the audio output running after pause, end of file and window close, and calls its engine unbounded on the main thread

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Verified in code on 2026-10-25 against `01e904a`. Review findings LIBRARY-2 and UI-1 are the same defect found by two finders; UI-8 and PERSISTENCE-8 sit in the same type. All four are fixed in `AudioPlaybackController` and its owner, and share one test seam.

**The engine is never stopped when playback stops.** `AudioPlaybackController.play()` starts the engine (`if !engine.isRunning { try engine.start() }`). `pause()` is `let t = computedCurrentTime(); playerNode.pause(); currentTime = t; isPlaying = false; stopTimer()`, with no engine call. The end-of-file branch in `scheduleOneChunk()`'s completion is `if isFinal { self.isPlaying = false; self.currentTime = self.duration; self.stopTimer() }`. The only `engine.stop()` calls are in `teardown()`, reached only from `load(url:)` of a different URL, and in `deinit`. `MeetingDetailView` owns the controller as `@StateObject var playback = AudioPlaybackController()`; it has no `.id(meeting.stem)` (UX78's comment in its `onChange(of: meeting.stem)` says so), that handler only calls `playback.pause()`, and the view has no `onDisappear`. `LibraryWindow.show()` sets `w.isReleasedWhenClosed = false` and keeps the window, and `LibraryWindowDelegate.windowWillClose` only notifies `WindowActivationManager`, so closing the Library keeps the view graph and the engine. `deinit` runs only when the detail pane leaves the hierarchy (a switch to Facts, a multi-select, a deselect).

So after one play then pause, or one play to the end, the engine's output IO keeps running, rendering silence through `AVAudioUnitTimePitch` and the main mixer, until another meeting's audio loads, an output-device change stops the engine, or the app quits. If audio is playing when the window closes, it keeps playing and UX78's header transport is inside the closed window. On macOS an active output IO normally makes coreaudiod hold a `PreventUserIdleSystemSleep` assertion; that is known platform behaviour, not measured here, which is why the owner walkthrough starts by measuring it. The 2026-10-25 idle sample of the running daemon (pid 77137: 18 MB footprint, zero wakeups over 10 s, 5 threads) neither confirms nor refutes this: that process has no `detail` events in its seven-day life, so it never played audio.

**Every engine call is synchronous on main.** The class is `@MainActor final class AudioPlaybackController`. `play()` and `restartScheduling(fromTime:resumePlaying:)` call `engine.start()` inline, `teardown()` calls `playerNode.stop(); engine.stop()`, and `load(url:)` calls `engine.disconnectNodeOutput` and `engine.connect`. `daemon/CLAUDE.md` says "Don't call `AVAudioEngine` synchronously and unbounded from anywhere (`EngineTeardown`, `boundedEngineStart` and `MicLevelMonitor.startBounded` are the sanctioned shapes)", and `boundedEngineStart`'s doc records why: "A Bluetooth headset renegotiating HFP was observed on 2026-06-12 to hang `engine.start()` for ~42 s on the main thread, freezing the whole app". The playback engine is a separate instance from the recorder's, but it starts on the same output route, so pressing Play, or a transcript tap through `playFrom(_:)`, while a headset renegotiates or a dock's USB audio wakes blocks main; during a recording that freezes the HUD's Stop, the menu and the hotkeys. No such freeze from playback is recorded: this is exposure, not an incident.

**Skip silence decodes the recording when it is off.** `load(url:)` always calls `loadSilentSpans(for:)`, which starts an unstored `Task.detached(priority: .utility)` running `WaveformPeaksLoader.load(audioURL:)` whatever `skipSilence` is (`@Published var skipSilence: Bool = false`). On a cold cache that decodes the whole file and writes `~/Library/Caches/MeetingPipe/waveforms/<stem>.peaks`. The detail tab is remembered in `@AppStorage`, so arrowing through rows with the Transcript tab open starts one full-file decode per row that nothing cancels, and `AudioTab` runs its own `WaveformPeaksLoader.load` for the same file. The verifier measured the cost down: the decode is streamed with bounded memory, well under a second per hour of 16 kHz audio, off main, and the cache is about 1.44 MB per recorded hour, already purged by retention drop and delete. It is transient cooperative-pool pressure, not a leak.

## Scope

The seam is `AudioPlaybackController` (`load(url:)`, `play()`, `pause()`, `restartScheduling`, `scheduleOneChunk`, `teardown()`, `loadSilentSpans(for:)`) plus `MeetingDetailView`'s lifecycle hooks.

1. **Stop the output when nothing plays.** In `pause()` and the end-of-file branch, re-anchor the schedule at the paused time (`restartScheduling(fromTime: t, resumePlaying: false)`, which resets `playSegmentStartFrame`) and then stop or pause the engine, so the resume position does not depend on `playerNode.lastRenderTime`, which is nil while the engine is stopped and makes `computedCurrentTime()` fall back to the segment start. `play()` and `restartScheduling` already restart the engine through `if !engine.isRunning`. A short grace before stopping (a few seconds, a named constant) is allowed so quick toggles do not restart the hardware each time.
2. **Stop when the surface goes.** `MeetingDetailView` pauses playback in `onDisappear`, which fires on window close (`LibraryRootView`'s own `onDisappear` relies on that to stop the library watcher), so closing the Library or leaving for Facts stops the audio and, through item 1, the engine. UX78's header transport and the summary-citation jump are unchanged: the jump raises its pending seek before the tab switch and must not pause.
3. **Bound and sequence every engine call.** `engine.start()` goes through `boundedEngineStart`, `playerNode.stop()` and `engine.stop()` through `EngineTeardown.run`, off main. `playerNode.play()`, `isPlaying = true` and `startTimer()` happen only after a start returns `.started`; `.timedOut` sets `loadError` and leaves `isPlaying` false. Engine operations run on one chain, so a load or teardown issued while a start is in flight waits for it, and after any timed-out call the controller replaces the engine and its two nodes (a fresh `AVAudioEngine` with `playerNode` and `timePitch` re-attached) instead of calling into the abandoned one again, `connect` and `disconnectNodeOutput` included. The controller takes its engine operations through an injected seam defaulting to the real engine, the `boundedEngineStart` precedent, so all of this is testable without an output device.
4. **Silent spans only when asked.** `loadSilentSpans` runs when `skipSilence` is on (at load if already on, and on the toggle). Its `Task` is stored and cancelled by `teardown()` and by the next `load`, and `WaveformPeaksLoader.compute(audioURL:)` checks `Task.isCancelled` between chunks so a cancel stops the decode.

## Explicitly not

- PERF12 (the 15 Hz `currentTime` clock re-rendering the detail pane) and ARCH15's `@Observable` migration of this controller. All three edit `AudioPlaybackController`; whichever lands second rebases on the others.
- UX78's header transport and its stem-change pause, which stay as shipped. UX78's owner walkthrough still applies after this lands.
- A size cap or LRU on the waveform cache: about 1.44 MB per recorded hour against about 230 MB per hour of audio, already purged by retention drop and delete.
- Sharing one in-flight peaks compute between `AudioTab` and the controller: optional, not required, since item 4 removes the controller's load in the common case.
- The iCloud download check before playback (`AVAudioFile(forReading:)` in `load(url:)` blocks main on a dataless file until it downloads): STOR6 item 4.
- Relying on `AVAudioEngine.isAutoShutdownEnabled`: check its availability on the macOS 14 floor before adding it as a belt-and-braces measure; items 1 and 2 are the fix.

## Acceptance

- `AudioPlaybackControllerTests` over the injected engine seam: play then pause leaves the engine not running once the grace has elapsed (injected clock, or a zero grace in tests); play to end of file the same; play after pause resumes from the paused position (assert `currentTime` and the scheduled start frame); a start that never returns within its budget leaves `isPlaying` false and `loadError` set, and a following `load(url:)` makes no call into the abandoned engine; a teardown issued during an in-flight start runs after it.
- `loadSilentSpans`: no peaks load when `skipSilence` is false (counting seam on the loader); one on the toggle; a `load` of a second URL cancels the first task.
- A source fence that `MeetingDetailView` pauses playback in `onDisappear` (the UX78 fences' style, since SwiftUI wiring has no runtime read), and one that no `engine.start()` or `engine.stop()` in `AudioPlaybackController.swift` sits outside the bounded helpers.
- `cd daemon && swift build` and `swift test` green, with the number of new tests in the commit body; `bash scripts/ci-local.sh` green.
- `docs/GUIDE.md`'s playback recipe updated in the same commit, since closing the Library now stops audio.
