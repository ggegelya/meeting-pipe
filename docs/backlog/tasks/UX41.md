# UX41: Names changed since this summary: quiet cue + one-click re-summarize

Band origin: filed 2026-07-29 (owner exploratory sweep, item 11: after renames "summary might need re-generation... or instead maybe we can infer summary with new names without specific extra re-generation call. I am not 100% sure what is the best option"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The split is real and confirmed on both sides. Generation applies the speaker overlay and bakes the resolved names into the summary text: `summarize()` composes the overlaid transcript (`summarize.py:453-461`, via `transcript_corrections.overlaid_structured` and `speaker_overlay.apply_overlay`) and renders `**Name**:` lines the model reads, so bullets, attendees, and action owners carry whatever names existed at that moment. Display never re-resolves: `MeetingSummary` is a flat decodable with no overlay step, and no summary surface references `SpeakerLabelStore` (grep zero). The repo already states it in as many words: "summaries and transcripts keep whatever they were written with" (`RosterRename.swift:14-16`). Meanwhile the transcript, cast strip, and People rail all resolve at display time and update immediately after a rename.

So after the owner names voices (the exact 2026-07-27 session: seven voices named post-meeting), the transcript says Anisha while the summary still says THEM-3, and nothing says why.

Decision, taken as delegated between the owner's two options:

- **Not silent substitution.** Rewriting names inside generated prose is unreliable (inflected languages, the owner's library is half Ukrainian where names decline by case; possessives; partial matches) and it would falsify provenance: the summary claims to be what the model wrote. Rejected.
- **Not auto-regeneration.** It costs an engine call (cloud money or local minutes) per rename batch, and PIPE11 just made regeneration deliberate and queued. The owner owns the click. Rejected.
- **Yes: a quiet, truthful cue with the fix one click away.** The register precedent is the "Summary edited locally" caption (`MeetingDetailView+Header.swift:94-106`) and the FEAT11 nudge rule ("a nudge, not a feature: no new storage, nothing auto-filled").

The derivation has one trap, found while tracing: a naive `mtime(speaker_labels.json) > mtime(summary.json)` check is falsified by the in-place summary rewrites that do NOT regenerate (the action done/reopen toggle through `MeetingLibraryService.setActionResolved` and the correction editor's `persistEdit`, both re-serialize `summary.json`). The truthful timestamp is `<stem>.run.json`'s `ts`, written at summarize time (`corrections.py:78-87`) and kept truthful by PIPE11 even for standalone re-summarizes (`summarize.py:876-905`). `MeetingStore` already parses `run.json` for backend/model/publish_state (:514, :535) and already prefetches content-modification dates in its scan (:318), so the derivation costs no new I/O class.

## Scope

- Derive `namesChangedSinceSummary` in `MeetingStore`'s post-scan overlay step (the `hasCorrections` shape at :362-367): true when the speaker-labels overlay's mtime is later than `run.json`'s `ts`; false when either file is absent (no summary yet, or never renamed; conservative, no cue). Roster-wide renames route through the same overlay files (`RosterRename` writes per-meeting overlays), so they are covered by construction.
- Render the cue in the detail header's caption slot beside "Summary edited locally": "Speaker names changed after this summary." with an inline "Re-summarize" affordance that opens the existing `ReSummarizeMenu` (UX29's NDA honesty comes free; the cue must not offer a cloud path the clamp forbids).
- Surface parity per the UX28 rule (a chip that exists in one place only is the named failure mode): decide-and-record between header-only (quiet, recommended: the list row stays calm, renames are deliberate acts whose consequence you check in the detail) or header + a row dot. Recommendation recorded: header-only; revisit if the owner reports missing it.
- The cue clears itself by construction: a re-summarize rewrites `run.json.ts` (PIPE11), flipping the comparison.

## Explicitly not in scope

Any rewriting of summary text (rejected above, recorded so the pickup session does not re-litigate). Auto-regeneration or batch "re-summarize all renamed" (the batch pane already covers multi-select re-summarize). Transcript-correction staleness (text edits already re-summarize through their own flow; only names have this silent split). `mp ask` index staleness (the fingerprint already covers overlay files; verified at `embed_index.py:349`).

Everything but the rendered eyeball is in. `swift build` and `swift test` green at **2029** (2018 before, 11 new), truth fences clean, both dash guards clean (no em-dash in any added line, none under `daemon/Sources` / `daemon/Resources`). **The `run.json` fixture question, confirmed at pickup as the spec asked:** it is not a CI4-pinned surface. `scripts/gen_contract_fixtures.py` generates exactly four (`publish-result`, `prefetch-progress`, `speaker-overlay`, `glossary`), and the hand-maintained five in `CONVENTIONS.md#cross-tree-golden-fixtures` are `meta-contract`, `chunking`, `json-extract`, `summary-md`, `transcript-corrections`. Reading `ts` on the Swift side pinned nothing and regenerated nothing.

The derivation is one pure `MeetingStore.namesChangedSinceSummary(overlayModified:runTimestamp:)`, deliberately taking a `Date?` and a `String?` rather than reading disk, so the four acceptance cases are unit tests and not filesystem choreography.

**One placement deviation, which is the spec's own reasoning carried one layer in.** The spec said the post-scan overlay step (the `hasCorrections` shape) and justified it with "costs no new I/O class", pointing at `MeetingStore` already parsing `run.json` at `:514`/`:535` and already prefetching mtimes at `:318`. Both of those lines are inside `buildMeeting`, not inside the post-scan step, and the difference is not cosmetic: `hasCorrections` is cheap there only because corrections live *outside* the recordings dir and the whole set is cached behind one directory mtime. `speaker_labels.json` and `run.json` are both *inside* the dir, so they are already in the per-stem signature. In `buildMeeting` a rename invalidates exactly the row it changed and every other scan costs nothing; in the post-scan slot it would have meant re-reading and re-parsing `run.json` for every row on every 500 ms scan, which is the exact TECH-A12 perf finding the cache exists to fix. So the flag is derived in `buildMeeting`, which is where the spec's stated constraint actually leads.

The trap is pinned twice, once pure and once through a real `performScan`, because a pure test alone cannot express it: the pure function never sees `summary.json`, so only a scan-level test proves that rewriting `summary.json` after a rename (the action done-toggle, a correction save) leaves the cue standing. The doc comment on the derivation names both wrong timestamps and why: `summary.json`'s mtime (two in-place rewriters that regenerate nothing) and `run.json`'s own mtime (`corrections.set_publish_state` rewrites the file after a publish, which the spec did not mention and which would have been the natural second guess).

**Two decisions the spec delegated, both taken and recorded:**

- **Surface parity: header-only**, as the spec recommended. The list row stays calm. A rename is a deliberate act whose consequence you check in the detail pane you are already in, and UX28's named failure mode is a chip that exists in one place while a *second* surface reports the same state differently; one surface reporting it is not that. Revisit if the owner reports missing it.
- **`fgSubtle`, not the neighbouring caption's `fgFaint`.** `fgFaint` sits near 2.8:1 and fails the 4.5 body floor, which is why the provenance row two lines up already moved off it with a comment saying so. A line that carries an action is the wrong place to keep that debt. "Summary edited locally" is left exactly as it is; it is not this task's line to change.

Two smaller things the spec did not name:

- The engine list moved into a shared `reSummarizeItems`, so the `...` menu's submenu and the cue's inline menu render one list. Writing the cue's menu as a second copy would have let UX29's clamp be applied in one and forgotten in the other, which is the drift `workflowChoices` already exists to prevent one level down. A fence counts the cloud engine's mentions in the header file so a third copy fails the build.
- The menu indicator stays **visible** on the inline affordance, unlike the header's `...` menu which hides it. That menu's label is an ellipsis glyph that already reads as a control; a bare word in a caption row does not, and hiding the chevron would have made the fix look like more caption.

A known and intended over-fire: a **re-transcribe** (ASR3) re-anchors the speaker overlay onto the new transcript, which bumps its mtime and raises the cue. The wording is a shade imprecise there (the names did not change, their anchors did), but the summary genuinely is stale after a re-transcribe, and the re-transcribe dialog already ends by telling the owner to re-summarize. Both write paths are change-gated (`carry.speakerOverlay != overlay`, and `PeopleRail.renamed` returning nil when nothing moves), so a no-op rename never raises it.
