# UX99: the inline summary editor saves with no staleness check, so it writes an old snapshot over a regenerated summary and reports Saved when the write fails

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source: F066 in the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md) (confirmed). Re-verified in code at HEAD `3a2da4fc` on 2026-11-14; it holds as stated. Code-derived, not seen in the field.

**The standalone window checks, the inline editor does not.** UX65 (done, see [q6-final.md](../q6-final.md)) made `CorrectionWindow.show()` capture `let loadedIdentity = SummaryIdentity.read(at: summaryURL)` right after parsing the summary, and `CorrectionWindow.performSave` compares it with `SummaryStaleness.hasMoved(loaded: model.loadedIdentity, current: SummaryIdentity.read(at: summaryURL))`, offering reopen or keep-against-current before writing a record. UX65 scoped `SummaryTab` out. `SummaryTab.beginEditing` builds `CorrectionViewModel(stem:recordingsDir:runMeta:originalSummary:)` without `loadedIdentity`, so it is nil, and `hasMoved` documents a nil baseline as fresh. `SummaryTab.persistEdit` never re-reads the file and never calls `performSave`: it writes the correction record with `originalSummary: model.originalSummary.jsonObject()` and then overwrites `<stem>.summary.json` with `model.makeCorrectedSummary()`.

**Scenario.** Start Re-summarize on a meeting, open Edit summary while it runs, save after it lands: the regenerated summary is replaced by the old snapshot plus the edits, and the correction record's `original_summary` is prose the current run never produced, which a later `CorrectionsTab.performRevert` would write back. Action ticks made after the editor opened (`setActionResolved` writes into the same file) are lost the same way.

**A failed write reports success.** `persistEdit`'s doc says "Returns false on disk-write failure". The correction record uses `do`/`catch` and returns `false` on failure, but the summary overwrite is `try? data.write(to: summaryJsonURL, options: .atomic)` followed by `return true`. `save(model:)` then shows the "Saved" cue, reloads and closes the editor, so the edit disappears from the reader with no message. UX13 (done, see [q4-final.md](../q4-final.md)) introduced the inline save error but did not reach this write. [ARCH10](./ARCH10.md) item 3 already owns this swallowed write (its Context names `SummaryTab.persistEdit` returning true) and routes it through `SummaryDocument.update`, which also refuses while a pipeline job for the stem is queued or running.

**Related.** [PIPE54](./PIPE54.md) (same band): the editor can write summary shapes the pipeline's schema rejects, and a Retry then re-summarizes over the edit. [HYG22](./HYG22.md) (same band): the editor's string lists bind rows by position. [ARCH22](./ARCH22.md): the target split that would make a view writing a sidecar a compile error.

## Scope

In `daemon/Sources/MeetingPipe/SummaryTab.swift`:

1. `beginEditing` captures `SummaryIdentity.read(at: summaryJsonURL)` immediately after `MeetingSummary.load(from: summaryJsonURL)` and passes it as `loadedIdentity`.
2. `persistEdit` runs the same check as `CorrectionWindow.performSave` before writing anything: if `SummaryStaleness.hasMoved` is true, offer `SummaryStaleness.choice`'s copy (reopen on the current summary, or keep against what is on disk now, recording the current file as `original_summary`), inline in the editor footer rather than a new dialog idiom. Prefer calling `CorrectionWindow.performSave` (or a shared helper extracted from it) for the record so the two surfaces cannot drift again.
3. The summary overwrite becomes a throwing write; on failure `persistEdit` returns `false`, so `save(model:)` shows the existing `saveError` and keeps the editor open with the edits. If ARCH10's `SummaryDocument.update` has landed, use it here and surface its busy-stem refusal through the same `saveError`. If this task lands first, ARCH10 item 3 still owns moving the write into `SummaryDocument.update`, and the commit body names that split.

## Acceptance

- Tests over the save path (extract `persistEdit`'s decision into a static or model function if needed, the `performSave` precedent):
  - editor opened, `summary.json` rewritten on disk (a regenerate), then save: nothing is written without the stale choice; choosing keep records the current file as `original_summary` and does not lose its content outside the edited fields; choosing reopen writes nothing;
  - editor opened and saved with the file unchanged: one record and one summary write, as today;
  - the summary write fails (read-only directory or injected writer): `persistEdit` returns false, the editor stays open, `saveError` is set, no "Saved" cue;
  - `beginEditing` sets a non-nil `loadedIdentity` for a summary that exists.
- `UX65`'s `CorrectionWindow` staleness tests stay green.
- `cd daemon && swift build` and `swift test` green, N new tests named in the commit body; `bash scripts/ci-local.sh` green.
- [docs/GUIDE.md](../../GUIDE.md)'s summary-editing recipe mentions what happens when the summary changed while editing, in the same commit, if it describes the save.
