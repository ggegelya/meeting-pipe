### Three decisions taken during the build that the spec did not pre-decide

1. **Webex and Slack stay `usesProcessAudio: false`.** The spec says "flip on the native `NativeLifecycleConfig`s" without naming which. Cisco holds the mic open post-call for ultrasound device discovery, a carve-out that predates DET2 and that an input read cannot see around; neither app was covered by the probe (Teams only); and `Coordinator` builds both adapters without a `halBus`, which a true flag requires. Flipping either needs its own measurement.
2. **The start-side scanner corroborator was NOT revived**, though this spec's Leg 2 says "the scanner corroborator revives with no change". That sentence is stale: it rests on the Context section's claim that `MeetingSourceScanner.collectSignals` "already calls `ProcessAudioSignal.defaultProbe` and feeds the scorer", and the DET2 cleanup had already deleted both the probe call and the scorer's disjunct, so there is nothing to revive without writing new code. Re-admitting bare brand-token titles on an audio read is a start-side false-positive question that [DET6](DET6.md) owns and gates on its own measurement, and the cost argument got worse rather than better (resolution is now a whole-list enumeration, which per candidate per scan is heavier than the old translate). DET6's spec and the three scanner comments now record this.
3. **A process-object-list listener was added**, which the spec offered as an alternative to the unresolved-streak refresh ("re-resolve on the existing unresolved streak or a list-change notification"). Both shipped, because the probe's `replayd` observation makes the list path load-bearing: a client that tears down and re-registers gets a new object ID, which a streak-only refresh notices late or not at all if the stale ID still reads.

## Context: the DET2 close is refuted, not reopened on a hunch

DET2 closed NO-GO on 2026-07-20: translating the meeting app's PID to a HAL process object returned `object 0, OSStatus 0` under all three mechanisms (Screen Recording grant alone, a live bare process tap, a private aggregate around it), corroborated by 13,419 `process_audio_unresolved` events over eight weeks, and `ProcessAudioSignal` was declared dead by design ("refuted, not untried").

On 2026-07-30 a headless enumeration probe in this repo's own harness, holding **no** TCC grant at all, showed the close measured the wrong process. `kAudioHardwarePropertyProcessObjectList` returned 33 live process objects, including `Microsoft Teams ModuleHost` (bundle `com.microsoft.teams2.modulehost`, the SlimCore media stack MIC8 proved owns the mic and the mute logs, a direct child of the `MSTeams` shell) and the WebView `audio.mojom.AudioService` helpers (`com.microsoft.teams2.helper`). Translating ModuleHost's PID resolved to its object with `OSStatus 0`; translating the shell PID returned `object 0, OSStatus 0`, the exact production failure signature. So the HAL was answering truthfully all along: the **shell** process the daemon detects (`com.microsoft.teams2` via NSWorkspace, the PID in `MeetingLifecycleContext.pid`) never registers as a CoreAudio client, and every one of the 13,419 unresolved reads asked about it. Mechanisms A/B/C never mattered because none of them changed the target. Neither the DET2 probe nor `ProcessAudioSignal` ever enumerated the list; that was the one query that would have exposed this.

Three facts from the 2026-07-30 run, each better than DET2's best case assumed: (1) enumeration and the per-object boolean reads (`kAudioProcessPropertyPID` / `BundleID` / `IsRunning` / `IsRunningInput` / `IsRunningOutput`) resolve with **no TCC grant**, from a disclaimed harness shell, so the daemon-side read is zero-setup (the det2 TCC caveat voids negative probe results, never positive ones); (2) every Teams audio helper carries the `com.microsoft.teams2` bundle prefix and ModuleHost is a direct child of the detected shell PID, so matching is a bundle-prefix check with PID ancestry as fallback; (3) the booleans are live (the MeetingPipe daemon itself read `isRunning=true output=true` while resident, and idle processes read `input=false`).

What this buys once revived: a UI-independent, locale-independent, redesign-proof answer to "is this app on the mic right now". Start-side, `MeetingSourceScanner.collectSignals` already calls `ProcessAudioSignal.defaultProbe` and feeds the scorer (weight 3, a `shouldWalkControlAX` precondition, and the required corroborator for bare-brand-token browser titles whose death filed DET6). End-side, `PromotionEngine` already classes `processAudioIsRunningInput` as its own `EndEvidenceClass.processAudio`. The prompt already names the attributed app. Nothing in the fusion vocabulary changes; only the read comes alive.

**Leg 2, the build (on GO).** Repoint the already-injectable resolution seam in [`ProcessAudioSignal.swift`](../../../daemon/Sources/MeetingPipeCore/Lifecycle/Signals/ProcessAudioSignal.swift) (`ProcessObjectResolver` / `defaultProbe`): instead of `translate(context.pid)`, enumerate `kAudioHardwarePropertyProcessObjectList` and match objects whose bundle ID shares the detected app's bundle prefix (fallback: PID ancestry to `context.pid`), OR-ing `isRunningInput` across matches (Teams splits audio across ModuleHost and the WebView audio service; "any of them on the mic" is the question). Subscribe the HAL listener per matched object and re-resolve on the existing unresolved streak or a list-change notification; the 1 Hz poll fallback already exists. Flip `usesProcessAudio` to true on the native `NativeLifecycleConfig`s **together with `requiresCorroboration = true` for `processAudioIsRunningInput`**, the safety rail the DET2 spike pre-registered so a mute- or churn-induced input drop can never solo-confirm an end. The scanner corroborator revives with no change. Browser bundles (e.g. `com.google.Chrome.helper`) match by the same prefix rule against the browser's own bundle, which is exactly the corroborator END5's admission gate wanted and DET6 still wants.

**Leg 3, the record corrections (same commit as leg 2, as filed).** The repo asserted the refuted claim in prose in these places: `ProcessAudioSignal.swift`'s header ("do not re-propose; that hypothesis is refuted, not untried"), `NativeLifecycleAdapter.swift` and `InputDeviceIdentity.swift` comments, `LifecycleAdapterTests.test_process_audio_signal_is_disabled_for_every_provider` (comment and the pin itself, which the flip inverts), and `tasks/DET6.md`'s "DET2 then closed the signal permanently" paragraph.
