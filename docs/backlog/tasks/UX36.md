# UX36: Summary reading measure: centered column, honest padding, wrapping metadata

Band origin: filed 2026-07-29 (owner exploratory sweep, item 4: "the summary content is cut in width at some level... make size of the text area dynamic to the size of the panel, or make max width of the right panel fixed, or any other options"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

What the owner sees as "cut at some width" is the reading-measure cap, not a clip. `SummaryLayout.readingMeasure = 640` (`SummaryRenderedView.swift:8-10`) is a deliberate typography decision (TECH-DSN8 / UX13: ~70 characters at body size, "reads like paper"), applied to the rendered summary at :91-93:

- `.padding(MPSpace.s5)` (20pt) is applied INSIDE the cap, so the real text column is 640 - 40 = 600pt.
- `.frame(maxWidth: .infinity, alignment: .leading)` then parks the capped block hard left, so on a wide window all remaining width is dead space on the right. The detail column itself has a min of 450 and no max (`LibraryWindow.swift:782`, `LibraryLayout.swift:25-26`), so the asymmetry grows with the window.

The same cap-then-left-park pattern repeats in `SummaryTab.swift:242/:245` and :287/:288 and in `CorrectionEditor.swift:41`. Two stray literals shadow the constant: `.frame(maxWidth: 460, ...)` at `SummaryTab.swift:421` and :435 (the BYO/preview area), which will not track any change to the shared measure.

A real horizontal-space defect hides underneath: `ActionItemRow`'s metadata band is a non-wrapping `HStack` inside the cap (`SummaryRenderedView.swift:325-338`: a 16pt spacer, owner chip, due chip, confidence chip, FEAT10 `EvidenceChips`), with no `ViewThatFits` and no wrap, so a long owner name plus several evidence chips compresses and truncates. The one hard `lineLimit(1)` in the reader is the attendee chip (:432). Prose itself wraps correctly (`.fixedSize(horizontal: false, vertical: true)`, e.g. :197, :323).

## Scope

Decision, taken as delegated: keep a reading measure. Unbounded text width is rejected on readability grounds (70-90 characters per line is the defensible measure; a 1200pt line is objectively worse to read), and a fixed max on the detail panel is rejected because it would punish the Transcript and Audio tabs that use the width. The fix is to make the measure honest and the layout symmetric:

- Apply `.padding` outside the cap (or widen the cap by the padding) so 640 is the true text measure.
- Replace the left-park with a centered placement (`.frame(maxWidth: .infinity, alignment: .top)` centering the measured block), so a wide window frames the column like a page rather than abandoning the right half. Apply the same change at the `SummaryTab` and `CorrectionEditor` sites so reader and editor stay aligned (the stated reason the shared constant exists).
- Fold the two 460 literals into a named constant in `SummaryLayout` (a second, narrower measure for preview panes) so they track future changes.
- Make the action metadata band wrap: `ViewThatFits` with a two-line fallback, or a trailing-truncation policy that keeps evidence chips visible; pick whichever reads better with real data, record the pick.
- Optional, owner-eyeball-gated: nudge the measure from 640 toward ~680 if the centered layout reads too narrow on the owner's screen. Not a spec requirement.

## Explicitly not in scope

A user-facing width setting. Changing the detail column's min/ideal (`LibraryLayout`). Transcript tab layout. The red scroll indicator in the owner's screenshot (stock scroller styling, not a defect).

## Acceptance

The measure constant is applied at every summary surface through `SummaryLayout` with no shadowing literals (grep for `maxWidth: 4` and `maxWidth: 6` literals in the summary surfaces comes back empty).

A layout-level test or presentation seam pins that the metadata band renders all chips at `detailMinWidth` (450pt column) without truncating the evidence chips (if not testable headlessly, the acceptance is the owner eyeball case below plus a code-review assertion that `ViewThatFits`/wrap is in place).

`cd daemon && swift build` and `swift test` green (baseline at filing: 1770). Repo dash guard green.

Owner eyeball: open the meeting from the 2026-07-27 screenshot at full-screen width; the summary column sits centered with even margins, nothing is parked against the left edge, and an action row with owner + due + confidence + evidence chips shows all of them at the narrowest detail width.

## Progress (shipped 2026-07-29, owner-owed on the eyeball)

Implemented across the three summary surfaces the spec names: `SummaryRenderedView.swift`, `SummaryTab.swift`, `CorrectionEditor.swift`. 1829 daemon tests green, 8 of them new (`SummaryLayoutTests.swift`), no pipeline change, dash guard and CI5 truth fences green. `LibraryWindow.swift` and `LibraryLayout.swift` are untouched, as scoped.

**The measure is honest now, and it moved.** The gutter was applied inside the 640 cap, so the real text column was 640 - 2 * 20 = 600pt. All four cap sites now read `.frame(maxWidth: readingMeasure).padding(contentPadding)` instead of the reverse, which widens the actual text column from 600 to 640 with no change to the constant. Worth naming because 600 was outside the 640-720 reading column `design/README.md` asks for, so the app had quietly drifted below its own design system, and closing that gap is a visible width change on its own before any centering.

**Centered, per the spec's own modifier.** The outer frame is `.frame(maxWidth: .infinity, alignment: .top)` at all four sites. `.top` is `Alignment(horizontal: .center, vertical: .top)`, which is exactly the pairing wanted: centered across, pinned to the top of the scroller. The inner cap keeps `alignment: .leading`, so the prose is still left-aligned inside a centered column rather than becoming centered text.

**`SummaryLayout` grew two named constants** so nothing shadows the measure: `contentPadding` (the gutter, `MPSpace.s5`, now meaningful because it sits outside the cap) and `noticeMeasure = 460`, which absorbs the two stray literals in the failed state. The spec called those the "BYO/preview area"; they are actually the failure-reason dump and the model-download notice, both centered state panels, which is what the constant's name and doc comment say. The acceptance grep for `maxWidth: 4` and `maxWidth: 6` in the three summary surfaces comes back empty.

**The band pick: `ViewThatFits` with a two-line fallback, not trailing truncation.** Truncation has to choose something to sacrifice and both candidates are bad here: the owner is the most load-bearing fact on an action item (who owes it) and a clipped "Alex Nov..." can name two people, while the anchors are the row's only route back to the recording. In a pane that already scrolls vertically a second line costs nothing, so paying width with height is the cheaper trade. The split is at the semantic boundary (owner / due / confidence on line one, FEAT10 anchors on line two), which converges on the shape the bullet rows already use, where anchors sit on their own line under the point. Residual risk is bounded and named in the code: the fallback is the last `ViewThatFits` child, so it renders as-is rather than being re-checked, and line one can still compress for an owner name of roughly 50 characters at the 450pt detail floor. At that floor the column is 410pt and a realistic owner + due + confidence needs about 255pt, so the case is far outside real data. `MeetingRow` dropped `ViewThatFits` deliberately, but that was a `List` problem (NSTableView caches row heights, so the branch picked at first measure outlived the width that picked it); these rows are in a `LazyVStack` inside a `ScrollView`, which caches no height.

**Decisions not in the spec.** (1) Status is `owner-owed`, not `done`: the backlog's rule is that eyeball work stays active, and the geometric half of the acceptance ("all chips visible at `detailMinWidth`") is precisely what a headless session cannot verify, so the spec's own escape clause applies. (2) A latent bug closed on the way: the band's guard read `action.evidence` directly, but `EvidenceChips` draws nothing without an `onCite` handler, so a static surface (the digest reader, the A16 compare pane) with anchors and no other metadata opened an empty indented band. A new `shownEvidence` gates on the handler and both the guard and the two wrap variants read it. (3) The inline editor's `contentPadding: 16` became the shared `SummaryLayout.contentPadding`. Its rationale ("avoid squeezing the fields further") was about the old geometry where padding ate into the measure; with the gutter outside, the fields get the full measure either way, and matching the reader is the whole reason the shared constant exists, since 16 against the reader's 20 would shift the column by 4pt a side across the edit crossfade. (4) `chipRow` went from `private` to internal, joining `glyphName` / `isInteractive` / `toggleLabel` as a test seam, and the inline `Spacer().frame(width: 16)` became a named `metadataIndent` leading pad so both wrap variants state the indent once. (5) The A16 compare pane's "Current" / "Candidate" headings had to move with the columns they label. They sat flush at the pane's leading edge, which was only 20pt off the summary text below them; centering the summaries would have left a heading a whole margin away from its own column on a wide window, so a `compareHeading` helper puts them on the same measure. The `Divider()` between the two is deliberately left full-bleed: a rule across the pane separates the two candidates more clearly than a measure-width one.

**Not done, and deliberately.** The optional 640 to 680 nudge is untouched. It is owner-eyeball-gated by the spec's own wording and a headless session cannot judge whether the centered column reads too narrow; `SummaryLayoutTests` pins the measure inside the design system's 640-720 band so the nudge stays safe to apply later. The `design/ui_kits/macos_app/SummaryLibrary.jsx` mockup was not re-authored: it models neither a reading-measure cap nor FEAT10's evidence chips, and restructuring a pane's layout blind is the visual churn the backlog forbids without eyes, so it is recorded as a Known lag in that kit's README beside the UX22 and FEAT11 ones.
