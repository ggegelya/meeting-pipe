# UX73: the HUD flag-a-moment acknowledgement is a whole-panel opacity dip and nothing else

Band origin: filed 2026-08-10 from the owner's 2026-08-04 testing notes, first item: "Flag in the hood - clicking on it gives no visual reaction except the fact that hood become semitransparent. Pretty weird feeling. it would be nice to have some indication or something. UX is not okay heree." Follow-on to UX46 (shipped 2026-08-03), not a regression of it. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The owner's description is exactly what the code does, and the code says so on purpose.

`MeetingSessionController.flagMoment` ([:266](../../../daemon/Sources/MeetingPipe/MeetingSessionController.swift#L266)) appends the elapsed offset to `markerSeconds`, calls `coordinator.hud.blink()`, and logs. `blink()` ([RecordingHUDWindow.swift:232](../../../daemon/Sources/MeetingPipe/RecordingHUDWindow.swift#L232)) animates the **whole panel's** `alphaValue` down to 0.4 and back:

```swift
/// FEAT8: a single quiet opacity blink acknowledging a flagged moment. No
/// persistent chrome. Under reduced motion it collapses to an instant
/// dip-and-restore.
```

So the entire acknowledgement is the panel going semi-transparent for one fast animation. That is the whole feedback loop, and three things make it read as no reaction rather than as a confirmation:

1. **It is not localized to the control.** A whole-window opacity change is the same gesture macOS uses for a window losing focus or being dismissed, so it reads as the HUD reacting to the click rather than to the flag. The button itself does not change at all.
2. **It is momentary and leaves nothing behind.** The comment's "no persistent chrome" is deliberate, but it means a user who blinked, or who is looking at the call window rather than the HUD, has no way to learn afterwards whether the press registered.
3. **It says nothing about what happened.** `flagMoment` computes both facts a person would want, the offset (`elapsed`) and which marker this is (`markerSeconds.count`), and sends **both to the log only**, at `:277-282`. The user-visible surface gets neither.

The consequence compounds because the markers are not visible anywhere else until much later either: `markerSeconds` is written out by `MarkerFile.write` at stop time ([:607](../../../daemon/Sources/MeetingPipe/MeetingSessionController.swift#L607)) and reset per recording ([:449](../../../daemon/Sources/MeetingPipe/MeetingSessionController.swift#L449)). So during the call there is no count, no list, and no undo, and the first confirmation that anything was flagged arrives after the meeting is over.

Both entry points share this: the control-row button and the right-click **Flag this moment** item ([RecordingHUDWindow.swift:625](../../../daemon/Sources/MeetingPipe/RecordingHUDWindow.swift#L625)) both route to the same delegate hop, which UX46 did correctly, so a fix at the acknowledgement is a fix for both.

## Scope

Replace the whole-panel dip with an acknowledgement that is local to the control and says what was recorded, using the two values `flagMoment` already has.

The register constraint is real and is why this is a task rather than a drive-by: `PRODUCT.md` calls the product quiet and deliberate, the HUD is a small always-on-top panel over a live call, and UX46 chose momentary-and-silent for a reason. The fix is a *legible* acknowledgement, not a loud one. Read `PRODUCT.md` and `design/README.md` before choosing.

Shapes worth weighing at pickup, roughly in increasing cost:

- A brief change on the button itself (fill, glyph swap to a filled flag, or a short scale) so the feedback is where the click was, instead of on the panel.
- A running count beside or on the button while the recording has markers, which is the persistent affordance the current design deliberately omits and the one that answers "did that register" without the user having to have been watching. `markerSeconds.count` is already the number.
- A momentary caption naming the offset, in the same slot the HUD already uses for its workflow line, so the user sees which moment was flagged rather than only that one was.

An undo is out of scope below, but note the count makes a later undo cheap, so do not design the count in a way that would preclude it.

The Transcript tab already anchors the saved markers to their segments after the fact ([TranscriptTab.swift:46](../../../daemon/Sources/MeetingPipe/TranscriptTab.swift#L46), reading `<stem>.markers.json`); this task is only about the live acknowledgement, so leave that alone.

## Explicitly not / out of scope

**Not the marker mechanism.** One writer, one file, correct offsets. FEAT8 built it and UX46 wired the second entry point; both are working and neither is touched.

**Not an undo or a marker list in the HUD.** The panel is 102pt of controls over a live call and a list does not belong there. The owner asked for an indication, not a manager. If an undo becomes wanted it is its own row.

**Not the reduced-motion path as a separate design.** Whatever replaces the blink must collapse sensibly under `MPMotion.reduceMotion` the way `blink()` already does, in the same code, not as a second implementation.

**Not keyboard operability of the HUD controls.** That is UX27, deferred at P4, and this task must not quietly re-open it.

**Not the hotkey path's silence when idle.** Pressing the flag hotkey outside a recording logs `marker_flag_ignored` and shows nothing. That is defensible (there is no HUD to acknowledge on) and is not what the owner reported.

## Acceptance

- The whole-panel `alphaValue` dip is gone as the acknowledgement for a flagged moment. A source-level test asserting `blink()` is no longer the flag path, or its removal, so the old behaviour cannot quietly return.
- A test drives two successive `flagMoment` calls during a recording and asserts the count the acknowledgement surface reads is 1 then 2, and that it resets to 0 on the next recording (the `:449` reset already exists and this pins that the surface follows it).
- A test asserts the acknowledgement state is derived from the same `markerSeconds` the marker file is written from, so the surface and the artifact cannot disagree about how many moments were flagged.
- A test asserts the right-click menu item and the button produce identical acknowledgement state, since UX46's single-writer property is what makes that true and it should stay pinned.
- Reduced motion is exercised by a test at whatever the new seam is, matching what `blink()` already covers.
- `cd daemon && swift build` clean, `swift test` green, with the number of tests this task adds recorded in the ship note. Do not pin an absolute suite total.
- No em-dashes in changed lines; repo dash guard green.

The visual judgement is owner-owed by construction: the daemon is a menu-bar app and is not screenshotable from a session, and this task's entire deliverable is what a control looks like when pressed.
