# DET17: A scheduled Google Meet whose tab is titled by the meeting name instead of a room code is never admitted, so browser Meet prompts in about 1 call of 6

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Sources: D001, D084 and D083 in the [recording reliability audit](../../audits/2026-11-13-recording-reliability-audit.md) and its [evidence file](../../audits/2026-11-13-recording-reliability-evidence.md); plan stage 4 ("Meet interim opener", patch E) in the same audit; the "A Google Meet call in a browser is rarely picked up" section of the audit and the [field evidence](../../audits/2026-11-13-field-evidence.md). Folded-in lows: D008 and D013 (same audit). Code re-read at HEAD 3a2da4fc on 2026-11-13.

**Regression.** [START2](../q5-final.md) (done, q5) promised that a plain-tab Meet call is discoverable by matching the page title against the browser adapter's patterns. END5 (88871c85, 2026-07-12) then narrowed `MeetingTitlePatterns.googleMeet` to "the host or the brand plus a 3-4-3 code", and that matcher is byte-identical at every work-laptop build era and at HEAD. START2's fix does not hold for the title a scheduled Meet actually shows.

**The matcher.** `MeetingTitlePatterns.googleMeet` in `daemon/Sources/MeetingPipeCore/Lifecycle/Adapters/LifecycleAdapter.swift` returns true only on `lowered.contains("meet.google.com")` or `lowered.contains("meet")` plus the `[a-z]{3}-[a-z]{4}-[a-z]{3}` code. Its comment says "A real in-call tab title always carries "Meet" ("Meet - abc-defg-hij", "abc-defg-hij - Google Meet")". On the work laptop the stable in-call title of a scheduled Meet in Chrome is the word Meet, a colon, a space and the meeting name in quotes, sometimes with Chrome's trailing speaker glyph, and never a code or the host (D084 checked every such title character by character without printing it).

**Two gates use that one matcher.**
- Admission: `MeetingSourceScanner.decideBrowserAdmission` admits on a URL fragment in the title (which never fires, DET6) or `browserWindowIndicatesStrongMeeting`, i.e. `BrowserMeetingLifecycleAdapter.strongTitleMatchers`, which holds only `googleMeet`. A named title matches no `defaultTitleMatchers` entry either, so the result is `.noMeetingSignal`, and the scanner's `case .noMeetingSignal: continue` writes no row (D083).
- Start: once engaged, `BrowserMeetingLifecycleAdapter.start` feeds `ShareableContentSignal` the same matchers over on-screen `SCWindow` titles (`getExcludingDesktopWindows(false, onScreenWindowsOnly: true)`), and a plain browser has no other primary signal that can read live (`WindowTitleSignal` is wired only when `handle.meetingWindow` exists, i.e. PWAs). A named title reads `window_present false`, so no `lifecycle/starting` and no prompt.

**Field evidence (work laptop, 2026-09-29 to 2026-11-13).** Chrome is the only browser in the log: 9 `discovery_shadow_pick` rows with `winner_kind browser`, 7 prompts, 1 recording. Six Chrome call episodes are counted: one recorded (stem 20261005-180843, title matched from first read to end) and five missed (1 certain, 3 probable, 1 possible).
- Chrome picks at 2026-10-06T08:58:38Z, 2026-10-07T09:03:34Z, 2026-10-21T12:32:54Z and 2026-11-11T13:59:31Z are each followed 25 to 181 ms later by `signal/shareable_content_window_present` value false, reason initial, and a `shareable_content_no_match` whose `candidate_titles` hold the named shape. No `lifecycle/starting` followed. The named title then stayed on screen 27.8, 13.6, 23.5 and 12.8 min (the last runs to the match at 14:12:18Z).
- 2026-11-11 is the certain call: the owner started stem 20261111-155951 by hand 21.5 s after the pick (`recording_started` with `bundle_id manual` at 13:59:52Z).
- 2026-10-07T12:00:03Z is the possible one: the title matched for about 0.5 s, the prompt lived 0.18 s, then the named shape returned.
- Replay: the widened shape matches 79 Chrome candidate titles on the four miss days (72 plain, 6 with the speaker glyph, 1 variant), where the current matcher matches 0. Of 83 Chrome candidate titles containing "meet" on those days, the other 4 are the bare word (3) and one starting with the Google brand; none carries a code or the host.

**Correction at filing (priority reason).** The class says 5 of 6 episodes got "no prompt at all". Four got no prompt at the call's start; on 2026-11-11 a prompt appeared only at 14:14:36Z, after the cut, and timed out; on 2026-10-07T12:00:03Z a prompt showed for 0.18 s. The P1 stands on the start misses.

**Correction at filing (which gate failed).** The class summary has `decideBrowserAdmission` returning `.noMeetingSignal` in the field misses. In all four logged misses the scanner did admit Chrome, on a title the log does not hold: `title_match` on `discovery_shadow_pick` is the scanner's hardcoded `preTitleMatch: true`, not proof of a code match (D084's verifier). The field audit reads it as a scan that landed on a load-time title. The observed failure is the adapter's `ShareableContentSignal`. The scanner gate fails on the same shape whenever no scan catches a load-time title, and that miss leaves no row by construction, so it cannot be counted (D083). Both gates need the shape.

**Correction at filing ("selected tab of an on-screen window").** `collectAXWindowTitles` reads every AX window of the browser, each showing its selected tab, on screen or not. Only the adapter's SCK read is on-screen only. So the "on-screen" half of the opener is enforced by the adapter, which is the gate that raises `.starting`, and that is where the scope puts it.

**The fence this task overrides on purpose.** `MeetingSourceScanner`'s admission comment says "Do not "fix" this by widening `strongTitleMatchers`: an unmeasured widening reopens the doc-title false start END5 closed", and DET6 holds that rule. This widening is measured, from the 79 captured field titles above. It is also narrow: the brand word must come first with a colon, so "Level 10 Meeting - Jira" (the 2026-06-30 false prompt) and "Meeting notes" cannot match. What is still unmeasured is the false-prompt rate: titles were only logged while Chrome was already engaged. Guard 1 below is what makes a false prompt cost a dismissal and never a recording.

**Folded-in lows.**
- D008 (code-derived, confirmed at filing): for a plain browser tab `ShareableContentSignal` is the only signal that can raise `.starting`, and it needs the Screen Recording grant. A browser meeting therefore never prompts without that grant. The docs describe the grant as audio-only: README's permission list says Screen Recording "gates `SCStream.capturesAudio` in TCC", `docs/SETUP.md`'s permission table says "The only way macOS allows capturing system audio", and the in-app `PermissionsCenter.Kind.rationale` says "Required for the other side of the call. Without it, recordings are mic-only."
- D013 (unverified low; code half confirmed at filing): a Chromium Meet PWA admitted by `matchesKnownMeetingPWA` with no matching title carries `titleMatch == false`. `readsProcessAudio` is native-only and the scan never sets `shareableContentActive`, so its only corroborators are the toolbar, Leave and Mute walks, and those run only when it is frontmost. So START3's name-only admission rarely wins. The field half ("false in both logged Safari picks") could not be checked: the work-laptop pack has no Safari or PWA rows, and the PWA branch handles Chromium prefixes only. Here it only means the fixture covers the code-less PWA shape.

**Filer's extension.** The audit's guard 1 names the timeout action only. "Always for Chrome" on the prompt's chevron (and `auto_consent_apps`) is the other no-click route: `handleMeetingStarted` calls `beginRecording` straight from idle for an auto-consented bundle. A browser source carries no audio evidence today, so this task applies guard 1 there too. The owner may drop that half.

## Scope

1. **One matcher for the named shape, in Core.** Add `MeetingTitlePatterns.googleMeetNamed`: the brand word Meet at the start of the title, a colon, then a non-empty rest, allowing a trailing speaker glyph. It is anchored and whole-word, so "Meeting...", "Meet the team..." and the bare word Meet do not match. Add it to `BrowserMeetingLifecycleAdapter.defaultTitleMatchers` and `strongTitleMatchers`, so `decideBrowserAdmission` admits it and `ShareableContentSignal` reads it live. Rewrite the scanner's "Do not widen" comment and the `googleMeet` comment to cite the fixture, not a guess.
2. **Captured-shape fixture.** Add a fixture of title shape classes, never real titles, with synthetic placeholder names. Positive: named, named plus glyph, room-code forms, host form. Negative: bare Meet, "Google Meet" landing, "Meeting notes - Google Docs", "Level 10 Meeting - Jira", a "Meet the team" page, "Webex vs Zoom Comparison". Also the code-less PWA shape for D013. Both matchers and `decideBrowserAdmission` are tested over it.
3. **Guard 1: a browser source is never recorded without a click.** In `MeetingSessionController.startPromptTimeout`, when `source.kind == .browser`, a `record` or `byo` default action acts as `skip`. The `prompt_timeout` row carries `default_action` as configured plus `effective_action`. In `handleMeetingStarted`, an auto-consented `.browser` source prompts instead of calling `beginRecording`. Every plain browser source is title-only at HEAD (no mic read), so this applies to room-code Meet tabs too, until [DET20](./DET20.md) or the browser reducer adds microphone evidence.
4. **Guard 2: a skipped or timed-out browser prompt is remembered per tab, not per browser.** For `.browser` sources, the timeout and Skip paths do not call `DetectionStateMachine.abandonPrompt`'s bundle-wide `recordCooldownEnd` and `armSkipLatch`. They record an in-memory key for that tab instead (bundle, window identity and a hash of the title; never logged, never persisted). The same tab re-sighted does not re-prompt; a different Meet title in the same browser does. The Skipped notification's Start recording action (`notifySkippedMeeting`) and the menu's suppressed row (`statusUI.setSuppressed`) stay available while that tab is sighted. Coordinate with [DET18](./DET18.md), which owns the general bundle-keyed latch: this item is only the browser exception.
5. **Count the misses.** When a listed browser shows the Meet brand in any AX window title and `decideBrowserAdmission` does not admit, emit `detector` / `browser_identity` with `bundle_id`, `shape` (a fixed class name such as `meet_bare`, `meet_landing`, `meet_other`) and `admitted: false`. Never a title. Throttle it on a (bundle, shape) signature, as `emitRejectedBrowserTabs` throttles `browser_tab_rejected`. Document it in `CONVENTIONS.md`'s event schema.
6. **Copy (D008), same commit.** README's permission list, `docs/SETUP.md`'s permission table and `PermissionsCenter.Kind.screenRecording`'s rationale each say Screen Recording is also what lets the app notice a meeting in a browser tab. `docs/GUIDE.md`'s "a small panel appears" recipe gains the browser specifics: the Meet tab has to be the selected tab of a window on screen, and an unanswered browser prompt never records by itself.
