# CI11: CI installs whatever uv is newest while the owner runs uv 0.11.8, so the tool that resolves and syncs the lock can differ silently between the two

Band origin: filed 2026-11-12 from the dependency, platform and AI-model upgrade review (owner approved "File all proposed"). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

On 2026-11-12:
- The owner's `uv --version` reports 0.11.8 (2026-04-27). PyPI's latest uv is 0.13.7 (2026-11-03).
- The pipeline job in `.github/workflows/ci.yml` runs `astral-sh/setup-uv@v3` with `enable-cache: true` and no `version:`, so each run installs the newest uv.
- `pipeline/pyproject.toml` has no `[tool.uv] required-version`.

CI8 documented the same class of failure for ruff: CI floated onto 0.16.0 while `uv.lock` pinned 0.15.12, and the two disagreed silently for weeks. uv is the tool that reads the lock (`uv sync --frozen`). A uv minor that changes resolution, lock revision handling or marker evaluation would show up in CI only, or only locally.

## Scope

1. Add `[tool.uv] required-version = "==<chosen>"` to `pipeline/pyproject.toml`, so a local uv outside the pin fails loudly.
2. Pass the same version to setup-uv's `version:` input.
3. Choose the version deliberately: either the owner's 0.11.8, or upgrade the owner to the latest and pin that.

DIST7 bumps and SHA-pins the action itself. Coordinate so the `version:` lands on whichever action reference DIST7 leaves.

## Explicitly not

- Not the action's own major or SHA pin (DIST7).
- Not pinning Xcode on the daemon job (CI9).

## Acceptance

- `uv sync --frozen` with a uv outside the pin fails with uv's required-version error.
- The CI log's setup-uv step reports the pinned version.
- `bash scripts/ci-local.sh pipeline` is green.
