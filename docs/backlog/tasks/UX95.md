# UX95: two SwiftUI views reassign a defaulted @State in init, the pattern the SDK 27 @State macro documents as not producing the expected value

Band origin: filed 2026-11-12 from the dependency, platform and AI-model upgrade review (owner approved "File all proposed"). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

In SDK 27, `@State` changed from a property wrapper to a macro. Apple's SDK 27 SwiftUI notes ("@State as Macro") warn that "assigning a new value to a `@State` property that has an initial value is an anti-pattern and won't produce the expected behavior". Their example is a view whose `body` sees the declared `0`, not the `42` its init assigned. The documented fix is to drop the initial value at the declaration and assign only in `init`.

The owner builds against SDK 27.2, and on 2026-11-12 the debug build was clean. So these are not compile errors. A grep of `daemon/Sources` for `State(initialValue` found seven sites. Five of them, the `TranscriptTab.swift` editors, declare their `@State` without a default and are fine. Two match the warned pattern:

- `SavedSearchViews.swift`, the saved-search rename view: `@State private var name: String = ""`, then `init` sets `_name = State(initialValue: initialName)`.
- `ClarifySheet.swift`: `@State private var scope: String?`, an implicit `nil` default, then `init` sets `_scope = State(initialValue: Clarify.defaultScope(workflowName: target.workflowName))`.

## Scope

- **[owner]** Open the saved-search rename sheet on an existing saved search: does the field show the current name? Open the Clarify sheet on a meeting with a workflow: is the default scope preselected?
- **[session]** For any view that misbehaves (or for both, if the owner prefers not to rely on it), remove the declared default so `init` is the only assignment. For the optional, use `@State private var scope: String?` with no `= nil` and keep the init assignment, per the reference.

## Explicitly not

- Not a sweep of all 211 `@State` declarations. Only init-assigned ones are affected.
- Not ARCH15's `ObservableObject` to `@Observable` migration.

## Acceptance

- The owner's two checks are recorded here.
- After the change, a grep for `@State` declarations with an initializer whose owning type also assigns `_<name> = State(initialValue:` returns nothing. Add that grep as a test or a fence if cheap.
- `cd daemon && swift build` and `swift test` are green.
