# OBS2: Degraded summaries are recorded as ordinary successes: an `auto` run that dropped to local on a rejected key, a failed language repair, and an unparseable speaker-cleanup reply leave no event and no field a reader can key on

Band origin: filed 2026-10-25 from the 2026-10-25 observability audit band ([audit](../../audits/2026-10-25-observability-audit.md) row O7: PY-3, FB-3, PY-4). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Re-verified against `main` at `01e904a` on 2026-10-25. None of the four paths below was observed in the owner's logs on this Mac (`config.toml` pins `backend = "anthropic"`, and `pipeline.log` holds no "falling back to local", "language repair" or "diarize cleanup" WARNING line), so every claim rests on the code read. Each is reachable in ordinary use.

**1. The `auto` ladder drops to local with a log line only.** `backend_fallback.run_with_local_fallback` is the one ladder for both `summarize.AutoFallbackClient` and `engine.AutoTextClient` (PIPE7). On a cloud failure in `fallback_exceptions()` (which includes `anthropic.AuthenticationError` and `anthropic.PermissionDeniedError`) or `is_billing_exhaustion`, it does `log.warning("Anthropic backend failed (%s); falling back to local", e)` and returns `local(), "local"`. There is no `events.emit` in the module, and `AutoFallbackClient.summarize` only sets `self.last_used_backend = backend`, so `corrections.write_run_sidecar` records `"backend": "local"` with nothing beside it. The daemon reads that value into `Meeting.backend` (`MeetingStore`) and the detail header's provenance line (`MeetingDetailView+Header.provenanceEngine`) renders it as "Local", the same as a deliberate local choice. A revoked key or an empty balance therefore turns every later meeting, Ask and digest into a 7B local summary with no surface saying so. Contrast `engine.complete_text`, which emits `engine_backend_substituted` for its own Apple-to-local substitution precisely because "a log line is not a surface" (PIPE12).

**2. The language repair fails quietly.** `summarize._verify_and_repair_language` (LANG1) logs `"language repair call failed (%s); keeping the original summary"` on an exception and `"language repair still diverges (%s); keeping the original summary"` when the retry is no better, then returns the wrong-language summary. The local path, `LocalSummaryClient._retry_on_language_mismatch` (LOCAL7), differs from the finder's description in one detail: a retry that parses is kept even when sections still diverge (it logs `"diverging sections now: %s"` at info), and only a retry that fails to parse keeps the first summary. Either way no event records that a summary shipped in the wrong language, which is the LANG1 case.

**3. An unparseable cleanup reply reads as "nothing to fix".** `diarize_cleanup._parse_edits_from_text` returns `[]` when neither the stripped reply nor `_largest_balanced_json_object` decodes, and the Anthropic client returns `[]` when the reply has no `tool_use` block. `cleanup_transcript` then emits `pipeline.diarize_cleanup` with `merges_count=0`, identical to a model that read the transcript and found no error. DIAR5's owner dwell (in [owner-verification.md](../owner-verification.md)) asks whether the pass helps, and cannot tell those two apart.

**4. The staged local path drops windows silently.** `summarize_staged._extract` logs `"staged extract window %d failed (%s); skipping it"` and continues, and the compose of a section or the title does the same; the closing `staged_local_summary` event carries `windows` and `facts` but no failed count. This path is latent behind `MP_STAGED_LOCAL`, which nothing sets (PIPE20), so it is the smallest leg here.

## Scope

1. **`backend_fallback` event.** In `run_with_local_fallback`'s fallback branch, emit `events.emit("pipeline", "backend_fallback", ...)` carrying `from_backend="anthropic"`, `to_backend="local"` and the `failure_details.describe(e, operation=...)` fields `cause`, `http_status` and `request_id` (never the message text). Add an `operation` keyword (`summary`, `ask`, `digest`) so the event says which caller fell back; the two call sites pass it. The missing-key branch stays info-level and emits nothing: no key configured is a choice, not a degradation. Keep `describe`'s import lazy, as `is_billing_exhaustion` already does.
2. **Run sidecar fields.** `run_with_local_fallback` returns the cause alongside the backend (or `AutoFallbackClient` records it) so `write_run_sidecar` can write `fallback_from` and `fallback_cause`, both absent on a run that did not fall back. `summarize.rewrite_run_sidecar` (PIPE11) carries them the same way. `CONVENTIONS.md` has no `<stem>.run.json` schema section today, only scattered mentions, so the two keys are documented beside the "Never launder the mismatch" rule, which already says the sidecar records what served rather than what config asked for.
3. **Library surface.** `MeetingStore` decodes `fallback_from` / `fallback_cause` into `Meeting`, and the provenance line in `MeetingDetailView+Header` reads, for example, "Local (Anthropic rejected the key)" through `SummarizationEngine`'s vocabulary, with the cause mapped to a short phrase. No new badge on the list row: the detail line is where the engine is already named.
4. **`language_check` event.** `_verify_and_repair_language` emits `pipeline.language_check` with `target`, `diverging` (the section names) and `repair` in `{ok, failed, still_divergent}` whenever a section diverged; nothing when the language cannot be checked or every section matched. `_retry_on_language_mismatch` emits the same action with `repair` in `{ok, unparsed, still_divergent}`, so the local client's own repair is visible too.
5. **`parse_failed` on the cleanup event.** Count windows whose reply did not parse (or carried no `tool_use` block) through `_gather_edits` and add `parse_failed_windows` to the `diarize_cleanup` event and the `<stem>.diarize_cleanup.json` audit, so `0 merges, 0 parse failures` and `0 merges, 3 of 3 windows unparsed` read differently.
6. **Staged count.** Add `windows_failed` and `sections_failed` to `staged_local_summary` (and to `staged_local_declined` when it fires after failures).

## Explicitly not / out of scope

- Failing the run, or refusing to fall back, on a rejected key. The ladder is the documented `auto` contract; the defect is that it is silent. A user-visible notice for a run that fell back belongs with UX90's done-notification variants and is not added here.
- Which exceptions the ladder catches: PIPE24 (529 overload) and PIPE28 (`NotFoundError` on a retired model id) own that set.
- Recording the transcript text or the model's raw reply in any event: the events carry counts, section names and typed causes only.
- A Library filter or list-row badge for degraded summaries. The fields make one possible; whether it is wanted is a separate decision.
- The Apple Intelligence language refusal: PIPE25.

## Acceptance

- `pipeline/tests/test_backend_fallback.py`: an `AuthenticationError`, a billing-exhaustion 400 and an `APIConnectionError` each emit one `backend_fallback` with the right `cause` and `operation`; the missing-key branch emits none; a `BadRequestError` that is not billing still raises and emits none.
- A run-all or summarize test on `auto` with a cloud stub that raises `AuthenticationError` writes `<stem>.run.json` with `backend: local`, `fallback_from: anthropic` and `fallback_cause: rejected_key`; a clean cloud run writes neither key.
- `test_summary_language.py` (or `test_summarize.py`): a repair that raises emits `repair: failed`, one that still diverges emits `still_divergent`, a clean repair emits `ok`, and a matching summary emits nothing. One local-client case for `unparsed`.
- `test_diarize_cleanup.py`: a fake client that returns unparseable text for every window produces `parse_failed_windows` equal to the window count and `merges_count=0`; a clean empty-edits reply produces `parse_failed_windows=0`.
- `test_summarize_staged.py`: one failing extract window is counted in `windows_failed`.
- `MeetingStoreTests` decodes the two keys; a header test renders the fallback phrase for a `rejected_key` cause and the plain label when the keys are absent.
