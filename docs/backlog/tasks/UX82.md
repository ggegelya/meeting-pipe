# UX82: Quit exits 1 so launchd relaunches the app, a crash loop restarts every 10 s forever, the termination ceiling calls exit() off main, and the Accessibility relaunch restarts onboarding at Welcome

Band origin: filed 2026-10-24 from the 2026-10-24 audit band ([architecture review](../../audits/2026-10-24-architecture-review.md) M7 and M11, [go-live assessment](../../audits/2026-10-21-go-live-assessment.md) UX-13). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

**Quit overloads the exit status.** TECH-UX7 (2026-05-28) changed the LaunchAgent to `KeepAlive = { SuccessfulExit = false }` (`scripts/launchd.plist.template`) and made `AppDelegate.flushAndExit` end with `exit(relaunch ? EXIT_FAILURE : EXIT_SUCCESS)`, where `AppDelegate.shouldRelaunchOnQuit(override:disableAutoRestart:)` is `override ?? !disableAutoRestart` and `UISettings.disableAutoRestart` defaults to false. So the menu's plain "Quit MeetingPipe" (Cmd+Q) exits 1 and the app comes back; only "Quit (do not relaunch)" (Opt+Cmd+Q, offered by `StatusBarModel.offersQuitWithoutRelaunch` only while the agent is enabled) exits 0. That was the owner's choice for the primary user, and `docs/GUIDE.md` documents it ("**Quit MeetingPipe** is not the one that closes it for good"). The costs:

- To launchd, a requested relaunch and a crash are the same event. Nothing in the logs or in `launchctl print` distinguishes them.
- There is no crash-loop breaker. The plist's only guard is `ThrottleInterval` 10 ("Don't fork-bomb if we're crashing on launch"), so an app that crashes during start relaunches every 10 s indefinitely. Nothing in `daemon/Sources` counts launches.
- Copy depends on the relaunch: `PipelineSectionView` tells the user a setting "applies once the daemon relaunches (Quit from the menu bar)", and GUIDE's Accessibility recipe says to "quit and reopen". `SingleInstanceGuard.standDownExitStatus` "Must stay 0" for the same reason.

**The termination ceiling exits from a background thread.** `AppDelegate.armTerminationCeiling` schedules `DispatchQueue.global(qos: .userInitiated).asyncAfter(deadline: .now() + 9)` and calls `exit(...)` there. `exit` runs `atexit` handlers and C++ static destructors on that thread while the main thread may still be inside `coordinator?.shutdown()` and audio render threads are live, which can turn a wedged quit into a crash report (and, with KeepAlive, a relaunch). `_exit` ends the process without running them. Both log lines before it (`Log.writeLine`, `Log.event`) are synchronous `FileHandle` appends today, so nothing is lost by skipping the handlers.

**The Accessibility relaunch restarts onboarding.** `OnboardingStepPermissions` tells the user "After granting, quit and reopen MeetingPipe for it to take effect" (UX21: macOS caches AX trust per process at launch). `OnboardingRootView` keeps its position in `@State private var step = 0` and `OnboardingGate` only records completion, so after the relaunch the window opens at "Step 1 of 5", Welcome, and the user walks the steps again. There is no button to relaunch; the user has to find Quit.

## Scope

0. **Owner decision, before any code: should plain Quit relaunch by default?** The options are (a) keep TECH-UX7's default (Quit relaunches unless "Relaunch after quitting" is off), or (b) Quit means quit, with relaunch-after-quit an opt-in. Items 1 to 3 hold under either; only the default of `disableAutoRestart` and the GUIDE copy change.
1. **Make a requested relaunch distinguishable from a crash.** Exit 0 on every quit the user asked for without a relaunch, and exit with one dedicated status for a requested relaunch (for example `EX_TEMPFAIL`, 75), written as a named constant beside `standDownExitStatus`. Before that exit, persist a one-shot "relaunch requested" marker in `UserDefaults` so the next launch can tell it was asked for. Recorded so it is not re-litigated: `launchctl kickstart` was the audit's suggestion, but the running job cannot kickstart itself without `-k`, which kills the caller mid-teardown; the pickup confirms this with `launchctl` on the owner's machine before rejecting it for good.
2. **Crash-loop breaker.** At the top of `App.main` (after `SingleInstanceGuard.standDownIfPeerIsRunning`, before the `Coordinator` exists), record the launch time in `UserDefaults`, ignoring launches that follow the item 1 marker. If more than 5 unrequested launches fall within 60 s, start in a safe idle mode: status item and menu only, no detection, no recorder, no preloader, one notification ("MeetingPipe stopped after crashing repeatedly"), a menu row to try a normal start, and a `daemon` `crash_loop_tripped` event with the launch count. Staying alive keeps launchd from respawning; the user's Quit then exits 0.
3. **`_exit` in the termination ceiling**, keeping both log lines before it. If PERF13's logger queue lands first, the ceiling drains it synchronously before `_exit`.
4. **Resume onboarding after the Accessibility relaunch.** Add "Relaunch MeetingPipe" beside the Accessibility row's notice. It persists the current step index in `UserDefaults`, then takes the item 1 requested-relaunch path; `OnboardingRootView` starts at a persisted step and clears it. Only the Permissions step (index 1) is resumable; the later steps hold `OnboardingWorkflowChoice` in memory (WF9) and resuming into them is not attempted.
5. Docs in the same commit: `docs/GUIDE.md` (the Quit rows and paragraph, the Accessibility recipe), `docs/SETUP.md` where it tells the user to quit and reopen after a grant, and the `PipelineSectionView` copy that relies on Quit relaunching.

## Explicitly not / out of scope

- Changing `SuccessfulExit = false` or `ThrottleInterval` in the plist. The breaker lives in the app so it can show the user what happened; launchd has no window.
- UX84's onboarding wiring (presets, the test recording, Dock presence, the tutorial disagreeing with first run). Only the restart-at-Welcome half of go-live SA-7 is here; UX84 must not re-file it.
- Making Accessibility trust apply without a relaunch. macOS caches it per process (UX21); this task only makes the relaunch one click.
- `rebuild.sh` and `install.sh` restart paths, which `bootout` and `bootstrap` the agent and do not depend on the exit status (DIST5 owns installer correctness).

## Acceptance

- `AppDelegateRelaunchTests` extended: a requested relaunch maps to the dedicated status and writes the marker; a plain quit with relaunch disabled maps to 0; the stand-down status stays 0.
- A pure `CrashLoopBreaker` (launch history in, verdict out, injected clock) with at least 5 tests: 5 launches in 60 s do not trip, 6 do, launches after a relaunch marker do not count, old launches age out, the history is bounded.
- A test pins that the ceiling's exit call is `_exit` (the `terminationCeilingExits` hook stays so the test runner survives).
- `OnboardingGateTests` or a new suite: a persisted step resumes at Permissions and is cleared after use; no persisted step starts at Welcome.
- `cd daemon && swift test` green, `bash scripts/ci-local.sh` green, N new tests in the commit body.
- Owner walkthrough (confirms, does not gate): Cmd+Q behaves as decided in item 0; granting Accessibility during onboarding and pressing Relaunch returns to the Permissions step with the row reading Granted.

## Amendment 2026-11-13 (audit band)

Source: [independent audit](../../audits/2026-11-12-independent-audit.md) F165 and F209, both low and listed only in its low table, so both were re-verified here in full against `main` at `3a2da4fc` on 2026-11-14 by code reading. Neither has been observed in the field. Both are quit-path gaps in the same `AppDelegate.flushAndExit` path this task already reworks.

**F165: SIGTERM is handled only on main, so a main thread already wedged never arms the ceiling.** `AppDelegate.installTerminationSignalHandler` does `signal(SIGTERM, SIG_IGN)` and handles the signal on `DispatchSource.makeSignalSource(signal: SIGTERM, queue: .main)`, whose handler calls `flushAndExit()`. `armTerminationCeiling()` is the first statement of `flushAndExit`, so it too runs on main. REC13's ceiling therefore bounds only a wedge that begins after the handler runs. When main is already wedged as the signal arrives, the event waits behind the wedge, the ceiling is never armed, and the default disposition has been removed. Correction at filing: "ignored outright" holds for a hand `kill`, which then does nothing at all; under launchd the process still dies, by SIGKILL once launchd's exit timeout passes, so the outcome there is a SIGKILL with no flush and no `daemon` `termination_ceiling_exceeded` row rather than a process that never exits.

**F209: a quit while `stop()` is in flight skips the termination flush.** `Coordinator.shutdown` calls `recorder.flushIntermediatesForTermination()` only `if recorder.isRecording`, `MeetingRecorder.isRecording` is `currentFile != nil`, and the flush itself opens with `guard let final = currentFile else { return }`. `MeetingRecorder.stop` calls `endSession()` first, which sets `currentFile = nil` ("so `isRecording` is false before anything below can re-arm or re-surface it"), then suspends at `await systemChannel.haltCapture()`, `teardownEngine()`, `drainWriters()` and `mergeIntermediates(...)`. Main is free during those awaits, so a quit or SIGTERM in that window runs `flushAndExit`, skips the flush, and exits with the writers undrained and the files unfinalized. The start-time manifest still lets the next launch's orphan sweep merge what reached disk, so the loss is whatever the writers had not drained, which is exactly what the flush exists to save.

**Scope additions:**

5. (F165) Take the signal off main. Install the SIGTERM source on a dedicated serial queue whose handler arms the ceiling first and then hands `flushAndExit` to main. Make the arm idempotent so `applicationWillTerminate` and the signal path arm one ceiling between them. Item 3's `_exit` applies to it unchanged.
6. (F209) Let the termination path see a stop in flight. The recorder keeps what `stop()` snapshotted (the final URL and its writers) until `finalizeFiles()` has run, and `shutdown` flushes when the recorder is recording or stopping; the flush works from that snapshot rather than `currentFile`, and is a no-op once the stop has finalized its files.

**Acceptance additions:**

- (F165) A test that the SIGTERM source's queue is not main and that its handler arms the ceiling before dispatching to main (a source fence in the `AppDelegateRelaunchTests` style is enough; a real signal would kill the runner), plus a test that arming twice schedules one ceiling.
- (F209) A recorder test: with a stop suspended after `endSession()` (an injected drain that waits), `flushIntermediatesForTermination()` drains and finalizes the session's writers; after the stop has finalized, it does nothing. A `Coordinator` test or fence that `shutdown` flushes on the stopping state.
- `cd daemon && swift test` green and `bash scripts/ci-local.sh` green, with the number of tests added in the commit body.

**Known limits, recorded rather than fixed.** The breaker reaches only fast crash loops: at launchd's 10 s `ThrottleInterval`, six launches span about 50 s, so only a crash within roughly 12 s of start trips it, and a later one loops untripped. A tripped launch still runs `App.main`'s pre-AppKit work (the single-instance guard, `LaunchRecord.begin`, the SEC8 Keychain migration, the model-token seed), so a crash there defeats the safe mode. `agent_job` rests on launchd setting `XPC_SERVICE_NAME` to the job label, which the owner's first `launched` row after install confirms (it should read `true` for the login-started copy); if it reads `false` there, Restart and onboarding's Relaunch are hidden everywhere, which fails safe.

**Owner question (open, does not block).** After a Quit and a reopen by hand, the running copy is not the agent's job, so it has no Restart row and no crash recovery until the next login. Should a hand-opened copy hand itself back to the agent (for example quit and `launchctl kickstart` the job), or is that fine as it is?

**Remainder.** F209 (item 6): a quit while `stop()` is between `endSession()` and `finalizeFiles()` still skips the termination flush. Doing it means the flush draining writers that `stop()` is itself awaiting a drain of, which needs the recorder to hand one owner the writers; unobserved in the field, and the orphan sweep merges what reached disk. **Owner checks** (installed build): the first `main` / `launched` row after install reads `agent_job: true`; Cmd+Q leaves the app closed and it does not come back; after logging in again, **Restart MeetingPipe** brings it back within a few seconds; with Relaunch after quitting on, Cmd+Q comes back and Opt+Cmd+Q does not; on a fresh onboarding, granting Accessibility and clicking **Relaunch MeetingPipe** returns to the Permissions step with the row reading Granted.

## Amendment 2026-11-21 (second fix review)

Found by the [second fix review](../../audits/2026-11-21-second-fix-review.md) (storage report, M2), confirmed by reading the code at `8426758b`.

Confirmed as built, and consistent with the spec's choice to stay up until the owner acts: `SafeModeController` has no timer and no re-evaluation, and the only ways out are its menu rows (`tryNormalStart`, which resets `CrashLoopBreaker` and requests a relaunch, and Quit). The cost is the case this task was filed for. A start-time crash tied to something transient (a device or window state present at login, a config value fixed a minute later) trips the breaker during a call, the cause then goes away, and every meeting for the rest of the day is missed with one notification and a warning icon as the only signals. Before UX82 the respawn loop would have healed at its next attempt.

Owner decision: keep safe mode sticky, or add one bounded automatic retry (a single requested relaunch after 10 to 15 minutes, counted by the breaker like any other launch, so a persistent crash returns to safe mode and stays there). If taken, acceptance: a breaker test where the retry launch crashes and no second retry is scheduled, one where it succeeds and the count resets, and a `safe_mode_auto_retry` event row. `swift test` green, 2 new tests.
