# REC17: a system-audio start that never returns is invisible to every fence, so 64 minutes of the far side went missing with no banner and the idle backstop nudged as if everyone had left

Band origin: filed 2026-09-17 from the owner asking why the "Still in a meeting?" notification fired twice during a live Teams call. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

The nudges were the symptom. The defect underneath is that `SystemAudioCapture.start()` has no bound, and a start that neither returns nor throws is a state none of the recording-integrity fences ([REC4](../q5-final.md), [REC8](./REC8.md), REC9, REC13) can see. On 2026-09-17 it stayed in that state for 64 minutes, the far side of the call was silence for all of it, and the only thing the owner was told was that nobody seemed to be talking.

## What happened, from the logs

That is the backstop working as designed on a genuinely quiet tail. The 2026-09-17 pair looked the same on screen and meant something entirely different.

## Why every layer stayed quiet

- **Nothing bounds the start.** `MeetingRecorder.startSystemCapture` runs `systemStartTask = Task { try await capture.start() ... }` with no timeout. Inside `SystemAudioCapture.start()`, both `SCShareableContent.excludingDesktopWindows(false, onScreenWindowsOnly: true)` and `try await stream.startCapture()` are unbounded awaits. The repo already bounds every neighbouring call for exactly this reason: `stop()` bounds the same start task with `runWithTimeout(seconds: 5, { await startTask?.value })` and the capture's `stop()` at 5 s (REC7), CONC3 gave `ShareableContentSignal` a 2 s `probeTimeout` around the same `SCShareableContent` call, and REC13 wrapped the engine calls in `runWithTimeout` and `boundedEngineStart`. The start of the system channel is the one call in the chain that was never bounded.
- **The liveness watchdog cannot see it.** `MeetingRecorder.checkSystemLiveness` opens with `guard isRecording, systemCapture != nil, systemFires > 0 else { return }`. The gate exists so the SCStream spin-up does not false-positive, and it means a stream that never spins up is never examined: no `system_capture_stall_detected`, no `handleSystemAudioLost`, no HUD banner, no REC8 auto-retry.
- **The retry cannot reach it.** `MeetingRecorder.retrySystemAudio` opens with `guard isRecording, systemCapture == nil, let systemURL = systemURL else { return }`. `startSystemCapture` assigns `self.systemCapture = capture` before the start task runs, so the hung capture holds the slot and a manual retry is a no-op, the same shape REC4 fixed for the `didStopWithError` path.
- **The idle backstop reads "never came up" as "silent".** `MeetingSessionController.engageMicGate` sets `latestSystemLevelDb = -120` at engage, `onSystemLevel` is only ever called from the system tap, and `armSystemLevelMirror` derives `hasSystem = Double(self.latestSystemLevelDb) > Self.systemSilenceThresholdDb` (-50 dB). A channel that never delivered a buffer and a channel delivering silence are the same value, so the moment the mic verdict went `muted_by_app` the streak ran unopposed.
- **The stop-time warning keys off the wrong two facts.** `remoteAudioWarning` sees `systemFires > 0` and `degraded == false` and says nothing. Sixty-four minutes of padded silence at the head is neither "mic-only" nor "interrupted" in its vocabulary.

## Scope

Three seams, smallest change first. Items 1 and 2 are the fix; item 3 is what stops the symptom from misleading the owner while the fix is degrading gracefully.

1. **Bound the system-audio start** in `MeetingRecorder.startSystemCapture`, wrapping `capture.start()` in `runWithTimeout` (abandon-on-timeout, the semantics `stop()` already relies on). Budget: the pickup session picks it; 10 s is 3.5x the worst healthy start of the last eight days (2.82 s on 2026-09-14), 24x under the owner's 240 s nudge, and still under the 30 s nudge the Preferences slider produces at its 60 s floor. A timed-out start emits `recorder`/`system_capture_start_timed_out` (`budget_s`, `is_retry`) and one `recorder.log` line, then routes through `handleSystemAudioLost(reason: "system_capture_start_timed_out")` so the existing chain does the rest: `systemCapture = nil` (retry reachable), `systemDegraded = true`, `onSystemAudioDegraded` (the HUD banner with its Retry button), and `scheduleSystemAudioAutoRetry` (REC8's one hands-off retry). `handleSystemAudioLost` guards on `let dying = systemCapture`, which the hung capture satisfies, so no new entry point is needed.
2. **Fence the late completion.** This is the part that makes item 1 safe rather than merely loud. After a timeout the abandoned `Task` keeps running inside ScreenCaptureKit, and on 2026-09-17 it did complete, 64 minutes later. As written, that late completion would log `SCStream started`, clear `systemDegraded`, and, if a retry had meanwhile opened or resumed the system file, deliver a second stream's buffers into the same `systemWriter` (its callback only checks `self.systemFile != nil`). `SystemAudioCapture.stop()` cannot pre-empt it either: it is `guard let stream = stream else { return }`, and `self.stream = stream` is assigned only after `startCapture()` returns. The fence: a capture that has been abandoned must, when `startCapture()` finally returns, stop that stream at once rather than adopt it, and must deliver no buffers. A small pure ledger (`SystemCaptureStartAttempt` or similar: `timedOut()` then `completed()` yields `.discard`, `completed()` first yields `.adopt`) keeps that decision testable without SCK; `SystemAudioCapture` gets a cancel flag the delegate and the post-`startCapture` path both consult. `handleSystemAudioLost`'s existing `Task { await dying.stop() }` stays, since it is correct for the recovered-then-lost shape.
3. **Teach the idle backstop that a down system channel is not a silent one.** `IdleStopBackstop.ingest(verdict:hasSystemAudio:at:)` gains a system-channel state (`.live(hasAudio:)` / `.down`), and `.down` holds the streak rather than advancing it. `MeetingSessionController.armSystemLevelMirror` feeds `.down` while the recorder reports the channel degraded or not yet started, and `.live` once the first buffer has arrived. The mic-only-by-permission case keeps its current behaviour: `Screen Recording denied` is a chosen state, the config key is literally `mic_only_silence_seconds`, and the backstop was built for it (TECH-C7). The dogfood record shows the backstop has never auto-stopped a real meeting, so holding it during an outage costs nothing measurable, and the HUD's degraded banner is the surface that tells the owner what is actually wrong.

Alternatives the pickup session should not re-litigate:

- **Changing the nudge copy instead of holding the streak** ("System audio is not being captured" in place of "No audio for a while") still fires a notification every 240 s for the length of the outage, on top of the HUD banner that already says it. Rejected.
- **Dropping the `systemFires > 0` gate from `checkSystemLiveness`** would make the watchdog fire 3 s into every healthy spin-up (the 2026-09-14 start took 2.82 s) and re-introduce the false positive the gate was written against. The bound belongs on the start, not on the watchdog.
- **Skipping the fetch when the cache is empty and failing fast** trades a slow start for a guaranteed mic-only recording after every dock/undock. REC5 made the re-fetch deliberate. Rejected.

## Explicitly not in scope, and observed but not filed here

- **Why ScreenCaptureKit took 64 minutes.** The daemon's `os.Logger` lines are INFO and are not persisted, and `log show` over the start window returned nothing for `MeetingPipe` or `replayd`, so the pickup session should not spend time on the cause. The fix is to bound and surface, the same stance REC7 took on the 2026-06-05 `stopCapture` hang.
- **The HAL storm at 12:34Z.** 1381 subscribe/unsubscribe cycles in 37 s is the daemon's own `halbus` re-subscribing on `process_audio_object_resolved` churn at roughly 37 Hz. It is unique in this log generation, it coincided with the start completing, and nothing here explains it. Named so it is not lost; not filed, because one occurrence with no user-visible cost is a watch, not a task.
- **The stop-time warning for a padded head.** A recovered outage clears `systemDegraded`, so `remoteAudioWarning` never mentions a gap the merge padded; only `intermediate_durations.head_offset_sec` records it. With items 1 and 2 the HUD banner is visible for the whole outage, so the owner is told during the meeting rather than after; whether the stop should also say "the first N minutes of the other side are missing" is a separate UX question. Not filed.
- **The `mute_state_window_disagreement` / `mute_state_cleared_blind` rows** at 11:30:57Z to 11:31:10Z are the known Teams two-window mute shape and unrelated.
- **REC8's owner-owed eyeball** (a killed SCStream recovering hands-off) is unchanged by this task and stays REC8's.

## Acceptance

- A test pins the bound: a `SystemAudioCapture`-shaped start that never completes produces `system_capture_start_timed_out` and reaches `handleSystemAudioLost` within the budget, after which `systemCapture` is nil (so `retrySystemAudio` is reachable) and `systemDegraded` is true. Where the recorder needs a live engine to reach that path, pin the pure ledger from item 2 instead and add a source-text fence in the `CaptureHealthREC16Tests` style asserting `startSystemCapture` awaits `capture.start()` only through `runWithTimeout`.
- A test pins the late-completion fence: `timedOut()` then `completed()` yields `.discard`; `completed()` alone yields `.adopt`; a discarded completion delivers no buffers and clears nothing.
- `IdleStopBackstopTests` gains the `.down` scenarios: a down system channel with a silent mic advances neither horizon across the full auto-stop window; the channel coming back `.live(hasAudio: false)` starts the streak from that moment, not from engage; `.live(hasAudio: true)` still resets it; and the existing fifteen scenarios keep their meaning through the signature change.
- The two existing surfaces keep working: the HUD banner appears within the budget of a hung start and its Retry button reaches `retrySystemAudio`, and REC8's auto-retry fires 7 s after the timeout (a `system_capture_auto_retry` row follows the `system_capture_start_timed_out` row).
- `README.md`'s troubleshooting entry "The recording is missing system audio (only my voice)" and `docs/GUIDE.md`'s backstop paragraph (under the Accessibility-missing recipe, "There is a backstop: after a long stretch of silence...") are updated in the same commit if their wording stops being true, per the same-commit contract in the root `CLAUDE.md`.
- `swift build` and `swift build -c release` clean with no new warnings, `swift test` green with the number of tests recorded in the ship note. Do not pin an absolute suite total.
- `python3 scripts/truth_fences.py both` green. `recorder` is an existing event category, so nothing is owed to the `CONVENTIONS.md` category table.
- No em-dashes in changed lines.
