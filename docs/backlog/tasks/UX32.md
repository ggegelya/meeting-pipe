# UX32: Workflow row quick actions (swipe + context menu)

Band origin: filed 2026-07-29 (owner exploratory sweep, item 1: "assess the possibility to have swipe actions on workflow rows, for removing, to make it simple"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Deleting a workflow today is a five-step gauntlet: select the rail row, have no meeting selected so the inspector appears (see UX33 on that reachability catch), click "Edit workflow", find Delete in the sheet, confirm. WF9's owner-owed cleanup (four duplicate "Client work" rows, a stub, a duplicate "Personal") pays that path once per row, which is exactly the friction that prompted this filing.

The feasibility question the owner asked is settled by the code: the WORKFLOWS rail is a real SwiftUI `List` (`LibrarySidebar.swift:21`, `.listStyle(.sidebar)` at :124), not a custom stack, so `.swipeActions` works on macOS without custom gestures. Workflow rows are the `ForEach` at `LibrarySidebar.swift:73-83` rendering `WorkflowScopeRow` (:409-474), and they carry no row-level affordances at all: no `.contextMenu`, no `.swipeActions`, only a `.help` tooltip (:467). The precedent is one section up in the same file: saved-search rows attach a context menu with Rename, Update, and a `role: .destructive` Delete (`LibrarySidebar.swift:56-61`).

One AppKit escape hatch shares that List: `.noNativeListSelection()` (:127) reaches into the backing `NSTableView` to set `selectionHighlightStyle = .none` (`NoNativeListSelection.swift:39-48`). It touches only the highlight style and should not block swipe actions, but it is the one thing worth a smoke test before committing to the swipe half.

UX30 (filed 2026-07-23, re-confirmed by the owner 2026-07-29) owns the delete flow's defects: neutral styling, the sheet not closing, a refused delete being invisible, and the alert copy understating that past meetings drop out of the WORKFLOWS rail. This task must not fork a second delete path around those fixes.

## Scope

Add two entry points to each workflow row, both routed through one shared delete flow:

1. A context menu on `WorkflowScopeRow` mirroring the saved-search precedent: "Edit workflow..." (opens the existing editor sheet for that row) and "Delete workflow..." with `role: .destructive`.
2. Trailing `.swipeActions` with the same two actions (Delete full-swipe disabled; destructive actions should not fire on momentum alone).

The delete goes through the same confirmation alert and the same store call the editor sheet uses, extracted to one host-level helper if needed so UX30's fixes (honest refusal surfacing, corrected alert copy) apply to both surfaces by construction. The default workflow's Delete is disabled with a visible reason, matching UX30's truthful-disabled requirement (`WorkflowStore.delete` refuses the default and returns `false`; `WorkflowsView.swift:612` already disables in the sheet).

Sequencing note: UX30 should land first or together; if this lands first, it must not duplicate the broken flow, it must extract-and-share it.

## Explicitly not in scope

Drag-to-reorder workflows (order is a store field edited elsewhere; separate concern). Multi-select of workflow rows. Duplicating a workflow from the menu (nothing asked for it; YAGNI). UX30's editor-sheet fixes themselves. Any change to `WorkflowStore.delete` semantics.

## Acceptance

Tests pin: the context menu offers Edit and Delete for a non-default workflow and a disabled-with-reason Delete for the default; the row delete path and the editor delete path invoke the same underlying flow (one implementation, asserted by both call sites hitting the same seam); a refused delete surfaces a reason (inherited from UX30's fix, pinned here for the row entry point).

Smoke-verified: swipe actions render and fire on a row in the real List despite `.noNativeListSelection()` (owner eyeball, since swipe rendering is not unit-testable).

`cd daemon && swift build` and `swift test` green (baseline at filing: 1770 tests). Repo dash guard green (no U+2014 in changed lines).

Owner eyeball: right-click a duplicate "Client work" row, Delete, confirm; the row disappears without opening the editor. Swipe left on another; same result.
