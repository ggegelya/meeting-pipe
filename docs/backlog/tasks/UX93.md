# UX93: Every stem-less failure notice is titled "Processing could not finish" and every job failure "Couldn't create the summary", whatever failed, and a stem-less notice's message is gone after a relaunch

Band origin: filed 2026-10-25 from the 2026-10-25 observability audit band ([observability audit](../../audits/2026-10-25-observability-audit.md) row O13, UI-1). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Re-verified against `main` at `01e904a` on 2026-10-25 by code reading. None of these branches has fired on the audit Mac (`events.jsonl` from 2026-10-12 to 2026-10-24 has no `recording_error`, `force_stop` or stop-stall row), and the installed build there predates UX80's title mapping, so the current copy has never been seen live.

**`notifyError` has no operation.** `Notifier.notifyError(_ message: String)` is `notifyFailure(FailurePresentation(diagnostics: message))`, so the operation defaults to `.processing` and the title is `FailureMetadata.Operation.processing.failureTitle`, "Processing could not finish". All 20 callers pass only a string. Among them: `MeetingSessionController` for the missing mic permission, "Could not start recording: ...", the stop-stall watchdog's `StopStallWatchdog.stallMessage` ("Still finishing a recording after N seconds..."), and "Could not finalize <file>"; `Coordinator` for the write-failure force-stop ("Recording stopped: couldn't keep writing <channel> audio to disk ...") and the quarantined-orphan notice; `MeetingLibraryService` for naming, rename, reassign, reset and merge failures. The [GUIDE](../../GUIDE.md) section 1 "Stopping" recipe promises a notification when finishing takes much longer; it is titled "Processing could not finish" while the recording is still being finished.

**The body hides the message and the dialog promises a retry that does not exist.** A stem-less notice's body is "Review failure details.". Clicking it opens `FailureDialog.show`, an alert with **OK** and **Details…** only. The recording messages match none of `FailurePresentation.isValidation`'s prefixes, so the cause is `.unknown` and the explanation is "Retry when you are ready, or open Details to inspect the failure.": there is nothing to retry from that dialog, and after a failed recording start there is nothing to retry at all.

**Job failures are all "summary".** `Coordinator`'s `onFailure` posts `FailurePresentation(error: error, operation: .summary)` with the stem. A transcription failure (`SinkDispatcher` records stage `.transcribe` with `error.localizedDescription`) or a SEC16 hold-back (stage `.transcribe`, `heldBackReason`) is not a `reportedFailure`, so `FailureMetadata.from` returns nil and the legacy metadata keeps `.summary`: the banner says "Couldn't create the summary" while the Library row for the same meeting, which maps `failureStage` in `MeetingDetailView.failureNotice`, says "Couldn't transcribe the recording".

**Stem-less Details do not survive a relaunch.** `Notifier.failures` holds the presentation in memory only, capped at 30 and evicted by `failures.keys.sorted().first`, which is random UUID order rather than age. After a relaunch the click handler falls back to `FailurePresentation(diagnostics: "")`: generic title, the retry line, and an empty Details pane.

**Narrowed from the finder (skeptic correction).** Job failures carry the stem: their body is "Review in Library.", `userInfo["failureStem"]` survives a relaunch, and the click opens the Library row through `openMeeting(stem:)`, which has the right title and the full reason. So for job failures only the banner title is wrong, and the lost-Details problem is confined to stem-less notices. Each recording branch also writes its own event (`recording_blocked`, `recording_error`), so a trace exists.

## Scope

1. **An operation per call site.** Add `recording` ("Couldn't record the meeting") and `people` ("Couldn't save the name") to `FailureMetadata.Operation`, Swift side only: they label notifications and are never written to a `<stem>.error.json`, so `failure_details.OPERATIONS` and the sidecar contract stay unchanged (an unknown `operation` in a sidecar makes `FailureMetadata.decode` return nil today, which is why they must stay out of it). `notifyError` takes a required `operation:` and an optional `title:` for the few sites whose title must say more than the operation: the force-stop ("Recording stopped early"), the stall ("Still finishing the recording"), finalize ("Couldn't finish the recording file"), and the quarantine ("Recordings kept for review"). Library naming, rename, reassign, reset and merge use `.people` or `.storage` as fits. No caller is left on the `.processing` default; make the parameter non-defaulted so the compiler enforces it.
2. **The message is the body.** A stem-less notice's body is the message itself (truncated to one line by the system as usual), not "Review failure details.". The dialog's explanation for an `.unknown` cause on a non-retryable operation (`recording`, `people`, `storage`) is the message, and the "Retry when you are ready" sentence is used only where a retry is actually offered.
3. **Job failures share the Library's mapping.** Extract `MeetingDetailView.failureNotice`'s stage-to-operation mapping (`publish` to `.publish`, `transcribe` to `.transcribe`, else `.summary`) into one function on `FailurePresentation` and use it in `Coordinator`'s `onFailure`, taking the stage from the `PipelineFailureSidecar` the dispatcher has just written for that stem. Banner and row then agree by construction.
4. **Persist what a stem-less click needs.** Put the operation, title and message (the same text as the body, so nothing new is disclosed to Notification Center's store) in `userInfo`, and rebuild the presentation from it when `failures` has no entry. Never put the full diagnostics or a traceback in `userInfo`. Evict `failures` by insertion order.
5. **Docs in the same commit.** [GUIDE.md](../../GUIDE.md) section 1, "Stopping": the slow-finish notice is titled "Still finishing the recording". Section 10, "A meeting that failed": the Details paragraph's last sentence (an error notification opens its meeting when one is known) gains that a notice with no meeting shows its message in the banner and keeps it after a restart. REC19 owns the force-stop's disk-full wording; this task changes only its title, so coordinate if both are in flight.

## Explicitly not / out of scope

- The force-stop message wrongly blaming a full disk at the WAV size cap: REC19.
- A Retry action on stem-less notices. Nothing stem-less is retryable as a job.
- Notification delivery, permission and the backstop nudge: UX92. Plain-language wording across notifications: UX86 (this task introduces no jargon and removes none).
- Held-back recordings being reaped and offered a futile Retry: SEC26. This task only makes the hold-back banner say what the Library row says.
- Python's failure taxonomy (a config cause is UX94's; structured failure payloads are OBS3's).
