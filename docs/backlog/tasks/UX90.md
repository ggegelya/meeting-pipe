# UX90: A publish that fails after the summary is written never reaches the menu's failed row, a partial publish notifies "Meeting published", and a paste-bundle skip notifies "Meeting processed" and logs "pipeline OK"

Band origin: filed 2026-10-25 from the 2026-10-25 observability audit band ([observability audit](../../audits/2026-10-25-observability-audit.md) row O3, UI-2 and FB-9). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Re-verified against `main` at `01e904a` on 2026-10-25 by code reading. Not reachable on the audit Mac (its `config.toml` enables only the filesystem sink, and its one `publish.json` is `state: full`); reachable on any multi-sink setup and on any cloud-engine meeting past the long-meeting gate.

**The menu's durable failed row skips every stem with a summary.** `MeetingStore.unrecoveredFailureStems(fileNames:now:)` is the only input to `MeetingLibraryService.failedMeetingCount()`, which feeds `StatusBarModel.failedMeetingsTitle` ("⚠ N meetings failed - open Library to retry"). Its loop starts with `if f.summary { continue } // produced: supersedes a stale error`, before the error sidecar is looked at. Its doc comment says it matches `buildMeeting`'s `.failed` precedence so "the badge and the Library list agree"; it does not. `buildMeeting` keeps the failure when `summaryURL == nil || recorded.stage == .publish`, or when a structured failure (`recorded.metadata != nil`) is newer than the summary. So an all-sinks-failed publish (exit 3, `<stem>.error.json` with stage `publish`, beside a `summary.json`) and a failed regenerate over an existing summary are both shown in the Library's Needs you rail and never counted in the menu. `MeetingStoreTests.test_unrecoveredFailureStems_finds_error_without_summary` pins the current skip (`c.error.json` plus `c.summary.json` is not counted).

**A partial publish is counted nowhere outside the Library.** A run where one sink lands and another fails exits 0 and writes `<stem>.publish.json` with `state: "partial"`. `buildMeeting` derives `failureReason` and `failureStage: "publish"` from it and `LibraryScope` puts `publishState == "none" || publishState == "partial"` in Needs you, but the filename-only menu scan cannot see the state at all. `StatusBarModel.failedMeetingsTitle`'s own doc calls the row the durable backup to a notification missed under Focus, which is exactly what it is not for these cases.

**The done banner announces a clean publish.** `PublishLanding.decide(publish:pageURL:)` returns `.sink` only when `landed.count == 1`, otherwise `.unnamed`, and never reads `PublishResult.state` or the failed sinks. `DoneNotificationCopy.make(landing:canCorrect:)` returns `title: "Meeting published"` whenever an open phrase exists. With Notion and the filesystem both configured and the Notion token expired, every meeting notifies "Meeting published / Open the local note" and the menu shows nothing. The per-sink `publisher/sink_failed` event (`publish_router.py`) does record the failure in `pipeline_events.jsonl`, so the log has a trace; the user-facing surfaces do not.

**A paste-bundle skip is announced as processed and logged as OK.** `orchestrate.run_all` returns `_skip_result(t, "byo", ...)` or `_skip_result(t, "too_long", ...)` and `main` exits 0, leaving `<stem>.READY_FOR_MANUAL.md` and no summary. The daemon's `.success` branch in `SinkDispatcher` writes `Log.writeLine("daemon", "pipeline OK -> \(pageURL?.absoluteString ?? "(local-only)")")` and `pipeline_succeeded` with only `file` and `page_url`. `Coordinator`'s `onDone` special-cases only `EmptyMarker.read`, so the run falls through to `notifyDone`, whose copy carries the comment "The summary exists (the title says so)" above `title: "Meeting processed"` and "Nothing was published.". The pipeline's own `run_skipped` event does say why; the daemon log and the banner contradict it. Past PIPE27's gate (about an hour on a cloud engine) the owner is told the meeting was processed while it is waiting for a manual paste.

This breaks [PRODUCT.md](../../../PRODUCT.md)'s "never hide a failure" on the path the GUIDE's "A destination refused it" recipe describes.

## Scope

1. **One precedence, two readers.** Extract the failure-selection rule `buildMeeting` applies (summary absent, or failure stage `publish`, or a structured failure newer than the summary; plus `publishState` `none` or `partial`) into one pure function in `MeetingStore`, and have both `buildMeeting` and the menu count call it. `unrecoveredFailureStems` keeps its filename pass and adds a content pass that reads only what the rule needs: `<stem>.error.json` (stage, metadata presence, mtime) for stems that carry it beside a summary, and `<stem>.publish.json`'s `state` for stems that carry one. The readers are injected so the function stays unit-testable without disk. `MeetingLibraryService.failedMeetingCount` caches the decoded state per stem keyed by file mtime so an unchanged library reads nothing twice per menu open; record the timing on a 500-stem fixture in the commit body. Fix the doc comment. The row's copy stays as is ("failed - open Library to retry" is true of a destination that failed).
2. **A partial variant of the done banner.** `DoneNotificationCopy.make` takes the run's `PublishResult` (already loaded by `Notifier.publishResult(stem:recordingsDir:)`) and, when `state == "partial"`, returns title "Meeting partly published" and a body that names the failed destination by `PublishSink.displayName` before the open phrase (for example "Not sent to Notion. Open the local note."). The Open action still opens what landed. `state == "none"` with a page URL cannot occur; leave the existing branches unchanged.
3. **A paste variant.** `Coordinator`'s `onDone` checks for `<stem>.READY_FOR_MANUAL.md` after the `EmptyMarker` check, the same file-presence idiom, and posts title "Ready for your summary", body "Open it in the Library to paste a summary.", with a click that opens the meeting (`openMeeting(stem:)`). No completion tone. ARCH10's `--result` envelope replaces the file probe when it lands; do not wait for it.
4. **Say it in the log.** `pipeline_succeeded` gains `publish_state` (`full`, `partial`, `none`, or null when no `publish.json` was written) and `skip_reason` (`paste` when the bundle exists, else null), and the daemon line reads `pipeline skipped (paste bundle)` or `pipeline OK (partial: <failed sinks>) -> <url>` instead of a bare OK.
5. **Docs in the same commit.** [GUIDE.md](../../GUIDE.md) section 10, "Anything else", the "A destination refused it" paragraph: say the banner reads "Meeting partly published" and names the destination, and the menu's failed row counts it until it is retried. Section 10, "A meeting that failed": the menu row now counts publish failures too. Section 1, "BYO, when you would rather write the summary yourself": the banner says "Ready for your summary". Update the Notification mockup in `design/ui_kits/macos_app/Notification.jsx` only if it gains the variants; the shipped strings are the contract.

## Explicitly not / out of scope

- Changing what `mp run-all` returns or exits with (ARCH10 owns the result envelope; the exit-3 contract in CONVENTIONS stays).
- A per-sink retry button in the banner. Retry stays in the Library, which already offers **Retry publishing** for a partial.
- Distinguishing `byo` from `too_long` in the banner. Both leave the same bundle and need the same paste; the reason stays in `run_skipped`. PIPE27 decides which engines the gate applies to.
- The no-speech and suspect-transcript skips: `EmptyMarker` already gives them honest copy.
- Structured failure payloads on `pipeline_failed` (OBS3) and degraded-success events such as a backend fallback (OBS2).

Replace `test_unrecoveredFailureStems_finds_error_without_summary`'s `c` assertion with the stage-aware one. A test that `buildMeeting` and the menu count agree on the same fixture directory.
