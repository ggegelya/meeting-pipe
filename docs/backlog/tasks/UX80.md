# UX80: Replace raw error dumps with clear messages, recovery actions, and bounded details

Band origin: filed 2026-09-11 at the owner's request after a read-only assessment on 2026-09-10 of failed meetings in the Library. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Problem and incident evidence

The owner reported that error text occupied most of the Library window, could not be scrolled, and pushed other controls outside the visible area. They asked for short explanations such as an expired-key message when justified, a useful fallback for unknown failures, and a small way to inspect details or prepare a report. The assessment examined the screenshot, the five meetings' saved failure records and event logs, and the code. It did not retry a meeting, call an API, or reproduce the layout in a running app. Filing this task does not authorize implementing it or processing the owner's meetings.

The stored failures distinguish two causes. All five recordings and finalized transcripts were present at assessment time; none had a summary, publish result, or run receipt. These are historical outcomes, not a check of the account's current balance or credential validity.

They do not establish why the application restarted. The screenshot's `20260903-113309` row separately carries `reason: "no_speech"` in its empty marker; it is not an API failure.

## Causal chain

1. [summarize.py](../../../pipeline/src/mp/summarize.py) propagates the provider exception. `orchestrate.main` in [orchestrate.py](../../../pipeline/src/mp/orchestrate.py) logs it with a traceback and returns exit 1. `summarize.main` has no equivalent general exception handler, so standalone regeneration has a different failure boundary. `_should_retry_anthropic` already excludes billing and authentication failures from automatic retries; the traceback's retry-wrapper frames do not prove that this billing request was retried.
2. [PipelineLauncher.swift](../../../daemon/Sources/MeetingPipe/PipelineLauncher.swift) retains the last 4,096 stderr bytes. `failureCaption(stderr:)` prefers an ERROR/CRITICAL record, then WARNING, then the entire retained tail. A long traceback can evict its leading ERROR record and leave the whole tail as the caption. `LaunchError.errorDescription` adds `pipeline exited 1:`. Full process output already goes to the local pipeline log.
3. [SinkDispatcher.swift](../../../daemon/Sources/MeetingPipe/Coordination/SinkDispatcher.swift) stores the localized error description as the failure reason. [PipelineFailureSidecar.swift](../../../daemon/Sources/MeetingPipe/PipelineFailureSidecar.swift) keeps the coarse stage, reason, and timestamp but has no separate cause or user-facing explanation. [MeetingStore.swift](../../../daemon/Sources/MeetingPipe/MeetingStore.swift) passes the reason to the views.
4. `MeetingDetailView.publishStateInfo` in [MeetingDetailView+Header.swift](../../../daemon/Sources/MeetingPipe/MeetingDetailView+Header.swift) appends the entire reason to `Processing failed`. `publishStateLine` renders it with `.fixedSize(horizontal: false, vertical: true)`, with no height or line bound. `MeetingDetailView.chromeBand` in [MeetingDetailView.swift](../../../daemon/Sources/MeetingPipe/MeetingDetailView.swift) places that header above the tabs, outside the content scroller.
5. `SummaryTab.failedState` in [SummaryTab.swift](../../../daemon/Sources/MeetingPipe/SummaryTab.swift) repeats the same reason inside a 150-point scroller. That bounds only the second copy; it cannot constrain the header. `MeetingLibraryService.retryMeeting` in [MeetingLibraryService.swift](../../../daemon/Sources/MeetingPipe/Library/MeetingLibraryService.swift) sends non-publish failures through the full recording job, even when a usable transcript already exists. `regenerateMeeting` provides an existing transcript-reuse path.

## Scope

### Separate diagnostics from presentation

Introduce one small, pure failure-presentation model that derives a short title, explanation, and recovery action from known facts. Keep raw diagnostics separately. Carry optional structured failure metadata from Python while the native exception is still available: a stable cause code, provider, operation, retry/remedy classification, and HTTP status/request identifier when present. Cover the existing command-specific catch boundaries, including `orchestrate.main`, standalone summarize, Ask, and publishing; a top-level catch alone misses errors already handled below it. Reuse the process communication seam rather than adding a reporting service or dependency.

Keep the daemon as the writer of `.error.json`. Preserve the existing stage and exit-code contracts, including publish exit 3 and cancellation. Persist the optional metadata so a restart does not lose the explanation. Read old stage/reason-only sidecars without rewriting them. Use narrowly recognized legacy signatures for known causes; absent, unknown, or malformed metadata must produce a short fallback while retaining available diagnostics. A generic HTTP 400 does not mean insufficient credits, and HTTP 401 alone does not establish expiry.

### One compact notice, with bounded details

Replace the duplicate Library explanations with one compact notice and contextual actions. The header, tabs, and content must remain reachable regardless of diagnostic length. Show raw diagnostics only after an explicit **Details…** action, in a bounded, scrollable sheet with selectable text and a visible close control. The Details control must be keyboard-accessible and VoiceOver-labelled; its visual size must not make its click target difficult to use.

Use this copy as the reference for the confirmed billing case, adapting the saved-artifact sentence to what actually exists:

> **Insufficient Anthropic credits**
>
> The summary could not be created. Your recording and transcript are saved. Add credits to your Anthropic account, then retry.
>
> Open billing · Retry summary · Details…

### Cause-specific recovery

| Confirmed cause | Expected presentation and action |
|---|---|
| Insufficient provider credits | Name the provider and credit problem; offer its billing page and an explicit retry after resolution. Do not claim the key expired. |
| Missing or rejected key | Explain whether the key is missing or was not accepted; open the relevant Integrations settings. Use expiry language only with explicit provider evidence. |
| Connection failure, temporary rate limit, timeout, or service outage | Give the specific short explanation when known and offer Retry. Do not conflate a permanent quota/billing refusal with a temporary rate limit. |
| Restart interrupted processing | Say **Processing interrupted** and offer the least work needed to resume. Preserve the separate wording and notification suppression for a run the user cancelled. |
| Unknown failure | Use operation-specific copy such as **Couldn't create the summary**, with Retry and Details. Do not claim that waiting will fix an unknown cause. |
| Missing model, insufficient memory, or a failed publish destination | Preserve the existing concrete remedy and name the affected operation or destination. Preserve any successful summary and other successful destinations. |

Route summary retries through the existing serialized job lane and reuse a valid, finalized transcript when no re-transcription is required. Preserve workflow/privacy policy resolution, provenance, duplicate-click coalescing, and cancellation. Do not offer a route that silently changes the backend or bypasses an NDA/local restriction. Publishing-only retries continue to use the saved summary.

### Apply the presentation rule across existing error surfaces

Audit and adapt the verified raw-error paths: Library row/detail retry dialogs and summary paste failures; `AskModel.outcome` and `AskView` error cards; `DigestsView.errorBanner`; `PeopleView.errorBanner`; `LibraryDialogs` failures; Preferences integration/model/storage failures; and `Notifier.notifyError`. Relevant files live under [the daemon source directory](../../../daemon/Sources/MeetingPipe/). Ask already scrolls, so its known defect is technical copy; Digests and People also have vertically expanding banners outside their lists. Trace additional callers of the changed failure transport and include any that expose the same diagnostic text.

Retain contextual titles such as **Couldn't create the digest** and **Couldn't rename this voice**. Notifications contain short copy and a useful route to the affected in-app surface where context is available. Existing concise validation messages should retain their specific instructions. Diagnostic windows remain places for technical detail, with bounded scrolling.

### Local report preparation

Add **Copy report** inside Details, with a preview of the exact exported content. Use a small allowlist of diagnostic fields, including app version, timestamp, failed operation, cause/provider, status, and request identifier where available. Exclude API keys, authorization headers, request/response bodies containing meeting content, transcript or audio content, meeting titles, personal paths, and unrelated log history. Do not copy the raw traceback wholesale and call it sanitized. Copying and previewing must work without network access.

Update [GUIDE.md](../../GUIDE.md) and affected [README.md](../../../README.md) recipes in the implementation commit. Document any cross-process/sidecar changes in [CONVENTIONS.md](../../../CONVENTIONS.md), add contract fixtures, and update existing generated fixtures when their writer changes. Update tutorial/design representations only where the changed controls make their current claims stale.
