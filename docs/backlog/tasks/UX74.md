# UX74: every duration readout is the audio file's mtime, so a touched recording reads as hundreds of hours

Band origin: filed 2026-08-10 from the owner's 2026-08-04 testing notes: "Meeting time causing some questions. If I select 'All time' I see untagget set to 2406 h. and total time 2469 h. It is 100 full days on avg which seems impossible. there seems some mistake or something, need verification." Verified: the mistake is real and it is arithmetic, not display. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

`Meeting.durationSec` is not a duration. It is the audio file's last-write time minus the timestamp encoded in the stem ([MeetingStore.swift:565-569](../../../daemon/Sources/MeetingPipe/MeetingStore.swift#L565)):

```swift
if let audio = audio {
    let mtime = (try? audio.resourceValues(forKeys: [.contentModificationDateKey])
        .contentModificationDate)
    duration = mtime.flatMap { $0 > startedAt ? $0.timeIntervalSince(startedAt) : nil }
} else {
    duration = transcriptJSON.flatMap { readJSON(at: $0) }.flatMap { $0["audio_seconds"] as? Double }
}
```

While nothing but the recorder ever writes the `.wav`, mtime really is the moment recording stopped and the proxy is right. The instant anything else touches the file (a copy, a restore, an `rsync`, a backup tool, a metadata rewrite) the value becomes "recording start to whenever that happened", which is unbounded and grows with age.

The honest number is in the sibling branch and is only consulted when the audio is **absent**. So the reliable source is skipped precisely when a file exists to be misread.

## Reproduced against the owner's live library, 2026-08-10

The owner's two reported figures reproduce almost to the digit, which is what identifies the mechanism rather than merely agreeing with the complaint.

| Quantity | Computed here | Owner's screenshot |
|---|---|---|
| Total, all time | 2473.9 h | 2469 h |
| Untagged, all time | 2407.1 h | 2406 h |
| Total real audio | **75.8 h** | not shown |

267 recordings. Summing `max(0, mtime - stemStart)` gives 2473.9 h; summing the WAV headers gives 75.8 h. The rail is over by a factor of **33**.

Five stems carry 2392.7 h of it, **96.7% of the headline figure**:

|---|---|---|---|---|
| `20260429-212202` | 544.6 h | 9.0 s | 9.0453125 | null |
| `20260429-212609` | 544.6 h | 8.0 s | present | null |
| `20260429-212712` | 544.5 h | 5.9 s | present | null |
| `20260501-113427` | 506.4 h | 5.7 s | 5.7 | null |

All five are early-corpus recordings of a few seconds each, all five have no workflow in their meta sidecar, and that is the whole explanation for the second reported number: with no workflow they bucket under `MeetingStats.untaggedName`, so the Untagged row absorbs nearly the entire artifact and the owner's 2406 h is 2392.7 h of file-mtime plus a genuine untagged remainder.

The proxy also fails quietly on real meetings, not only on these five. It is an upper bound in every case (any post-stop write only ever moves it up), so the rail's *shape*, "where did the hours go", is skewed even after the outliers are removed.

## Three surfaces read it, not one

The Meeting time rail is where the owner noticed it, but the same value drives:

- `MeetingStats.MeetingFacts.durationSec` ([MeetingStats.swift:414](../../../daemon/Sources/MeetingPipe/MeetingStats.swift#L414)), hence every AI8 row: hours, average length, and the Total line.
- The Library list row's length label ([MeetingRow.swift:152](../../../daemon/Sources/MeetingPipe/MeetingRow.swift#L152)).
- The meeting detail header's length ([MeetingDetailView+Header.swift:346](../../../daemon/Sources/MeetingPipe/MeetingDetailView+Header.swift#L346)), the "32:57" beside the date.

Those last two read plausibly on most meetings, which is why this survived: the proxy is usually right, so the two per-meeting surfaces look fine and only the aggregate makes the outliers visible.

`MeetingStats.derive` and `accumulate` were read and are correct. Do not go looking there.

## Scope

Make `MeetingStore` derive duration from the audio itself and treat mtime as the last resort it always should have been.

Preference order at the seam above:

1. The transcript sidecar's `audio_seconds`. Measured coverage on this library: **220 of 249** transcripts carry it, and it is exact for the five stems above (9.0453125, 5.7, 6.3 all match the WAV header). The current code already knows how to read it; the change is consulting it before the file stat rather than only when the file is gone.
2. A header read of the audio when there is no `audio_seconds` (29 transcripts here, plus any row whose transcript has not been written yet). `AVAudioFile.length / processingFormat.sampleRate` is header-only and cheap. Note `WaveformPeaks.swift:116` already computes exactly this (`Double(totalFrames) / sampleRate`), so there is a working example in-tree, but it sits behind a full peaks decode; do not reuse that path, only its arithmetic.
3. Mtime, last, and clamped. It is the only source available for a still-recording row and for a `.wav` with no transcript at all, so it should not be deleted; it should stop outranking the truth.

The comment at `:560-564` explains the current order and becomes false with this change. Rewrite it rather than leaving it.

Keep the caching behaviour intact: duration is computed inside the same per-stem derivation that `cacheable` governs, and a `.done` row's value is cached. A header read is cheap but it is not free, so it must not run on every rescan of every row.

## Explicitly not / out of scope

**Not a repair of the five stems' mtimes.** Touching the owner's recordings to fix a display bug is the wrong direction, and it would hide the defect rather than fix it. They are the regression fixture.

**Not a clamp alone.** Rejected: capping the proxy at some plausible ceiling would make the five stems stop shouting while leaving every other row silently over-reported, and it invents a magic number where an exact answer is on disk.

**Not `MeetingStats`.** Its bucketing, ordering and formatting were read against the reported numbers and are correct. The defect is entirely upstream of it.

**Not the retention path.** `AudioRetention` reads `isSettled`, not `durationSec`, so no reclaim decision is affected by this. Checked so the next session does not have to.

**Observed but not filed:** 29 of 249 transcripts have no `audio_seconds` at all. That is fine for this task (step 2 covers them) but if it turns out to be a writer gap rather than old-format residue, it deserves its own row.
