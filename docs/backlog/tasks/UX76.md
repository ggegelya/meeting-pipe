# UX76: three accreted captions on the workflow rail row truncate the workflow name itself

Band origin: filed 2026-08-10 from the owner's 2026-08-04 testing notes, with a screenshot: "left panel has some small issues related to readability. check screenshot 'personal' workflow. none of the words properly read. perhaps we need to switch UI and use different approach here." Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The owner's screenshot of the Library rail's WORKFLOWS section reads:

```
General                              54
Pers… · defa… · no c…               120
Client work · no context              2
```

The middle row is their main workflow (105 of the library's meetings at the time CAL3 measured it) and its **name is the first thing truncated**. The row identifies nothing.

The cause is accretion, visible in the source. `WorkflowScopeRow` ([LibrarySidebar.swift:472-513](../../../daemon/Sources/MeetingPipe/LibrarySidebar.swift#L472)) puts five things in one `HStack` under a single `.lineLimit(1)`:

1. the optional emoji
2. `Text(workflow.name)`, the only element that identifies the row
3. `· default` when `workflow.isDefault`
4. `WorkflowNameCollision.railCaption(others:)`, WF9's duplicate-name note
5. `· no context`, FEAT11's `WorkflowContextHint.listMarker`

Then `.lineLimit(1)`, a `Spacer(minLength: 0)`, and the count.

Each caption arrived with its own task and each is individually defensible; the source comments say so, and they are right about the information. What nobody owned is the **total width budget**. In a fixed-width rail with five siblings competing, SwiftUI truncates them all, and the name has no priority over the decorations describing it. The other two rows corroborate the mechanism precisely: `General` carries no captions and reads fine, `Client work` carries one and keeps its name, `Personal` carries two and loses everything.

So the row degrades exactly backwards. The name is what the user clicks; the captions are footnotes about the name. When space runs out the footnotes should go first, and instead they survive at the name's expense.

## Scope

Make the workflow name legible at any rail width, and stop the captions competing with it.

The owner's own read ("perhaps we need to switch UI and use different approach here") is the right frame: this is a layout-policy question, not a tuning question, and picking the smallest change that keeps all five facts on one line would reproduce the defect at a slightly narrower rail. Decide the policy first, then implement it.

Directions worth weighing at pickup, in increasing order of how much they change the row:

- **Priority.** Give the name `.layoutPriority` above the captions so they truncate first and the name truncates last. Smallest possible change, keeps the current shape, and is enough if one caption at a time is the normal case.
- **Demote the captions to non-text.** The two markers are booleans, so they do not need words: a small glyph or dot with the existing `.help` text carries the same information at a fraction of the width. FEAT11's marker already has `listMarkerHelp` attached for exactly this, and its accessibility label is already the long form.
- **Two lines.** Name on the first line, captions on a second in `fgSubtle`. Costs vertical space in a rail that has plenty and removes the competition entirely.

Constraints the pickup must respect:

- **The three facts stay reachable.** `· default`, the WF9 collision note, and FEAT11's no-context marker each exist because a task established the user needs them. This task changes how they are presented, never whether they are present. Whatever replaces a word must keep its `.help` and its accessibility label.
- **The DSN3 floor.** Contrast at 4.5:1, and `fgFaint` does not clear it while `fgSubtle` does, so a caption demoted visually must not be demoted into `fgFaint`. Dynamic Type applies: no new `.system(size:)` literals, which the CI font-size guard flags on any changed line.
- **The tooltip layering already in the file.** FEAT11's `.help` is on the `Text` rather than the row specifically so it does not fight WF9's row-level tooltip. Do not collapse them.

Also in scope, since it is the same row and one pass is cheaper than a second row later: check the smart-folder and saved-search rows above ([:409](../../../daemon/Sources/MeetingPipe/LibrarySidebar.swift#L409), [:454](../../../daemon/Sources/MeetingPipe/LibrarySidebar.swift#L454)) for the same competition. They looked simpler when read on 2026-08-10 but were not measured.

## Explicitly not / out of scope

**Not removing any of the three captions.** WF9 and FEAT11 each established the need. Presentation only.

**Not the rail's width or a resize handle.** A wider rail postpones the defect rather than fixing it, and the row must read at whatever width the rail is.

**Not the meeting counts.** The trailing number and its dimmed-when-zero treatment (TECH-UI-8) rendered correctly in the screenshot.

**Not the INSIGHTS section below.** The screenshot shows `Facts 54` rendering fine, and UX68 owns Preferences scroll position, not this.

**Not WF9's underlying duplicate-name situation.** Its own comment is explicit that cleaning up same-named workflows is the owner's call, not the app's.

## Acceptance

- A test over the pure caption-composition (extracting one if the row does not already expose it) asserts that with all three captions present the workflow name is preserved intact, whichever presentation is chosen. This is the reported defect and it must be pinned by something other than eyes.
- A test asserts each of the three facts is still conveyed with all three present: `· default`, the WF9 caption, and the FEAT11 marker, each with its `.help` or accessibility text intact. A fix that fits by silently dropping a fact is not a fix.
- A test covers the two-caption case from the screenshot (`Personal`: default plus no-context) specifically, since that is the exact configuration that failed.
- No new `.system(size:)` literal on any changed line, so the DSN3 font-size guard stays green. Any new colour clears 4.5:1.
- `cd daemon && swift build` clean, `swift test` green, with the number of tests this task adds recorded in the ship note. Do not pin an absolute suite total.
- No em-dashes in changed lines; repo dash guard green.

Rendering is owner-owed: this is a layout change in a menu-bar app that is not screenshotable from a session.
