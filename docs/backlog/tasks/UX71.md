# UX71: the Ask pane shows answers as raw markdown and leaves its trailing column empty

Band origin: filed 2026-08-04 at the owner's request, found while walking AI12 the day it shipped: "UI of this ASK page a bit weird. you may see the right empty panel which makes no sense to display, it would be cool to re-design it to avoid right panel. somehow. or make the use of it. formatting of the mssages feels missing rich text." Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Two presentation problems on one surface, raised together and filed together because a session redesigning the pane should see both.

**The answers are rendered as plain text, so markdown shows through.** `AskView.swift:383` is `Text(a.answer)`. SwiftUI's `Text` renders a `String` literally, so an answer containing `**Planning the final release**` shows the asterisks. The owner's screenshot has five numbered items every one of which displays its `**` markers. The engines are prompted for prose and return markdown, so this is the normal case and not a malformed answer. The neighbouring surface already solves it: the summary is rendered through `SummaryRenderedView`, so the app has a renderer and the Ask pane simply does not use it.

**The trailing column is dead space.** Ask occupies the centre column of the Library's `NavigationSplitView` (`LibraryWindow.swift:849`), and the detail column beside it has nothing to show for a rail that is not a meeting list, so it renders a placeholder ("Answers are drawn from your meetings, on-device, with citations.") next to an answer that is already on screen. On the owner's display that is roughly half the window saying nothing. Restating what the pane is, beside the pane doing it, is the specific problem rather than the placeholder's wording.

Note the geometry interacts with UX70 but is not the same defect: UX70 is the window growing past the screen with the answers unreachable, and it is filed as its own row because it is a correctness problem rather than a design one.

## Scope

**Rendering.** Route the answer body through the same renderer the summary uses rather than writing a second one. Two constraints: `.textSelection(.enabled)` has to survive, because UX48 established that a real mouse selection is how text gets out of this app; and citations already render as their own chips below the body, so the renderer must not turn a bracketed stem reference in the prose into a second, competing affordance.

**The column.** A design decision rather than a defect, and the owner named both options: remove the trailing column for this rail, or give it something worth showing. Anything put there has to be worth half a window, and the obvious candidates are already elsewhere (citations are chips under the answer, history is the stack itself). Removing it is the cheaper answer and probably the right one, but the split-view's column behaviour is shared with the meeting rails, so check what else moves before changing it.

## Explicitly not / out of scope

**Not the window-growth bug**, which is UX70 and lands first if both are in flight, since a height fix may change what the column looks like.

**Not the reading measure or the answer stacking.** UX36's capped column and AI3's newest-first order both stand.

**Not a markdown renderer of its own.** If `SummaryRenderedView` cannot be reused as is, say why in this spec before writing a second one; two renderers drifting is the shape `daemon/CLAUDE.md` warns about repeatedly.

**Not the empty-state invitation.** UX38's centred invitation on a fresh Ask is a different surface and is not what the owner reported.
