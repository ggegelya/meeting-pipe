# REC27: a wedged AVAudioEngine survives a timed-out teardown or restart and is then called synchronously on the main thread by the next start, wake or watchdog tick, so one audio wedge can freeze the app

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Review findings RECORDING-1 (high, verdict plausible) and RECORDING-10 (low, confirmed), re-read in code at `01e904a` on 2026-10-25. [REC13](./REC13.md) (parked in [owner-verification.md](../owner-verification.md)) made the stop path survive a wedged engine queue, and that still holds. What it left is the engine itself, and every engine call outside `stop()`.

**A timeout abandons the call and keeps the engine.**

- `MeetingRecorder.teardownEngine()` (stop step 5) runs `EngineTeardown.run(removeTap:stop:revertVoiceProcessing:)` with `[engine]` closures, and on `!teardown.isClean` only logs `"WARN: audio engine teardown timed out (...) - finalizing the intermediates anyway"` and `engine_teardown_timed_out` with `path: "stop"`. The same `engine` is what the next meeting's `start()` uses. The start-timeout path is the one that already retires it: `unwindFailedEngineStart(micURL:recreateEngine: true)` calls `replaceEngine(reason: "failed_start_unwind")`.
- `InputDeviceRecovery.recoverCapture`: a halt timeout (`host.haltEngineForRecovery()` reporting either step unfinished) emits `engine_teardown_timed_out` with `path: "recover_capture"` and ends in `reportRecoveryFailure(); return`. A restart timeout (`case .timedOut` of `host.restartEngine()`) does the same under the comment "The abandoned restart may still be wedged on this engine, so we do NOT recreate it here: its config-change observer is bound to it." That reason has been stale since [REC16](./REC16.md) shipped on 2026-08-22: `MeetingRecorder.replaceEngine(reason:)` disarms the observer and re-arms it on the new instance (`if wasArmed { deviceRecovery.armConfigurationChangeObserver() }`), and [REC15](./REC15.md)'s `replaceCondemnedEngine()` already swaps engines mid-recording through it.

**What then calls that engine synchronously on the main thread, unbounded.**

- `start(outputDir:captureMode:voiceProcessing:)` is `@MainActor`, and so is `buildMicChain(voiceProcessing:micURL:)`, which calls `try engine.inputNode.setVoiceProcessingEnabled(true)` when voice processing is on, `let micFormat = engine.inputNode.outputFormat(forBus: 0)`, and `installMicTap(captureFormat:)`, whose `GuardedTapInstall.install(...) { engine.inputNode.installTap(onBus: 0, bufferSize: 4096, format: captureFormat) ... }` runs on the caller's thread.
- `unwindFailedEngineStart(recreateEngine: false)`: `engine.inputNode.removeTap(onBus: 0)` and `try? engine.inputNode.setVoiceProcessingEnabled(false)`.
- `InputDeviceRecovery.checkTapLiveness()`, on a `.main` `DispatchSourceTimer` every second for the whole recording: `let engineRunning = host.engineIsRunning` (`engine.isRunning`) is read before `TapWatchdogPolicy.decide`, so it keeps being read after `micCaptureAbandoned`, the flag REC15 added to stand this loop down.
- `MeetingRecorder.handleDidWake()`: `"engine_running": engine.isRunning` and `if !engine.isRunning { deviceRecovery.recoverFromTapStall() }`.
- `liveInputFormat()` (`engine.inputNode.outputFormat(forBus: 0)`), reached on main from `evaluateConfigurationChange`, `recoverFromTapStall` and `recoverCapture`, and `replaceCondemnedEngine()`'s `try engine.inputNode.setVoiceProcessingEnabled(true)`.

The repo's own record of 2026-08-14 is that "Every `AVAudioEngine` call serializes on that queue" ([gotchas](../../../daemon/docs/gotchas.md#a-notification-observer-with-a-queue-makes-the-poster-wait), from `sample 57648`, the engine queue blocked in 2516 of 2516 samples). If the format read, `isRunning` and `installTap` queue there too, which depends on AVFAudio internals the code cannot show (the reason the verifier rated this plausible rather than proven), then after one timed-out teardown the next `start()` blocks main with no bound: the menu bar, HUD, Library and hotkeys freeze, the meeting is not recorded, and only a force-quit recovers. After a timed-out recovery mid-meeting, the next 1 Hz tick does the same during a live recording, so Stop and the force-stop hotkey stop responding. That is the failure [`boundedEngineStart`](../../../daemon/Sources/MeetingPipe/BoundedEngineStart.swift) was written against (2026-06-12: `engine.start()` hung about 42 s on main, "freezing the whole app ('Record did nothing')"), it breaks the [daemon rule](../../../daemon/CLAUDE.md) "Don't call `AVAudioEngine` synchronously and unbounded from anywhere", and it contradicts REC13's ship note "Nothing calls the engine synchronously and unbounded any more".

**Each abandoned call keeps a thread for good.** `runBlockingWithTimeout` hands the operation to `runBoundedSync`, which runs `DispatchQueue.global(qos: .userInitiated).async { operation(); done.signal() }`; on timeout that thread stays blocked inside AVFAudio, and nothing counts or caps it. One bad recording can abandon about 13 to 15: three teardown steps, plus up to `InputDeviceRecovery.recoveryFailureBudget` (5) recoveries of two halt calls or one restart each. The daemon runs for a week between restarts (pid 77137 had been up 7 days 8 hours on 2026-10-25), so these accumulate across meetings, and past GCD's thread limit (about 64) the bounded helpers can no longer schedule their own operation or waiter, at which point the bounds stop being bounds. CI8's `RunWithTimeoutTests.test_blocking_stays_bounded_when_more_calls_wedge_than_the_pool_has_threads` pins one more wedge than the core count, which is the cooperative-pool half, not GCD exhaustion.

**Field record.** The precondition has happened twice: the 2026-06-12 start wedge and the 2026-08-14 engine-queue wedge. Not observed since: the log generation on this Mac (`events.jsonl` from 2026-10-12, 3 recordings, 4 `configuration_change_recovered`) holds no `engine_teardown_timed_out`, `engine_start_timed_out` or `configuration_change_unrecoverable` row. This is filed on code plus the documented precondition.

**A failed start leaves state behind (RECORDING-10).** `start()` writes the marker first (`try? captureMode.marker.write(to: modeMarkerURL, atomically: true, encoding: .utf8)`) and then runs `var chain = try buildMicChain(...)`. `buildMicChain` enables voice processing before it can throw, on `guard micFormat.sampleRate > 0 else { throw RecorderError.fileCreateFailed("inputNode reports zero sample rate ...") }` or on `RecorderError.fileCreateFailed("mic file: ...")`, and both throws (from the first call and from REC15's retry call) leave `start()` with no unwind. Voice processing then stays enabled on the input node; the next `buildMicChain` resets `voiceProcessingEnabledForSession = false` before deciding, so neither a later VP-off session nor `teardownEngine` reverts it, which is the 2026-05-13 symptom (other apps hear the user at reduced gain until the process exits). Narrow: `ConfigStore.voiceProcessing` defaults false, and the owner's `config.toml` has `voice_processing = false` on 2026-10-25. The marker is removed only by `persistAfterMerge` (and by orphan recovery), so every throwing exit after it is written (both `buildMicChain` calls, the tap-refused throw, a failed and a timed-out engine start) leaves `<stamp>.capturemode` in raw/. That is debris rather than an orphan, since `OrphanRecordingRecovery.detectOrphanStems` keys on `.mic.wav` and `.system.wav`, and raw/ held none on 2026-10-25. The start-time recovery manifest does not leak the same way: `MeetingSessionController.beginRecording` calls `writeRecoveryManifest` only after `audioRecorder.start` returns.

## Scope

Seam: `MeetingRecorder` (`start`, `buildMicChain`, `installMicTap`, `unwindFailedEngineStart`, `teardownEngine`, `handleDidWake`, the `InputDeviceRecoveryHost` conformance) and `InputDeviceRecovery` (`recoverCapture`, `checkTapLiveness`).

1. **A timeout condemns the engine.** In `teardownEngine`, on `!teardown.isClean`, call `replaceEngine(reason: "teardown_timed_out")`; `deviceRecovery.standDown()` has already disarmed the observer, so nothing is re-armed. In `recoverCapture`, route the halt timeout and the restart `.timedOut` through a host method that retires the engine (`replaceCondemnedEngine()` or a sibling carrying the reason), and delete the stale "do NOT recreate it here" comment. The abandoned closures hold the old instance through `[engine]` until they return; the recorder must hold no second reference, so a replaced engine whose abandoned call later returns deinits instead of running beside its replacement. Whether recovery then retries on the fresh engine in the same pass or leaves it to the next device change or tick is the pickup's call; say which in the commit body.
2. **No engine call on the main thread.** The voice-processing toggle, the input-format read, `installTap` (with the ObjC barrier and the condemn step inside the bounded closure, and the outcome returned through a lock-boxed value the way `boundedEngineStart` does), `unwindFailedEngineStart`'s removeTap and revert, `replaceCondemnedEngine`'s enable, `liveInputFormat`, and both `isRunning` reads go through `runBlockingWithTimeout`; `buildMicChain` becomes async (`start()` already is). Each is awaited before the next, and the watchdog skips its read while a recovery is in flight, so engine calls never overlap. The watchdog's read is single-flight, so a wedged read costs one thread rather than one a second, and a read that times out is itself a wedge: condemn, and stop asking for this recording. REC8's un-gating from `engine.isRunning` stays, pinned by `TapWatchdogPolicyTests`. This is the load-bearing half: item 1 alone does not help when the wedge is in the HAL or coreaudiod, where the fresh engine's first `inputNode` access blocks the same way.
3. **Cap abandoned calls.** One process-wide count of blocking engine calls abandoned on timeout, incremented at the timeout branch of the helper the recorder uses, each abandonment emitting `engine_call_abandoned` (category `recorder`; `site`, `abandoned_total`). Past a small threshold the pickup names and argues, the recorder stops issuing engine calls: a start fails fast with a new `RecorderError` case (which `MeetingSessionController.startFailureReason`, exhaustive by design, maps to its own `recording_error` reason), and one notification tells the owner to restart MeetingPipe, instead of leaking further threads.
4. **Unwind every failed start.** One exit path in `start()` (a `do`/`catch`, or a `defer` keyed on success) that removes `<stamp>.capturemode` on every throw and, on the two `buildMicChain` throws that have no unwind today, reverts voice processing when this start enabled it, through item 2's bounded path. The engine has not started on those throws, so the revert is not the wedge case. Replacing the engine instead is not equivalent: nothing establishes that disposing an engine reverts VPIO on the device, and `teardownEngine`'s doc records that macOS does not even disable it on stop.
5. **Make the claims true.** The `daemon/CLAUDE.md` rule and `MeetingRecorder.stop`'s "every wait below is a suspension" note then hold for the whole recorder. Add one line to REC13's row in `owner-verification.md` saying the start, recovery, wake and watchdog engine calls were left synchronous at its ship and are this task's (the REC18 precedent for annotating a parked row).

## Explicitly not

- The stop path's order and bounds. ARCH8 fenced `stop(limitSeconds:)`'s step order and REC13's budgets stand; item 1 adds one call inside step 5.
- `MicLevelMonitor`'s engine ([REC18](./REC18.md) deletes it) and the Library playback engine (`AudioPlaybackController` starts and stops its own `AVAudioEngine` synchronously on main, the review's UI-8 ([PERF21](./PERF21.md)); no recording is at stake there, and it is not filed here).
- A general main-thread stall detector: [PERF11](./PERF11.md) makes a freeze like this readable afterwards; it does not prevent one.
- The `.capturemode` write reporting its own failure, and recovery failing closed on an unreadable marker: the observability audit's start-marker task (REC21 as drafted on 2026-10-25) owns that line. This task only removes the marker on a failed start; whichever lands second rebases onto the other.
- Measuring whether `isRunning` and the format read really block behind a wedged engine queue. The wedge cannot be provoked on demand, and the fix does not depend on the answer.
- Abandoned calls from other subsystems (`ShareableContentSignal`, the AX probes) in the same GCD pool: this counter covers the recorder's engine calls only.

## Acceptance

- `InputDeviceRecoveryTests` (fake host): a halt that times out retires the engine once and installs no tap on it (`test_aHaltThatTimesOutFailsWithoutTouchingTheTap` keeps its no-tap assertion); a restart that times out retires it; after either, the watchdog reads engine state only through the bounded host call, and a tick whose read times out condemns the engine and starts no second read while the first is outstanding.
- A recorder test through an injected teardown runner (or a source fence where no seam exists, saying so): a stop whose teardown times out emits `engine_replaced` with `reason: "teardown_timed_out"`, and the next start binds a different engine instance.
- A source fence in the `CaptureHealthREC16Tests` style: in `MeetingRecorder.swift` and `InputDeviceRecovery.swift`, every `setVoiceProcessingEnabled`, `outputFormat(forBus:`, `installTap(`, `removeTap(`, `.isRunning`, `.start()` and `.stop()` on an engine sits inside a closure handed to `runBlockingWithTimeout`, `runBoundedSync`, `boundedEngineStart` or `EngineTeardown`; any allowlisted exception carries its reason in the test.
- Pure tests for the cap: the count rises on each abandonment, `engine_call_abandoned` is emitted per abandonment, refusal starts at the threshold, and a start past it fails fast with the typed error without touching the engine.
- A test (or a fence where no seam exists, saying so) that every throwing exit of `start()` leaves no `<stamp>.capturemode`, and that the two `buildMicChain` throws revert voice processing when this start enabled it.
- `cd daemon && swift build` and `swift build -c release` warning-clean under `-strict-concurrency=targeted`, `swift test` green with N new tests stated in the commit body, `bash scripts/ci-local.sh` green, `python3 scripts/truth_fences.py both` green (the new actions are in the existing `recorder` category).
- The restart notice is new user-visible copy: read `docs/GUIDE.md` first, and update it and `README.md` in the same commit if either describes what happens when the audio device sticks.
- Evidence (confirms, does not gate): after `./scripts/rebuild.sh`, any later `engine_teardown_timed_out` or `engine_call_abandoned` row is followed by a next recording that starts, with the app responsive throughout.
