# UX67: the Startup toggles stop responding and only a full quit brings them back

Band origin: filed 2026-08-04, found by the owner while walking UX55 the day it landed. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Walking UX55 on 2026-08-04, the owner opened Preferences ▸ General ▸ Startup and found **Launch at login** and **Relaunch after quitting** would not move. Reported verbatim: "launch at login and relaunch toggles were untoggleable. but after full quit it become normal."

Three properties the owner confirmed, and they are what make this narrow enough to act on:

- **Not a frozen window.** The rest of Preferences behaved: the window opened and closed normally. So this is not the synchronous-work-on-main freeze class this repo has been bitten by (`Log` of that class in the root notes); it is scoped to those two controls.
- **Cleared by a full quit**, not by closing and reopening the Preferences window. The owner opened and closed that window during the same session without it helping.
- **The session had just been through `./scripts/rebuild.sh`**, which relaunches the app and which touches the login agent through `scripts/lib/login-agent.sh` (the helper UX42 added, guarded by `scripts/test-login-agent-guard.sh`, precisely so a rebuild cannot re-arm a login-start the owner turned off).

**Not UX55.** That task changed the status-bar menu's predicate (`StatusBarModel.offersQuitWithoutRelaunch`) and never touched either toggle's binding. It is named here only because its walkthrough is what surfaced this.

## Two candidate mechanisms, both real, and the task is to tell them apart

**Candidate A: the write is being refused and the switch is correctly showing the machine.** `launchAtLoginBinding` (`PreferencesView+General.swift:119-125`) sets through `LaunchAtLoginModel.set(enabled:)`, which assigns `status = service.set(enabled: ...)`. Its own comment states the design: "The switch renders whatever launchd is left holding after the write, not what was asked for, so a refused `launchctl` cannot leave the control showing a state the machine does not have (UX42)." That is deliberate and right. The consequence is that a `launchctl` refusing every write is indistinguishable, at the control, from a dead toggle: it snaps back each time. `LaunchAtLoginStatus` carries an `error`, and the pane already renders it in the group footer (`:68`), so the deciding evidence is whether a message was showing under the group at the time. The owner did not report one, which is suggestive but not conclusive, since nobody was looking for it.

**Candidate B: the pane is holding a stale reading and never re-takes it.** `LaunchAtLoginModel` reads once, in `init` (`:18-21`, `self.status = service.status()`), and is a `@StateObject` on `GeneralSectionView` (`:31`), so its lifetime is the view's rather than the window's. Nothing re-reads on window open, on foreground, or on any notification. If the agent's real state changed underneath the pane, which is exactly what a `rebuild.sh` in the same session can do, the control renders the state that was true when the view was first built. **This is UX53's missing-refresh class**, and UX53 scoped Preferences out with an explicit instruction for this situation: "Not non-meeting surfaces (Preferences, Diagnostics, the status-bar menu) unless a pass finds the same class there, in which case name it rather than fixing it here." This is that naming.

The two are distinguishable by evidence rather than by argument, which is why neither is assumed here. A is a `launchctl` failure and leaves a footer error and a non-zero exit; B leaves no error at all and is cured by anything that rebuilds the view, which a full app quit does and a window close may not.

## Scope

Determine which mechanism it is before changing anything, because the fixes are different and the wrong one leaves the defect in place while looking addressed.

Reproduce first, with `rebuild.sh` in the loop since that is the one thing known to have been in the session. If it will not reproduce, the cheaper route is to make the two distinguishable in the field: `LaunchAtLoginService.set` already returns a status carrying an error, so log the refusal (a `preferences` event with the `launchctl` exit status and stderr tail) whenever a write does not move `isOn`. That turns the next occurrence into a log line instead of another walkthrough report.

If B, re-take the reading rather than caching it for the view's lifetime: the seam is `LaunchAtLoginModel`, and the pattern to copy is the one UX55 used on the menu side, which re-reads in `refreshMenuBeforeDisplay` because AppKit calls it before every display. The Preferences equivalent is a re-read when the pane appears or the window becomes key. Do **not** make it a per-render read: `status()` spawns `launchctl`, and UX55's shipping note records why an inline read there would have been one subprocess per download-progress tick on the main queue.

If A, the control is behaving as designed and the defect is that the refusal is silent in practice; surface it where the user is looking rather than only in the group footer.

## Explicitly not / out of scope

**Not the UX42 design that the switch renders the machine rather than the request.** That is load-bearing and correct: a control showing a state launchd does not hold is the defect UX42 removed.

**Not a general Preferences refresh sweep.** UX53 deliberately kept its sweep to meeting surfaces, and widening it here would repeat the mistake of growing a task past its evidence. Other Preferences panes are unexamined; if the same shape is found, that is a row of its own.

**Not `scripts/lib/login-agent.sh`.** Its guard is what stops a rebuild re-arming a disabled login-start, and any change to it requires `bash scripts/test-login-agent-guard.sh` per the root `CLAUDE.md`. This task should not need to touch it, and if it turns out it does, that gate is mandatory.
