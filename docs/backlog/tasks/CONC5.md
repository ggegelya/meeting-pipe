# CONC5: fourteen files hand-roll `Process()` with four drain and timeout policies, so a stuck `security` call hangs launch, ffmpeg drains stderr after exit, and a timed-out merge leaves ffmpeg running

Band origin: filed 2026-10-24 from the 2026-10-24 audit band ([architecture review](../../audits/2026-10-24-architecture-review.md) M5 and M6, [go-live assessment](../../audits/2026-10-21-go-live-assessment.md) PD-7). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Verified in code on 2026-10-24. `grep -rn "Process()" daemon/Sources` returns 14 sites in 14 files: `KeychainSecrets.swift`, `MuteRedactor.swift`, `RecordingPostProcessor.swift`, `AudioTranscoder.swift`, `LocalServerReaper.swift`, `LaunchAtLoginService.swift`, `LaunchAgentScheduler.swift`, `ModelDownloadSupervisor.swift`, `DoctorRunner.swift`, `PipelineLauncher.swift`, `LocalModelPreloader.swift`, `Preferences/PreferencesView+Pipeline.swift`, `Preferences/MCPStatusStore.swift`, `CLI/DoctorCommand.swift`. Each picks its own drain order and its own bound, and the policies in use are:

- **Drain after exit, no bound.** `KeychainBackend.run` calls `process.waitUntilExit()` and only then `readDataToEndOfFile()` ("The output is a single token, well under the pipe buffer, so drain-after-exit cannot deadlock"). The pipe argument holds, but nothing bounds the wait. `App.main` runs `SecretsStore.migrateEnvFileIfPresent()` and `Secrets.loadIfPresent()` before `NSApplication.shared` exists, and `loadIfPresent` spawns `/usr/bin/security find-generic-password` once per entry in `KeychainSecrets.managedKeys` (four). A `security` call that blocks (a locked login keychain asking to unlock, a wedged `securityd`) blocks launch with no menu-bar item and no log line. `LaunchAgentScheduler.launchctl` is the same shape: `p.waitUntilExit()` with no ceiling.
- **Wait, then read what is buffered.** `MuteRedactor.runFFmpeg` and `RecordingPostProcessor.runFFmpeg` call `proc.waitUntilExit()` and then `errPipe.fileHandleForReading.availableData`. If ffmpeg writes more than the pipe buffer (64 KiB) to stderr it blocks on the write while the daemon blocks on the exit, which is the textbook deadlock. Both pass `-loglevel warning`, which makes it unlikely on a healthy file, not impossible on a damaged one (a long run of per-packet warnings). `AudioTranscoder.runFFmpeg` already does it the right way round ("Drain stderr before waiting: ffmpeg on a long recording can fill the pipe buffer and deadlock"), so the two orders coexist in three ffmpeg wrappers.
- **Abandon on timeout, never kill.** `RecordingPostProcessor` bounds a merge with `runWithTimeout(seconds: mergeCeilingSeconds)` (300 s) and on timeout logs `merge_timed_out` and keeps the intermediates. `runWithTimeout` only stops waiting: the ffmpeg child keeps running and keeps writing the temp file, and the next `recoverOrphanedRecordings` pass can start a second ffmpeg on the same stem.
- **Escalating watchdogs, each written once.** `PipelineLauncher` terminates and then sends `SIGKILL` after 10 s; `LaunchAtLoginService` and `MCPStatusStore.read(timeout:)` carry UX67 `DispatchWorkItem` watchdogs that call `terminate()`; `DoctorCommand` polls a 10 s deadline. These are correct and are the shape to keep, but there are three copies.

M6, the cooperative-pool half. CI8 moved blocking engine calls off the cooperative pool and wrote the rule in `daemon/CLAUDE.md` (the `runWithTimeout` entry). Two blocking sites were not covered, because `Task.detached` still runs on the cooperative pool:

- `Coordinator.reapStorage` runs `Task.detached(priority: .background) { OriginalsReaper.sweep(); AudioRetentionSweep.sweep(...); LocalServerReaper.reapIfOrphaned() }`. `AudioRetentionSweep.sweep` calls `AudioTranscoder.compressToFLAC`, a synchronous ffmpeg run per WAV, and `LocalServerReaper.reapIfOrphaned` loops `Thread.sleep(forTimeInterval: 0.5)` up to 20 times and spawns `/bin/ps` through `commandLine(of:)`. This runs at launch and after every pipeline job.
- `SummarizationPromptPreview.load` (in `PreferencesView+Pipeline.swift`) wraps a synchronous `mp summarize --print-prompt` in `Task.detached(priority: .userInitiated)` with no bound, and reads stdout to EOF before stderr, so a child that fills stderr first deadlocks.

## Scope

1. One subprocess primitive, `ProcessRunner.run(executable:arguments:environment:timeout:)` in a new `daemon/Sources/MeetingPipe/ProcessRunner.swift`. It runs on GCD, never on the cooperative pool (an async wrapper resumes a continuation, the `runBlockingWithTimeout` pattern), drains stdout and stderr concurrently into bounded buffers (keep the tail, the way every caller already does), and on timeout sends `SIGTERM`, waits a short grace, then `SIGKILL`s and reaps. It returns status, both tails, and whether it timed out. `PipelineLauncher`'s escalation is the reference behaviour; take its constants, do not invent new ones.
2. Migrate in this order, one commit is fine: `KeychainBackend.run` (a ceiling of a few seconds; a timed-out read is `nil`, the same as a missing item, and logs once; the executable path becomes an `init` parameter defaulting to `/usr/bin/security` so a test can hang it), the three ffmpeg wrappers (`MuteRedactor.runFFmpeg`, `RecordingPostProcessor.runFFmpeg`, `AudioTranscoder.runFFmpeg`), with the merge ceiling passed as the runner's `timeout` so a timed-out merge kills its ffmpeg, then `LocalServerReaper.commandLine(of:)`, `LaunchAgentScheduler.launchctl` and `SummarizationPromptPreview.load`. The long-lived streaming spawns (`PipelineLauncher`, `ModelDownloadSupervisor`, `DoctorRunner`, `LocalModelPreloader`) keep their own handlers: they stream progress, which a run-to-completion primitive does not model. `LaunchAtLoginService`, `MCPStatusStore` and `DoctorCommand` may migrate when touched.
3. Move `Coordinator.reapStorage`'s detached block onto a serial GCD queue (`DispatchQueue(label: "com.meetingpipe.reaper", qos: .background)`), and extend the existing CI8 entry in `daemon/CLAUDE.md` with the clause "`Task.detached` is not off-pool." rather than adding a new entry: that file is at 22,440 of its 24,000 B cap (DOC15 owns the cap).

## Acceptance

- New `ProcessRunnerTests` (MeetingPipeTests), driving `/bin/sh -c` children: a child writing 1 MiB to stderr and 1 MiB to stdout before exit completes without deadlock and returns both tails; a child that ignores `SIGTERM` and sleeps past the timeout is gone (`kill(pid, 0)` fails) within timeout plus grace, and the result says timed out; a child that exits non-zero returns its status and stderr tail; the blocking wait runs on the runner's GCD queue, not in a Swift task (assert with `dispatchPrecondition(condition: .onQueue(...))` inside the wait).
- A test that a timed-out `RecordingPostProcessor` merge leaves no ffmpeg child alive (inject a fake ffmpeg script that sleeps), and still keeps the intermediates and emits `merge_timed_out`.
- A test that `KeychainBackend.value(for:)` returns `nil` within its ceiling when the injected executable hangs.
- `cd daemon && swift build` and `swift test` green, new test count in the commit body. `bash scripts/ci-local.sh` green.
- Evidence (confirms, does not gate): after `./scripts/rebuild.sh`, `ps -ax | grep ffmpeg` shows no stray ffmpeg after a forced merge timeout in a dogfood run.

## Amended 2026-10-25 (performance review)

### Overlapping retention sweeps share one FLAC temp; coalesce, reorder the reaper, bound the FLAC encode

From the 2026-10-25 performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified): PERSISTENCE-6 (medium) and SUBPROCESS-15 (low), both confirmed. Re-checked in code at `01e904a`. Item 3's serial queue is also the fix for a defect this spec does not name; the review adds three small legs to it and corrects two magnitudes.

**Overlapping retention sweeps.** Every `reapStorage` call starts its own `Task.detached(priority: .background) { OriginalsReaper.sweep(); AudioRetentionSweep.sweep(...); LocalServerReaper.reapIfOrphaned() }` with no in-flight guard, so a job finishing while a sweep runs starts a second one beside it. With a workflow on `compress` and a backlog (turning compress on for a library holding months of WAVs), both compute the same candidates and call `AudioTranscoder.compressToFLAC` on the same WAV, which encodes to a fixed `<stem>.flac.writing` and opens with `try? fm.removeItem(at: temp)`. The verifier's trace: the second encode unlinks the first's temp, the first moves the second's partial file onto `<stem>.flac`, fails its duration check and removes it, and the second finds no temp (`outputMissing`); a lagging sweep catches up with the leader and from then on they collide on every remaining file, so neither makes progress, at two to three times the CPU and disk. With three sweeps there is a narrow window where one sweep's `try? fm.removeItem(at: flac)` deletes another's verified FLAC after that one has deleted the WAV, which loses the meeting's audio. Reachable only with a `compress` or `drop` policy, because `sweep` returns at `guard policies.values.contains(where: { $0.policy != .keep })`; the owner's personal Mac has no `audio_compressed` row (2026-10-25).

Added to item 3:

- Every `reapStorage` body goes through the one serial queue item 3 names; that alone removes the overlap, so the queue must stay serial.
- Coalesce bursts. A Library batch re-run calls `onDone` once per meeting (`PipelineJobDispatcher.route`'s `.success` branch), and each queued sweep re-reads every summarized meeting's sidecars in `AudioRetentionSweep.candidates`. A pending flag on main lets a burst queue at most one follow-up behind a running sweep.
- Run `LocalServerReaper.reapIfOrphaned()` first in the block. It is cheap and frees an orphaned `mlx_lm.server`'s RAM, and at `01e904a` it waits behind the whole compress backlog.
- Bound the FLAC encode when `AudioTranscoder.runFFmpeg` moves to `ProcessRunner` (item 2). At `01e904a` it is `readDataToEndOfFile()` then `proc.waitUntilExit()` with no ceiling, and item 2 names a timeout only for the merge. Measure one `-compression_level 8` encode of an hour-long final and set the ceiling from it, documented beside the constant; a timed-out encode leaves the WAV, like every other failure path in `compressToFLAC`.

Magnitudes, so the pickup does not over-weight them: `LocalServerReaper`'s `Thread.sleep(forTimeInterval: 0.5)` loop runs only when an orphaned server marker exists, not on every sweep; and the main-thread `scanOrphanStems` in the same function measured 0.6 ms on the owner's 61-entry `raw/` (verifier, 2026-10-25), tens of ms at a year's 10k to 15k entries. Moving that scan off main, the orphan sweep's in-flight guard and its retry cap belong to the orphan-sweep task filed beside this amendment on 2026-10-25 ([REC24](./REC24.md) "A failed orphan re-merge is retried after every job forever, and two job completions can merge the same orphan at once over one temp file").

Rejected: a unique temp name per encode. With the serial queue no two encodes of one WAV can run, and a uuid temp is new debris that `AudioRetentionSweep.candidates` and the doctor would have to learn.

Added acceptance:

- A test over the queue seam (extract a small `StorageJanitor` owning the queue and the pending flag if `Coordinator` is not testable directly): two back-to-back requests run the sweep body strictly one after the other (an injected body that records overlap sees none); five requests during a running sweep produce exactly one follow-up; the reaper step runs before the retention step.
- An `AudioTranscoderTests` case with an injected ffmpeg that sleeps past the ceiling: `compressToFLAC` throws a timeout, no child is left running, and the WAV is untouched.

### Calibrate StopStallWatchdog against the merge ceiling item 2 makes real

The 2026-10-25 performance review (finding RECORDING-7, low after verification) adds one leg that item 2's merge-ceiling change has to carry. Re-read in code at `01e904a` on 2026-10-25.

**The stop-stall canary sits under the bound it says it exceeds.** `StopStallWatchdog.defaultCeilingSeconds` is `90`, and its doc reads "the two waits that legitimately take time are already bounded well below this (the writer drain at 10 s, the ffmpeg merge at its own ceiling), so a stop still running at 90 s is stuck, not slow". `RecordingPostProcessor.mergeCeilingSeconds` is `300.0`. `MeetingSessionController.stopRecording(file:source:summaryMode:)` arms the watchdog around the whole of `await recorder.stop(limitSeconds:)`, whose own bounds add up to about 348 s: `SystemAudioChannel.haltCapture()` 5 + 5 s, an in-flight recovery drained by `deviceRecovery.standDown()` (halt 2 + 2 s, restart 8 s), `teardownEngine()` 3 x 2 s, `drainWriters()` 2 x 10 s, then the merge at up to 300 s. A merge that runs past 90 s (less whatever the pre-merge steps took), bounded and healthy by its own ceiling, therefore emits `stop_exceeded_ceiling` and posts `notifyError(StopStallWatchdog.stallMessage(elapsed:))` for a stop that then finishes. Today the 300 s only abandons the await; once item 2 passes it as the runner's timeout it is a real bound, which is when the watchdog's sentence becomes checkable, so the fix belongs with it.

**Measured, so low.** `recorder.log` on 2026-10-16: a 2116 s meeting went from `stopping:` to `recorder stopped` in 1.96 s, its merge taking 1.9 s (`merge length policy` at 07:33:43.938Z, `ffmpeg merge exit=0` at 07:33:45.846Z), and a 1120 s meeting in 0.78 s end to end, about 1100x realtime. A 3 h meeting merges in about 10 s, perhaps 30 s under load, so the false alarm needs ffmpeg starved tenfold or a slow disk. These two stops are also the first field numbers for the flush window [UX79](./UX79.md) left unmeasured: under 2 s end to end.

**Added scope.** With item 2's change, make the canary consistent with the bound. Preferred: arm it in two phases, the capture-teardown half keeping 90 s (which covers its own ~48 s of bounds) and the merge half getting a ceiling above `mergeCeilingSeconds`, through a phase hook from `MeetingRecorder.stop` to the controller. If the pickup argues for one ceiling instead, raise it above the summed bounds and state what that costs a genuine teardown wedge (about six minutes before anyone is told). Two phases keep REC13's fast canary for the wedge class it was built for. Correct the doc comment either way.

**Explicitly not (this leg).** Releasing `.stopping` before the merge (splitting `stop()` after `finalizeFiles` and post-processing by stem) so a back-to-back meeting is never held off: the measured merge is seconds, and the split reopens REC11's state-ownership invariants and ARCH8's fenced step order. `toggleManual`'s `.stopping` no-op stays; UX79 already took the inert Start row out of the menu.

**Added acceptance.**

- A constant fence beside `StopStallWatchdogTests` (the `AppDelegateRelaunchTests` shape): the merge-phase ceiling exceeds `RecordingPostProcessor.mergeCeilingSeconds`, and the teardown-phase ceiling exceeds the sum of the pre-merge bounds, so raising any of those constants past its canary fails a test.
- A stop whose merge phase runs past 90 s but under its ceiling emits no `stop_exceeded_ceiling`; a teardown phase past 90 s still does.

### Redaction ceiling and outcome, killed-merge promotion, self-clearing handler drains, MCP stderr, off-main schedule bindings, and a timed-out Keychain read as unreadable

The 2026-10-25 performance review (eight subsystem finders over HEAD `01e904a`, every finding adversarially re-verified) re-read the sites this task migrates. Findings SUBPROCESS-1, SUBPROCESS-2 and RECORDING-5 restate the ffmpeg legs, SUBPROCESS-8 and PERSISTENCE-12 the scheduler, UI-9 and SUBPROCESS-17 the Preferences spawns, SUBPROCESS-16 and MAINTHREAD-12 the Keychain. The context above holds; what follows is what a pickup needs beyond it, re-verified in code on 2026-10-25.

**1. The redaction ffmpeg needs its own ceiling and outcome.** Scope item 2 passes a `timeout` only for the merge. `MuteRedactor.runFFmpeg` is awaited at the head of `SinkDispatcher.runDaemonTranscription`, before the row's live entry exists, so a wedged redaction holds the whole serial lane with no row entry, no Cancel and no stall flag (the job-level backstop is filed separately from the same review). Give it a ceiling scaled to the input's duration: the merge ffmpeg processed 2,116 s of audio in 1.9 s on 2026-10-16 (`recorder.log`, `merge length policy` at 07:33:43.938Z, `ffmpeg merge exit=0` at 07:33:45.846Z), so a minute plus a small fraction of the duration is generous. A timeout maps to `.failed(.ffmpegFailed)`, so SEC16 holds the meeting back, and never to `.notNeeded`, which would let the uncut recording through. Remove `<stem>.redacting.wav` only after the killed child is reaped, so no ffmpeg is still writing an unlinked file.

**2. A killed merge must not reach promotion, and a late-opening one must not touch the next attempt.** `RecordingPostProcessor.produceFinal` removes a stale `<stem>.merging.wav` before each attempt, so an abandoned ffmpeg that had already opened its output keeps writing an unlinked inode and cannot reach the new file. One that stalled before opening its output could later truncate the next attempt's file of the same name. On the ceiling, kill and reap before `writePostProcessFailure`, never call `promoteMerged` after a kill, and either reap before the next attempt or give each attempt a unique temp name.

**3. A readabilityHandler drain must clear itself at EOF.** The review's verifier measured a `readabilityHandler` left installed after EOF firing about 650,000 times a second, a full core, for as long as its `Pipe` is retained. If `ProcessRunner` drains through handlers rather than blocking reads on its own queue, it sets each handler to nil on empty data and again at termination. The one live instance outside this task's sites, `ModelDownloadSupervisor`'s stderr handler, is in [CONC7](./CONC7.md)'s amendment of the same day.

**4. Two Preferences spawns.** `MCPStatusStore.read(timeout:)` sets `process.standardError = Pipe()` and never reads it, so a chatty child fills the pipe and is killed by the 20 s watchdog as a spurious failure; set it to `FileHandle.nullDevice` in this task (one line) rather than when touched. `SummarizationPromptPreview.load` is already in scope; its child also has no ceiling, so it takes the runner's default.

**5. The schedule bindings run on main, once per picker step.** Migrating `LaunchAgentScheduler.launchctl` bounds each call, but its callers are SwiftUI binding setters on main: `digestEnabledBinding`, `digestWeekdayBinding` and `digestTimeBinding` call `applyDigestSchedule()`, and the `backup*Binding` setters call `applyBackupSchedule()`, which run `DigestSchedulerService.apply` or `BackupSchedulerService.apply`, so `PipelineLauncher.findMP()`, an atomic plist write and two `launchctl` spawns (`bootout`, `bootstrap`) per DatePicker step. `daemon/CLAUDE.md`'s UX67 rule says every `launchctl` call is watchdogged and off main; these are neither, and [STOR10](./STOR10.md) adds a third call to the same path (`launchctl print` to verify the bootstrap). `launchctl bootout` of an agent that is running also stops it, so changing the backup time while a scheduled `mp backup` runs kills it mid-archive, which [STOR8](./STOR8.md) records is written under its final name. Add: run `apply` on one serial utility queue so a later setting cannot be overtaken by an earlier one, debounce it about a second after the last change, and have `install` skip `bootout` and `bootstrap` when the plist bytes are unchanged. No backup or digest agent was installed on the owner's Mac on 2026-10-25, so this is latent there.

**6. A timed-out Keychain read is not a missing item.** Scope item 2 says a timed-out read is `nil`, the same as a missing item. [SEC23](./SEC23.md)'s 2026-10-25 amendment types the read (`found`, `notFound`, `unreadable`) because `SecretsStore.init` stores `""` for `nil`, and its `persist()` removes the Keychain item for an empty value, so a read that timed out at launch would delete the user's token on the next edit of any other field (the review's MAINTHREAD-12 verifier reached the same conclusion). A timeout is `unreadable`. Moving the save itself off main is [CONC8](./CONC8.md)'s.

#### Added acceptance

- `MuteRedactorTests` with an injected ffmpeg that sleeps past the ceiling: the outcome is `.failed(.ffmpegFailed)`, no child is alive afterwards (`kill(pid, 0)` fails), no `.redacting.wav` remains, and the full WAV is untouched.
- A merge test with an injected ffmpeg that sleeps past the ceiling: `promoteMerged` is never called, no child is alive, `merge_timed_out` is emitted, and the next attempt's output is not truncated by the killed one.
- An `MCPStatusStore` test with a child that writes 1 MiB to stderr: the status read completes inside its timeout instead of being killed.
- A schedule test with an injected `launchctl` runner: ten quick `apply` calls produce one install; an `apply` whose plist is unchanged runs no `launchctl`; no runner call is made on the main thread.
- A `KeychainBackend` test with an injected executable that hangs: `value(for:)` returns `unreadable` within the ceiling, and a following save that edits another account neither sets nor removes it.
