# AI11: Ask engine hardening: incremental index, bounded memory, honest budget

Band origin: filed 2026-07-29 (owner exploratory sweep, item 6, off a real incident: Ask "is superslow, it ate ALL available memory and even more, then Mac hang and reboot happened in few min after"). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

P1 because the broken promise is "a question about your own meetings must never take the machine down", and it did, with a hard reboot. The owner may re-band. Cross-referenced with LOCAL16 (filed the same day), which owns the shared memory-guard primitive; this task consumes it in the ask path.

## Context

The incident mechanism, traced 2026-07-29 with every link cited:

1. **Any library change invalidates the entire index.** `load_or_build` reuses the cached index only when `library_fingerprint` (every `*.md`, `*.summary.json`, `*.transcript_corrections.json`, `*.speaker_labels.json` by name/mtime/size, `embed_index.py:337-359`) matches exactly (:386). One new meeting, one rename, one correction: full rebuild. There is no incremental refresh (AI2's own recommendation, `docs/spikes/ai2-embedding-rag-latency.md:66`, never done). On 2026-07-29 the cache manifest said `count: 2398` from 2026-07-06 against 418 `.md` / 198 `.summary.json` now on disk, so the next ask was guaranteed the full rebuild.
2. **The rebuild is memory-unbounded.** `chunk_library` reads and holds the whole corpus as strings (`embed_index.py:216-244`); the embed call makes a second copy (`[c.text for c in chunks]`, :278) and `MLXEmbedder.embed` a third (prefixing, :165); batches of 32 accumulate into one `np.vstack` (:167-176). Nothing calls `mx.clear_cache()` or sets an MLX cache limit anywhere in the repo. AI2 hit exactly this on this Mac and survived only via a harness-local free-RAM watchdog ("a first attempt swap-stormed the machine and OOM-killed the model server", ai2 doc :26) that never shipped into `mp ask`.
3. **A kill loses everything, so slowness compounds into a loop.** The index is saved only after a complete build (`embed_index.py:392-396`). The daemon SIGTERMs the subprocess at 10 minutes (`PipelineLauncher.swift:440`, :821-833). A library big enough to exceed 10 minutes rebuilds from zero on every ask, forever, with no progress signal (ask.py never imports `events`; the `__MP_PROGRESS__` heartbeat is run-all-only, `orchestrate.py:60-64`).
4. **The context budget undercounts Cyrillic by ~2x.** `CHARS_PER_TOKEN = 4` (`ask.py:37`) sizes the retrieved pack at 16,000 chars for the default 4,000-token budget (:87-92). LOCAL13 measured Ukrainian at 0.47-0.49 tokens/char against EN 0.22-0.25 (`docs/spikes/local13-local-model-refresh-bench.md:120`, :443), so a UK-heavy pack is ~7,800 real tokens. AI2 measured the 14B aborting on the memory watchdog at 8K and OOM-crashing plus swap-storming the machine at 16K (ai2 doc :36-38, :46). On a local backend this alone can reproduce the incident; `--context-tokens` is user-settable with no clamp (`ask.py:148-149`).
5. **Local answering stacks models in one process.** `answer_question` holds the e5 embedder for the index lifetime (`embed_index.py:145-156`) while `engine.complete_text` on a local (or apple_intelligence-substituted, `engine.py:141-149`) backend spawns a multi-GB `mlx_lm.server` child per question and tears it down after (`engine.py:103-117`). A concurrently triggered `mp actions --cluster` (Facts view, `LibraryWindow.swift:857-871`) loads a second independent MLX runtime with no coordination.

The retrieval itself is sound: top-k over the index with a packed, bounded context (`ask.py:87-92`, `rag.pack_context`), exact dense search fine at this scale (`embed_index.py:290-292`). The owner asked "I think we may need some rag or something"; RAG is already there. The failure is the index lifecycle and the absence of memory bounds around it.

## Scope

1. **Incremental index refresh.** Keep the per-file fingerprint but diff it: re-chunk and re-embed only stems whose source files changed, drop vectors for removed stems, reuse the rest. Persist per-stem so the manifest can say which stems are current.
2. **Checkpointed builds.** Save embedded batches as they complete (or per N stems) so a killed build resumes instead of restarting. Acceptance is literally "kill it mid-build, run again, it finishes from where it was".
3. **Memory bounds.** Take LOCAL16's guard primitive: a free-RAM floor sampled between batches that aborts the run with a named, surfaced error before the machine swaps; `mx.clear_cache()` (or the mlx equivalent) between batches so the Metal cache cannot grow unbounded; release the embedder before the local answer model is spawned (retrieval is done by then; holding e5 across the answer serves nothing).
4. **Script-aware budget + clamp.** Derive chars-per-token from the retrieved text's script mix using LOCAL13's measured constants (or count real tokens if the embedder's tokenizer is cheap to reuse), and clamp `--context-tokens` to a per-backend-tier safe ceiling (the AI2 measurements are the table: 4K safe everywhere, 8K only below 14B, 16K nowhere local today).
5. **Observability.** Emit `pipeline` events for index rebuild start/done (chunk and stem counts, duration) and per ask (backend, retrieved stems, packed tokens), and a stdout progress heartbeat the daemon can surface (the UX37/UX38 spinner has something real to show). New event actions ride the existing `pipeline` category (CONVENTIONS event table untouched; fences stay green).
6. **Embedder preflight under the egress guard.** `MLXEmbedder._ensure_loaded` (`embed_index.py:148-156`) calls `load()` bare; under an armed guard with an uncached e5 it dies with a raw huggingface error. Mirror `summarize_local._spawn`'s fail-closed message shape (:721-731) naming `mp prefetch-model`.

## Explicitly not in scope

Changing the embedder model or promoting it to config (adjacency, noted: `DEFAULT_EMBED_MODEL` is hardcoded at `embed_index.py:39`; fine to leave until a reason to swap exists). A vector database (numpy exact search is the right size for a personal library; state this so nobody "upgrades" it). Warm-server reuse for the answer model (LOCAL10/11 territory; spawn-per-question is slow but memory-serial, and changing it changes the memory math this task is bounding). The Ask UI (UX37/UX38). The digest path (verified separate: `digest.py` imports no embed machinery and is deterministic-first).

## Acceptance

Pipeline tests: a two-stem library builds, then one stem's `.md` mtime changes and only that stem's chunks re-embed (fake embedder counts calls per text); a removed stem's vectors disappear; a simulated abort between batches leaves a checkpoint the next build resumes from (embed-call count proves no full restart); `--context-tokens 100000` clamps to the ceiling and says so; a UK-script pack sizes to its measured budget (chars in pack lower than the EN case for the same token target); the guard abort raises the named error and emits its event; the uncached-embedder-under-guard case produces the actionable message, not a huggingface traceback.

`cd pipeline && uv run --extra dev ruff check src tests`, `pyright`, and `pytest -q` green (baseline at filing: 1050 tests). Truth fences green (no new config keys or event categories; if a config key IS added for the guard floor, it lands documented in config.example.toml in the same commit).

Owner eyeball: `mp ask` on the real 400+ file library completes with the machine responsive throughout; a second ask reuses the index in seconds; adding one new meeting and asking again does a small delta refresh, not a full rebuild (visible in the new events).

## What shipped (2026-07-31)

All six scope items landed. The index manifest is per stem (`schema_version` 2, `stems: {stem -> fingerprint}`), so `refresh_index` re-embeds only the meetings whose own source files moved, drops a removed stem's rows, and reuses the rest; it writes a complete index back every `CHECKPOINT_EVERY_STEMS` (8) meetings with an empty completeness stamp, so the checkpoint IS the index and a kill resumes from it rather than restarting. LOCAL16's `MemoryWatchdog` is checked between batches (stage `ask index embed`) and `mx.clear_cache()` runs after every MLX batch and on `release()`; `answer_question` releases the embedder before the answer model spawns. The context budget is derived from the retrieved text's Cyrillic share against LOCAL13's two measured rates (4.0 and 2.0 chars/token) instead of a flat 4, and `--context-tokens` is clamped to `resource_guard.tier_for(ram).context_token_ceiling` for `local` / `apple_intelligence` / `auto`. `ask_index_refresh_started` / `_done` / `ask_answered` / `ask_context_clamped` ride the existing `pipeline` category, and the `__MP_PROGRESS__` heartbeat (promoted from `orchestrate` into `events.emit_progress`) carries `stems_done` / `stems_total` for UX38 to render. `MLXEmbedder._ensure_loaded` refuses an uncached model under an armed guard with the `mp prefetch-model` message shape.

No new config keys (the guard floor is LOCAL16's existing `summarization.local_memory_floor_pct`), so the truth fences are untouched. Pipeline suite 1131 -> 1157.

Two decisions the spec left open, recorded: the clamp covers `auto` as well as `local`, because `auto`'s fallback leg is the same local model and losing a little cloud context is cheaper than losing the guarantee; and the heartbeat is emitted per batch rather than from a background timer, and is suppressed under `--json` so a piped payload stays parseable.
