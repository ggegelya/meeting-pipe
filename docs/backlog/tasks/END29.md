# END29: A headphone switch whose microphone return the app misses ends a live Teams recording 12 minutes later, cut back to the switch

Band origin: filed 2026-11-16 (group A's end-engine batch, at the owner's request after [END21](./END21.md)'s Stop rule was settled). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

The owner asked on 2026-11-16 how END21's trim rules handle switching headphones mid-call. The answer, from the code as it stands after [END18](./END18.md) and END21, has one unprotected case, which this task files.

**The normal switch is safe.** Teams releases its input for a few seconds while the device changes ([END15](./END15.md) measured a re-acquire inside 22 s on 2026-10-22). `ProcessAudioSignal` reports the release, `PromotionEngine.handleInMeeting` opens a hold led by `process_audio_is_running_input_false` (a weak end, `isDefinitive` false), and when the mic comes back the signal emits live and `handleEndingProvisional` reverts the hold unconditionally (`event.kind.vetoesLoneEnd`, kept by END18). Nothing is stopped or trimmed.

**The missed return.** If the engine never receives that live reading, its `states` keep process audio at `.ended`. Then:

1. `tick(at:)` sees no live vetoer, so neither dwell is blocked.
2. The pair cannot form if nothing else ended (the Leave button and the window stay live through a switch), so the lone dwell decides: `now.timeIntervalSince(loneSince) >= loneDwell` with `loneSince` the release (END18 item 4), 720 s.
3. END18's lone-dwell refusal does not apply: it fires only for a window-gone lead with the Leave button live (`leadClassContradicted` requires `leading.evidenceClass == .callWindowOrControl`), and this hold is led by process audio.
4. The recording ends about 12 minutes after the switch with `confirmed_by: [lone_dwell]`, and END21's `TeardownHoldPolicy.trimPoint` cuts at process audio's release (`evidence.processAudio == .ended`), so the transcript leaves out everything from the switch on. Under a lossless capture that is restorable; under NDA or regulated mode it is deleted at stop.

**How the return could be missed.** DET8 (2026-08-05) caught a Teams audio client tearing down and re-registering under a new process-object ID, which is why `processAudioIsRunningInput` carries `requiresCorroboration`. `ProcessAudioSignal` follows such changes through a list-change listener and a poll: since [DET21](./DET21.md) a list change triggers one coalesced re-resolve (`process_audio_reresolved`) and an unresolved resolve backs off 2 s doubling to 60 s. The return is missed only if the resolver keeps a stale object that reads false and no list change or poll moves it to the new one, or if the new object does not match the bundle the resolver enumerates for. Neither has been observed; this is the shape the code allows, not a measured rate.

**Amended 2026-11-16 (owner): the minimised-window variant ends in about 60 s, not 12 minutes.** Minimising a native call window, or moving it to another Space, makes `ShareableContentSignal` (on-screen windows only, `onScreenWindowsOnly: true`) read the window as gone. Under a live mic that end is vetoed (`end_vetoed`) and opens no hold, but the engine keeps it in `states` as `.ended` with the minimise's stamp. If a headphone switch's mic return is then missed, the release pairs with that old window-gone: `tick`'s pair counts each evidence class from its earliest ended stamp (`endedSince[kind.evidenceClass] = min(...)`), so the call-window class has "dwelled" since the minimise and the pair confirms 60 s after the release, cut back to the switch. The seam is [END14](./END14.md)'s 2026-11-13 amendment (F031, G024: a class counted as ended while a sibling reads live, and stale stamps counting toward the pair); this task's fix should land with it or on it, and its acceptance gains the case below.

## Scope

Two changes, smallest first.

1. **Engine: a mic-led hold does not lone-confirm against a live call UI.** In `PromotionEngine.tick(at:)`, extend END18's `leadClassContradicted` idea to a process-audio lead: refuse the lone dwell while the Leave button reads `.live` in `states` and nothing of another class ended inside the hold (`otherClassesEndedInside`). A real leave always takes the Leave control away (it reads invalid, or the window goes), which ends the refusal and lets the pair or the lone dwell decide as today. The idle backstop stays the ceiling, since `.endingProvisional` is not `isLive` (`SilenceAutoStopPolicy` does not stand down).
2. **Signal: pin that a re-registered object's return is emitted.** A `ProcessAudioSignalTests` case where the matched process object disappears and a new one for the same bundle appears reading running: the next re-resolve or poll emits `onChange(true)`. If it does not, that is the defect to fix in `ProcessAudioSignal`; if it does, the engine change above is the backstop for the cases the test cannot reach.

The pickup decides whether item 1 also covers an app without a Leave reading (an unarmed Leave button): recommended no, since there is then nothing to contradict the release.

## Explicitly not

- Changing END21's trim rules: they are the owner's decisions of 2026-11-16, and the trim is the second-order harm here; the end is the first.
- [DET23](./DET23.md)'s MicHolderMonitor as the fix: it is log-only by design. It may later give the engine a second process-audio opinion, which is its own decision.
- The device-switch gap measurement: END15's owner remainder.

## Amendment 2026-11-17 (post-audit fix review)

Found by the [post-audit fix review](../../audits/2026-11-17-post-audit-fix-review.md) (lifecycle report, M1), confirmed by reading the code at `78b72306`. The ship note's residual ("ends 12 minutes after the flicker") is wrong. In `PromotionEngine.tick(at:)`, `micLeadContradicted` is a level read on every tick (`leave?.state == .live` among its terms) and `loneHeld` is `!leadClassContradicted && !micLeadContradicted && awake(from: loneSince, to: now) >= loneDwell`. In `handleEndingProvisional` the only anchor move is `let anchor = (event.kind.vetoesLoneEnd && previous?.state == .live) ? event.timestamp : loneSince`, so `loneSince` does not move when the Leave contradiction lifts. Scenario: a headphone switch opens a mic-led hold and the return is missed; the call goes on for 20 minutes with Leave live; the owner starts a screen share and the Leave element reads invalid for a few seconds (the reliability audit counted three such flickers of 5.5, 8.3 and 38.3 s in six recordings). On the next 0.25 s tick the refusal is gone and the dwell has long run out: `.ended` with `lone_dwell`, and END21 cuts the transcript back to the hold's start. Never earlier than before this task, but the protection does not hold on this route. `leadClassContradicted` (END18) has the same shape.

Scope addition: when a refusal lifts, count the lone dwell from that moment (move `loneSince` to the lifting reading's stamp), or require the lifting reading to stand for `confirmDwell`. Acceptance addition: a test with the flicker after `loneDwell` has elapsed; `test_the_leave_going_invalid_lifts_the_refusal_END29` covers only a flicker 30 s into the hold. Correct the ship note.

**Progress (2026-11-17): amendment shipped.** `PromotionEngine.loneDwellRefused(leading:startedAt:states:)` is now the one pure predicate for both refusals (END18's window-led `leadClassContradicted` and this task's mic-led `micLeadContradicted`), read by `tick`. `handleEndingProvisional` evaluates it before and after recording each reading, and a reading that turns it from refusing to not refusing moves `loneSince` to its own stamp (the review's preferred option: requiring the lifting reading to stand for `confirmDwell` would still end a live call 60 s into a flicker longer than that, and one measured flicker stood 38.3 s). Both refusals are level reads over the readings, so they can only lift when a reading arrives; `tick` needed no change. Tests: `test_a_leave_flicker_after_the_lone_dwell_restarts_it_rather_than_ending_at_once_END29` (a mic-led hold refused for 20 minutes, a Leave flicker: no end on the next tick) fails on the old engine; `test_the_leave_going_invalid_lifts_the_refusal_END29` now expects the end `loneDwell` after the lift (930 + 720 s), not after the release (900 + 720 s), by design. `test_a_window_led_hold_lifted_after_the_lone_dwell_ends_a_lone_dwell_later_END29` pins the cost on END18's side: with no process audio there is no pair route, so a window-led hold refused for longer than `loneDwell` that sees a real leave ends `loneDwell` after the Leave goes, not on the next tick, and trims nothing; the gotchas section names it. The anchor only moves forward. The corpus traces pass unchanged (one, `webex_ultrasound_retention_en`, now clears the dwell by 0.3 s rather than 0.5 s). Docs: daemon gotchas (END29 section), ADR 0017's lone-dwell and revert bullets, the `endingProvisional` doc comment.

## Amendment 2026-11-21 (second fix review)

Found by the [second fix review](../../audits/2026-11-21-second-fix-review.md) (follow-ups report, M1 and M2), confirmed by reading the code at `8426758b`.

Two things, neither a regression of the two commits.

1. The named residual is real and its cost is larger than "ends early". `PromotionEngine.pairEdges(in:holdStartedAt:)` takes a class's edge as its earliest ended member once no class-mate reads live (`edges[cls] = min(edges[cls] ?? reading.at, reading.at)`), so a window minimised early in a missed-return hold has already "dwelled" by the time one Leave read comes back invalid, and the pair holds on the next tick. The commit pins this as `test_a_minimised_window_plus_a_leave_flicker_still_pairs_residual_END29`. Because it is an engine end with process audio released, END21 then cuts at the release: every minute of the live call after the headphone switch leaves the transcript, and under NDA or regulated capture those minutes are truncated on disk. The rule the 2026-11-17 amendment applied to `loneSince` fits here: a class's edge should not predate the moment its last live member went ended. The ship note argues that would change END14's class edge and END18's declined exemption; that argument should be tested against the 2026-11-12 Zoom hold trace before it is accepted.

2. Owner decision, excluded by this spec's "Explicitly not". On the genuine end of a missed-return hold, `TeardownHoldPolicy.trimPoint(concludingAt:evidence:conclusion:)` still returns `max(releasedAt, hold.startedAt)`, and `releasedAt` is still the headphone switch. So the minutes END29 now keeps recording are cut from the transcript when the owner really leaves, and deleted by `recorder.stop(limitSeconds:)` under NDA or regulated capture. The title failure is delayed, not prevented, in those modes. A narrow option: a mic-led hold that a live Leave ever refused does not cut at the release (the call evidently ran on), and falls back to the pair's own edge.

Acceptance if taken: the residual test flips to `no_end` for the flicker case, a new test pins that a genuine end after a refused hold does not trim before the last live Leave reading, and the three `no_end` traces plus the Zoom hold trace still replay as recorded.
