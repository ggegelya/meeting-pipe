# UX88: workflow matching rules and the auto-record allowlist ask for raw bundle ids and regular expressions, and a malformed regex silently never matches

Band origin: filed 2026-10-24 from the 2026-10-24 audit band ([go-live assessment](../../audits/2026-10-21-go-live-assessment.md) UX-11). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Verified in code on 2026-10-24.

**The workflow editor's rules are two free-text fields.** `WorkflowsView.matchingRuleRow` renders `TextField("bundle id", ...)` and `TextField("title regex (optional)", ...)` per rule, and the section footer explains them as "Bundle id matches the meeting app (e.g. `us.zoom.xos`, `com.microsoft.teams2`). Title regex is case-insensitive and tests the window title". A user has to know that Zoom is `us.zoom.xos`, that new Teams is `com.microsoft.teams2` and classic Teams is `com.microsoft.teams`, and how to write a regular expression.

**A typo fails silently.** `WorkflowMatcher.ruleScore` compares `rule.bundleID != source.bundleID` exactly, so a misspelled id scores 0 forever. `WorkflowMatcher.titleMatches` compiles the pattern with `try? NSRegularExpression(...)` and returns `false` when it does not compile, so a regex with an unbalanced parenthesis or bracket never matches and the meeting falls through to the default workflow with no message anywhere. Characters like `(`, `[`, `+` and `.` are common in meeting titles a user would paste.

**The auto-record allowlist has the same shape.** `PreferencesView+Recording`'s "Auto-record allowlist" group is a `TextField("us.zoom.xos", ...)` in monospace with an **Add** button; entries render as raw bundle-id tags.

**What the app already knows.** `MeetingAppRegistry` loads the bundled `meeting_apps.toml` (six native bundle ids: Zoom, both Teams, Slack, both Webex) plus the user overlay, and every recorded meeting's sidecar carries its source app. `NSWorkspace` resolves a bundle id to an app name and icon. AI9's learned routing (GUIDE.md "A learned suggestion") already proposes a workflow from the app a meeting came from, without asking for an id.

The rule data model is daemon-only: the pipeline reads no `bundle_id` or `title_regex` from workflow files (`grep -rn title_regex pipeline/src` is empty), so the editor can change without a Swift/Python contract change.

## Scope

1. **An app picker.** One shared `MeetingAppPicker` view lists the registry's apps plus any app seen as a meeting source in the library, each with its name and icon from `NSWorkspace`, and an **Other app…** entry that opens an application chooser (`NSOpenPanel` on `/Applications`) and reads the chosen bundle's identifier. The stored value stays the bundle id. The workflow rule row and the auto-record allowlist both use it; allowlist tags render as app names.
2. **"Title contains" by default.** The title field becomes a plain substring match: the editor stores `NSRegularExpression.escapedPattern(for:)` of what the user typed, so the stored `title_regex` and `WorkflowMatcher` are unchanged and every existing rule keeps working. A **Use a pattern** toggle on the row keeps raw regex for power users, and a rule whose stored regex is not an escaped literal opens with that toggle on, showing the regex as stored.
3. **Validation where the user types.** In pattern mode the row shows "This pattern is not valid" under the field when `NSRegularExpression` fails to compile it, and Save is refused for that rule. `WorkflowMatcher` logs one `workflow.rule_regex_invalid` event (existing `workflow` category) the first time a stored rule fails to compile, so a rule hand-edited into the TOML is not silent either.
4. **Docs in the same commit**: GUIDE.md's "How a meeting picks one" and README's matching-rule paragraph describe the picker and "title contains", and `CONVENTIONS.md`'s event table gains the new action if the truth fences require it.

## Explicitly not / out of scope

- Changing matching precedence or scoring (bundle plus title 3, bundle 2, title 1). Unchanged.
- Browser-tab routing by host (meet.google.com versus teams.live.com in the same browser). The title field covers the common case; per-host rules would need the detection source to carry the tab host, which is DET6's ground.
- Recording-consent posture for `auto_consent_apps`: SEC24 (P3). This task changes how the list is edited, not what it means.
- A broader rename of "workflow": UX86.

## Acceptance

- Tests: a "title contains" input with regex metacharacters (`Q3 (EU) planning [draft]`) is stored escaped and matches that literal title through `WorkflowMatcher.resolve`; a stored non-literal regex round-trips with pattern mode on; an invalid pattern is reported by the row's validator and refused on save; `WorkflowMatcher` emits `rule_regex_invalid` once per invalid stored rule, not per meeting.
- Tests: the picker's source list merges registry apps and library source apps without duplicates, and an unknown bundle id falls back to showing the id.
- Existing `WorkflowMatcher` tests stay green unchanged, which is the proof stored rules did not move.
- `cd daemon && swift build` and `swift test` green, N new tests in the commit body; `python3 scripts/truth_fences.py both` green.
