# UX108: Single-meeting Reprocess, Re-summarize with and Regenerate summary rewrite the summary and republish straight off the click

Band origin: filed 2026-11-13 (audit band 2026-11-13, see [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md)). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Source: finding F067 in the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md) (data lens, confirmed). The [field evidence report](../../audits/2026-11-13-field-evidence.md) files F067 under "cannot tell from this data": 77 regenerate and 76 republish requests between 2026-05-28 and 2026-09-04, with no log surface that says whether any of them landed on a hand-edited summary.

**The rule already exists, for the batch form only.** UX61 (done 2026-08-16, see [q6-final.md](../q6-final.md)) recorded the owner's line in `BatchActionConfirmation`'s doc comment: a gate is owed for "destruction of what the owner wrote by hand", and `Re-summarize all` confirms because "`regenerateMeeting` overwrites `<stem>.summary.json`, which is exactly where `SummaryTab.persistEdit`'s text edits and `setActionResolved`'s done ticks live". `BatchActionsPane` raises `BatchActionConfirmation.resummarize(count:cloudCount:)` before `runRegenerate()`. UX61's spec never considered the single-meeting entry points, which overwrite the same file.

**The single-meeting entry points, re-read at HEAD on 2026-11-13.**

1. Detail header, More actions menu (`MeetingDetailView+Header.swift`, `actionsMenu`): `Button("Reprocess\u{2026}") { toolbarAction("reprocess") { _ = libraryModel.retryMeeting(stem: meeting.stem) } }`. The ellipsis promises a surface that never opens, and the `Result` is thrown away.
2. Detail header, `reSummarizeItems` (shared by the More actions submenu `reSummarizeMenu` and UX41's inline "Re-summarize" cue in the caption row): each engine row calls `runReSummarize(backend:)`, which runs `libraryModel.regenerateMeeting(stem:backend:)` at once.
3. Library row context menu (`MeetingRow.contextMenuItems`): `Button("Regenerate summary") { Task { await onRegenerate() } }`, wired in `LibraryListView.row(for:)` to `regenerateMeeting(stem:)`.
4. Detail failure banner (`MeetingDetailView.failureNotice`): the "Re-summarize with <local engine>" button shown when `meeting.failureSuggestsLocalReSummarize`, which calls `regenerateMeeting` directly. It overwrites an existing summary when the failed meeting has one.

**Why Reprocess on a healthy meeting is a regenerate plus a republish.** `MeetingLibraryService.retryMeeting(stem:)` reads the failure sidecar; on a meeting with none, `failure?.stage != .transcribe` is true, so a meeting with `hasReusableTranscript` goes to `regenerateMeeting(stem:)`, which runs `launcher.summarize` and, on success and unless the meeting moved into zero egress mid-run, chains into `performRepublish`. Without a reusable transcript it enqueues a full run, which also rewrites the summary. Only a publish-stage failure with a summary on disk takes the non-destructive `republishMeeting` path.

**Refusals.** `retryMeeting` returns `.failure` for `LibraryError.noAudio` (no reusable transcript and no final recording) and `LibraryError.metaWriteFailed` (SEC25 manifest restore could not land). The header's `_ =` drops both, so the click does nothing visible.

Correction at filing: the audit's "row Reprocess" does not share the defect. `MeetingRow` offers its own `Reprocess` only when `meeting.status == .failed`, and `runRetry()` already presents "Retry failed" on `.failure`; the failure banner's Retry likewise shows `FailureDialog`. The silent refusal is the detail header's Reprocess only.

Correction at filing: `BatchActionConfirmation.resummarize(count: 1, cloudCount:)` cannot be reused as is. Its title is `"Re-summarize \(count) meetings?"` and its message is plural ("these summaries"), and its `cloudCount` is derived from `isZeroEgress`, which ignores the engine the user picked, so "Re-summarize with" the local engine on a non-zero-egress meeting would be told it is a paid call. The single-meeting form needs singular copy and the chosen backend.

Related: [PIPE54](./PIPE54.md) (same band) is the other way Retry re-summarizes over a user's edit; [ARCH10](./ARCH10.md) owns the per-meeting file contract that views rewrite `summary.json` through.

## Scope

1. **A single-meeting confirmation on the existing type.** Add `BatchActionConfirmation.resummarizeOne(reachesCloud: Bool)` (name open) beside `resummarize(count:cloudCount:)` in `BatchActionConfirmation.swift`: singular title ("Re-summarize this meeting?"), the same sentences about edits and done ticks being lost and the recording and transcript being untouched, and the paid-call clause gated on `reachesCloud` exactly as `merge` does. `reachesCloud` is true only when the meeting is not `isZeroEgress` and the resolved backend for this run is a cloud engine (the explicit `backend` for Re-summarize with, otherwise the workflow or configured backend).
2. **A pure gate decision.** One function (on the same type or a sibling) that says whether a single-meeting action needs the confirmation: yes when `meeting.hasSummaryJSON` and the action would regenerate (Regenerate summary, every Re-summarize with row, the failure banner's local re-summarize, and Reprocess unless `retryMeeting` would take the publish-only path for a publish-stage failure with a summary on disk). No summary on disk means nothing hand-authored can be lost, so no dialog.
3. **Wire every entry point through it.** `actionsMenu`'s Reprocess, `runReSummarize(backend:)` (which covers both `reSummarizeMenu` and the UX41 inline cue), `MeetingRow`'s Regenerate summary, and `failureNotice`'s Re-summarize with the local engine. Use the SwiftUI `.alert` idiom UX61 chose, destructive confirm button, Cancel as `.cancel`. The `toolbar_action` event for `reprocess` and `re_summarize_<backend>` is logged when the action actually runs, after confirmation, so the existing audit trail counts real runs.
4. **Surface the header Reprocess refusal.** Replace `_ = libraryModel.retryMeeting(...)` with the same `FailureDialog.show(FailurePresentation(error:title:))` the failure banner uses.
5. Docs in the same commit: `README.md`'s Library detail and row-menu passages, and any `docs/GUIDE.md` recipe that describes Reprocess, Re-summarize with or Regenerate summary.

## Explicitly not

- Gating Republish or Retry publishing: UX61's recorded rule is that republish destroys nothing the owner authored.
- `SummaryTab`'s Reprocess with a custom prompt (TECH-FEAT7): it produces a candidate in a compare pane and replaces nothing until the user accepts.
- An undo or a pre-regenerate backup of `<stem>.summary.json`: a larger change, and the confirmation is what UX61 chose for the same destruction.
- WF8's post-reassign Regenerate offer (`offerReassignFollowups`): already a user-chosen dialog; if its copy omits the edit loss, that is a separate copy fix.
- Re-transcribe: it leaves the summary alone and already confirms (ASR3).
- PIPE54's schema-rejection path, where an automatic Retry re-summarizes over an edit.
