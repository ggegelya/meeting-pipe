# UX69: A running job cannot be cancelled for its first minute

Band origin: filed 2026-08-04, split out of UX50's second pass rather than folded into it (UX50's seam is the progress entry's lifetime; this one is a missing cancellation capability). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The owner reported during UX50's 2026-08-04 walkthrough that Cancel "is not offered immediately after Reprocess and appears only some time later", so there is a window in which a running job cannot be stopped. UX50 measured the window rather than guessing it, from the owner's own run of `20260716-163031` in `events.jsonl` and `pipeline_events.jsonl`:

```
13:03:39.998Z  toolbar_action reprocess        (click)
13:03:40.034Z  transcription engine_started    (FluidAudio, in-daemon)
13:04:32.574Z  transcription engine_succeeded  (+52.5 s)
13:04:33.553Z  pipeline run_started            (+1.0 s)
13:04:38.629Z  pipeline stage_progress beat 1  (+5.1 s)  <- Cancel first appears
```

**58.6 s with no Cancel offered.**

The cause is that Cancel is gated on `activeProcessing`, and only a pipeline heartbeat writes that entry. For a full run-all, nothing beats until the daemon's own FluidAudio pass finishes. That pass took 52.5 s on this 110 minute meeting and **scales with meeting length**, so the window is not a fixed cost the owner can learn to expect. The remaining ~6 s is fixed: `mp` process start plus one 5 s heartbeat interval.

**The two halves of the window need different fixes, which is why this is one task with two legs rather than two tasks.** The ~6 s tail is presentational: the subprocess exists and `PipelineLauncher.cancelActiveRun` has a handle to signal, so the entry is simply published later than it could be. The 52.5 s head is not: during the in-daemon ASR pass there is no subprocess and nothing retained, so `cancelActiveJob` would have nothing to act on. Offering Cancel there without a real cancellation seam ships a dead control, which is worse than not offering it.

Related and deliberately not merged: UX50 fixed the stuck `Cleaning up` row (the progress entry outliving the job) and landed 2026-08-04 as `99a42bd`. That fix is about when the entry **ends**; this task is about when it **begins** and what a cancel during ASR should do.

## Scope

Two legs, smallest change each.

**(a) The tail.** Publish the `activeProcessing` entry when `invokePipeline` spawns the subprocess, rather than waiting for the first heartbeat. That is the exact moment `PipelineLauncher.cancelActiveRun` becomes able to signal something, so the control appears when it starts working and not before.

**(b) The head.** A cancellation seam in `TranscriptionRunner` so the in-daemon FluidAudio pass can be interrupted, plus a cancelled-during-transcription completion that lands the same way the run-all cancel does today: a terminal `interrupted` marker, the row still retryable, and nothing reported as a failure (no `pipeline_failed`, no banner, no notification). UX50 already established that shape and `PipelineLauncher.isCancellation` is the existing predicate; reuse both rather than inventing a second cancellation vocabulary.

If leg (b) turns out to need a FluidAudio API that does not exist, stop and say so rather than shipping a Cancel that only sometimes works: leg (a) alone is a legitimate partial, and the honest outcome is a shortened window with the remainder named.

## Explicitly not / out of scope

- **Do not offer Cancel during ASR without leg (b).** A control that is visible but cannot stop the work is the failure this task exists to avoid, and it is worse than the current silence.
- **Do not solve it by shortening the heartbeat interval.** That trims about 5 s of a 58.6 s window and leaves the scaling head untouched.
- **Do not reopen UX50's modelling.** A cancelled run completes as `LaunchError.cancelled` with an `interrupted` marker and reports nothing; that was decided, shipped, and verified on the owner's own run.
- Cancelling an **Ask** is already covered: `AskModel.cancel` closes its run out synchronously and drops the late completion by run id, pinned by five `AskModelTests`.

## Acceptance

- With a meeting reprocessed, the row offers **Cancel from the moment the pipeline subprocess is spawned**, not from the first heartbeat. Pinned by a test on the dispatcher that asserts the entry is published on spawn.
- A cancel issued **during the in-daemon transcription pass** stops the work and completes as a cancellation: terminal marker `stage: interrupted`, row still retryable, and no `pipeline_failed` event, banner, or notification. Pinned by a test at the `TranscriptionRunner` seam.
- The event log for such a run shows `pipeline_cancelled` and does **not** show `pipeline_failed`.
- `swift build` clean and `swift test` green, with new tests covering both legs (count left to the session that writes them).
- `python3 scripts/truth_fences.py both` green if any event category or config key moves.
