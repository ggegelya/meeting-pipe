# LOCAL23: Local summarize sizes its requests in characters against the cloud gate's knob, so one call can run past Qwen2.5's 32K context or a tight tier's ceiling, and map-reduce makes about 115 calls for two hours of speech

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Review findings PYTHON-2 (finder high, verifier confirmed high) and PYTHON-8 (finder medium, verifier plausible medium: the code facts are verified, the wall-clock magnitude is not). One task, because the verifier's note on PYTHON-2 is that changing the routing without resizing the windows sends many more meetings through 1,500-char map calls. Re-checked against `main` on 2026-10-25 in [summarize_local.py](../../../pipeline/src/mp/summarize_local.py); figures marked measured were computed at HEAD with the pipeline's own functions.

**1. Routing reads characters and the cloud knob, never tokens, the tier or the model.** `LocalSummaryClient.summarize` map-reduces only on `if self._map_reduce_above_chars and len(transcript) > self._map_reduce_above_chars`, and both summarize constructions (`providers._local_summary`, and the `auto` ladder's local rung, the `_local` closure in `summarize.AutoFallbackClient.summarize`) pass `map_reduce_above_chars=...skip_above_chars`, the cloud paste-bundle knob (default 80000, which `config.py` glosses as about 20,000 tokens and an hour of speech). `context_token_ceiling` is read only by `ask.context_ceiling` and `doctor`, although `ask.context_ceiling`'s docstring says "one table is what keeps the summarize path and the ask path agreeing". `orchestrate._check_too_long` exempts local backends, so every local transcript up to 80,000 chars goes to the model in one request.

**2. What that request costs.** The fixed prompt is `augment_with_schema(system_prompt)`: measured at 6,725 chars for `_load_system_prompt("")` and 15,857 with the schema, roughly 4,000 to 5,000 tokens at LOCAL13's measured 0.25 tokens per char for Latin text. At LOCAL13's 0.49 for Cyrillic (`summarize_staged.tokens_per_char`, and the same rates as chars per token in `ask.chars_per_token`), an 80,000-char Ukrainian transcript is about 39,000 tokens, so one request is about 43,000 input tokens: past Qwen2.5's native context of 32,768 (`max_position_embeddings` in the cached 3B's `config.json` on 2026-10-25; every curated preset is Qwen2.5) on every preset, and five times the 32 GB tier's 8,000-token ceiling. The tier table records where that ceiling comes from, "AI2 measured the 14B on this 32 GB Mac: fine at 4K tokens, watchdog abort at 8K, OOM at 16K", and the 14B is admitted on 24 and 32 GB. `MemoryWatchdog.check` runs in `_chat_completion` before each request ("Checked BEFORE the request"), so it cannot stop one in-flight call whose read timeout is `scaled_request_timeout(120, 4000)`, 520 s, and [LOCAL18](./LOCAL18.md) doubts its floor is reachable at all. LOCAL16 decided "the 80k threshold stands; the guard aborts before swap rather than silently truncating content" (its out-of-scope list, archived in [q6-final.md](../q6-final.md)); this task keeps the no-truncation half and replaces the premise of the other.

**3. The ceiling is the 14B's, and the default model is not tight.** Holding every model to the 14B's ceiling would be a regression of its own: [engine-comparison.md](../../engine-comparison.md) records the 7B single-pass with "zero failures over 26 meetings" on the 32 GB Mac. `resource_guard.TIGHT_FRACTION`'s comment names the population that has produced OOM reports ("The 7B on 16 GB and the 14B on 24-32 GB both land here"), and `resource_guard.assess(model_id, ram_gb).fit` already computes it. On the owner's 48 GB Mac (16,000-token ceiling, 20 GB model cap) every preset is `fits`. On the 16 and 24 GB tiers the ceiling is 4,000 tokens, which the fixed prompt alone already reaches, so no window size honours it with the current prompt.

**4. Map-reduce is sized for the wrong rate and pays the prompt on every call.** `_MAP_WINDOW_CHARS = 1_500` and `_MAP_OVERLAP_CHARS = 200`, with the comment "Cyrillic tokenizes at ~1.7 tokens/char, so ~1500 chars keeps a worst-case map call near the ~4K-token safe budget once the fixed system prompt, JSON schema, and output are added". LOCAL13 measured 0.49, not 1.7, and the fixed prompt alone is 15,857 chars, so a window is under a tenth of each map call's input. Measured: `chunked_windows` cuts a 110,000-char transcript (about two hours with timestamps) into 85 windows, and `_reduce_partials` merges them in batches of `_REDUCE_BATCH = 4` in 21, 6, 2 and 1 calls, so 115 sequential full-`MeetingSummary` generations at `max_tokens` 4000, each with a possible schema repair and a LOCAL7 language retry. [engine-comparison.md](../../engine-comparison.md) measured a whole single-pass meeting at about 57 s on the 7B and 84 s on the 14B, model load included; at even a third of that per call, 115 calls is over 35 minutes, past `PipelineLauncher.summarize`'s `timeout: 20 * 60` (the Library's Re-summarize), and a three-hour meeting nears `PipelineLauncher.defaultMaxRuntime` (`90 * 60`) for run-all. That is an estimate; acceptance measures it.

**5. A language repair re-runs all of it.** `summarize._verify_and_repair_language` (LANG1) calls `client.summarize(system_prompt=system_prompt + language_reinforcement(target), transcript=transcript, ...)` on the same client, so a map-reduced summary whose merge still drifts is windowed, mapped and reduced again from scratch, and the changed system prefix also defeats the server's prompt-cache reuse.

**Reachability.** A `local` backend, keyless `auto`, and every NDA or regulated meeting, which `effective_backend` forces on-device. The owner's `config.toml` on 2026-10-25 has `backend = "anthropic"` and the 3B as `local_model`.

## Scope

1. **One token estimator the summarize path can import.** LOCAL13's two rates live twice (`ask.chars_per_token`, `summarize_staged.tokens_per_char`). Move one copy into `resource_guard` beside `tier_for` and make the other two delegate to it. `resource_guard` keeps `summarize_local` inside the lazy-import contract, where `ask` would pull numpy in through `embed_index`, and [PIPE20](./PIPE20.md) may delete `summarize_staged`.
2. **A request budget in `summarize_local`.** Count input tokens (system prompt plus transcript, each at its script rate), the quantity AI2's ceiling and `ask`'s clamp both measure. The budget is the native context minus `max_tokens` (a named 32,768 constant documented as Qwen2.5's, used for a Custom model id too), lowered to `tier_for(ram_gb).context_token_ceiling` when `assess(model, ram_gb).fit == "tight"` and that ceiling still leaves room for at least one 1,500-char window above the fixed prompt. Where it does not (the 4,000-token tiers), keep the native budget and log one warning per run naming the gap, rather than routing to map calls that would still exceed it. Unknown RAM keeps the current rule.
3. **Route on it.** `LocalSummaryClient.summarize` stays single-pass when the estimated request fits the budget and the transcript is under `_map_reduce_above_chars`, and map-reduces otherwise. The char knob stays an upper bound, so [PIPE27](./PIPE27.md)'s split of it into `local_chunk_above_chars` composes with this rather than conflicting.
4. **Size the windows on it.** `_summarize_map_reduce` derives window chars from the budget minus the fixed prompt, converted at the transcript's rate, floored at the current 1,500 chars and keeping the 200-char overlap; the 1.7 tokens-per-char comment goes. The map prompt and schema do not change.
5. **Repair only the merge.** A LANG1 repair of a map-reduced summary re-runs only the reduce. Preferred shape, which leaves LANG1's call as it is: the client keeps the map partials of the last transcript it windowed, keyed on the transcript and the target, and a repeat `summarize` on the same transcript reuses them and runs only `_reduce_partials` under the new system prompt. LANG1's keep-the-original-on-failure fallback is unchanged.

## Explicitly not

- A compact map prompt or a partial schema for map calls. That is the pipeline-shape lever [LOCAL14](./LOCAL14.md)'s staged summarizer already is (EXTRACT over script-aware windows), waiting on its owner bench in [owner-verification.md](../owner-verification.md); a second one here would move that lever without the bench. On the 4,000-token tiers that leaves the ceiling unmet, which item 2 logs rather than hides.
- Truncating a transcript to fit, which LOCAL16 rejected and this task keeps rejected.
- A deadline that returns a partial summary under the daemon's caps. It needs a sidecar marker so a truncated summary is not passed off as complete ([PIPE34](./PIPE34.md) and [ARCH10](./ARCH10.md) own those contracts); measure after items 3 and 4 first.
- A per-model ceiling computed from each model's KV size, or retuning the tier table. The `tight` rule reuses the policy's own population; a per-model table is a later decision for [LOCAL18](./LOCAL18.md)'s measurement to inform.
- How many finished requests the server keeps resident: the sibling task filed from this review (finding PYTHON-1 ([LOCAL22](./LOCAL22.md))).
- [PIPE20](./PIPE20.md) item 4 drops LOCAL7's inner retry so LANG1 owns language repair everywhere; item 5 here keeps that from costing a full re-run on a long meeting. Whichever lands second runs the other's language tests. [OBS2](./OBS2.md)'s event for a failed language repair is unaffected.
- The cloud gate itself and token-usage recording ([PIPE27](./PIPE27.md)).

## Acceptance

- Routing tests in `test_summarize_local.py`, with RAM and fit injected and the fake `mlx_lm.server`:
  - an 80,000-char Cyrillic transcript on the 7B at 48 GB map-reduces (fails on the current code, which sends it single-pass);
  - a 40,000-char Cyrillic transcript on the 14B at 32 GB (`tight`) map-reduces, and every request the fake server receives, map and reduce, is estimated at or under 8,000 input tokens (fails on the current code);
  - a 30,000-char English transcript on the 7B at 32 GB stays single-pass with a request byte-identical to the current one;
  - a 15,000-char transcript on the 7B at 16 GB stays single-pass and logs the ceiling gap once;
  - unknown RAM reproduces the current routing.
- A window-count test: a 110,000-char English transcript on the 7B at 48 GB makes at most 3 map calls on the fake server, against 85 at HEAD 01e904a.
- A LANG1 test: a map-reduced summary whose merge drifts language is repaired with zero map calls and at least one reduce call, and a repair that still drifts keeps the original.
- `test_resource_guard.py`: the promoted estimator gives 0.25 for Latin text, 0.49 for Cyrillic and interpolates a mix; the existing `ask` and staged sizing tests stay green unchanged.
- `cd pipeline && uv run --extra dev pytest -q` green with the number of new tests in the commit body; ruff and pyright (`--extra mcp`) clean; `bash scripts/ci-local.sh pipeline` green.
- Evidence (confirms, does not gate; a session can run it on this Mac, where the 3B is the cached preset on 2026-10-25): summarize one real transcript over 80,000 chars with `--backend local` before and after, and record each run's request count and wall time in the commit body.
