# UX33: Workflow inspector rework

Band origin: filed 2026-07-29 (owner exploratory sweep, item 1: the workflow details panel "looks quite strange to me, I think it requires rework", decision delegated and taken: rework is warranted). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

`WorkflowInspector.swift` (187 lines) renders the right-column pane for a selected workflow scope. Traced 2026-07-29, the "strange" read decomposes into six concrete defects:

1. **The Edit button floats mid-pane.** The layout is `ScrollView > VStack` (:11-12) with a `Spacer(minLength: 0)` at :18 meant to pin the "Edit workflow" button (:19-23) to the bottom. A `Spacer` inside a `ScrollView` is inert (the scroll view sizes to content), so a workflow with little content shows a short card and a large empty region below it. This is the biggest single contributor to the broken feel.
2. **A 320pt ribbon in an unbounded pane.** The inspector caps itself at `minWidth: 240, idealWidth: 260, maxWidth: 320` (:27) while the detail column it sits in has a min of 450 and no max (`LibraryWindow.swift:782`, `LibraryLayout.swift:25-26`). On a wide window the pane is mostly background.
3. **"Modes" usually says "-".** `modesLine` (:131-133) returns "-" whenever NDA is off, which is most workflows. A permanent row whose value is a dash is noise.
4. **Recent chips look interactive and are not.** The RECENT section (:87-111) renders up to 5 meeting titles as chip-backgrounded `Text` (:95-108) with no button, tap gesture, or navigation. Clicking a recent meeting does nothing.
5. **Trigger leaks implementation detail.** `triggerLine` (:115-129) prints raw bundle ids and `/regex/` strings joined by commas; "Output" truncates a Notion DB id to an 8-char slug (:140-143). Neither is written for the product's register (PRODUCT.md: quiet, deliberate, non-technical owner).
6. **The pane is unreachable whenever a meeting is selected.** The detail-pane branch order at `LibraryWindow.swift:950-954` is multi-select, then single meeting, then workflow scope, so selecting a workflow in the rail while a meeting selection exists shows the meeting, not the inspector. The pane is effectively an empty state, not an inspector.

Also missing entirely: retention policy (a real `Workflow` field, visible only in the editor sheet), meeting count, last-meeting date. The pane has exactly one affordance (Edit).

## Scope

Redesign `WorkflowInspector` into a pane that fills its column and earns each row:

- Identity header: emoji/colour, name, DEFAULT badge, the FEAT11 context state line (keep; it is good), and the context prompt behind a disclosure rather than a 3-line dump ahead of the facts.
- Facts that earn their row: drop "Modes" when it would read "-" (show it only when NDA or redaction is on); humanize Trigger ("Matches Microsoft Teams" plus a quiet secondary line for title rules); show Output as the sink names with the Notion target's display name where the picker already knows it.
- Add the two cheap truths the pane is missing: meeting count for the scope and the last meeting's date (both derivable from the already-loaded scope counts and meeting list; no new disk reads).
- Recents become buttons: clicking one selects that meeting in the list (the selection state lives on `LibraryRootView`; hand the tap up rather than resolving stems in the inspector).
- Actions: keep Edit primary; visually pin it (give the pane a non-scrolling footer or accept content-flow placement, but kill the dead region); the row-level Delete stays UX32's.
- Layout: widen to fill the detail column with a centered max around 400-480pt so it reads as a card, not a ribbon.
- Reachability: decide-and-record between (a) selecting a workflow rail scope clears the meeting selection so the inspector always shows, or (b) the inspector is also reachable from a compact header chip when a meeting is open. Recommendation: (a); it matches how scope switches already feel and is one line where the scope changes.
- Extract the row derivation into a pure `InspectorPresentation`-style type per the repo's decide-pattern (daemon/CLAUDE.md "Pure logic on its own type"), so trigger humanization and row visibility are table-tested.

## Explicitly not in scope

Inline editing in the inspector (the sheet remains the single editor). UX32's row actions. Any new analytics beyond count and last-date. Changing `LibraryScope` resolution semantics (TECH-B4 name-based resolution stays; UX30 owns the alert-copy honesty about it).

## Acceptance

Unit tests on the extracted presentation type: trigger humanization cases (bundle-only rule, bundle+title rule, no rules), Modes row hidden when NDA and redaction are both off and shown otherwise, Output naming with and without a known Notion display name, recents capped at 5.

A UI-level test (or the presentation seam) pins that tapping a recent invokes the selection callback with the right stem.

The reachability decision is recorded in this file at pickup and the chosen behavior is pinned by a test on the scope-change path.

`cd daemon && swift build` and `swift test` green (baseline at filing: 1770). Repo dash guard green.
