# UX33: Workflow inspector rework

Band origin: filed 2026-07-29 (owner exploratory sweep, item 1: the workflow details panel "looks quite strange to me, I think it requires rework", decision delegated and taken: rework is warranted). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

`WorkflowInspector.swift` (187 lines) renders the right-column pane for a selected workflow scope. Traced 2026-07-29, the "strange" read decomposes into six concrete defects:

1. **The Edit button floats mid-pane.** The layout is `ScrollView > VStack` (:11-12) with a `Spacer(minLength: 0)` at :18 meant to pin the "Edit workflow" button (:19-23) to the bottom. A `Spacer` inside a `ScrollView` is inert (the scroll view sizes to content), so a workflow with little content shows a short card and a large empty region below it. This is the biggest single contributor to the broken feel.
2. **A 320pt ribbon in an unbounded pane.** The inspector caps itself at `minWidth: 240, idealWidth: 260, maxWidth: 320` (:27) while the detail column it sits in has a min of 450 and no max (`LibraryWindow.swift:782`, `LibraryLayout.swift:25-26`). On a wide window the pane is mostly background.
3. **"Modes" usually says "-".** `modesLine` (:131-133) returns "-" whenever NDA is off, which is most workflows. A permanent row whose value is a dash is noise.
4. **Recent chips look interactive and are not.** The RECENT section (:87-111) renders up to 5 meeting titles as chip-backgrounded `Text` (:95-108) with no button, tap gesture, or navigation. Clicking a recent meeting does nothing.
5. **Trigger leaks implementation detail.** `triggerLine` (:115-129) prints raw bundle ids and `/regex/` strings joined by commas; "Output" truncates a Notion DB id to an 8-char slug (:140-143). Neither is written for the product's register (PRODUCT.md: quiet, deliberate, non-technical owner).
6. **The pane is unreachable whenever a meeting is selected.** The detail-pane branch order at `LibraryWindow.swift:950-954` is multi-select, then single meeting, then workflow scope, so selecting a workflow in the rail while a meeting selection exists shows the meeting, not the inspector. The pane is effectively an empty state, not an inspector.

Also missing entirely: retention policy (a real `Workflow` field, visible only in the editor sheet), meeting count, last-meeting date. The pane has exactly one affordance (Edit).

## Scope

Redesign `WorkflowInspector` into a pane that fills its column and earns each row:

- Identity header: emoji/colour, name, DEFAULT badge, the FEAT11 context state line (keep; it is good), and the context prompt behind a disclosure rather than a 3-line dump ahead of the facts.
- Facts that earn their row: drop "Modes" when it would read "-" (show it only when NDA or redaction is on); humanize Trigger ("Matches Microsoft Teams" plus a quiet secondary line for title rules); show Output as the sink names with the Notion target's display name where the picker already knows it.
- Add the two cheap truths the pane is missing: meeting count for the scope and the last meeting's date (both derivable from the already-loaded scope counts and meeting list; no new disk reads).
- Recents become buttons: clicking one selects that meeting in the list (the selection state lives on `LibraryRootView`; hand the tap up rather than resolving stems in the inspector).
- Actions: keep Edit primary; visually pin it (give the pane a non-scrolling footer or accept content-flow placement, but kill the dead region); the row-level Delete stays UX32's.
- Layout: widen to fill the detail column with a centered max around 400-480pt so it reads as a card, not a ribbon.
- Reachability: decide-and-record between (a) selecting a workflow rail scope clears the meeting selection so the inspector always shows, or (b) the inspector is also reachable from a compact header chip when a meeting is open. Recommendation: (a); it matches how scope switches already feel and is one line where the scope changes.
- Extract the row derivation into a pure `InspectorPresentation`-style type per the repo's decide-pattern (daemon/CLAUDE.md "Pure logic on its own type"), so trigger humanization and row visibility are table-tested.

## Reachability decision, taken at pickup 2026-07-29

**(a): selecting a workflow rail scope clears the meeting selection.** Taken as recommended, and implemented as `LibraryScope.clearsMeetingSelection` (true only for `.workflow`), read by one `onChange(of: scope)` in `LibraryRootView`.

Why not (b), the compact header chip: it adds a second entry point to a pane whose problem is that it is unreachable, which leaves the original branch-order bug in place and pays for it with new chrome in a header PRODUCT.md's register wants quiet. (a) removes the condition instead of routing around it.

Why the rule is scoped to `.workflow` and not "any scope change": `.allMeetings` is what Facts, People, Ask, Quick Find, and the `meetingpipe://open?stem=` deeplink all switch to *before* setting a selection, in the same closure. A blanket clear would fire on that scope write and undo the navigation those five surfaces had just performed. Pinned by `test_no_other_scope_clears_the_meeting_selection`.

Residual, accepted: with a meeting open under a workflow scope, getting back to the inspector still means deselecting. That is one click, the toolbar keeps its own `Edit workflow` button in that state, and it is the same shape every other scope already has.

## Explicitly not in scope

Inline editing in the inspector (the sheet remains the single editor). UX32's row actions. Any new analytics beyond count and last-date. Changing `LibraryScope` resolution semantics (TECH-B4 name-based resolution stays; UX30 owns the alert-copy honesty about it).

## Second pass, 2026-07-29 (the owner's eyeball, and the ribbon that survived it)

The eyeball happened the same day: "workflow view looks better, yet still ugly, also 'edit workflow' button looks like something from another world". A layout review was mocked at true scale and approved before any further code was written.

**The card was still a ribbon.** `cardMeasure = 416` was derived as `LibraryLayout.detailMinWidth (450) - 2 * padding`, which is a correct derivation of the wrong quantity: it sizes the card for the narrowest window the app allows and then freezes it at every width. On the owner's 1230pt pane that left 812pt of background. This task was filed to kill "a 320pt ribbon in an unbounded pane" and shipped a 416pt ribbon in an unbounded pane. The spec is what failed, and it failed by self-contradiction: "widen to fill the detail column with a centered max around 400-480pt" asks for two things that cannot both be true at 1230pt, and the first pass followed the number rather than the intent. `.frame(maxWidth:)` already shrinks a wider cap back at the floor, so the floor never needed deriving at all.

`cardMeasure` is now `cardMaxWidth = 720`, owner-picked, a ceiling rather than a width. It is the top of the 640-720 reading column `design/README.md` asks for. The summary's own measure moved to 680 in the same session and deliberately stops short of 720: prose has a measure ceiling near 90 characters a line, a label/value grid does not, so the two numbers differ because the content does. A test pins the card inside the band and pins that it exceeds the floor-derived figure, which is the relation that actually matters now.

**Widening alone would have bought whitespace, not information.** The rows were a stacked eyebrow-over-value column, so extra width just moved the right edge. `InspectorRow` now renders a label/value grid above a `gridFloor` and falls back to the stacked form below it via `ViewThatFits`, so a narrow pane is unchanged and a wide one reads as a spec sheet.

**The footer was the "another world" control.** It was a full-pane `bgRaised` plinth: a filled band running the whole 1230pt to hold one ~140pt button, three times wider than the card above it, which is why it read as a separate surface rather than as this card's footer. It is now the card's width, carries a hairline instead of a fill (`design/README.md` is explicit that resting surfaces get a hairline and no fill), and puts Edit at the card's trailing edge so content-left and action-right bound the card. The capsule and `.mpGhost` were never the problem and are unchanged; the first pass was right about the style and wrong about the surface.

Verified: `swift build` clean, **1879 daemon tests, 0 failures**. The old floor-derivation test was replaced rather than edited, since it pinned exactly the relation being rejected; three tests stand in its place (grows past the floor-derived width, stays inside the design band and above the prose measure, and a source fence that the footer carries no `bgRaised` and aligns trailing).

**Owner-owed, still.** Rebuild (`./scripts/rebuild.sh`) and select Client work on a wide window: the card should fill sensibly with the facts reading as a grid rather than a list, and the Edit button should look like it belongs to the card under it. Then narrow to the detail floor and confirm the rows fall back to the stacked form without squeezing.

## Third pass, 2026-07-30: Edit moves to the top right

Owner, on seeing the shipped footer: "can we move edit button to the top right? it looks lonely bottom left". One correction for the record, since it does not change the answer: the second pass had already moved Edit to the card's *trailing* edge (`dd22cc9`), and the owner had rebuilt past that commit, so the running build showed it bottom-right rather than bottom-left; the "bottom left" recollection is of the screenshot from before that pass. The lonely part was accurate either way, and it was the band, not the side.

Edit now rides the identity row's trailing edge, pushed there by a `Spacer` rather than a frame of its own, and the footer band is deleted outright: the pane is a single `ScrollView` again. This is the second route this task's own spec offered ("give the pane a non-scrolling footer **or** accept content-flow placement"), so it needs no re-argument. Top right beside the name it edits is the mac inspector convention, and the action rides the first row in the pane, so "does not scroll away" survives in practice without a band to enforce it. The workflow name gained `lineLimit(1)` with tail truncation so a long name truncates rather than shoving the button off the card's edge.

The footer fence was replaced rather than edited, since it pinned a footer that no longer exists. The new one asserts no `private var footer` and no `bgRaised` survive, that `editButton` is its own named piece, and that inside the identity row the `Spacer` *precedes* `editButton` (without that ordering the button would sit beside the name instead of at the edge). It strips `///` and `//` comments before scanning, because the code's own history note names the plinth the fence bans, and it was mutation-verified two ways: removing the `Spacer`, and moving `editButton` out of the row. Both turn it red.

Verified: `swift build` clean, **1888 daemon tests, 0 failures** (no count change; one fence replaced another), truth fences green.

**Owner-owed, unchanged:** the eyeball on a wide window, now with Edit at the top right.
