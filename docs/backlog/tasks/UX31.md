# UX31: One name per summarization engine (the label drift, and the two backends with no name at all)

Band origin: filed 2026-07-28 (owner report: the detail header says "Claude (cloud)" while the Re-summarize menu one click away says "Anthropic (cloud)", for the same backend on the same meeting). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

**UX31 (P2, new): every summarization backend is named differently depending on which surface you are looking at, and two of the six are not named anywhere.** The owner reported the Claude/Anthropic pair; a sweep of the label sites found the same drift on the other backends plus a coverage hole that is worse than the drift.

Reported defect, one backend under two names, side by side. `provenanceLabel` renders `anthropic` as "Claude (cloud)" (MeetingDetailView+Header.swift:351) while `reSummarizeMenu` renders the same id as "Anthropic (cloud)" (MeetingDetailView+Header.swift:459). Both live in the same file, both are on screen at once when the `...` menu is open over the header, and they describe the same `api.anthropic.com` call on the same meeting. The owner hit this on `20260727-140126`, whose `run.json` records `"backend": "anthropic"`.

Found defect 1, the drift is not confined to that pair. Each backend is spelled differently per surface, with no site agreeing with all the others:

Found defect 2, two shipped backends have no label on five of seven surfaces, and this is the half that misinforms rather than merely annoys. `claude_cli` and `openai` are selectable in Preferences (PreferencesView+Pipeline.swift:36-37) and both are implemented end to end in the pipeline (`provider_claude_cli.py`, `provider_openai.py`, PROV1). Neither appears in `provenanceLabel`, whose `default` returns nil (MeetingDetailView+Header.swift:354), and the caller drops the whole row on nil (MeetingDetailView+Header.swift:332), so a meeting summarized by OpenAI displays **no engine at all** where every other meeting displays one. Neither appears in the workflow backend picker (WorkflowsView.swift:439-444), so a workflow cannot pin them even though the global setting offers them; nor in `WorkflowInspector.backendLabel`. `ProcessingRequest.progressLabel` falls through to a bare "Summarizing" (State.swift:158), losing the engine distinction that comment says the label exists to carry. `AskView.backendFooter` falls through to string interpolation and renders the raw config id: "Answered via claude_cli" (AskView.swift:161).

Root cause, and the reason this recurs. There is no single home for these strings. Seven independent hardcoded switch tables and option arrays each restate the vocabulary, so adding a backend means remembering six edits nobody is prompted to make, and `claude_cli` plus `openai` demonstrate what happens when that memory fails. This is the same failure mode `daemon/CLAUDE.md` already names for config defaults under the `ConfigDefaults` / ARCH5 rule: a literal at each read site is how two surfaces come to disagree about a value nobody changed. `WorkflowBackend` (Workflow.swift:6-11) is not that home as it stands, since it models only four of the six ids and the sidecar-driven surfaces key off the raw string.

Vocabulary to settle on, owner decision recorded 2026-07-28: name the vendor for API backends, name the tool for the CLI backend.

| Backend id | Name | Where it runs |
|---|---|---|
| `anthropic` | Anthropic | cloud |
| `openai` | OpenAI | cloud |
| `claude_cli` | Claude CLI | cloud (the one exception to the vendor rule: this is the name of the binary it shells and the subscription it rides, not an API path) |
| `apple_intelligence` | Apple Intelligence | on-device |
| `local` | Local MLX | on-device |
| `auto` | Auto | cloud, falls back to local |

Scope. One pure type keyed off the raw backend id (a string, since sidecars carry strings and the enum covers four of six), exposing the registers the surfaces actually need and no more: a bare name for pickers, a qualified "Name (where it runs)" for provenance / menus / inspector, and a present-tense phrase for the busy and Ask lines. Every site above reads it; no site keeps a literal. The `auto` row keeps its longer picker gloss, since "cloud, fall back to local" is behaviour, not a name, and belongs to the picker's explanatory register. Preferences' "Apple (experimental)" loses the parenthetical to the shared name and keeps its experimental warning where that warning already lives (PreferencesView+Pipeline.swift:317-319), rather than encoding a caveat in an identity. The provenance line stops returning nil for a known backend; nil stays only for a genuinely unknown id, which is what that behaviour was for.

Explicitly not: no change to any backend id, config value, or sidecar key (these are display names only, and `summarization.backend` is a written contract with the pipeline); no change to which backends exist or which a workflow may pin (adding `claude_cli` and `openai` to the workflow picker is a labelling consequence, not a new capability, and if pinning them needs pipeline work then the picker entry waits and the task says so); no re-litigation of the NDA/regulated clamp copy (UX29 owns that register); no Python-side rename (the pipeline's user-facing surface is the CLI, out of scope by the de-CLI standing rule).

Acceptance: a fence test asserts every backend id offered in the Preferences picker resolves to a non-empty label in every register, so a seventh backend cannot ship half-named the way these two did; presentation tests pin that the provenance line and the Re-summarize menu render the identical string for `anthropic`, and that a meeting recorded under `openai` renders an engine row rather than dropping it; a test pins that no surface renders a raw config id. Grepping the daemon for the literal strings in the drift table above returns only the new single home. Full daemon suite green, `swift build` clean. Owner eyeball: open a meeting summarized in the cloud and confirm the header and the `...` menu agree on the engine's name.
