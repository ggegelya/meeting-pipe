# REC23: the after-job orphan sweep can merge a recording that is still starting, delete its live intermediates, and publish a few-second stub in place of the meeting

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Review finding MAINTHREAD-4: finder high, verifier plausible and high. Re-checked in code at `01e904a` on 2026-10-25. Not reproduced, and nothing on the owner's personal Mac shows it firing: `events.jsonl` there holds no `orphan_recording_recovered` row at all, and the work laptop's logs were not visible to the review.

**The only guard for the live recording is a UI mirror.** [REC6](../q6-final.md) (shipped 2026-07-12) runs the orphan sweep from `Coordinator.reapStorage`, which runs at launch and from the `onDone` that `PipelineJobDispatcher.route` calls on every successful job, Library regenerates and republishes included. Its exclusion of the recording in progress is `let liveStem = libraryModel.liveRecordingStem`, passed to `OrphanRecordingRecovery.scanOrphanStems(in:excludingStem:)`. That property has one writer, `StatusBarController.setRecording` (`libraryModel?.liveRecordingStem = file.deletingPathExtension().lastPathComponent`), and `MeetingSessionController` calls it only after `try await self.coordinator.audioRecorder.start(...)` returns. The recorder's own `currentFile` is set later still inside `start()`, after the engine is up.

**What is on disk before that.** `MeetingRecorder.start` names the stem (`let stamp = formatter.string(from: Date())`), writes `<stamp>.capturemode`, and `buildMicChain` opens `<stamp>.mic.wav` with `AVAudioFile(forWriting:settings:)`, all before `switch await boundedEngineStart(seconds: MeetingRecorder.engineStartBudgetSeconds, ...)` suspends the main actor. The `.recovery.json` manifest, one of the two markers the scan treats as deliberate, is written by `writeRecoveryManifest` only after `start()` returns. So during the engine start the stem has a fresh `.mic.wav`, a `.capturemode`, no final and no recovery marker, and `liveRecordingStem` does not name it. `scanOrphanStems` lists it: an intermediate with no final, modified inside `maxOrphanAge`.

**How long the window is.** On the owner's personal Mac (built-in mic, 48 kHz), `recorder.log` shows 39 to 68 ms from `mic file opened` to `engine started` across the three starts on 2026-10-13 and 2026-10-16. `engineStartBudgetSeconds` is 8 s, and the bound exists because a Bluetooth headset renegotiating HFP hung `engine.start()` for about 42 s on 2026-06-12, so on a headset the window can be seconds. A job finishing inside it needs no coincidence beyond back-to-back meetings, where meeting N's pipeline completes minutes into meeting N+1, and [END17](./END17.md)'s resume path adds starts that closely follow a stop.

**Why the snapshot turns into loss.** `Coordinator.recoverOrphanedRecordings` hands the snapshotted list to `Task { @MainActor [weak self] in let result = await OrphanRecordingRecovery.recover(stems: stems, in: dir) ... }`, and `recover` walks it sequentially with nothing re-read per stem. Stems are timestamps sorted ascending, so the live stem is always last. If its turn comes while `.mic.wav` is still the bare header (4,096 bytes for these files, as REC17's 2026-09-17 `system.wav` showed), `RecordingPostProcessor.recoverOrphan`'s `fileSize(micURL) > 4096` floor skips it and nothing is lost. If any earlier stem is in the list, that stem's merge runs first (up to the 300 s `mergeCeilingSeconds`), the start finishes meanwhile and the tap writes, and `recoverOrphan` then merges the growing `.mic.wav` and `.system.wav` through `produceFinal`, promotes the result to `<stem>.wav`, and runs `try? FileManager.default.removeItem(at: mic)` and `(at: system)`. `recover` next reads the manifest the start has since written, restores `<stem>.meta.json` from it, runs `cleanupStartMarkers` (removing `.capturemode`, `.offrecord`, `.recordfail.json` and the manifest), and returns the stub as ready, so `jobDispatcher.enqueue` transcribes, summarizes and publishes a few seconds of audio under the live meeting's workflow (or quarantines it, for a redact-opt-in recording). The recorder writes the rest of the meeting into the unlinked inodes. At stop `mergeIntermediates` finds neither path, logs "neither mic nor system has audio data", returns false, and the session posts "Could not finalize ... The raw recording was kept and will be recovered automatically", which is no longer true: the audio is freed when the files close.

**A sibling defect makes the precondition permanent.** An earlier stem in the scan turns a narrow race into a reliable one, and a stem whose re-merge keeps failing stays in every scan for good, because its `.recordfail.json` exempts it from the 24 h cutoff and nothing counts attempts (filed beside this task on 2026-10-25 from the same review: [REC24](./REC24.md) "A failed orphan re-merge is retried after every job forever, and two job completions can merge the same orphan at once over one temp file"). With no earlier stem, loss needs the engine start to complete during the synchronous scan itself, so the start continuation runs ahead of the recover Task and the synchronous `engageMicGate` and `armLifecycleLeaveButton` wiring that follows gives the tap time to write.

**A rarer path of the same class.** When `MeetingRecorder.drainWriters` times out at stop (`writerDrainTimeoutSeconds`, 10 s, REC7), the drain is abandoned and keeps writing (`SerialBufferWriter.drain(timeout:)`: "the drain keeps running on the queue, which strong-captures the file it writes"), a `.recordfail.json` is written, and `setIdle` clears `liveRecordingStem`. The next job's sweep then merges and deletes intermediates a writer still holds open, and whatever the abandoned queue writes afterwards is lost.

**The broken promise** is REC1's and REC6's: intermediates are deleted only after a verified merge of a finished capture, and, in REC6's words, "the currently-recording stem ... is excluded so an in-flight recording is never merged mid-write". Not a regression: the window has existed since REC6 shipped on 2026-07-12, because `boundedEngineStart` (2026-06-12) already put an await between file creation and `setRecording`, so this is filed new rather than as a REC6 reopen. P1 because when it fires the whole meeting is lost and a stub is published in its place; by the REC10 and [REC14](./REC14.md) precedent (data loss on a path reached only after another failure) the owner may re-band to P2, since the wide path needs an earlier orphan already in the scan.

## Scope

1. **The recorder says which stems it owns.** `MeetingRecorder` gains a main-confined `private(set) var ownedStems: Set<String>` (the name is the pickup's; a set because an abandoned drain's stem and the next recording's can coexist). `start()` inserts the stem straight after `let stamp = ...`, before the `.capturemode` write and `buildMicChain`, and removes it on every throwing exit after that point (a `defer` that removes it unless the start succeeded is the simplest shape, since `buildMicChain`'s `fileCreateFailed`, the `tapRefused` branch and both `boundedEngineStart` failure branches all throw). `stop()` removes it only after `mergeIntermediates` returns. When `drainWriters` reports `writerWedged`, the stem stays owned until the abandoned drain finishes: `SerialBufferWriter` gains a `whenDrained(_:)` that enqueues a closure behind everything pending, which hops to main and removes the stem. A disk that never comes back keeps the stem owned until the next launch, whose sweep (nothing owned) recovers it.
2. **The sweep asks the recorder, at scan time and again per stem.** `Coordinator.reapStorage` and `recoverOrphanedRecordings` exclude `audioRecorder.ownedStems` instead of `libraryModel.liveRecordingStem`; `AudioRetentionSweep.sweep(liveStem:)` takes the same source for consistency (harmless at `01e904a`, since retention acts only on a stem with a final and a summary). `OrphanRecordingRecovery.recover(stems:in:)` takes an `isOwned: @MainActor (String) -> Bool` and awaits it on main immediately before each stem's `RecordingPostProcessor.recoverOrphan`, because the snapshot can be minutes old when a stem's turn comes. A skip at that per-stem check emits `coordinator`/`orphan_recovery_skipped_owned` with `stem`, so the field log can say whether the window is ever hit.
3. `libraryModel.liveRecordingStem` keeps its UI role (the row pulse, the toolbar) and stops being read by any storage path. Correct the two comments that say otherwise: `scanOrphanStems`'s "Pass `libraryModel.liveRecordingStem`" and the REC6 paragraph in `reapStorage`.

## Explicitly not

- A freshness rule in the sweep (skip intermediates modified in the last few minutes, like `MeetingStore.liveCaptureFreshnessSec`'s 60 s for a list row). It would also skip REC6's purpose, the after-job recovery of a stop-time merge failure, which is recent by construction. The owner set comes from the one object that knows.
- Moving `setRecording` earlier, or writing the recovery manifest before the engine starts. Either narrows the window without closing it, and an early manifest would mark a stem whose start failed as a deliberate orphan.
- The retry cap, the in-flight guard and the main-thread scan of the same sweep: the sibling task named above. Both edit `recoverOrphanedRecordings` and `recover`, so whichever lands second rebases; this one is P1 and should go first.
- The retention sweep's overlap, the blocking work in `Task.detached`, and killing a timed-out ffmpeg: [CONC5](./CONC5.md) (amended 2026-10-25 from the same review).
- The 2026-10-25 observability audit's O17 (crash-recovery markers written with `try?`, quarantine on an unreadable manifest) touches `recover` and `cleanupStartMarkers` too; a different defect, filed from that audit.
