# UX89: Recording ▸ Output directory is a live free-text path, so a typo re-points new recordings, backups, Ask and digests, and after a restart the Library opens on an empty folder

Band origin: filed 2026-10-24 from the 2026-10-24 audit band ([go-live assessment](../../audits/2026-10-21-go-live-assessment.md) UX-14). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Verified by code reading on 2026-10-24; not exercised live.

**The field writes as you type.** `PreferencesView+Recording`'s "Audio" group renders `TextField("", text: $store.outputDirPath)` in monospace beside **Choose…** and a reveal button. `ConfigStore.outputDirPath` is `@Published` with `didSet { scheduleSave() }`, and `scheduleSave` writes `config.toml` 0.5 s after the last keystroke. A pause mid-edit saves a half-typed path as `[recording] output_dir`.

**Everything that reads the library follows the saved value, except the Library.** `Coordinator.liveOutputDir` reads `configStore.outputDirPath` on every call, so the next recording is written under the new path (a directory that may not exist yet). The pipeline reads `recording.output_dir` from `config.toml` in `digest.py`, `backup.py`, `ask.py`, `mcp_serve.py`, `summarize.py` and `doctor.py`, so a scheduled backup backs up the wrong folder and Ask answers from nothing. The Library window does not move: `Coordinator` builds `LibraryWindowModel(recordingsDir:)` once from the init-time value, with the comment "a live change needs a daemon restart for the library window (rare)", and `MeetingStore.recordingsDir` is a `let`. At the next launch the Library opens on the new path, and every earlier meeting appears to be gone.

**The safe path exists and is hidden.** `LibraryMover` (SEC12) plans a move, names the byte count, refuses while a recording or a pipeline job is in flight (`LibraryMover.inFlightReason`), refuses an occupied or synced destination, and `StorageStatsStore.executeMove` moves first and repoints `outputDirPath` last. Its **Move library…** button is rendered only inside `PreferencesView+Storage.syncGroup`, which shows only when a sync provider is detected. On an unsynced library the only control is the raw text field, which bypasses all of those refusals.

**Same `let` after a confirmed move.** `executeMove` sets `outputDirPath`, but `MeetingStore` keeps watching the old directory, so even the guided move leaves the Library on the moved-away folder until a restart. Not observed in the field; follows from the same init-time snapshot.

## Scope

1. **No free-text path.** Replace the Recording pane's `TextField` with a read-only path label plus two actions: **Move library…** (the existing `LibraryMover` plan and confirmation, now offered whether or not a sync provider is detected) and **Use another folder…** (point at a folder without moving anything, behind a confirmation that says the current library stays where it is and stops showing). Both write `outputDirPath` only after the user confirms. The Storage pane's **Recordings folder** row gets the same two actions instead of reveal only.
2. **The Library follows the root.** On a confirmed change, rebuild the Library's `MeetingStore` (and the `PrepCardStore` built beside it) on the new root, or, if re-rooting the live model is not tractable in this task, the confirmation says the app will relaunch and does so. Say which in the commit body; the init-time comment in `Coordinator` is updated either way.
3. **A missing root is visible.** When `outputDirPath` does not exist at launch, the Library's empty state says "Your recordings folder is not at <path>" with **Choose folder…**, instead of the ordinary first-run empty list.
4. **Docs in the same commit**: README's Recording reference and any GUIDE.md recipe naming the field.

## Explicitly not / out of scope

- Where a new install's library lives by default (outside iCloud-synced folders) and the welcome copy: STOR6. This task changes how an existing path is changed, not its default.
- Moving the `published/` filesystem-sink folder, which `LibraryMover` deliberately leaves alone. Unchanged.
- A config-file hand edit of `output_dir`. Still allowed; item 3 makes its failure visible.
- Preferences regrouping: UX87 decides which pane this row lives in; this task changes the control, wherever it ends up.

## Acceptance

- Tests: the Recording pane no longer binds a `TextField` to `outputDirPath` (a fence in the existing source-reading style, or a view-model test if the row gains one); **Use another folder…** writes the path only after confirm; **Move library…** from the Recording pane uses `LibraryMover.plan` and is refused with the in-flight reason while a recording is active.
- Tests: after a confirmed change the Library's store reports the new root (or the relaunch path is taken); a missing root yields the named empty state, not the generic one.
- `cd daemon && swift build` and `swift test` green, N new tests in the commit body; `bash scripts/ci-local.sh fences` green.
- Owner check: change the folder from the Recording pane to a fresh empty folder, see the confirmation, accept, and the Library shows the empty folder at once; change it back and every meeting is there, with no restart.

## Amendment 2026-11-13 (audit band)

Source: [independent audit](../../audits/2026-11-12-independent-audit.md) F058 (medium, confirmed). Re-verified against `main` at `3a2da4fc` on 2026-11-14 by code reading; not observed in the field. The audit itself notes this task already names the stale root after `executeMove`; what follows is the consequence its text does not carry.

**Reopening the Library after a move wipes the search index and the duration cache.** `Coordinator` builds three things from one init-time snapshot under the comment "a live change needs a daemon restart for the library window (rare)": `PrepCardStore(recordingsDir: recordingsDir)`, `LibraryWindowModel(recordingsDir: recordingsDir, durationCacheURL: MeetingDurationCache.defaultURL())`, and `SearchIndexer(store: libraryModel.meetingStore)`. `StorageStatsStore.executeMove` runs `LibraryMover.execute(plan)` (a `moveItem` of the whole folder) and then only assigns `configStore.outputDirPath`; no relaunch is requested. The chain on the next Library open:

- `MeetingStore.start()` calls `attachWatcher()`, whose first act is `FileManager.default.createDirectory(at: recordingsDir, withIntermediateDirectories: true)`. That recreates the moved-away folder, empty, in the place the owner just left, which after a move prompted by SEC12's sync warning is inside the synced folder.
- The listing of that empty folder succeeds, so `SearchIndexer.reconcile`'s guard (`SearchIndexReconciler.mayApply`, which skips only when "the library scan listed nothing and could not read the recordings folder") lets the reconciler delete every indexed stem from `MeetingPipe/search/index.sqlite`.
- `MeetingStore`'s scan does `durationCache.prune(keeping: Set(byStem.keys))` then `persistDurationCacheIfChanged()`, writing an empty cache to the shared `MeetingDurationCache.defaultURL()`.

The Library shows no meetings, and new recordings land in the new root but stay invisible until a relaunch. Correction at filing: nothing is lost from disk. The index and the cache live outside the library and both rebuild on the next launch against the new root, at the cost of a full reindex and a duration re-derivation for every meeting; the lasting artefact is the recreated empty folder in the old location.

**Scope additions (F058):** item 2 covers all three snapshots, not only `MeetingStore` and `PrepCardStore`: the `SearchIndexer` re-roots with the store (or the relaunch path is taken). If re-rooting is chosen, the old store is stopped before the new one starts, so no `attachWatcher` ever runs against the moved-away path; if the relaunch is chosen, it is the move's last step.

**Acceptance additions (F058):**

- A test over a headless model with a temp library: move it with `executeMove`, then stop and start the Library's store; the old folder does not exist afterwards, the store lists the moved meetings (or the relaunch path was taken), the `SearchIndexer` still holds every stem, and the duration cache file still has every stem.
- `attachWatcher` creating a missing root is fine for a first run but not for a root the app moved away from: a test that a store whose root was the source of a completed move never recreates it.
