# PERF13: smaller main-thread costs in the Library rails, the Guide and Diagnostics windows, and the logger

Band origin: filed 2026-10-23 from the traces and code audit run for the owner's "the app feels slow" report. Each item is small; together they are the remaining main-thread work after [PERF9](./PERF9.md), [PERF10](./PERF10.md) and [PERF12](./PERF12.md). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Items

Measured in the 2026-10-23 trace that switched Library rails through `meetingpipe://library?scope=...` (Library already open):

1. **People rail derivation on main.** `PeopleView.reaggregate` reads the disk in `Task.detached`, then runs `rederive()` inside `await MainActor.run { ... }`, and that calls `PeopleRail.derive(roster:meetings:commitments:)` on main. Measured: 146 samples. Fix: derive in the detached task and hand only the result to main. `rederive()` from a clustering landing can stay on main if it stays cheap, or move off main too.
2. **Facts "due" labels computed in row `body`.** `FactsView` calls `cluster.agingLabel(now: now)` inside the row's body, and `PeopleView` calls `commitment.agingLabel(now: Date())` (`Facts.swift`, `func agingLabel(now:)`). Measured: 81 samples under `OpenActionRow.body`. Fix: compute labels once per derivation, keyed on the day, so a midnight rollover still refreshes them.
3. **Logger file I/O on the caller's thread.** `Log.appendData(_:to:)` runs `rotateIfNeeded`, a `fileExists`, and then an open, seek, write and close of a `FileHandle` for every `Log.event` or `writeLine`, usually on main. Measured: 47 samples for a handful of events. Fix: a serial logging queue with long-lived handles, keeping rotation semantics (PERF7) and crash safety. State the crash-safety story before deferring any write: an unflushed tail on crash must be bounded and documented.

Confirmed by code reading, not measured:

4. **Guide window re-parses the document while scrolling.** `GuideView` renders a non-lazy `VStack` over every block and calls `AttributedString(markdown:options:)` in `inline(_:)` during body. Its scroll-position preference updates `@State`, so each section crossing re-parses the whole document. Fix: parse once in `load()`, use a `LazyVStack`, and isolate the rail's hover state in a child view.
5. **Diagnostics window loads logs on main.** `DiagnosticsView.reload()` calls `DiagnosticsLog.load(...)` synchronously, which reads up to four generations of `events.jsonl` and `pipeline_events.jsonl` (about 5 MiB each) and parses them line by line on every appear and filter change. Fix: load in a detached task and assign on main, with a loading state.
6. **`MeetingDiscoveryWatcher.sampleMicBusy` on a main `Timer`** (every 3 s, or 12 s idle). Measured cheap: 5 to 9 samples per minute. Listed so it is not rediscovered; move it only if it is touched for another reason.

## Amended 2026-10-24 (audit band)

The [architecture review](../../audits/2026-10-24-architecture-review.md) (M8) adds a correctness half to item 3, verified in `daemon/Sources/MeetingPipe/Logger.swift` on 2026-10-24: the logger is not thread-safe, not only slow. `Log.appendData(_:to:)` has no lock and no queue. It calls `rotateIfNeeded`, then, when the file is missing, `FileManager.default.createFile(atPath:contents:attributes:)`, which replaces whatever is there; otherwise it opens `FileHandle(forWritingTo:)` (no `O_APPEND`), calls `seekToEnd()`, and writes. About 385 `Log.event` and `Log.writeLine` call sites reach it from main, the audio writer queues, GCD workers and pipe-reader handlers. So two lines written at the same moment can seek to the same offset and the second overwrites the first in `events.jsonl`; two writers can both see a missing file after a rotation and one `createFile` discards the other's line; and two threads can both pass `rotateIfNeeded`'s size check and shift generations twice, dropping a generation early. `PipelineLauncher` has the same shape for `pipeline.log`: each `mp` spawn opens a long-lived `FileHandle`, seeks to the end once, and writes stdout chunks at that handle's own offset, so two concurrent spawns overwrite each other, and a rotation while a handle is open leaves that spawn writing into the renamed generation. The Python side is not affected: `mp.events` opens `pipeline_events.jsonl` with `path.open("a")`, which is `O_APPEND`.

Item 3's fix already proposes one serial logging queue; with this amendment it must also guarantee ordering and no loss:

- Every append, rotation and first-create for a log family goes through that one serial queue, on a descriptor opened with `O_WRONLY | O_APPEND | O_CREAT` and mode 0600, so the kernel places each write at the end even if a second process ever appends.
- `pipeline.log` either gets a per-spawn file (`pipeline.<stem>.<pid>.log` or similar, which also makes a run's output findable) or routes its chunks through the same queue. The pickup picks one and says why in the commit body.

Added acceptance for item 3:

- A test that 8 concurrent writers each appending 1,000 distinct `Log.event` lines produce exactly 8,000 parseable JSONL lines across the base file and its generations, none lost or interleaved mid-line.
- A test that concurrent writers crossing the rotation size rotate once, not twice (generation count and contents checked).
- A test that two simulated `mp` output streams written concurrently to the pipeline log lose no bytes, under whichever `pipeline.log` design is chosen.

## Amended 2026-10-25 (observability audit band)

The [observability audit](../../audits/2026-10-25-observability-audit.md) (finders LG-4, LG-5, SW-17) found the 2026-10-24 amendment's last sentence true for `pipeline_events.jsonl` and false for `pipeline.log`, and the races reached in the owner's real logs. Verified in code on 2026-10-25.

**`pipeline.log` has two writers on every run, not only under concurrent spawns.** `orchestrate._configure_logging` adds a `StreamHandler(sys.stderr)` and a `logging.FileHandler(log_file)` on the same `pipeline.log`, and `PipelineLauncher.runMP` opens its own `FileHandle(forWritingTo: logURL)`, calls `seekToEnd()` once, and writes every stdout and stderr chunk at that handle's offset. So every `run-all` line reaches the file twice (Python's own append, then the daemon's copy of stderr), and because the daemon's handle is not `O_APPEND`, its writes land at a stale offset over whatever Python appended since. Measured on this Mac: 5 of the 8 `run-all:` runs in `pipeline.log` end in a torn fragment line (for example `ing sentinel written: .../raw/20261016-095827.apple_pending.json`), and the 2026-10-16 12:46:34 `MissingSecretError` traceback appears twice. Other subcommands (`summarize`, `merge-meetings`, `ask`) only `basicConfig` to stderr and have the daemon as their single writer. Separately, the `emit_progress` docstring says the progress sentinel is "stripped from the daemon's view of `pipeline.log`", but `runMP`'s stdout handler writes the chunk before scanning it for the sentinel.

**The `events.jsonl` race was reached, and every reader hides it.** `events.jsonl` line 651 is the tail of a row (`n ","ts":"2026-10-16T09:46:28.265Z"}`), written in the same millisecond as `lifecycle` / `idle` while a recording entered stopping; it is 1 unparseable line of 1,148, and it sits exactly where OBS5's stop-trigger question needed a row. `mp logs` (`logs_cmd`, "Skip rather than abort") and `mp analyze-detection` skip a `json.JSONDecodeError` silently, `DiagnosticsLog` drops a line whose `JSONSerialization.jsonObject` fails, and `jq` aborts on it. A lost row is indistinguishable from an event that never fired.

**The logger drops whole events and lines silently.** `Log.event` returns without writing when `JSONSerialization.isValidJSONObject(dict)` is false, which is the case for `Double.nan`, `Double.infinity`, `URL`, `Date` and `UUID` values (measured with a Swift snippet). `appendData` returns on `guard let handle = try? FileHandle(forWritingTo: url)`, and `runMP`'s `logHandle` is `try?` too, so a failed open loses the whole run's output except the 4 KB stderr tail. No current call site passes a non-JSON value (spot grep); latent. CONVENTIONS.md "Non-serializable attributes" documents the drop as intended.

Item 3 additionally must:

- **Give `pipeline.log` one owner per file.** Either Python skips its `FileHandler` when the daemon spawned it (an `MP_RUN_ID` from OBS4, or a dedicated flag) and the daemon's copy, through the serial queue on an `O_APPEND` descriptor, is the only writer; or the daemon writes a per-spawn `pipeline.<stem>.<pid>.log` and stops appending stderr to the shared file. The pickup picks one and says why in the commit body; a hand-run `mp run-all` must still get a log. Either way the sentinel is stripped or the docstring is corrected.
- **Coerce instead of dropping.** A non-JSON attribute value is written as its string form (and `NaN` and infinity as `null` with a sibling `<key>_invalid: true`), so the event survives, and CONVENTIONS.md's "Non-serializable attributes" section is rewritten to match Python's `default=str` in the same commit.
- **Report a failed append.** When the descriptor cannot be opened or written, fall back to one os.Logger `.error` per log family per launch with the path and errno `privacy: .public` (OBS1's helper cannot be used here, because it writes through this same path).
- **Count what readers skip.** `mp logs` and `mp analyze-detection` print `N unparseable lines skipped` to stderr when N > 0, and `DiagnosticsView` shows the count, so a torn log is visible.

Added acceptance:

- A test that one spawned `run-all` writing through both Python logging and stderr leaves each line exactly once in its log, with no torn fragment, under the chosen design.
- `Log.event` with a `URL`, a `UUID` and `Double.nan` attribute writes one parseable row with string and null values.
- A fixture log with one torn line makes `mp logs` and `mp analyze-detection` report 1 skipped line, and `DiagnosticsLog` return a skipped count of 1.

### Logger race observed in the live log, three fix corrections, Python as the second pipeline.log writer, and a cost model and fix shape for the Diagnostics reload

The 2026-10-25 performance and long-term-stability review (eight subsystem finders over `01e904a`, every finding adversarially re-verified) confirmed items 3 and 5 as filed: findings DETECTION-9, MAINTHREAD-10, PERSISTENCE-3 and PYTHON-15 on the logger, and MAINTHREAD-7, PERSISTENCE-4, SUBPROCESS-9 and UI-3 on Diagnostics. This section adds only what the spec lacks: the race caught in the owner's live log, three corrections to the proposed fix, the second `pipeline.log` writer, and a cost model and fix shape for item 5. Everything below was re-checked against `main` at `01e904a` and the owner's `~/Library/Logs/MeetingPipe` on 2026-10-25.

#### Item 3: the overwrite race is in the live log

The live `events.jsonl` (1,148 lines, 2026-10-12 to 2026-10-24) has exactly one unparseable row, and it is this race at a recording stop. At `2026-10-16T09:46:28.257Z` the coordinator logged `state_change` from `recording` to `stopping`; 8 ms later two rows were emitted in the same millisecond. The file holds `{"action":"idle","category":"lifecycle","ts":"2026-10-16T09:46:28.265Z"}` followed by the orphaned tail `n ","ts":"2026-10-16T09:46:28.265Z"}`: both writers seeked to the same end, the longer row landed first, and the 73-byte `idle` row overwrote its head. One stop-cascade event is lost, and `DiagnosticsLog.parseLine` and `mp logs` skip the remnant without a word. It happened where the 2026-10-24 amendment predicted, at the moment several sources emit at once: main, `MicGate`'s publish queue, the HAL bus queue, `AXLeaveButtonSignal`'s queue, `CallTeardownWatcher`'s read queue and discovery's scan queue all reach `Log.event` (several through `LogEventAdapter`) with no lock between them.

#### Three corrections to the proposed fix

**The other process writing `events.jsonl` is the doctor CLI, not Python.** One verifier said `mp.events` also appends to `events.jsonl`; it does not (`events.emit` writes only `pipeline_events.jsonl`, through `path.open("a")`). The second process is this binary's own `MeetingPipe doctor` (`DoctorCommand` emits `Log.event(category: "doctor", action: "probe", ...)` per probe), which `scripts/ci-local.sh` and `scripts/test-app-relocation.sh` run while the daemon is up; 285 of the 1,148 live rows are doctor probes from 19 runs on 2026-10-24. So `O_APPEND` is load-bearing across processes, and a long-lived descriptor would also have to notice a rotation done by that other process (compare `fstat` of the open descriptor with `stat` of the path before each write, reopen on mismatch) or it keeps appending into `events.1.jsonl`. The simpler shape: open per write with `open(2)` and `O_WRONLY | O_APPEND | O_CREAT`, mode 0600, which removes the overwrite and first-create races with no descriptor to track, plus one in-process lock (or the serial queue) around `rotateIfNeeded` and the append, which removes the double rotation.

**Do not freeze `logsDir`.** Several findings propose resolving `Log.logsDir` once. Eleven test files (`LoggerTests`, `GuardedTapInstallTests`, `UncaughtExceptionLoggerTests`, `StopStallWatchdogTests`, `MeetingSourceScannerTests`, `MeetingLibraryServiceTests` and five more) call `setenv("MEETINGPIPE_LOGS_DIR", ...)` mid-process and rely on per-call resolution, so a `static let` would break them. The per-call cost is still worth removing: today every line runs `createDirectory` inside the `logsDir` getter, builds `ProcessInfo.processInfo.environment` up to three times (`resolveLogsDir`, `isRunningUnderTests`, `maxLogBytes`), and in production, where no XCTest variable is set, calls `NSClassFromString("XCTestCase")` every time. Read the two variables with `getenv`, memoize `isRunningUnderTests` (whether XCTest is loaded cannot change within a process), and create each resolved directory once.

**Name the synchronous callers before deferring anything.** The correctness half needs no queue (per-write `O_APPEND` plus the lock). Whether to also move the work off the caller's thread is the pickup's call: item 3 measured 47 samples for a handful of events on 2026-10-23, and the review's verifiers put the per-line cost at tens of microseconds at about 1 Hz. If writes do go async, `UncaughtExceptionLogger.record` calls `Log.writeLine` first precisely because, in its own words, "it is unbuffered and lands even if the event write does not", and `AppDelegate.flushAndExit` (SIGTERM and quit) is the other last chance; both need a synchronous drain, and so does every test that reads a log right after emitting.

#### Item 3: `pipeline.log` has a second writer, Python itself

The 2026-10-24 amendment covers concurrent spawns; it misses that each spawn already has two writers. `orchestrate._configure_logging` adds a `StreamHandler` on stderr and a `FileHandler` on the same `pipeline.log` (`O_APPEND`), and `PipelineLauncher.runMP` copies that stderr into `pipeline.log` through `logHandle`, a `FileHandle(forWritingTo:)` positioned once with `seekToEnd()` at spawn. While both streams carry the same bytes in the same order, the daemon's positional writes land on Python's identical bytes and a record appears once; when the daemon's copy lands first, Python's append writes it again after it. The live file shows it: the `2026-10-16 12:46:34,784 ERROR mp.run_all: run-all failed: $ANTHROPIC_API_KEY is not set` record and its whole traceback appear twice back to back, while `orchestrate.main` logs it once (`log.exception("run-all failed: %s", e)`), so the record a postmortem reads first is the one that doubled. `_configure_logging` also calls `events.rotate_if_needed(log_file)` after the daemon opened its handle, so a Python-side rotation can rename the file under it. Fix: the daemon sets one environment flag on every `mp` spawn and `_configure_logging` skips its `FileHandler` when the flag is present, since the daemon already captures stderr; a terminal run keeps the handler, the only file sink it has. This composes with either `pipeline.log` design the 2026-10-24 amendment offers. [T9](./T9.md) edits the same function (its directory), and review finding SUBPROCESS-12 ([CONC7](./CONC7.md)), filed from the same review's subprocess findings, edits the same `logHandle` (`runMP`'s termination handler can close it before the readability handlers have drained); whichever lands second rebases.

#### Item 5: what a reload costs

`DiagnosticsLog.load` reads every generation of both families whole (`String(contentsOf:)`), and for every line runs `JSONSerialization`, `formatDetail` (filter, sort, map and join over every key) and up to two `ISO8601DateFormatter` parses (`isoDate`) before `filterAndSort` applies since, category, action and the `displayLimit` of 2000, so a 15-minute window costs the same as All. `DiagnosticsView.reload` runs it on main from `.onAppear`, both `.onChange` handlers, `.onSubmit` and the Reload button. Each family self-bounds at four 5 MiB files (PERF7), about 40 MiB across both; PERF7 recorded `events.jsonl` at 63 MB / 338k lines before rotation existed, so the cap holds roughly 200k lines, which the verifiers put at several seconds of main per interaction. It is latent today: on 2026-10-25 `events.jsonl` is 175 KB / 1,148 lines and `pipeline_events.jsonl` 4.5 KB, with no rotated generations. Opened during a recording once the logs are at the cap, the stall holds the HUD's Stop and the global hotkeys for its length. `displayLimit`'s doc comment ("Cap the rendered set so a multi-megabyte log cannot stall the window") is false, since the cap applies after the full parse, and UX20's ship note in [q6-final.md](../q6-final.md) repeats the claim; correct the comment in the same change.

Fix shape for item 5, beyond "load in a detached task":

- A request token: `reload` bumps a generation number, runs `load` off main, and assigns on main only if the token is still current. Cancellation alone does not stop a stale result overwriting a newer one.
- Decide before building: read `ts`, `category` and `action` first, reject, and build `detail` only for rows that survive (or only for the at most 2000 returned). A raw-substring test such as `"category":"micgate"` is fine as a cheap reject ahead of the parse, with the JSON parse kept as the authority.
- Early exit for `since`: `Log.logGenerations` returns oldest first and lines ascend within a file, so walk generations newest first and stop at the first file wholly older than `since`. `pipeline_events.jsonl` interleaves in time with `events.jsonl`, so keep the final sort over the bounded set. For All, read a bounded tail per family instead of every line.

#### Added acceptance

- `LoggerTests`: a child process appending with `O_APPEND` (a `/bin/sh` loop) concurrent with in-process `Log.event` calls leaves every line from both intact; a `MEETINGPIPE_LOGS_DIR` changed with `setenv` between two `Log.event` calls sends each line to its own directory; if a long-lived descriptor is kept, a rename of `events.jsonl` by another process sends the next `Log.event` to a fresh `events.jsonl`.
- If appends go async: `UncaughtExceptionLogger.record`'s line is on disk when `record` returns, and the drain `flushAndExit` calls leaves nothing queued.
- pytest: with the daemon's spawn flag set, `_configure_logging()` (run in a subprocess, as T9's test runs it) adds no `FileHandler`; without the flag it adds one. Swift: a `runMP` test whose fake `mp` writes one logging-formatted record to stderr finds it exactly once in `pipeline.log`.
- `DiagnosticsLogTests`: over a fixture whose rotated generations lie wholly before `since`, `load` opens only the base file (an injected reader records the URLs); with a category that matches none of 10,000 fixture rows, `formatDetail` runs zero times (an injected formatter counts); a view-model test where the older of two overlapping reloads finishes last keeps the newer result; the injected loader asserts it is not on main.
- Evidence (confirms, does not gate): a scan of the live `events.jsonl` over a week with at least one recorded call finds no unparseable row.

Proposal for the owner, not a re-band: item 3's correctness half now has an observed lost row and touches no UI, so it could be split into its own task or picked first rather than wait on the rail, Guide and Diagnostics items.

### Guide re-parse: the rail hover trigger, and LazyVStack made optional

The 2026-10-25 performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified) confirms item 4 in its finding UI-15 (verified low) and adds the trigger it missed and a correction to its fix. Re-checked against the tree on 2026-10-25.

**The rail hover is a trigger, not only scrolling.** `GuideView` holds `@State private var hovered: Int?` beside `current` and `jumpTarget` on the one struct whose body builds both the rail and the document. Each rail row's `.onHover { inside in if inside { hovered = section.blockIndex } ... }` therefore re-evaluates the whole body, and the document is a non-lazy `VStack` over `ForEach(Array(blocks.enumerated()), id: \.offset)` in which every paragraph, bullet, numbered item and table cell calls `inline(_:)`, which is `try? AttributedString(markdown: s, options: opts)`. `docs/GUIDE.md` is 56,931 bytes and 313 non-empty lines on 2026-10-25 (62 headings in the rail, 39 list items, 37 table rows), so one sweep of the pointer down the rail re-parses the whole document once per row it crosses. Scrolling is cheaper than item 4 implies: `updateCurrent(from:)` already skips an unchanged `current` (`if resolved != current { current = resolved }`), so a scroll costs one re-parse per section crossing, not per frame.

**Correction to item 4's fix: `LazyVStack` is optional.** The rail's mark comes from `headingProbe(at:)` reporting every heading's offset through `GuideHeadingOffsets` into `GuideDocument.currentSection(offsets:sections:)`, and the rail's jump is `proxy.scrollTo(target, anchor: .top)`. In a `LazyVStack`, headings that are not realized report no offset, so the mark would be decided from a partial picture. The required fix is the other two halves: parse inline markdown once in `load()` (into the block model, or a parallel array `GuideDocument` builds), and move `hovered` into a rail child view so a hover cannot invalidate the document. `current` and `jumpTarget` stay on `GuideView`, as its comment requires ("Held here rather than in the rail so the two columns share one reader"); with pre-parsed strings a `current` change is cheap. Adopt `LazyVStack` only together with a test that the mark still follows scrolling.

**Comments items 3 and 5 must correct.** The same review's comment-drift list (handed to [HYG10](./HYG10.md)) names two comments whose behaviour this task changes, so this task's commits correct them: `DiagnosticsLog`'s "Cap the rendered set so a multi-megabyte log cannot stall the window" (item 5: the cap is applied after every generation has been read and parsed on main), and `Logger.swift`'s rotation comment ("a writer that loses a rotation race just appends to a fresh file", item 3 and its two amendments). The archived PERF7 entry in `q6-final.md` that repeats the second claim is a record and stays as written.

Added acceptance for item 4:

- A `GuideDocumentTests` case that every paragraph, bullet and table-cell block carries its parsed `AttributedString` after `GuideDocument.parse`, and a source fence that `AttributedString(markdown` no longer appears in `GuideView.swift`.
- If `LazyVStack` is adopted, a test that `GuideDocument.currentSection` still yields the expected section from the offsets a partially realized stack reports.
