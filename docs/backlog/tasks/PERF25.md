# PERF25: Smaller pipeline costs: every summarize reads every earlier meeting's sidecar to find one, and a local run reloads the model between speaker cleanup and summarize or after any request longer than five minutes

Band origin: filed 2026-10-25 from the performance review (eight subsystem finders over HEAD 01e904a, every finding adversarially re-verified). Each item is small; this is the [PERF13](./PERF13.md) shape, one task for the low-severity remainder of the review's Python area. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Items

Re-checked against `main` on 2026-10-25.

1. **The prior-meeting scan reads the whole library.** Review finding PYTHON-10 (low, confirmed). `summarize._prior_meeting_context` (AI6) runs inside every `summarize()`, so on every run-all and every Library re-summarize: `for summary_json in out_dir.glob("*.summary.json")`, it skips stems at or after the current one and calls `read_meta(summary_json).get("workflow_id")` on every earlier one, keeping the largest matching stem. That is one `<stem>.meta.json` read per earlier summarized meeting to find a single one; [PERF9](./PERF9.md) counted about 434 meetings on 2026-10-23. Sub-second on a local disk, but the owner's library sits in iCloud-synced `~/Documents` ([STOR6](./STOR6.md) found six files already evicted on 2026-10-24), and a read of an evicted file blocks on a download. Fix: sort the candidate stems below the current one newest-first and stop at the first workflow match. That is the same answer (the newest earlier stem in that workflow) in usually 1 to 10 reads. `read_meta`'s object check stays [PIPE29](./PIPE29.md)'s.
2. **Speaker cleanup and summarize each load the model.** Review finding PYTHON-14 (low, confirmed), first half. With `diarize_cleanup = true`, an effective backend of `local` (which every NDA or regulated run resolves to) and no warm server, `orchestrate.run_all` calls `cleanup_transcript(t["json"], cfg=cfg)`, which builds `providers._local_cleanup`'s own `LocalSummaryClient` and closes it in its `finally` (`if owns_client: ... close()`), and `close()` kills the server it spawned (`_terminate_proc`). Seconds later `summarize(t["md"], cfg=cfg, backend=backend)` builds a second client through `_select_backend`, whose `_ensure_running` finds no server and spawns one, reloading the weights (4.3 GB for the 7B, about 8.7 GB for the 14B; [engine-comparison.md](../../engine-comparison.md) counts a fresh load inside its per-meeting latency). Fix: when the run's resolved backend is `local`, `run_all` builds one client through `providers._local_summary(cfg)` (or [PIPE32](./PIPE32.md)'s factory once it exists), passes it to `cleanup_transcript(..., client=LocalCleanupClient(shared, max_tokens=...))` and to `summarize(..., client=shared)`, and closes it once. Both callees already leave an injected client open (`owns_client = client is None` in `cleanup_transcript`, and "Only a client summarize() built itself is closed" in `summarize`).
3. **The idle timer kills the server after a long request.** PYTHON-14, second half. `LocalSummaryClient._reset_idle_timer` runs only when a request or a window starts, and `_on_idle_timeout` is `with self._lock: self._terminate_proc()`. A request longer than `DEFAULT_IDLE_TIMEOUT_SEC = 300.0` (a 14B single pass can run to its 520 s read timeout) fires the timer mid-call; the callback waits on the lock and kills the server the moment the call returns, and the next reset's `Timer.cancel()` is a no-op once the callback is already waiting. A LANG1 repair or the next cleanup window then respawns and reloads. Fix: stamp a monotonic `_last_activity` when each request completes, and have `_on_idle_timeout` return and re-arm under the lock when activity is newer than the timeout.

Revisit only if a stall on a dataless sidecar is observed there. - Server ownership. [LOCAL21](./LOCAL21.md) makes the daemon the only owner and deletes the Python idle timer, after which item 3 is void and item 2 shrinks to not closing a server the client does not own. Check at pickup and drop whatever has become dead code.
- iCloud dataless handling ([STOR6](./STOR6.md)) and unreadable sidecars ([PIPE29](./PIPE29.md), [PIPE35](./PIPE35.md)).
