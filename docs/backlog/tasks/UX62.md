# UX62: the Republish cue and the open-published affordance are blind to the filesystem sink, which is the default workflow's only sink

Filed 2026-08-03 by the audit band. Proposed high, downgraded to medium by an independent skeptic on the grounds that the capability survives and only the nudge dies.

## What is wrong

`MeetingStore.needsRepublish` decides "this meeting changed since it was published" by looking only for `.notion.json` and `.obsidian.json` sidecars, so a meeting published to the filesystem or LAN sink returns false forever.

- `daemon/Sources/MeetingPipe/MeetingStore.swift:688` is `return lc.hasSuffix(".notion.json") || lc.hasSuffix(".obsidian.json")`, the entire set of sidecars that count as evidence of a publish.
- `daemon/Sources/MeetingPipe/MeetingStore.swift:690` is `guard !publishURLs.isEmpty else { return false }`, which makes a filesystem-only publish indistinguishable from never published.
- `daemon/Sources/MeetingPipe/MeetingRow.swift:279` is the sole consumer of the flag, so the row's inline Republish capsule dies with it.
- `daemon/CLAUDE.md:30` forbids exactly this: "Don't read a per-sink sidecar (`<stem>.notion.json`) to learn whether a run published ... Read `<stem>.publish.json` via `PublishResult.load` (PIPE1)."

The correct signal is already on disk one file away. `20260803-103042.publish.json` carries `"page_url": "file:///Users/.../published/20260803-103042.summary.md"` under `sinks.filesystem`.

Scale, measured on the owner's library 2026-08-03: the default workflow is `Personal` (`is_default = true`, single `type = 'filesystem'` sink), holding 117 of 190 tagged meetings. On disk, **107 of 245 stems** have a `.filesystem.json` and no `.notion.json`, and **13 of the last 15 meetings** are in that blind class. Every NDA meeting is too, since NDA mode force-selects filesystem-only sinks.

`daemon/Sources/MeetingPipe/MeetingDetailView+Header.swift:440` and `:446` are the only open-the-published-note affordances, branching on Notion and Obsidian, so a filesystem publish also has no open action despite `page_url` being a `file://` URL `NSWorkspace.open` handles directly.

## What the skeptic established, recorded

This is a missing nudge, not a lost capability. Republish stays unconditionally available in the row context menu (`MeetingRow.swift:462`), the detail `...` menu (`MeetingDetailView+Header.swift:316`) and the batch pane (`BatchActionsPane.swift:269`). So the owner can always republish; they are just never told they should.

## Scope

Compute the last-publish timestamp from `<stem>.publish.json` via `PublishResult.load` instead of globbing per-sink sidecars, so every sink that ran counts, and delete the two-sidecar filter.

In the same file, give the detail header an open affordance for a filesystem or LAN publish off `publish.json`'s `page_url`.

Reuse whatever pure sink-naming helper UX49 lands, since UX49 is fixing the same rule for the done notification and this is that rule applied to the header and the staleness flag. PIPE14 is the same root cause on the state field rather than the timestamp; whichever lands first should leave the helper the other reuses.

## Acceptance

Suite green with new tests. A meeting published only to the filesystem, whose summary is then edited, shows the Republish capsule. The detail header offers an open action for it. A test pins `needsRepublish` over a `publish.json` carrying each sink type.
