# STOR7: deleting a meeting trashes its `raw/` files but leaves its published copies, its corrections, its search vectors and its voice samples behind, and the confirm says "every file"

Band origin: filed 2026-10-24 from the 2026-10-24 audit band ([go-live assessment](../../audits/2026-10-21-go-live-assessment.md) PP-10). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

Verified in code on 2026-10-24. Every delete path (the detail header's Delete…, the list's context menu, `BatchActionsPane`, the batch trash in `MeetingLibraryService`) ends in `MeetingLibraryService.softDeleteMeeting(stem:)`. It trashes every entry in the library directory whose `MeetingStore.stem(of:)` matches, then the kept original at `originalsDir()/<stem>.wav` (ADR 0016), removes the waveform peaks cache, and emits `meeting_deleted` with `files_count` and `original_trashed`. The confirm, `LibraryDialogs.confirmSoftDelete`, tells the user: "Every file for this meeting (audio, transcript, summary, sidecars) goes to the Trash."

What a meeting leaves behind after that, by location:

- **Published copies.** The filesystem sink writes `<output_dir>/<stem>.summary.md` and `<stem>.actions.json` (default `~/Documents/Meetings/published`), the Obsidian sink writes `<vault>/<folder>/<stem>.md`, the LAN sink writes to a mounted share, and Notion holds a page. Their locations are recorded only in the per-meeting sidecars (`<stem>.filesystem.json` carries `summary_path` and `actions_path`; `<stem>.obsidian.json` carries `note_path`; `<stem>.notion.json` carries the page id). `softDeleteMeeting` trashes those sidecars along with everything else, so the only pointers to the published copies go to the Trash and the copies themselves stay, now unfindable from the app. There is no `mp` command that archives a Notion page (`grep -rn -i "unpublish\|archived" pipeline/src` finds none).
- **The corrections corpus.** `CorrectionStore` writes `~/Library/Application Support/MeetingPipe/corrections/<stem>.json`, outside the library, and nothing deletes it. It is training data by design (`SummaryStaleness` doc comment), and `mp backup` archives it.
- **The semantic index.** `mp.embed_index` keeps chunk text and vectors under `~/Library/Caches/meeting-pipe/ai2-index`. `plan_refresh` drops a removed stem only on the next refresh, so a deleted meeting's text stays on disk and answerable by `mp ask` until something refreshes the index. The keyword index (`SearchIndexReconciler`) does drop it on its next reconcile.
- **Voice samples.** `mp.roster` stores up to 12 sample embeddings per person with no record of which meeting each came from, so a deleted meeting's samples cannot be found, let alone removed.
- **Digests and backups.** A weekly digest under `digests/` quotes the meeting; a backup archive contains it. Neither can be edited per meeting, and neither should be silently.

## Scope

1. **One enumerator of a meeting's footprint**, `MeetingFootprint.locate(stem:)` (Swift, beside `softDeleteMeeting`), returning the raw files, the kept original, the waveform cache, the corrections file, and the published copies read from the sink sidecars **before** they are trashed. Pure over an injected file system, so it is testable without a library.
2. **Delete what is local and derived**, in `softDeleteMeeting`: trash the corrections file and the local published copies (filesystem sink files, the Obsidian note) along with the raw files, and kick an index refresh (or a targeted `mp` call that drops the stem's rows) so `mp ask` stops answering from it. Add the counts to `meeting_deleted` (`corrections_trashed`, `published_trashed`, `index_pruned`).
3. **Ask about what is off the machine.** When a `.notion.json` or `.lan.json` exists, the confirm gains a checkbox, off by default, "Also remove the published Notion page / network copy". Notion archiving goes through a new `mp unpublish <stem> --sink notion` (the daemon does not call Notion; ARCH11 and HYG10 own that rule), which sets the page to archived and is idempotent on a page already gone (PIPE23's 404 handling, if it has landed). The LAN copy is a file delete on the mounted share, skipped with a notice if the share is not mounted.
4. **Name what stays.** The confirm's text lists, in one sentence, what is not removed: voice samples learned from the meeting, digests that quote it, and backups. Replace "Every file for this meeting" with the true scope. Read `docs/GUIDE.md` first and update its delete recipe in the same commit.

## Explicitly not

- Removing voice samples per meeting. That needs per-sample provenance in `roster.json`, a schema change; SEC22 owns making `roster forget` cascade and SEC24 owns voiceprint retention. Record here only that, without provenance, the confirm must say samples stay.
- Rewriting digests or backup archives. Both are point-in-time documents; the confirm names them.
- A hard delete. Every removal stays a move to the Trash, as now, except the Notion archive, which is Notion's own soft delete.
- A typed owner for the per-meeting file set. ARCH10 (`MeetingFiles`) is the structural fix; if it lands first, `MeetingFootprint` is its delete view rather than a second list of suffixes.

## Acceptance

- `MeetingFootprintTests` (MeetingPipeTests): a stem with a filesystem sidecar locates both published paths; an Obsidian sidecar locates its note; a corrections file is found; a missing sidecar yields no published paths; a stem with no kept original reports none.
- A `softDeleteMeeting` test over a scratch library and scratch published dir: after delete, the corrections file and local published copies are in the injected trash, `meeting_deleted` carries the new counts, and a sidecar pointing at a path that no longer exists does not fail the delete.
- pytest for `mp unpublish`: archives the page id from `.notion.json` through a fake client, treats a 404 as done, exits non-zero with a message when the token is missing; and a test that the targeted index prune removes the stem's rows and leaves the rest.
- `cd daemon && swift test` and `cd pipeline && uv run --extra dev pytest -q` green, ruff and pyright clean, new test counts in the commit body; `python3 scripts/truth_fences.py events` green for the new attributes.
- Evidence (confirms, does not gate): delete a dogfood meeting that was published to the filesystem sink; its `published/` files are in the Trash and `mp ask` no longer cites it.

## Amended 2026-10-25 (observability audit band)

From the [observability audit](../../audits/2026-10-25-observability-audit.md) (SW-18), verified in code on 2026-10-25 against `main` at `01e904a`. Delete and forget paths beyond meeting deletion report success they never checked, and `meeting_deleted` itself overstates.

- **`meeting_deleted` counts what matched, not what was trashed.** `softDeleteMeeting` logs `"files_count": matching.count` after a loop that catches each `trashItem` failure with `Log.main.warning(...)` (os.Logger, reason redacted). It does return `.failure(firstFailure)` so the caller can show an error, but the event says every file went.
- **Voiceprint Reset.** `VoiceprintProfile.reset(at:)` is `try? FileManager.default.removeItem(at: url)`, and the Preferences button runs `VoiceprintProfile.reset(); voiceprintMeetings = 0` with no event. A failed removal of biometric data shows "0 meetings learned" while the file is still there.
- **Roster rename carry.** `RosterRename`'s per-meeting carry catches `SpeakerLabelStore.replace` failures with `Log.main.warning("roster rename carry failed for \(stem): ...")`, and `roster_rename_done` reports only `meetings_carried`, so a rename that left some meetings under the old name looks complete.
- **Model eviction.** `StorageStatsStore.evictUnusedModels` runs `try? FileManager.default.removeItem(at: dir)` per directory and then logs `models_evicted` with `"bytes_freed": bytes` computed before any removal.
- **Digest delete.** `DigestsView.trash(_:)` is `try? FileManager.default.trashItem(at: url, resultingItemURL: nil)`; the list reloads, so a failure is visible only as the row not going away.

**Added to scope:** item 2's new `meeting_deleted` counts are joined by `files_trashed` and `files_failed` (and `files_count` keeps its meaning as matched, or is dropped, said in the commit); `VoiceprintProfile.reset` returns a `Result`, Preferences re-reads `meetingsLearned` after it and shows the error on failure, and a `coordinator` `voiceprint_reset` event carries `ok` and `reason`; `roster_rename_done` gains `meetings_failed` and the callers of `RosterRename.run` (`TranscriptTab`, `PeopleView`) say "N meetings kept the old name" when it is non-zero; `models_evicted` reports the count and bytes of directories actually removed plus `failed`; `DigestsView.trash` surfaces a failure through the view's existing `FailurePresentation`. Each failure also gets a file-log line (OBS1's `Log.failure` if it has landed).

**Added to acceptance:** a `softDeleteMeeting` test with one injected trash failure asserts `files_trashed` and `files_failed`; `VoiceprintProfileTests` for a removal that fails (read-only parent in a temp dir) returning a failure and leaving the count; `RosterRenameTests` for one failed carry reported in `meetings_failed`; a `StorageStatsTests` case where one eviction fails and `bytes_freed` excludes it.

## Amended 2026-10-25 (performance review)

From the 2026-10-25 performance review (findings LIBRARY-7 and PERSISTENCE-5, both confirmed), re-checked in code against `01e904a`. Item 1's `MeetingFootprint.locate` and item 2's rewrite of `softDeleteMeeting` are where these land, so they are recorded here rather than filed as a second task editing the same function.

- **Every delete lists the whole library, on main.** `MeetingLibraryService.softDeleteMeeting(stem:)` starts with `entries = try fm.contentsOfDirectory(at: dir, includingPropertiesForKeys: nil, options: [])` and filters it by `MeetingStore.stem(of:)`, once per stem, then calls `fm.trashItem(at:resultingItemURL:)` file by file. Its callers are main-thread UI: the list row's context menu, `MeetingDetailView`'s header (`_ = libraryModel.softDeleteMeeting(stem: meeting.stem)`), `LibraryWindowModel.softDeleteMeeting(stem:)`, which forwards it synchronously, and `BatchActionsPane.runSoftDelete()`, which is `@MainActor` and loops `for (i, stem) in stems.enumerated() { if cancelRequested { break }; switch libraryModel.softDeleteMeeting(stem: stem) { ... } }` with no suspension point. A batch Move to Trash is therefore O(selected x library entries) of listing plus 7 to 10 `trashItem` calls per meeting (61 files over 9 stems on this Mac on 2026-10-25), all on main: the progress state never paints and Cancel cannot take effect until the loop ends, and `trashItem` is slower again on the owner's iCloud-synced `~/Documents`. The merge's fragment cleanup calls `softDeleteMeeting` inside `DispatchQueue.main.async` too; a handful of fragments, negligible on its own.
- **Export has the same loop.** `BatchActionsPane.runExport()` is started from a view button, so it runs on main, and its loop builds and writes one markdown bundle per meeting without yielding. A single Export (`MeetingLibraryService.exportMeeting(stem:to:)`) runs `fm.copyItem(at: src, to: dst)` for the recording on main: an APFS clone on the same volume, a full copy of a 100 to 600 MB file across volumes. It is recorded here because one off-main batch runner should serve both loops in `BatchActionsPane`; the pickup may split export into its own commit.

**Added to scope:** `MeetingFootprint.locate` takes the directory listing as input (one `contentsOfDirectory` per batch, grouped by stem) instead of listing per stem; the per-stem trash work runs off main (a serial utility queue, or `Task.detached`, hopping to main per item for progress), so `runSoftDelete`'s `cancelRequested` is checked between items and actually stops the batch; `runExport` and `exportMeeting`'s copies move off main the same way, through the same runner rather than a second copy of the loop. Keep the `originals/` cascade and the waveform-cache removal. The directory watcher sees every trash; its 500 ms debounce coalesces them, and nothing here suppresses it.

**Added to acceptance:** a batch delete over a scratch library of N stems lists the directory once (counting seam on the listing); a runner test that a cancel set after the first item stops before the second and that progress is published per item; a test that the export copy does not run on the main thread.

## Amendment 2026-11-13 (audit band)

From the [2026-11-12 independent audit](../../audits/2026-11-12-independent-audit.md) (F071, confirmed, medium, antipattern lens; F170, unverified low) and the [2026-11-13 responsiveness audit](../../audits/2026-11-13-responsiveness-audit.md) (P024 and P032, low, both read from code), re-verified in code at HEAD on 2026-11-13. The off-main trash runner and the cancel-between-items check are already in the 2026-10-25 performance amendment above; what follows is what that amendment does not cover.

- **F071: batch run state dies with the pane, the run does not.** `BatchActionsPane` holds `@State private var state: BatchState = .idle` and `@State private var cancelRequested: Bool = false`, and every action starts its loop as an unstructured `Task { await runX() }` from a button (`runRepublish`, `runRetranscribe`, `runRegenerate`, `runMerge`, `runSoftDelete`, `runExport`). `LibraryWindow.detailPane` shows the pane only while `selected.count > 1` and swaps in `MeetingDetailView` the moment the selection drops to one row. The Task keeps looping, but the pane that owned its progress and its `onStop: { cancelRequested = true }` is gone; a re-created pane starts `.idle` and its Stop writes a different `@State`. Scenario: confirm "Re-summarize 20 meetings", click one row to read it, and the remaining 19 engine calls run with no surface and no way to stop them.
- **P024: a single delete leaves the trashed row selectable.** The two single-delete UI callers discard the result and do nothing else: the list row's `onSoftDelete: { [weak libraryModel] in _ = libraryModel?.softDeleteMeeting(stem: meeting.stem) }` and `MeetingDetailView`'s `confirmDelete()` (`_ = libraryModel.softDeleteMeeting(stem: meeting.stem)`), both through `LibraryWindowModel.softDeleteMeeting(stem:)`. `softDeleteMeeting` itself neither removes the row, clears the selection nor calls `MeetingStore.refresh()`, so the row and detail pane stay until the directory watcher's 0.5 s trailing debounce (`MeetingStore.debounceSec`) fires and the rescan lands: about 0.55 to 0.75 s, read from code rather than measured. A failed trash is also silent at both callers, because `_ =` drops the `.failure`.
- **P032: batch trash and export hold main.** Confirmed as the performance amendment states. Correction at filing: batch `runExport` writes one markdown file per meeting via `MeetingMarkdownBundle.build` and copies no audio; only the single-meeting `exportMeeting(stem:to:)` copies the recording, so the batch export cost is the bundle builds and writes, not file copies. The responsiveness audit's field pack holds one `meeting_deleted` in 45 days, so the cost is unmeasured in the field.
- **F170 (low, verified): drag-out leaves a plaintext copy behind.** `MeetingDragItem.writeBundleToTemp` writes `NSTemporaryDirectory()/meetingpipe-<stem>.md`, built by `MeetingMarkdownBundle.build` from the summary and the full transcript, on every drag, with `.atomic` at the umask mode. Nothing removes it: `git grep "meetingpipe-"` over `daemon/`, `pipeline/` and `scripts/` finds only that writer and its doc comment, and neither `softDeleteMeeting`, retention nor this task's footprint enumerator knows the path. A deleted meeting's transcript therefore survives in the temp directory until the OS purges it.

**Added to scope.**

5. (F071, P032) **One root-owned batch model.** Move every batch loop (`runRepublish`, `runRetranscribe`, `runRegenerate`, `runMerge`, `runSoftDelete`, `runExport`) out of `BatchActionsPane` into a model owned at the Library root beside `AskModel` (the UX37 precedent: an `@StateObject` on `LibraryRootView`), holding the stems, progress, result and a cancel flag. One run at a time; starting a second while one runs is refused with the running one named. The pane, and a strip visible whatever the selection, render from that model, so Stop reaches the run from anywhere. The trash and export work runs off main through the runner the performance amendment already specifies; this item changes who owns it, not how it runs.
6. (P024) **Acknowledge a single delete at the confirm.** On confirm, drop the stem from the list and the selection at once, run the listing and the trash off main, call `MeetingStore.refresh()` on completion, and on failure restore the row and show the error through the Library's existing failure presentation instead of `_ =`.
7. (F170) **Drag-out temp copies.** Either delete `meetingpipe-<stem>.md` after the drag session ends, or write it under an app-owned temp subdirectory that `softDeleteMeeting` (and the footprint enumerator, item 1) clears for that stem and the launch sweep empties; create it 0600 either way. The pickup picks one and says why.

**Added to explicitly not.** A queue of batch runs (one at a time is the bar). Undo of a trash (the Trash itself is the undo).

**Added to acceptance.**

- (F071) A batch-model test: start a run over three stems with a fake engine that suspends per item, change the selection to one row (drop the pane), then set cancel through the model; the run stops before the third item and the model reports it, which fails on `main` because the pane's `@State` is gone.
- (F071) A test that a second batch start while one runs is refused and leaves the first untouched.
- (P024) A single-delete test: after confirm, the stem is absent from the list and the selection before any watcher event fires, and a delete whose trash fails puts the row back with the error.
- (F170) `MeetingDragItemTests`: the bundle is written 0600 and is removed by the chosen cleanup path (drag end, or `softDeleteMeeting` for that stem).
- `cd daemon && swift test` green, N new tests in the commit body.
