# UX56: Preferences opens behind other windows

Band origin: filed 2026-07-31, owner-reported during UX42's walkthrough: "Also noticed that preferences opened behind other windows. maybe it is already filled in as task, and related to window context." It was not already filed. Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

Opening Preferences puts the window up but not in front, so it appears behind whatever the user was looking at.

**Treat this as a suspected UX39 regression first, because UX39 shipped the same day and rewrote exactly this path.** Preferences is one of the three Dock-participating windows that hand their open sequence to `WindowActivationManager`: `PreferencesWindow.swift:28` and `:62` both call `WindowActivationManager.shared.showWindow(w)`, and that manager was introduced by UX39 (landed `70ea61e`, 2026-07-31) to fix the Library sitting at the tail of Cmd+Tab.

The mechanism it introduced is the thing to examine. `showWindow` deliberately **defers** fronting by a run-loop turn (`WindowActivationManager.swift:87-98`): it sets the activation policy, then does `makeKeyAndOrderFront` plus `NSApp.activate()` inside `onNextRunLoopTurn`. The deferral is correct and load-bearing, and the reason is documented there: `setActivationPolicy` is processed asynchronously, so activating in the same turn is evaluated against a still-accessory app and lands the window at the Cmd+Tab tail. But a deferred activation is a deferred activation, and on the second and later opens the policy is already `.regular`, so the deferral buys nothing while still giving the previously-frontmost app a turn to keep or reclaim focus. Cooperative activation on macOS 14 can decline `NSApp.activate()`, and UX39's own notes record that the close-side handoff (`NSApp.deactivate()`) was chosen knowing its worst case is a no-op.

That is a hypothesis with a clear shape, not a conclusion. The pickup should establish first whether this predates UX39, since the answer changes the fix: if it is a regression, the fix is in the manager's sequence; if it is older, it is in how Preferences is opened. Both `git log` on `PreferencesWindow.swift` and simply building the commit before `70ea61e` will answer it.

The Library was not reported with this symptom on the same day (the owner opened it repeatedly during UX39's own MRU and count-drift tests and it came forward correctly), which is itself a clue: whatever differs between the two open paths is where to look, and the most obvious difference is that Preferences is frequently opened while another app is frontmost, whereas the Library was opened from the menu bar with MeetingPipe already active.

## What the pickup established (2026-08-04)

**It is a UX39 regression, and the fix therefore belongs in the manager's sequence rather than in how Preferences is opened.** `git log` on `PreferencesWindow.swift` names `70ea61e` (UX39) as the last commit to touch either open branch, and its diff is the whole answer: before it, both branches ran `w.makeKeyAndOrderFront(nil)` and then `NSApp.activate(ignoringOtherApps: true)` **synchronously** in the menu item's own call, handing the count over only afterwards. After it, both hand the window straight to `WindowActivationManager`, which raises the policy and then fronts plus activates a run-loop turn later. `PreferencesWindow` decides nothing about fronting any more, so there is nothing in it to fix.

**One correction to this spec's own reasoning, and it changes which case is broken.** The Context reads the deferral as buying nothing "on the second and later opens". That is not what the code does: `didCloseWindow` drops the policy back to `.accessory` on the last close, so closing Preferences and reopening it from the status-bar menu is a **first-window** open again, policy raise and all. Every open on that path raises the policy, however many times it is repeated. The case where the app is already `.regular` is a Preferences window opened **while another Dock window is up**, which is a well-travelled path: the Library toolbar's gear (`LibraryToolbar.swift:44`), Cmd+, through UX48's main menu (which only exists while a Dock window is up), the workflow sheet's Vocabulary cross-link (`LibraryWindow.swift:659`), and the permission and Integrations deeplinks.

That case is also the one with corroboration. UX48's pickup rebuilt `292dfe49`'s zero-opacity Cmd+, button in a headless probe and found it **did** fire, with `NSApp.mainMenu` nil, so on 2026-07-31 Cmd+, over the Library was opening Preferences all along. The owner reading that as "nothing happened" and this report ("preferences opened behind other windows"), filed the same day, are very likely one symptom seen twice.

**What could not be measured in the pickup, and why the owner walkthrough is still the measurement.** The discriminating fact is whether macOS grants the deferred `NSApp.activate()`. On the macOS 14 floor that is cooperative: the grant depends on this app holding activation eligibility from the user's click on the status item or the key press. A CLI-launched probe never holds it, so it would be declined in the synchronous and the deferred variant alike and would prove nothing about the difference. Hence no probe, and hence the walkthrough below.

## Scope

Establish regression or not, then fix in the right place, keeping UX39's guarantee intact: whatever changes, the app must still land at the **front** of the Cmd+Tab MRU rather than its tail, which is what UX39 existed to fix and what a naive "front it immediately" revert would undo.

If the deferral is the cause, the shape to consider is deferring only when the policy actually changed (first window), and fronting synchronously when the app is already `.regular`. That preserves the documented reason for the deferral while removing it from the path where it buys nothing. `WindowActivationManager` already knows which case it is in: `shown.insert(...).inserted && shown.count == 1` is exactly the first-window test it uses to decide whether to set the policy at all.

**Shipped as that shape with one change, 2026-08-04:** the condition is a `policyRaiseInFlight` flag rather than the first-window test itself. The rule the code now states is "wait exactly while a policy raise is in flight", which is the reason the wait exists rather than a proxy for it, and the proxy is wrong for the case the existing `test_two_windows_open_and_one_closed_stays_regular` already exercises: two windows opened in the same run-loop turn are **one** transition, so a second window fronting immediately would issue its `activate` against the still-accessory app (the very MRU tail UX39 exists to prevent) and would land underneath the window opened before it. The flag is cleared by the deferred block, both branches run one shared closure so they cannot drift apart, and four tests pin the new branch.

## Explicitly not / out of scope

**Not a revert of UX39.** Its MRU and count-drift fixes were owner-verified on 2026-07-31 and must survive; a fix that puts the app back at the Cmd+Tab tail is not a fix.

**Not the three panels that skip the handshake on purpose** (QuickFind, Onboarding, Correction). They call `NSApp.activate()` themselves by design and QuickFind was confirmed working the same day.

**Not the close-side handoff.** `NSApp.deactivate()` and the unfalsifiable menu-bar criterion around it belong to UX48, which owns the missing main menu that made that leg unobservable.

## Acceptance

Opening Preferences from the status-bar menu while another application is frontmost brings the Preferences window to the front, key and ready for input, on the first open and on every subsequent one.

The Library keeps its UX39 behaviour: after opening it, MeetingPipe sits **second** in Cmd+Tab, not at the tail. This is the regression guard and must be checked in the same pass, since it is the thing most likely to be broken by fixing this.

`WindowActivationManagerTests` gain the case for whichever sequence is chosen, driven through the existing injected `Effects` seam that records call order.

`cd daemon && swift build` and `swift test` green. No em-dashes in changed lines.
