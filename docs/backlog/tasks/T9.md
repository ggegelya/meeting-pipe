# T9: swift test appends thousands of lines to the real pipeline.log, because the Python child it spawns opens a hard-coded log path instead of MEETINGPIPE_LOGS_DIR

Band origin: filed 2026-10-24 from the 2026-10-24 audit band ([go-live assessment](../../audits/2026-10-21-go-live-assessment.md) QG-5). Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

The go-live run on 2026-10-21 saw both suites append about 8,000 synthetic lines to the real `~/Library/Logs/MeetingPipe/pipeline.log` and pytest leave a stale `mlx-server.json` there. Re-checked on 2026-10-24, after CI8 and DIST4 landed: 31,984 of the 32,181 lines in the dev Mac's `pipeline.log` read `synthetic frame`, the file was last written at 17:42 that day, and nothing in either change touched the cause.

**The finding is narrower than "both suites".** The two event-log writers really are isolated: Swift's `Log.resolveLogsDir` honours `MEETINGPIPE_LOGS_DIR` and the XCTest environment, and `PipelineLauncher` appends a child's stdout to `Log.logsDir/pipeline.log`, which is the redirected dir under test. The leak is two Python writers that never ask `events.logs_dir()`:

1. **`orchestrate._configure_logging`** builds `Path(os.path.expanduser("~/Library/Logs/MeetingPipe"))` itself and opens `pipeline.log` there. `FailureProcessTests` launches `daemon/Tests/MeetingPipeTests/Fixtures/failure-process.py` with `"MEETINGPIPE_LOGS_DIR": dir.path`; its `run-all` branch goes through `orchestrate.main`, which calls `_configure_logging()`, and the fixture's error carries `"synthetic frame\n" * 2000`. The child is not under pytest and the variable is ignored for the text log, so each `swift test` run with a pipeline venv adds about 2,000 lines to the user's log.
2. **`local_server.marker_path(home=None)`** resolves `Path.home() / "Library" / "Logs" / "MeetingPipe" / "mlx-server.json"`. `LocalSummaryClient._spawn()` calls `local_server.write_marker(...)` with no home, and `test_summarize_local.py`'s `_fake_spawn` drives `_spawn()` with a fake pid 4242, so pytest writes a marker into the real logs dir. `server_log_path()` beside it already routes through `events.logs_dir()`. `LocalServerReaper` checks the process's command line before signalling, so a stale marker is noise in `mp doctor`, not a kill risk.

Read-only users of the real path (`logs_cmd.LOGS_DIR`, `analyze_detection.DEFAULT_EVENTS_PATH`, `doctor._RECORDER_LOG`) do not write and are listed only so the fix is not over-scoped.

The docs say this class is closed. `CONVENTIONS.md`'s event-log section says both writers are isolated and "the trap is historical, not ongoing". That is true of `events.jsonl` and `pipeline_events.jsonl` and false of `pipeline.log` and `mlx-server.json`.

## Scope

1. `orchestrate._configure_logging` takes its directory from `events.logs_dir()`.
2. `local_server.marker_path` resolves `events.logs_dir() / MARKER_NAME` when `home` is `None`, keeping the `home` parameter its tests use.
3. A fence so the next bypass is caught by a test rather than by a log: a pytest that scans `pipeline/src/mp` for writes under the logs path (the `"Library/Logs"` literal and `"Logs" / "MeetingPipe"` path joins) and allows only `events.logs_dir` plus the named read-only sites, each with a reason.
4. `FailureProcessTests` also asserts that the child's `pipeline.log` landed in its temp `dir`, pinning the cross-process half end to end.
5. Correct the `CONVENTIONS.md` paragraph in the same commit: name `pipeline.log` and the marker, and say they were fixed here.

## Explicitly not / out of scope

- Cleaning the lines already written. Nothing rewrites a user's log; the owner can delete the `synthetic frame` block by hand. `mp.events.is_test_residue` filters JSONL rows only, and `pipeline.log` is free text.
- Removing the `sys.modules` pytest redirect from `events.py` and moving isolation into `conftest.py`: that is T6. Either order works; after both, isolation is the environment variable alone.
- The Swift logger's thread safety: PERF13's logger item.
- Making the daemon's job lane run `FailureProcessTests` in CI (it skips there without a venv): T7's skip gate decides that.

## Acceptance

- New pytest cases: with `MEETINGPIPE_LOGS_DIR` set to `tmp_path`, `_configure_logging()` (run in a subprocess, since it no-ops when the root logger already has handlers) creates `tmp_path/pipeline.log`; `marker_path()` equals `tmp_path/"mlx-server.json"`; the source fence in item 3 passes, and fails on a planted `expanduser("~/Library/Logs/MeetingPipe")` write (tried and reverted).
- `FailureProcessTests` asserts `dir/pipeline.log` exists after the run (it still skips without a venv).
- Session check, stated in the commit body: on the dev Mac, `grep -c "synthetic frame" ~/Library/Logs/MeetingPipe/pipeline.log` and the `mlx-server.json` mtime are unchanged across a full `swift test` and `pytest` run.
- `cd pipeline && uv run --extra dev ruff check src tests`, `uv run --extra dev --extra mcp pyright`, `uv run --extra dev pytest -q`, and `cd daemon && swift test` green, with the new test count in the commit body; `python3 scripts/truth_fences.py` clean after the CONVENTIONS edit.

## Amended 2026-10-25 (observability audit band)

Same class as this task, a test writing into the live logs folder, through a third door this spec does not name.

**The writer.** `scripts/test-app-relocation.sh` (DIST4) runs the staged app's `"$APP/Contents/MacOS/MeetingPipe" doctor` with the caller's environment. `DoctorCommand` emits `Log.event(category: "doctor", action: "probe", ...)` per probe, and `Log.resolveLogsDir` falls through to `~/Library/Logs/MeetingPipe` because `MEETINGPIPE_LOGS_DIR` is unset and the process is not under XCTest. The script says so in its header ("The staged doctor reads this Mac's config and logs its probe events like any `MeetingPipe doctor` run"), and `scripts/ci-local.sh`'s daemon step runs it on every local pass, while the root `CLAUDE.md` row says the script "Touches nothing live".

**What it leaves.** The dev Mac's `events.jsonl` holds 285 `doctor` rows, all dated 2026-10-24 (19 runs of 15 probes), and they were that day's only daemon rows. They carry TCC readings from a staged, ad-hoc-signed copy with its own code identity, for example `permission.microphone` at `warn` with "Mic permission not yet requested" at 2026-10-24T13:08:06Z while the installed daemon held the grant. `mp.events.is_test_residue` keys on meeting stems and the fake engine, which probe rows lack, so every reader takes them as real doctor history.

The `--with-pipeline` leg runs only `mp --help` and `mp --version` and writes nothing, so it needs no change.

## Amendment 2026-11-13 (audit band)

Added from the [2026-11-13 field evidence](../../audits/2026-11-13-field-evidence.md), sections "Pipeline and publishing" (finding "Test runs on this laptop wrote into the production logs") and "Daemon health and cross-check of the code audit" (finding "Test suites wrote into the live logs"), plus the residue counts in "Transcripts and summaries". Re-verified against HEAD on 2026-11-13.

**The field confirms this task on a second machine, and shows the residue is permanent.** On the work laptop's pack: `pipeline.log` holds 68,000 of 79,883 lines (85.1 percent) reading `synthetic frame`, in 34 blocks of 1,999 after timestamps on 2026-09-14, 2026-09-18, 2026-10-01 and 2026-10-12, and 17 of its 18 ERROR records since 2026-09-14 are the fixture's fake credit failure. `pipeline_events.jsonl` has 702 of 1,133 `run_started`, 118 of 126 `run_failed` and 63 of 63 `sink_failed` rows as pytest residue (last on 2026-07-14), and 2,489 of 16,649 pipeline events name a pytest path; `stage_*` rows of residue runs carry no meeting key, so no content filter can drop them. `daemon.log` has 250 of 259 `pipeline FAIL` lines test-shaped. Any failure count read from these files for May to mid October is mostly fiction.

**`is_test_residue` misses the merge rows.** `events._MEETING_KEYS = ("file", "stem", "wav", "meeting")`. `merge_meetings` emits `meetings_merge_resumed` and `meetings_merged` with `primary=primary_audio.stem, fragments=frag_stems` and no other meeting key, so the field's 8 such rows (two bursts on 2026-07-14) escape the filter. Correction at filing: adding `fragments` to the tuple is not enough, because the loop only tests `isinstance(value, str)` and `fragments` is a list of stems; the check has to iterate list values too.

**Correction at filing: the FailureProcessTests leg is closed at HEAD, incidentally.** Since PERF13 (`e04c07b0`, 2026-11-12) `PipelineLauncher.runMP` sets `env[Self.pipelineLogOwnerKey] = Self.pipelineLogOwnerDaemon`, and `orchestrate._configure_logging` returns on `MP_PIPELINE_LOG_OWNER == "daemon"` before it opens the hard-coded path; the daemon's own tee writes `Log.logsDir.appendingPathComponent("pipeline.log")`, which `Log.resolveLogsDir` redirects under XCTest. `FailureProcessTests` spawns through that launcher, so a `swift test` at HEAD should no longer append `synthetic frame` to the real file, which matches the field seeing no residue after 2026-10-12. Likewise the pytest `mlx-server.json` write is covered by conftest's `_private_server_marker` (PIPE22). Items 1 to 4 still stand: `_configure_logging` still builds `Path(os.path.expanduser("~/Library/Logs/MeetingPipe"))` for any spawn without the owner flag, and `local_server.marker_path` still defaults to `Path.home()`, so both remain one missing flag or fixture away from the same leak. The session check in Acceptance is now the proof that nothing reaches the file, not a before and after of a leak in progress.

**Added scope.**

8. `events._MEETING_KEYS` gains `primary` and `fragments`, and `is_test_residue` checks every string in a list value against `_REAL_STEM`, so the merge rows are filtered. (pipeline-and-publishing#4)
9. A fence that fails when a test run changes anything under the real logs directory: `scripts/ci-local.sh` records the size and mtime of every file under `~/Library/Logs/MeetingPipe` (when it exists) before the pipeline and daemon suites and fails if any changed after. Read-only, no-op on CI where the directory does not exist. (daemon-health-and-audit-crosscheck#6)

**Explicitly not, added.** A run id on every pipeline event, which is what would make the residue `stage_*` rows filterable: that is OBS4. A one-time scrub of the existing `pipeline.log` and JSONL generations: an owner choice, since nothing in the repo rewrites a user's log. Temp-dir leaks: T11.
