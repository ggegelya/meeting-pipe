# UX77: the toolbar calls queued work "Processing N" while the row calls the same job "Queued"

Band origin: filed 2026-08-10 from the owner's 2026-08-04 testing notes, with a screenshot annotating both surfaces: "Re-transcribe the meeting has confusing wording: 1 part shows 'queued' the other one shows 'processing'". Status and priority live in this file's header; [INDEX.md](../INDEX.md) lists every task.

## Context

The owner's screenshot has two red boxes on one screen: the Library toolbar pill reads **Processing 1** while the meeting's own inline row reads **Queued: Re-transcribe**. One job, two nouns, and they contradict each other about whether anything is happening yet.

The toolbar pill is fed the **queue depth**, not a count of running work:

- `Coordinator.swift:326`: `onQueueDepth: { [weak self] depth in self?.statusBar.setProcessingCount(depth) }`
- `StatusBarController.setProcessingCount` ([:247](../../../daemon/Sources/MeetingPipe/StatusBarController.swift#L247)) stores it and mirrors it into `libraryModel?.processing.count`
- `LibraryToolbar.swift:130` renders `processingShape(label: "Processing \(processingCount)")`

The same number also drives the menu-bar title clause, `"Processing (\(processingCount))"` ([StatusBarController.swift:287](../../../daemon/Sources/MeetingPipe/StatusBarController.swift#L287), and `StatusBarModel.swift:151` and `:203` for the two menu variants), so the mislabel is on three surfaces, not one.

The per-meeting row is the one that is right. `ProcessingPresentation.label` ([LibraryProcessing.swift:44-56](../../../daemon/Sources/MeetingPipe/LibraryProcessing.swift#L44)) distinguishes the two states deliberately:

```swift
case .active(let p):
    if let label = p.label, !label.isEmpty { return label }
    return "\(MeetingRow.stageLabel(p.stage)) \(MeetingRow.formatDuration(Double(p.elapsedSec)))"
case .queued(let job):
    return "Queued: \(job.label)"
```

`LibraryProcessing.presentation` even documents that a meeting can be in only one of the two, so the active job wins "by construction rather than by precedence rules". That distinction is correct and worth keeping; the defect is that the aggregate surface collapses both into the word "Processing" and then displays the count of the union.

The owner's screenshot is the honest worst case: the queue held exactly one item, it had not started, so "Processing 1" was describing zero running jobs.

## Scope

Make the aggregate surfaces say something true about a depth that includes waiting work, and keep the per-meeting distinction that already works.

The cheapest correct framing is that the number is a queue depth, so name it as one. Options for the pickup, and this is a copy decision more than a code one:

- One neutral noun for the union, e.g. `In queue 3` or `3 in queue`, which is true whether or not the head is running.
- A split that matches the row vocabulary, e.g. `Processing 1 · 2 queued`, which is more informative and costs a second value through the seam (the `onQueueDepth` callback currently carries only the depth).

Whichever is chosen, the constraint is that **the toolbar, the menu-bar title, and both menu variants use the same vocabulary as each other and as the row.** Three of the four read from `processingCount` already, so the fix should be at the label derivation rather than at four call sites.

Two things to preserve:

- **DSN7, one clause not a pile-up.** `applyTitle`'s comment ([:279](../../../daemon/Sources/MeetingPipe/StatusBarController.swift#L279)) records that the menu-bar title carries exactly one clause and that background work only takes the base state's place while idle, by priority. A split label must not turn that into two clauses.
- **The separate-object optimisation.** `ProcessingTracker` is its own `ObservableObject` precisely so queue-depth ticks do not re-render the rail, list and detail ([LibraryWindow.swift:64](../../../daemon/Sources/MeetingPipe/LibraryWindow.swift#L64)). If the split option is taken, the second value rides the same object.

Read `docs/GUIDE.md` before settling the wording and update the recipe if it names either word, per the CLAUDE.md same-commit rule for user-visible surfaces.

## Explicitly not / out of scope

**Not `LibraryProcessing`.** Its two-state split is the correct half and the model for the fix.

**Not the queue itself.** Depth, ordering, and dedupe are unchanged. This is what the number is called.

**Not the "Stopping…" pill.** `LibraryToolbar.swift:127` renders it from a different status branch and is accurate.

**Adjacency, named so it is not silently absorbed:** UX69 covers a running job not being cancellable for its first minute, and the project memory records that Regenerate bypasses the job queue entirely (so `run.json` is not written and the MLX badge goes stale). Both touch this same queue surface and neither is this task. If a pickup finds the depth also excludes regenerate jobs, that is UX69's neighbourhood or a new row, not a silent widening of this one.

## Acceptance

- A test over the pure label derivation asserts the reported case: a queue holding one not-yet-started job does not produce a label claiming work is in progress. It must fail against `main`, which returns "Processing 1".
- A test asserts the toolbar pill, the menu-bar title clause, and both `StatusBarModel` menu variants derive from one shared label function, so a future edit cannot make three of them drift from the fourth.
- A test asserts the per-meeting row still reads `Queued: <label>` for a pending job and the stage-plus-elapsed form for an active one, unchanged.
- If the split option is taken, a test pins that the menu-bar title still carries exactly one clause (DSN7).
- `cd daemon && swift build` clean, `swift test` green, with the number of tests this task adds recorded in the ship note. Do not pin an absolute suite total.
- `docs/GUIDE.md` updated in the same commit if it names either word.
- No em-dashes in changed lines; repo dash guard green.
