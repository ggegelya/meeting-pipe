# UX83: with `user_label` empty, which is the default and is never asked for, the owner's own voice keeps the raw diarizer id "1", is counted as a roster match, and reaches summaries as an attendee

Band origin: filed 2026-10-24 from the 2026-10-24 audit band ([go-live assessment](../../audits/2026-10-21-go-live-assessment.md) FQ-2, UX-4, and its "Fix before anyone else installs it" item 7). Status and priority live in this task's ToC row in [meetingpipe-q6-backlog.md](../meetingpipe-q6-backlog.md).

## Context

The go-live assessment saw the digit "1" as a speaker in 7 of 9 transcripts on a Mac whose `user_label` was unset. Re-traced in code on 2026-10-24; every step is reproducible by reading:

1. **The default is empty and nothing asks.** `config.example.toml` ships `user_label = ""` and `install.sh` copies it. The five onboarding steps under `daemon/Sources/MeetingPipe/Onboarding/` (Welcome, Permissions, Workflow, PublishTarget, Test) carry no name field. The only control is Preferences ▸ Pipeline ▸ **Your name**, from FEAT3-FINISH.
2. **The raw id survives finalize.** FluidAudio names clusters `String(nextSpeakerId)` (`SpeakerManager.createNewSpeaker` in the pinned 0.14.8 checkout), so ids are "1", "2", and so on. `resolve_speaker_labels` in `pipeline/src/mp/diarize.py` maps the identified owner only `if me is not None and label`, and its loop skips `spk != me`, so with an empty label the owner's cluster is neither named nor turned into a `THEM-x`. It keeps "1". `_write_embeddings_sidecar` then stores the owner's vector under the key "1".
3. **The app counts it as a roster match.** `VoiceResolution.derive` in `daemon/Sources/MeetingPipe/VoiceResolution.swift` tests `MeetingCast.isUnnamedCluster` (`THEM-` or `speaker_` prefix, so "1" fails), then the owner check (skipped when `owner.isEmpty`), then `canEnroll`, which is true because "1" is a key of the embeddings sidecar. So the owner's voice gets `origin = .roster` and inflates `rosterMatched`. `TranscriptDisplay.displayName(for:)` returns "1" unchanged.
4. **Naming it does not stick.** A `.roster` chip offers only **Rename everywhere...**, which runs `mp roster rename --old 1`; by reading `RosterStore.rename` and `roster_cmd.py`, that returns "not renamed" and exits 1, because "1" was never enrolled. Line reassignment works per meeting only. Enrolling the owner into the roster would not help either: `resolve_speaker_labels` never roster-matches the `me` speaker.
5. **It leaks into summaries.** The summarizer reads the transcript with "1" as a speaker, so "1" becomes an attendee and an action owner. [DV5](./DV5.md)'s 2026-08-19 survey found 357 bare numbers among 1126 owned open actions on the owner's library. DV5 did not attribute them, but a bare number is exactly the shape this defect produces.
6. **The copy is wrong about it.** The Preferences sublabel says "so speaker labels read as your name, not \"Speaker 1\". Leave blank to keep generic labels", and `config.example.toml` says "instead of \"Speaker 1\"". Blank does not produce "Speaker 1" or any generic label; it produces "1".

The self voiceprint is unaffected: `_me_signals` still identifies and enrols the owner on every stereo meeting. The pipeline knows which voice is the owner; it only lacks a word to write.

## Scope

1. **Ask in onboarding.** A short step (or a field on Welcome; coordinate the placement with [UX84](./UX84.md), which rewires the onboarding steps) titled along the lines of "What should transcripts call you?", prefilled from `NSFullUserName()`, editable, written through `ConfigStore.summarizationUserLabel`. Prefilled, not silently defaulted: the account name may be a nickname or "admin", and it ends up in published summaries.
2. **Never leave a raw diarizer id on the owner.** In `resolve_speaker_labels`, when `me` is identified and the label is empty, map it to the existing `USER_SPEAKER` constant (`speaker_user`), which the channel-fallback path already uses for the same person, so one reserved label covers both paths. A cluster that is not the owner keeps its current treatment.
3. **Render and classify it as the owner.** `TranscriptDisplay.displayName(for:)` renders `speaker_user` as "You". `VoiceResolution.derive` classifies `speaker_user`, and for meetings finalized before this change a purely numeric label that is a key of the embeddings sidecar, as `.you`, never `.roster`. Its chip offers **Set your name...**, which writes `user_label` and carries the name into past meetings through the speaker-label overlay (the `RosterRename.carry` idiom), so nothing rewrites `<stem>.json`. The summarize input renders the reserved label as a word, not an id (`render_markdown` in `pipeline/src/mp/markdown.py`).
4. **Fix the copy** in Preferences and `config.example.toml` to say what blank actually does after this change.

## Explicitly not

- Silently writing the macOS account name into `config.toml` for existing installs. Asking once is the point.
- Changing how the owner is identified (`_resolve_me_id` precedence, `identify_user_speaker`'s 0.6 mic fraction). Applying the owner's label per segment rather than per cluster is [DIAR6](./DIAR6.md).
- Diarization labels other than the owner's reaching summaries (`THEM-x`, unnamed clusters). That is [FEAT21](./FEAT21.md). Moving the field out of Pipeline in Preferences is [UX87](./UX87.md).
- Roster behaviour for other people ([FEAT19](./FEAT19.md)).

## Acceptance

- `pipeline` tests: an identified owner with an empty label maps to `speaker_user`, with a set label to that label; no finalized transcript from a fixture with an identified owner carries a purely numeric speaker; the embeddings sidecar keys the owner's vector under the reserved label.
- `daemon` tests: `VoiceResolution.derive` classifies `speaker_user` and a numeric embedded label as `.you` and does not count either in `rosterMatched`; `TranscriptDisplay.displayName(for: "speaker_user")` is "You"; Set your name writes `summarization.user_label` and carries into a second meeting's overlay; the onboarding step prefills from an injected account name.
- A test fails without the change (today "1" classifies as `.roster`).
- `cd pipeline && uv run --extra dev ruff check src tests`, `pyright`, `pytest -q` green; `cd daemon && swift build` and `swift test` green; new test counts in the commit body; `python3 scripts/truth_fences.py both` green.

- Owner check after install (confirms, does not gate): a fresh meeting with the name set shows the owner's name; a past meeting showing "1" shows "You" and takes the name from **Set your name...**.
