# Responsiveness

Companion to the independent audit of 2026-11-12 (`2026-11-12-independent-audit.md`, in this folder), whose executive summary carries the conclusions drawn from this file.

Added 2026-11-13 at the owner's request: the app should react at once to every action, and it does not (the Record click takes about a second to show anything). This is about perceived latency, the time from a click or key press to the first visible acknowledgement, not throughput, which the main audit rated well. Four tracers followed the interaction journeys and one swept the app for main-thread work and deliberate delays; skeptics re-read every claimed delay; timings were measured from the work-laptop event log where two events bracket an action. 43 slow interactions survived (10 refuted).

**Diagnosis.** Throughput is fine because the heavy work (transcription, merge, pipeline) already runs off the main thread and is bounded. Responsiveness is a different property and nothing in the code measures or enforces it: daemon/Sources has no click event, no first-paint event, no signpost and no main-thread stall probe, so the audit could rate performance 4.5 of 5 without ever timing a click. The 43 verified items share three shapes. (1) Completion-first UI: the visible change is written in the completion of the work (recorder start, an mp subprocess, launchctl, the 0.5 s file-watcher debounce) instead of at the click, and work in flight is a private flag (recordingStartInFlight, wantsPlayback) rather than a state the UI can draw, so the click looks ignored and a second input is dropped. (2) Synchronous work on the main thread between awaits: the Accessibility walk after Record before PERF15, capture file creation today, the status menu rebuild in every state setter before PERF24, launchctl and Keychain subprocesses inside control setters. A function marked @MainActor async is not off main; its synchronous stretches block every window. (3) Cold paths: windows and panels rebuilt on every open, and a launchd job with no ProcessType whose main thread was measured at priority 20 on this Mac against 46 to 47 for apps. Fixes also reach the owner late: the largest measured offender (the walk after Record) was fixed on 2026-10-26 but only reached the work laptop on 2026-11-12, so for a month 17 of 44 Record clicks took more than a second before the HUD could draw. I re-derived the start and stop numbers from the pack independently and they match the journey traces.

## Principles that would stop this recurring

- Acknowledge on the event, reconcile on the result. The first statements of every action handler set a visible state (pressed and disabled, label, spinner, row removed, glyph flipped) before any await, subprocess, file read or Accessibility call. The completion promotes that state or reverts it with a reason shown in the same place.
- Work in flight is a state, not a Bool. Anything that can exceed 100 ms gets a named state the UI draws (Starting, Stopping, Cancelling, Saving, Moving, Renaming) and that decides what the next input does. recordingStartInFlight and wantsPlayback are the pattern to retire: nothing can render them, and presses that meet them vanish.
- Never drop an input silently. Accept it, latch it for when the current work ends, or refuse it visibly, and log which. toggleManual's `.stopping: break` and play()'s first guard are the two code-verified counter-examples.
- The main thread only draws. Budget 50 ms per main-thread job. No Process, launchctl, Keychain, Accessibility, HAL property call, AVAudioFile or AVAudioEngine call, directory listing or Data(contentsOf:) on main. @MainActor async is not off main: the synchronous stretch between two awaits blocks every window, as capture file creation does today.
- Visible calls first, bookkeeping after the frame. Inside one main-thread job nothing paints until the job returns, so the order of statements is the latency. Put the two or three calls the user sees first and push teardown, logging and sidecar writes to the next turn or a queue.
- The app's own writes update the UI directly. Patch the model or call MeetingStore.refresh() at the click; the 0.5 s watcher debounce exists for changes made outside the app and must never be the path by which the app learns what it just did.
- Debounce the expensive part only. Echo the keystroke and filter in memory at once; debounce the index lookup or the subprocess and let it refine what is already on screen.
- Animation never stands in front of an acknowledgement, and opposite choices must not look the same. A confirmation should not start invisible behind work, fades stay at or under 180 ms, and Record and Skip need different first frames.
- Optimistic UI stays truthful. Say Starting, not Recording, until audio flows; show the failure where the optimism was shown; restore a row that could not be trashed.
- Keep warm what is opened daily. Build the HUD, prompt and daily windows once, hold them across closes or prebuild at idle after launch, and parse static documents once per process.
- Click-to-feedback is a measured product metric with a budget, an event pair per action, a stall probe and a fence in ci-local.sh. A comment that says work is off main or never blocks the UI is a claim: line 558 of MeetingSessionController.swift says the await never blocks the UI while the call it awaits blocked main for 3.1 s on 2026-11-12.
- A fix counts when it is installed. Record the commit hash in the app_rebuild and launch events so field data is read by build, not by date, and rebuild the daily machine when a latency fix lands.

**Latency budget.** Scope: time from the input event (mouse up, key down, hotkey) to the first frame that shows the app took it. 1. Pressed state on pointer down: within 1 frame (16 ms), always. 2. First acknowledgement of the action itself (label, spinner, row change, window ordered front): 100 ms hard limit at p95, target 50 ms, and it must be set in the same main-thread turn as the event, so it does not depend on any await. 3. Main thread: no single job over 50 ms; log a stall at 100 ms; treat 250 ms as a bug. 4. Work that cannot finish in 100 ms continues behind a named in-progress state. Past 1 s the state must visibly change (spinner or elapsed text); past 3 s it says what it is waiting for; past 10 s it offers Cancel. 5. Record: click to Starting shown, 50 ms. Click to recording confirmed (timer running): p50 250 ms, p95 1 s on the built-in or a wired device; a Bluetooth route may take longer but stays in Starting with a reason after 1.5 s. Zero starts with a main-thread stall over 100 ms, including the first after launch. 6. Stop: click to HUD leaving and menu bar reading Stopping, 50 ms. A new Record during the merge is accepted or answered within 100 ms. The merge itself (median 3.6 s today) has no budget; it is throughput. 7. Prompt after detection is not click latency, but budget it: state_change to prompt_shown p95 100 ms (a warm prompt already takes a median 49 ms; after more than 5 minutes of quiet the median is 300 to 430 ms in every era). 8. Windows: warm open on screen in 100 ms; cold open 250 ms with the frame up and a placeholder; no open blocked on a subprocess. Menu bar menu: drawn from cached values, under 50 ms of main-thread work in menuNeedsUpdate. 9. Typing: echo in the same frame; in-memory results within 50 ms of each keystroke; index or subprocess refinement within 250 ms of the last one. 10. Edits and deletes of the app's own data: the edited surface and every other surface showing it update within 100 ms, without the 0.5 s watcher debounce. 11. Animation: starts on the event, at most 180 ms, never the only acknowledgement. Current standing against line 2: the recording journey fails it on every start (minimum 104 ms after the recorder's start line, before the fade); most Library and Preferences items are unmeasured.
