# Meeting Pipe — macOS App UI Kit

HTML/JSX recreations of the shipped Swift menu-bar daemon's surfaces, faithful to structure, labels, layout, and the design tokens. These are mockups for design exploration, not real AppKit code.

The kit covers the surfaces that ship today, plus one anticipated near-future surface (onboarding):

| Component | Maps to | Source of truth |
|---|---|---|
| `MenuBarDropdown.jsx` | `StatusBarController.swift` | the `rebuildMenu()` function |
| `MeetingPrompt.jsx` | `MeetingPromptWindow.swift` | the 600×64 horizontal `NSPanel` pill + the `⌄` chevron menu |
| `Notification.jsx` | `Notifier.swift` | `notifyDone` / `notifyRecordingStarted` body strings |
| `PreferencesWindow.jsx` | `Preferences/PreferencesView.swift` + the per-section files | the 820×660 `NavigationSplitView` (General / Recording / Prompt / Pipeline / Integrations / Permissions / Advanced), floor 780×660 |
| `SummaryLibrary.jsx` | `LibraryWindow.swift` + `LibrarySidebar` / `LibraryListView` / `MeetingRow` / `MeetingDetailView` + tabs | the shipped `NavigationSplitView` Library (rail + filtered list + Summary / Transcript / Audio tabs) |
| `OnboardingPermissions.jsx` | *(anticipated)* | the four-permission grant list (Microphone, Screen Recording, Accessibility, Notifications); see the README install steps |

`index.html` shows them composed against a faux desktop so you can see how the
menu bar, dropdown, and prompt sit on screen together.

## Caveats specific to this kit
- The `SummaryLibrary` and `PreferencesWindow` mockups draw a light window chrome (border, radius, shadow) inline; the real app uses native `NSWindow`. The `macos_window.jsx` starter stays available for framing screenshots.
- Tabs and panes are interactive in the mockups (the Library detail tabs, the Preferences sidebar) so a reviewer can click through; the real app persists those selections.
- Translucency: real `NSVisualEffectView .hudWindow` blends with whatever is behind it on the desktop. Web `backdrop-filter` only blends with what is in the page, which is close enough for design review.
- Only `OnboardingPermissions` is still a proposed design rather than a faithful recreation of shipped code. Every other surface in this kit mirrors a surface that ships today, faithful to structure, labels, and tokens (not byte-identical to AppKit).
- Known lag from UX22 (not yet re-mocked; a rendered eyeball is owner-owed): `MenuBarDropdown` does not show the new **"Finish setup"** checklist row (a submenu of unmet setup items that appears until everything is green), and the onboarding flow gained a **"Where summaries go"** publish-target step (Notion token + database picker + a read-only Verify) between the workflow and test steps. Update these when the surfaces are next re-mocked from screenshots.
- Known lag from FEAT11 and UX44, same caveat: `PreferencesWindow` does not show the Pipeline pane's new **Vocabulary** group (wrong-to-right term rows plus an *Applies to* scope picker, sitting between People and Summarization prompt; since UX44 also a one-line lede row above the picker, a greyed non-persisted sample row on an empty scope in `fg-subtle`, and an "Also catch near-misses" toggle row under Add term). Nor is the **workflow editor sheet** in this kit at all, so its new `Vocabulary…` card under Context prompt has nothing to lag against yet. Also, `SummaryLibrary` does not show the **cast strip** above the Transcript tab's lines (one chip per voice, with a `Name` affordance on the unresolved ones and, since UX40, a per-chip context menu whose items depend on where that voice's name came from, and since FEAT14 also on whether roster matching came close to somebody without naming them, which adds a `Name as <person>` item with an uncertainty caption under it) or the quiet `· no context` marker beside a workflow's name in the rail. All of these reuse existing primitives and tokens (`SettingsGroup` / `SettingsFullRow` / `SettingsToggleRow`, the `SettingsTag` chip shape, the rail row's `· default` treatment), so the lag is coverage, not a new pattern.
- Known lag from UX41, same caveat: `SummaryLibrary`'s detail header shows the `Summary edited locally` caption but not the second caption that can sit under it, `Speaker names changed after this summary.` with an inline **Re-summarize** menu (shown when the speaker overlay was written after the run that produced the summary). Same slot, same caption register. Both captions are `fg-subtle`: `fg-faint` sits near 2.8:1 against a 4.5:1 body floor, so DOC12 moved the `Summary edited locally` neighbour off it too. Coverage rather than a new pattern.
- Known lag from UX76, same caveat: `SummaryLibrary`'s `SLWorkflowRow` still renders the rail's footnotes as the words `· default` and `· duplicate name`, which is what the app shipped until UX76 demoted all three to glyphs. That task exists because the words were the defect: three captions plus the name under one `.lineLimit(1)` truncated together and the owner's main workflow rendered as `Pers… · defa… · no c…`, identifying nothing. Re-mocking it means picking glyph shapes, which is a design judgement the owner owes on the running build rather than a blind edit here, so it waits. Two things to carry into that re-mock: the mock has never modelled FEAT11's no-context marker at all, and its captions sit on `--mp-fg-faint`, which is around 2.8:1 against the 4.5:1 floor DOC12 moved a neighbouring caption off, so a re-mock should land them on `--mp-fg-subtle` like the app does.
- Known lag from UX36, same caveat: `SummaryLibrary`'s summary pane models no reading measure at all, so it does not show the shipped 720pt column left-aligned in the capped detail pane with a 20pt gutter outside the cap (the app used to park that column hard left with the gutter inside it, then briefly centered it; both forms lost to left-aligned-under-a-cap). The Transcript pane in that mockup is likewise unmeasured: since 2026-07-29 the transcript rides the same 720 measure as the summary (cast strip, captions, and rows all on one stack, playback transport full-bleed), so the two reading tabs share both edges. It also does not model the detail pane's **chrome band**: the title, metadata, provenance line and tab strip sit together on `bg-sunk` spanning the full pane, with a `border-strong` hairline as the band's bottom edge, so they read as recessed chrome rather than as the body's first content. It is why the header is not on the reading measure (the Transcript and Audio tabs are full-width, so a measured header would be misaligned against them). The tab strip's labels are left-packed with the active underline sized to its own word. Two things settled after the owner saw it running and are worth carrying into any re-mock: the band **recesses** rather than lifts, since `bg-raised` against the dark canvas was an 11-of-255 step nobody could find; and the measured column **left-aligns** rather than centring, which is affordable because the detail column is now itself capped at `LibraryLayout.detailMaxWidth` (1040), so window growth widens the meeting list instead of the reading pane and every tab's content shares one left edge. `SLActionItem`'s metadata band is a plain non-wrapping flex row and does not show FEAT10's `[mm:ss]` evidence chips, which in the app share that band and wrap it to a second line via `ViewThatFits` when the detail column is narrow. Both are coverage rather than a new pattern, but re-mocking the pane means restructuring its layout, so it waits for eyes on a screenshot rather than a blind edit.
