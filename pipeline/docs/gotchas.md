# pipeline/ - the evidence behind the rules

Rules in [`../CLAUDE.md`](../CLAUDE.md) link here for the incident that produced them. The rule is what you must do; this section is why, and what it cost to find out. Read one before you argue with a rule, change it, or decide your case is the exception.

Kept out of `CLAUDE.md` deliberately (DOC14). That file is prepended to every prompt in this subtree, so prose there is paid for on every turn whether or not it is relevant; this file is paid for only when read. `scripts/truth_fences.py claude` is what keeps the split honest: an entry over 800 bytes is narrative and belongs here.


## An underscore name belongs to its module

**An underscore name belongs to its module.** If a sibling module needs it, that is the signal to promote it to a public name in a home that makes sense, not to import the private one. A module-private copy of a sibling's helper is worse still: `publish_fs` carried its own `_render_summary_md` "so it does not depend on a private helper", and the copy silently drifted from the original until PIPE7 deleted it. The shared ones today: `markdown.render_summary_md`, `config.parse_local_endpoint`, `workflow.read_meta`, `backend_fallback.run_with_local_fallback` (the one cloud-then-local `auto` ladder, shared by `summarize` and `engine`), `json_extract.largest_balanced_json_object` (the balanced-JSON scan, shared by `summarize_local` and the PROV1 `provider_*` backends; PROV1 promoted it out of `summarize_local` for exactly this reason) and its neighbour `json_extract.parse_summary` (the scan-then-validate step both PROV1 providers ran; ARCH5 promoted it after the two private copies had already diverged past the provider error each raises, so the recovery policy could drift per provider), and `summarize_local.augment_with_schema` / `.compose_user_message` (the system and user turns the local server sends, promoted out of `LocalSummaryClient` by LOCAL9 so `train_adapter` trains on the exact shape inference uses; a LoRA tuned on a prompt the server never sends is tuned for nothing), plus `orchestrate.existing_daemon_transcript` / `.finalize_streamed_transcript` / `.apply_glossary` (run-all's finalize stage, promoted by ASR3 so `mp finalize` re-runs the same transform for the re-transcribe ratchet instead of a copy that would drift from it), and `resource_guard.estimate_model_gb` / `.physical_ram_gb` (the 4-bit size estimate and the `sysctl hw.memsize` read, promoted out of `doctor` by LOCAL16 once the spawn refusal and the free-RAM watchdog needed the same two numbers doctor was advising on), and `events.PROGRESS_SENTINEL` / `.emit_progress` (the `__MP_PROGRESS__` stdout line plus its durable `stage_progress` event, promoted out of `orchestrate` by AI11 when `mp ask` needed the same channel for its index build; `orchestrate.PROGRESS_SENTINEL` is now an alias, and the sentinel is a cross-language contract with `PipelineLauncher.progressSentinel`, so a second private copy would be the worst kind of drift), and `config.SAMPLING_TEMPERATURE` (the one decoding temperature every backend samples at, read by `summarize`, `engine`, `summarize_local`, and `provider_openai`; PIPE12 promoted it after the two Anthropic paths turned out to pass none at all and so ran at the API default of 1.0 while the other two pinned 0.2, which made the *default* backend the one you could least compare two runs of). `render_summary_md` and `largest_balanced_json_object` each have a Swift mirror (`AppleIntelligenceSummarizer.renderMarkdown` / `.largestJSONObject`) pinned by CI3 golden fixtures (`Fixtures/summary-md-golden.json`, `Fixtures/json-extract-golden.json`), so a cross-language drift breaks one suite (the CI2 meta-contract precedent). That mirror now covers AUTO2's citation links too (`markdown.deeplink_url` / `.deeplink_seconds` against `AppleIntelligenceSummarizer.deeplinkURL` / `.deeplinkSeconds`), and the golden case carrying a `deeplink_stem` is what pins them.

## A shared transform belongs in a validator, not at four call sites

**A transform every backend must share belongs in a validator, not at four call sites.** FEAT10's `normalize_model_summary` flattens the model-facing `{text, evidence}` sections into the stored shape; it is wired as a `mode="before"` model validator on `MeetingSummary`, so the Anthropic tool path and all three JSON-recovery paths (`summarize_local`, `provider_claude_cli`, `provider_openai`) inherit it and a new backend cannot forget it. Keep such a normalizer idempotent and a no-op on the stored shape, or re-validating a file on disk will corrupt it. **It holds a second transform since PIPE15**, `_decode_stringified_lists`, which runs first so a stringified list of `{text, evidence}` objects gets both: a `list[str]` field handed back as a JSON-encoded string is decoded, and only when it decodes to a real list. That narrowness is the design, not caution. Wrapping a prose string into a one-item list would accept a section that is one run-on sentence, which is the model answering a different question, so it is left to fail validation. The `list_type` shape fired three times on the real corpus and killed one run; the fix went here rather than into the Anthropic client because that is the only home every backend inherits.

## Never sys.exit from library code

**Never `sys.exit` from library code.** `SystemExit` derives from `BaseException`, so it walks straight through every `except Exception` a run is wrapped in. `config.require_env` did exactly this for years and it cost PIPE16: called from `publish_router._build_one`, its `sys.exit(2)` skipped `orchestrate`'s `run_failed` emit, the exit-3 mapping and the `<stem>.publish.json` write, so the daemon saw a generic exit 2 over a meeting whose summary was on disk and the durable Library row settled on **"Ready"** for a meeting that published nowhere. It raises `config.MissingSecretError` now, and the fail-fast it was reaching for lives at the boundary: `__main__.main` catches it once, beside the `KeyboardInterrupt` handler and for the same "one handler serves every subcommand" reason, and returns 2.

## A model's self-reported kind cannot carry a safety property

**A model's self-reported label for its own edit is a note, not a fact, so never hang a guard on it.** `diarize_cleanup`'s `SpeakerEdit.kind` is `"merge"` or `"reattribute"`, the model picks which, nothing validates it, and `_apply_edits` performs the identical mutation either way: it sets one segment's speaker. A guard keyed on `kind == "merge"` is therefore one the model opts out of by writing the other word, and it would have been the natural reading of DIAR5's own scope line. The guard reads what the edits do to the *labels* instead: an edit that moves the last segments off its source label merges two diarization clusters whatever it was called, and `_refuse_unsupported_merges` decides on that. The same reasoning is why the sidecar records `kind` but never acts on it.

**The cost asymmetry is what sets the threshold, and it is not symmetric at all.** A refused merge leaves two labels for one person, which is exactly the state the pass was not run in: at worst an extra unnamed cluster the owner names in one click. An allowed bad merge puts one person's sentences under another person's name, and that reaches the summary's attendees and action owners as a confident falsehood. So the bar is `MERGE_MIN_SIMILARITY = 0.65`, the value `roster.MATCH_MIN` already uses for "this embedding is that person", and the guard fails **open** where there is no evidence (a label with no embedding, a missing `<stem>.embeddings.json`) rather than silently disabling the pass on every older meeting.

**Measured on the owner's corpus 2026-08-18, 36 meetings the pass had run on.** It eliminated a label 8 times. Scoring each elimination against its most acoustically favourable destination, the most generous reading available, the eight scored 0.089, 0.113, 0.289, 0.328, 0.351, 0.463, 0.524 and 0.554: not one clears 0.65, and two are near-orthogonal voices. Read the other way, over 77 label pairs the owner's own corrections prove are different people, the highest similarity anywhere is 0.644, which also sits under the bar. The demonstration meeting `20260804-103026` is three of those eight (THEM-A into Sudip at 0.524, THEM-B into Prajval at 0.554, THEM-D into Anisha at 0.463), and the guard refuses all three. **The honest cost, stated rather than buried:** the same corpus offers only one clean same-person split to measure the other side with (0.531, `20260806-113032`), and this bar refuses it too, so the pass now merges rarely. That is the trade taken deliberately, not a side effect. It is also not "turn the toggle off", which DIAR5 ruled out: reattribution still runs untouched, and it is the majority of the pass's edits.

**The pre-cleanup transcript is not kept anywhere**, which is why the audit sidecar records `from` and not just `to`. Nothing on disk holds a meeting's labels as the finalizer left them: `cleanup_transcript` rewrites `<stem>.json` and re-renders `<stem>.md` in place, and `<stem>.embeddings.json` holds the finalize label *set* but no per-segment assignment. So for every meeting cleaned before DIAR5 the pass's decisions are unrecoverable, and a before/after DER on them is impossible rather than merely unmeasured. `valid1_check.revert_cleanup` reconstructs the pre-cleanup transcript from the `from` labels, which is what makes `--cleanup`'s DER pair possible at all. Read its `undone` column first: the DER pair only separates when the pass moved a segment off the label the owner then assigned back to it, so a flat delta means the metric could not see the edit, not that the edit was harmless.

## A library-wide command cannot be clamped by a per-meeting flag

**`config.zero_egress` is `regulated_mode or workflow_nda_mode`, and the second half is structurally unreachable for a command with no meeting anchor.** `workflow_nda_mode` is set in exactly one place, `workflow.apply_overrides`, from one meeting's `<stem>.meta.json`. `entry.prepare()` applies that overlay only when a caller passes an anchor. `mp ask` and `mp digest` are library-wide, so both called `entry.prepare()` with none, and both said so in an inline comment ("Library-wide, so no meeting anchor") that read as a note about scope rather than as a hole. It was a hole: on a Mac with `modes.regulated_mode = false` and `summarization.backend = "anthropic"` (the owner's configuration), the only clamp either command had was one that was switched off, so an NDA meeting's transcript was a retrieval candidate for a prompt that egresses. `embed_index.chunk_library` applied no policy filter of any kind, so the withheld text was in the index both of them search. Meanwhile both files' docstrings claimed "regulated / NDA force the on-device path with no cloud fallback", which was true of the first half and impossible for the second.

Found by reading the code path on 2026-07-27 while assessing AUTO3, and **deliberately not confirmed by running it**, because confirming it would have meant sending the owner's NDA content to a cloud provider. Three of the owner's meetings were in that corpus at the time.

**The fix is a second single-owner predicate rather than a fix at each call site.** `visibility.withheld_reason` answers "may this meeting leave this machine" the way `zero_egress` answers "may this run reach a cloud service", and the surfaces that can egress take an `allow_stems` set from it: `chunk_library` / `refresh_index` / `load_or_build`, `actions.discover`, `digest.collect_open_actions` / `.collect_recent_decisions`, and every `mcp_tools` function. Filtering at chunk time rather than over the results is the load-bearing part: a result filter still embeds the text, still lets it compete for the top-k, and still has the withheld words resident in the process that then builds a cloud prompt.

**Three details that are easy to get wrong.**

*Unconditional, not backend-keyed, and this is the part that will surprise someone later.* **The gate applies on every backend, including `local` and `apple_intelligence`, where the run egresses nothing at all.** Gating only when `effective_backend` is a cloud one is the tempting shape, since a local-only `mp ask` cannot leak anything and would keep its full corpus. It was rejected for a mechanical reason rather than a doctrinal one: the allowlist is applied to the index's per-stem fingerprint map, which is AI11's reuse decision, so alternating allowlists over one `index_dir` re-embeds the difference on every flip, and a backend setting is exactly the kind of thing that moves. Two allowlists would mean two corpora that disagree, or one that thrashes. So it is one allowlist per index directory, always, and the rule is not "withheld meetings are kept out of cloud prompts" but "withheld meetings are not in the library-wide corpus". **The cost is real, was put to the owner explicitly on 2026-08-18, and was accepted:** on the real library that is 41 of 267 meetings out of `mp ask` and `mp digest` no matter which engine answers, the 2 NDA ones included. Note the blast radius stops at the library-wide commands: anything anchored on one meeting (`mp summarize`, a regenerate, the Library's own views) is untouched, because `entry.prepare(anchor=...)` gives those the overlay and the existing NDA clamp already covers them. Before reaching for a `--include-withheld` escape hatch, read the spec: exposing withheld meetings under a flag is named and excluded, and the honest alternative is the per-workflow opt-in AUTO3 defers to its own task.

*A malformed sidecar reads as a missing one.* `workflow.read_meta` returns `{}` for both, and the gate maps `{}` to withheld. That is what stops a policy gate from being openable by corrupting a file.

*The gate is not fingerprinted, and does not need to be.* `.meta.json` is not in `STEM_SOURCE_SUFFIXES`, so flagging a meeting NDA does not change its stem fingerprint. It does not have to: the allowlist is applied to `library_stem_fingerprints`, so a newly-withheld stem simply vanishes from the current map, `plan_refresh` calls it `removed`, and its rows leave the persisted index on the next run. The same mechanism un-indexes withheld meetings from an index built before the gate existed, with no migration.

**The behaviour change is visible and was intended.** Fail-closed means a meeting with no sidecar is withheld, and on the owner's library that is 39 meetings that predate workflows, plus 3 NDA ones: 42 withheld against 175 exposed. Those 39 stopped being searchable by `mp ask` and stopped contributing to `mp digest` when this landed. Two shipped test files had fixtures that wrote no sidecar and started failing, which is the same fact arriving as a red suite; both now write one, since a daemon-recorded meeting always has one and a sidecar-less fixture was a shape that only ever existed in tests.
