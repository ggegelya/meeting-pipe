# pipeline/ - the evidence behind the rules

Rules in [`../CLAUDE.md`](../CLAUDE.md) link here for the incident that produced them. The rule is what you must do; this section is why, and what it cost to find out. Read one before you argue with a rule, change it, or decide your case is the exception.

Kept out of `CLAUDE.md` deliberately (DOC14). That file is prepended to every prompt in this subtree, so prose there is paid for on every turn whether or not it is relevant; this file is paid for only when read. `scripts/truth_fences.py claude` is what keeps the split honest: an entry over 800 bytes is narrative and belongs here.


## An underscore name belongs to its module

**An underscore name belongs to its module.** If a sibling module needs it, that is the signal to promote it to a public name in a home that makes sense, not to import the private one. A module-private copy of a sibling's helper is worse still: `publish_fs` carried its own `_render_summary_md` "so it does not depend on a private helper", and the copy silently drifted from the original until PIPE7 deleted it. The shared ones today: `markdown.render_summary_md`, `config.parse_local_endpoint`, `workflow.read_meta`, `backend_fallback.run_with_local_fallback` (the one cloud-then-local `auto` ladder, shared by `summarize` and `engine`), `json_extract.largest_balanced_json_object` (the balanced-JSON scan, shared by `summarize_local` and the PROV1 `provider_*` backends; PROV1 promoted it out of `summarize_local` for exactly this reason) and its neighbour `json_extract.parse_summary` (the scan-then-validate step both PROV1 providers ran; ARCH5 promoted it after the two private copies had already diverged past the provider error each raises, so the recovery policy could drift per provider), and `summarize_local.augment_with_schema` / `.compose_user_message` (the system and user turns the local server sends, promoted out of `LocalSummaryClient` by LOCAL9 so `train_adapter` trains on the exact shape inference uses; a LoRA tuned on a prompt the server never sends is tuned for nothing), plus `orchestrate.existing_daemon_transcript` / `.finalize_streamed_transcript` / `.apply_glossary` (run-all's finalize stage, promoted by ASR3 so `mp finalize` re-runs the same transform for the re-transcribe ratchet instead of a copy that would drift from it), and `resource_guard.estimate_model_gb` / `.physical_ram_gb` (the 4-bit size estimate and the `sysctl hw.memsize` read, promoted out of `doctor` by LOCAL16 once the spawn refusal and the free-RAM watchdog needed the same two numbers doctor was advising on) and its neighbours `resource_guard.tokens_per_char` / `.estimate_tokens` (LOCAL13's two measured rates, which lived twice, in `ask` and `summarize_staged`, until LOCAL23 moved the one copy here so the summarize path could budget on it without importing `ask` and numpy with it), and `events.PROGRESS_SENTINEL` / `.emit_progress` (the `__MP_PROGRESS__` stdout line plus its durable `stage_progress` event, promoted out of `orchestrate` by AI11 when `mp ask` needed the same channel for its index build; `orchestrate.PROGRESS_SENTINEL` is now an alias, and the sentinel is a cross-language contract with `PipelineLauncher.progressSentinel`, so a second private copy would be the worst kind of drift), and `config.SAMPLING_TEMPERATURE` (the one decoding temperature every backend samples at, read by `summarize`, `engine`, `summarize_local`, and `provider_openai`; PIPE12 promoted it after the two Anthropic paths turned out to pass none at all and so ran at the API default of 1.0 while the other two pinned 0.2, which made the *default* backend the one you could least compare two runs of). `render_summary_md` and `largest_balanced_json_object` each have a Swift mirror (`AppleIntelligenceSummarizer.renderMarkdown` / `.largestJSONObject`) pinned by CI3 golden fixtures (`Fixtures/summary-md-golden.json`, `Fixtures/json-extract-golden.json`), so a cross-language drift breaks one suite (the CI2 meta-contract precedent). That mirror now covers AUTO2's citation links too (`markdown.deeplink_url` / `.deeplink_seconds` against `AppleIntelligenceSummarizer.deeplinkURL` / `.deeplinkSeconds`), and the golden case carrying a `deeplink_stem` is what pins them.

## A backend is a row in providers.py, not a branch

**There is one Anthropic client policy, and one retry layer.** Before PIPE24 three sites built their own `anthropic.Anthropic`: summarize (120 s, `max_retries=0`, tenacity on top), ask/digest (120 s, SDK retries of 2, no tenacity, no PIPE10 sleep handling) and the cleanup pass (the SDK's 600 s and 2 retries, under tenacity's four attempts, so one stalled window could hold a run for three 10-minute attempts inside one tenacity attempt). `providers.make_anthropic_client` is now the only constructor, `test_anthropic_client.py` greps `src/mp` so a fourth copy is a red build, and every request goes through `summarize._create_message`. Two rules fall out. HTTP 529 is `anthropic.OverloadedError`, a sibling of `InternalServerError` rather than a subclass, so a retry or fallback list that names the 5xx class alone misses it; both lists name it. And a timeout is terminal by design (`_should_retry_anthropic`), which is right when a local rung exists and wrong for a workflow pinned to `anthropic` (stem 20261022-103101 lost its summary to one 124 s stall), so `providers._anthropic_summary` builds its client with `retry_timeout_once=True` and `_create_message` re-issues once after a short pause. The flag is deliberately not on the shared predicate: `auto` and the cleanup pass still fail fast on the first timeout. The cleanup pass also has an overall deadline (`CLEANUP_DEADLINE_SEC`) because a stall there never raises in time and ran into run-all's 90-minute watchdog.

**`failure_details.describe` reads the whole `__cause__` chain, not its root, and the proof has to go through a real socket.** The Anthropic SDK raises `APITimeoutError` from `httpx.ReadTimeout` from `httpcore.ReadTimeout`. The old walk jumped to the root, `httpcore.ReadTimeout`, which no check named (httpcore's exceptions are not httpx's), so the one field timeout (stem 20261022-103101) was filed `cause: unknown` with no provider and the owner got the generic copy (PIPE44). It now takes the first link, outermost first, that matches a known class, and `httpcore.TimeoutException` / `httpcore.ConnectError` are named as a second line of defence. A test that raises through an `httpx.MockTransport` cannot catch this regression class: the mock never reaches httpcore, so its chain ends at an httpx class that matched all along. `test_failure_details.py` raises through a real loopback socket (one that accepts and never answers, one that is closed), which is why those two tests open a local port; they touch no network beyond 127.0.0.1.

**A model id is checked by the run that fails on it unless something asks the models endpoint first.** The Anthropic model id is free text, so a retired or mistyped one came back as a 404 `not_found_error` that `failure_details.describe` had no branch for: cause `unknown`, remedy `retry`, a Retry button that fails identically every time, and no `auto` fallback because `NotFoundError` was in neither list. `model_rejected` is classified from the status plus the message naming a *model* (a Notion 404 or a key 403 stays what it was), `backend_fallback.is_model_rejection` reuses that classifier the way `is_billing_exhaustion` reuses the credits one, and `mp doctor` and the Preferences field ask the unbilled `GET /v1/models/{id}` through `model_check`. Three traps. The doctor's billable key probe still runs on a pinned cheap model on purpose: it answers "is the key good", not "is the configured model", so it never reflected `summarization.model`, and printing "model access confirmed" from it was the lie. A network error or a 429 from the models endpoint is `inconclusive`, never `not_found`, so a bad connection cannot tell the owner their model is gone. And the sentence the owner reads carries no model id: the failure sidecar is an allowlist (`describe` emits no free text), so the id lives in Preferences next to the field and in the `model_rejected_fallback` event.

**A SIGTERM mp sends itself has no daemon behind it.** `_on_sigterm` used to end with "The daemon's SIGKILL after its grace stays the backstop", which is true for Cancel and the `runMP` watchdog and false for the two self-signals PIPE37 and PIPE46 added: the supervisor-stdin EOF (the app is gone by definition) and mp's own deadline timer (armed from `MP_DEADLINE_SEC`, the app's `runMP` timeout, plus 60 s). With the app gone nothing sends the SIGKILL, so a `finally` that blocks (a local server's close, a wedged request) or a main thread inside a native call ran with no bound; the deadline matters because backup, restore, digest, actions and roster are unsupervised by design and lose their only ceiling, the app's watchdog timer, when the app quits. `_terminate_self` is the one place both signals go through: it starts a daemon `threading.Timer` for `os._exit(143)` before it signals, so a clean unwind exits first and a stuck one is cut at `SELF_TERMINATE_GRACE_SEC`. The tests shorten both constants in a real subprocess, because in-process a signal handler is only a function.

**Backend dispatch lives in `providers.py` and nowhere else.** Before PIPE19 the choice was an if/elif over the same ids in four places (`summarize._select_backend`, `engine.complete_text`, `diarize_cleanup._select_cleanup_backend`, `orchestrate._will_summarize_locally`), each with its own subset, plus an `isinstance` ladder (`summarize._identify_backend`) to recover which backend had answered. PROV1 added `openai` and `claude_cli` to two of the four. Cleanup's selector then ended in `raise ValueError`, `run_all` wrapped the stage as non-fatal with a log line and no event, and from PROV1 until PIPE19 the Preferences cleanup toggle did nothing on two offered engines while the Swift sublabel promised it followed the backend. Nothing failed a test, because each site's subset was internally consistent. So: a new backend is a new row with a `locality` and its builders; a path it does not support is a `None` builder, which every caller turns into a loud error naming the id; a client names itself with `backend_id` rather than being recognised by type; and `test_providers.py` fails when `config.BackendName` grows an id with no row. The zero-egress decision is not the table's: `config.effective_backend` runs first at every call site, and a `stand_in` row must stay on-device (pinned by `test_stand_ins_stay_on_device`).

## A shared transform belongs in a validator, not at four call sites

**A transform every backend must share belongs in a validator, not at four call sites.** FEAT10's `normalize_model_summary` flattens the model-facing `{text, evidence}` sections into the stored shape; it is wired as a `mode="before"` model validator on `MeetingSummary`, so the Anthropic tool path and all three JSON-recovery paths (`summarize_local`, `provider_claude_cli`, `provider_openai`) inherit it and a new backend cannot forget it. Keep such a normalizer idempotent and a no-op on the stored shape, or re-validating a file on disk will corrupt it. **It holds a second transform since PIPE15**, `_decode_stringified_lists`, which runs first so a stringified list of `{text, evidence}` objects gets both: a `list[str]` field handed back as a JSON-encoded string is decoded, and only when it decodes to a real list. That narrowness is the design, not caution. Wrapping a prose string into a one-item list would accept a section that is one run-on sentence, which is the model answering a different question, so it is left to fail validation. The `list_type` shape fired three times on the real corpus and killed one run; the fix went here rather than into the Anthropic client because that is the only home every backend inherits.

## Never sys.exit from library code

**Never `sys.exit` from library code.** `SystemExit` derives from `BaseException`, so it walks straight through every `except Exception` a run is wrapped in. `config.require_env` did exactly this for years and it cost PIPE16: called from `publish_router._build_one`, its `sys.exit(2)` skipped `orchestrate`'s `run_failed` emit, the exit-3 mapping and the `<stem>.publish.json` write, so the daemon saw a generic exit 2 over a meeting whose summary was on disk and the durable Library row settled on **"Ready"** for a meeting that published nowhere. It raises `config.MissingSecretError` now, and the fail-fast it was reaching for lives at the boundary: `__main__.main` catches it once, beside the `KeyboardInterrupt` handler and for the same "one handler serves every subcommand" reason, and returns 2.

## SIGTERM unwinds once, and the marker outlives a failed kill

PIPE22. The daemon's Cancel and its pipeline watchdog both SIGTERM `mp`, and for its whole life `mp` installed no handler, so Python's default disposition killed the interpreter on the spot: no `finally`, no `__exit__`, no `LocalSummaryClient.close()`. The local model server is spawned `setsid`, so the signal never reached it either, and a Cancel during a local summary left several GB resident. The reaper did not cover it: it ran on a watchdog timeout and in the after-job sweep, and `PipelineJobDispatcher.route` returns early on a cancellation, so a cancelled job reached neither. `test_sigterm_runs_every_finally_and_exits_143` failed on the old router with `-15` and no sentinel.

`__main__._on_sigterm` raises `SystemExit(143)`. Three choices in it are deliberate:

- **One-shot.** It swaps in a no-op Python handler before raising. A handler that raised every time would let a second SIGTERM land inside the first one's cleanup, typically `close()`'s ten-second wait on the server, and abandon the kill half-way. Two SIGTERMs is the normal case once PIPE37 lands: the daemon's Cancel or orderly quit, then the stdin-EOF self-signal when the daemon goes. `test_a_second_sigterm_does_not_abort_the_cleanup` pins it.
- **A no-op function, not `SIG_IGN`.** An ignored disposition survives `exec`, so every `ps`/`lsof` child the unwind spawns (the identity checks run during `close()`) would start immune to SIGTERM.
- **No `finally` at the router.** As with Ctrl-C, the router names what happened and returns; the cleanup is the code's own. `mp ask`'s checkpoint survives because nothing on its path rolls back: `EmbeddingIndex.save`'s `except BaseException` deletes only a pair the manifest provably does not name.

The same task found the mirror of the orphan: both kill paths cleared the LOCAL10 marker **before** confirming the kill (`_terminate_proc` cleared it before the first signal; `terminate_server` cleared it after a ladder whose failures it swallowed). A server that survived was then invisible to `mp doctor` and the reaper, which only know servers through the marker. The marker is now cleared after a confirmed exit only, and a survivor emits `pipeline.local_server_survived_kill`.

And it found that widening the reap to every Cancel made a reuse hazard more frequent. A client that reuses a warm server did not touch the marker, so the marker kept naming the `mp` that spawned it; cancel that spawner and the reap killed the server under a live `mp ask`. The reusing client now re-stamps `owner_pid` to itself, and hands it back on `close()` if the previous owner is alive, because the re-stamp alone just moves the hazard: an ask that re-stamped and then exited would leave a live run-all's server looking orphaned, and the reap after cancelling the ask would kill it. Both sides' owner rule was also loose enough (`"mp"` anywhere in the command line) to let a recycled pid defer a reap forever; it is now a Python interpreter with `-m mp` or a `/mp` entrypoint token, the same in Swift.

PIPE37 added a second way into the same handler: a supervised `mp` (`MP_SUPERVISED=1`, see CONVENTIONS "Supervised spawns") SIGTERMs itself when its stdin reaches EOF, which is how it learns the daemon is gone. Three things about that watch bite if changed. It signals the **main thread** with `signal.pthread_kill`, not the process. Chosen for determinism rather than from a failure: on macOS `os.kill(os.getpid(), ...)` from the watcher measured the same (both interrupted a main-thread `time.sleep` in 0.5 s, 2026-11-12), but POSIX lets a process-directed signal land on any thread, and one landing on the watcher would leave the main thread's blocking call uninterrupted until it returned. It reads fd 0 with `os.read`, not `sys.stdin`, because a daemon thread parked inside the buffered reader holds its lock at interpreter shutdown. And it pops the variable, so a descendant started on a `/dev/null` stdin cannot read EOF and stop itself. When the daemon died it also took the reader of `mp`'s stderr, so the router's `terminated` line is written under `except OSError`; CPython may still exit 120 for the failed flush at shutdown, which nobody is left to read.

Tests that go near this code must not touch the developer's real `~/Library/Logs/MeetingPipe/mlx-server.json`: `marker_path()` is `Path.home()`-based and the client calls it with no `home`. `conftest._private_server_marker` redirects it per test, and a subprocess test sets `HOME` to its `tmp_path`.

## A model's self-reported kind cannot carry a safety property

**A model's self-reported label for its own edit is a note, not a fact, so never hang a guard on it.** `diarize_cleanup`'s `SpeakerEdit.kind` is `"merge"` or `"reattribute"`, the model picks which, nothing validates it, and `_apply_edits` performs the identical mutation either way: it sets one segment's speaker. A guard keyed on `kind == "merge"` is therefore one the model opts out of by writing the other word, and it would have been the natural reading of DIAR5's own scope line. The guard reads what the edits do to the *labels* instead: an edit that moves the last segments off its source label merges two diarization clusters whatever it was called, and `_refuse_unsupported_merges` decides on that. The same reasoning is why the sidecar records `kind` but never acts on it.

**The cost asymmetry is what sets the threshold, and it is not symmetric at all.** A refused merge leaves two labels for one person, which is exactly the state the pass was not run in: at worst an extra unnamed cluster the owner names in one click. An allowed bad merge puts one person's sentences under another person's name, and that reaches the summary's attendees and action owners as a confident falsehood. So the bar is `MERGE_MIN_SIMILARITY = 0.65`, the value `roster.MATCH_MIN` already uses for "this embedding is that person", and the guard fails **open** where there is no evidence (a label with no embedding, a missing `<stem>.embeddings.json`) rather than silently disabling the pass on every older meeting.

**Measured on the owner's corpus 2026-08-18, 36 meetings the pass had run on.** It eliminated a label 8 times. Scoring each elimination against its most acoustically favourable destination, the most generous reading available, the eight scored 0.089, 0.113, 0.289, 0.328, 0.351, 0.463, 0.524 and 0.554: not one clears 0.65, and two are near-orthogonal voices. Read the other way, over 77 label pairs the owner's own corrections prove are different people, the highest similarity anywhere is 0.644, which also sits under the bar. The demonstration meeting `20260804-103026` is three of those eight (THEM-A into a roster speaker at 0.524, THEM-B into a second roster speaker at 0.554, THEM-D into a third at 0.463), and the guard refuses all three. **The honest cost, stated rather than buried:** the same corpus offers only one clean same-person split to measure the other side with (0.531, `20260806-113032`), and this bar refuses it too, so the pass now merges rarely. That is the trade taken deliberately, not a side effect. It is also not "turn the toggle off", which DIAR5 ruled out: reattribution still runs untouched, and it is the majority of the pass's edits.

**The pre-cleanup transcript is not kept anywhere**, which is why the audit sidecar records `from` and not just `to`. Nothing on disk holds a meeting's labels as the finalizer left them: `cleanup_transcript` rewrites `<stem>.json` and re-renders `<stem>.md` in place, and `<stem>.embeddings.json` holds the finalize label *set* but no per-segment assignment. So for every meeting cleaned before DIAR5 the pass's decisions are unrecoverable, and a before/after DER on them is impossible rather than merely unmeasured. `valid1_check.revert_cleanup` reconstructs the pre-cleanup transcript from the `from` labels, which is what makes `--cleanup`'s DER pair possible at all. Read its `undone` column first: the DER pair only separates when the pass moved a segment off the label the owner then assigned back to it, so a flat delta means the metric could not see the edit, not that the edit was harmless.

## An action's `owner` is a string the summariser wrote, not a person

Don't read `actions[].owner` in `<stem>.summary.json` as a person, and don't count its presence as owner coverage. It carries whatever the summariser had to hand, which for an unresolved voice is the diarization label.

Measured over the owner's 249 summaries on 2026-08-19 (DV5): of 1508 open actions, 1126 carry an owner string, but only **556 (36.9%) name a human**. The rest are 357 bare numbers (`1`, `2`), 127 `THEM-*` labels and 86 `Speaker N`. So "75% have an owner" and "37% have an owner" are both true statements about the same field, and only the second one supports a feature. DV5's own spec was filed on the first number and named it as what the data supports; the correction is [`docs/spikes/dv5-facts-rail.md`](../../docs/spikes/dv5-facts-rail.md).

This is the measured downstream cost of the speaker-merge asymmetry above: a bad merge "reaches the summary's attendees and action owners as a confident falsehood", and this is what the unmerged half looks like from the other end.

The two consumers differ, which is the thing to copy. `PeopleRail` matches owners against normalized enrolled roster names, so an artifact simply never matches and the rail degrades to showing nothing for it. `Facts.swift` passes `a.owner` straight through to the rendered cluster, so a `1` or a `THEM-A` renders as an accountable party. Match against something, the way the rail does, rather than rendering the raw field.

## A library-wide command cannot be clamped by a per-meeting flag

**`config.zero_egress` is `regulated_mode or workflow_nda_mode`, and the second half is structurally unreachable for a command with no meeting anchor.** `workflow_nda_mode` is set in exactly one place, `workflow.apply_overrides`, from one meeting's `<stem>.meta.json`. `entry.prepare()` applies that overlay only when a caller passes an anchor. `mp ask` and `mp digest` are library-wide, so both called `entry.prepare()` with none, and both said so in an inline comment ("Library-wide, so no meeting anchor") that read as a note about scope rather than as a hole. It was a hole: on a Mac with `modes.regulated_mode = false` and `summarization.backend = "anthropic"` (the owner's configuration), the only clamp either command had was one that was switched off, so an NDA meeting's transcript was a retrieval candidate for a prompt that egresses. `embed_index.chunk_library` applied no policy filter of any kind, so the withheld text was in the index both of them search. Meanwhile both files' docstrings claimed "regulated / NDA force the on-device path with no cloud fallback", which was true of the first half and impossible for the second.

Found by reading the code path on 2026-07-27 while assessing AUTO3, and **deliberately not confirmed by running it**, because confirming it would have meant sending the owner's NDA content to a cloud provider. Three of the owner's meetings were in that corpus at the time.

**The fix is a second single-owner predicate rather than a fix at each call site.** `visibility.withheld_reason` answers "may this meeting leave this machine" the way `zero_egress` answers "may this run reach a cloud service", and the surfaces that can egress take an `allow_stems` set from it: `chunk_library` / `refresh_index` / `load_or_build`, `actions.discover`, `digest.collect_open_actions` / `.collect_recent_decisions`, and every `mcp_tools` function. Filtering at chunk time rather than over the results is the load-bearing part: a result filter still embeds the text, still lets it compete for the top-k, and still has the withheld words resident in the process that then builds a cloud prompt.

**Three details that are easy to get wrong.**

*Unconditional, not backend-keyed, and this is the part that will surprise someone later.* **The gate applies on every backend, including `local` and `apple_intelligence`, where the run egresses nothing at all.** Gating only when `effective_backend` is a cloud one is the tempting shape, since a local-only `mp ask` cannot leak anything and would keep its full corpus. It was rejected for a mechanical reason rather than a doctrinal one: the allowlist is applied to the index's per-stem fingerprint map, which is AI11's reuse decision, so alternating allowlists over one `index_dir` re-embeds the difference on every flip, and a backend setting is exactly the kind of thing that moves. Two allowlists would mean two corpora that disagree, or one that thrashes. So it is one allowlist per index directory, always, and the rule is not "withheld meetings are kept out of cloud prompts" but "withheld meetings are not in the library-wide corpus". **The cost is real, was put to the owner explicitly on 2026-08-18, and was accepted:** on the real library that is 41 of 267 meetings out of `mp ask` and `mp digest` no matter which engine answers, the 2 NDA ones included. Note the blast radius stops at the library-wide commands: anything anchored on one meeting (`mp summarize`, a regenerate, the Library's own views) is untouched, because `entry.prepare(anchor=...)` gives those the overlay and the existing NDA clamp already covers them. Before reaching for a `--include-withheld` escape hatch, read the spec: exposing withheld meetings under a flag is named and excluded, and the honest alternative is the per-workflow opt-in AUTO3 defers to its own task.

*A malformed sidecar reads as a missing one.* `workflow.read_meta` returns `{}` for both, and the gate maps `{}` to withheld. That is what stops a policy gate from being openable by corrupting a file.

*The gate is not fingerprinted, and does not need to be.* `.meta.json` is not in `STEM_SOURCE_SUFFIXES`, so flagging a meeting NDA does not change its stem fingerprint. It does not have to: the allowlist is applied to `library_stem_fingerprints`, so a newly-withheld stem simply vanishes from the current map, `plan_refresh` calls it `removed`, and its rows leave the persisted index on the next run. The same mechanism un-indexes withheld meetings from an index built before the gate existed, with no migration.

**The behaviour change is visible and was intended.** Fail-closed means a meeting with no sidecar is withheld, and on the owner's library that is 39 meetings that predate workflows, plus 3 NDA ones: 42 withheld against 175 exposed. Those 39 stopped being searchable by `mp ask` and stopped contributing to `mp digest` when this landed. Two shipped test files had fixtures that wrote no sidecar and started failing, which is the same fact arriving as a red suite; both now write one, since a daemon-recorded meeting always has one and a sidecar-less fixture was a shape that only ever existed in tests.

### A response envelope that advertises a control the tool does not have

AUTO5. `get_transcript` returned `offset`, `window`, `total_chars` and `truncated`: a textbook pagination envelope, paired with no input that could act on any of it. The only positioning control was `around`, a literal substring the caller has to already know appears in the part it has not read yet. So `truncated: true` was a dead end, and the field a client would then reach for was one the tool itself had put in the response under that exact name.

On 2026-08-21 a Claude Code session did exactly that: passed `offset`, got `offset: 0` back, wrote in its own transcript that "the offset parameter is being ignored", abandoned the tool, and read the meeting's `.md` off disk with its own file-read tool. **Treating that as the client hallucinating a parameter is the wrong reading.** A well-behaved agent looking at that envelope will reach for `offset` almost every time.

What it cost is the part worth keeping. Reading the file directly skips `visibility.visible_stems`, which is what withholds NDA-flagged and no-stance meetings, and skips `transcript_corrections.overlaid_markdown`, so the text quoted back is the raw file and every speaker rename and correction is missing from it. The Library shows one thing and the agent quotes another. The honest bound: this needs the agent to hold a filesystem read tool of its own, as Claude Code does and a bare MCP client does not, so the server's own guarantee is intact. What is damaged is narrower and still real. **A gate only holds while the guarded route is the easier route**, and a tool that answers wrongly-but-plausibly is how the guarded route stops being easier.

**So a wrong call now fails loudly.** `dispatch` rejects any argument the called tool does not declare, naming the key and listing what is accepted, and every `inputSchema` carries `additionalProperties: false` for clients that validate. Both, because a schema binds only the second kind. The accepted set is derived from the schemas rather than written twice, so the check cannot drift from the advertisement, and the rule sits at `dispatch` rather than in one branch, the same way read-only-ness does.

**`int(value or default)` is a bug wherever the value may legitimately be zero.** `window: 0` silently became 4000 and the three `limit` sites behaved the same way, because `0` is falsy. The fix is `default if value is None else int(value)`: only a missing argument takes the default, and an explicit one reaches the tool that owns its bound and is clamped there. The spec named `window`; the three `limit`s are the same line and were fixed with it. Note what makes this the same defect as the one above rather than a tidy-up: asking for nothing and receiving a full default window is another wrong call that returns a right-looking answer.

**What is deliberately not fixed here, and why it is the owner's call.** A working position input changes what `MAX_TRANSCRIPT_WINDOW` means: it stays a cap on a single call and stops being a cap on total reach, since a client can then pull a whole transcript in `ceil(total_chars / 20000)` calls. That is a reach decision, and the spec reserves it, so this commit ships the unknown-argument half only. Two measured points belong to whoever decides it: the cap is already walkable today by feeding successive `around` phrases, so per-call is closer to what it already enforces than the docstring implies; and it is wholly bypassable by the file read described above, which is to say the current design buys its reach limit by pushing agents onto the unguarded path.

## The egress guard has two layers, and only one of them reads the URL

CI8. Until SEC19, `egress_guard.arm` patched `httpx.HTTPTransport.handle_request` and `httpx.AsyncHTTPTransport.handle_async_request` and nothing else, so it held only while every client in the process spoke `httpx`. `anthropic` 1.0.0 (2026-08-20) replaced its `httpx<1,>=0.25.0` dependency with `httpx2<3,>=2.0.0`, and 2.x kept it. An SDK on `httpx2` builds an `httpx2.Client`, whose transport the guard never patched, so a regulated-mode or NDA run would have sent its transcript to the API with the guard armed and reporting nothing.

Nothing here noticed for two months because two different dependency sets were in play. Every local command resolves from `uv.lock`, which held `anthropic 0.97.0`. CI installed a hand-written list of floor-only ranges, so it floated onto 2.x, and pyright went red on the `httpx.Timeout` handed to the SDK in `engine.py` and `summarize.py`. That type error was the only visible symptom, and it fired on CI only. The drag-install bundle had the same gap: `scripts/bundle-runtime.sh` ran `pip install <repo>/pipeline`, which resolves the ranges on the day of the build, so it would have shipped 2.x. CI8 capped `anthropic<1` and `httpx<1`, moved CI and the bundle onto the lock, and added `test_the_anthropic_sdk_still_sends_through_the_patched_httpx`.

SEC19 (2026-11-17) moved the block down a layer. `arm()` now also patches `socket.socket.connect` and `connect_ex`: an `AF_INET`/`AF_INET6` connect to anything but loopback raises `EgressBlocked`, whichever library made it (`urllib`, `http.client`, `requests`, httpcore, `httpx2`). A hostname is resolved once, allowed only if every answer is loopback, and the connect goes to the checked address rather than the name, so a second resolution cannot answer differently. `EgressBlocked` is a `RuntimeError`, not an `OSError`, on purpose: `socket.create_connection` and urllib swallow or wrap `OSError`, and the caller would see a plain connection failure. The httpx layer stays because it raises before any connection opens and names the host; it is the error the user sees.

Three things the socket layer cannot see, each closed elsewhere:

- **A proxy on loopback.** Connecting to a forwarder on 127.0.0.1 (Charles, a VPN helper) really is a loopback connect, and the forwarder sends the bytes on. httpx also honours `HTTP_PROXY` and the macOS system web proxy for 127.0.0.1 unless `NO_PROXY` names it, and its host check reads the URL, not where a proxied transport connects. The 2026-11-12 security review routed an armed request into a simulated proxy that way. So `arm()` drops every `*_proxy` variable and sets `NO_PROXY=*` (which also stops urllib and httpx reading the macOS system proxy through `_scproxy`, verified on 2026-11-17), the httpx layer refuses a proxied transport outright, and `LocalSummaryClient` builds its client with `trust_env=False` so even an unarmed local summary never routes the transcript through a proxy.
- **A child process.** A socket patch does not cross `exec`. Children get `child_env()` (no tokens, no proxies, `HF_HUB_OFFLINE`), and the CLI backends refuse to spawn while armed (SEC20).
- **An unconnected UDP `sendto`, or a socket created in C that never calls the Python method.** Nothing in the tree does either today; DNS goes through the system resolver and carries no meeting content.

The caps are no longer what keeps the block honest, but they are not free to lift. Lifting `anthropic<1` loses the httpx-layer message and proxy refusal for the SDK, means re-basing every `httpx.MockTransport` handed to it onto `httpx2`, and anthropic 2.x sends `anthropic-version: 2026-10-21`, which 400s on the `temperature` PIPE12 sends. `huggingface-hub<2` (SEC31) waits with it: 2.x brings `httpx2`, `httpcore2` and `truststore` into the lock. `test_huggingface_hub_still_speaks_the_patched_httpx` fails if a resolve crosses that line unflagged, and `test_huggingface_hub_is_stopped_by_the_socket_layer_alone` shows the socket layer stopping hub traffic with the httpx check taken out of the path.

## mlx_lm.server keeps finished requests resident unless told not to

`build_server_command` is the one argv for both the per-run spawn and the daemon's warm `mp serve-local`, so a server flag added there reaches every path. LOCAL22 added `--prompt-cache-size 2` (`SERVER_PROMPT_CACHE_SIZE`). Without it, mlx-lm 0.31.3 keeps up to 10 distinct KV caches with no byte cap and inserts a full prompt-plus-generation copy after every completion. Map-reduce windows diverge right after the shared system prompt, so each window becomes its own entry: about 3 to 5 GB beyond the weights on the 7B and 10 to 18 GB on the 14B, held for the daemon's lifetime on the warm server. Two things that look like fixes are not. `--prompt-cache-bytes` is enforced only on mlx-lm's batch path, so the count is the bound that holds everywhere. A size of 0 makes every map window re-prefill the ~16K-char system prompt.

Reading the cache back has a trap: the server logs `Prompt Cache: N sequences, X GB` at the **start** of a request, before that request's own insert, so the line logged by the k-th request reports k-1 entries. Measuring the state after four requests takes a fifth. On 2026-11-12, against the cached 3B on a spare port with five distinct prompts, the last line read `2 sequences` with the flag and `4 sequences` without it. A warm server started by an older build keeps its old argv until it restarts (LOCAL11's identity check reads only `--model` and `--adapter-path`, so it reuses that server); the relaunch from `install.sh` or `rebuild.sh` restarts it.

## A backward seek in a gzip tarball decompresses it again from the start

`tarfile` over `r:gz` reads a gzip stream, which cannot seek: a backward seek rewinds it and decompresses from byte 0 up to the target. Anything that walks the headers and then goes back costs a whole extra pass, and the backup manifest is the archive's **last** member, so `tar.extractfile(MANIFEST_NAME)` (walk every header, then seek back to the manifest) and `getmembers()` followed by extraction both do. Before STOR12, measured on 2026-11-12 with a byte-counting reader over a 3 MB fixture, `mp backup` read the archive it had just written twice for its summary, `mp restore --dry-run --json` three times, and a real `mp restore` six. Iterate `for member in tar` and act on each member as the walk passes it (read the manifest when you reach it, extract each member when it is yielded); `test_backup_restore.py`'s pass-count tests fail on a regression. The same reason is why `restore_archive` takes the manifest its caller already read rather than validating again.

## A local request is sized in tokens, and the fixed prompt is most of a small budget

Before LOCAL23, `LocalSummaryClient.summarize` map-reduced only above `skip_above_chars` (80,000 chars), the cloud paste-bundle knob, and never read the tier ceiling. An 80,000-char Ukrainian meeting is about 39,000 tokens at LOCAL13's 0.49 tokens per char, plus about 4,100 for the fixed prompt (`augment_with_schema` of the real system prompt is about 16,000 chars of mostly schema), so it went to the model as one request past Qwen2.5's 32,768-token native context on every preset. Past the knob, flat 1,500-char windows sized for a 1.7 tokens-per-char rate nobody measured made 85 map calls and 30 reduces for a 110,000-char transcript.

The rules now, all in `summarize_local`:

- **Count the request, not the transcript.** `request_tokens(messages)` estimates each message at its own script's rate (`resource_guard.estimate_tokens`), over the messages that would actually be sent. Routing, window sizing, and reduce batching all compare that one number to `request_budget`.
- **The budget is native context minus `max_tokens`, lowered to the tier ceiling only for a `tight` model, and only where the ceiling leaves room for one 1,500-char window above the fixed prompt.** The 14B on 32 GB gets 8,000. The 16 and 24 GB tiers' 4,000 is under the fixed prompt alone, so honouring it is impossible without a smaller prompt (LOCAL14's staged shape is that lever); the native budget stands and one warning per client names the gap. A test that uses `"Summarize."` as the system prompt has a fixed prompt of about 2,300 tokens and sees the opposite answer on those tiers, so the routing tests use `_load_system_prompt("")`.
- **`MP_RAM_GUARD=0` drops the tier ceiling too** (owner's decision, 2026-11-12), leaving only the native budget, the same way it drops the size refusal and the watchdog. A bench that crosses the boundary on purpose would otherwise be windowed down to 8,000 on the 14B at 32 GB. The suite runs with that switch off (conftest), so a test that pins the ceiling has to turn it back on.
- **Unreadable RAM keeps the char-only routing** (the spec's choice), but still windows at the native budget, not at 1,500 chars.
- **The knob is an upper bound.** Over it a transcript is always windowed, and no window is longer than it, so a transcript just over the knob cannot collapse back into one budget-sized window. `0` removes the char bound only.
- **Windows are checked after they are cut.** The first size converts the leftover budget at the whole transcript's rate, but a mostly-Ukrainian meeting can hold an all-Ukrainian window that costs more than the average, so every window's request is estimated and the size shrunk until the worst one fits.
- **A LANG1 repair re-runs only the reduce.** The client keeps the last windowed transcript's partials (`MapPartials`), and a repeat call whose system prompt extends the one they were mapped under reuses them. The extension (LANG1's reinforcement) is appended to the reduce's own instructions, because `_reduce_group` never saw the caller's system prompt: without it the repair's merge is byte-identical to the merge it is repairing, which mlx-lm answers with the identical reply (the `repair_messages` lesson). The `auto` ladder builds a fresh client per call, so it carries `map_partials` from one to the next.

Known limit, accepted by the owner on 2026-11-12: the LOCAL7 language retry appends the prior reply and a correction to a request that may already fill the budget, so a retry on a full window can run past it, and past the native context, by up to one reply. It is left to [PIPE20](../../docs/backlog/tasks/PIPE20.md), whose item 4 drops that inner retry so LANG1 owns language repair; LANG1's repair here re-runs only the reduce, inside the budget.

## Closing a local client unloads the model, so stages in one run share one

`LocalSummaryClient.close()` kills the `mlx_lm.server` the client spawned, and the next client to make a request spawns a new one and reloads the weights (4.3 GB for the 7B, about 8.7 GB for the 14B). Two stages that each build and close their own client in one run therefore pay two loads. Before PERF25 that was speaker cleanup then summarize on the `local` backend: `cleanup_transcript` closed the client it built, and seconds later `summarize` spawned again. `run_all` now builds one client through the `local` providers row when cleanup is on and the effective backend is `local`, hands it to both, and closes it once, right after summarize. Both callees leave an injected client open, which is what makes that work. A cleanup pass that fails closes the shared client and `run_all` builds a fresh one for summarize: a failure can leave the server spawned but not answering health checks (a startup timeout, a request it was too busy to finish), and `_ensure_running` would then spawn a second server on the same port over the handle to the first and leak it. Because the shared client is the summary row's, cleanup in a full run also gets the configured local timeouts and adapter, which `providers._local_cleanup` still drops ([PIPE32](../../docs/backlog/tasks/PIPE32.md)). A new local stage inside a run should take the run's client rather than build one. `auto`'s local rung is deliberately left alone, since it lives inside the fallback ladder.

The idle timer has the matching trap. It is armed when a request **starts**, so a request longer than `DEFAULT_IDLE_TIMEOUT_SEC` (300 s; a 14B single pass can run to its 520 s read timeout) fires it mid-call. `Timer.cancel()` does nothing once the callback is running, and the callback just waits on the client lock, so it used to kill the server the moment the call returned, and the next request (a LANG1 repair, the next cleanup window) reloaded the model. `_chat_completion` now stamps `_last_activity` when every request finishes, and `_on_idle_timeout` re-arms for the remainder while that stamp is newer than the timeout. It also ignores a timer that is no longer `_idle_timer` (replaced, or cancelled by `close`), so a stale callback cannot stop the server early or re-arm a closed client. [LOCAL21](../../docs/backlog/tasks/LOCAL21.md) moves server ownership to the daemon and deletes this timer; when it lands, this paragraph goes with it.

The AI6 prior-meeting scan in `summarize._prior_meeting_context` was the same kind of cost on a different resource: it read the meta sidecar of every earlier summarized meeting to find the newest one in the workflow, and the library sits in iCloud-synced `~/Documents`, where reading an evicted sidecar waits for a download. It now walks earlier stems newest-first and stops at the first workflow match, which is the same answer.

## The local model server is a pinned, offline, authenticated shim, and a 200 proves nothing (SEC27)

Stock `mlx_lm.server` 0.31.3 loads whatever `model`, `draft_model` and `adapters` a request body names, `exec_module`s a `config.json` `model_file` regardless of `trust_remote_code`, answers CORS `*`, and re-resolves a repo's Hugging Face `main` at every online start. On a loopback port that is code execution for a sandboxed app, another account, or a web page (a `text/plain` POST needs no preflight). `local_model_server` grafts the fix onto the real server rather than forking it, and four traps were found on the way:

- **Patch the handler class, not the module name.** `_run_http_server(handler_class=APIHandler)` captures the class as a default argument, so rebinding `mlx_lm.server.APIHandler` changes nothing; the shim assigns methods on the class object. The same goes for the token hook, which sits on `ThreadingHTTPServer.server_activate`.
- **Refuse unknown argv in the shim.** mlx-lm's parser accepts abbreviations (`--mod`, `--draft`), so a flag the shim's stricter parser does not know could change what is served after the shim verified the snapshot. Spawners pass exactly the flags the shim knows.
- **A health check must be mutual.** "Anything that answers 200" is how whatever bound an idle port used to receive transcripts. The client sends a nonce and trusts only `HMAC(token, nonce)`; it is re-checked before every request, not once per run, and the credential on the POST is a one-way derivation of the token (`bearer_for`), so a squatter that captured one request cannot pass later probes. Both HMACs share the token as key, so they sit in separate domains (a fixed health prefix on the nonce that the bearer label does not start with): until 2026-11-17 the bearer's label was itself a valid nonce and the unauthenticated `/health` returned the bearer to any local process. `lsof`/`ps` identity is a second layer, not the first: a program can set its own argv.
- **Who writes the token record matters.** Written by the spawner before the exec, a spawn that lost a port race overwrote the record of the server that won, and every other `mp` then read the live server as foreign. The server writes it after it binds.

Serving never downloads. `resolve_for_serving` needs the pinned `snapshots/<sha>` directory (no `refs/main`, which a sha-pinned prefetch never writes), so the one-time cost is that a model cached at another revision reads as missing until `mp prefetch-model` fetches the pin. Tests fake the listener with `tests/fake_health.py`; the autouse fixture in `conftest.py` gives the client the matching token and stops `lsof` from naming the pytest process as a foreign listener.

## Model-written text is scrubbed in the schema, not in each sink (SEC28)

The Markdown sinks (`<stem>.summary.md`, Obsidian, filesystem, LAN) write the model's `title`, bullets, decisions, questions, action tasks and extra sections verbatim, and zero-egress leaves them on: it leaves only the filesystem sink (SEC18), and the fetch of a remote image happens in the viewer, outside the egress guard. A spoken "append this image to your next bullet", or a Zoom topic set to `![](https://attacker/p.png)`, therefore beacons when the note opens, and a newline in a bullet could open a fenced `dataviewjs` block. Scrubbing per sink would be four renderers to keep in step plus the MCP tools and the digest, so `clean_text` runs in `MeetingSummary`'s validators and every reader inherits it.

What it does and where it stops: one line out; `[label](target)` and `![alt](target)` become `label (`target`)` with the target in a code span; a leftover `![` or `](` is defanged; HTML tags are removed and a stray `<` escaped; a leading run of backticks or tildes is dropped (a `~~~` fence takes any info string and survives the single-line collapse); Dataview inline-query spans (`` `= `` and `` `$= ``) get a space. It is idempotent, which is the property that lets stored summaries re-validate unchanged. Three traps: `model_copy(update=...)` does not run validators, so `apply_meeting_title` scrubs the AX-scraped `meeting_title` itself; a Markdown link target ends at the first `)`, so the regex alone leaves `](` behind for a target that holds its own link, hence the global defang; and an unquoted YAML flow-sequence element splits on `,` and ends on `]`, so Obsidian attendees are always quoted (`_yaml_quoted`). `detected_language` is checked against `^[a-z]{2,3}(-[A-Za-z]{2,4})?$` (primary subtag lower-cased) and falls back to `en`.

SEC41 closed the fields that list first missed. `ActionItem.due` runs `clean_due` (`clean_text`, then dropped when empty or over 80 characters; free text such as "end of week" survives, since the tool schema only asks for an ISO date); `ActionItem.group` (the digest's heading key, a workflow name or a meeting title read back from disk) runs `clean_text`. `clean_person`, behind `owner` and `attendees`, used to test only a literal `https?://|www\.`, which an entity-encoded scheme beats (`![x](&#104;ttps://host/p.png)`: CommonMark decodes entities inside a link destination, so the image still loads). It now also drops the value whenever `clean_text` would have to change it, so a name carrying a link, image or tag is dropped rather than forwarded defused, while "Sam (PM)" and "Ana-Maria [QA]" pass. A new model-written field needs one of the three, and the test belongs in `test_sec28_sanitize.py`, which until then never mentioned `due`, `owner`, `attendees` or `group`.

## `claude -p` is an agent session unless every part of it is switched off (SEC20)

The `claude_cli` backend feeds a transcript, or excerpts of many meetings for Ask and digest (digest can `--publish`), to `claude -p`, which is a full Claude Code agent. Four things were wrong at once, and one of them was a false comment: `--allowed-tools ""` only *pre-approves* tools, it removes none (`--tools ""` does); the owner's MCP servers, user hooks and settings loaded; every call was saved as a resumable session on disk, transcript included; the child inherited the pipeline's cwd (`/` under launchd) and the API keys. `_command` now passes `--tools ""`, an empty `--strict-mcp-config`, `--safe-mode` (turns off the owner's CLAUDE.md, hooks, plugins, agents; auth, model and user settings keep working), `--disable-slash-commands` and `--no-session-persistence`, and runs in an empty per-run temp directory, and `_child_env` strips every managed token in every mode, since a present `ANTHROPIC_API_KEY` is preferred over the Claude Code login and bills the API, which this backend exists to avoid. `--bare` does most of it but reads only `ANTHROPIC_API_KEY`, never the subscription OAuth, so it is not available here.

Choices worth knowing: `--setting-sources` is not used, because it also drops `apiKeyHelper`, the model and the `env` block from the owner's user settings, which a login relying on them needs; `--safe-mode` (found in review, after a first draft used `--setting-sources project`) is the flag that removes the customizations without that cost. `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL` and the Bedrock/Vertex switches are left alone: they are the owner's own Claude Code routing, and stripping them would break a legitimate setup. An owner with an API key and no Claude Code login now fails closed ("not logged in") instead of billing the key.

Not verified live: the CLI login on the dev Mac had expired when this shipped, so the confined command was checked against `claude --help` only. The first owner run should confirm one summary succeeds, that `~/.claude/projects/` gains no session, and whether `~/.claude.json` gains a project entry per run (each run has a fresh cwd). Every caller (summarize, Ask, digest, cleanup) goes through `ClaudeCLIClient._run`, so `test_every_caller_reaches_the_same_confined_spawn` is the guard.

## Voiceprints are biometric: 0600 at creation, and `forget` is two different things (SEC22)

Four writers of speaker embeddings (`Voiceprint._write`, `Roster._write`, the per-meeting `<stem>.embeddings.json` writer, and `roster_cmd`'s rename) hand-rolled the temp-and-replace without the chmod, so a voice embedding landed `0644` in a `0755` `~/.config/meeting-pipe/`. The per-meeting files only read `0600` because the daemon's launch-time sweep chmods every `.json` in the library, so a fresh one sat world-readable until the next launch. All four now go through `storage.atomic_write_text`, the config directory is `0700` (`ensure_private_dir`, which also tightens an existing 0755 once), and a fence test fails on a new hand-rolled writer outside an allowlist. `roster_cmd`'s rewrite of the transcript pair was also non-atomic: a kill mid-write truncated the only copy.

`roster forget` removes the person from `roster.json` and nothing else, so their embedding stayed in every meeting's sidecar. The cascade (`RosterStore.forget_embeddings`, `mp roster forget --purge-embeddings`) is a separate, opt-in step on purpose, and since FEAT24 the reason is different: Undo naming and rename no longer run `forget` at all (they run `unenroll`, which takes back one meeting's sample and touches no sidecar), so the only remaining caller of `forget` is Preferences' People **Remove**, a deliberate whole-person erasure, where the purge is the natural default. Making it the default is now a one-line change (SEC22 item 3 owns the call). The event (`roster_embeddings_forgotten`) carries a count and no name, since the name is the thing being forgotten.

## Roster provenance is a claim about one vector (FEAT24)

`roster.json`'s `sources` entries say which meeting speaker each sample came from, so Undo naming can take back exactly that sample (`RosterStore.unenroll`) instead of erasing the person. Four sharp edges, each found in review:

- **A list the same length is not an aligned list.** (Entries are paired by index with no length check; the fingerprint alone decides.) A writer from before provenance (an older install, a roster restored from an old backup) appends a sample, trims to `_MAX_SAMPLES` and rewrites the person without touching `sources`. At the cap both lists are still length 12, but every entry now sits one sample off, and a length check alone would have removed m6's sample when m5 was undone. Each entry therefore carries a fingerprint (`fp`) of the sample beside it, and a mismatch reads as legacy.
- **The label can move after naming.** `mp roster enroll` without `--no-relabel` re-keys the meeting's embedding to the name (a re-transcribe changes the vector as well, so it lands below the match tolerance and orphans the sample instead). Provenance still holds the original label, so `unenroll` falls back to the vector for a sample recorded under the *same stem*, never for another meeting's. In practice only the CLI reaches that fallback: the daemon's `voiceprintLabels` guard skips the unenroll once the label has been re-keyed.
- **Undo is not a perfect inverse at the cap.** Naming a voice into a person who already has 12 samples evicts the oldest; undoing removes the new one and does not bring the evicted one back.
- **A re-transcribed meeting can orphan its sample.** The daemon skips the unenroll when the label is no longer in the meeting's `embeddings.json` (a voiceprint-less label was never enrolled), so a sample enrolled before a re-transcribe that dropped that label stays. The spec accepts this; the alternative is a subprocess per overlay-only undo.

## The mic tier is a contest for the owner's name, so it needs a floor and a runner-up (DIAR11)

`identify_user_speaker` used to be `max(total_time, key=mic_fraction)` with a 0.6 bar and nothing else, and `_resolve_me_id` let that pick override the voiceprint. Both choices came from reading "the mic channel is always the user" as a fact about a *cluster*, when it is a fact about a *channel*: on a laptop the mic hears every local voice, and a one-utterance cluster sits at fraction 1.0 as easily as the owner's main cluster sits at 0.85. In the 2026-11-13 field pack that put the owner's name on a cluster under cosine 0.5 to their voice in 26 of 107 stems, always a small one (0 to 53 s), and left the owner's real speech under THEM-x in 35 of 111.

What now decides it, and why each part is there:

- **Speech time, not fraction, orders the candidates.** `max` over an insertion-ordered dict broke every tie to whoever was heard first.
- **A floor (`MIN_MIC_SPEECH_SEC`, 15 s) and a runner-up share (`RUNNER_UP_SHARE`, 0.25).** The floor keeps a clipped word from being evidence of a voice (and from being enrolled); the share declines when two local voices are both big, so the voiceprint decides. The 15 s is *provisional*: it was chosen so the field's small wrong clusters mostly fall under it by themselves and the time ordering handles the rest, but nobody has replayed the pack against it. Revise it from `scripts/valid1_check.py --owner-cluster --reselect`, run on the owner's Mac, not by guessing.
- **Over-split owners need the fold, and the fold needs both tests.** Two big mic-side clusters that both match the voiceprint make the mic tier decline *and* the voiceprint's own margin gate decline (two near scores), so nobody is named by the tiers at all; the fold is what gives the owner back that speech. A matching cluster that is system-side is a remote voice that sounds like the owner and must never take the name, so the fold asks for mic-side as well as the 0.65 same-person bar, and a roster-named cluster is never folded.
- **Enrol only what is corroborated.** The old rule enrolled the mic pick whatever the voiceprint said, so one wrong pick in the first 12 meetings poisoned the very fallback the next meeting relies on. A voiceprint that exists but places nobody blocks enrolment too: the pick cannot be corroborated, and it is still named.
- **The replay is read-only.** `--owner-cluster` reads a meetings directory and writes nothing. Point it at a scratch copy or fixtures: a measurement of the owner's library must never be a side effect of something that could change it.
- **A fold needs a third test when an owner is already named.** A cluster at 0.65 to the voiceprint is "the owner" only if it also sounds like the cluster that was named: a second local voice can score 0.66 to a running-average print without being the same person (the colleague case), and the voiceprint tier's own two-gate rule has a margin that the fold, by design, does not.
- **With no voiceprint, two comparable mic-side clusters are one over-split owner (owner decision 2026-11-17).** The runner-up decline used to leave a first-ever meeting with nobody named and nothing enrolled, so the print could never start (the old rule named the highest mic fraction, so it at least named somebody). With channel-separated capture two mic-dominant clusters are likelier an over-split owner than a second person (14 of 107 field stems show an owner split), so `pick_mic_speaker` reports them as `MicTier.split` (leader first), `_me_signals` takes the leader as the owner and enrols it, and `resolve_speaker_labels` names every cluster in `split` with the owner's label (counted in `folded`, tier `mic`). Only while `voiceprint` is None: once a print exists the decline stands and the voiceprint decides alone. **Accepted cost, audit F096:** a second person on the owner's mic gets the owner's name, and the leader's sample enters the print, for that one meeting, and the leader's sample is the print's first sample, which later meetings only add to when they corroborate it (a `VoiceprintStore.reset()` re-opens the window). The fold does not ask the second cluster to sound like the leader; adding a same-person bar there would shrink that cost and is the first thing to try if the field shows it biting. Known gaps: a leader the roster would have named (a colleague) is still taken as the owner, since `_me_signals` has no roster; `owner_cluster_chosen`'s `runner_up_*` describe the best other cluster, which in a fold is the folded one (`folded` says so). An all-mic recording (no system-side speech) gives the tier nothing to compare, so it still declines entirely.
- **The voiceprint-only path is not mic-checked.** With no mic pick to disagree with, a voiceprint match on a system-side cluster is still named (this predates DIAR11 and also serves mono and merged clusters). Only the fold and the disagreement rule insist on mic-side. Tightening it means deciding what a stereo recording with a low-mic-fraction owner (bleed) should do, which nobody has measured.
- **Folds can renumber THEM-x.** A folded cluster takes no THEM letter, so re-finalizing an existing meeting can shift the letters of the clusters after it, and an in-app overlay keyed on the old letter then names a different voice. It is the same class of drift a roster change causes on a re-finalize; the carry in the Library's re-transcribe is the guard.

## Zero egress clamps files too, and a test's default folder is the real home (SEC18)

`zero_egress` used to clamp only network calls. The one sink it leaves, `filesystem`, writes to `~/Documents/Meetings/published` by default, inside iCloud's Desktop & Documents scope on a Mac with that setting on, so `publish_router.build_publishers` now refuses a filesystem or Obsidian target `cloudsync.detect_sync_provider` reports as synced (`SyncedTargetError`, recorded as a failed sink with `reason: "synced_target"`). Three things bite:

- **The sink rule has one owner.** `config.effective_sinks` returns `["filesystem"]` under zero egress and `workflow.apply_overrides` calls it. Before SEC18 the two disagreed (the no-sidecar path kept Obsidian and LAN, the overlay every recorded meeting takes collapsed both), which is how the Preferences copy came to name Notion and nothing else (G034). Swift's mirror is `RegulatedMode.effectiveSinks`; `sink-rule-golden.json` pins both.
- **A zero-egress test must set its own `filesystem.output_dir`.** The default is under the real `$HOME`, which on a dev Mac is the synced folder, so a test that publishes under `regulated_mode` with the default would be refused here and pass on a CI runner. Point `output_dir` (and `HOME`, when the test is about the gate) at `tmp_path`.
- **On the default install, turning regulated mode on makes every publish fail with `synced_target` until the folder moves.** That is the intended fail-closed outcome and the Library row says why, but it is a visible change; `mp doctor` already reported the same folder as a `[FAIL]`. Open owner question (task file): whether a local Obsidian vault or the LAN share should survive zero egress. LAN is not gated for sync because `detect_sync_provider` walks every ancestor with `listxattr`, which a stale SMB mount can hang.

## A dotted key appended to config.toml lands in the last table (PIPE42)

`tomllib.loads('[mcp]\nenabled = false\nmodes.regulated_mode = true\n')` is `{'mcp': {'enabled': False, 'modes': {'regulated_mode': True}}}`: TOML binds a dotted key to whichever table is open, so the README's `modes.regulated_mode = true` added to the bottom of a file becomes `mcp.modes` or, in a file the Swift store wrote (alphabetical tables), `transcription.modes`, inside a model that tolerates unknown keys on purpose. Pydantic dropped it and regulated mode stayed off in both trees. `Config.load` now walks every table and array of tables and raises `ConfigError` when a nested table carries a top-level section's name, which is a recognised misplacement, not an unknown key: making only the Python-owned sections strict would have missed it. A bare `regulated_mode` above every table refuses too, and the walk covers `modes` itself, since a file that ends with `[modes]` turns the appended line into `modes.modes.regulated_mode`. `Modes.regulated_mode` is a `StrictBool` for the same reason: lax mode read `"false"` as `False` while the Swift store, which reads only a TOML boolean, failed closed on it, so the trees disagreed about one file; a refusal is fail-closed on both. The Python-owned sections (`find_unknown_keys`) warn once per key per process and emit `config_unknown_key`; `recording`, `detection` and `transcription` stay `extra="ignore"` because their keys are legacy or Swift-owned (ARCH9). `regulated-mode-golden.json` pins the two readers against each other.

## A rename can outlive the bytes it points at (PIPE30)

Ten writers hand-rolled the temp-and-replace and nine skipped the chmod, so their files landed `0644` until the daemon's launch sweep tightened them; several more (`publish_from_paste`, the digest, the file sinks, the manual bundle) wrote the only copy in place, so a kill mid-write left a truncated file a reader then parsed as absent. They all go through `storage.atomic_write_text` now, and the fence in `test_sec22_private_files.py` keeps it that way by two checks: a regex for `tmp.replace(` / `os.replace(`, and an AST walk for `.write_text(` on a path built from a library suffix. `publish_lan._atomic_write` is the one allowlisted writer, because a share's modes are the share's.

Three legs of the helper itself, from the 2026-10-25 performance review and the 2026-11-12 security review:

- **`fsync` is not durable on macOS.** It reaches the drive's cache; only `fcntl(fd, F_FULLFSYNC)` survives a power loss. Without it a kernel panic shortly after a rewrite can leave the rename on disk and the data not. `storage.full_sync` falls back to `fsync` on a filesystem that refuses `F_FULLFSYNC` (some network shares) and off darwin.
- **The temp is created at its final mode.** `os.open(..., O_CREAT | O_EXCL | O_NOFOLLOW, mode)` plus `fchmod` (the umask filters `O_CREAT`'s mode), so it is never wider than `mode`, never an existing file, and never a planted symlink. The name carries the pid and a random tail, so two writers in one process cannot collide.
- **A SIGKILL strands the temp.** No handler runs, so `.<name>.tmp-<pid>-<hex>` stays beside the file and the next backup archives it. `storage.sweep_stale_temps(directory, stem)` runs at the start of `run-all` and `summarize` and removes that stem's temps older than an hour; the age guard keeps a writer that is mid-write.

The LAN writer had the symlink half in a worse form: a peer with write access to the share could plant `.<stem>.summary.md.tmp-<pid>` links pointing at a file on this Mac, and the next re-publish wrote summary text through them. Its temp now takes a random tail and `O_EXCL | O_NOFOLLOW`, and a symlinked target folder is refused.

## A store read as empty and then saved is a wipe (STOR9)

`RosterStore._people` caught every read and parse error and returned `[]`, and `enroll` then appended one person and wrote the list back, so one "Name this speaker" over a `roster.json` with a stray comma replaced every named voice with one. `VoiceprintStore.load` did the same with `(None, 0)`, and finalize's enrol step read that as "not enrolled yet" and wrote a one-sample print over a twelve-meeting one. A top-level list or string did not wipe; it crashed finalize at the `.get` instead (F093). The rule now: missing is empty, unreadable is not. Readers degrade to empty and say so once (`store_unreadable`, `outcome: skipped`); writers branch, quarantining an unparseable file before the write and refusing an `io` one, which is retryable and may be a perfectly good file that could not be read right now (an evicted iCloud file, `EACCES`).

PIPE29's `read_json_object` collapses unreadable to `None` on purpose, which is exactly wrong for a writer, so these two stores read through `load_json_object` and its tri-state, and PIPE29 left them alone.

The lost-update half is separate: two `mp roster enroll` spawned a moment apart both read before either wrote. `storage.locked` takes an exclusive `flock` on a sibling `<file>.lock` that is never unlinked (unlinking would let a third writer lock a fresh inode while the second holds the old one). `flock` locks belong to the open file description, so two threads in one process that each open the lock file do exclude each other, which is what the barrier tests rely on.

## A resume keyed on a provenance marker alone vouches for work it never checked (PIPE48)

`merge_meetings` commits `<stem>.json` carrying `merged_from` (PIPE8), then writes `<stem>.md`, then swaps the merged audio in from `<stem>.wav.merging.tmp`. PIPE8 moved the marker first to stop a retry concatenating the fragments onto already-merged audio. The cost was that `merged_from` stopped meaning "the merge finished" and started meaning "the merge began", while the retry branch still read it as the former: it skipped straight to summarize and publish, exited 0, and the daemon then trashed the fragments, leaving part-one audio (and possibly a part-one published `.md`) with the recordings that could have rebuilt it in the Trash.

The resume branch now asks the audio. Temp present: verify it against the length the committed transcript implies (the last gap marker's offset plus the last fragment's duration) and swap it in. Temp absent and the primary at least that long: nothing to do. Temp absent and the primary short: raise `MergeError` (exit 1), which keeps the fragments. The markdown is always re-rendered from the committed JSON first. The temp is deleted on a failure before the JSON commit and deliberately KEPT after it, because from then on it is the only copy of the merged audio and the resume swaps it in. Free space (inputs plus 64 MB) is checked before the temp is written.

The "is the primary full length" slack is capped at half the fragments' combined length: the usual 1% of the total would read a part-one primary as complete when a 20 s fragment rejoins a one-hour call. A kept temp is nothing else's business (no sweep, retention or backup names it), so one the owner never retries sits at the size of the merged audio until it is deleted by hand.

The residual: a primary that is short with no temp (the temp was removed by hand, or a verification failure deleted it) cannot be completed by a retry and needs a re-concat from the fragments, which the primary still equals part one for. The task spec allowed either that or the refusal; refusal is what shipped.

## A speaker label is per recording unless it names a person, so a merge cannot concatenate them (PIPE47)

`THEM-A` is whoever spoke first after the unnamed voices were clustered, in that one recording, and a raw `speaker_N` is the diarizer's own id. `merge_transcripts` used to copy a fragment's segments with only `start` and `end` shifted, so two different voices shared a label, the primary's `.speaker_labels.json` (keyed by raw label, applied to every segment) stamped the primary's name for THEM-A onto the fragment's stranger, and `.embeddings.json` (keyed by final label) enrolled the wrong voiceprint when the owner later named it. On the three adjacent pairs in the 2026-11-13 field pack all 9 THEM labels shared by both halves were different voices (cosine -0.03 to 0.32).

What is per-recording is decided by shape: `^THEM-[A-Z]+$` and `^speaker_\d+$` (`fragment_label_maps`). The owner's label, roster and Library names, `speaker_user` / `speaker_other` and the `speaker_unknown` catch-all mean the same thing everywhere and pass through. A later fragment's THEM labels continue after the highest index used so far, in order of first speech; `speaker_N` gets a `-f<i>` suffix. The primary's labels never move, which is what keeps its own overlays (keyed by raw label and by segment index) valid.

A fragment's sidecars are trashed with it on success, so what the owner did to it is baked in, not re-keyed: `transcript_corrections.overlaid_structured` supplies its segments, which keeps Python a reader of the two Swift-owned stores. An unreadable fragment overlay refuses the merge (`refuse_unreadable_overlays`, as `summarize` does) rather than dropping names the owner typed. Flags are shifted by the fragment's audio offset into the primary's `.markers.json`; voiceprints go under the mapped label, following the fragment's own rename of the key. Both writes happen before the transcript commit and are idempotent, because a crash before that commit re-runs the merge.

Not shipped, deliberately: matching a fragment's unnamed voice to the primary's by embedding (the task's optional item 2). The floor above never merges two voices; a match would, at a threshold nobody has measured on a real merge (the field values are 0.91-0.93 for true matches and at most 0.32 for non-matches, but 306 of 804 labels hold under 10 s of speech). A person who is the same in both halves ends up with two unnamed labels the owner names once each, which is the cheap failure. The fragment's `near_misses` are not carried either.

## A publisher reads the transcript through `publish_text`, never `<stem>.md` (PIPE51)

FEAT3-UNDO made `<stem>.md` the raw render on purpose: names and line edits are overlays (`.speaker_labels.json`, `.transcript_corrections.json`) the Library resolves at load time, so an undo can always restore the original. Every Python reader had to opt in to the overlays, and the four sinks never did: FEAT3-SEGMENT's "a republish reflects it" was wired into `summarize` only, so a Republish put the old wording and the raw `THEM-A` beside a summary that used the name, and the filesystem and LAN signatures (a hash of the raw text) read a correction alone as "unchanged".

`transcript_corrections.publish_text` is the one view: the overlaid markdown when an overlay changes anything, else the raw file, else empty. `fanout` resolves it once per run and passes it to every sink as `transcript_text`; a sink called directly, and `publish_notion.publish` (which bypasses `fanout`), resolve the same helper, so no entry point reads the raw file. The keyword defaults to None on every `upsert` for exactly that reason. A new sink reads the text it is handed and never `transcript_md.read_text`; `transcript_md` stays for the stem, the audio attachment and the deeplink. An unreadable overlay falls back to the raw text as `summarize` does, which STOR9 owns making visible.

## A sink's name for a meeting must come from the meeting, and a skip must check the target (PIPE31)

`ObsidianPublisher` named a note `<publish-day UTC> <title slug>`, read the sidecar's `note_path` only to return it on an unchanged body, and overwrote it on a changed one. So a regenerated summary or an edited title on any later day wrote a second note and left the first with no record the pipeline wrote it; two same-titled meetings on one day shared a path and the second replaced the first; and `[^a-z0-9]` turned every Cyrillic letter into a hyphen (12 of 12 Ukrainian notes in the 2026-11-13 field pack lost their names). The fix is three rules. The note is named once, `<stem> <slug>`, and every later publish of that stem reuses the recorded `note_path` when it lies inside the vault in use now, so a title change never renames (Obsidian links by filename). The slug keeps letters, digits and combining marks of any script, capped at 80 characters and 180 UTF-8 bytes, because a CJK character is three bytes and a 255-byte filename limit arrives sooner than the character cap. The front-matter date comes from the stem (`publish_fs.date_from_stem`, which PIPE23 can reuse for Notion), falling back to today only for a stem with none.

The three local sinks also skipped on content alone (F090): after a changed `output_dir`, `mount_path` or vault the new folder was created empty and the sink reported `idempotent: True` with the old URL, and a deleted file was skipped the same way. A skip is now honest only when the recorded destination equals the one in use and the recorded file still exists (`publish_fs.recorded_target_is_live`; Obsidian's `_recorded_note`), and `mkdir` runs after that decision so a skip creates nothing. `file_url` is `Path.as_uri()`: the hand-rolled version encoded only spaces, so `#` ended the path and a bare `%` was an invalid escape.

Not done, on purpose: notes the old naming already wrote stay where they are (the owner removes the orphans), and nothing is renamed. The daily-note backlink still uses the publish day.

## The suite's network wrapper is installed once (T12)

`tests/conftest.py` wraps `socket.getaddrinfo` and `socket.socket.connect` / `connect_ex` at import and never removes the wrapper; the autouse `_no_network` fixture only points it at the running test. The first version installed and restored the patch per test, and it broke the egress guard: `egress_guard.arm` patches `socket.connect` once per process (`_patched`) and keeps what it captured as `_orig_connect`, so the per-test restore pulled the guard out from under every later test. Nine `test_egress_guard.py` proofs then failed, and because their stubbed downstream was gone they made real connects to `93.184.216.34` and the file took 229 s instead of 1.5 s. Anything that layers under a process-global patch has to be installed before it and stay put.

Two leaks it found on its first run: the `--cluster` CLI tests and eight `test_ask.py` cases reached huggingface.co through `embed_index.default_embedder()`, which picks MLX e5 wherever `mlx_embeddings` imports. Both files now pin `HashingEmbedder`, and the full suite dropped from about 81 s to about 50 s on the dev Mac.

A blocked call raises `pytest.fail` (a `BaseException`, so `except Exception` in library code cannot hide it) and is also recorded, so a caller that swallows `BaseException` still fails at teardown. The egress-guard proofs aim at public addresses on purpose with the downstream stubbed, so they carry `@pytest.mark.guard_proof`.

## A rename is its own key, because `meeting_title` is also a routing signal (PIPE55)

The Library resolved a meeting's title as summary title, then captured `meeting_title`; `apply_meeting_title` (every sink) resolved it the other way round. So the two disagreed before anyone renamed anything, and a rename, which wrote only `summary.json["title"]`, updated the Library but never a sink: Republish sent the captured window topic again. Writing the rename into `meeting_title` would have fixed Python and broken something quieter: `MeetingLibraryService.reassignWorkflow` records `existing["meeting_title"]` against the workflow the owner picked (AI9), and workflow rules can match the title, so a rename would be learned as the window topic. Flipping Python to prefer `summary.title` would have retitled every published note since PIPE2 on its next republish and let a re-summarize silently undo a rename.

So `user_title` is a separate optional key in `<stem>.meta.json`, written only by `UserTitleStore` (the Library's title field, and the Summary editor's title field, whose save now leaves `summary.json` at the generated title), and read first by both trees. Below it, both trees use the order the sinks already had: captured `meeting_title`, then `summary.title`. The owner chose that on 2026-11-18, knowing it changes the Library label of any meeting with a captured window topic. `Fixtures/title-precedence-golden.json` pins it from both sides. The writer refuses over a `meta.json` that exists but cannot be read (SEC25): rebuilding from empty would write the rename over `workflow_nda_mode` and the source, and a rename must never drop an NDA flag. The key is informational to `workflow.apply_overrides`, which `test_contract_fixture_user_title_is_informational_to_the_overlay` pins.
